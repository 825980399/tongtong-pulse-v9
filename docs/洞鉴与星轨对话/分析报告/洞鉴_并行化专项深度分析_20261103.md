## 〇、结论摘要（先看这段）

### 0.1 一句话

**曈曈现在不是"CPU 打满"，是"CPU 闲着但关键线程被拖住"。** 单核占用约 34%（整机 16 核的 2.1%），RSS 4.17GB 稳态不再涨；但 **L1 实时池被一个本该异步的全库代码扫描周期性占用（单次 10.6 秒，是正常值的 20-100 倍）**，而这件事之所以发生，是因为"延迟线程只在启动窗口内启动"的闸——启动窗口一过，设计好的异步路径就永久失效，退回同步执行。

### 0.2 五个池的真实尺寸（预算 vs 实际）

| 池 | 预算（thread_budget 上限） | 代码创建时用的值 | **实测线程数** | 判定 |
|---|---|---|---|---|
| L0 生命线 | 1 | 1 | **1** | ✅ |
| L1 实时 | 6 | **8**（`max(4, cpu//2)`） | **8** | ❌ 超 2，且**配置项被忽略** |
| L2 认知 | 6 | 8（读配置） | **8** | ❌ 超 2 |
| L3 自动化 | 4 | 4（`max(2, cpu//4)`） | 0（懒创建） | ⚠️ 配置项被忽略 |
| Adaptive | 4 | 4 | 0（懒创建） | ✅ |
| HybridIO | 8 | 8 | 0（懒创建） | ⚠️ 事实未启用 |
| cortex_parallel | 8 | 8 | **4** | ✅ |
| struct_parallel | 6 | 16 | **6** | ✅ 收敛有效 |
| 其余 9 个预算池 | — | — | **0** | ❌ 表与实际不符 |

**★ 关键 bug：分层池的"预算收敛"只改了日志，没改池。**
`InfoField.__init__` 先用未收敛的原始值把 4 个池建出来了（[InfoField.py:514-535](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/field/InfoField.py#L514-L535)），之后才调用 `apply_minimums` 把**局部变量**改小（[InfoField.py:542-554](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/field/InfoField.py#L542-L554)）。日志打印的是被改小的值，池子里跑的仍是 8 个线程。活体证据：py-spy 抓到 `L1-RealTime_0 … L1-RealTime_7` 共 8 条、`L2-Cognitive_0 … _7` 共 8 条。

### 0.3 线程总量：Python 82 / OS 178，差 96

| 口径 | 数值 | 来源 |
|---|---|---|
| Python 活跃线程 | **82** | py-spy dump / health_snapshot.threads.n=81 |
| OS 线程 | **178-182** | psutil.num_threads() |
| **未登记原生线程** | **≈96-100** | 差值；py-spy `--native` 同样只列出 83 条 ⇒ 这 96 条**不是 Python 线程** |
| 其中 CPU>20s 的原生线程 | **约 10 条**（最高 64s） | psutil.threads() 逐 tid 统计 |

结论：这 96 条是 **ONNX Runtime / fastembed 的原生计算线程池**（`VectorEncoder` 用 `TextEmbedding(threads=2)`，但 ORT 的 intra-op 池按核数起线程），不是线程泄漏。**问题在于 thread_budget 只统计 Python `threading.enumerate()`，天然看不见这 96 条**——所以"线程预算 58"这个数字对真实 OS 线程量没有约束力。

### 0.4 业务常驻 49 条 > 池 worker 33 条

预算模块的前提是"线程大头是池 worker"，但实测反过来：

| 类别 | 数量 |
|---|---|
| 池 worker（L0/L1/L2/cortex/struct/Hybrid 监控等） | 33 |
| **业务常驻（Thread-N 未命名 9、2 个 HTTP `serve_forever`、2 个未命名 ThreadPoolExecutor、语音监听、Playwright、双腿、动机循环等）** | **49** |

所以"总预算 58 < 60"这个账只是**池子那本账**，另外 49 条从来没有被任何预算表管过。

### 0.5 重活落在哪

py-spy 采样（两次 20-25s）抓到的 CPU 归属：

| 叶子函数 | 占比 | 属于 |
|---|---|---|
| `_iterdir` | **32.0%** | 代码审计目录遍历 |
| `_detect_dead_code` | **29.0%** | 代码审计死代码检测 |
| `_parse_methods` | **13.1%** | `ast.parse` |
| `_parse_classes` | 4.9% | `ast.parse` |
| `AcceptWaveform` | 27.6% | 语音监听（thread 6920，累计 CPU 185s，全进程最高） |
| `copy2` + `_keep_backup` + `safe_write_json` | **≈11%** | 备份链写盘 |
| `virtual_memory` | 2.6% | psutil 内存采样 |
| `safe_read_json` + `raw_decode` | 3.1% | JSON 读 |

**并且 `_detect_dead_code` / `_iterdir` 的采样栈根是 `L1-RealTime_5`** —— 一个本该只做低延迟脉冲的实时线程。

## 三、队列与调度

### 3.1 四层队列压测

| 层 | 设计 | 实测 | 判定 |
|---|---|---|---|
| L0 | 单线程 + 8s 超时 + watchdog 0.5s | 无超时日志 | ✅ 健康 |
| L0 看门狗 | 超时后重建池 | 历史 2 条"看门狗"记录，归类为 `logging_io` | ⚠️ 卡点在**日志写盘**，不是业务慢（见 3.3） |
| L1 | 队列 1000 / 水位 0.9 / 8 线程 | 无拒绝、无水位告警 | ⚠️ 队列本身不堵，但**被长任务占线程** |
| L2 | 队列 300 / 超限丢低优先级 | 无拒绝 | ✅ 未饱和 |
| L3 | 硬限 200 | 懒创建未用 | ⚠️ 基本空转 |
| EventBus | 队列 1000，单 worker | 启动即 subs=0 / queue=0 / delivered=0 | ⚠️ 事实未承载业务事件 |

### 3.2 优先级实际生效情况

**部分生效**。L2 有明确的"超限丢低优先级"逻辑，但 L1/L3 没有优先级——`ThreadPoolExecutor` 是 FIFO，提交顺序即执行顺序。所谓"L0 生命线优先"靠的是**独立池 + 独立线程**，不是队列优先级。

### 3.3 日志是全进程的单点串行

[logger.py:993](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/logger.py#L993) 用的是**全局共享的 `SafeRotatingFileHandler`，同步写、无 `QueueHandler`/`QueueListener`**（handler 类见 [logger.py:555](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/logger.py#L555)）。后果：

- 每条日志都要抢同一个 handler 锁并落盘；线程越多，串行化越明显
- 历史 L0 看门狗卡死点被自诊断归类为 `logging_io`，与"日志同步写盘"完全吻合
- 这也是 py-spy 里大量线程停在 `logging`/`write` 的原因之一

### 3.4 一个"永远为真"的队列告警

[m363_diag_bridge.py:142](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/m363_diag_bridge.py#L142)：

```python
out["queue_alarm"] = {"alarm": bool(_bus.m360_check_queue_alarm())}
```

`m360_check_queue_alarm()` 返回的是**dict**，`bool(dict)` 对任何非空字典恒为 `True`。于是诊断日志里 `队列告警=True` 在 queue=0 时也照打（现场日志每 3 分钟一条，持续 1.6 小时）。真告警因此被淹没。

## 四、并行化机会清单

> 前提校正：整机 16 核、单核占用 34%，**CPU 不是瓶颈**。收益主要来自**消除阻塞**（IO 等待、锁串行、长任务占线程），而不是"多开线程算得快"。GIL 也决定了纯 Python 计算多线程不加分。

| # | 机会 | 现状证据 | 收益估算 | 风险 | 优先级 |
|---|---|---|---|---|---|
| **A** | **代码学习同步扫描移出 L1** | `PulseCodeLearner` 触发时日志 `延迟线程未启动（outside_startup_window）⇒ 走原同步扫描` **7 次**；正常批次 100-500ms，扫描批次 **10656ms**；py-spy 栈根 `L1-RealTime_5` 正在 `_detect_dead_code`/`_iterdir` | L1 实时池不再被占 10s+；周期性卡顿消失；削平 CPU 尖峰（采样中该扫描占 **61%**） | 低（改为 `force=True` 或放宽启动窗口即可，异步线程本身已实现） | **P0** |
| **B** | **日志改 QueueHandler + QueueListener** | [logger.py:993](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/logger.py#L993)，全库无 `QueueHandler` | 日志调用从"抢锁+落盘"降为入队；消除线程串行点；L0 看门狗 `logging_io` 卡点消失 | 低（标准库现成，注意停机 flush） | **P0** |
| **C** | **备份链收紧** | `backup=True` 默认；`copy2` 6.4% CPU | 写放大 4× → 1×（只对关键小文件保留 1 代） | 中（丢一代回滚能力） | P1 |
| **D** | **pair trim 改增量** | `readlines()` 全读 + 全量重写；trim.bak 144MB | 峰值内存与 IO 减半；消除分钟级写停顿 | 中（需保证追加语义） | P1 |
| **E** | **AST 扫描加 mtime/hash 缓存** | `_parse_methods` 13.1% + `_parse_classes` 4.9%；`[方法体定位] 355 次/秒` | 只扫变更文件，扫描从 10.6s → 预计 <1s（本次变更率约 5%） | 低 | P1 |

| **G** | **ONNX/BLAS 线程数与 Python 池相乘** | 96 条原生线程，约 10 条高 CPU；`threads=2` 未必被 ORT 采纳 | 限制过度订阅，减少上下文切换 | 低 | P2 |
| **H** | **快照写盘增量** | 771MB 全量重写（读侧已切 parquet，写侧仍全量） | 单次保存从秒级降到毫秒级 | 中高（格式变更） | P2 |
| **I** | **队列水位出口** | `get_backpressure_stats` 零调用 | 有观测才能谈调优 | 低 | P2 |

### 4.1 不推荐并行化的地方（已确认瓶颈不在此）

| 对象 | 理由 |
|---|---|
| L0 生命线 | 1 线程是**设计**（保序 + 保命）；加线程会破坏事件顺序 |
| `PulseCore` 脉冲派发 | 已按器官并行，且实测未饱和（无拒绝） |
| 向量检索 | ORT 原生线程已在使用多核；再叠 Python 线程只会增加切换 |
| 快照序列化（内存侧） | 属 CPU 密集 Python 代码，GIL 下多线程无收益，应进程化或改格式 |

## 五、分阶段建议

### 保守路线（先做，低风险，1 周内）

1. **A：把周期性代码审视的 `force=True` 打开**（或在运行期允许异步起步）。
   —— 单点改动，收益最大：直接消掉 L1 上 10s+ 的同步扫描。
2. **B：日志换 QueueHandler/QueueListener**。
   —— 消除全进程日志串行点，同时把 L0 看门狗的历史卡点（`logging_io`）根治。
3. **E：AST 扫描按 mtime 增量**。
   —— 把 10.6s 的扫描降一个数量级（与 A 叠加后几乎不可感知）。
4. **I：把 `get_backpressure_stats()` 接进 health_snapshot**，同批修掉 `bool(dict)` 的假告警。
5. **修预算收敛顺序**：先算 cap、再建池；让 `l1_threads/l3_threads` 真正被读取。

保守路线预期：CPU 峰值削平、L1 卡顿消失、写放大可控、队列可观测。**不改任何架构语义**。

### 激进路线（保守路线验证后，2-4 周）

1. **C+D**：备份链改为"关键文件 1 代 + 异步落备份"；pair 文件改分片追加，trim 只做分片轮换（不再全量重写）。
2. **F**：定义"同器官串行、跨器官并行"的显式并发模型（替代 `organ_max_concurrent_pulses=0` 的隐式无上限）。
3. **H**：快照写盘改增量（与现有 parquet 读路径对齐），并清理 771MB 全量文件的历史 `.bak`。
4. **G**：固定 ORT intra-op 线程（如 4），避免与 Python 池 8 线程相乘。
5. **进程化 CPU 密集扫描**：把"代码审计/死代码检测"整体放进独立子进程（目前已有 `pid=32548` 的子进程扫描，可统一为唯一路径），彻底隔离 GIL 与 IO。

### 验收口径（建议写进下一批任务书）

| 指标 | 现状 | 目标 |
|---|---|---|
| L1 长任务（>1s）次数 | 约每 30 分钟 1 次（10.6s） | **0** |
