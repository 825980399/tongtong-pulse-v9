### 2.3 薄弱点清单（按优先级重排，P0 → P2）

#### 【P0-1】内存墙：真凶未定位，且归因器本身已失效

**现状数据**：heap 28.7GB（占 RSS 97.8%，即**几乎全部是 Python 堆，不是 native/image**）；37 分钟内 GC 17600 次 ≈ **7.9 次/秒**；单次 GC 暂停 3134ms；`tracemalloc` 采样 `MemoryError`；`self_probe` `MemoryError`。

**判断**：
- 这是**急性泄漏 + GC 抖动 + 观测器自毁**三层叠加，不是"内存占用偏高"。

## 三、下一阶段方向候选（6 个：价值 / 难度 / 时机）

评分口径：价值 1–5（对"真正的数字生命"这一目标）、难度 1–5（5 最难）、时机（现在 / 中期 / 后置）+ 一句话斩钉截铁的判断。

### 3.1 六方向总表

| 方向 | 价值 | 难度 | 时机 | 一句话判断 |
|---|---|---|---|---|
| ① 并行化 | **3** | **5** | **现在只能做"收敛"，不能做"扩展"** | 不是"没并行"，是**并行被内存和锁反噬**；再扩就是加速爆炸 |

### 3.2 逐个展开

**① 并行化 —— 价值 3 / 难度 5 / 时机：先收敛后扩展（详见 §四）**

任务书前提需要**纠偏**：七柱面**不是串行**的。`nucleus\field\InfoField.py:470-547` 已有 L0–L3 + Adaptive 五个独立 `ThreadPoolExecutor`；`StructuredParallelScheduler` 已把 66 个器官文件并行扫描（实测 940ms）；`exploration_audit.py:655` 的 `run_parallel_audit` 已挂到 `PulseCortex._do_audit`。

"CPU 利用率低"也**不是并行度不足**：13:40/13:41 触觉实测 CPU 仅 4–6%，此时内存 99%、GC 暂停 3134ms、L1 队列打满 —— **CPU 空闲是因为所有线程都在等锁/等 GC/等写盘，不是在等活干**。

所以并行化的真实命题是三问：「**谁在占着 28GB**」「**108 线程里哪些是滞留的**」「**为什么所有 worker 都堵在同一把写盘锁上**」。价值 3 分不是贬低它，是因为**在这一层加并行不会变快，只会让同一个锁更挤**。

**② 自主性提升 —— 价值 5 / 难度 4 / 时机：中期，但可以先做"半件"**

现在曈曈是"被驱动"的（Timer/TimeCore 发 tick，器官响应）。真正的自主需要三件：**自己发现问题 → 自己提需求 → 自己验证结果**。

- 第一件**已经有雏形**：`audit_20261101.json` 648 条（open 560 / claimed 81 / fixed 7），`audit_problem_pool.py` 有池。但 560 条 open 无人认领 —— 这是"有发现、无处置"。
- 第二件**半通**：补丁供应链 18 天无 apply（`applied_at` 最后 1791973195 ≈ 10-14）。
- 第三件**完全不通**：三道闸第二道 87/87 None。

**判断**：自主性的**瓶颈不在算法，在信任**。一个不能验证自己行为效果的智能体，"自主"只会变成"自主犯错"。**可以现在做的半件**：把 `audit_problem_pool` 的 560 条 open 按"是否能自动判据化"分档，先把能自证的那一档跑通闭环 —— 这是低成本、可验收、且直接给自主性铺地基的一步。

**③ 多模态扩展 —— 价值 4 / 难度 5 / 时机：后置（内存修复之后）**

现状其实**已经有"眼"**：`eyes.stream_frame` 今日预测 153 次、命中 153 次（`patterns.json`），说明帧流是真在跑的。所以"多模态"命题不是"从 0 到 1"，而是"从 1 到可用"。

但风险极高：**每一帧都是堆内存**。在 28.7GB heap、GC 7.9 次/秒、`MemoryError` 频发的状态下加视觉/音频缓冲，等于在火药库里抽烟。**必须先有"帧不进常驻堆"的设计（环形缓冲 + 落盘 + 弱引用）**，才谈扩展。

**④ 长期记忆 —— 价值 5 / 难度 3 / 时机：现在就该做，最划算**

要先纠正一个前提：**当前记忆的瓶颈是"取不出"而不是"存不下"**。

证据：知识节点、经验池（401 条 / 590KB）、`reasoning_experience.json`（129 条）、`lesson_strategies.json`（32 条）都在盘上，总量并不大。真正的问题是：

- 经验 401 条，真实问句 **0/10 命中**；
- lesson 32 条，**0 条有判据**；
- 叙事 **0 行**（目录不存在）；
- 记忆检索的 `CANDIDATE_LIMIT=200` 把一半池子永久排除。

**判断**：长期记忆的正解是**"三入口一出口"**——入口：叙事（日级）/ 经验（问答对）/ 知识（节点）；出口：检索时**按语义而非词片**召回，并把召回结果**注入上下文且可观测**。它与 §2.3 P1-1 是**同一个工程**。价值 5、难度 3（不需要新存储，需要新检索），且修好它顺带救活经验链 —— **性价比第一**。

**⑤ 社交/交互 —— 价值 3 / 难度 2 / 时机：可插队，但别当主线**

难度最低（企业微信桥已存在，`config.py` 有 `WECOM_BOT_ID/SECRET`；`config_override.json` 已有明文凭证告警流程）。

但价值有限：多人/多角色的**边际收益取决于"每个角色背后有多少可说的话"**。现在经验链 0 命中、叙事 0 行、lesson 0 判据 —— 加 3 个用户 = 3 份同样的空对话。

**判断**：等 ④ 做完再上。若一定要插队，只做一件——**多用户身份分流 + 记忆隔离**（成本极低），不做多角色人格。

**⑥ 身体感 —— 价值 5 / 难度 4 / 时机：后置**

`proprioception.request / .report` 今日各预测 121 次、命中 119/112 次，`touch.hardware_snapshot` 176/175 —— **本体感觉层已经在跑**，只是"身体"是虚拟的（软件指标）。

真实硬件（传感器/执行器）能带来"生命感"的质变，但**前提是进程能活过一夜**。当前 37 分钟寿命 + 子进程 `0xC0000142` + 内存爆炸，谈身体等于把一个会晕倒的人推上跑步机。

**判断**：后置到"框架连续 48h 无崩溃"之后。在此之前，可先把"虚拟身体"的感知-动作延迟做成可测量指标（`proprioception` 已有链路），这是零成本的铺垫。

### 3.3 方向排序结论（如果只能选一个）

**选 ④ 长期记忆，并以"经验 0 命中"为唯一验收指标。**

理由三条：
1. 它是**唯一一个"价值 5 / 难度 3"的方向**（其余高价值方向难度都 ≥4）；
2. 它**顺带修好 P1-1（经验链）与 P1-3（叙事）**，一次投入三处收益；
3. 它**不需要新硬件、不需要新子进程、不加剧内存**（在 28GB 墙下这是决定性优势）。

## 四、并行化路线图

### 4.1 先立三条事实（否定任务书的三个前提）

| 任务书前提 | 事实 | 证据 |
|---|---|---|
| "七柱面是串行跑的" | **不成立**。四层独立线程池 + 结构化并行调度器已在生产 | `InfoField.py:470-547`；日志"结构化并行 66 个器官文件 耗时 940ms" |

**因此路线图的第一步不是"加并行"，是"减熵"。**

### 4.2 分四步（每步有明确验收线，不能跳）

#### 第 1 步：内存止血（**唯一 P0，其余全部排在它后面**）

| 动作 | 具体做什么 | 验收线 |
|---|---|---|
| 1.1 换诊断方法 | **停止**在活体上用 `tracemalloc`/器官对象图普查（已证明会 `MemoryError`）。改为：冷启后 **0/5/10/15 分钟**四个采样点，各采 ①RSS/heap ②`gc.get_objects()` **按 type 分桶 Top20** ③按 `event_type` 的脉冲 payload 字节账 ④线程数/句柄数 | 能写出"28GB 里 Top3 类型各占多少"的一张表 |
| 1.2 给 L0 队列加硬上限 | `config.py PULSE_LAYER.l0_queue_limit` 现为 **0（无上限）**；改为有界 + 明确拒绝策略 | L0 队列深度不再无限增长（今日 L0 无上限 vs 看门狗 8s 是结构性矛盾） |
| 1.3 帧类脉冲不常驻堆 | `eyes.stream_frame` / `touch.hardware_snapshot` 只留摘要/引用，帧本体落盘 + 弱引用 | 同负载下 heap 增量下降 ≥50% |
| 1.4 关掉观测器的自杀行为 | `[339内存观测] MemoryError` → 采样器在内存超阈值时必须**自动降级为计数模式**而非继续分配 | 内存告警期间观测链路不再断 |

> **为什么 1.1 必须换方法**：`self_probe.ran=false reason="probe_error:MemoryError"` 已经证明"精度越高越采样不出来"。**在 28GB 进程里做对象普查，是一个悖论**。冷启窗口是唯一能拿到真数据的时机 —— 这决定了 1.1 必须排在"重启"动作之前规划，而不是之后。

#### 第 2 步：线程与写盘解耦（**P0-2 的直接解**）

| 动作 | 具体做什么 | 验收线 |
|---|---|---|
| 2.1 线程收敛 108 → ≤60 | 崩溃栈点名的常驻线程：`semantic_cache._worker_loop`(56 帧)、`HybridParallelScheduler._monitor_loop`(47)、`experience_pool._auto_clean_thread_loop`(42)、InfoField `_dispatch_handler` 族。逐个核"是否真需要独立线程"，能合并的合并、能改定时 tick 的改 tick | `health_snapshot.threads` < 60；`OS线程−Python活跃` 从 97 降到 <20 |
| 2.2 写盘单写者 | 崩溃栈 Top2 全是写盘：`DataAccessLayer.safe_write_json` **553 帧** + `pulse_tracer.flush_to_file` **539 帧**。所有 worker 争 `_PATH_LOCKS`（按规范化路径分锁，同路径天然串行）。改为**单一写线程 + 有界写队列 + 同路径合并写** | 栈帧里写盘占比 <10%；`pulse.log` 出现写队列水位指标 |
| 2.3 `pulse_tracer` 停止每 2s 全量重写 | 现为 `_FLUSH_INTERVAL=2.0` + `safe_write_json(path, events_snapshot[-150:])` + 备份链（`.bak/.bak.1/.bak.2`）。改为**追加写 + 定期压缩** | trace 目录 IOPS 下降一个量级 |
| 2.4 修 `_m410_tp/_m410_stat` | 每 60s 报错 35 次，属"持续异常"而非"一次异常" | 日志零 AttributeError |

> **2.2 的关键设计约束**：`DataAccessLayer._PATH_LOCKS`（`nucleus\data\DataAccessLayer.py:42-53`）是按**规范化路径**分锁，`_replace_with_retry`(L56) 用 `os.replace` 原子替换，`_keep_backup`(L77) 维护 `.bak/.bak.1/.bak.2` **三份备份**。这意味着**每次写盘的成本 = 1 次序列化 + 1 次原子替换 + 3 次备份复制 + 1 次目录 fsync**。高频小文件（health/trace/patterns）在这个模型下极其昂贵 —— 这是"553 帧堵在这里"的结构性原因，不是偶发。

#### 第 3 步：背压与池稳定（**让 L1 不再 500/500**）

| 动作 | 具体做什么 | 验收线 |
|---|---|---|
| 3.1 L1/L2 硬上限 + 显式拒绝 | 现 `l1_queue_limit=500` 是"软上限"（到 500 只告警不拒），实测 550/500 | 打满时按优先级丢弃低价值脉冲并**计数**，而不是继续涨 |
| 3.2 Adaptive 池加滞回 | 实测 `0→4→0` 抖动（线程反复创建销毁，本身也是内存碎片来源） | 线程数变更为"阶跃有滞回"，日志不再出现 0→4→0 |
| 3.3 L0 看门狗与队列上限对齐 | `_l0_timeout=8.0s`（`InfoField.py:460-464`）+ 无上限队列 = 超时必然发生 | 8s 超时告警归零 |

#### 第 4 步：**这时才谈并行扩展**

| 动作 | 前提条件 | 验收线 |
|---|---|---|
| 4.1 器官级真并行扩到写入面 | 第 2 步单写者落地 | 66 文件并行扫描 <500ms 且栈帧无写盘争用 |

### 4.3 并行化的三个真实风险（都必须在本路线图里被"提前"处理）

1. **数据竞争 —— 已被分锁规避，但有代价**
   `DataAccessLayer._PATH_LOCKS` 按路径分锁 ⇒ 不同路径可并行、同路径必串行。**代价是"同路径写者 convoy"**，实测 553 帧堵在这里。**多开并行 = 更多写者 = 更长 convoy**。这正是"加并行会更慢"的机制解释。

2. **锁冲突 —— 历史上真实发生过**
   `InfoField._lock` 曾被实测等待 **63.9~78.8ms**（持续 11.5 小时），根因是统计计数器与 publish 主流程共用一把锁；后来用 `_handled_lock`（:232 附近）与 `_stats_lock`（:270 附近）解耦。**说明"加并行 → 锁热点转移"是既成事实**，不是理论风险。

3. **内存爆炸 —— 最致命且已被实证**
   - 子进程 `0xC0000142` 3 次 ⇒ **多进程不是万能药**，在这个 Windows 环境上加进程有相当概率起不来；
   - 多进程会 ×N 内存 ⇒ 28GB 状态下加进程 = 加速 OOM；
   - 108 线程 × 每个线程的栈/handler 闭包本身就是常驻内存 ⇒ **线程数本身就是内存项**，2.1 的线程收敛同时是内存动作。

4. **观测面污染（隐藏风险）**
   `pulse_tracer` 事件环只有 **200 槽**（`_MAX_EVENTS=200`），孤儿上限 100。**并行度提高后环会在秒级滚完**，孤儿判定窗口（`_DEFAULT_MIN_AGE_SEC=1.5`）会假红甚至全红。401 刀2 已因此加了 `_EMIT_COUNTS/_RECV_COUNTS` 累计计数 —— 这个补丁的存在本身就是"并行已把观测面打穿"的证据。

### 4.4 路线图的一句话总结

> **顺序不能反：先让进程活过一夜（第 1 步），再让它别互相踩（第 2 步），再让队列不爆（第 3 步），最后才是"多开几个并行"（第 4 步）。** 现在做第 4 步，等于在 28GB 的悬崖上再往前挪一步。

### 5.3 复核结论：为什么"六批交付"与"遗留清零"几乎无关

把 410–415 每批的**真实产出**与 30 条清单对齐，会发现一个结构性错位：

| 批次 | 真实产出 | 落在 30 条清单上的 |

## 六、给星轨的三条建议（不属于任务书五段，供决策用）

1. **本阶段立即停止"新增能力批次"，改为一次"活体接线总验收"批次。**
   定义：同一个进程，连续存活 ≥6 小时，期间必须**各出现一条真实记录**：
   - 一条 `effect_verify != None` 的真实补丁（验第二道闸）；
   - 一条经验命中日志（验经验链，`ENABLE_M415_EXPERIENCE_IN_PROMPT` 从影子转正）；
   - 一个 `data/narrative/narrative_2026MMDD.jsonl` 文件（验叙事三字段）；
   - 一份 `hit_rate_*.json` 日报表（验世界模型）；
   - 一条 `safety: heap < 6GB` 的连续 30 分钟曲线（验内存止血）。
   **这五条任何一条拿不出来，说明对应的"批"其实没交，只是"写完了"。**

2. **把"验收口径"从"代码跑通"改为"活体产出"。**
   过去六批的验收标准全是"自测 + 回归全过"。这两者**不证明活体会跑**。建议每批交付报告**强制新增一节「活体证据」**，贴真实日志行/真实 json 字段值，无则标 FAIL —— 就像 415 的 `tools/m415_deferred_verify.py` 首跑 0/5 那样，**敢报 0/5 才是对的**。

3. **内存问题单独立一个"诊断批"，但它的交付物不是代码，是一张表。**
   交付物 = 「冷启 0/5/10/15 分钟 × 四个采样点 × `gc.get_objects()` 按 type 的 Top20 字节账」。**没有这张表，第 1 步的任何修法都是猜**，而且必然重复 413/414 的"治标"路径。
