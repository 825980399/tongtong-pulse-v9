### #1 自我愿景一成不变 —— 成立·双卡死实证

**现象链（一手日志）**：
```
同一句愿景主题反复生成：
19:10:58 / 19:27:47 / 19:29:43 / 19:33:27  均="我注意到「代码」是我的知识盲区，准备通过搜索和阅读来填补这个空白"
19:13:23 / 19:16:15 / 19:34:45              均="技术架构 基础 概念 原理"
19:22:07 两条："关于「代码」，我需要更多的一手资料..." + "我计划集中加强「代码」领域的学习——当前有1个相关节点..."
   ↓ 每条都被同一规则拦掉
[双腿学习治理] 跳过重复主题: <同一句> ≈ 已学习 <同一句>
```

**机制根因（源码级）**：
- [PulseInnerWorld.py:6824](file:///d:/xinrenlei/tongtong-pulse-v9/organs/brain/PulseInnerWorld.py#L6824) 规则=`价值观TOP1={_top_val}——自我愿景的核心基调由排名第一的价值观决定，当前愿景方向围绕'{_top_val}'展开`
- **但 `_top_val` 的来源是正则从问题文本里抠的**：[PulseInnerWorld.py:6605](file:///d:/xinrenlei/tongtong-pulse-v9/organs/brain/PulseInnerWorld.py#L6605) `re.search(r'价值观\s*(?:TOP)?(\d+)\s*[:：]?\s*(\S+?)(?:[、，,;\s]|$)', question)`
- **这不是从价值观系统/成长记忆动态读取**，是从输入文本提取字面量 ⇒ 愿景基调的"输入面"实际只有**问题文本**一个源

**双重卡死机制**：
| 环节 | 行为 | 结果 |
|---|---|---|
| 生成侧 | 同一价值观锚点+无成长记忆输入 → 产出同一主题 | 主题恒同 |
| 治理侧规则A | `跳过重复主题`（已学习集合比对） | 拦掉重复 |
| 治理侧规则B | `抽象表述拦截…取消` | 拦掉笼统表述 |
| **交互** | A拦→下一轮生成仍是同一句→再被A拦 | **闭环死锁，零新学习** |

**影响面**：愿景维度**完全静止**（12分钟内12次跳过，0次新学习）。这不是"愿景慢"，是**愿景学习通路被规则关闭**。
**处置方向**：治A不治B无效——必须先解决"生成侧无新输入"（价值观演化/成长记忆/外部反馈三源任一接入），否则解A会让同一句重复流入学习。

### #4 GIL 并行（七柱并行下深研）—— 成立·结构性限制已确证

**一手证据**：
- 并行度=12（`并行审查完成: 共662个问题 (高0/中43/低619) 并行度=12`）
- **全仓线程池、零进程池**：[InfoField.py](file:///d:/xinrenlei/tongtong-pulse-v9/nucleus/field/InfoField.py#L443) L443/449/455/461（L0-L3四层）+L467（自适应池）+L708+L1456，**七处全 `ThreadPoolExecutor`**；grep `ProcessPoolExecutor` 在 nucleus 面**零命中**
- `subagent_runner` dry_run 拦截本窗累计=38（执行通道半闭）

**GIL 影响判定**：
| 任务类型 | GIL 影响 | 现状 |
|---|---|---|
| I/O 密集（网络/文件/等待） | 无影响，线程池最优 | ✅ 当前选择正确 |
| CPU 密集（AST解析/审查/编译） | **串行化，并行度12≠12倍** | ❌ 662审查、AST扫描正是这一类 |
| 长周期任务（子进程已隔离） | 不受 GIL 影响 | ✅ SafeEvolutionExecutor 子进程模式正确 |

**结论**：**并行底座是线程的，适合 I/O；但审查/扫描这类 CPU 密集负载被 GIL 锁成串行**。"并行度12"对 CPU 负载是**名义并行**。这正是 #4 的真实痛点。
**与"周期性任务子进程+脉冲回主进程+InfoField接入"方案的结构评估**：
- 可行性**高**：SafeEvolutionExecutor 已有子进程模式先例（`子进程完成: mode=review...pid=36412`），模式可复用
- 关键约束：**子进程结果回主进程必须走 InfoField 消息（不能直接改内存态）**，否则等于绕过脉冲总线
- 风险：进程间序列化成本 + 每进程独立内存（RSS 会升）——需与 #A 内存面联动评估

| "先让曈曈正确发现问题"的判据建议 | ①**问题池落盘后可抽样**才谈误报率；②`placeholder_alias`这类"结构性误报"应由**入库口拦截**（不是事后标记）；③区分 `code_defect`（真缺陷）/`scan_noise`（扫描噪音）/`data_pollution`（数据污染）三类，不同类走不同出口 |

### 2.4 数据利用优先级（用户问题6核心）

**用户问：我们只根据运行数据分析问题，曈曈自己发现的要不要重视、怎么重视？**

**洞鉴判定：必须重视，且当前是"浪费了最稀缺的自发现能力"。**

理由（证据支撑）：
1. **曈曈的自发现质量不低**：18:15:18 那条反思（tool_search 6.6s→推理路径过复杂→先快规则）是**运行日志分析者（我们）看不到的**——它是**从内部体验出发的自我诊断**，与外部日志分析互补（外部看现象，内部看动机）
2. **但产出全废**：662零落盘、回流无下游、修复无通道 ⇒ **内部视角的自发现在系统里没有出口**
3. **外部 vs 内部的分工建议**：
   - 外部（星轨/洞鉴/烛微）：判"系统是否正确运转"（指标/架构/机制）
   - 内部（曈曈）：报"我哪里不舒服"（体验/效率/困惑）
   - **必须建"内部症状→外部诊断"的转诊通道**：曈曈自发现问题落盘→按类型分流→`code_defect` 类进补丁池、`experience` 类进优化清单、`pollution` 类进清洗队列
