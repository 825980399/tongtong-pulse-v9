## 4. 实测结果（真实数据，非生产负载）

### 4.1 热冷池 · 节点增删查（`PulseNodePool`）

| 操作 | 样本 | 吞吐 (ops/s) | p50 | p95 | max |
|------|------|-------------:|----:|----:|----:|
| **add** | 1000 | ~891 | 0.091 ms | 6.76 ms | 20.34 ms |
| **get 全量** | 1000 | ~911,245 | 0.0007 ms | 0.0029 ms | 0.019 ms |
| get · L3 | 96 | ~506,864 | 0.0025 ms | 0.0036 ms | 0.0055 ms |
| get · L2 | 289 | ~930,458 | 0.0007 ms | 0.0026 ms | 0.011 ms |
| get · L1 | 615 | ~1,029,460 | 0.0007 ms | 0.0027 ms | 0.019 ms |

> 观测：本次运行中 `hot_size=0`、`warm_size=152`、`cold_size=0`。L3 节点未落到热池，符合当前容量治理策略（热池仅容纳被高频激活的节点；批量灌入的 L3 节点尚未触发升热）。**非缺陷**，仅记录。
>
> `add` 的 p95/max 偏高（6.76 / 20 ms）来自共振引擎索引与冷缓存驱逐的偶发开销，属写入路径正常代价。

### 4.2 FAISS 向量检索（`FAISSVectorStore`）

| 项 | 值 |
|----|----|
| faiss 可用 | `True` |
| index_type | `auto` |
| **index_ready** | **`False`（brute-force 回退模式）** |
| 入库向量 | 2000（dim=512） |
| 入库吞吐 | ~8,775,779 ops/s（入库极快） |
| search p50 / p95 / max | **38.55 ms / 47.32 ms / 49.77 ms** |
| 查询吞吐 | ~24.9 ops/s |

> **重要解读**：本环境 FAISS 单例处于 **brute-force 回退模式**（`index_ready=False`，未构建 ivf/flat 索引）。2000×512 的暴力余弦相似度单次扫描约 38 ms，**这是回退模式的预期开销，不是缺陷**。生产环境若启用 FAISS 索引（`index_ready=True`），检索时延将下降 1~2 个数量级。
>
> 附加发现（已记录，非本批修复）：`FAISSVectorStore.add_vectors` 在 brute-force 回退分支以 `return`（无值）结尾，返回值恒为 `None`；benchmark 已改为以 `get_stats().vector_count` 判定入库成功（实测 2000/2000 落盘）。

## 5. 与第71批接线代码的关系

本次 T4 仅做性能观测，未改动任何生产代码。第71批的 Neo4j 双写 / InfluxDB 只写 / 分布式路由接线均**默认关闭**：

- 开关全 `False` 时，`PulseNodePool` 的 `_m71_*_enabled()` 直接返回，双写/只写分支不进入，主流程与基准数字反映的是「未启用外部存储」的基线。
- 启用后预期会引入外部 IO 开销（网络写 Neo4j / InfluxDB），建议在生产框架装配后、开关灰度开启时，复用本工具做对比基准。

1. 生产框架重启并装配 KAL `_node_pool` 后，重跑本工具以获得 KAL 阶段真实数字。

3. 灰度开启双写/只写开关后，建议用 `--nodes`/`--faiss-count` 同规模重跑，对比开启前后 add/get 时延增量。
