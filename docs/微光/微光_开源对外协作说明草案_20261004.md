## 一、项目是什么（一句话 + 用途）

> **Tongtong PulseNet** —— 一个**正在生长的仿生数字生命框架（研究原型）**。

- **是什么**：数十个仿生器官在「脉冲信息场」中协同工作，知识在压缩链中自我沉淀，持续探索一个开放问题：**纯软件系统，能不能真的拥有自主性？**
- **不是什么**：不是聊天助手，也不是编程工具（沿用现有 README 首段定义）
- **协议**：**GNU AGPL-3.0**（见 `LICENSE`）
- **定位限定（新增建议）**：本研究原型包含**虚构设定**；不作任何关于"生命/意识"的科学宣称
- 🔒 **不写**：拟亲关系叙事、真实业主/未成年人的任何指代（详见 §五）

## 三、贡献流程（issue → PR → 门禁）

**现状（实测）**：`.github/` 仅含 `PULL_REQUEST_TEMPLATE.md`；**无 `.github/workflows/`（CI = NONE）** → 外部贡献者**看不到自动门禁**。

**建议流程（文档化替代）**：

1. **Issue**：描述问题/需求（模板可复用现有 PR 模板结构）
2. **PR**：提交前本地跑通五道门禁（下方命令化清单）
3. **评审**：维护者按批次节奏合入

**五道门禁（对外可执行版，命令清单待烛微提供）**

| # | 门禁 | 判据 |
|---|---|---|
| 1 | 静态检查 | ruff `F` 类错误 = 0 |
| 2 | 导入冒烟 | 改动文件可 import |
| 3 | 测试 | 相关 pytest **0 failed** |
| 4 | 静默异常门禁 | 只降不升 |
| 5 | 行尾一致 | CRLF/LF 与项目约定一致（`.gitattributes` 为准） |

🔒 **不公开**：门禁豁免名单、阈值变更审批机制、内部批次编号与排期规则。

## 四、批次 / 票体系（**对外简化版**）

| 对外表述 | 内部对应 | 暴露程度 |
|---|---|---|
| Issue | 票（ticket） | ✅ 可公开 |
| Pull Request | 一批施工 | ✅ 可公开 |
| Review / Merge | 验收 | ✅ 可公开 |
| 批次（batch） | 项目以批次推进：任务书 → 施工 → 交付报告 → 验收 | ✅ 可公开（仅节奏描述） |
| 问题分级 P0-P3 | 内部优先级 | ⚠️ **仅保留 P0-P3 语义，不公开分级规则** |
| — | 裁决机制、登记册字段、挂账/顺延规则、角色分工 | 🔒 **不公开** |

**一句话版（建议直接用于 README）**：
> 项目以「批次」迭代推进，每个批次包含任务书、施工、交付报告与验收四个环节；问题以 issue 跟踪，欢迎以 PR 参与。
