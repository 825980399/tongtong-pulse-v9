# 自动化任务书规范（单任务粒度）

**版本**：v1.0
**产出批次**：主线第28批 T2（对应债务 P2-173）
**关联文档**：`docs/星轨-路灯自动化协作模式设计_v1.0.md`（本规范是其 §2.3「定时任务触发逻辑」的**修订与细化**）
**性质**：流程规范（★不涉及框架代码改动）

---

## 一、问题：自动化任务「领取即空转」

### 1.1 实测证据（2026-09-12）

| 时间 | 事件 |
|---|---|
| 00:35 | 星轨下发第27批任务书（工时段落：4 项 × 1~4 小时，**总工时约 10 小时**） |
| 01:23 | 路灯侧巡检定时任务触发，将任务书从 `任务书/` 移入 `任务书/处理中/` |
| 01:22 – 06:22 | **另外 6 次触发，零产出** |

判定「零产出」的四条硬证据：
1. 无 `.bak_batch27/` 备份目录（说明**未开始实施**）；
2. 无任何 `tmp/*m27*` 补丁脚本；
3. `交付报告/待分析/` 为空；
4. **`00:35` 之后全库 0 个 `.py` / `.md` 被修改**（决定性）。

### 1.2 根因

> **单次自动化运行的时间/步数预算 ≪ 一个批次的既定工时。**

- 批次粒度：10 小时（含 pytest 分片、verify、报告撰写）
- 单次运行预算：分钟级（且需在单个运行内完成"领取→核实→实施→门禁→报告"全链）
- 结果：领取动作完成（廉价、幂等），但执行环节**无法推进** ⇒ 任务书永久停留在「处理中」

**结论**：这不是"路灯偷懒"，而是**任务粒度与执行预算不匹配**。修复方向必须是**缩小单次任务的粒度**，而不是要求单次运行做更多。

## 二、优化方案（推荐 · 方案A：单任务粒度）

### 2.1 核心规则

| 规则 | 取值 | 说明 |
|---|---|---|
| **单次任务只含 1 个子任务** | 1 项 | 禁止把 4 项打包成一个定时任务 |
| **单项预估工时上限** | ≤ 1.5 小时 | 含门禁与报告 |
| **单项改动文件上限** | ≤ 5 个 | 超出说明粒度仍偏粗 |
| **必须无需人工介入即可验证** | 是 | 需重启框架验证的项**单独**成任务 |
| **必须可独立交付** | 是 | 每项产出自己的交付报告（或同一报告中独立小节） |

### 2.2 拆解示例

原第27批（4 项 / 约 10 小时）拆为：

```
任务 A：T1 深度思考超时保护（含配置化 + 灰度 + 单测）        ≈ 1.5h
任务 B：T2 核心模块文档字符串（3 文件）                       ≈ 0.5h
任务 C：T3 单元测试补充（23 例）                              ≈ 1.0h
任务 D：T4 类型注解 + mypy 验证                               ≈ 0.5h
```

每一条都可独立领取、独立交付、独立验收。

### 2.3 领取与交付的原子性约定

```
领取（原子）：任务书 → 处理中/ 的同时，写入 tmp/_claims/<批次>.claim（含开始时间）
执行         ：按 T0 核实 → 备份 → 实施 → 门禁 → 报告
交付（原子）：报告落 交付报告/待分析/ + 任务书 → 已完成/ + 删除 .claim
```

**关键新增**：`.claim` 文件让"领取后是否真的推进过"变得**可观测**——
下一轮巡检若发现 `.claim` 存在但**超过 2 小时无任何源码 mtime 变化**，
即判定为"空转"，此时应当：① 回退任务书到 `任务书/`（**不要**继续挂在处理中）；
② 输出一份「待办报告」说明未完成原因与建议拆分方式。

## 四、执行纪律（补充）

1. **禁止囤积**：一个批次未交付前不得读取其他任务书（沿用 v1.0 约定）；
2. **禁止假交付**：门禁未全绿时不得写"已完成"，应写"部分完成 + 未完成项 + 原因"；
3. **时间盒**：单项超过预估工时 2 倍仍未完成 → 触发回退（见模板 §五）；
4. **可观测**：关键阶段（领取/备份/实施完成/门禁结果/交付）写入 `.claim` 或记忆日志，
   使"是否空转"无需翻查全部产物即可判断；
5. **环境限制如实记录**：沙箱限流等环境问题必须附**报错原文**，不得用"测试通过"糊过去。

## 五、测试配额管理（★第29批新增）

### 5.1 问题：沙箱「删除配额」会打断测试

本项目的运行环境对**文件删除**设有配额（本批实测阈值 **50 / 每个 agent 回合**），
超限时抛 `SystemExit`，报错原文形如：

```
SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":615,"threshold":50,"scope":"turn","targets":[...]}
```

**★关键实测结论（第28批，推翻了此前的误解）**：`count` 是
**「本回合内所有删除尝试的累计」**，而**不只是某个测试目录的文件数**。
第28批用两轮探针实验证明：
- m19 夹具的临时根目录只写 **1 个文件**（调 `integrate_code_review` 前后 1 → 1，新增 0）；
- 项目根的 `.ruff_cache` **只增量写、不删**（156 → 157 → +0 → +0）；
- 而 **pytest 自带的临时目录清理**（`Temp\pytest-of-Administrator\garbage-*`）同样计入 ——
  第28批报错原文的 `targets` 正是它。

⇒ 因此「把测试夹具改小」并不能根治；**根治靠"降低单回合删除总量" + "让删除失败不致命"**。

### 5.2 易触发配额的测试类型（实测清单）

| 类型 | 典型文件 | 现象 |
|---|---|---|
| 目录级隔离重建 | `test_self_awareness_m19.py`、`test_self_awareness_m18/m20.py` | 单文件全量跑即累积数百次删除 |
| 快照 / 向量库落盘往返 | `test_snapshot_checksum_m13.py`、`test_vector_store*.py` | 连续合并跑易在中途 `SystemExit` |
| 事件总线 / 旁路监听 | `test_event_tap_m17.py` | 临时目录多、删除密集 |
| 大分片合并 | 任意「≥10 个测试文件同跑」 | 累计删除量线性叠加 |

⚠️ **失败特征辨识**：报错含 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`、`"scope":"turn"`，
或测试进程**在远短于正常耗时的时间内结束**（如 m19 正常 80s+，被拦时 1~8s）——
出现这些即为**环境限流**，**不是代码回归**。切勿据此改代码或改测试断言。

### 5.3 规避策略（按优先级）

1. **小分片跑**：单片 **4~8 个测试文件**，每片一次独立工具调用（配额按回合计，跨回合重置）；
2. **高密度文件单独跑**：`test_self_awareness_m19.py` **独占一个回合**；
   仍被拦时**按测试类拆**（`pytest "tests/x.py::TestA" "tests/x.py::TestB"`）；
3. **失败先复跑确认**：任何失败都先**单跑该文件**确认。单跑通过 ⇒ 判定环境限流，不计入回归；
4. **清理残留要趁配额恢复**：`tmp/_sa19_tests` 等残留会进一步吃掉配额；
   应在**新回合**（配额重置）清理，必要时**分批删除**（每批 ≤ 50 个文件）；
5. **夹具侧加固**（已落地，见 `tests/test_self_awareness_m19.py::_safe_rmtree`）：
   捕获 `BaseException`（含 `SystemExit`），被拦时只记 warning 并继续，
   使测试**不因清理失败而失败**。

### 5.4 配额耗尽后的回退方案

| 情况 | 处置 |
|---|---|
| 单片被拦 | 换下一个回合重跑该片（配额跨回合重置） |
| m19 被拦 | 下一回合单跑；再被拦则按测试类拆跑，并在交付报告注明覆盖情况 |
| 清理残留被拦 | **不强行清理**；在报告中列出残留路径，下回合处理 |
| 反复被拦且影响交付 | 交付报告中如实记录（附报错原文 + `count` 值），把未覆盖用例列为「下批必跑项」 |

### 5.5 领取与执行「测试类任务」的注意事项

1. 领取时先落地任务书的「**测试配额风险评估**」字段（见 §三 模板）；
2. 计划里**显式写出分片方案**（哪几个文件一片、m19 是否独占回合），避免临场乱跑；
3. 门禁中的 pytest **不追求"一次性全量跑"**，判据是**累计通过数 = 基线 + 新增**；
4. 交付报告必须写清：总通过数、分片明细、被环境拦下的文件与**复跑结论**。

## 六、备选方案（方案B：只做领取 + 待办报告）

若短期内无法把任务书拆到单任务粒度，则退化为：

```
1. 检测到新任务书 → 不移动文件，仅登记到 tmp/_pending/<批次>.json
2. 输出《待办报告》：任务项清单 + 每项预估工时 + 建议拆分方式
3. 由用户/星轨决定何时让路灯在**交互会话**中执行
```

**代价**：失去"无人值守自动推进"；**收益**：绝不出现"领取即空转"的悬挂状态。
本规范推荐优先实施方案A；方案B 作为兜底。
