代际	能力	落地状态

总表定位：P3 属「暂缓项5」，原因标注为「需探查器具备自主推理能力，长期目标」。本文档的任务是把这句话展开为可评估、可分层、可落地的技术设计，明确哪些部分近期可做、哪些必须等前置能力成熟。

二、现状盘点（代码级事实）
2.1 现有三条探查通道
通道	实现	触发方式	自主性
工具初筛	_tool_channel → self_inspector.run_tool_checks()（ruff/bandit/mypy/compileall）	周期全量扫描	无，目标集编译期写死
规则检查	_rule_channel → self_inspector.detect_code_issues()（18 种 _check_* 检测器）	周期全量扫描	无，规则集写死
LLM 深度审查	_llm_channel → SafeEvolutionExecutor.run_runtime_guided_review()	运行时异常触发（有 error_snapshot / queue_depth≥50 / reentry）	弱，触发条件硬编码，仅审查「已发生的异常」
2.2 现有「自主」成分的真实边界
代码中**最接近「自主」**的是 run_runtime_guided_review（第 319~385 行）：它采集运行时指标 → 发现异常 → 把「异常现场 + 相关代码 + 相关日志」喂 LLM 定向审查。

但它的「自主」是被动触发 + 单跳的：

触发被动：只有出现异常才启动，不会主动预判「哪里可能出问题」。
单跳无循环：审完即止，不会根据审查结果再推导「还有哪些相关文件/方法需要深入查」。
目标固定：只审 error_snapshots 里的异常现场，不会扩散到「未报错但有隐患」的代码。
2.3 接入链路
周期触发：PulseCortex._run_parallel_audit_async() → run_parallel_audit(_inspector) → record_audit_findings_to_hub(_report)（回流学习枢纽）
异常触发：PulseCodeLearner → run_runtime_guided_review(inspector)
两条链路都已闭环，P3 不必重造轮子，只需在「探查策略」这一层叠加自主决策。

三、本质差距分析
P3 与 P0~P2 的差距不在「探查能力」而在「探查决策」，具体三点：

维度	现状（P0~P2）	P3 目标	差距本质
决策主体	人预先定义「查什么」（规则/工具/异常类型）	探查器自己决定查什么	决策从编译期移到运行期
目标自适应	三通道目标集固定，与上一轮结果无关	根据「上轮发现」动态调整下轮策略	缺「探查 → 反馈 → 再探查」闭环
探查深度	全量一次性扫描，无深度调节	高风险区域深挖、低风险区域浅扫	缺「假设 → 定向探查 → 验证」循环
一句话结论：P3 的「自主」本质是把探查从一个「静态扫描器」升级为一个「自主规划器」——它能根据已发现的问题，自行生成「下一步该查什么」的假设，并验证假设。

四、可行形态：三层递进设计
这是本文档的核心产出。P3 不是「一次大改」，而是分三层递进，每层都可独立验收、独立回退。

P3-L1：探查策略自反馈（近端可落地，不依赖 LLM 自主规划）
目标：让探查器把「上一轮探查结果」作为本轮输入，动态调整「查哪些器官/文件/规则」，实现有记忆的定向探查。

核心机制：

从 record_audit_findings_to_hub 回流的数据中，提取「历史问题分布」（哪些文件/类型反复出问题）。
下一轮探查时，对「历史高频问题区域」加权深扫，对「长期干净区域」降频浅扫。
复用 ProbeRegistry 的 priority 字段做「探查优先级动态调整」，不新增架构。
依赖：仅依赖现有 P0~P2 已落地的能力 + 学习枢纽的历史数据，无新前置。

自主性等级：⭐⭐（有记忆、有反馈，但「查什么」的规则仍由人定义）

P3-L2：探查假设生成 + 验证闭环（中期，规则式已落地）
目标：让探查器从「已发现的问题」推导「可能相关的其他问题」，形成「假设 → 定向探查 → 验证」循环。

核心机制：

从已发现 issue 出发，生成「关联假设」——例如「这个文件有 silent_exception，同器官的其他方法是否也有？」
对假设做定向探查（只查假设指向的范围），验证假设成立与否。
验证结果回流，修正下一轮假设生成。
依赖与落地修正：原方案设想接入 AutonomousDeriver.derive，但代码事实表明 AutonomousDeriver 只推导「知识节点」（value/keywords/semantic_relations），完全不涉及代码 issue，无法直接复用。故改为规则式假设生成（nucleus/probe_hypothesis.py），用「问题类型 → 关联假设」静态规则表实现，零外部依赖。

落地状态：✅ 规则式假设生成 + 定向验证均已落地（probe_hypothesis.py 假设生成 + self_inspector.detect_code_issues(target_organs=...) 定向扫描 + PulseCortex 闭环接入，开关 use_probe_hypothesis，验收通过）。「假设 → 定向扫描 → 验证命中」闭环完整。

自主性等级：⭐⭐⭐（能自己生成「该查什么」的假设，但假设空间仍受限于「已发现的问题」）

P3-L3：完全自主规划（长期，依赖 LLM 自主推理成熟）
目标：探查器完全自行决定「查什么、查多深、何时停」，无需人预定义任何探查目标。

核心机制：

接入成熟的 LLM 自主规划能力，由 LLM 根据「系统状态 + 历史问题 + 架构约束」自主生成探查计划。
探查计划动态拆解为「探查步骤」，逐步执行、逐步评估、动态调整。
自我评估「探查是否已充分」，决定何时停止（避免过度探查浪费算力）。
依赖：LLM 自主推理/规划能力成熟（这是框架外的前置，不是本模块能独立补齐的）。

自主性等级：⭐⭐⭐⭐⭐（完全自主，真正的「长期目标」）

六、风险与边界
风险	影响	缓解
L1 过度拟合历史问题	反复扫同一区域，忽略新问题	加权而非排他；保留全量扫描的「兜底低频通道」
L2 假设生成偏差	推导出错误关联，浪费定向探查	假设置信度阈值 + 验证后回滚；错误假设不污染学习枢纽
L3 过度探查	自主规划失控，耗尽算力	探查预算上限 + 停止条件硬约束
能力边界误判	把 L1/L2 的「有反馈」误当成「真自主」，偏离长期目标	明确定位：L1/L2 是「迈向自主的过渡」，不是 P3 终点
七、实施建议（分层立项）
建议按层独立立项，不一次性推进 P3：

P3-L1 可近期立项：依赖全部就位，风险低，能做出真实可验收的「有记忆定向探查」，且为 L2/L3 铺路。验收标准：历史高频问题区域的探查命中率提升，且不遗漏新问题（兜底通道不丢）。→ 已落地：docs/P3-L1立项方案-探查策略自反馈.md（11/11 验收通过）。
P3-L2 中期立项：改为规则式假设生成（probe_hypothesis.py），已落地「假设生成 + 定向验证」完整闭环（验收通过）。
P3-L3 长期观察：等 LLM 自主推理能力成熟后再评估，当前不建议立项，避免产出「又一个规则清单」这种背离定位的半成品。
八、结论
P3 的「自主」本质是把静态扫描器升级为自主规划器，核心差距在「探查决策」而非「探查能力」。
可行形态分三层：L1（策略自反馈）近端可做，L2（假设生成）中期可做，L3（完全自主）长期观察。
本轮不写代码，本文档作为可行性设计供小林评审；L1 已按立项方案落地（P3-L1立项方案-探查策略自反馈.md，11/11 验收通过），L2/L3 待后续评估。
