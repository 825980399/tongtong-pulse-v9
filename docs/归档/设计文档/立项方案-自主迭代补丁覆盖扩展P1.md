一、背景与问题
1.1 现状
自主迭代链路里，SafeEvolutionExecutor._generate_patch() 只有 3 类 if/elif 硬编码修复，其余 15 类检测器命中后返回 None（SafeEvolutionExecutor.py:509-523）：
已接线（3 类）
修复方式
silent_exception
except Exception: pass → 记录日志
bare_except
except: → except Exception as e: + 日志
status_request_duplicate
统一为 return self.get_stats()
问题：18 个检测器能发现问题，但只有 3 类能自动生成补丁，其余 15 类「只检测、不修复」。自主迭代的「真实覆盖率」仅 3/18。
1.2 关键发现（本方案的分析结论）
1. unbounded_deque 是「漏接线」而非「不可修」：repair_with_distillation() 里 _local_fixable_types 已经把它列为「本地规则可修」（SafeEvolutionExecutor.py:141），但 _generate_patch() 里没有对应的 elif 分支——是历史遗留的接线遗漏。
2. 18 类检测器都有 suggestion 修复建议文本（self_inspector.py:1014-1107），但「有建议文本」≠「能安全自动替换」，需逐一评估语义。

二、方案设计：诚实扩展 3 → 6
2.1 核心原则
不为了覆盖率数字硬扩，只扩展「语义明确、纯文本替换、能安全验证」的类型。 高危/需人工判断的类型明确不碰，保持「补丁正确性优先」。

2.4 修复的安全保障（复用现有安全门）
新增的 3 类补丁完全复用现有安全链路，不新增风险面：
1. 副本验证：verify_in_copy() 在项目副本中验证补丁（语法 + 功能冒烟）
2. 唯一出现校验：original_pattern 必须唯一匹配才替换
3. 语法复验：替换后 compile() 校验
4. 核心文件审批：_is_core_file() 判断，核心文件必须人工审批
5. 原子写：mkstemp + os.replace
6. 备份回滚：CodeBackupManager + rollback_last

六、诚实边界说明
本方案不承诺「18 类全覆盖」，而是诚实把覆盖率从 3 类提升到 6 类：
• 6 类是「能安全自动修」的上限，其余 12 类要么是安全敏感（eval/shell/SQL），要么是需上下文判断（死循环/原子写/资源关闭），自动修反而危险。
• 剩余 12 类的问题仍会被检测，只是补丁生成走 LLM 路径（_submit_llm_patch）或人工审查（_patch_generic），这是刻意设计，不是能力缺失。
• 若未来要进一步提升覆盖率，应走「LLM 修复 + 副本验证」路径（已有 repair_with_distillation 雏形），而非硬编码更多 elif。
