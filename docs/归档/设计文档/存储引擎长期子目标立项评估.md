二、现状盘点（代码级事实）
2.1 当前检索体系：五维共振引擎（自有范式）
框架的检索不是「向量 embedding + ANN」，而是 ResonanceEngine（nucleus/synapsys/ResonanceEngine.py）的五维共振打分：
• _calc_memory_dim（记忆维）、_calc_space_dim（空间维）、_calc_logic_dim（逻辑维）、_calc_time_dim（时间维）、_calc_state_dim（状态维）
• resonate / resonate_topk 综合五维打分排序
这是 PulseNet 自有的检索范式，不是通用向量检索。「接入向量引擎」意味着要么替换这套自有范式，要么在其上叠加向量维度——两者都是架构级决策，不是加个库的事。
2.2 向量检索现状：仅「预埋扩展点」
nucleus/fast_ops.py 的 fast_vector_search 是纯 Python 暴力余弦相似度，注释明确：
当前为纯 Python 实现，性能足以支撑十万级节点。当节点数突破百万级时，可将此模块替换为 C/faiss 实现。
即：向量检索的性能瓶颈阈值是「百万级节点」，当前已预留替换点。
2.3 分片现状：零实现，仅「未来」注释
代码里搜「分片/shard/分布式/一致性哈希」，只有：
• GlobalClock.py、OrganProtocol.py、OscillonField.py 等处的「未来分布式」注释
• PulseStomach.py 的「万亿级 → 数据分片、分布式器官集群」展望
没有任何分片实现，也没有一致性哈希、跨机通信、节点定位等基础。
2.4 当前节点规模：≈ 0
实测当前快照 pulse_knowledge_snapshot.json 的 nodes 为空，node_count_at_save 为 0。系统处于初始化/早期阶段，远未到「十万级」更遑论「百万级/千亿级」。

三、关键判断
「分片跨机」和「向量引擎」都依赖同一个前提：单机节点数真的逼近内存/性能上限。而这个前提当前完全不成立。
这两个子目标是「千亿级」的终极手段（设计文档第 251 行），属于「等真实压力出现再启动」的触发式工作，不是「现在就做」的常规迭代。在节点规模 ≈ 0 的当下立项实施，属于过早优化，会：
1. 引入分布式复杂度（一致性哈希、跨机通信、节点定位、脑裂处理）却无处验证——因为没有真实压力场景来检验正确性；
2. 外部依赖（Milvus/FAISS）带来部署成本，但检索性能瓶颈尚未出现；
3. 可能破坏刚落地且未充分验证的分层存储内核（A/C'/B'/D）。

六、评估结论
暂不立项。 理由：
1. 触发前提未到：节点规模 ≈ 0，远未到百万级向量瓶颈线，分片/向量引擎无真实压力场景可验证。
2. 过早优化风险：分布式复杂度 + 外部依赖在无压力验证下引入，只会增加维护负担和回归风险。
3. 优先级错配：刚落地 A/C'/B'/D + P3-L1/L2 都尚未灰度验证，当前应聚焦「验证已落地能力」而非「叠加更远期改造」。
建议动作：保持「暂缓」定位，在总表中标注明确的触发条件（见第四节），等真实压力出现再启动立项。届时评估文档已备好，可快速启动。
