### 4.2 未修复：38 个 SIM115（`open()` 未用上下文管理器）—— 经评估为「设计使然」，不应机械修复

| 范围 | 数量 | 评估结论 |
|---|---|---|
| 生产源码 | **2** | ★**有意保持句柄**，改 `with` 会破坏功能 → **不修** |
| `tests/` + `tools/` | 36 | 测试夹具的临时打开；批量改造收益低、风险散布 → **记录债务** |

**2 个生产源码的逐个论证**：

1. `nucleus/mnemosyne/lazy_snapshot.py:187`
   ```python
   self._file = open(self.path, "rb")          # ← 句柄存入实例属性
   self._mm = mmap.mmap(self._file.fileno(), 0, access=mmap.ACCESS_READ)
   ```
   该句柄是**懒加载快照的生命周期要素**（与 `mmap` 绑定，由 `_close_mm()` 统一释放）。
   改成 `with` 会在 `_build()` 返回时关闭文件 → `mmap` 失效。**属 ruff 误报（设计模式使然）**。

2. `nucleus/reasoning/evolution_worker.py:143`
   ```python
   _stderr_fp = open(stderr_file, "w", encoding="utf-8", buffering=1)
   sys.stderr = _stderr_fp                          # ← 重定向进程 stderr
   ```
   需**保持到子进程退出**才能持续捕获崩溃栈。改成 `with` 会提前关闭 → 丢失崩溃日志。
   **属设计使然**。

> **建议**：在 `ruff.toml` 中评估将生产代码目录的 `SIM115` 置为忽略
> （或加 `# noqa: SIM115` 并注明理由），避免该规则持续产生「无法动作的告警」。

**757 个 P2 + 25 个 P3 的绝大多数为「格式/现代化」类，可由 ruff `--fix` 自动消除。**
本批**未批量执行**，理由如下：

1. **风险面**：一次性改动数百处，分布于数十个文件，会污染改动清单、破坏「批次改动可追溯」原则；
2. **非缺陷**：这些规则不涉及运行语义（`I001`/`UP031`/`RUF100` 等均不改变行为）；
3. **任务书边界**：任务书明确「只修复明确的、低风险的 P0 级问题」，而 P0 = 0。

**建议的单开批次方案（供裁决）**：

| 步骤 | 内容 | 预估 |
|---|---|---|
| 1 | 建立 `.bak_batchN` 备份 + 记录 `ruff --statistics` 基线 | 5 min |
| 2 | 按规则分批 `ruff check --select <规则> --fix`（每批 1~2 条规则） | 20 min |
| 3 | 每批后跑全量 pytest + `verify`，确认零回归 | 30 min |
| 4 | 高风险规则（`PLW1510` 等涉及语义）**逐个人工确认**，不自动修 | 30 min |
| 5 | 输出治理报告 + 更新债务清单 | 15 min |

**预期收益**：827 → 约 50（仅剩需人工判断的项）。
**建议优先级**：P3（低）—— 当前无功能影响，宜在主线功能批次之间的空档期执行。

## 八、口径统一（★主线第30批 T3 补充）

历史上出现过三个不同的「代码问题」数字（590 / 591 / 827），实测定位如下：

| 扫描范围 | 命令 | 条数（2026-09-12 实测） |
|---|---|---|
| 项目根递归（**含 `tests/`**） | `ruff check --output-format json .` | **836** |
| 核心模块（**不含 `tests/`**） | `ruff check --output-format json nucleus organs functions tools` | **578** |
| 仅 `nucleus organs` | `ruff check --output-format json nucleus organs` | 477 |

**结论**：`590/591` 与 `827/836` 的差异**不是规则集不同，而是扫描范围是否包含 `tests/`**。
`tests/` 目录贡献了约 **258 条**（836 − 578），主要来自测试夹具的 import 排序与
`open()` 使用习惯。

### 8.2 正式口径定义（自本批起生效）
