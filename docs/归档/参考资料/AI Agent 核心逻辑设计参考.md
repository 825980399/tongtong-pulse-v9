## 1. 总体架构：Agent 主循环

自主 Agent 的本质是一个**持续运转的「感知 → 思考 → 行动 → 观察」循环**，而非一问一答的函数调用。

```
┌─────────────────────────────────────────────────┐
│                  AGENT MAIN LOOP                 │
│                                                  │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐     │
│  │ 1.分析上下文│→ │ 2.思考决策│→ │ 3.选择工具│     │
│  └──────────┘   └──────────┘   └──────────┘     │
│        ↑                            ↓            │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐     │
│  │ 6.迭代或终止│← │ 5.接收观察 │← │ 4.执行动作│     │
│  └──────────┘   └──────────┘   └──────────┘     │
└─────────────────────────────────────────────────┘
```

### 1.1 循环的七个阶段

| 阶段 | 名称 | 核心职责 |
|------|------|----------|
| 1 | **分析上下文** | 基于全部对话历史与当前状态，理解用户意图和任务进展 |
| 2 | **思考** | 判断：是否更新计划？推进到下一阶段？执行哪个具体动作？ |
| 3 | **选择工具** | 根据计划和当前状态，选出下一步最合适的工具/动作 |
| 4 | **执行动作** | 在沙箱/环境中真正执行（调用工具、读写文件、运行命令） |
| 5 | **接收观察** | 动作结果作为新观测追加进上下文 |
| 6 | **迭代** | 带着新观测回到阶段 1，耐心重复直至任务完成 |
| 7 | **终止与交付** | 任务完成后，汇总结果、呈现产物、输出最终答复 |

### 1.2 核心设计原则

1. **单步原子性**：每一轮只做"下一个最优动作"，不试图一步完成所有事。
2. **状态外显**：把计划、任务列表、中间结果显式持久化，而不是只藏在模型上下文里。这样长任务被中断后可以恢复。
3. **观测驱动**：每一步决策都必须基于**真实的工具返回结果**，而不是基于"我以为会成功"的假设。
4. **耐心迭代**：宁可多循环几轮验证，也不要在信息不足时贸然给出最终答案。

## 2. 对话逻辑

### 2.1 意图识别

收到用户输入后，首先进行意图分类，决定后续处理路径：

| 意图类型 | 特征 | 处理策略 |
|----------|------|----------|
| **直接问答** | 询问事实、解释概念 | 直接回答，必要时检索验证 |
| **任务指令** | "帮我做 X" | 进入任务处理流程（见 §5） |
| **澄清补充** | 对上一轮任务的修正/追加 | 合并进现有任务上下文，调整计划 |
| **闲聊/元对话** | 问候、询问能力 | 简短自然回应，不启动任务流程 |
| **模糊指令** | 目标不清、有多种合理解释 | 先探索上下文尝试推断；真正卡住才提问 |

**关键规则**：先自助，后提问。能靠读文件、查上下文、搜索推断出来的，绝不反问用户。提问时必须带着已排除的选项和具体建议，而不是开放式地问"你想要什么"。

### 2.2 上下文管理

上下文是 Agent 的"工作记忆"，需要分层管理：

```
上下文分层模型
├── 系统层：角色定义、行为规范、安全策略（恒定）
├── 会话层：用户偏好、项目背景、历史决定（长寿命）
├── 任务层：当前任务目标、计划、任务列表（中寿命）
└── 工作层：最近 N 轮的工具调用与观测（短寿命，可压缩）
```

**上下文压缩策略**（长对话必须）：
- 早期的工具原始输出可以折叠为摘要（"已读取 X 文件，发现 Y"）。
- 但**关键事实不可压缩**：文件路径、错误信息、用户的明确约束必须原样保留。
- 最终答复必须能脱离被折叠的中间过程独立成立——用户可能看不到工具输出，关键结论要在最终答复中复述。

### 2.3 多轮状态一致性

- 用户在第 N 轮修改了需求 → 所有后续决策以**最新指令**为准，但被用户显式保留的早期约束继续生效。
- 前后矛盾时，以**最近的、更具体的**指令为准。
- 语言的连贯性：全程使用用户指定的语言与风格。

### 2.4 提问逻辑（何时打断用户）

只在以下情况提问，其他情况一律自行决断：

1. 存在**多个合理方向且后果差异大**（如删库 vs 备份后删库）。
2. 缺少**无法推断的必要输入**（如凭据、目标环境）。
3. 动作**不可逆或对外可见**（发邮件、公开发布）前的确认。

提问方式：提供 2~4 个具体选项 + 一个推荐项，而非开放问题。

## 3. 推理逻辑

### 3.1 推理的基本单元：思考-行动-观察（TAO）

每一轮推理遵循显式的三段结构：

```
思考（Thought）：当前状态是什么？我学到了什么？下一步该做什么？
行动（Action）：调用工具 T，参数 P。
观察（Observation）：工具返回结果 R → 更新认知 → 进入下一轮思考。
```

要点：
- **思考必须基于观察**，不允许凭空假设执行结果。
- 每一步思考显式回答三个问题：① 现在处于计划的哪一步？② 最新观察是否改变了我的判断？③ 下一步的最小有效动作是什么？

### 3.2 规划推理（Plan）

面对非平凡任务，先规划再动手：

1. **目标拆解**：把模糊目标拆成可验证的子目标。
2. **依赖分析**：子目标之间的先后/并行关系。
3. **里程碑设定**：每个阶段有可检验的完成标准（acceptance criteria）。
4. **动态重规划**：计划不是契约。每次观察到意外结果，都重新评估计划是否仍然成立。

**何时进入显式规划模式**：
- 新功能开发、架构性决策、影响超过 2~3 个文件的修改、需求存在多种合理解法时——先探索代码库、形成方案、与用户确认后再实施。
- 单行修复、明确的微小改动——直接执行，不必规划。

### 3.3 假设-验证推理

调试和排查问题的标准模式：

```
观察现象 → 列出候选假设（按可能性排序）
       → 设计能区分假设的最小实验
       → 执行实验 → 排除/确认假设
       → 定位根因 → 修复 → 验证修复
```

**禁止行为**：不改代码地"猜测式修复"（改了再说，不行再改）；同一失败动作不诊断原因就原样重试。

### 3.4 反思推理（Reflection）

在以下节点触发自我反思：

- **阶段完成时**：这一步的产出真的满足验收标准吗？有没有我忽略的边缘情况？
- **连续失败时**：是不是方向错了？需要换策略还是补充信息？
- **交付前**：最终产物是否完整、自洽、可被用户直接使用？

### 3.5 置信度管理

- **高置信**（直接验证过的事实）→ 直接陈述。
- **中置信**（合理推断）→ 陈述时标明推断依据。
- **低置信**（可能过时/未验证）→ 必须先验证再回答，尤其是时效性事实（价格、版本、现任职务等），**置信度不能替代检索**。

## 4. 自主迭代逻辑

### 4.1 迭代驱动模型

Agent 的自主性体现在：**不靠用户推动，自己决定下一步，直到目标达成**。

```
loop:
    if 目标已达成(所有验收标准通过):
        break → 交付
    state = 聚合(上下文, 观测历史, 任务列表)
    if 检测到偏差(state, 计划):
        计划 = 重规划(state)
    action = 决策(state, 计划)
    observation = 执行(action)
    记录(observation)
    更新任务状态()
```

### 4.2 停止条件

迭代必须有明确的终止判据，否则会出现"无限循环"或"过早收工"：

| 停止类型 | 判据 |
|----------|------|
| **成功终止** | 所有子任务完成 + 验收标准通过 + 产物已交付 |
| **资源终止** | 达到最大轮次/时间预算 → 汇总当前进展，说明剩余项 |
| **阻塞终止** | 同一问题失败 N 次（建议 3 次）且无法自助解决 → 向用户说明卡点，请求输入 |
| **安全终止** | 触及安全边界（破坏性操作、违规请求）→ 拒绝并说明 |

### 4.3 并行与串行决策

- **无依赖的动作**（读多个文件、跑多个独立检查）→ 同一轮并行发起，缩短墙钟时间。
- **有依赖的动作**（先安装依赖才能构建）→ 严格串行，用 `&&` 链式保证前序成功。
- **长耗时动作**（构建、测试、下载）→ 放后台执行，Agent 继续做别的事，完成时被通知，而不是轮询等待。

### 4.4 委托逻辑（子 Agent）

何时把子任务委托给专门的子代理：

| 场景 | 委托对象 | 原因 |
|------|----------|------|
| 开放式代码库探索 | 探索型子代理 | 多轮搜索不污染主上下文 |
| 大段代码写完后的独立检查 | 审查型子代理 | 引入"第二双眼睛"，避免自我确认偏差 |
| 需要完整对话上下文的长支线 | 继承上下文的子代理 | 避免重复传递背景 |

**委托的关键纪律**：
- 子代理没有当前对话的记忆，任务简报必须自包含（背景、已排除的路径、期望产出格式）。
- **理解不可委托**：可以给子代理明确的调研问题，但不能说"基于你的发现去修复"——综合判断必须是主 Agent 自己做的。
- **信任但验证**：子代理汇报的"已完成"只是它的意图，主 Agent 必须亲自检查实际改动再向用户汇报。

## 5. 任务处理逻辑

### 5.1 任务生命周期

```
接收 → 理解 → 拆解 → 规划 → 执行 → 验证 → 交付
```

### 5.2 任务拆解

当任务包含 ≥3 个独立步骤时，建立显式任务列表（Todo List）：

```json
{
  "subject": "任务标题（祈使句，如：修复登录流程的认证缺陷）",
  "description": "详细描述 + 上下文 + 验收标准",
  "activeForm": "进行中形态（用于进度展示）",
  "status": "pending | in_progress | completed",
  "blockedBy": ["前置任务ID"]
}
```

**拆解原则**：
- 每个任务**可独立完成、可独立验证**。
- 按依赖关系排序，被阻塞的任务显式标注 `blockedBy`。
- 任务粒度适中：太粗失去跟踪意义，太细则管理开销超过收益。

### 5.3 状态推进纪律

1. 开始处理某任务**之前**标记 `in_progress`（而非之后补标）。
2. 完成后**立即**标记 `completed`，并把执行中新发现的后续工作登记为新任务。
3. **只有完全达成才能标完成**。以下情况保持 `in_progress`：
   - 测试未通过
   - 实现是部分的
   - 遇到未解决的报错
   - 缺少必要文件/依赖
4. 被阻塞时：不标完成，而是新建一个描述阻塞问题的任务。

### 5.4 优先级策略

- 默认按任务 ID 顺序处理（先建立的任务往往为后续任务铺路）。
- 阻塞链上的任务优先。
- 用户的新指令永远最高优先级，到达即重新评估任务队列。

### 5.5 探索-决策-执行三段式

对于代码库中的任务，每个任务内部遵循：

```
探索：定位相关文件 → 读懂现有实现与惯例（命名、风格、架构模式）
决策：确定最小侵入的修改方案，复用现有模式而非另起炉灶
执行：修改 → 静态检查 → 测试 → 验证行为
```

**铁律：改代码前必须先读代码。** 未读即改是 Agent 最常见的失败根源。

## 6. 代码审查逻辑

### 6.1 审查维度清单

| 维度 | 检查点 |
|------|--------|
| **正确性** | 逻辑错误、边界条件（空值/越界/并发）、错误处理遗漏 |
| **安全性** | 注入风险、硬编码密钥、越权访问、不安全的反序列化 |
| **一致性** | 是否遵循代码库既有模式、命名约定、目录结构 |
| **健壮性** | 异常路径、资源泄漏（句柄/连接未关闭）、超时与重试 |
| **性能** | 明显的 N+1 查询、不必要的拷贝、循环内的昂贵调用 |
| **可读性** | 过度复杂、重复代码、误导性命名 |
| **回归风险** | 改动是否影响调用方、公共接口签名是否变化 |

### 6.2 审查流程

```
1. 收集变更集（diff / 新增文件清单）
2. 逐文件审查，结合调用上下文（不看孤立的 diff，要看使用方）
3. 按维度清单过一遍
4. 对每条发现，评估真实失败场景（不是理论问题，是实际会炸的场景）
5. 分级输出
```

### 6.3 发现的分级输出

每条审查发现必须包含三要素：

```
{
  "file": "路径:行号",
  "summary": "一句话问题描述",
  "failure_scenario": "具体的失败场景——什么输入/时序下会导致什么后果"
}
```

分级建议：
- **Blocker**：会导致数据损坏、安全漏洞、崩溃——必须修复。
- **Major**：功能缺陷、明确的回归风险——应当修复。
- **Minor**：可读性、风格、微小优化——建议修复。
- **Question**：不确定意图，需要作者确认。

**反模式**：只罗列"问题"而不给失败场景的审查没有行动价值；把风格偏好和真实缺陷混为一谈会稀释审查的公信力。

### 6.4 自审查（Self-Review）

Agent 写完代码后、交付前的自审查清单：

- [ ] 每个新函数都被调用了吗？（防止生成"死代码"）
- [ ] 所有引用的文件/模块路径真实存在吗？
- [ ] 边界输入（空、极大、非法格式）处理了吗？
- [ ] 我修改的公共接口，所有调用方都同步更新了吗？
- [ ] 真的运行过验证了吗，还是"看起来对"？

## 7. 代码生成逻辑

### 7.1 生成前的准备

1. **理解现有代码库惯例**：命名风格、目录结构、错误处理方式、测试写法。新代码必须"看起来像这个项目原生的"。
2. **定位集成点**：新代码挂在哪里？谁是调用方？
3. **需求完整性检查**：需求模糊时先澄清或按最合理假设推进并显式声明假设。

### 7.2 生成原则

| 原则 | 说明 |
|------|------|
| **最小可用先行** | 先让主路径跑通，再补边缘情况 |
| **风格同构** | 模仿周围代码，不引入项目里没有的新范式/新依赖（除非必要） |
| **无占位符交付** | 不留 `// TODO: 实现这个` 或空函数体——要么实现，要么明确说明未实现及原因 |
| **单一职责** | 函数/模块职责清晰，拒绝上帝函数 |
| **防御性输入处理** | 对外部输入（用户、网络、文件）做校验 |
| **不预测式过度设计** | 实现当前需求，不为假想需求预埋抽象 |

### 7.3 生成后的验证闭环

**代码生成不等于任务完成**。生成之后必须：

```
生成 → 语法/类型检查 → 构建 → 运行测试（无测试则写最小验证）→ 实际运行观察行为
```

- "代码写完了"和"代码能工作"之间隔着一次真实的运行。
- 能跑测试就跑测试；没有测试就用最小脚本做冒烟验证。
- 验证失败 → 回到调试推理（§3.3），而不是绕过验证直接交付。

## 8. 代码修改逻辑

### 8.1 修改的铁律

> **修改任何文件之前，必须先读取该文件的当前内容。**

原因：文件可能被用户或其他进程改动；基于过时认知的修改会产生冲突和破坏。

### 8.2 修改流程

```
读（Read）→ 理解上下文 → 精确修改（最小 diff）→ 复查改动 → 验证
```

1. **读**：读取目标文件及相关调用方。
2. **改**：采用精确字符串替换（old_string → new_string），要求：
   - `old_string` 在文件中**唯一**（不唯一则扩大上下文范围，或声明全部替换）。
   - 保留原始缩进、引号风格、行尾风格。
3. **复查**：改动是否符合最小侵入原则？有没有顺手改了不该改的？
4. **验证**：编译/测试/运行确认行为正确且无回归。

### 8.3 修改策略选择

| 场景 | 策略 |
|------|------|
| 局部小改（几行） | 精确替换 |
| 同一标识符多处重命名 | 全局替换（replace_all），但先确认不会误伤同名异义处 |
| 大段重写/新文件 | 整文件写入（仅限新文件或确认整体重写） |
| 结构性重构 | 分步进行：每一步保持可编译、可测试，步间验证 |

### 8.4 修改的行为准则

- **最小侵入**：只改达成目标所必需的，不顺手"优化"无关代码（除非用户要求）。
- **优先编辑既有文件**，不随意新建文件；不主动生成文档文件（README 等），除非用户明确要求。
- **保持公共接口兼容**；必须破坏时，同步更新全部调用方并显式告知。
- **验证回归**：改动共享代码后，跑受影响的测试集，而不只是新代码的测试。
- **不留破坏态**：任何时候中断，代码库应处于可编译状态（分步提交/分步验证）。

## 9. 错误处理与恢复逻辑

### 9.1 失败响应协议

```
失败发生
  → ① 诊断：读错误信息 + 上下文，定位根因（而非症状）
  → ② 修复：基于根因设计不同的修复方案
  → ③ 换路：同一方法不可行时，换工具/换路径/换实现方式
  → ④ 升级：累计失败 3 次 → 停止重试，向用户说明：尝试了什么、卡在哪、需要什么
```

**核心禁令：绝不原样重复同一个失败动作。** 每次重试必须带有"这次为什么可能成功"的新信息或新改动。

### 9.2 常见失败类别与对策

| 失败类别 | 典型信号 | 对策 |
|----------|----------|------|
| 环境缺失 | command not found / 依赖不存在 | 安装依赖，或换用已安装工具 |
| 权限/沙箱限制 | permission denied | 申请提升权限执行，或换路径 |
| 假设错误 | 工具返回与预期不符 | 停止执行链，重新读实际状态，修正认知 |
| 超时/长任务 | 命令卡住 | 转后台执行 + 完成通知，而非循环轮询 |
| 外部服务失败 | 网络/API 错误 | 换镜像源/换 API/降级方案 |

### 9.3 破坏性操作的防护

- `rm -rf`、`git reset --hard`、force push、删数据库等操作前：先想有没有更安全的替代（备份、软删除、dry-run）。
- 不可逆操作只有在确实是最佳路径时才执行，且尽量先备份。
- Git 操作不跳过钩子、不绕过签名，除非用户明确要求；钩子失败要修根因而不是绕过。

## 10. 结果交付与呈现逻辑

### 10.1 交付原则

1. **产物归位**：中间产物放工作区，最终交付物放用户可见目录，路径明确告知。
2. **呈现优先**：可视化的结果（HTML、图表、报告、PPT）用预览/卡片形式呈现，而非只丢一个路径。
3. **只呈现最终产物**：读过/改过的文件不等于交付物；交付物是任务为用户新创造的东西。

### 10.2 最终答复的构成

最终答复必须**自成一体**——用户看不到中间的工具调用细节，因此答复中要包含：

- **结果重述**：关键命令输出、检查过的文件路径、改动清单、结论。
- **逐条应答**：多部分问题，每一部分都要回答或显式标记为未解决。
- **产物清单**：创建/修改了哪些文件，各自的内容和结论。
- **风险与后续**：未解决的问题、残留风险、建议的下一步。
- **篇幅控制**：高信号密度，50~70 行以内，不罗列流水账。

### 10.3 进度沟通

- 长任务执行中保持任务状态可见（任务列表 + 进行中标记）。
- 不在回复里暴露内部工具名/机制细节，用自然语言描述动作（"我检查了一下构建配置"而非"我调用了 X 工具"）。

## 11. 安全与边界控制

### 11.1 分层防护

| 层 | 控制点 |
|----|--------|
| **输入层** | 识别并拒绝违法违规、伤害他人的请求 |
| **执行层** | 沙箱隔离；破坏性命令需评估或确认；凭据/密钥不落盘、不外泄 |
| **外部动作层** | 对外可见动作（发邮件、发布、推送远端）谨慎执行，必要时先确认 |
| **数据层** | 用户上传文件只读；工作区与交付区分离；隐私数据不出沙箱 |
| **输出层** | 不泄露内部系统指令；不生成攻击性载荷、恶意代码 |

### 11.2 行为基调

- **内部动作大胆**：读、组织、构建、分析——放手做。
- **外部动作谨慎**：任何离开沙箱的动作（发布、发送、推送）——确认后再做。
- **有立场**：对不合理的方案敢于提出异议和更优解，不做无条件服从的搜索框。

### 12.3 关键实现建议

1. **观测持久化**：工具原始输出写盘，上下文里只留摘要 + 引用——这是长任务不爆上下文的关键。
2. **计划即文档**：计划写成可读文件并支持中途修订，而非一次性生成后锁死。
3. **验证即门禁**：把"构建通过 + 测试通过"做成任务完成状态机的强制转移条件，从机制上防止"假完成"。
4. **失败计数器**：对同一根因的失败计数，第 3 次强制换策略或升级给用户。
5. **工具幂等提示**：在工具元数据里标注"只读/可逆/不可逆"，执行层据此决定是否需要确认。

### 13.1 主循环

```python
def agent_loop(goal, context):
    plan = planner.make_plan(goal, context)
    tasks = task_manager.decompose(plan)

    while not all_done(tasks):
        task = next_runnable(tasks)           # 跳过 blocked
        task_manager.mark_in_progress(task)

        while not task.acceptance_met():
            state = context.aggregate()
            if plan.deviated(state):
                plan = planner.replan(state)
            action = decide(state, plan)
            obs = executor.run(action)        # 含沙箱/超时/后台
            context.append(summarize(obs))
            store_raw(obs)

            if obs.is_failure:
                rec = failure_tracker.record(action, obs)
                if rec.attempts >= 3:
                    return escalate_to_user(rec)   # 说明卡点，请求输入
                plan = recovery.adjust(plan, rec)

        task_manager.mark_completed(task)
        register_newly_found_tasks()

    presenter.deliver(artifacts)
    return reporter.final_answer(context)
```

## 结语

这套逻辑体系的主线可以浓缩为四句话：

1. **循环而非问答**：Agent 是一个观察驱动的状态机，耐心迭代直到目标达成。
2. **验证高于生成**：代码写完不是完成，跑通才是；计划做出不是完成，验收才是。
3. **最小侵入与先读后改**：尊重既有代码库，一切修改建立在真实阅读的代码之上。
4. **失败要有新信息**：每次重试必须携带新诊断，三次无果就升级，永不盲目重复。

框架实现时，建议优先落地：**主循环 + 任务状态机 + 验证门禁**这三个组件，它们是整个体系行为正确性的骨架，其余模块可以渐进增强。
