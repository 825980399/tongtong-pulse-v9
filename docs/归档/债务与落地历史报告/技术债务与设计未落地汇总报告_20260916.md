## 三、GPU 利用情况深度分析

### 3.1 GPU 实现现状（已完整实现！）

**关键发现**：GPU 向量检索加速实际上已经完整实现，并非 "只有宣告没有使用"。

#### GPUCore.py（nucleus/GPUCore.py，243 行）



| 方法                    | 功能            | 状态           |
| --------------------- | ------------- | ------------ |
| `probe_gpu()`         | 探测 GPU 硬件信息   | ✅ 已实现        |
| `gpu_available()`     | 检查 GPU 是否可用   | ✅ 已实现        |
| `get_vram_pressure()` | 获取显存压力        | ✅ 已实现        |
| `batch_cosine_gpu()`  | GPU 批量余弦相似度计算 | ✅ 已实现（核心计算）  |
| `gpu_cache()`         | GPU 计算结果缓存    | ⚠️ 零调用方（未使用） |
| `get_gpu_core()`      | 获取 GPU 核心单例   | ✅ 已实现        |

#### GPU\_VECTOR\_SEARCH 配置（config.py 第 2904 行）



```

&#x20;   "enabled": True,                    # 总开关已开启

&#x20;   "min\_candidates": 2000,            # 候选向量数下限

&#x20;   "min\_dim": 64,                      # 向量维度下限

&#x20;   "max\_candidates\_per\_call": 200000, # 单次最大候选数

&#x20;   "auto\_disable\_after\_slower": 5,     # 连续跑输5次自动停用

&#x20;   "win\_ratio": 1.0,                    # GPU比CPU快多少倍算胜出

}
```

#### fast\_ops.py 中的 GPU 调用链



```
fast\_vector\_search()          # 主入口（nucleus/fast\_ops.py第77行）

&#x20;   ↓ 决策是否用GPU

&#x20;   ↓ 决策通过

&#x20;   ↓ 调用

```

#### GPU 自适应机制（不靠猜，靠测）

`_GPU_STATE` 状态变量：



* `enabled`: None = 未判定，True/False

* `cpu_ms_avg`: CPU 路径历史均值

* `gpu_ms_avg`: GPU 路径历史均值

* `slower_streak`: GPU 连续跑输次数

* `calls`: 总调用次数

* `gpu_calls`: GPU 实际执行次数

**设计要点**：不同显卡 / 驱动的性能拐点差异极大，与其把阈值写死，不如让框架自己跑出来 ——GPU 连续跑输 CPU 就自动停用，绝不拖慢。

### 3.2 GPU 可能未充分利用的原因分析

虽然 GPU 已完整实现，但用户反馈 "GPU 利用率纹丝不动"，可能原因：

#### 原因 1：device\_router 成本模型判定 GPU 不划算（最可能）



* `device_router.should_use_gpu()` 会根据实测带宽 / 算力现算盈亏平衡点

* GTX 1050 Ti（4GB 显存，算力 6.1）是入门级显卡

* 小批量向量检索时，CPU 的 Cython 实现可能比 GPU 更快（PCIe 传输开销）

* 框架可能已自动判定 GPU 不划算，停用了 GPU 路径

#### 原因 2：min\_candidates=2000 阈值较高



* 实际检索场景中，候选向量数可能很少达到 2000

* 知识节点检索通常候选数在几百到一千

* 阈值以上才走 GPU，导致 GPU 很少被触发

#### 原因 3：缺少可观测日志



* GPU 执行时的日志可能不够明显

* 用户在任务管理器中看不到 GPU 利用率，可能误以为 GPU 没工作

* `_gpu_state_snapshot()` 可导出状态，但可能未接入 status 命令

#### 原因 4：gpu\_cache 零调用方



* `GPUCore.gpu_cache()` 方法存在但全项目零调用方

* 这是一个未被使用的缓存机制，但不影响主计算路径

### 3.3 GPU 利用优化建议

#### 建议 1：验证 GPU 自适应状态

在框架运行时执行以下检查：



```
from nucleus.fast\_ops import \_gpu\_state\_snapshot

print(\_gpu\_state\_snapshot())
```

查看：



* `enabled`: 是否被自动停用

* `calls`: 总调用次数

* `gpu_calls`: GPU 实际执行次数

* `slower_streak`: 连续跑输次数

#### 建议 2：降低 min\_candidates 阈值测试

将 `min_candidates` 从 2000 降至 500，观察 GPU 是否被更多调用：



```
GPU\_VECTOR\_SEARCH = {

&#x20;   "min\_candidates": 500,  # 从2000降至500

&#x20;   ...

}
```

#### 建议 3：增加 GPU 可观测性



* 在 status 命令中显示 GPU 自适应状态

* GPU 执行时打印更明显的日志（可观测，不刷屏）

* 增加 GPU 使用率统计指标

#### 建议 4：接入 gpu\_cache

将 `gpu_cache()` 接入高频重复查询场景，减少重复计算。

#### 建议 5：GPU 专项验证批次

安排一个专项批次：



1. 验证 GPU 自适应状态和实际调用情况

2. 优化阈值和成本模型

3. 增加可观测性

4. 接入 gpu\_cache

5. 性能对比测试（GPU vs CPU）
