> 状态：核心改造完成，待本地运行验证

## 一、背景与诉求

上一轮（v26.0）打通了「自动应用 + 重启 + 健康度驱动」的闭环骨架，但仍有三个环节依赖外部研发伙伴（路灯）人工兜底：

1. **发现问题**：仅靠静态规则 `detect_code_issues`，缺「运行日志动态归因」。
2. **修改前后对比记录**：`_generate_diff_summary` 是粗糙的逐行 zip 对比，无标准 diff 归档、无全链路溯源。
3. **创建测试工具实际运行**：只跑 2 个既有脚本，**不会为本次修改动态生成测试**。

本轮（v27.0）补齐这三块，新增一个 `EvolutionLoop` 编排器把完整流水线显式串起来。

---

## 二、新增能力（4 个新模块）

| 模块 | 职责 | 对应环节 |
|------|------|---------|
| `nucleus/evolution/LogAnalyzer.py` | 运行日志动态归因 | ①发现问题 ②精准定位 |
| `nucleus/evolution/DiffArchiver.py` | 标准 diff 归档 + 全链路溯源 | ④修改前后对比记录 |
| `nucleus/evolution/TestGenerator.py` | 动态生成冒烟测试并运行 | ⑤创建测试工具实际运行 |
| `nucleus/evolution/EvolutionLoop.py` | 完整闭环编排器 | 全流程串联 |

### 1. LogAnalyzer —— 日志动态归因（如何发现问题 + 找到准确位置）

不再只统计 ERROR/WARNING 数量，而是把「运行日志 → 具体代码位置」精确关联：

- **解析 Traceback 的 `File "xxx.py", line N, in func`** → 精准提取出错文件 + 行号 + 方法名。
- **解析 ERROR/CRITICAL 日志** → 提取器官名 + 错误摘要，并按「去时间戳」聚合，识别高频故障点（如「控制器导航失败 ×3」）。
- **结合 runtime_metrics 的 error_snapshots** → 把异常现场与代码位置关联。
- **跳过 Traceback 堆栈内容**，避免把 `raise XXX` / `ValueError:` 误判为独立 ERROR。

输出：`list[IssueLocation]`，每个含 `file_path/line/method/error_type/message/count/first_seen/last_seen`。

### 2. DiffArchiver —— 标准 diff 归档 + 全链路溯源（修改前后对比记录）

- **标准 unified diff**：用 `difflib.unified_diff` 生成 `git diff` 同格式的 diff 文件，归档到 `data/evolution/patches/<patch_id>.diff`，可人工 review、可 `git apply`。
- **全链路溯源**：记录「问题 → 定位 → 改码 → 测试 → 应用」的结构化 JSON，归档到 `<patch_id>.trace.json`。
- **总索引**：维护 `trace_index.json`，供查询「框架历史上做过哪些进化、每次改了什么、为什么改、结果如何」。

### 3. TestGenerator —— 动态测试工具生成（创建测试工具实际运行）

每个补丁生成后，根据 `file/method/issue_type` **自动生成针对该修改的轻量冒烟测试脚本**，放进 `data/evolution/tests/` 并实际 `subprocess` 运行：

1. **语法校验**：`ast.parse` 校验修改后代码。
2. **import 校验**：子进程隔离 `importlib.import_module`（含项目根目录注入 sys.path）。
3. **方法存在性校验**：确认目标方法存在且 `callable`。
4. **回归测试**：运行既有轻量脚本（test_parquet_stage_a / verify_patch_coverage）。

### 4. EvolutionLoop —— 完整闭环编排器

把 8 个阶段串成显式流水线：

```
discover_issues()  →  发现问题（日志归因）
       ↓
archive_patch()    →  diff 归档 + 溯源
       ↓
test_patch()       →  动态冒烟测试
       ↓
request_apply()    →  写入「立即应用」请求
       ↓
judge_evolution()  →  健康度对比（回升保留/下降回退）
```

## 五、完整闭环全景

现在框架的自我进化不再是「被动周期自审 + 外部人工兜底」，而是：

```
运行日志动态归因（LogAnalyzer 精确定位 file:line:func）
       ↓
静态规则检测（SelfInspector.detect_code_issues）
       ↓
合并问题队列（日志归因 + 静态规则）
       ↓
进化沙箱推演（EvolutionSandbox）
       ↓
生成补丁（SafeEvolutionExecutor，含核心文件自动批准）
       ↓
副本验证（PatchManager.verify_in_copy：语法+import+回归）
       ↓
diff 归档 + 全链路溯源（DiffArchiver）
       ↓
动态冒烟测试（TestGenerator 生成并运行）
       ↓
立即应用请求（EvolutionDriver.request_apply_now）
       ↓
主循环检测 → 应用补丁 → 重启
       ↓
三关验证（SelfVerifier）
       ↓
健康度对比（EvolutionDriver.judge_evolution：回升保留/下降回退）
```
