三、全面深度审查清单（本窗口核心任务）
这是本轮审查的完整维度清单。不是只做其中几项，而是十层全部覆盖。每条都要定位到 文件:方法:行号，禁止泛泛而谈。
第一层：基础规范层（静态工具即可覆盖）
用 compileall/ruff/mypy/bandit 全量扫描，逐项核实：
1. 语法与编译正确性：语法错误、未定义变量、导入缺失、参数不匹配、返回值类型错误
2. 编码规范与风格：命名、缩进、注释、导入顺序、文件头模板
3. 类型安全与类型契约：类型注解缺失、类型不匹配、隐式转换、接口出入参不一致
4. 依赖与包管理：未使用依赖、版本冲突、循环依赖、废弃/漏洞依赖
5. 基础代码异味：死代码、重复代码、过长函数、过大类、魔数、空 catch
重点关注：v25.1 新增的 runtime_metrics.py/parallel_scheduler.py/tooling_runner.py/exploration_audit.py 是否完全通过工具检查。
第二层：工程质量层（规则引擎 + 浅语义）
对应 CODE_STYLE 的反模式 AP1-AP70，重点：
1. 并发安全：锁粒度、死锁、竞态、线程池误用、无锁共享变量、重入（AP5/AP8/AP53/AP54/AP63）
2. 资源泄漏：文件句柄、网络连接、缓存无上限、队列积压、subprocess 未回收（AP70）
3. 错误处理：异常吞噬、静默失败、重试缺失、超时缺失、降级路径（AP47）
4. 数据一致性：持久化原子性、快照读写、跨模块状态同步、缓存与主存一致（AP61）
5. 模块耦合：跨模块直接调用、循环依赖、隐式全局变量、反向依赖（AP1/AP67）
6. 性能瓶颈：O(n²) 遍历、重复查询、无索引查找、阻塞调用（AP54）
7. 单例与全局状态安全：单例初始化竞态、全局变量无锁、状态残留、重复初始化（AP63）
8. 可维护性：职责不清、过长方法、深层嵌套、重复逻辑、硬编码（AP23/AP28/AP32）
第三层：架构设计层（深度语义分析）
1. 架构分层与边界清晰度：九大系统分层是否合理、边界是否清晰、职责是否越界
2. 接口契约一致性：调用方期望字段 vs 提供方输出字段、脉冲 payload vs 订阅方读取字段（AP17）
3. 循环依赖：模块间/类间/启动顺序循环依赖
4. 扩展性与开闭性：新增器官是否需要改核心代码、插件化程度（规则8）
5. 可测试性：组件可独立测试、依赖可注入、边界可模拟
6. 生命周期管理：初始化顺序、停止顺序、资源释放顺序、重启状态残留（规则4/12）
第四层：逻辑闭环层（核心价值区，最深的一层）
这是 PulseNet 这类事件驱动架构的命门，必须逐链路追踪：
1. 端到端链路闭合性：发射的事件是否有订阅方、产生的数据是否有消费方、触发的信号是否有后续处理
2. 假闭环/伪功能：有日志但实际没执行、有保护但实际不生效、有接口但实际是空实现（AP55/AP56/AP57/AP58）
3. 逻辑断层：上游产出下游需要但中间缺传递环节、A 期望的字段 B 从未提供
4. 触发条件有效性：阈值过高永远不触发、冷却过长、依赖未初始化的模块（AP52）
5. 降级兜底有效性：异常后业务是否正常、降级路径是否可观测、兜底是否静默失效
6. 能力完整性：应有能力缺失、预留接口被当成已实现（v10.0 预留）、配套机制缺失
7. 类型契约匹配：蒸馏/生成的规则类型是否被下游消费方识别、是否存在类型不匹配静默丢弃（AP14）
第五层：运行时质量层（结合日志/埋点）
1. 运行时并发验证：实际死锁、真实竞态、锁等待时长、线程池阻塞（读 runtime_metrics）
2. 性能与吞吐：脉冲耗时、队列深度、CPU/内存占用、热点函数
3. 资源泄漏验证：长时间运行的句柄/内存/连接/队列增长趋势
4. 时序与顺序：事件顺序、消息乱序、周期任务重入、优先级反转
5. 稳定性与故障复现：异常触发条件、崩溃堆栈、故障传播路径
第六层：安全与合规层
1. 输入验证与注入：SQL 注入、命令注入、代码注入、未校验输入（AP69）
2. 路径遍历与权限绕过：文件路径拼接未净化、权限校验缺失、越权
3. 敏感信息泄漏：密钥硬编码、敏感信息打日志、密码明文（AP21/AP68）
4. 供应链安全：依赖库漏洞、废弃组件、恶意依赖
5. SSRF 防护：nucleus/ssrf_guard.py 的 is_safe_http_url 是否覆盖所有出站请求（本轮刚修复了文件名 bug，需验证所有调用方都真正命中）
第七层：PulseNet 专项架构维度
1. 脉冲通信专项：TTL 有效性、优先级调度、幂等真实性、风暴策略、订阅匹配（规则1/7/14）
2. 器官生命周期专项：启动注入顺序、停止资源释放、状态残留、注册注销完整性（规则4/12）
3. 信息场专项：四层调度正确性、负载降级、线程池隔离、积压处理（规则11）
4. 终身学习闭环专项：规则产出-消费匹配、学习结果落地、反馈链路闭合、规则过期清理
5. 记忆分层专项：快照一致性、检索命中率、遗忘机制、跨层同步（规则5/12）
第八层：层级交叉校验（自增强闭环）
不只分层独立审查，还要打通：
1. 下层疑点→上层验证：规则引擎标出的并发风险/泄漏嫌疑，推到运行时埋点做采样验证
2. 上层结论→下层实锤：LLM 审查发现的假闭环/架构反模式，沉淀成新规则（反哺 self_inspector）
3. 运行时异常→定向审查：埋点捕捉的队列积压/锁等待/重入，触发 LLM 对对应模块定向深审
4. 审查-修复闭环：发现问题必须打通到解决（发现→分析→修复→验证→审批→应用→回流），不止于出报告
第九层：能力完备性与薄弱点专项（不是找 bug，是找"该有但没有"）
前八层是「缺陷发现」，这一层是「能力盘点」。要回答：框架该具备的能力，有哪些缺失、有哪些是空壳、有哪些质量不足？
1. 能力清单盘点：按「感知/分析/决策/行动/反馈」五类，列出框架当前已有能力，逐一标注成熟度（成熟/半成品/空壳/预留）
2. 缺失能力识别：对照宪法、全景图、设计文档的「设计意图」，找出「该实现但完全没实现」的能力
3. 预留接口核查：所有标注「预留 vX.X」的空接口，是否被业务链路真实调用、空实现是否导致链路断裂（这是历史反复踩的坑）
4. 能力质量评估：已实现的能力是否「能用但不精准/不完整」，而非简单判断「有无」
5. 能力组合缺口：单项能力都有，但组合起来缺中间环节（如：能检测问题、能生成补丁，但缺「自动验证补丁是否引入新问题」）
关键：这一层禁止只输出「缺什么」的空话，每个结论必须附「该能力的证据代码 + 对应设计文档依据」。
第十层：框架整体性与能力串联驱动专项（最容易被忽略，也最关键）
前九层都是「点状/线状」审查，这一层是「面状/整体性」评估。核心问题：框架的诸多能力是「各自为战的孤岛」，还是「串成一条感知→分析→决策→行动→反馈的整体闭环」？
1. 整体闭环链盘点：追踪这条主链是否每一环都真实接通——
感知异常（运行时埋点/日志/硬件）
  → 分析定位（工具层/self_inspector/LLM 定向审查）
  → 决策（大脑皮层/动机循环/激素）
  → 行动（补丁生成/审批/自动应用/重启）
  → 反馈（验证学习枢纽/体验池/蒸馏）
  → 回灌提升（规则反哺/语义增强/并行调度优化）
找出链上哪一环「产出无人消费」或「环节间缺传递」。
2. 能力孤岛识别：逐一核对已建成的能力是否被真正调用、调用方是否有后续消费。重点核查这批 v25.1 新增能力是否「建了但没串起来」：
• runtime_metrics（埋点数据是否被代码学习/健康 UI 消费）
• parallel_scheduler（是否真正统一了各模块并行，还是各模块仍各用各的线程池）
• tooling_runner（工具结果是否进入蒸馏/修复闭环）
• exploration_audit（三通道审查结果是否被消费，还是只出报告）
• 本地语义理解 7 项（是否真正参与意图路由，还是只算出来没用于决策）
• verification_learning_hub（蒸馏出的规则是否被下游复用，还是只记录）
3. 串联驱动缺口：哪些能力「单独能跑、但没被主流程驱动」——例如：探查编排是否只被心跳低频触发、运行时异常是否真的触发 LLM 定向审查、蒸馏规则是否真的反哺规则引擎。
4. 整体一致性：同一概念在多处实现是否口径一致（如负载分级阈值、人格模板、规则类型），避免「A 模块和 B 模块对同一件事的判断互相矛盾」。
5. 整体演进方向：基于整体性评估，给出「下一步该优先串联哪条链、补齐哪个断点」的架构级建议，而不是零散修 bug。
这一层的输出目标：画出一张「当前能力串联全景图」，标注每条链的闭合/断裂状态，让框架从「一堆器官」变成「一个真正协作的整体」。
