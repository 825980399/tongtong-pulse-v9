三、方案设计（分三期，按风险/收益排序）
第一期：硬件 tier 驱动器官降级（R1，核心闭环）
目标：让硬件 tier 真正影响器官装配，实现「低配保命、高配全开」。
方案：新增配置开关 use_hardware_tier_degradation（默认 False）。
• 启动装配前，PulseHardwareLauncher 提前评估 tier（用真实硬件数据）。
• _init_organs 读取 tier，低配时自动关闭非核心器官（复用现有 feature_flag 机制）：
• minimal：仅核心（心脏/大脑皮层/内在世界/胃/嘴巴）
• standard：核心 + 功能（视觉/运动/内分泌等）
• high：全开
风险：中等（涉及装配核心）。需处理器官依赖关系（关闭器官时其依赖方降级）。
第二期：硬件检测维度扩展（R2/R3）
目标：补齐检测维度，让「看家底」看得更全。
方案：PulseTouch 新增采集：
• CPU L1/L2/L3 缓存（读 /sys/devices/system/cpu/cpu0/cache/index*/size）
• GPU 共享显存（nvidia-smi 的 shared memory，或 /sys 集成显卡）
• 磁盘类型（SSD/HDD 判定）与 I/O 速率
风险：低。纯增量，不影响现有字段。
第三期：运行时自适应智能化 + 不设上限（R4/R5）
目标：让运行时调整更「智能」，且不硬编码上限。
方案：
• 引入「负载学习」：InfoField 记录历史负载 → 自适应调整线程池（而非固定阈值）。
• 澄清并移除硬件资源硬上限：内存池容量（max_hot 等）是业务容量非硬件上限，保持可配置；真正涉及硬件的地方（线程池、缓存）改为「按检测到的硬件能力动态计算，无人工上限」。
风险：中高（涉及调度核心，需长稳验证）。
第四期：C/Python 混合架构落地（R6）
目标：把已预埋的 Cython 扩展在目标环境编译落地，并扩展底层硬件操作用 C。
方案（分两步）：
1. 编译落地：用 setup_cython.py 在目标平台（Linux/Windows）编译 3 个已有扩展，验证 fallback 切换正确。
2. 扩展底层 C 操作：新增 nucleus/hardware/ Cython 模块，把硬件检测的底层 syscall/文件读取（/proc、/sys、nvidia-smi 解析）下沉到 C，Python 只做封装。
风险：高（涉及编译工具链、跨平台、A/B 性能验证）。建议单独立项，不与前三期混在一起。

#

问题本质
