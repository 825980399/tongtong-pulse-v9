## 一、动机与目标

### 1.1 现状问题

| # | 问题 | 源码证据 |
|---|---|---|
| 1 | 全部 LLM 智能依赖单一 DeepSeek 端点，无成本观测 | config.py:961-997（REMOTE_API_CONFIG） |
| 2 | 免费额度（智谱/火山/百炼）无法利用，轮换渠道需改代码重启 | 9 个调用点读同一配置块 |
| 3 | 限流形同虚设：全局信号量只有 PulseLung 接入，其余 8 处调用方不限流 | nucleus/api_rate_limiter.py:45-80 |
| 4 | 配置里 `deepseek-v4-flash/pro` 走的端点与官方渠道未核实，模型名真实性存疑 | config.py:967/970 |

### 1.2 目标架构

```
PulseLung 及 8 个调用方（零改动，仍读 REMOTE_API_CONFIG）
        │  http://localhost:3000/v1/chat/completions
        ▼
┌─────────────────────────────────────────────┐
│  本地网关（New API，exe 直接运行，SQLite）      │
│  · 模型名映射 · 优先级/权重分流 · 失败重试      │
│  · 用量统计 · 渠道健康监控                     │
└─────────────────────────────────────────────┘
   │(高优先级)      │(低优先级)      │(低优先级)     │(兜底)
   ▼               ▼               ▼             ▼
 DeepSeek官方    智谱GLM-4.7    火山豆包        Ollama本地
 deepseek-v4-   -Flash         doubao-seed    localhost:11434
 flash/pro      (永久免费)      (每日重置)     (离线兜底)
 (付费,敏感链路)
```

**核心收益**：框架侧理想情况只改 config.py 一个配置块；渠道增删、免费轮换、模型映射全部在网关 Web 界面完成；统一用量统计补上成本观测短板。

## 二、网关选型结论

| 项目 | Star | 状态 | Windows 无 Docker 部署 | 结论 |
|---|---|---|---|---|
| **New API**（QuantumNous） | 47.7k | v1.0.0-rc.36（2026-09-08），几乎每日发版 | ✅ Releases 提供 new-api exe（约 132MB），双击即跑，默认端口 3000，SQLite 零配置 | **推荐** |
| LiteLLM（BerriAI） | 58.4k | 1.100.1，极活跃 | ✅ `pip install litellm[proxy]`，YAML 声明式配置 | 备选（与 Python 栈同构，但 2026-08 曝过服务端模板注入 RCE 漏洞 CVE-2026-42203，需及时升级） |

**选 New API 的理由**：活跃维护 + Web 管理界面（渠道/令牌/看板）+ Windows 原生 exe 免 Docker + 继承 One API 全部功能（渠道管理、负载均衡、失败重试、按成功率自动禁用、模型映射）。个人单机场景 SQLite 足够，无需 MySQL。

## 三、渠道分级设计（核心策略）

### 3.1 隐私分级原则

> 进化闭环外发的是自身源码与知识库，免费档普遍允许记录数据。因此**敏感链路走付费 DeepSeek 官方**（V4-Flash 闲时输入 ¥1.5/百万 token，成本极低），免费额度只承接数据不敏感环节。

### 3.2 渠道与模型分级表

| 渠道 | 端点 | 模型（2026-09 有效名） | 免费方式 | 网关优先级 | 承接任务 |
|---|---|---|---|---|---|
| DeepSeek 官方 | `https://api.deepseek.com` | `deepseek-v4-flash`（0731）、`deepseek-v4-pro`（0813） | 付费（峰谷计价：Flash 闲时 ¥1.5/¥4.5 每百万） | **高**（对外名 deepseek-v4-pro / v4-flash 直接路由） | 补丁生成、SelfReflection、SafeEvolutionExecutor 审查——全部含源码的敏感链路 |
| 智谱 BigModel | `https://open.bigmodel.cn/api/paas/v4` | `glm-4.7-flash`（200K 上下文） | 官方免费（并发约 1-2，响应偏慢） | 低 | 对话闲聊、OCR 增强、搜索词提炼——数据不敏感且对延迟不敏感 |
| 火山方舟（豆包） | `https://ark.cn-beijing.volces.com/api/v3` | `doubao-seed-2-0-pro-260215` 等（名称+日期后缀） | 每模型每日 50 万 token（0 点重置，第三方实测口径；接入条件以控制台为准） | 低 | L1→L2 知识压缩等周期性批量任务（注意：若采用官方定价的 DeepSeek 托管版 `deepseek-v3-2-251201` 需另行评估） |
| 阿里百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | Qwen 系列 | 每模型 100 万 token，**90 天有效**（免实名） | 低 | 短期冲刺用（如大重构期），不做长期依赖 |
| Ollama 本地 | `http://localhost:11434` | 本地已拉取模型（如 qwen3:8b） | 永久免费、离线 | 最低（兜底） | 网络中断时兜底 |

### 3.3 对外模型名映射（框架零改动的关键）

网关保持与现配置相同的对外模型名，框架完全无感知：

| 对外名（框架看到的） | 实际路由 |
|---|---|
| `deepseek-v4-pro` | DeepSeek 官方 v4-pro（高优先级）→ 失败时降级智谱 glm-4.7-flash（次级渠道） |
| `deepseek-v4-flash` | DeepSeek 官方 v4-flash（高优先级）→ 火山豆包（次级）→ Ollama（兜底） |

> 说明：当前 config 中的端点直连 `api.deepseek.com`，模型名与官方现行模型一致（2026-07-24 后 deepseek-chat/reasoner 别名已退役，v4-flash/pro 为现行名）——此前报告"模型名疑似占位"的判断修正为：**模型名真实，端点真实**，但建议顺带核实该 API Key 的来源渠道是否为官方。

### 3.4 任务-通道路由（网关侧模型映射实现）

New API 的"模型重定向"（JSON，左为对外名/右为实际名）+ 渠道优先级/权重组合即可实现，无需框架感知：

- 补丁生成链路（LLMEvolutionEngine、SafeEvolutionExecutor）→ 请求里带 `deepseek-v4-flash` → 高优先级渠道 = DeepSeek 官方（敏感数据不出付费渠道）
- 后台批量链路（知识压缩、节点提炼）→ 网关侧将此类请求的低峰时段调度交给豆包渠道（如需更细粒度按任务分流，见第五章 P2 可选项）

## 四、对接实施清单

### 4.1 网关部署（一次性，约 15 分钟）

```bash
# 1. 下载 https://github.com/QuantumNous/new-api/releases 的 Windows exe
# 2. 运行（默认端口 3000，SQLite 零配置，初始账号 root/123456，首登必改密）
# 3. 登录 http://localhost:3000 → 渠道 → 添加：

#    渠道1：DeepSeek 官方
#      类型=DeepSeek  密钥=官方API Key
#      模型=deepseek-v4-flash,deepseek-v4-pro   优先级=高
#    渠道2：智谱
#      类型=智谱  密钥=BigModel Key
#      模型=glm-4.7-flash   优先级=低
#    渠道3：火山方舟
#      类型=OpenAI  Base URL=https://ark.cn-beijing.volces.com/api/v3
#      模型=doubao-seed-2-0-pro-260215 等   优先级=低
#    渠道4：Ollama
#      类型=OpenAI  Base URL=http://localhost:11434  密钥=任意（如 ollama）
#      模型=本地模型名，模型重定向 {"deepseek-v4-flash":"qwen3:8b"}   优先级=最低

# 4. 令牌 → 创建一个无限额令牌（即框架用的 API Key）
# 5. 设置 → 运营设置 → 配置失败重试次数（建议 2 次）
```

### 4.2 框架侧改动（最小面）

**必改（1 处）**：config.py:968-997 的 `REMOTE_API_CONFIG`：

```python
"api_url": "http://localhost:3000/v1/chat/completions",  # 含完整路径（原配置即此格式）
"api_key": "<网关令牌>",
# default_model / advanced_model 保持 deepseek-v4-flash / deepseek-v4-pro 不变
```

改后**必须重启进程**：`REMOTE_API_CONFIG` 在热重载黑名单中（config.py:2485-2492），且 ssrf_guard 的受信主机缓存只初始化一次（ssrf_guard.py:35-39，会自动把 api_url 主机加白，localhost 没问题，但不重启缓存不刷新）。

**可不改但建议顺手统一（6 处兜底默认值）**：PulseLung.py:200/202/204/526、PulseController.py:1502、PulseSpiritualCore.py:529、PulseInnerWorld.py:8146/18708、ocr_engine.py:136、LLMEvolutionEngine.py:41、SelfReflectionEngine.py:36 的 `.get("default_model", "deepseek-v4-flash")` 兜底值——只要配置字段非空就不会触发，暂不动也安全。

**必须提前核实的坑（3 处硬编码）**：`SafeEvolutionExecutor.py:645/1958/2052` **直接写死 `"model": "deepseek-v4-flash"` 不读配置**。因网关对外名保持同名，这三处实际不用改；但未来若改对外模型名，这三处必改——建议列入技术债清单。

### 4.3 已知注意事项

| # | 事项 | 说明 |
|---|---|---|
| 1 | 超时设置碎片化 | 各调用点硬编码 10/15/30/60 秒不等（config 的 timeout 字段无代码读取）。网关转发增加一跳延迟后，PulseController 的 timeout=10 可能偏紧，接入后优先观察这条链路 |
| 2 | 限流不完整 | 除 PulseLung 外 8 个调用方不走 api_rate_limiter。接入网关后限流可下沉到网关侧按渠道配置，反而是改善 |
| 3 | Ollama 降级不经过网关 | PulseLung 的 `_call_ollama` 走原生 `/api/generate`（PulseLung.py:1111/1191，base_url 硬编码 ：42），独立于网关链路，维持现状即可（双保险） |
| 4 | 免费渠道条款 | 智谱/火山/百炼免费档均可能记录数据用于训练，第 3.1 节的分级原则必须执行——含源码/知识库的请求只走付费 DeepSeek 渠道 |
| 5 | New API 升级 | rc 版本迭代快，建议固定一个验证过的版本，升级前看 changelog |
| 6 | LiteLLM 备选 | 若未来想要声明式配置与 Python 同栈，可切 LiteLLM（`pip install litellm[proxy]` + config.yaml），但注意其 2026-08 的 RCE 漏洞历史，保持升级 |
