## 一、结论先行

**`baseline_errors=0` 不是"采集时机不对"，也不是"对比逻辑写错"，而是「基线样本源根本不存在」。**

五层根因，按贡献度排序：

| # | 根因 | 性质 | 实测证据 | 贡献度 |
|---|---|---|---|---|
| **R1** | **日志源已轮转/截断** —— 100% 补丁早于当前 `pulse.log` 首行 | **数据基座断裂（主因）** | 日志覆盖 11.9h；补丁时间跨度 09-04→09-11；**67/67 与 60/60 补丁 100% 早于日志首行** | ★★★★★ |
| **R2** | **ERROR 样本极度稀疏** —— 全天仅 2 行 ERROR | 样本稀薄 | ERROR 2 行 / 47608 行 = **0.004%**；INFO+DEBUG = 99.13% | ★★★★☆ |
| **R3** | **日志格式不含文件名** —— 含 `.py` 的行仅 0.75% | 匹配判据失效 | `.py` 出现 357/47608 行；格式为 `[模块] 级别: 消息` | ★★★☆☆ |
| **R4** | **验证语义错配** —— 通过的定义是"没弄坏"而非"修好了" | **设计缺陷（本质）** | `verification.stage=regression_test_passed`、`regression="2通过/0失败"` | ★★★★★ |
| **R5** | **`None`（缺失）与 `0`（真实为零）被混同** | 数据质量 | 评估器自认 **62 条 `unverifiable`、仅 2 条 `real_effectiveness_computable`** | ★★★☆☆ |

> **一句话**：当前机制把「修复前错误基线」寄托于**在历史日志里考古**，而考古现场（历史日志）已被清空，且现场本身也几乎不埋 ERROR、不写文件名。
> 更根本的是——**即便基线拿到了，"验证通过"也只意味着"改完没弄坏"，不等于"问题被修好了"**。

### 2.2 质量评估器已自认不可判定

`patch_quality_report.json` 的 `summary` 字段（框架自己算的）：

```json
{
  "fake_pass": 2, "unverifiable": 62, "not_applied": 3,
  "good": 0, "mediocre": 0, "bad": 0,
  "avg_score": 76.9, "applied": 56, "verified": 64,
```

**关键读数**：
- `real_effectiveness_computable = 2` → 67 条补丁里**只有 2 条**能算出真实有效率

- `claimed_effectiveness_avg = 0.9766` → 但"声称有效率"高达 **97.66%**
- `good/mediocre/bad **全为 0**` → 评级体系事实上**从未产出过任何有效分级**

> ★ 这是"质量分虚高"（P0-4）在补丁领域的直接投影：**声称 97.66% 有效，实测 3% 可判定**。

### 2.3 多档位重算：无论如何调参都救不回来

对全部补丁位置，在**真实 `pulse.log`** 上重跑错误计数（`since` 取 全量/1天/7天/30天 × 匹配档位 取 `file`/`file_or_method`/`file_method`）：

| `file`（当前生产配置） | 全量 / 1 / 7 / 30 天 | 67 | **6** | **9.0%** | 90 |
| `file_or_method` | 全量 / 1 / 7 / 30 天 | 67 | **6** | **9.0%** | 90 |
| `file_method`（第41批前旧判据） | 全量 / 1 / 7 / 30 天 | 67 | **1** | **1.5%** | 15 |

（`patch_history.json` 同法测得 4/60 = **6.7%**）

**★决定性观察**：**四种窗口的结果完全相同**（6/6/6/6）。

这说明——**窗口设置不是问题**。日志总共只覆盖 11.9 小时，1 天窗口与 30 天窗口自然等价。

## 三、五层根因详析

### R1 · 日志源已轮转/截断（主因，贡献度 ★★★★★）

**取证输出**：

```
[R1] logs/ 目录全景
   pulse.log                    5.78 MB  2026-09-13 23:21
   pulse_crash.log              6.19 MB  2026-09-08 23:23
   pulse.log 首行时间: 2026-09-13 11:30
   pulse.log 末行时间: 2026-09-13 23:21
   ★日志覆盖跨度: 11.9 小时

[R1-b] 补丁生成时刻 vs 日志覆盖范围
   patch_quality_report.json
      补丁时间戳: 2026-09-04 01:18 → 2026-09-11 02:04
      ★早于日志首行的补丁: 67 / 67 (100.0%)
   patch_history.json
      补丁时间戳: 2026-09-04 01:18 → 2026-09-11 02:04
      ★早于日志首行的补丁: 60 / 60 (100.0%)
```

**结论**：`baseline_errors` 的采集窗口是 `[now - 7d, now]`，而补丁全部生成于 **09-04 ~ 09-11**，
`pulse.log` 却只从 **09-13 11:30** 开始 → **样本源与补丁时间轴完全不相交**。

任何基于当前 `pulse.log` 的基线采集，**必然**返回 0。第41批的回填工具
（`tools/backfill_baseline_errors.py`）即使再跑 100 次，结果也一样 —— 它读的是同一个已被截断的日志。

**这解释了为什么第41批修过一次（P0-263）、第42批又修一次，问题依旧**：
前两批修的是**判据**（`file_method` → `file`）和**窗口**（`since=0` → `now-7d`），
但**没碰数据基座**（日志留存）。判据再准，考古现场空了也是白搭。

### R2 · ERROR 样本极度稀疏（贡献度 ★★★★☆）

```
[R2] 日志级别分布
   INFO      26787  (56.27%)
   DEBUG     20404  (42.86%)
   WARNING     219  ( 0.46%)
   <无>        196  ( 0.41%)
   ERROR         2  ( 0.00%)      ← 全天 11.9 小时仅 2 行
```

**结论**：即便日志完整覆盖补丁时刻，随机一个文件位置能命中 ERROR 的概率也极低。
实测 67 个位置只有 6 个（9.0%）命中，且这 6 个命中的合计 90 条错误，**高度集中在极少数热点文件**
（`PulseLiver.py` 单文件独占 15 条）。

> 副作用：基线一旦 >0，也往往是**文件级热点噪声**，而非"该方法真的有 N 个错"。

### R3 · 日志格式不含文件名（贡献度 ★★★☆☆）

```
[R3] 日志行格式样本
   | 2026-09-13 11:30:21 [框架] INFO: 初始化 曈曈 v9.5 PulseNet...
   | 2026-09-13 13:16:35 [肝] DEBUG: 压缩信任评估: 新L2节点信任=60 (源L1平均=52)
   | 2026-09-13 20:18:22 [PulseSnapshot] DEBUG: 增量保存检测到零变更，跳过写盘（防御性校验）

   ★含 '.py' 文件名的日志行占比: 357 / 47608 (0.75%)
```

**结论**：框架日志以 `[器官中文名]` 为前缀，**从不写 `.py` 文件名**。
第41批把判据从 `file_method`（文件名+方法名同时出现）放宽到 `file`（仅文件名），
命中数从 1 → 6，已榨干该判据的潜力；但受限于只有 0.75% 的行含文件名，天花板就是 9%。

### R4 · 验证语义错配（本质缺陷，贡献度 ★★★★★）

这是最容易被忽略、却最关键的一层。

**当前"验证通过"实际做了什么**（取自 `patch_history.json` 的 `verification` 字段）：

```json
{
  "passed": true,
  "stage": "regression_test_passed",
  "errors": [],
  "verify_depth": "standard",
  "import":   { "ok": true, "reason": "副本 patch_copy_PulseHeart import 成功",
                "sandbox": { "duration_ms": 125 } },
  "regression": "2通过/0失败",
  "behavior":  { "checked": false, "equivalent": true, "reason": "依赖 self 状态，非纯函数" },
  "signature": { "checked": false, "consistent": true,
                 "reason": "方法 refresh_runtime_params 在修改前/后无法定位，跳过签名校验" },
  "verify_entries": ["syntax", "import", "regression", ...]
}
```

**逐项拆解其真实含义**：

| 检查项 | 实际结论 | 是否证明"修好了" |
|---|---|---|
| `syntax` | 补丁后代码语法合法 | ❌ 只证明能解析 |
| `import` | 副本能成功导入 | ❌ 只证明不炸在导入期 |
| `regression` "2通过/0失败" | 关联测试未被弄坏 | ❌ 只证明**没弄坏** |
| `behavior.checked = false` | **行为等价性根本没检查** | ❌ 明确跳过 |
| `signature.checked = false` | **签名一致性根本没检查** | ❌ 明确跳过（"无法定位"） |

> ★★ **核心结论**：`verification.passed = true` 的语义是
> **"改完之后没有变得更糟"**（No-Regression），
> 而 `baseline_errors → after_errors` 想表达的语义是
> **"改完之后问题真的消失了"**（Problem-Fixed）。
>
> **这两件事在当前系统里被合成了一个布尔值 `verified`。**
> 于是"没弄坏"被当成"修好了"上报，这就是任务书所说的**假通过**。

即便把 R1~R3 全部修好、基线采集正常，只要这个语义合成不改，
`verified=true` 依然只代表 No-Regression —— **空转不会真正结束**。

### R5 · `None` 与 `0` 被混同（贡献度 ★★★☆☆）

- `patch_history.json`：`baseline_errors` **字段缺失 2 条**、值为 `None`
- 采集函数 `_count_errors_for_location` 在**任何异常**下都 `return 0`：

```python
except Exception as e:
    _module_logger.debug("统计位置错误数失败（按 0 处理）: %s: %s", type(e).__name__, e)
    return 0
```

**后果**：

| 真实情况 | 写入值 | 下游理解 | 后果 |
|---|---|---|---|
| 日志不存在 / 采集失败 | `0` | "修复前 0 个错" | **把"不知道"伪装成"没问题"** |
| 该位置确实 0 个错 | `0` | "修复前 0 个错" | 正确，但无法与上一种区分 |

→ `effectiveness = (baseline - after) / baseline` 在 `baseline=0` 时**除零**，
代码只能退化为 0 或 1，最终堆出 `claimed_effectiveness_avg = 0.9766` 的虚高数字。

## 五、影响面

| 维度 | 现状 | 影响 |
|---|---|---|
| 补丁效果可判定率 | 2 / 67 = **3.0%** | 无法区分"有效修复"与"无效但无害" |

## 七、修复方向（详见《补丁验证机制修复方案_v1.0.md》）

| 层 | 方向 |
|---|---|
| R1 | **主动基线（Active Baseline）**：补丁应用前对目标位置执行**一次性复现探针**测 `before_errors`，不再依赖历史日志 |
| R2 | 引入**结构化错误事件流**（不依赖日志文本考古），或至少提升 ERROR 留存密度与留存期 |
| R3 | 日志格式增加 `file:line` 结构化字段；或改由探针直接产出，绕开日志匹配 |
| R4 | **拆分验证语义**：`no_regression`（现有）与 `problem_fixed`（新增）分开记录，禁止合成单一 `verified` |
| R5 | 基线打 `baseline_source` 与 `baseline_confidence`；`None`/未知**不得**落为 0，必须显式 `unknown` |
