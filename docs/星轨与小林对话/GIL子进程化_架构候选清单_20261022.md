## 1. 要解决的问题（原始动机）

`run_parallel_audit` 是 CPU 密集的 AST 全仓扫描，跑在活体主进程里 ⇒ 与心跳/对话**争 GIL**：

- 单次审查约 12 分钟一轮，扫描期其它协程的时延被拉长；
- 审查期间 `pulse.log` 的心跳间隔出现尖峰（非业务成因）；
- 审查与派单同进程 ⇒ 审查卡住时派单也卡住，"两条链互相拖"。

子进程化能同时解掉三点：**CPU 并行**、**故障隔离**（审查崩了不带走活体）、**时延解耦**。

## 2. 候选方案 A：审查全量外置子进程（洞鉴原方案）

**做法**：`run_parallel_audit` 改为 `subprocess` 拉起 `tools/audit/audit_worker.py`，父进程只收结果；中间进度用 **InfoField 单向消息**回主进程（`nucleus/field/InfoField.py`）。

**代价（必须先量清，不能拍脑袋）**

| 项 | 风险 | 量化口径 |
|---|---|---|
| 启动开销 | 每次审查冷启动 Python + import 全仓模块 | 实测 `python -c "import nucleus.main"` 冷启耗时；与 12min 周期比是否可忽略 |
| 数据一致性 | 子进程读 `data/` 时父进程在写（节点池/补丁池） | 需要快照式读取或只读窗口 |
| 消息通道 | InfoField 是**主进程内**的事件场，不是 IPC | 需确认能否承载跨进程消息；不能就得新开管道（新增面） |
| 产物归属 | 子进程产物落盘位置必须与主进程一致，否则重演 A-17（验证产物进生产目录） | 必须先有域过滤（344 补3 已落地） |
| 可观测性 | 子进程日志不能直接进 `pulse.log`（A-17 同一教训） | 走 stdout 归集 + 父进程单点写 |

**结论**：收益真实，但**新增面（IPC + 产物归属 + 日志归集）大于本批可验证范围** ⇒ 后置。

## 3. 候选方案 B：只把「沙箱验证」外置（更小切口）

**做法**：不动审查，只把 `dispatch_and_verify` 的沙箱调用放到常驻 worker 池（2-3 个 `python -I` 子进程，长连接 stdin/stdout）。

**为什么可能更划算**

- 沙箱**本来就已经是子进程**（`sandbox_limits.execute_code_in_subprocess`）⇒ 只是把"每次 spawn"改成"常驻复用"，不新增 IPC 语义；
- 345 刀6 已把验证环节改成 `ThreadPool` 并发（`verify_patches_concurrent`，默认 2）；**它是 GIL 挡着的**——真并行必须多进程 ⇒ 这是从现有实现**自然长出来**的下一步；
- 派单仍串行 `hard_cap=1`，安全闸不动。

**要先回答的问题**

1. 常驻 worker 的**状态污染**：同一个子进程连续跑多个补丁，`_g` 里残留前一个补丁的符号 ⇒ 可能把"缺 import"兜成假阳（344 补2 刚把注入面收窄，别在这里破功）。**对策**：每补丁一次 `exec` 后清 `_g`，或干脆一补丁一进程（那就退回现状）。
2. 常驻 worker 的**生命周期**：活体重启时孤儿进程清理；超时补丁要不要杀 worker。
3. **失败归因**：worker 崩溃 vs 补丁报错，必须能分开（现在靠 returncode + stderr 标记，可复用）。

## 4. 不建议的方向

- **不建议**把审查与派单放同一个子进程：两者失败模式不同，合起来会让"审查崩了"表现为"派单失败"，归因倒退。
- **不建议**用线程池假装解决 GIL：345 刀6 的 `verify_patches_concurrent` 已明确只是**减少串行等待**（沙箱调用本身释放 GIL 的部分是真实的，但 AST/JSON 解析不释放），不要把它写成"并行审查"。

## 5. 排批前置（建议按此顺序）

1. 破零成立（O3 至少 1 条真的 `applied`，不是 cap 豁免刷出来的）；
2. 派单机制稳定 1 个重启窗：`[345cap]` 豁免次数可数、`verify_patches_concurrent` 台账（`data/patches/patch_verify_attempts.jsonl`）无串账；
3. 域过滤已生效（344 补3）：隔离产物不进生产、补丁池不收 `tmp/` 条目；
4. 先做**方案 B 的 1 个 worker 试点**（不是 3 个），量三个数：验证时延、worker 崩溃率、`_g` 残留导致的假阳数；
5. 方案 A 待 B 试点数据出来后再评估。

## 6. 判定标准（避免"做了但没验"）

- 并行度**可观测**：同时活跃 worker 数有读数，不是"看起来快了"；
- 假阳**可数**：`_g` 残留导致的"缺 import 被兜住"必须有计数，且 ≥1 即回退；
- 停/启**可收口**：活体重启后无孤儿 worker（`proc_gen` 与 pid 对表）；
- 失败**可分档**：worker 崩 / 补丁错 / 环境缺，三档各自计数。
