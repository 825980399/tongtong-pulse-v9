## §结论一句话

**自主进化链不是"断在哪一环"，而是断在"本地规则层"与"验证层"两处，且二者互为放大器：**
**本地规则 688 次尝试仅 6 次成功（0.87%），其余 682 次 `no_safe_fix` 全部导向 LLM；而 LLM 补丁的验证又因 `baseline_errors` 全 0 而"假通过"，问题没真修，于是下一轮再调 LLM——这就是 97% 依赖度与 1.8% 自主修复率的共同病根。**

> **可修 or 改口径？答案是"两者都要"**：本地规则层的门槛错位（trust=30 < 门禁 40 却判 approved）=**工程缺陷可修**；验证层 `baseline_errors=0` 假通过=**工程缺陷**（根因是日志被外部清理，属**数据约束**）；依赖度 97% 口径错位=**改口径**。

## T2 逐环节漏斗量化 —— 主断点定位

```
 发现(issue) ──► 记录 8583 条 ──► 调度(EvolutionLoop 在跑)
                    │
                    ├─ 本地规则 688 ──[682 no_safe_fix]──► 塌陷
                    │                    └─[6 success]
                    └─ LLM 生成 110 补丁 ──► 审批 70 通过 ──► 应用 72
                                                              │
                                                    验证 83(形式) ── 真验仅 13
                                                              │
                                                    注入回填 1/56 (1.8%)
```

**主断点 = 本地规则层（第 4 环节）**
- 证据：`local_learning_attempts.jsonl` 688 条中 **682 条 `no_safe_fix`（99.1%）**，success 仅 6 条。
- 机制：`SafeEvolutionExecutor.py:4186` 在"无风险模式"下直接落 `no_safe_fix`，把问题**推给 LLM 通道**（:4068 注释明示"交给既有 LLM 通道"）。
- **次断点 = 验证层（第 7 环节）**：56 补丁 `baseline_errors` 全为 0（假通过），修复前后无区分 → 问题没真修 → 下一轮重现同样问题（总账 P0-263）。
- **第三断点 = 审批口径矛盾**：样例补丁 `trust=30` **低于门禁 40**（config.py:1099）却 `status=approved/applied=True`——**门禁未生效或历史遗留脏数据**。

## T4 LLM 依赖结构分析

**97% 依赖的结构性原因**（总账 P0-262）：实测 97% 依赖度中 **98.8%（2077 次）来自自主进化循环**；对话类 `SCENE_LUNG=0`（全库无埋点）。→ **依赖度指标被"进化循环自调用"污染**，不代表真实对外 LLM 依赖。

**本可本地替代、却依赖 LLM 的环节**：

| 环节 | 现状 | 本地替代方案 | 依赖度降幅预估 |
|---|---|---|---|
| 静默异常捕获 | 本地规则已生成，但 trust=30 < 门禁40 被卡 → 转 LLM | 将此类**确定性规则补丁**信任分上调至 ≥40，或单列低危快速通道 | 高（占本地尝试绝大多数） |
| 单方法级修复 | `no_safe_fix` 直接推 LLM（:4068/:4186） | 扩展"无风险模式"规则覆盖面（if/else、日志缺失等固定模式） | 中-高 |
| 进化效果验证 | `baseline_errors` 全 0，靠 LLM 复算 | 修复日志留存（P0-272）→ 本地可比对 | 中（间接降依赖） |
| 依赖度统计口径 | 进化自调用混入 97% | 区分 `origin=user_query`(309) vs `evolution_task`(4138) 分列 | —— 改口径 |
