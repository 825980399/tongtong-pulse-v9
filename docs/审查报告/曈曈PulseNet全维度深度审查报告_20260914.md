## 二、P0 致命问题

### A1. 核心文件「强制人工审批」被代码移除 —— 直接违反演化宪法

**这是本次审查最严重的发现。**

演化宪法 `BLUEPRINT_CONSTITUTION.md` 2.8.7 节明文规定：

> 核心文件强制人工审批：main.py/config.py/base/nucleus/pulse/field/mnemosyne/reasoning 等基础设施补丁**一律 verified（需审批）**

`CODE_STYLE.md` 21.4 节、宪法第五部分「核心变更审批原则」均重申此铁律，理由是「落实『最终决策权在创造者手中』」。

**但代码已反向修改。** `nucleus/reasoning/SafeEvolutionExecutor.py:2473-2512`：

```python
# ★进化闭环升级(完美级): 核心文件不再强制人工审批，
#   改为「强验证兜底 + 健康度对比 + 自动回退」三重防线共同保障安全。
_is_core = self._is_core_file(patch.get("file", ""))
if _auto_apply:
    ...
    else:
        if _is_core:
            patch["is_core_file"] = True   # ← 仅打标，不再降级为 verified
        patch["status"] = "approved"        # ← 核心文件也自动批准
```

`_is_core_file`（:301）的判定名单与宪法完全一致（main.py/config.py/base/nucleus/pulse/field/mnemosyne/reasoning），但判定结果**只用于打 `is_core_file` 标记**，不再强制 `status="verified"`。只要 `EVOLUTION_CONFIG.auto_apply_enabled=True`，对 `main.py`、`config.py`、脉冲引擎、快照系统的自动补丁即可无人审批直接落地。

- **影响**：自我迭代系统获得了改写自身基础设施（含启动入口、全局配置、脉冲总线、持久化）的自主权，宪法的最高安全约束在代码层失效。三重防线（副本验证/健康度对比/回退）是**事后补救**，无法替代宪法要求的**事前人工闸门**——一个语法正确、能通过副本 import、但语义有害的核心补丁仍会落地。
- **建议**：恢复 `if _is_core: patch["status"] = "verified"` 的强制分支，使核心文件无条件转人工审批；`auto_apply` 仅对非核心、低风险补丁生效。若确需调整此宪法条款，必须走附录 I 修宪流程（技术宪法需两方以上通过），而非以代码注释单方面变更。

### A2. 存储引擎「增量保存」实为整体重写，「百亿级」承诺在当前实现下不成立

`docs/百亿级存储引擎磁盘持久化设计.md` 与进度总表宣称阶段 A（Parquet）/C'（外置索引）/B'（冷存储）/D（按需加载）均已落地验收。实测：

- 主知识快照 `data/knowledge/pulse_knowledge_snapshot.json` 实测 **447.7 MB / 13256 节点**，平均 **34.5 KB/节点**。
- 体积构成：`semantic_relations` 占 **87.2%（381 MB）**，`linked_nodes` 占 11.3%（51 MB），真正的知识正文 `value` 仅占 0.5%（2.3 MB）。
- `PulseSnapshot._incremental_save`（:527）的「增量」逻辑是：`safe_read_json` 把 447MB 整体读入 → 内存合并变更节点 → `_atomic_write_with_rotation` **整体重写 447MB**。增量只省了「序列化变更节点」的 CPU，**完全没有省 I/O**，每次保存仍是近 0.5GB 的读+写。
- Parquet（`IndexStore.py`）、惰性加载（`lazy_snapshot.py` LRU）确实存在，但它们是**旁路索引/视图**，主持久化路径仍是单体 JSON。

**推论**：13256 节点已产生 447MB 快照，线性外推到设计承诺的「百亿级（10^10）」节点，单体 JSON 路径在物理上不可能成立（将达 PB 级且每次全量重写）。当前实现与「百亿级存储引擎」的命名严重不符。

- **影响**：保存耗时随知识库线性增长，节点数到十万级即可能出现分钟级保存阻塞；磁盘占用爆炸（已观察到 3 份 467MB 等量 .bak 轮转备份，单 data 目录 2.9GB）。
- **建议**：① 给 `semantic_relations`/`linked_nodes` 设全局上限并按权重淘汰（见 C2）；② 将主持久化真正迁移到 Parquet 列式 + 分片，使「增量保存」成为只追加分片而非整体重写；③ 在文档中如实标注当前真实承载量级，撤回或限定「百亿级」表述。

## 三、P1 高危问题

### B1. 器官降级（SUSPENDED）状态空转 —— F4 自愈闭环未真正生效

进度总表 1.12/第 37 项宣称「F4 沉默器官分级自愈 alert→restart→degrade 已落地验证通过」。实测：

- `BasePulseOrgan.degrade()`（base/BasePulseOrgan.py:583）置 `status = OrganStatus.SUSPENDED`。
- 但 `_handle_pulse_safe`（:453）只在 `status == OrganStatus.FUSED` 时拦截脉冲；`is_available()`（:551）只排除 `FUSED`。
- 全仓 Grep `SUSPENDED`：**仅** 出现在 base/BasePulseOrgan.py（degrade/recover）与 const.py 定义处，**没有任何分发链路读取它**。

**结论**：器官被「降级」后，状态标为 SUSPENDED，但仍照常接收并处理所有脉冲——降级是**纯标记、零效果**。F4 的 degrade 动作在调度层是空操作，自愈闭环只有 restart 真正有效。

- **建议**：在 `_handle_pulse_safe` 与 `is_available` 中将 `SUSPENDED` 一并纳入拦截（或按设计意图区分「降级=只处理 L0 生命线」）。

### B2. 子进程 GBK 解码崩溃回归（L16 声称已修复）

进度总表 1.6 节标记「L16 subprocess GBK 解码崩溃：4 个文件（统一 encoding）✅ 全部完成」。实测 `tests/test_orphan_event_audit_m10.py` 仍因该问题失败：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x80 in position 35
（subprocess._readerthread → buffer.append(fh.read())）
```

子进程捕获输出未指定 `encoding='utf-8'`，Windows 默认 GBK，遇非 GBK 字节即崩。这是 L16 的**回归或漏修**。

- **建议**：统一所有 `subprocess.run/Popen/check_output` 显式传 `encoding='utf-8', errors='replace'`，并加一条 CI 守卫测试防止再回归。

### B3. 全量测试套件 23 失败 / 8 错误（CI 红灯）

`python -m pytest`：**1771 passed, 23 failed, 8 errors**（耗时 7 分钟）。失败聚集：

| 测试模块 | 失败数 | 性质 |
|---------|-------|------|
| test_tmp_cleanup_m45 | 9 | 依赖 `tmp/` 下产物，已被 ruff.toml 排除/清理，断言文件不存在 |
| test_channel_concurrency_m24 | 3 | LLM 渠道并发切换/降级逻辑 |
| test_quota_monitor_m32 | 4 | 配额监控降级阈值 |
| test_multi_step_retrieval_m31 | 3 | 多步检索渠道分支 |
| test_orphan_event_audit_m10 | 2 | GBK 解码（见 B2） |
| test_request_dedup_m26 | 1 | 肺请求去重 |

部分失败是测试自身脆弱（tmp_cleanup 依赖外部产物），但 channel/quota/retrieval 系列指向 LLM 调度真实逻辑回归。**一个宣称「P0-P4 全部完成、框架总评分 95/100」的项目，测试套件不应是红灯。**

- **建议**：失败用例逐一归因（产品 bug vs 测试脆弱），修复后纳入 CI 必过门禁。

### B4. 补丁「冷却门」对自动应用路径形同虚设

宪法 2.8.7 / CODE_STYLE 21.3 要求补丁落地前三道安全门：信任分 + 风险等级 + **冷却时间**。实测：

- `PatchManager._check_patch_safety`（:1499）第一行：`if patch.get("status") == "approved": return {"safe": True}` —— approved 直接放行，**跳过信任/风险/冷却三关**。
- 自动审批在入队时（`save_pending_patch`:155）就把低风险+高信任补丁置为 `approved`，但**入队时不检查冷却**。
- `apply_all_pending(only_approved=True)`（:1550）只处理 approved。

**结论**：`auto_apply_cooldown`（默认 86400s/24h）这道门对自动应用路径**从未被执行**——补丁入队即 approved，应用时又因 approved 直接放行。冷却门是死代码。

- **建议**：冷却检查应在入队自动审批时执行，或对 auto_approved 补丁在 `_check_patch_safety` 中不跳过冷却门。

### B5. 上帝类 PulseInnerWorld.py：23112 行 / 365 方法

实测 `organs/brain/PulseInnerWorld.py`：

- **23112 行**，1 个类，**365 个方法**；13 个方法 >200 行，57 个 >100 行。
- 最长方法 `_on_inference_request` = **1453 行**；`_knowledge_retrieve` 538 行；`_route_to_deriver` 470 行；`_deep_self_review` 360 行。
- 34 个 `_detect_*/_is_*` 检测器方法（文档先后称 14/17/18 个，均与代码不符）。

项目结构树图自己已标注「⚠️框架最大文件…超负荷路由中枢…与器官协作分层初衷相悖」。单文件 23k 行已超出多数编辑器/审查工具/人脑的有效处理范围，是缺陷滋生与合并冲突的温床，也直接拖累 A1 类安全审查的可执行性。

- **建议**：按职责拆分（推理路由 / 符号推理 / 知识检索编织 / 自我审视 / 元认知报告 至少 5 个独立器官或模块），这也是进度总表「方向 A 拆分上帝类」的待办，应提升优先级。

### B6. 设计文档与代码系统性脱节（文档不可作为可信基准）

项目以 docs 为「唯一事实源」，但实测脱节严重：

## 四、P2 中等问题

### C1. 仓库污染：509MB 备份 + 整项目副本，污染所有工具口径
- 34 个 `.bak_batch*` 目录 = **509MB / 9869 个 .py 副本**；`.release-tmp/` 是一份完整项目副本（26MB）；`data/code_backups/` 多份历史快照；根目录 4 个 `config.py.bak_*`（各 218KB）；一个 **0 字节的 `nul` 文件**（Windows 保留名，易引发工具异常）。仓库总计 **4.2GB**。
- **直接后果**：ruff 全仓统计被 `.release-tmp` 副本翻倍（2475 条 vs 干净范围 1374 条），bandit/搜索/索引全部受污染。
- **建议**：将 `.bak_*`/`.release-tmp`/`code_backups` 移出工作区或纳入 `.gitignore` 并物理清理；删除 `nul` 残留文件。

### C2. semantic_relations 无全局上限，是快照膨胀主因
- `PulseNode.add_semantic_relation`（:720）只做「同目标同类型去重」，**无单节点关系数上限**；PulseLiver 的 `_semantic_quota` 只限单次扫描批次，不限累计。
- 实测平均每节点 159 条关系、最高 1764 条；linked_nodes 平均 156、最高 2228。这是 A2 中 381MB 的直接来源。
- **建议**：为每节点的 `semantic_relations`/`linked_nodes` 设硬上限（如 64），超限按 weight 淘汰最弱关系。

### C3. RUF012 类级可变默认值（59 处）
- 类属性直接赋 `dict`/`list` 默认值，多实例共享同一对象。在「器官零状态」（宪法规则 4）语境下，若器官被多实例化或测试复用，存在跨实例状态串扰风险。
- **建议**：改为 `__init__` 内实例化，或用 `ClassVar` + 不可变默认。

### C4. exec / eval 面（4 处 exec + 3 处 eval）
- `PatchManager.py:1019-1020` exec：用于补丁行为等价探针，已有纯函数判定 + `__builtins__` 隔离 + 全异常兜底，**受控可接受**。
- `PulseInnerWorld.py:9013` `eval(f"{_a}{_op}{_b}")`：入参经正则约束为 `int op int`，风险低但仍是对构造串求值；:17302 与 `SymbolicReasoner.py:728` 已用 AST 白名单 + 空 builtins，**实现良好**。
- **建议**：9013 处改用 `operator` 模块直接运算，消除 eval。

### C5. 五维权重双重定义
- `config.py:665 RESONANCE_WEIGHTS` 与 `nucleus/synapsys/ResonanceEngine.py:38 WEIGHTS` 各定义一份相同的 0.40/0.30/0.15/0.10/0.05。值当前一致（符合宪法规则 3），但双源易在「修宪」时不同步。
- **建议**：ResonanceEngine 改为引用 config 单一来源，或加一致性断言测试。

## 五、P3 建议项

- **D1 MD5 安全告警（bandit 20 处 HIGH/B324）**：经核验均为去重指纹/缓存键用途（如 InfoField:1493 L3 去重），非密码学安全场景，功能上可接受。建议统一加 `usedforsecurity=False` 消除告警噪音。
- **D2 代码质量告警 1374 条（干净范围）**：主要为 UP031 printf 格式化(450)、I001 import 未排序(247)、RUF100 失效 noqa(168)、SIM115 open 未用 with(140)、UP020 open 别名(107)。其中 1115 条可 `ruff --fix` 自动修复。建议分批治理，先清 RUF100/SIM115（与资源泄漏相关）。
- **D3 依赖未锁版本**：`requirements.txt` 全部用 `>=`，无 lock 文件，构建不可重现。建议补 `requirements.lock` 或 `pip-tools`。
- **D4 洞察死数据**：全景图已自陈 InsightBoard 27 类型中 11 个「仅写未读」、1 个 phantom（code_fix_suggestion 无写入方）、6 个 TTL key 全仓无引用。建议清理或补消费方。

## 八、总体评价

曈曈 PulseNet 是一个**架构野心极大、工程意识真实在线**的框架：脉冲总线、补丁原子化、凭证安全、并发埋点等核心机制的实现质量达到了工业级水准，1802 个测试用例也证明了团队对可验证性的重视。

但它正处在**「能力快速膨胀」与「治理跟不上」**的失衡点：自我迭代系统在追求「完美级闭环」的过程中，悄悄拆掉了宪法亲手立下的核心安全闸门（A1）；存储引擎挂着「百亿级」的名字，主路径却仍是会随知识增长而整体重写的单体 JSON（A2）；F4 自愈、补丁冷却等被文档宣布「已落地验证」的闭环，在代码层其实是空转的死状态（B1/B4）。最危险的不是这些缺陷本身，而是**文档已无法反映代码真相**（B6）——这意味着团队正基于失真的「事实源」做决策。

一句话：**地基的工程质量配得上它的野心，但自我演化的安全边界正在被自己的进化逻辑侵蚀，且文档已失去校准能力。** 当务之急不是加新能力，而是把 A1/B1/B4 这三道「宣称存在、实则失效」的安全闸门重新焊死，并让文档重新成为可信基准。
