## 1.3 新能力对"运行上限"的战略意义

**结论：方向一致，但"上限验证"的真正主仪器是超算镜像，InfluxDB 是其记录仪——两者应作为同一工作流并行准备，而非先后两批。**

- 烛微 C2 已给镜像三阻塞点（aibot SDK 无 PyPI 包 / pyaudio 需 portaudio / **Cython 无 Linux 编译分支**）。本件认同第三点是决定性的：Linux 回落 Python 而基线不标注，性能数据与 Windows 不可比，"上限"结论失效。
- 更优组合建议：**172 同窗四件套 = 镜像制作（补 Cython Linux 分支）+ InfluxDB 接线（含 RSS 点）+ 内存长稳取证 + L3 精简器收益观测**。共享一次 Linux 长跑窗，产出"上限曲线"。
- 有无遗漏的更优先候选：**有一个——Cython Linux 分支应先于/并行于 InfluxDB 开关**，否则 InfluxDB 记录到的是失真基线。face_welcome 维持③（影子自115批未退出，属可随时插队的行为变更小刀，不占新能力设计位）。

## 3.2 角色边界与"交付-销账"断点根因

**根因（交付-销账为何断）**：

1. **销账权与交付动作分离**：施工提交（路灯）与登记册状态变更（星轨批处理）在不同提交、不同时刻；只读方（烛微/微光/洞鉴）只能"查出欠账"不能改状态。
2. **交付报告不是状态机事件**：报告/提交信息是"交付证据"，但没有任何机械环节把它转成登记册状态变更；销账依赖裁决周期，批次加速后裁决跟不上交付。
3. **缺少对账门**：无自动比对"提交中已带票名 ↔ 登记册状态"的门禁，欠账只能靠前置分析或审查发现。实证：14欠销账中的3张（夜间编排/内在世界净化/内存维度分级）是在洞鉴10-07报告点名后，由 `db9e4a3` 补销——**销账由审计压力触发，而非流程自动发生**。

**边界判定**：

- 只读方"实跑≤120s 单文件测试"额度（161 Q1裁决）：对落点级取证**基本够用**，但方向级/长稳类判定天然依赖窗口，额度解决不了——建议明确"只读方可提交'验收票建议'，由星轨在窗口批统一执行"，已有此模式，建议固化。
- **洞鉴自身节奏建议**：全面审查不必每批——**每 6–8 批一次，或在阶段转换点（P0清零/新能力启动/版本转正）触发**；期间以"方向级验证"（如本件）响应里程碑。价值定位：独立交叉验证 + 机械可复核判据，而非重复取证。
