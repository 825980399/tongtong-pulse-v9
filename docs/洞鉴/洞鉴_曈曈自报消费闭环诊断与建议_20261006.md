## 〇、一句话结论

曈曈的「自我问题发现」能力**已经成型且持续在运行**，落地文件也早已存在；真正断裂的是**最后一公里——团队消费**：瞳瞳自己每晚把问题查出来、分级、落盘，但其中"需要人处理"的告警**堆积 178 条无人处置、消费率接近 0**。小林设想的"自报问题→团队定期阅读处理"不是新能力建设，而是**把一个已建好但空转的闭环接上**；现有运行日志只是原料（L0），不构成该能力本身。

## 一、发现：自报体系已有三层落地（实测）

| 层 | 落地物 | 实测情况 |
|---|---|---|
| L2 画像层 | `data/self_awareness/report_*.txt` | **24 份定时报告**，由 `nucleus/self_awareness/DailyScheduler.py` 每日 03:00 自动生成（落盘点 :298；当天已生成则跳过，:238）；覆盖 7 个维度：代码静态 / 运行时 / 知识 / 进化 / 产出-消费配对 / 虚假闭环 / 代码结构 |
| L1 事件层 | `nucleus/reporting/report_bus.py`（ReportBus，765 行） | 统一信封 + P0/P1 分级 + 订阅分发 + 落盘；**消费追踪方法已写好**：`get_unconsumed` / `mark_consumed` / `_resolution_rate` / `check_consumer_staleness` |
| L1 队列文件 | `data/reports/alerts.jsonl`、`data/reports/todo.jsonl` | alerts **199 条**：其中 `needs_human=True` **178 条**、P0 **173 条**、P1 5 条（类型：evolution 92 / health 86）；todo 180 条（144 条 `serp_clean_suggestion` 明确标注 `needs_downtime=True, auto_executed=False`） |
| 自修通道 | `data/patches/pending_patches.json`（约 226 KB） | 能自修的问题走补丁队列（19 个在队）；修不了的按设计应进 alerts/todo 等人处理 |

**自报质量实证**（2026-10-05 03:00 报告，综合 86.82/100）：

- 自行点出 `nucleus.mnemosyne.PulseNodePool` 闭环健康度 **0 分**、`MasterSlaveReplication` **30 分**、`PulseCognitiveReflector` **0 分**（虚假闭环检测）；
- 自行识别 **2,435 个孤立函数**（占 38.6%）、4 个超级函数、2 组循环调用；
- 自行发现知识冲突 11 处（高危 4，涉及 L3 永久锁定节点）、孤岛知识节点 1,247 个；
- 自行统计 ruff 问题 3,917 条并给复跑命令；
- 8 个运行时错误被正确聚类（实为同一环境缺失 `typing_extensions` 的重复报错）。

**判断：发现侧不是摆设，是一个合格的"永不疲倦的巡检岗"。**

## 二、断点：消费率 ≈ 0（四处实锤）

1. **日报没有人类读者**：全项目引用 `report_*.txt` 的只有 DailyScheduler 自身（防重复）与测试；docs 侧引用全部位于 archive 和早期设计文档。
2. **人读队列无状态机**：`todo.jsonl` 180 条**无 status 字段、无 consumed 标记**——只写不读；alerts 的 178 条 needs_human 无处置留痕。
3. **修剪 ≠ 处理**：`tools/cleanup_reports.py` 只做磁盘修剪防占满，报告是被"清理式归档"，不是被"阅读式闭环"。
4. **两本账不通**：项目早在第 46 批《自认知报告消费机制 v1.0》（`docs/设计文档/自认知报告消费机制_v1.0.md`）就写明现状"消费率 ≈ 0%"，目标含"P1 任务队列 → 债务清单"。ReportBus 后来按设计落地了，但**"P1 告警 → 待裁决登记册"这一步从未接线**——曈曈自报问题与团队登记册至今是两套互不相通的账。

## 三、运行日志算不算这个能力？——不算，它是 L0 原料

`logs/` 实测 318 文件 / 58.0 MB（pulse.log 系列单文件 6–11 MB、crash.log 11.8 MB）。日志是行级流水：**无分级、无去重、无待办语义、无消费状态**，人无法直接阅读（同一 `typing_extensions` 缺失会刷成几十行）。它不构成"自我发现能力"，而是该能力的输入原料。

正确分层（前三层已存在）：

```
L0  logs 流水（58MB，人读不了）
      ↓ 已接线
L1  ReportBus 告警事件（已实现；178 条 needs_human 堆积中）
      ↓ 已接线
L2  每日自认知画像 report_*.txt（已实现；无人阅读）
      ↓ ★唯一缺失
L3  人读摘要 digest + 登记册转登 + mark_consumed 闭环
```

## 四、建议：三刀接闭环（不新建体系、不破坏制衡）

总原则：**复用现成 ReportBus 与登记册，只补接线；曈曈只"报"不自裁、不自改；核实权在微光/烛微，拍板权在小林。**

### 刀1 · 每晚人读摘要 digest（曈曈侧，小改）

- 每晚自认知报告后，对 `get_unconsumed()` 中 `needs_human=True` 条目做**去重 + 分级 + 建议摘要**，产出 `data/reports/digest_YYYYMMDD.md`（一页内：P0/P1 计数、Top5 问题、建议动作、复跑命令）。
- 验收：① digest 由现有调度自动产出；② 连续 3 晚条目与 alerts/todo 原始数据可对账（数字一致）；③ 不新增除 digest 外的任何文件。

### 刀2 · 微光每批读 digest → 转登记册 → 回写消费（流程侧，零生产代码）

- 微光（现有职责3"巡 data / 查只写不读"的自然延伸）每批开工前读最新 digest：核实为真的问题，转登《待裁决登记册》，来源标记"**曈曈自报**"；处置后调用 `mark_consumed` 回写。
- 验收：① 每批交付物含"自报核实清单"（转登 N 条 / 误报 M 条 / 存疑 K 条）；② alerts 出现首批非修剪性 consumed 记录；③ 登记册可按"曈曈自报"来源筛选统计。

### 刀3 · 每周消费率指标（度量侧，零新逻辑）

- 直接调用 ReportBus 现成的 `_resolution_rate` / `get_consumer_health`，每周出一个数：自报问题消费率、平均处置时延。
- 验收：连续 4 周可读数；目标首月消费率 > 60%（178 条存量 + 增量分 4 周摊），之后 > 85%。

### 存量处置建议

178 条 needs_human（173 条 P0）首次消化时做一次**存量大扫除**：微光+烛微联合一次性分诊（真问题转登记 / 误报标 false_positive——SelfInspector 已自带误报名单机制 `add_false_positive`），避免新流程一启动就背历史包袱。

## 五、为什么主动式优于被动式（本项目语境）

1. **边际成本趋零**：自报每晚自动跑，问题发现不占用任何人力；被动式（等人撞到 bug 或审计抽查）要付完整排查成本。
2. **发现质量已验证**：虚假闭环 0 分、知识冲突、孤立函数等均为曈曈先于人工自报，与后续人工审计结论吻合。
3. **不增加新角色/新文件体系**：接的是现成 ReportBus + 现成登记册 + 现成微光职责，成本仅三刀。
4. **制衡无损**：自报不绕流程——机器只发现与建议，核实、派单、拍板、施工仍在微光/星轨/小林/路灯手里。
