# 曈曈PulseNet项目协作规范与经验教训总结

**版本**: v1.0（2026-09-17编制）
**编制**: 星轨
**适用范围**: 星轨（规划/验收）+ 路灯（执行）+ 用户（决策）三方协作
**核心目的**: 总结第52-67批修改过程中的经验教训，避免重复犯错，提高任务质量和验收通过率

---

## 一、经常出错的地方（按类别分类）

### 1.1 数据来源核实不充分 ⚠️ 高频错误

**典型案例**:
- **第66批T0偏差**: 健康诊断报告"655个代码问题"，路灯直接使用此数据。星轨验收时发现真实数据是 `ruff --statistics=2264`（55规则），全库 `F/E9=0`（零真实bug）。健康诊断的"代码问题"是误报，包含大量风格建议和非bug项。
- **经验库污染率**: 第65批之前污染率97.4%，实际是分类逻辑过宽导致的误标记，不是真正的污染。

**根本原因**:
- 直接使用框架输出的统计数据，没有核实数据来源和计算口径
- 混淆了"告警数"和"真实bug数"
- 没有区分"建议"和"必须修复"

**预防措施**:
1. **任务书中必须明确数据来源和核实方法**: 例如"使用 `ruff --statistics` 命令核实代码问题数量，区分F（致命）/E（错误）/W（警告）级别"
2. **路灯执行时必须核实数据**: 不能直接使用健康诊断或其他模块的输出，需要用独立方法核实
3. **星轨验收时必须复核关键数据**: 特别是数量级较大的数据（如"几百个问题"、"97%污染率"）
4. **数据口径要写清楚**: 例如"代码问题"要说明是ruff的哪个级别，"污染率"要说明计算方法

---

### 1.2 配置不合理/不匹配 ⚠️ 高频错误

**典型案例**:
- **快照保存频率**: `FULL_SAVE_INTERVAL=600`（10分钟），但实际保存需要7510秒（2小时5分钟），导致永远在保存，形成恶性循环。
- **增量保存阈值**: `INCREMENTAL_MAX_NODES=50`，实际运行中10分钟内变更节点通常超过50个，所以几乎每次都走全量保存，"增量保存"名存实亡。
- **Parquet已启用但只是额外副本**: `FEATURE.use_parquet_snapshot=True`，但每次还是先写479MB JSON，再写17MB Parquet，Parquet没有发挥主存储作用。
- **队列深度上限**: 队列深度上限5000，但告警阈值设置不合理，导致2000+时才告警，已经积压严重。

**根本原因**:
- 配置参数是"拍脑袋"设置的，没有基于实际性能数据
- 配置之间没有联动校验（如保存间隔 < 保存耗时）
- 新功能启用后没有替换旧功能，而是并行运行，增加开销

**预防措施**:
1. **任务书中必须说明配置参数的依据**: 例如"将FULL_SAVE_INTERVAL从600改为3600，依据是当前全量保存需要约7510秒，1小时间隔可以保证保存完成"
2. **配置修改后必须验证**: 不能只改配置，要实际运行验证配置是否生效、是否合理
3. **配置联动校验**: 新增配置时要检查与现有配置的关系，避免矛盾
4. **新功能替换旧功能**: 启用新功能（如Parquet）后，要评估是否可以关闭或降级旧功能（如JSON），避免双重开销

---

### 1.3 代码语法错误 ⚠️ 低级错误

**典型案例**:
- **config.py第1163行**: `priority: 6,  # ★2026-09-15紧急调整：深度思考模型复杂请求易超时，降级备用`
  - 这是YAML风格的键值对（`key: value`），错误地写在了Python字典中
  - Python字典应该是 `"priority": 6,` 而不是 `priority: 6,`
  - 导致 `NameError: name 'priority' is not defined`
  - 这个错误导致所有import config的脚本都失败（verify_phase17_1_5.py、verify_semantic_kernel.py等）

**根本原因**:
- 修改配置时复制粘贴了YAML格式的内容，没有转换为Python格式
- 修改后没有运行语法检查（`python -m py_compile`）
- 没有运行基本的import测试

**预防措施**:
1. **修改config.py后必须运行语法检查**: `python -m py_compile config.py`
2. **修改后必须运行import测试**: `python -c "import config; print('config import OK')"`
3. **任务书中明确要求**: "所有修改的.py文件必须通过py_compile语法检查，config.py必须通过import测试"
4. **路灯交付报告中必须包含语法检查结果**: 不能只说"修改完成"，要附上检查命令和输出

---

### 1.4 环境判断错误 ⚠️ 中等频率

**典型案例**:
- **WriteGuard误判**: WriteGuard误判framework进程为测试环境，导致ReportBus无法写生产目录，出现12条WARNING：`WriteGuard: 检测到测试环境，写入已重定向到测试目录`
- 实际是正常的framework进程（通过main.py启动），不是测试环境

**根本原因**:
- 环境判断逻辑不严谨，可能通过命令行参数、当前目录、或环境变量判断
- 没有优先通过显式配置判断
- 缺少环境判断的日志输出，难以排查

**预防措施**:
1. **环境判断优先使用显式配置**: 如 `WRITE_GUARD_ENV = "production"`，而不是自动推断
2. **环境判断必须输出日志**: 输出判断依据（如"通过main.py启动，判断为生产环境"），便于排查
3. **提供强制指定环境的配置**: `WRITE_GUARD_FORCE_ENV = None`，可覆盖自动判断
4. **测试环境和生产环境要有明确的区分标志**: 如启动入口、配置文件、环境变量等

---

### 1.5 性能问题未提前发现 ⚠️ 严重问题

**典型案例**:
- **快照保存7510秒**: 这个问题应该在更早的时候就被发现，但直到队列深度2000+、框架明显变慢时才引起注意
- 代码注释中已经记录了"03:14出现过921.17秒，与队列深度1566强相关"，说明问题早已存在，但没有持续跟踪

**根本原因**:
- 缺少持续的性能监控和告警
- 性能指标没有纳入常规验收标准
- 问题出现后没有根因分析，只是临时处理

**预防措施**:
1. **任务书中必须包含性能验收标准**: 例如"全量保存时间<300秒"、"增量保存时间<10秒"
2. **路灯交付时必须提供性能测试数据**: 不能只说"功能正常"，要附上性能测试结果
3. **星轨验收时必须验证性能指标**: 特别是涉及核心流程的修改（如保存、加载、查询）
4. **建立性能基线**: 每个批次记录关键性能指标，发现退化立即告警

---

### 1.6 增量/异步机制不完善 ⚠️ 设计缺陷

**典型案例**:
- **"增量保存"名存实亡**: 当前的增量保存只是判断"变更节点数是否小于50"，不是真正的增量日志。超过50个变更就走全量保存，实际几乎每次都是全量。
- **异步保存缺失**: 保存在主线程执行，持有RLock，阻塞其他操作，形成锁竞争+队列积压的恶性循环。

**根本原因**:
- 设计时只考虑了"有没有这个功能"，没有考虑"这个功能是否真正有效"
- 缺少边界条件测试（如变更节点数刚好超过阈值时的行为）
- 没有考虑高负载下的性能表现

**预防措施**:
1. **任务书中必须说明机制的工作原理**: 例如"增量保存通过增量日志记录节点变更，启动时先加载全量快照再应用增量日志"
2. **必须包含边界条件测试**: 如"变更节点数=49/50/51时的行为"、"增量日志损坏时的恢复机制"
3. **必须包含高负载测试**: 如"保存期间对话响应是否正常"、"队列深度是否持续增长"
4. **机制必须有开关和回退**: 新机制可以关闭，回退到旧机制，避免出问题时无法恢复

## 八、总结

本规范基于第52-67批的实际经验编制，核心原则：

1. **数据必须核实**: 不能直接使用框架输出，要用独立方法验证
2. **配置必须有依据**: 不能拍脑袋设置，要基于实际性能数据
3. **语法必须检查**: 修改后必须py_compile+import测试，特别是config.py
4. **验收必须实测**: 不能只看交付报告，要实际运行测试验证
5. **流程必须规范**: 任务书发布、路灯执行、星轨验收都有检查清单
6. **债务必须更新**: 任务派发和验收后必须立即更新技术债务清单
7. **性能必须监控**: 建立性能基线，持续监控，发现退化立即处理
8. **新功能必须有开关**: 可关闭回退，避免出问题时无法恢复

**本规范将在以后每批任务书中引用和更新，确保经验教训不重复犯错。**
