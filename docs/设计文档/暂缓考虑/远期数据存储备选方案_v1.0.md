## 二、备选方案设计

### 2.1 方案选择原则

1. **单机可运行**——不需要多机集群
2. **Python生态友好**——通过HTTP API或Python SDK调用
3. **开源免费**——不被墙，能下载
4. **渐进式迁移**——保留Parquet主存储，只换加速层
5. **成熟稳定**——不追新技术，选经过验证的方案

### 2.2 推荐备选方案：ArcadeDB统一多模

**一个数据库替代FAISS + Neo4j + InfluxDB**

```
┌─────────────────────────────────────────────┐
│  主存储层（保留不动）                        │
│  Parquet文件 + 三层冷热分离                  │
│  负责：知识节点原始数据、持久化              │
├─────────────────────────────────────────────┤
│  加速层（备选：ArcadeDB）                   │
│  ├── 向量检索（内置JVector/HNSW）           │
│  ├── 图查询（内置Cypher）                   │
│  └── 时序监控（内置TimeSeries）             │
│  负责：检索加速、关联查询、健康监控          │
├─────────────────────────────────────────────┤
│  接口层（已实现，不动）                      │
│  VectorStore / GraphStore / TimeSeriesStore │
│  负责：屏蔽底层实现差异                      │
└─────────────────────────────────────────────┘
```

### 2.3 为什么选ArcadeDB

| 对比项 | ArcadeDB | 理由 |
|--------|----------|------|
| 开源协议 | Apache 2.0 | 完全免费，无商业限制 |
| 下载方式 | zip包直接下载 | 不被墙（非CloudFront CDN） |
| 启动内存 | 最小16MB | 比Neo4j（2-4GB JVM）轻得多 |
| 数据模型 | 图+向量+时序+文档+KV+全文 | 一个引擎搞定向量+图+时序 |
| 查询语言 | SQL + Cypher + Gremlin + GraphQL | 兼容现有代码风格 |
| Python调用 | HTTP API（REST） | Python项目通过requests调用 |
| ACID事务 | 完整支持 | 数据一致性有保障 |
| 嵌入式 | 可嵌入JVM/独立服务/Docker | 部署灵活 |

### 2.4 备选方案B：LanceDB + FalkorDB + QuestDB

如果ArcadeDB不适合，这个方案作为第二选择：

| 组件 | 替代 | 特点 |
|------|------|------|
| LanceDB | FAISS | 嵌入式向量数据库，自动管索引，pip安装 |
| FalkorDB | Neo4j | 轻量图数据库（Redis模块），pip安装 |
| QuestDB | InfluxDB | 时序数据库，SQL接口，性能更高 |

**优势**：全部pip安装，不被墙，Python原生
**劣势**：三个组件，需要维护三个连接

## 三、什么时候需要启动备选方案

### 3.1 升级触发条件（满足任意一条）

| 触发条件 | 说明 | 当前状态 |
|---------|------|---------|
| FAISS bug反复修不好 | 索引构建不稳定，影响检索质量 | 第73批修复中 |
| 节点数超过50万 | 单机冷热分离开始吃力 | 1.2万（远未到） |
| 向量检索延迟超过500ms | 影响对话体验 | 159ms（暴力余弦） |
| Neo4j一直装不上 | 关联查询只能暴力遍历 | 被墙跳过 |
| InfluxDB写入性能不够 | 监控数据量增长太快 | 只写1%采样 |
| 需要多跳关联查询加速 | 3度关联查询太慢 | 节点内暴力遍历 |

### 3.2 不升级的理由（现在）

1. **节点数太少**——1.2万节点，离单机天花板（几百万）还远
2. **FAISS还在修**——先修好现有方案，不要同时做两件事
3. **InfluxDB刚装好**——还没用起来就换是浪费
4. **接口层已留好**——真要换，改接口实现就行，不需要大改代码

## 四、迁移路径（如果以后真要换）

### 4.1 阶段一：验证ArcadeDB可行性

```
步骤：
1. 下载ArcadeDB zip包，解压到D:\arcadedb
2. 启动独立服务（端口2480 HTTP）
3. 用Python requests调用，验证基本读写
4. 导入现有12000个节点数据，测试查询性能
5. 对比FAISS暴力余弦 vs ArcadeDB向量检索
```

### 4.2 阶段二：接口层切换

```
代码改动：
1. nucleus/fast_ops.py：FAISSVectorStore → ArcadeDBVectorStore
2. nucleus/distributed/neo4j_dualwrite.py：Neo4j → ArcadeDB Graph
3. nucleus/distributed/influxdb_writer.py：InfluxDB → ArcadeDB TimeSeries
4. 保留开关：ENABLE_ARCADEDB = True/False
```

### 4.3 阶段三：数据迁移

```
数据迁移：
1. 从Parquet导出全部节点数据
2. 导入ArcadeDB（图节点+向量+属性）
3. 双写验证：写Parquet的同时写ArcadeDB
4. 双读验证：查询先读ArcadeDB，回退到Parquet
5. 切换完成：ArcadeDB为主，Parquet为备份
```

### 4.4 阶段四：下线旧组件

```
下线：
1. FAISS索引文件 → 不再使用
2. InfluxDB → 停止服务
3. Neo4j（如果以后装了）→ 停止服务
4. 只保留：Parquet主存储 + ArcadeDB加速层
```
