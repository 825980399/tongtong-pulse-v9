## 一、项目背景与目标

### 1.1 背景

曈曈PulseNet v9.5是一个仿生数字生命框架，包含56个仿生器官在脉冲信息场中自主协作。当前交互方式为**控制台命令行**（`python main.py`），存在以下局限：

1. **信息展示不直观**：56个器官状态、激素水平、队列深度、能量状态等关键指标只能通过日志文本查看
2. **思考过程不可视**：内在世界思考、自学习过程、进化补丁审批等复杂流程缺乏可视化
3. **核心链路不透明**：眼睛→视觉皮层→对话模块等核心链路状态只能通过人体UI简单显示
4. **任务管理分散**：批次任务（路灯/星轨协作）通过文档管理，缺乏统一界面
5. **多渠道切换不便**：火山/DeepSeek/智谱等大模型渠道切换需要修改配置文件

### 1.2 目标

打造一个**专为仿生数字生命设计的图形化交互界面**，不仅是通用AI助手界面，更要突出曈曈的生命特征：

| 目标维度 | 具体目标 |
|----------|----------|
| **生命可视化** | 56个器官协同工作、激素情绪波动、核心链路状态实时可视化 |
| **思考透明化** | 内在世界思考过程、自学习/进化过程、决策链路可追溯 |
| **交互自然化** | 对话、任务、文件、设置统一入口，支持@引用和/指令 |
| **状态可观测** | 健康状态、队列深度、能量水平、大模型依赖度等指标仪表盘 |
| **操作便捷化** | 补丁审批、渠道切换、配置热重载、框架启停一键操作 |

### 1.3 设计原则

1. **生命优先**：界面首先是"数字生命的窗口"，其次才是"编程助手"
2. **信息分层**：关键状态一眼可见，详细信息可下钻，避免信息过载
3. **实时反馈**：所有状态变化实时推送，延迟<1秒
4. **可定制化**：面板布局、指标选择、主题风格可用户自定义
5. **向后兼容**：控制台模式继续保留，图形界面为可选增强
6. **性能友好**：界面本身不消耗过多资源，不影响框架运行性能

#### 3.4.1 🫀 器官状态面板

**设计**：56个器官按系统分组展示（感知/认知/情感/行动/生存/进化）

| 系统 | 器官示例 | 状态展示 |
|------|----------|----------|
| **感知系统** | 眼睛、耳朵、皮肤、鼻子 | 输入状态、帧率、识别结果 |
| **认知系统** | 大脑皮层、海马体、前额叶 | 思考状态、记忆读写、决策中 |
| **情感系统** | 激素、情绪、杏仁核 | 激素水平、情绪状态、波动曲线 |
| **行动系统** | 嘴巴、手、主动交互 | 输出状态、动作执行、主动行为 |
| **生存系统** | 心脏、肺、胃、肾、肝脏 | 心跳节律、呼吸频率、消化状态、过滤负载 |
| **进化系统** | 代码学习、补丁、自修复 | 学习进度、补丁审批、修复状态 |

**每个器官展示**：
- 器官名称 + 图标
- 运行状态（🟢正常/🟡忙碌/🔴异常/⚫休眠）
- 当前负载（0-100%进度条）
- 最近活动时间
- 悬停显示详细信息（处理脉冲数、平均响应时间、错误率）

**功能**：实时展示曈曈的内在思考过程

**思考阶段展示**：

7. **记忆更新**：新记忆写入、经验总结、学习记录

**展示方式**：
- 时间线流式展示（每一步实时出现）
- 每一步可展开查看详情（检索到的记忆、推理规则、候选方案）
- 耗时统计（每一步耗时、总耗时）
- 大模型调用标记（哪些步骤调用了大模型、哪个渠道、耗时多少）

```
┌─────────────────────────────────────────────────────────┐
│                    前端（Web界面）                        │
│  Vue3 + TypeScript + Element Plus + ECharts + Monaco    │
│  WebSocket实时通信 + RESTful API                          │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP/WebSocket
┌────────────────────────▼────────────────────────────────┐
│                  后端API层（FastAPI）                      │
│  ┌──────────┬──────────┬──────────┬──────────────────┐  │
│  │ 对话API  │ 状态API  │ 任务API  │ 文件/配置API      │  │
│  └──────────┴──────────┴──────────┴──────────────────┘  │
│  ┌──────────────────────────────────────────────────────┐│
│  │ WebSocket推送层：日志/器官状态/思考过程/指标实时推送    ││
│  └──────────────────────────────────────────────────────┘│
└────────────────────────┬────────────────────────────────┘
                         │ 进程内调用 / 共享内存
┌────────────────────────▼────────────────────────────────┐

│  56个器官 + 脉冲信息场 + 内在世界 + 自学习 + 进化系统      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 技术栈选型

| 层级 | 技术选型 | 选型理由 |
|------|----------|----------|
| **前端框架** | Vue3 + TypeScript | 生态成熟、学习曲线平缓、Element Plus组件丰富 |
| **UI组件库** | Element Plus | 中文文档好、组件全面、适合管理后台风格 |
| **图表库** | ECharts | 功能强大、支持实时数据、中文文档好 |
| **代码编辑器** | Monaco Editor | VS Code内核、语法高亮强大、支持diff对比 |
| **状态管理** | Pinia | Vue3官方推荐、轻量、TypeScript友好 |
| **路由** | Vue Router | 官方路由、支持标签页模式 |
| **HTTP客户端** | Axios | 成熟稳定、拦截器支持好 |
| **WebSocket** | 原生WebSocket + 重连机制 | 实时通信必需 |
| **后端框架** | FastAPI | 异步高性能、自动文档、TypeScript类型生成 |
| **WebSocket服务** | FastAPI WebSocket | 与REST API统一框架 |
| **进程通信** | 多进程共享内存 / 队列 | 与曈曈核心框架解耦 |
| **打包部署** | Electron（可选桌面版） | 跨平台桌面应用、系统托盘支持 |

### 4.3 实时通信设计

**WebSocket消息类型**：

| 消息类型 | 推送频率 | 内容 |
|----------|----------|------|
| `log` | 实时 | 日志条目（级别、器官、时间、内容） |
| `organ_status` | 1秒/次 | 56个器官状态快照 |
| `hormone` | 1秒/次 | 激素水平 + 情绪状态 |
| `queue_depth` | 500ms/次 | L0-L3队列深度 |
| `thinking` | 实时 | 思考过程阶段更新 |
| `metrics` | 5秒/次 | 性能指标、大模型统计 |
| `alert` | 事件驱动 | 告警通知 |
| `task_update` | 事件驱动 | 任务状态变更 |
| `patch_pending` | 事件驱动 | 新补丁待审批通知 |

**性能优化**：
- 状态合并推送（1秒内多次状态变更合并为一次推送）
- 差异推送（只推送变化的字段，不全量推送）
- 客户端节流（UI更新频率限制为30fps）
- 断线重连（指数退避重连机制）
- 消息压缩（大消息使用gzip压缩）

## 五、与现有系统的集成点

### 5.1 需要封装的核心接口

| 现有模块 | 需要封装的接口 | 封装方式 |
|----------|---------------|----------|

| **器官管理器** | `get_all_organs_status()` → 器官状态列表 | 定时采样（1秒/次），状态合并推送 |
| **PulseHormones** | `get_hormone_levels()` → 激素水平 | 定时采样，变化推送 |
| **InfoField** | `get_queue_depths()` → L0-L3队列深度 | 定时采样（500ms/次） |
| **日志系统** | 日志输出回调 | 注册日志监听器，实时推送 |
| **配置系统** | `get_config()` / `set_config()` / `reload()` | 配置读写封装，热重载触发 |
| **补丁系统** | `get_pending_patches()` / `approve()` / `reject()` | 补丁管理封装 |
| **大模型渠道** | `get_channels()` / `switch_channel()` / `get_stats()` | 渠道管理封装 |

### 5.2 需要新增的中间层

| 中间层 | 功能 | 实现方式 |
|--------|------|----------|
| **API服务进程** | 独立进程运行FastAPI，与框架进程通信 | 多进程架构，共享内存/队列通信 |
| **状态聚合器** | 聚合56个器官状态、激素、队列等，合并推送 | 后台线程，定时采样+差异计算 |
| **思考过程捕获器** | 捕获内在世界思考过程，结构化后推送 | 钩子/回调机制，在思考各阶段插入捕获点 |
| **日志转发器** | 将框架日志转发到WebSocket | 日志Handler注册，异步转发 |
| **权限控制层** | API访问权限控制（只读/读写/管理） | API Key + 角色权限 |

### 5.3 兼容性设计

1. **控制台模式保留**：图形界面为可选增强，`python main.py`继续支持纯控制台模式
2. **渐进式启用**：通过配置项`ENABLE_GUI_UI`控制是否启动API服务和界面
3. **无侵入式集成**：API层通过现有接口封装，不修改框架核心逻辑
4. **降级机制**：界面断开不影响框架运行，重连后自动同步状态
5. **版本兼容**：API版本化（`/api/v1/`），后续升级不破坏旧客户端

## 七、风险与注意事项

### 7.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| **实时通信性能** | 56个器官状态+日志+思考过程高频推送可能导致性能瓶颈 | 状态合并推送、差异推送、客户端节流、消息压缩 |
| **前后端耦合** | API层修改可能影响框架核心逻辑 | 无侵入式封装、API版本化、充分测试 |
| **前端复杂度** | 功能模块多，前端代码量可能很大 | 模块化设计、组件复用、按需加载 |
| **跨平台兼容** | Windows/Linux/macOS差异 | 基于Web技术，Electron跨平台，测试覆盖主要平台 |

### 7.2 项目风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| **范围蔓延** | 界面功能越做越多，偏离核心目标 | 严格按阶段实施，每阶段验收后才进入下一阶段 |
| **与技术债务冲突** | 界面开发引入新的技术债务 | 界面代码同样遵守ruff/mypy门禁，纳入技术债务管理 |
| **用户需求变化** | 开发过程中用户需求变化 | 敏捷开发，每阶段可调整优先级，核心功能优先 |
| **维护成本** | 界面代码增加维护负担 | 文档完善、代码规范、自动化测试覆盖 |

### 7.3 注意事项

1. **安全第一**：API层必须有权限控制，敏感操作（配置修改、补丁审批、框架启停）需要认证
2. **稳定性优先**：界面崩溃不能影响框架运行，API服务与框架核心进程隔离
3. **性能友好**：界面本身资源消耗<5%CPU、<200MB内存，不影响框架性能
4. **可回滚**：每个阶段完成后有备份，出现问题可回滚到上一阶段
5. **文档同步**：界面功能必须有用户文档，操作说明清晰
6. **测试覆盖**：API层单元测试覆盖率>80%，前端核心组件有E2E测试
