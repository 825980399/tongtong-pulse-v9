## 一、设计目标与边界

### 1.1 为什么要分布式

当前单机架构（Parquet + 冷热分离 + FAISS）支撑上限约 **1000-3000 万节点**，
瓶颈依次是：单机内存（热节点常驻）、单机磁盘 IO（Parquet 扫描）、CPU（向量检索）。
亿级节点必须分片到多机。

### 1.2 第70批做什么 / 不做什么

| 做 | 不做 |
|---|---|
| 分片策略设计与接口定义 | 引入分布式运行时 |
| 复制与一致性模型设计 | 接入真实节点注册表 |
| 路由与负载均衡设计 | 数据实际迁移 |
| 配置占位（默认关闭） | 跨机通信组件 |

**理由**（对应任务书风险表第2项）：分布式改造风险高，先冻结设计再实施，
避免"边设计边施工"导致的架构返工。

## 二、分片策略

### 2.1 三种候选方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| 按 node_id 哈希 | 分布均匀、实现简单 | L1 热节点被打散，无法针对热数据优化 |
| 按 evol_level | 层级局部性好，冷热策略可分层 | 层内数据倾斜无解（L1 可能远大于 L3） |
| **混合（level + 哈希）** | **保留层级局部性 + 摊平层内热点** | 实现稍复杂 |

### 2.2 推荐：混合分片

```
分片空间（共 16 片，可配置 DISTRIBUTED_SHARD_COUNT）
┌────┬────────────────────────┬────────────────────────────┐
│ L1 │  shard 0-1   (2 片)     │  热数据，副本数可上调       │
│ L2 │  shard 2-7   (6 片)     │  温数据                     │
│ L3 │  shard 8-15  (8 片)     │  冷数据，副本数可下调       │
└────┴────────────────────────┴────────────────────────────┘
```

- 先按 `evol_level` 定位大区（偏移固定：L1=0, L2=2, L3=8）
- 区内用 **md5 稳定哈希** 取模（跨进程/跨平台结果一致，便于客户端自行计算路由）
- 实测隔离性：`L1` 与 `L3` 的分片集合无交集（见测试 `test_24_level_partition`）

### 2.3 接口定义

```python
get_shard_id(node_id, evol_level) -> int      # 计算所属分片
get_shard_nodes(shard_id)         -> List[str] # 分片所在存储节点（副本列表）
migrate_shard(shard_id, target)   -> bool      # 迁移（第71批+实施）
get_distribution(node_ids, levels)-> Dict[int,int]  # 分布统计（验证倾斜）
```

### 2.4 分片元数据

- **路由表**：分片 → 存储节点列表（含副本）
- **健康状态**：每片维护 0.0~1.0 健康分
- **迁移策略**：负载不均时按分片迁移（第71批+实施，当前返回 False）

## 三、复制与一致性

### 3.1 复制策略

- **主从复制**：一主多从，读写分离
- **副本数**：默认 3（`DISTRIBUTED_REPLICA_COUNT`），可按层级差异化：
  - L1 热节点副本数↑（读多、可用性要求高）
  - L3 冷节点副本数↓（省存储）
- **延迟监控**：复制延迟纳入健康分计算

### 3.2 一致性模型

| 级别 | 语义 | 适用 | 性能 |
|---|---|---|---|
| `eventual`（默认） | 最终一致，写入即返回，异步复制 | L2/L3 温冷数据 | 高 |
| `strong` | 强一致，等待多数副本确认 | L1 热节点、关键元数据 | 低 |

- **冲突解决**：默认「最后写入胜出（LWW）」；强一致路径下可用向量时钟（第71批+评估）

### 3.3 接口定义

```python
write_with_consistency(node_id, data, consistency_level) -> bool
read_with_consistency(node_id, consistency_level)        -> Any
sync_replicas(shard_id)                                  -> bool
```

★当前实现：未启用分布式时一律返回"未实施"（False / None），**零副作用**。

## 四、路由与负载均衡

### 4.1 三种路由方式

| 方式 | 优点 | 缺点 |
|---|---|---|
| 客户端路由 | 少一跳，延迟低 | 路由表过期会失败 |
| 代理路由 | 路由表集中，客户端简单 | 代理成单点+额外延迟 |
| **混合（推荐）** | **客户端缓存直连 + 代理兜底** | 需处理缓存失效 |

### 4.2 负载均衡策略

| 策略 | 说明 | 适用 |
|---|---|---|
| `round_robin` | 轮流分配 | 节点同构 |
| `least_conn`（默认） | 选连接数最少 | 通用，推荐默认 |
| `consistent_hash` | 同 key 恒定节点 | 缓存友好 |
| `dynamic` | 连接数/健康分 加权最小 | 节点异构 |

- **健康分**：`update_node_health(node_id, 0.0~1.0)`；低于 0.5 不参与路由
- 无健康节点时 `route_request()` 返回 `None`，**由调用方决定降级**（不静默失败）

### 4.3 接口定义

```python
route_request(request_type, node_id, data) -> Optional[str]
get_healthy_nodes(min_health=0.5)          -> List[str]
update_node_health(node_id, health_score)  -> None
acquire/release(node_id)                   -> None   # 连接计数
```

第六节路线第72批项已落地（第二阶段：单机逻辑模拟，与第71批同默认关闭）。

### 9.1 实现位置

```
nucleus/distributed/replication.py
├── ReplicationNode(node_id, role, data)   # 含 version / updated_at / replication_lag_ms
└── MasterSlaveReplication(
        default_consistency="eventual",
        replica_count=3,
        strong_acks=2,        # 强一致需确认的副本数阈值
        lock=None)            # 默认 RLock，线程安全
```

设计约束（与第70/71批一致）：
- **单机关联性模拟**：无真实跨机网络/存储，副本为进程内字典；
- **零外部依赖**：纯标准库 + 线程锁，不引入第三方组件；
- **默认关闭**：当前由调用方按需构造实例，不接入常驻生产链路。

### 9.2 核心接口与语义

```python
register_node(node_id, role="slave")                 -> bool
write_with_consistency(node_id, data,
                       consistency="eventual",
                       replica_count=3)              -> int   # 返回已确认副本数（ack）
read_with_consistency(node_id, consistency="eventual") -> Any  # 返回主副本数据（LWW 取最高 version）
promote_slave(node_id)                               -> bool  # 从→主
get_replication_lag(node_id)                         -> float # 毫秒
get_replication_stats()                              -> dict
consistency_level_for_shard(evol_level)              -> str  # L1→"strong"；L2/L3→"eventual"
```

**写入语义**
- `eventual`：写全部 `replica_count` 副本即返回；副本数 = 传入 `replica_count`。
- `strong`：写到第 `strong_acks` 个副本即视为「多数确认」返回；副本不足 `strong_acks` 时按实际可达副本数确认（单机模拟下副本即同进程多副本结构，恒可达）。
- **冲突解决**：最后写入胜出（LWW）——以 `version` 单调递增 + `updated_at` 时间戳定序，读路径取最高 `version`。

**层级一致性映射**（`consistency_level_for_shard`）
| evol_level | 一致性级别 | 理由 |
|---|---|---|
| L1 | `strong` | 热节点 / 关键元数据，写多读多，须强一致 |
| L2 | `eventual` | 温数据，容忍短暂不一致换吞吐 |
| L3 | `eventual` | 冷数据，写极少，最终一致即可 |
