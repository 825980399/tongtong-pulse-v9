**设计**：路灯　**批次**：主线第46批 T3　**对应债务**：P0-1

## 一、设计目标

把"报告生成"与"报告消费"解耦，用**统一分发层**取代当前的点对点硬编码。

| 现状 | 目标态 |
|---|---|
| 生成器各自落盘/丢弃 | **统一注册**：所有报告登记到注册表 |
| 格式异构（JSON/文本/HTML/仅日志） | **统一信封**：`ReportEnvelope` 包裹，机器可消费 |
| 消费者需自行知道路径 | **订阅分发**：消费者声明订阅，分发器推送 |
| 无严重度字段 → 无法分级 | **统一分级**：P0/P1/P2 机器可读 |
| 消费率 ≈ 0% | **可度量**：消费率 / 触发率 / 解决率 / 时延 |

## 三、统一信封（★核心契约）

```python
@dataclass
class ReportEnvelope:
    """所有自认知报告的统一外层。"""
    report_id: str            # 唯一 ID
    report_type: str          # "self_awareness" | "patch_quality" | "pollution" | ...
    generated_at: float       # ★生成时刻（消费端判断新鲜度）
    generator: str            # 生成模块名
    severity: str             # ★"P0" | "P1" | "P2" | "info"
    summary: str              # 一句话摘要（人类可读）
    payload: dict             # 原始报告体（JSON 化）
    anomalies: list[Anomaly]  # ★机器可读的异常列表
    schema_version: str = "1.0"

@dataclass
class Anomaly:
    """★可触发动作的原子单元（报告里"哪里有问题"的结构化表达）"""
    code: str                 # 稳定编码，如 "PATCH_BASELINE_ZERO"
    severity: str             # "P0" | "P1" | "P2"
    title: str
    detail: str
    metric_value: float | None = None
    threshold: float | None = None
    target: str = ""          # 关联对象（文件/模块/记录 id）
    suggested_action: str = ""  # "generate_patch" | "enqueue_task" | "log_only"
```

**★为什么必须有 `Anomaly`**：现有报告只有"数据"，没有"这条数据意味着什么问题"。
没有它，消费者只能靠正则硬解析文本 —— 这是消费率 0% 的技术根因。

## 四、分级消费规则

| 级别 | 判据（示例） | 动作 | 时延要求 |
|---|---|---|---|
| **P0** | 补丁验证空转率 > 90%；经验库污染率 > 50%；健康分 < 阈值；连续 3 轮修复率 < 10% | **立即**：告警 + 触发补丁生成（T1 协同）+ 写入事件总线 | 同周期内 |
| **P1** | 单模块质量下降；污染率 20~50%；留存字段缺失率 > 5% | **纳入任务队列** → 技术债务清单（星轨/路灯处理） | 下一批次 |
| **P2** | 统计类、趋势类、信息类 | **仅记录归档** + 指标面板 | 无 |

**优先级判定（`PriorityRouter`）**：

```
1. 报告自带 severity     → 直接采用
2. 无 severity 但有 Anomaly → 取 Anomaly 中最高 severity
3. 两者皆无             → 按 report_type 查默认档位表
4. 仍无法判定           → 降级 P2（★保守，避免误触发）
```

## 五、消费者模块接口

```python
class ReportConsumer(Protocol):
    """报告消费者统一接口。"""
    def subscribed_types(self) -> set[str]: ...
    def min_severity(self) -> str: ...            # "P0"/"P1"/"P2"
    def consume(self, env: ReportEnvelope) -> ConsumeResult: ...

@dataclass
class ConsumeResult:
    consumer: str
    report_id: str
    accepted: bool            # 是否认领
    action_taken: str         # "none" | "alert" | "patch" | "enqueue" | "clean"
    action_ref: str = ""      # 生成的补丁 id / 任务 id
    note: str = ""
```

**内置消费者（建议实施顺序）**：

| # | 消费者 | 订阅 | 动作 |
|---|---|---|---|
| C1 | `AlertConsumer` | P0 | 写 `data/reports/alerts.jsonl` + 日志 WARN |
| C2 | `PatchTriggerConsumer` | P0 且 `suggested_action=generate_patch` | 调补丁生成（**与 T1 协同**） |
| C3 | `TaskQueueConsumer` | P1 | 写入技术债务清单候选 |
| C4 | `NarrativeSelfConsumer` | `self_awareness` | **改造现有硬编码链路**为订阅式 |
| C5 | `MetricsConsumer` | 全部 | 采集消费率/触发率/解决率/时延 |

## 六、闭环：效果验证（★不可省略）

```
报告生成 → 异常检测 → 优先级判定 → 触发动作 → 【效果验证】→ 回写
                                        ↑                │
                                        └──── 未解决 ─────┘（升级/重试）
```

| 环节 | 实现 |
|---|---|
| 动作记录 | `ConsumeResult.action_ref` 落到报告上，形成 `report → action` 关联 |
| 重测 | 动作执行后，**重新生成同类报告**，比对 `metric_value` 是否越过阈值 |
| 判定 | 解决 = 越阈且持续 ≥ 1 个报告周期；未解决 = 仍未越阈 |
| 升级 | 连续 2 个周期未解决 → severity 升一级 + 告警 |

> ★ 没有这一环，"触发动作"就只是"发了个通知"，闭环仍然断着。
> 这正是当前 `patch_quality_report` 报出 3% 可判定率却**无人处理**的原因。

## 七、关键指标定义

| 指标 | 定义 | 采集点 | 目标 |
|---|---|---|---|
| **报告消费率** | `有 accepted=true 消费者的报告数 / 总报告数` | `MetricsConsumer` | **≥ 80%** |
| **异常触发率** | `产生 action_taken ≠ none 的异常数 / 总异常数` | 同上 | P0：100%；P1：≥ 60% |
| **问题解决率** | `效果验证判定"已解决"的异常数 / 已触发动作的异常数` | 效果验证 | **≥ 50%**（首年） |
| **闭环时延** | `问题解决时刻 − 报告生成时刻` 的中位数 | 同上 | P0：≤ 1 个报告周期 |

### 采集与展示

| 项 | 方案 |
|---|---|
| 存储 | `data/reports/metrics.jsonl`（追加写，按天滚动） |
| 聚合 | 每日由 `DailyScheduler` 汇总 → `data/reports/metrics_daily.json` |
| 展示 | ① 并入自我认知画像报告新增"【闭环健康度】"段落<br>② `tools/report_metrics_cli.py` 命令行查看<br>③ 与 T2 的污染率、T1 的可判定率共用同一指标管道 |
| 告警 | 消费率 < 50% 连续 2 天 → 自身也是一个 P1 异常（自反监控） |

## 八、与 P0-2 / P0-3 的协同

| 债务 | 协同设计 |
|---|---|
| **P0-2 补丁验证（T1）** | 补丁质量报告的 `unverifiable` 计数 → 直接映射为 `Anomaly(code="PATCH_BASELINE_ZERO", severity="P0")`<br>→ 触发 `PatchTriggerConsumer` → 生成"修复验证机制"的补丁 |
| **P0-3 经验库污染（T2）** | 污染率 > 50% → `Anomaly(code="SERP_POLLUTION_HIGH", severity="P0")`<br>→ 触发 `TaskQueueConsumer`（清洗需停机，不适合自动打补丁） |
| **P0-4 质量分虚高** | 消费率/解决率本身就是"自认知体系的质量分"，为其提供**真实可判定**的样板 |

## 九、落地路径与灰度

| 阶段 | 内容 | 验收 |
|---|---|---|
| **G0** | 只加 `ReportEnvelope` + 注册表 + 落盘，**不分发** | 报告落盘率 100%；零行为变化 |
| **G1 观测** | `MetricsConsumer` 上线，**只统计不触发** | 能算出真实消费率基线 |
| **G2 告警** | `AlertConsumer` 接管 P0 | 告警准确率 ≥ 80% |
| **G3 任务** | `TaskQueueConsumer` 接管 P1 | 债务清单自动补充 |
| **G4 闭环** | 效果验证回写 | 解决率可计算 |

**开关**：`ENABLE_REPORT_CONSUMPTION`（默认 `False`）
→ 关闭时**不注册、不分发、不落盘**，与现状完全一致。

## 十、风险评估

| 风险 | 影响 | 缓解 |
|---|---|---|
| 误判 P0 → 触发错误补丁 | 框架被自己改坏 | G2 阶段**只告警不自动打补丁**；自动补丁延到 G4 后 |
| 报告量爆炸（1108 行日志/12h） | 分发开销 | 按 `report_type` 聚合；P2 只留日汇总，不逐条分发 |
| 环形触发（A 触发 B，B 又触发 A） | 死循环 | 同一 `report_type + anomaly.code` 冷却期 ≥ 1 周期；全局动作配额 |
| 消费率被"假消费"注水 | 指标失真 | `accepted` 必须伴随 `action_taken` 或明确的 `none` 理由；纳入审计 |
| 改造现有叙事自我链路 | 破坏已工作功能 | G0/G1 阶段**保留原硬编码路径**，双写；G4 验证后再切换 |
