## 二、可优化模式（实测 4 类，剔污染口径）

| 指标 | 值 |

| 重复 prompt 组数 | 18 条记录涉及 ≥5 次的组 |

| 典型 | 搜索意图分类 prompt（同一模板重复出现） |

**结论**：意图分类、极性判别这类**确定性任务**的 prompt 高度模板化，
**结果可复用**。第41批已落地 `nucleus/llm/semantic_cache.py`（L1 仅观测，阈值 0.92），
本模式正是它的目标场景 —— **待 L2 启用后可直接收益**。

### 模式 2：失败调用未记录原因（**可诊断性**）

| 指标 | 值 |
|---|---|
| failed 条数 | 9（剔污染后） |
| **error 为空** | **9 / 9（100%）** |

**结论**：失败时 `error` 字段恒空 → 无法区分"网络超时 / 限流 / 参数错误 / 内容审核"，
**重复试错不可避免**。补记 `error` 是**极低风险、高收益**的动作（也提升 T1 的数据质量分）。

### 模式 3：`prompt_version` 全缺失（**无法归因**）

233/233 条为空。**后果**：无法按提示词版本回溯效果差异，精简前后的对比**没有基线**。

### 模式 4：渠道/模型选择分散（**成本与延迟**）

剔污染后仍有 **6 个渠道 / 6 个模型**。确定性任务（意图分类、极性判别）无需大模型，
可用最便宜的渠道或本地规则。

## 三、追问合并机制设计（仅设计）

### 3.1 现状问题

自主进化循环中，一个补丁的验证可能触发**多次 LLM 调用**（生成补丁 → 评估质量 →
反思改进 → 再验证）。每次调用都是**独立短调用**，累计成本高、上下文重复。

### 3.2 合并策略（三档，按风险递增）

| 档 | 策略 | 适用 | 预期收益 | 风险 |
|---|---|---|---|---|
| **A. 结果复用** | 同 prompt（规范化后）在 T 秒内命中缓存 → 直接复用 | 幂等任务（分类/判别） | 高（实测 ≥18%） | **低** |
| **B. 失败退避** | 同 prompt 连续失败 N 次 → 熔断 T 分钟 | 限流/超时类失败 | 中（避免无效重试） | **低** |
| **C. 批合并** | 同一"追问链"内的 K 次短调用 → 合并为 1 次长调用（多问题单次回答） | 进化循环的"生成+评估+反思" | 高（K:1 降幅） | **中**（提示词需重构、输出需解析拆分） |

### 3.3 C 档（追问链合并）设计要点

1. **识别追问链**：同一 `trace_id` 谱系 / 同一 `origin` + 时间窗（如 60s）内的连续调用
2. **合并提示词**：把 K 个"系统+用户"对拼成**单次多轮**，要求模型**分段输出**（带分隔标记）
3. **输出拆分**：按分隔标记切分 → 回填各自的 `trace_id`（保持可观测性）
4. **回退**：解析失败时**降级为逐条调用**（保证正确性，只损失收益）
5. **开关**：`ENABLE_LLM_CALL_BATCH_MERGE`（默认 False，灰度）

### 3.4 ★不建议做的事

* **不要**把"内在模型输出"记入训练集（防自我蒸馏退化螺旋，见 P1-256/第43批 T3 铁律）
* **不要**为了降低依赖度而跳过必要的验证调用（会牺牲正确性）

## 六、与内在模型的关系

本方案是**依赖度治理的实施路线**，与内在模型各层的关系：

| 层 | 组件 | 与本方案的关系 |
|---|---|---|
| L1 | 语义缓存器（第41批） | **A 档的直接载体**（命中即省调用） |
| L1 | 数据质量评估器（第43批） | 提供"调用数据是否可信"的前置判据 |
| L2 | 经验检索器（第42批） | 减少"为找经验而调 LLM"的次数 |
| L4 | 补丁质量评估器（第42批） | 减少"无效补丁-重复发现-重复调用"的循环 |
| L4 | 模型自更新器（第43批） | 让上述模型持续迭代、退化可回滚 |

**★核心判断**：依赖度的真正来源是**进化循环的重复发现问题**（第41批定性：
98.8% 调用来自自主进化）。因此**最高杠杆的动作不是"合并调用"，而是让补丁真正生效**
（→ L4 补丁质量评估器 + 进化真实基线）。**调用精简是辅助手段，不是主线。**
