# 预埋设计原则与演进路线

**版本**：v1.0
**日期**：2026-09-10
**设计人**：星轨
**定位**：曈曈PulseNet框架演进的元方法论——从"被动修复"到"预埋式演进"
**核心哲学**：外物是拐杖不是腿，每一次修复都应该让架构更清晰，而不是仅仅把bug压下去

---

## 一、为什么需要预埋设计原则

### 1.1 问题陈述

在过去的技术债务清理中，我们发现了以下模式：

1. **补丁摞补丁**：修了A模块导致B模块出问题，然后再修B模块，每个修复都是孤立的
2. **设计实施时大量补强**：等到PHASE18正式启动时，发现基础数据缺失、接口不统一，需要大量返工
3. **根因分析不深**：很多修复只解决表面现象，没有深入到系统性根因
4. **前后不连贯**：上一批修复的产出没有被下一批复用，每次都重新采集数据

### 1.2 核心理念

**技术债务不是"欠账"，而是"演进的线索"。**

每修一个问题，都应该：
- 让整个系统的架构更清晰
- 为下一个问题的解决做前置铺垫
- 为后续的设计实施预埋数据和接口

**没有预埋意识的修复，是"还债"；有预埋意识的修复，是"投资"。**

## 二、三条核心原则

### 原则1：技术债务清理必须"向前看一步"

**旧模式**：
```
发现问题 → 修复问题 → 验证修复 → 结束
```

**新模式**：
```
发现问题 → 深度分析根因 → 修复问题 
  → 顺便为下一个问题/下一个设计做预埋 
  → 验证修复 → 记录预埋点
```

**具体要求**：
- 每修复一个P0/P1问题，必须问自己："这个修复的产出，能不能被后续的设计复用？"
- 如果能，就在修复时顺手把接口/数据结构/日志格式做成"可扩展"的
- 修复完成后，在技术债务清单中记录"预埋点"：本次修复为XX设计预留了XX接口/数据

**示例**：
- 修复"自主进化修复率为0"时，不只是修LogAnalyzer的正则，而是扩展self_inspector的定位能力，同时为器官关联图谱预留`export_organ_call_graph()`接口
- 修复"QICA意图分类"时，不只是加规则，而是把意图分类结果做成可输出的结构化数据，为关联图谱的"器官使用频率"提供数据源

### 原则2：发现问题后必须做"三层深度分析"

#### 第一层：直接根因
- 这个问题为什么发生？
- 是代码bug、设计缺陷、还是数据问题？

#### 第二层：关联影响
- 修复这个问题会不会影响其他模块？
- 会不会引入新问题？
- 有没有类似的问题在其他模块存在？

#### 第三层：前置铺垫
- 这个问题的根因，是不是下一个问题的前兆？
- 能不能顺便把下一个问题也解决了？
- 这个修复的产出，能不能被后续设计复用？

**具体要求**：
- P0问题必须做三层分析
- P1问题至少做两层分析
- 分析结果写入技术债务清单的"分析记录"字段

**示例**：
- 问题：自主进化修复率为0
  - 第一层：LogAnalyzer对普通ERROR行只提取organ，file/method为空
  - 第二层：SafeEvolutionExecutor拿不到代码片段→跳过修复；self_inspector有定位能力但没被调用
  - 第三层：self_inspector的定位能力可以扩展为统一的定位服务，同时为器官关联图谱提供调用关系数据

### 原则3：修改必须"前后连贯"，禁止"补丁摞补丁"

**禁止**：
- 只修表面现象，不改根因
- 修了A模块，导致B模块出问题，然后再修B模块
- 每个修复都是孤立的，没有考虑整体架构

**要求**：
- 修复前先画"影响链"：这个修改会影响哪些模块？
- 修复时考虑"下一跳"：这个模块修好后，下一个该修的是什么？能不能顺手做了？
- 修复后验证"回归"：有没有引入新问题？

## 三、可执行的检查清单（每次修复前必过）

```
□ 1. 这个问题的直接根因是什么？（第一层）
□ 2. 修复这个问题会影响哪些模块？（第二层）
□ 3. 这个问题的根因，是不是其他问题的前兆？（第三层）
□ 4. 修复的产出（数据/接口/日志）能不能被后续设计复用？
□ 5. 如果能复用，接口是否做成了可扩展的？
□ 6. 有没有顺手把"下一个该修的问题"的前置铺垫做了？
□ 7. 修复后会不会引入新问题？有没有做回归验证？
□ 8. 本次修复的"预埋点"是否记录到技术债务清单？
```

## 四、技术债务清单新字段规范

在`完整进化路线与技术债务清单_v1.0.md`中，每个P0/P1问题增加以下字段：

| 字段 | 说明 | 示例 |
|------|------|------|
| **根因层次** | 直接根因/关联根因/系统性根因 | 系统性根因：日志输出层不携带位置信息 |
| **影响链** | 修复会影响哪些模块 | LogAnalyzer → SafeEvolutionExecutor → 修复率 |
| **预埋点** | 本次修复为哪个后续设计做了铺垫 | 为器官关联图谱预留了`export_organ_call_graph()`接口 |
| **下一跳** | 修完这个后，下一个该修的是什么 | 下一个：日志输出层自动附加位置信息 |
| **分析深度** | 做了几层分析 | 三层（直接根因+关联影响+前置铺垫） |

## 十、总结

**预埋设计原则的本质，是从"反应式工程"升级到"预见式工程"。**

- 反应式工程：问题来了才修，修完就忘，下一个问题来了再修
- 预见式工程：修一个问题时，看到下三个问题，顺便把路修好

**每一次修复，都应该是一次架构投资，而不是一次债务偿还。**

当我们用这个视角看待技术债务时，技术债务就不再是"负担"，而是"演进的路标"——它告诉我们系统的薄弱环节在哪里，也指引我们下一步应该往哪里走。
