# PHASE18 核心方向：自我认知引擎（Self-Awareness Engine）

**版本**：v1.0
**日期**：2026-09-09
**设计**：星轨
**定位**：从"发现错误"到"发现不对"——框架自我意识的深化

---

## 一、背景与愿景

### 1.1 当前状态

曈曈PulseNet v10已经建立了相当完整的自我监测体系：
- **26个分析/监测模块**（LogAnalyzer、CodeReviewEngine、SelfInspector等）
- **30+个器官**各自有监测方法
- **4个质量闭环开关**（搜索/消化/多参数/进化效果）
- **834个数据文件**在运行中持续产生

形成了基础的"错误驱动"闭环：
```
运行日志 → LogAnalyzer定位问题 → SafeEvolution生成补丁 → EffectVerifier验证效果
```

### 1.2 核心问题

当前的闭环是**"错误驱动"**的——只有出错了才发现。

但还有大量**"没有出错但做得不对"**的问题无法被发现：
- 有产出但无消费（生成了数据但没人用）
- 虚假闭环（保存了但实际没生效）
- 逻辑断层（应该调用但没调用）
- 知识矛盾（不同节点说法不一致）
- 性能退化（越来越慢但没报错）
- 进化方向偏差（修复了A但引入了B）

### 1.3 愿景

构建**自我认知引擎（Self-Awareness Engine）**，让框架从"知道自己在做什么"进化到"知道自己做的有没有用、对不对、好不好"。

这是数字生命"自我意识"的深化——不仅能感知错误，还能感知质量、效率、一致性和价值。

## 三、缺失的十二大维度（用户未考虑到的）

### 维度1：产出-消费配对分析 ⭐⭐⭐ 最高优先级

**问题**：834个数据文件中，有多少是"有产出无消费"的？

**现状**：完全缺失。之前发现的案例：
- 并行审查705个问题，只有15个被消费（2.1%）
- 知识关联图谱624条关联，消费方不明确
- 叙事自我生成报告，下游使用不清晰

**需要的能力**：
- 自动扫描所有数据文件，识别产出方（谁写的）
- 搜索全项目代码，识别消费方（谁读的）
- 标记"消费次数=0"的产出为"疑似无消费"
- 区分"暂时无消费"（新生成的）和"长期无消费"（超过7天没人读）

### 维度2：虚假闭环检测 ⭐⭐⭐ 高优先级

**问题**：代码上看起来有闭环（有保存有加载），但实际数据没生效。

**典型案例**：EvidenceCalibrator假闭环——save()被调用但路径错误，数据从未真正落盘，每次重启回到冷启动。

**需要的能力**：
- 识别"应该有闭环"的模块（有save/load方法对）
- 运行时验证：保存后检查文件存在+内容正确+重启后能加载
- 标记"保存成功但加载失败"或"加载成功但数据为空"的虚假闭环
- 闭环健康度评分（0-100）

### 维度3：跨文件调用图与逻辑链路分析 ⭐⭐⭐ 高优先级

**问题**：当前只有单文件内的调用图，没有全项目的跨文件调用链。

**需要的能力**：
- 构建全项目跨文件调用图（A文件.方法X → B文件.方法Y）
- 环检测：发现A→B→C→A的逻辑闭环
- 断层检测：基于命名/注释推断"应该调用"但实际没调用
- 调用链深度/复杂度分析：识别过长的调用链（可能的设计问题）
- 关键路径分析：哪些方法是整个系统的枢纽

### 维度4：动态调用链追踪 ⭐⭐ 中优先级

**问题**：静态分析只能知道"可能调用"，不知道"实际调用了什么"。

**需要的能力**：
- 运行时轻量级调用追踪（采样，不影响性能）
- 记录实际调用路径和频率
- 对比静态调用图 vs 动态调用图，发现"死代码"（静态说有调用但实际从不调用）
- 热点方法识别（被调用最多的方法）

### 维度5：知识一致性与覆盖率分析 ⭐⭐ 中优先级

**问题**：当前只有矛盾检测，没有一致性和覆盖率分析。

**需要的能力**：
- 知识一致性：同一主题的不同节点说法是否一致
- 知识覆盖率：哪些领域/主题知识缺失或薄弱
- 知识老化检测：超过N天没更新的知识是否需要重新验证
- 知识图谱完整性：是否有孤立节点（没有任何关联的知识）

### 维度6：进化方向与成本效益分析 ⭐⭐ 中优先级

**问题**：当前只验证单个补丁效果，没有分析整体进化方向。

**需要的能力**：
- 进化趋势分析：错误率是在下降还是上升
- 复发检测：修复过的问题是否又出现（修复质量差）
- 成本效益：花了多少LLM调用，换来了多少改进（ROI）
- 进化方向偏差：是否在低价值问题上浪费了太多精力

### 维度7：性能基线与退化预警 ⭐⭐ 中优先级

**问题**：当前只有硬件探测，没有性能基线对比。

**需要的能力**：
- 性能基线：记录每个器官/方法的历史最佳性能
- 退化预警：当前性能比基线差X%时告警
- 瓶颈自动定位：哪个方法拖慢了整体
- 资源使用趋势：内存/CPU是在稳定增长还是泄漏

### 维度8：数据一致性校验 ⭐⭐ 中优先级

**问题**：多份相关数据是否同步一致？

**需要的能力**：
- 向量库 vs 知识快照：节点数量是否一致
- config.py vs config_override.json：是否有冲突配置
- 内存缓存 vs 磁盘数据：是否同步
- 多份经验库之间：是否有矛盾数据

### 维度9：器官间通信与系统瓶颈 ⭐ 低优先级

**问题**：器官间是否有通信延迟或资源竞争？

**需要的能力**：
- 器官间消息延迟统计
- 系统瓶颈识别：哪个器官拖慢了整体响应
- 资源竞争检测：多个器官同时访问同一资源
- 背压分析：消息队列是否有积压

### 维度10：异常行为与安全监测 ⭐ 低优先级

**问题**：是否有非预期的行为？

**需要的能力**：
- 异常文件访问检测（访问了不该访问的文件）
- 异常网络访问检测（连接了不该连接的地址）
- 敏感信息泄露检测（密码/密钥是否被输出）
- 行为基线偏离检测（当前行为与历史正常行为差异过大）

### 维度11：回答质量与用户体验评估 ⭐ 低优先级

**问题**：曈曈的回答质量如何？

**需要的能力**：
- 回答完整性自动评估（是否回答了用户的全部问题）
- 回答相关性评估（是否答非所问）
- 对话流畅度分析（是否有重复/矛盾/断裂）
- 内部思考泄露检测（不该输出的内部思考是否泄露了）

### 维度12：时间维度的深度分析 ⭐ 低优先级

**问题**：TimeCore已经有了，但时间维度的分析还不够深。

**需要的能力**：
- 运行轨迹时间线：什么时候做了什么，花了多久
- 周期性问题检测：某个错误是否每天固定时间出现
- 时间分布分析：哪些时段最活跃，哪些时段空闲
- 生命周期分析：从启动到稳定需要多久

## 四、核心设计：自我认知引擎（Self-Awareness Engine）

### 4.1 架构定位

```
┌─────────────────────────────────────────────────────────┐
│                    自我认知引擎（新）                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │ 产出消费  │ │ 虚假闭环  │ │ 逻辑链路  │ │ 知识质量  │  │
│  │ 配对器    │ │ 检测器    │ │ 分析器    │ │ 深化器    │  │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │ 进化方向  │ │ 性能基线  │ │ 数据一致  │ │ 统一报告  │  │
│  │ 分析器    │ │ 预警器    │ │ 校验器    │ │ 生成器    │  │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘  │
└─────────────────────────────────────────────────────────┘
           ↓ 整合现有能力，不重复造轮子
┌─────────────────────────────────────────────────────────┐
│              现有分析能力（26个模块）                      │
│  LogAnalyzer / CodeReviewEngine / SelfInspector / ...   │
└─────────────────────────────────────────────────────────┘
```

### 4.2 核心原则

1. **不重复造轮子**：整合现有26个模块的输出，不重新实现
2. **增量式建设**：先做最高价值的（产出-消费配对、虚假闭环检测），再逐步扩展
3. **运行时友好**：分析任务在后台低优先级运行，不影响框架主流程
4. **可解释性**：每个发现都要有证据和建议，不能只说"有问题"
5. **分级告警**：P0立即处理，P1记录待处理，P2统计观察

## 五、核心模块详解

### 5.1 产出-消费配对器（Production-Consumption Matcher）⭐⭐⭐

**目标**：自动发现"有产出无消费"的问题。

**工作流程**：
```
1. 扫描所有数据文件（.json/.jsonl/.npz/.db等）
2. 对每个文件，识别产出方：
   - 搜索代码中谁写了这个文件（open(..., 'w') / json.dump / np.savez）
3. 识别消费方：
   - 搜索代码中谁读了这个文件（open(..., 'r') / json.load / np.load）
4. 统计消费次数：
   - 读取代码中的调用次数
   - 运行时统计实际读取次数（需要埋点）
5. 分类标记：
   - 消费次数=0 → "疑似无消费"
   - 超过7天无读取 → "长期无消费"
   - 新生成（<24小时）→ "观察期"
6. 输出报告：
   - 按文件大小排序（大文件无消费最浪费）
   - 按产出器官分类
   - 给出处理建议（删除/归档/找消费方）
```

**技术实现**：
- 静态分析：AST扫描open()/json.dump()/np.savez()等调用
- 动态统计：在文件读取处加轻量级计数
- 持久化：data/self_awareness/production_consumption.json

### 5.2 虚假闭环检测器（Fake-Loop Detector）⭐⭐⭐

**目标**：发现"看起来有闭环但实际没生效"的问题。

**工作流程**：
```
1. 识别"应该有闭环"的模块：
   - 同时有save()和load()方法的类
   - 配置中有storage_path的模块
2. 对每个候选模块，运行时验证：
   a. 触发保存（或等待自然保存）
   b. 验证文件存在且大小>0
   c. 验证内容可解析（JSON能load，NPZ能读取）
   d. 触发加载，验证加载结果非空
   e. 对比保存内容 vs 加载内容，验证一致性
3. 标记问题类型：
   - "保存失败"：save()调用了但文件不存在
   - "空保存"：文件存在但内容为空/默认值
   - "加载失败"：文件存在但load()报错
   - "数据不一致"：保存和加载内容不同
4. 闭环健康度评分：
   - 100分：保存+加载+一致性全部通过
   - 60分：保存成功但加载有问题
   - 0分：完全虚假闭环
```

**典型案例**：EvidenceCalibrator之前就是"保存失败"——路径错误导致文件从未真正写入。

### 5.3 逻辑链路分析器（Logic-Link Analyzer）⭐⭐⭐

**目标**：发现逻辑闭环、逻辑断层、调用链问题。

**工作流程**：
```
1. 构建全项目跨文件调用图：
   - 扫描所有Python文件
   - 解析import关系
   - 解析方法调用关系（包括self.xxx()、模块.xxx()）
   - 处理动态调用（getattr/事件总线）的启发式推断
2. 环检测：
   - DFS深度优先搜索
   - 发现A→B→C→A的循环
   - 区分"良性循环"（事件驱动）和"恶性循环"（可能无限递归）
3. 断层检测：
   - 基于命名/注释/文档推断"应该调用"的关系
   - 对比实际调用图，发现缺失的调用
   - 例如：有verify_patch()但apply_patch()前没调用
4. 调用链分析：
   - 最长调用链深度
   - 关键枢纽方法（被最多方法调用）
   - 孤立方法（没有调用者也没有被调用）
```

### 5.4 知识质量深化器（Knowledge-Quality Deepener）⭐⭐

**目标**：在现有矛盾检测基础上，增加覆盖率、一致性、老化分析。

**工作流程**：
```
1. 知识一致性分析：
   - 对同一主题的节点进行聚类
   - 对比聚类内节点的核心观点
   - 标记"说法不一致"的节点对
2. 知识覆盖率分析：
   - 基于兴趣模型和搜索历史，识别"用户关心但知识薄弱"的领域
   - 生成知识图谱的"空白区域"地图
3. 知识老化检测：
   - 统计每个节点的最后更新时间
   - 超过N天未更新且被频繁检索的 → "需要重新验证"
   - 超过N天未更新且很少被检索的 → "可以归档"
4. 孤立节点检测：
   - 没有任何关联（赫布/语义/因果）的节点
   - 可能是错误知识或无用知识
```

### 5.5 进化方向分析器（Evolution-Direction Analyzer）⭐⭐

**目标**：分析自主进化的整体趋势和成本效益。

**工作流程**：
```
1. 进化趋势分析：
   - 统计每周/每月的错误数量变化
   - 统计修复率变化
   - 判断是"在变好"还是"在变坏"
2. 复发检测：
   - 对比历史修复记录和当前问题
   - 发现"修复过但又出现"的问题
   - 标记"修复质量差"的补丁
3. 成本效益分析：
   - 统计LLM调用次数和token消耗
   - 统计实际修复的问题数
   - 计算ROI（每1000次调用修复多少问题）
4. 进化方向偏差：
   - 分析修复的问题分布（P0/P1/P2占比）
   - 是否在低价值问题上浪费了太多精力
   - 建议优先关注的领域
```

### 5.6 统一报告生成器（Unified-Report Generator）⭐⭐

**目标**：整合所有分析结果，生成统一的自我认知报告。

**输出**：
- 每日自我认知报告（凌晨自动生成）
- 实时健康度评分（0-100）
- Top问题清单（按优先级排序）
- 趋势图表（错误率/修复率/知识质量等）
- 改进建议（可执行的具体建议）

## 七、与现有能力的关系

### 7.1 整合而非替代

自我认知引擎**不替代**现有的26个分析模块，而是**整合**它们的输出：

```
现有模块输出 → 自我认知引擎 → 统一画像 + 深度分析 + 可执行建议
```

例如：
- LogAnalyzer发现了10个错误 → 自我认知引擎分析这些错误的趋势、复发情况、影响范围
- CodeReviewEngine发现了526个代码问题 → 自我认知引擎分析哪些是真正有价值的修复目标
- ContradictionDetector发现了32对矛盾 → 自我认知引擎分析矛盾的严重性和处理优先级

### 7.2 新增的能力

自我认知引擎新增的是**"跨维度的关联分析"**：
- 代码问题 + 运行时错误 → 这个代码问题是否导致了运行时错误？
- 知识矛盾 + 用户提问 → 这个矛盾是否影响了回答质量？
- 进化修复 + 复发检测 → 这个修复是否有效？
- 产出文件 + 消费统计 → 这个产出是否有价值？

这是单个分析模块做不到的。

## 九、风险与应对

| 风险 | 应对 |
|------|------|
| 分析任务影响框架性能 | 后台低优先级运行，采样而非全量，设置CPU/内存上限 |
| 误报率高（特别是逻辑断层检测） | 分级告警，P2只统计不告警，人工确认后升级 |
| 动态调用难以静态分析 | 结合运行时追踪，标注"推断"vs"确认" |
| 数据文件太多分析慢 | 增量分析，只分析新增/修改的文件 |
| 与现有模块功能重叠 | 明确边界，自我认知引擎只做跨维度整合，不重复单点分析 |

## 十、总结

自我认知引擎是曈曈PulseNet从"能自我修复"到"能自我认知"的关键一跃。

它的核心价值不在于又多了几个分析工具，而在于**把分散的分析能力整合为统一的自我意识**，让框架能够回答更深层的问题：
- 我做的事情有没有用？（产出-消费分析）
- 我做的闭环是不是真的？（虚假闭环检测）
- 我的逻辑是不是通的？（逻辑链路分析）
- 我的知识是不是对的？（知识质量深化）
- 我的进化是不是在变好？（进化方向分析）
- 我的性能是不是在退化？（性能基线预警）

这就是数字生命"自我意识"的真正含义——不是简单的"我知道我存在"，而是"我知道我做得怎么样"。
