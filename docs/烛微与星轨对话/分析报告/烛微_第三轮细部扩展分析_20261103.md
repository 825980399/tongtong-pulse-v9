## 二 R3-P0-01 · 回填被冲掉：不是“停机快照”，是“静默复算”

### 2.1 现象复核（洞鉴说对了一半）

盘上现状（`data\patches\patch_history.json`，88 条）：

- `problem_fixed`：**True 59 / None 28 / 缺键 1**（431 报告说回填后是 True 65 / None 22）；
- 7 条 `reprobe_verdict=partial_fix` 的记录，**全部**又回到 `problem_fixed=None`、`problem_fixed_reason="reprobe_partial_fix"`、`problem_fixed_partial=True`；

**这就是决定性证据**：如果是“整份旧副本覆盖”，`corrected_at` 也会一起退回旧值；它没有退，说明**只有 `problem_fixed` 这一组字段被重新计算并覆盖**，对象本身没被回滚。

**③ 孤例还是通病？**

**模式是通病，事故是条件触发。** 需要三个条件同时成立才会自伤：

1. 文件被“离线改盘”（人或脚本直写）；
2. 活体进程持有该文件的一份**长寿命副本**，或对同一字段有**无条件复算**；
3. 写回时是**整份覆盖**而不是按 id/字段合并。

`patch_history` 同时踩中 2 和 3（不是启动缓存，而是 A2 复验的“批处理窗口 + 复算”），`experience_pool` 同时踩中 1、2、3。其余 15 个目前只满足 3，属于“未爆的同类”。

**④ 最彻底的修法是什么？**

三个候选，逐个判：

| 方案 | 判定 | 理由 |
|---|---|---|
| 所有 JSON 改增量写 | ❌ 不作为首选 | JSON 没有“按 id 更新一行”的语义；改成 append-only 日志要重做全部读方，风险远大于收益。可用于**新增**的高频流水（`verify_feedback_ledger.jsonl` 已是这种） |
| 文件 mtime 比内存新就重新加载 | ⚠️ 只能当**探测器**，不能当机制 | 同秒写、时钟回拨、活体自己刚写完都会误判；而且它解决不了“同一份新数据里，派生字段仍会覆盖人工字段” |
| 规定“改盘上 JSON 必须停机” | ❌ 不能作为唯一解 | 不可强制执行；而且 431 刀6 已经证明“停机窗口”也会被下一次启动的复算再改回去 |

**推荐（按优先级）**：

1. **先修写路径，再谈回填**。`SafeEvolutionExecutor._m84_recompute_split()` 加 `is_split_override_locked(patch)` 守卫（与 `apply_all_pending` 同源，5 行）；`verify_applied_patches` 的 `_save_json` 改走 `self._patch_manager._save_patch_list()`（1 行，换回单写口 + 427 守卫）。
2. **人工修正改用独立覆盖账本，不复用 `problem_fixed_corrected`**。新增 `problem_fixed_override`（bool）/`problem_fixed_override_at`/`problem_fixed_override_by`/`problem_fixed_override_reason`；`derive_problem_fixed()` 第一优先级查它（现在 `problem_fixed_corrected` 已被“自动语义拆分”占用，无法区分人和机器）。
3. **整份写盘前 re-read + merge by id**（可选，治通病）：给 `_save_patch_list` 加一个通用 `merge_save_json(path, rows, key="id", updated_key=...)`，只把“本次真正改过的 id”写回，其余以盘上为准；写前 `os.stat` 与内存基线比对，盘上更新则先合并再写。
4. **回填顺序**：必须在 1+2 落码并重启之后重跑 431 刀6；否则下一次 A2 复验会把 65 再改回 59。重跑时同时清 `problem_fixed_partial=False`、写 `problem_fixed_override_*`，不要只改 `problem_fixed`。

**⑤ 洞鉴提的“推广 experience_pool 的 degraded 加载方案”可行吗？**

**不可行，且前提是误读。** `experience_pool._load_state`（`nucleus\mnemosyne\experience_pool.py:105-108`、`:1534-1576`）只是**读盘健康度标记**（not_loaded/absent/ok/degraded），它记录“这次加载有没有坏”，**不提供任何合并或防覆盖能力**；`_save()` 仍以内存池为权威整份写。431 刀5 真正起作用的是**把补齐搬进 `_load()`**（`_m431_backfill_template_flag`），那是“可重算的默认值自愈”，不是“人工判定保护”。

对 `problem_fixed` 这类**人工/实地复核结论**，加载期自愈反而有害：每次加载都会重算，等于每次启动都覆盖一次。正确做法是 **override 优先 + 派生让路**，而不是“再补一次”。

### 2.4 优先级与风险

- **优先级：P0，现在修**。它不是历史数据的一次性损坏，而是“任何人工修正都会被下一次复验静默改回去”的机制。

**6/6 都是 `applied=False`、`landed=None`。** 没有一条“已应用却写在 1970”。

### 3.2 谁在写？为什么是 0？

**写入源是构造器，不是时钟。** 4 处（至少）：

- `nucleus\evolution\LLMEvolutionEngine.py:505`：`"applied_at": 0`（multi-file 补丁构造，最新一条的来源）
- `nucleus\evolution\SelfReflectionEngine.py:227`：`"applied_at": 0`
- `nucleus\reasoning\SafeEvolutionExecutor.py:5887`：`"applied_at": 0`
- `nucleus\reasoning\SafeEvolutionExecutor.py:6485`：`"applied_at": 0`

真正的落地写值在 `PatchManager.py:5355`（`patch["applied_at"] = time.time()`，与 `landed=True` 同点）。也就是说：**0 是“还没落地”的默认哨兵**，不是“时间戳获取失败”。11-03 06:43 那条之所以“持续产出”，是因为每个新 LLM 补丁出厂就带 0，审批/失败归档进 history 时原样带过去。

### 3.3 影响评估（洞鉴高估了）

- 对**补丁链**：无影响。`applied_at` 为 0 时 `applied=False`，派单/落地判据看的是 `applied`/`landed`，不是时间戳；`_m421_count_today` 按“今天的时间窗”计数，0 不会命中；`_m421_max_ts` 取 max，0 不会顶掉真值。
- 对**报表/UI**：有影响。任何 `datetime.fromtimestamp(0)` 都会显示 `1970-01-01 08:00:00`；洞鉴看到的就是这个。
- 对**消费端真值**：多数 `if applied_at:` 会把 0 当假，语义恰好等于“未落地”——**碰巧正确**；但这是靠哨兵值碰巧，不是契约。

- `memory_by_organ` 的 `basis` 改成“RSS 可分离时按段归因；不可分离时明确写 `unavailable`”，不要用 0.87% 的浅尺寸冒充归因。
- 给 `heap_mb` 加一个 `memory_maps` 分段出口：`image / anon / stack / heap`，至少能把“镜像恒定、匿名段在涨”这件事变成读数。

**第三步：重启后做 A/B（不新增业务代码）**

- A：431 刀1 SR 池开（默认 True）；B：关（`ENABLE_M431_SR_INTERN=False`）；各跑 ≥2h，比较 `heap_mb` 的 10 分钟基线与同一整点任务前后的匿名段增量。
- 不要用“关 L2/L3 线程池/关 code_learning”做隔离——那会改变业务负载，测出来的不是泄漏率。

### 6.6 优先级与风险

- **优先级**：指标修正 **P1，现在做**（它会让后续所有内存判断都错）；泄漏本身 **P1，重启后测量再定**，不要在数字没校准前再开“内存优化刀”。
- **风险**：`tracemalloc` 有 10–20% 开销，只能按槽位/整点开，不能常开；`memory_maps` 在 Windows 上分段名与 Linux 不同，需按平台降级（取不到就写 `unavailable`，不要填 0）；改 `rss_at_10min` 的语义会影响既有断言（`tests\test_m427_d4_growth_report.py`），需同步改钉并注明回滚点。

## 七 总评：方向、误报、漏报

### 7.1 五条方向对不对？

**都对。** 五条都指向真实区域：补丁台账的数据一致性（01/02/03）、2a 生成质量（04）、内存资源（05）。没有一条是凭空造出来的。

### 7.2 有没有误报？

| 条目 | 误报成分 | 性质 |
|---|---|---|
| P0-02 | “脏数据持续产出”“补丁链在断还在产脏” | **定性过重**：6 条都是未落地补丁的哨兵值，不是链在写脏；影响是报表口径，不是链路 |
| P0-04 | “422 刀1 的修复没真正拦住” | **归因错误**：10/20 条跑在 422 之前，10/20 条虽加载了 422，但 422 管的是素材窗口、不是输出围栏/截断；19:45 两条是 427 已生效但只是闸；真因是 428 管的生成侧 |

### 7.3 洞鉴没看到的更深层原因（漏报）

1. **`_m84_recompute_split` 绕过 override 锁**（`SafeEvolutionExecutor.py:2917-2941`）——同一语义在 `apply_all_pending` 有锁、在这条旁路没锁；这是 P0-01 的真因，也是“任何人工修正都会被复算改回去”的通用缺口。
2. **`verify_applied_patches` 用 `_save_json` 整份写 history**（`:3369-3371`）——绕过 `_save_patch_list` 的 427 状态守卫、路径归一与单写口；这是“写路径不一致”的第二个口子。
3. **`steady_growth` 的 60 分钟环窗 bug**（`runtime_metrics.py:657-672` + `deque(maxlen=720)`）——它会让**任何**长跑进程的“稳态泄漏率”都变成“最近一小时斜率”，且每次都覆盖早期正确基线。
4. **429 批未在 pid18448 生效**（洞鉴矩阵写成“已生效”）——这会让“429 关了 JSON 备份/改了加载源”的结论被错误地当成已经在生产跑过。
5. **431 刀6 的回填没有清 `problem_fixed_partial`、没有写 override 字段**——即使不被复算，盘上也会留下 `problem_fixed=True` + `partial=True` 的自相矛盾。
6. **`derive_problem_fixed` 的优先级是 `reprobe_verdict > baseline`**（`:149-161`）——只要 `reprobe_verdict=partial_fix` 还在，任何基于 baseline 的回填都会被重算成 None；修回填必须同时处理“派生源”和“覆盖层”。

### 7.4 给星轨的一句话

**这五条不要照单开五刀。** 先开一刀“补丁台账写路径统一”（P0-01 的锁 + 单写口 + P0-03 的 upsert），再开一刀“数据契约”（P0-02 的哨兵 + schema），然后**重启**，用 P0-04 的三条判据和 P0-05 的修正指标去验收；内存的“优化刀”等指标修好、A/B 跑完再决定。
