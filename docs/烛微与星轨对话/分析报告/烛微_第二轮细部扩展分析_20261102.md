## 一 第一组：补丁链三连环

### R2-P01 · 2a 拒收 63/63，"判据过严" —— ⚠️ 现象对，归因反了

**现状**：`data\audit\failed_patches\` **63 条**（洞鉴 15:03 时 60 条），**63/63 stage=2a**，**62/63 是同一个方法** `PulseLiver._compress_group`，**50/63 片段仍带 ``` 围栏**。

**决定性证据：63 条没有一条能通过 `ast.parse`**。

```
遍历 63 条 modified_code → ast.parse:
  ok=0  bad=63
  错误分布: {"unexpected indent": 63}
```

原因不是"try 块不平衡"，而是**围栏行在列 0 让 `textwrap.dedent` 失效**：

```
modified_code 首行 = "```python"（列 0）
后续行            = "        try:"（8 空格）
dedent 的共同前缀 = ""（被围栏行拉平）⇒ 缩进原样保留 ⇒ ast.parse: unexpected indent
```

`_m376_try_balance`（`nucleus\reasoning\PatchManager.py:343`）只是**先撞上来的那道闸**；即使把它关掉，关 2 的 `ast.parse`（:3968 之后）也会以 `unexpected indent` 拒收。

**再看 3 条标本（任务书要求）**：

| 标本 | original_code | modified_code | 能否安全 apply |
|---|---|---|---|
| `…221359_…31bc` | 4 行，```python + try: + 注释 + `feats=…` | 5 行，同样停在 try 体内 | **不能**：片段在 try 中间截断，替换后方法体残缺 |
| `…221400_…3d00` | 4 行，`try:` 后接 `l2_node.evidence_chain = [` | 7 行，补完 list 后 `return …stage4` | **不能**：try 无 except，且原片段只覆盖方法中段 |
| `…125358_…280a` | 4 行，同上 | 12 行，重写了 `_compress_group` 前半段 | **不能**：新片段自带 `def`，与原文片段不同粒度 |

**结论**：判据不严，**片段生成坏了两处**（围栏未剥、按行截断在 try 内）。洞鉴建议的"放宽 2a"会让关 2 用更泛化的 `SyntaxError` 拒收，反而丢失 `open_lines/tail` 这些可定位信息。

**精确修法**：

1. `PatchManager.py:3943-3944`：在 `textwrap.dedent` **之前**剥围栏——
   `if _s.lstrip().startswith("```"): _s = _s.split("\n", 1)[1]`，再 dedent（6 行）。
2. 同上：`_mod_norm` 解析失败时，**在 2a 之前**加一道"片段可解析"预检，理由写"生成片段不完整（围栏/截断）"，而不是让 try 平衡闸背锅（12 行）。
3. 生成侧：`get_method_body` 之后按 **AST 语句边界**扩窗，禁止在 `try/finally/with` 体内截断（30 行，落在抽取器）。
4. 按 `(file, method)` 计失败次数，连续 3 次拒收冷却 24h（现在按 patch id 计，换 id 就绕过；62/63 同一方法就是证据）。

**连带影响**：只动规范化与留痕，不改关 0/1/2/3 的裁决；剥围栏后 `_m90_missing_patch_fields` 与 ratio 的输入变干净，可能放行一批原本被"缩进"误杀的补丁——需回归 `tests\test_m376_d4_try_balance.py`。

### R2-P03 · 涨速 1.344MB/min，"泄漏回来了" —— ⚠️ 读法错：是启动阶跃，不是持续泄漏

**pid 33156 的完整 RSS 曲线（肝 T-107a，共 32 个采样）**：

| 时刻 | uptime | RSS | 相对基线 |
|---|---|---|---|
| 15:03:30 | 34s | **3.81GB** | 0.00 |
| 15:13:34 | 638s | 5.38GB | +1.57 |
| 15:23:50 | 1254s | **6.27GB** | +2.46 |
| 15:34–15:54 | ~2500–3100s | 6.28–6.35GB | 平台 |
| 16:05:01 | 3725s | **6.83GB** | +3.02（第二次阶跃） |
| 16:15–17:42 | 4300–9585s | 6.89–6.91GB | **平台 87 分钟** |

**最近 1 小时：7,068 → 7,074MB = 0.16MB/min；当前 `growth_mb_per_min = −0.119`。**

**所以 1.344MB/min 是"启动 ramp 窗口"的平均斜率**。同一份日志在 15:05:28 甚至报过 **1815.9MB/min**——这个指标是短窗瞬时斜率，不能当泄漏率用。第一轮 0.277 与第二轮 1.344 的差别，本质是**采样窗口落在 ramp 的哪一段**。

**两次阶跃的归属（部分坐实）**：

- 15:05–15:23：知识库加载（`知识库: 14583节点, L3=4272个`，15:05:56）+ 代码学习首批（15:06:01 起），与我 416 的结论一致（parquet 行物化约 2GB）。
- 16:05：**未坐实**。前后日志只有常规节拍/快照，未定位到单点；标"待查"。

**`memory_by_organ` coverage 0.75% 是设计内的**，不是 bug：`basis="organ_object_graph(depth<=2, shallow_getsizeof)（不是 RSS）"`，209 条记录里 top 器官是肝 0.96MB（pct 35%）。它测的是"从器官根出发、深度≤2 的浅尺寸"，天然覆盖不到 pyarrow/numpy/队列里的裸 dict——这与 416 的结论一致，**不要拿它当 RSS 归因**。

**修法**：

1. **先改指标**：把"启动 ramp"与"稳态增长"分开——记录 `rss_at_10min` 作为基线，之后算斜率；`growth_mb_per_min` 增加 `window_sec` 字段，避免 1815 与 −0.119 这种读数被当成同一口径。
2. 定位 16:05 阶跃：对 16:00–16:06 打一次 `tracemalloc` window 快照差分（不是 resident），或用 `pyarrow.total_allocated_bytes()` 每 5 分钟记一次。
3. 若要把 6.9GB 基数降下来：知识库改**懒加载/分页**（现在启动即全量物化 14583 节点 + L3 4272），这是唯一能降基数的地方；线程 195 OS 也有成本（105 落差）。

**隔离测试（任务书问"关掉 code_learning 还涨吗"）**：从曲线看，15:06 代码学习开始后 RSS 仍在 15:23 才到 6.27，且 15:34 后平台——**code_learning 不是持续增长源**；但它是 15:05–15:23 阶跃的共同参与者，无法只靠现有日志分离。要分离必须做一次"关 code_learning 冷启"的对照，属批 B。
