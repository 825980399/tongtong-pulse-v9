## 〇、一句话结论

**v1.0 的方向是对的，P0 主链也基本抓到了；但它目前更像“问题清单的施工版”，还不是“可验收、可回滚、可追责的工程路线”。**

施工前建议补三件事：

1. **补 P0-0 内存泄漏分诊**——活体唯一自报 `is_leak_signal=True` 的硬信号，v1.0 没有排期；
2. **补 3 个高影响闭环**——知识自污染、伦理闸门 36s 同步阻塞、规则/handler 只记录不行动；
3. **把“只观察”改成“观察 + 收敛”**——线程预算、原生线程、进程池容量、向量库/compaction 都要有根因修复刀，而不只是 health 里多几个数。

补完这三类，v1.0 才能变成可施工的 v1.1。

## 二、必须先补的 6 个高影响项

### 2.1 内存泄漏信号没有排期（最该补）

**证据**（联合报告 §1.12 / §6，活体 health_snapshot）：

```
process_rss_mb = 6245.1
growth_mb_per_min = 179.667
steady_growth_mb_per_min = 6.126
is_leak_signal = True
```

**问题**：v1.0 的 P0/P1/P2 没有一条“内存泄漏定位”批次。steady 6MB/min ≈ 8.6GB/天，当前 RSS 已 6GB；这不是“以后再说”的 P2。

**建议新增 P0-0：内存泄漏分诊**

- 刀1：`tracemalloc` + `gc` + `objgraph` 三路采样，定位 top 增长对象；
- 刀2：区分缓存增长 / 快照列表 / 线程栈 / 原生库 RSS；
- 刀3：给出“可回收 / 不可回收 / 需要上限”的结论；
- 验收：24h `steady_growth_mb_per_min < 1`，或明确“这是有上限的缓存”。

**白话**：先查清楚是“真的漏”还是“缓存没上限”；不查就修，容易把正常缓存砍掉。

---

### 2.2 知识自污染回环没有排期

**证据**：联合报告 P1-3 已登记“检索命中自己生成的旧答案 → 再次强化 → 污染经验池”。

**问题**：v1.0 没有对应批次。

**建议新增 P1-9：知识自污染回环治理**

- 入口闸：`source=qa` 的经验入库前标记“是否自己生成 / 是否被用户纠正”；
- 检索闸：同一问题命中自己旧答案时降权/跳过；
- 反馈闸：用户纠错后回标污染；
- 验收：污染样本回灌率下降，检索命中不再放大旧错误。

**白话**：不能把“自己昨天说的”当成“今天的事实”，否则越学越偏。

---

### 2.3 伦理闸门同步阻塞 36s 没有排期

**证据**：联合报告 P1-4：伦理闸门在回答路径上同步阻塞，最坏 36s。

**问题**：v1.0 没有这条。

**建议新增 P1-10：伦理闸门异步化**

- 快路径：本地规则先给“放行 / 拒绝 / 待审”；
- 慢路径：LLM 伦理复核异步，不阻塞首答；
- 高风险才等待，低风险先答后审；
- 验收：普通对话 p95 不再被伦理闸门拉长；高风险仍有拦截。

**白话**：不能每句话都先过一遍“伦理庭审”再开口；低风险先答，高风险再拦。

---

### 2.4 本地规则覆盖率 0.7% / 21+3 类“只记录不行动”没有排期

**证据**：联合报告：

- P2-1：OA4 shadow `rule_hit=1/142`（0.7%）；
- P2-4：21+3 类结果只记录不行动。

**问题**：v1.0 只在“一句话”里提了“大部分 handler 只记录不行动”，没有批次。

**建议新增 P1-11：规则覆盖与 handler 行动化**

- 先统计 21+3 类里哪些是“应该行动但没行动”；
- 每类选 1 个最小行动闭环（写状态 / 发脉冲 / 触发检索）；
- 规则命中率目标从 0.7% 提到可测的 5–10%；
- 验收：每类有“输入→行动→可观测结果”的 e2e 用例。

**白话**：现在很多“听到了”只是记在本子上，没有真的去做；先把最关键的几类变成动作。

---

### 2.5 自认知 5 个 tick 全 `return ok` 没有排期

**证据**：联合报告 P2-3：`PulseSelfAwareness` 五个 tick 全是空实现。

**问题**：v1.0 没有这条。

**建议新增 P2-8：自认知 tick 行动化**

- 每个 tick 至少产出一个可观测结论（健康 / 异常 / 无变化）；
- 接入 `health_snapshot` / 叙事事件；
- 验收：连续 10 个 tick 有非 `ok` 的真实分支，或明确“本 tick 无异常”的原因。

**白话**：自认知不能只“打卡”，要真的说“我现在哪里不舒服/哪里正常”。

---

### 2.6 10 个轮询线程没有具体拆除批次

**证据**：《脉冲架构全维度落地分析》§2.1 列了 10 个轮询：

自主意图 2700s、自主探查约 60s、演化线程、LivenessWatchdog、runtime_state_writer 2s、param_patch_manager 300s、backup_retention、GradientTracker 10s、启动蒸馏、健康检查线程。

**问题**：v1.0 的 P3 只写“L2 全事件驱动”，没有“先拆哪几个、怎么验收”。

**建议新增 P1-12 / P3-1：轮询拆除分两期**

- 一期（P1）：`runtime_state_writer` 2s 改变化驱动、`LivenessWatchdog` 改心跳驱动、自主意图去掉兜底 sleep；
- 二期（P3）：演化/探查/补丁 apply 挂 `time.tick`，EventBus 升级为业务主脉；
- 验收：每个线程有“替换前后 wake 次数 / CPU / 延迟”对比。

**白话**：不是一次把 10 个闹钟全拆了，而是先拆最费电、最容易误事的三个。

## 三、v1.0 里“只观察、没修复”的根因刀

这些在烛微 36 条文档里有，但 v1.0 的批次只写了“进 health / 看见”，没有写“怎么修”。

| 项 | v1.0 现状 | 需要补的修复刀 |
|---|---|---|
| A3 硬件口径 | P0-批1 只采集 | 统一 `HardwareProfile`：逻辑/物理/P-E/NUMA/cgroup/thermal |
| A4 进程池内存 | 未提 | worker 数 = min(CPU, 可用内存/单 worker RSS) |
| A5 线程预算 | P0-批1 只进 health | `inventory()` 超预算要告警/收敛，不只是看 |
| A6 原生线程 | P0-批1 只观测 gap | `threadpoolctl` 运行时限 BLAS/OpenMP，目标 gap <15 |
| A7 进程池容量 | P0-批1 只报实际数 | 日志/health 同时报 `capacity/spawned/pending`，别再拿 max_workers 当实际 |
| A8 降级同步执行 | 未提 | broken pool 后走 fallback 队列，不在 publish 线程跑 CPU 任务 |
| B3 向量库 | P1-批2 “降频率” | 改 append-only 分片，别每次全量 `np.savez` 29MB |
| B4 冷存 compaction | P1-批2 “避开高峰” | 阈值从 2 改“文件数+大小+磁盘压力”三判据，可暂停 |
| B8 备份配额 | 未提 | `.bak/.failed/.protected` 总字节/代数上限 |
| B9 快照内存 | 未提 | 分批迭代节点，避免锁内大列表 + JSON 全量 |
| C3 告警风暴 | 未提 | `AlertGovernor`：60s 去重/合并/冷却，防止告警自激 |
| C4 器官公平 | 未提 | per-organ 虚拟时间/aging，防止单器官饿死其他 |
| C5 硬件采样 | 未提 | 独立 `ResourceSampler`，不依赖 Touch 器官 |
| E4 假硬件检测 | 未提 | `OscillonField.detect_hardware_capability` 标 `implemented=False`，别误当真实探测 |

**共同问题**：v1.0 把“可见性”当成“修复”，但上述每一项都需要“采集 + 判定 + 执行”三刀，不是一刀。

## 四、需要拆批/调顺序的地方

### 4.1 P0-批3 混了两个变量

`离线兜底主链互斥` + `补丁链自动应用` 是两类完全不同的风险。按“每批只改一类变量”的原则，应拆成：

- **P0-批3a**：离线兜底条件修复（纯逻辑，可单测）；
- **P0-批3b**：补丁链 apply=0 分诊（先查为什么 22 天 0 应用，再决定是否打开 `local_auto_apply`）。

补丁链必须补：

- 一条“安全补丁端到端应用 + 回滚”的验收；
- `apply=0 / voided=17 / pending=3 / state=degraded` 的前后读数；
- 不是“改个开关”就算完成。

**白话**：一个是“路走不通”，一个是“车从来没上路”；混在一批，出问题无法归因。

### 4.2 P0-批5 两刀太粗

“统一预算账本 + 磁盘压力进 load_level”至少应拆 3 刀：

- 5a：`ResourceSnapshot` + 统一账本；
- 5b：`HardwareProfile`（cgroup/thermal/P-E/NUMA/disk type）；
- 5c：`thread_budget` / `native_caps` / process pool 的真实收敛。

否则 2 刀会把“观测、策略、执行”混在一起，出问题无法归因。

### 4.3 P1-批4/5 没覆盖“失联四段”的全部

联合报告说失联处置是四段：

1. `PulseHealthMonitor` 漏订阅 `OrganEvent.SILENT`；
2. `PulseEmergencyHandler._attempt_recovery` 是 `return True` 桩；
3. `PulseSystemManager` 开关没开；
4. 恢复策略没有真实动作。

v1.0 只写了前两段。需要补：

- SystemManager 开关评审；
- 四段端到端故障注入（杀器官/断心跳/恢复）；
- 验收：失联后 30s 内进入 degraded，恢复后回到 normal。

### 4.4 P2-批3 L2→L3 融合可能该提前

`compress=13 / fuse=0` 是知识生长的核心闭环，不是“保整体性”的附属项。建议从 P2 提到 P1，至少先做“为什么 fuse 恒 0”的定位。

### 4.5 P3 太虚，缺“L2 全事件驱动”的具体批次

P3 只写了 L1→L4 的层级目标。需要补：

- 10 个轮询线程的逐个替换表；
- `EventBus` 是否从“旁路遥测”升级为“业务主脉”的决策；
- Event Sourcing 先选一个子系统试点（建议经验池/健康状态），不要全框架一起改。

## 五、治理字段缺失（洞鉴逐条比对时会卡住）

v1.0 的批次表缺以下列，建议 v1.1 补上：

| 字段 | 为什么需要 |
|---|---|
| **Owner** | 路灯/洞鉴/烛微，谁施工谁验收 |
| **是否重启** | 原则里写了“必须停机醒目标注”，表里没有 |
| **回滚开关/回滚点** | 每批必须有 config flag 或 `.bak` 回滚 |

```
批次 | 刀数 | 内容 | Owner | 是否重启 | 回滚开关 | 基线 | 验收命令 | 依赖
```

## 七、施工前检查清单（给星轨拍板）

### 7.1 必须先回答的 5 个问题

1. **内存泄漏**：先查还是先修？如果不查，P1 的所有“延迟优化”都可能被泄漏抵消。
2. **补丁链**：22 天 0 应用，是“开关关”还是“验证/审批卡住”？打开 `local_auto_apply` 的风险谁承担？
3. **离线兜底**：条件反转修复后，如何证明“真的能走到”？需要一条 e2e 用例。
4. **伦理闸门**：36s 是模型延迟还是同步等待？异步化后高风险拦截率会不会下降？
5. **P3 轮询拆除**：先拆哪三个？EventBus 是否要成为业务主脉，还是继续让 InfoField 承担？

### 7.2 必须补的基线

| 指标 | 当前/来源 | 目标 |
|---|---|---|
| OS 线程数 | 141 | 60–80 |
| Python 活跃线程 | ≈81 | 20–30 |
| 原生线程 gap | 60 | <15 |
| 进程池实际 worker | 1（容量 8+4） | 4–8（有任务时） |
| 主进程平均 CPU | 0.16 核 | 负载下 30–60% |
| 对话 p95 | 24–26s | 不退化，目标 ≤26.7s |
| RSS steady growth | 6.126 MB/min | <1 MB/min |
| eval | B0=B2=0/52 | 非零、可区分 |

### 7.3 必须补的验收方式

- 每批一条“可机械比对”的命令/断言；
- 每批一个回滚开关/回滚点；
- 每批标注“是否重启”；
- 每批标注 Owner；
- 改数据格式的批次，附迁移脚本/回滚脚本。

## 八、建议的施工顺序（修正版）

```
456 交付 → 457 拆 4 段
  → P0-0 内存泄漏分诊
  → P0-批1 可观测性（磁盘/线程/进程池/原生 gap）
  → P0-批2 依赖一致性
  → P0-批3a 离线兜底
  → P0-批3b 补丁链分诊
  → P0-批4 L0 上限 + deadline
  → P0-批5 资源预算（拆 5a/5b/5c）
  → P1 存储（快照/向量/compaction/fsync/备份）
  → P1 失联四段 + 表达仲裁
  → P1 知识自污染 / 伦理闸门 / 规则行动化 / 轮询一期
  → P2 StateCommitter / RecoveryManager / WAL / 迁移
  → P2 自认知 / 孤儿事件 / L2→L3
  → P3 EventBus / Event Sourcing / 稀疏激活
```

**关键依赖**：

- P0-批5 依赖 P0-批1 的 `ResourceSnapshot`；
- P1 存储依赖 P0 的磁盘压力信号；
- P1 失联四段依赖 `PulseHealthMonitor` 订阅修复；
- P2 StateCommitter 依赖 WAL/迁移设计，不能先改状态再补日志。

---

## 九、结语

v1.0 已经把“该修什么”列得比较全，但还缺三样东西：

1. **缺“最危险的那一个”**——内存泄漏；
2. **缺“只记录不行动”的行动化**——知识自污染、伦理闸门、规则/handler、自认知；
3. **缺“施工治理”**——Owner、重启、回滚、基线、验收命令、迁移、计数对账。

把这三样补进 v1.1，再按“先止血、再降延迟、最后保整体”的顺序施工，这份路线才能既稳又可验收。
