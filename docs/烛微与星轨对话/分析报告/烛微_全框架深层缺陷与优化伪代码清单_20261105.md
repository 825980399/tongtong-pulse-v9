## 一、结论摘要（先看这 10 条）

1. **磁盘 I/O 完全不在自适应回路里**：`InfoField` 的硬件快照只有 CPU/内存/GPU；`_get_load_level()` 没有磁盘参数；`hardware_probe` 只测磁盘容量，不测 IOPS/await/queue。`[NEW]`
2. **三套自适应控制器各算各的**：`parallel_scheduler` 按物理核×1.5、`Hybrid` 按物理核×0.6、`ReasoningWorkerPool` 按全局并行度×0.75，互不知道对方存在；线程预算表 58，实际 Python 活跃约 81。`[NEW/DEEP]`
3. **进程池“有 8+4 个位置，只来了 1 个 worker”**：`ProcessPoolExecutor` 懒生成，`PulseLiver` 提交后立刻 `future.result()`，任务串行；日志“8 个工作进程”是容量，不是实际进程。`[DEEP]`
4. **全量快照可能 768MB 级重写**：`PulseLiver` 每 60 秒调 `snapshot.save()`；变更 >200 节点或距上次全量 6 小时就全量；全量 JSON + L1 快照 + Parquet + `fsync`，没有磁盘预算。`[NEW]`
5. **快照不是跨存储原子的**：JSON、L1、Parquet、`vectors.npz` 各自写、各自替换；崩溃可能留下“节点数对不上/向量与节点不匹配”的半个自我。`[NEW]`
6. **脉冲优先级没有 deadline**：L0 队列无上限，L1 软上限 500，L2/L3 有上限，但 `priority` 只决定入哪个池，不能保证用户对话 24 秒内返回；脉冲风暴/硬件告警还可能自激。`[NEW]`
7. **没有“注意力令牌”**：Cortex 有多个 `MouthEvent.SPEAK` 出口，后台反思/自主表达/对话回复可以同时具备发言条件；没有单一全局工作空间做最终承诺。`[NEW]`
8. **`SelfState` 没有单写者**：身份、记忆、目标、情绪散在 `PulseSnapshot`、`PulseNodePool`、`SelfAwarenessEngine`、`PulseInnerWorld` 等对象里，没有版本化提交；并行车道越多，越容易出现“最后写入者赢”。`[NEW]`
9. **线程/原生线程治理不完整**：141 条 OS 线程、135 条 Wait、1 条 Running；约 60 条原生线程（OpenBLAS/faiss/sklearn/rayon）不受 Python 线程预算约束；`thread_budget.inventory()` 没进 health。`[DEEP]`
10. **依赖/构建有硬冲突**：`requirements.txt` 写 `numpy<2.0`，实际安装与 `requirements.lock` 是 `numpy 2.4.6`；Cython `.pyd` 的 ABI 风险没有 CI 闸。`[NEW]`

## 二、全局资源治理（A 组）

### A1 `[NEW][P0]` 三套自适应控制器没有统一预算，公式互相打架

**证据**

- `nucleus/parallel_scheduler.py:_calc_base_parallelism()`：物理核 ×1.5；16 逻辑/8 物理 ⇒ 基础并行度 12，压力低时可翻倍到 24，最后被逻辑核 16 截断。
- `nucleus/HybridParallelScheduler.py:_calc_target_processes()`：物理核 ×0.6 ⇒ 4 个进程；`_ensure_pools()` 日志“进程池初始化完成: 4个进程”。
- `nucleus/reasoning/ReasoningWorkerPool.py:__init__`：`max_workers = max(2, int(global_parallelism * 0.75))`；日志“推理进程池已启动: 8个工作进程”。
- `utils/thread_budget.py:DEFAULT_CAPS`：所有池上限合计 58；但实测 Python 活跃约 81（141 OS 线程 − 60 原生线程）。
- 三套控制器没有共享 `ResourceSnapshot`，也没有“进程 + 线程 + 原生线程”的统一上限。

**根因**

每个子系统只对自己负责，把“并行度”当成局部旋钮；没有全局资源账本，也没有“进程池与线程池相加不能超过物理核/内存/磁盘预算”的约束。

**影响**

- 负载上来时，一个控制器扩线程、另一个扩进程，第三个扩原生池，互相 oversubscribe；
- 8 物理核上可能同时存在 12 个 cortex 线程、8 个推理进程、4 个 Hybrid 进程、58 个池线程、60 个原生线程；
- 结果是上下文切换、内存带宽争抢、缓存失效，尾延迟反而变差。

**伪代码**

```python
@dataclass(frozen=True)
class ResourceBudget:
    cpu_cores: float
    mem_mb: int
    disk_mbps: float
    disk_iops: int
    gpu_mem_mb: int = 0

class ResourceGovernor:
    def __init__(self, profile: HardwareProfile):
        self.profile = profile
        self.total = self._derive_total_budget(profile)
        self.ledger = BudgetLedger(self.total)

    def request(self, lane: str, want: ResourceBudget,
                priority: int, deadline: float | None) -> Lease | None:
        # 关键：进程/线程/原生线程都从同一账本扣减
        if not self.ledger.can_fit(want):
            if priority >= P0:
                self.ledger.preempt_lower_priority(want)
            else:
                return None
        return self.ledger.acquire(lane, want, deadline)

    def release(self, lease: Lease) -> None:
        self.ledger.release(lease)
```

**验收**

- 任意时刻 `sum(active leases) <= total`；
- 16 逻辑/8 物理机器上，进程 worker + Python 池线程 + 原生线程的“可运行并发”不超过物理核的 1.5 倍；
- 压测时 p95 不退化，上下文切换/秒不高于基线 1.2 倍。

### A2 `[NEW][P0]` 磁盘 I/O 不在自适应回路：只有容量，没有压力

**证据**

- `nucleus/field/InfoField.py:340-350` 的 `_hardware_snapshot` 只有 `cpu_usage / mem_usage / gpu_usage / gpu_memory_usage`，**没有磁盘字段**。
- `InfoField._get_load_level(cpu, mem, gpu, gpu_mem)`（`:1586`）没有磁盘参数。
- `InfoField._check_high_load()`（`:1420+`）只读 CPU/内存/GPU；磁盘不参与 `light/moderate/heavy/critical`。
- `nucleus/hardware_probe.py:_detect_deep_hardware()` 的 `disk` 只有 `total_gb / free_gb / usage_pct`；注释写“磁盘类型”，代码没有类型/IOPS/await。
- `organs/senses/PulseTouch.py` 的硬件快照 `disk` 只有 `usage_percent`；告警阈值 90/95 是**容量百分比**，不是 I/O 压力。
- 全仓 `grep "disk_io_counters|read_bytes|write_bytes|await|iops"`：没有运行时采集点（只有零散 fsync/read_count 业务计数）。

**根因**

硬件抽象层把“磁盘”当“剩余空间”，没有把“磁盘”当“有队列、有延迟、有吞吐上限的资源”。

**影响**

- 快照/Parquet/向量库/日志同时写时，磁盘 await 可能几百毫秒，但自适应仍认为“CPU/内存低，可以扩”；
- 用户对话的检索/读文件被后台 compaction 拖慢，p95 出现尖刺；
- 磁盘满/只读/坏道只能靠异常发现，不能提前降载。

**伪代码**

```python
@dataclass
class DiskPressure:
    read_mbps: float
    write_mbps: float
    read_iops: int
    write_iops: int
    await_ms: float
    queue_depth: float
    free_gb: float
    level: str  # low / medium / high / critical

def sample_disk(prev, cur, dt) -> DiskPressure:
    read_mbps = (cur.read_bytes - prev.read_bytes) / dt / 1e6
    write_mbps = (cur.write_bytes - prev.write_bytes) / dt / 1e6
    read_iops = (cur.read_count - prev.read_count) / dt
    write_iops = (cur.write_count - prev.write_count) / dt
    await_ms = ewma((cur.read_time + cur.write_time) / max(1, cur.read_count + cur.write_count))
    free_gb = shutil.disk_usage(ROOT).free / 1e9
    return DiskPressure(..., level=classify(read_mbps, write_mbps, await_ms, queue_depth, free_gb))
```

接入点：

```python
# InfoField
disk = resource_governor.disk_pressure()
load = _get_load_level(cpu, mem, gpu, gpu_mem, disk)
if disk.level in ("high", "critical"):
    pause_background_writes()      # 只降后台，不降对话
```

**验收**

- health 每秒/每 5 秒有 `disk.read_mbps/write_mbps/await_ms/queue/free_gb`；
- 人为制造 200MB/s 写入时，后台快照/compaction 自动暂停或限速，对话 p95 不超过基线 +10%；
- 磁盘 free <10% 时提前告警，不等到写失败。

### A3 `[NEW][P1]` 硬件探测口径不统一：逻辑核/物理核/总内存/可用内存混用

**证据**

- `hardware_probe.detect_hardware_tier()`：`cores = psutil.cpu_count(logical=True)`，`memory_gb = psutil.virtual_memory().total`；
- `_detect_deep_hardware()`：`physical_cores = psutil.cpu_count(logical=False)`，`mem_available_gb = psutil.virtual_memory().available`；
- `HybridParallelScheduler.__init__`：`_cpu_count = os.cpu_count()`（逻辑核），`_physical_cores` 另算；`_detect_memory_gb()` 用 total；
- `parallel_scheduler._calc_base_parallelism()`：优先 `_physical_cores`，否则逻辑核 ×0.6；
- `InfoField` 用 `cpu_info.get("cores")` 和 `mem_info.get("total_gb")`；
- 没有任何地方读 P/E 核、NUMA、cgroup 限额、thermal、电源计划。

**根因**

硬件探测是“多个局部函数各自读 psutil”，没有一个 `HardwareProfile` 单一事实源。

**影响**

- 同一台机器在不同模块眼里是 8 核/16 核、16GB/47.9GB、可用/总量；
- 容器/cgroup 限额下，`os.cpu_count()` 可能远大于实际可用；
- P/E 核机器上，把重任务放到 E 核，延迟不可预测；
- 没有 thermal，长时间满载降频后线程数不变，吞吐下降。

**伪代码**

```python
@dataclass(frozen=True)
class HardwareProfile:
    logical_cores: int
    physical_cores: int
    p_cores: int
    e_cores: int
    numa_nodes: int
    mem_total_mb: int
    mem_available_mb: int
    cgroup_cpu_quota: float | None
    cgroup_mem_limit_mb: int | None
    disk: DiskProfile
    gpu: GpuProfile
    thermal: ThermalProfile
    sampled_at: float

def get_hardware_profile(force=False) -> HardwareProfile:
    if not force and cache.fresh(ttl=30): return cache.value
    profile = HardwareProfile(...)  # 统一在这里读 psutil / cgroup / nvidia-smi
    cache.set(profile)
    return profile
```

**验收**

- 全仓只有 `HardwareProfile` 读硬件；其他模块只消费；
- 每个读数带 `source/timestamp`；
- cgroup 限额场景下并行度按 quota 而不是 host 核数。

### A4 `[NEW][P1]` 推理进程池 worker 数不看内存，低内存机器有 OOM 风险

**证据**

- `ReasoningWorkerPool.__init__`：只按 `os.cpu_count()` 和 `global_parallelism * 0.75` 算 `_max_workers`，没有读可用内存；
- `HybridParallelScheduler._ensure_pools()`：有 `_memory_gb < 8 => min(2)`、`<16 => min(4)` 的内存保护；
- 两套进程池策略不一致：Hybrid 有内存闸，Reasoning 没有。

**根因**

进程池的“进程数”只按 CPU 算，没有把“每个 worker 的 RSS + spawn 复制成本”纳入预算。

**影响**

- Windows spawn 每个 worker 都会重新导入模块；如果 worker 导入 numpy/faiss/torch，单个进程可能几十到几百 MB；
- 8 个 worker 可能让 RSS 从 6GB 涨到 8GB+，在 16GB 机器上触发换页/OOM；
- 当前实际只生成 1 个 worker，所以问题被“低利用率”掩盖；一旦真正扇出就会暴露。

**伪代码**

```python
def worker_count(profile: HardwareProfile, per_worker_mb: int) -> int:
    cpu_cap = max(1, int(profile.physical_cores * 0.75))
    mem_cap = max(1, (profile.mem_available_mb - RESERVE_MB) // per_worker_mb)
    return min(cpu_cap, mem_cap, MAX_WORKERS)
```

**验收**

- 进程池启动前打印 `worker_count / per_worker_mb / mem_available`；
- 内存 <20% 可用时自动缩到 1–2 个 worker；
- 压测 8 worker 时 RSS 不超过预算，无 swap。

### A5 `[DEEP][P1]` 线程预算表 58，但实际 Python 活跃约 81：预算没有真正约束所有池

**证据**

- `utils/thread_budget.py:DEFAULT_CAPS` 合计 58（l0 1 + l1 6 + l2 6 + l3 4 + adaptive 4 + hybrid_io 8 + ext_op 8 + ext_sched 2 + struct_parallel 6 + cortex_parallel 8 + self_awareness 2 + legs_learn 3）。
- 同文件头注释：“实测活体 `threading.active_count()=89~90`，其中 81 个是 `concurrent.futures` 的线程池 worker”。
- 当前活体：141 OS 线程 − 60 原生线程 ≈ 81 Python 线程。
- `thread_budget.inventory()` 已实现，但没有接进 health/日志；无法知道哪个池超了。

**根因**

`cap()` 只在建池时调用；有些池没有登记/没有走 `cap()`，或者 `ThreadPoolExecutor` 的 worker 数被动态重建绕过预算。

**影响**

- 预算表看起来“已经收敛”，实际线程仍多；
- 线程栈/句柄/上下文切换成本被低估；
- 无法回答“这 81 条线程分别属于谁”。

**伪代码**

```python
def enforce_budget():
    inv = thread_budget.inventory()
    for pool in inv["pools"]:
        if pool["threads"] > pool["cap"]:
            log.warning("pool over budget", pool)
            pool["executor"]._max_workers = pool["cap"]  # 仅重建时生效
    return inv

# health 每 60s
health["thread_budget"] = thread_budget.inventory()
```

**验收**

- health 能看到每个池的 `cap/threads/queue/at_cap`；
- 实际 Python 线程 ≤ 预算表 + 允许的未登记业务线程；
- 超预算池有 WARNING，且能定位到池名。

### A6 `[DEEP][P1]` 原生线程上限只靠环境变量，仍有约 60 条原生线程

**证据**

- `utils/native_thread_caps.py`：默认 `OMP_NUM_THREADS=4`、`RAYON_NUM_THREADS=2`，注释说“限制后 18 条”；
- 当前 `thread_guard` 连续报 `OS线程−Python活跃=60`（基线 53，+7）；
- `requirements.lock` 有 `faiss-cpu 1.15.0`、`numpy 2.4.6`、`sentence-transformers 5.5.1`、`torch 2.6.0`，这些库都可能自建 OpenMP/rayon 池；
- 没有 `threadpoolctl` 运行时限制。

**根因**

环境变量只在库“第一次建池”时生效；有些库在 caps 之前已导入，或者忽略环境变量；没有运行时统一限流。

**影响**

- 60 条原生线程不进入 Python 线程预算，Task Manager 看起来“线程很多”；
- 与 Python 线程/进程池抢物理核，造成 oversubscription；
- 尾延迟不稳定，尤其在 numpy/faiss 批量操作时。

**伪代码**

```python
from threadpoolctl import threadpool_limits

def apply_runtime_caps():
    # 启动时：环境变量（越早越好）
    apply_native_caps()
    # 运行时：对已加载的 BLAS/OpenMP 库统一限流
    return threadpool_limits(limits={
        "blas": 4, "openmp": 4, "mkl": 4,
    })
```

**验收**

- 启动后 60 秒，`psutil.Process().num_threads()` 与 `threading.active_count()` 的差值 ≤15；
- numpy/faiss 批量操作时 CPU 不出现 16 核全满的 OpenMP 池；
- 编码吞吐不下降（线程少反而减少上下文切换）。

### A7 `[DEEP][P1]` 进程池日志“8 个工作进程”是容量，不是实际；只有 1 个 spawn 子进程

**证据**

- 日志：`ReasoningWorkerPool: 推理进程池已启动: 8个工作进程 (CPU=16核, 并行度=11)`；
- 日志：`HybridParallelScheduler: 进程池初始化完成: 4个进程`；
- 活体：只有 `pid=38776` 一个 spawn 子进程，2 条线程、60MB、2.4 小时 CPU 2.59s；
- `ProcessPoolExecutor` 懒生成 worker；当前只有 1 个并发任务。

**根因**

日志把 `max_workers` 当成“已启动进程数”；实际 `ProcessPoolExecutor` 在第一次 `submit` 时才 spawn，且只按并发任务数生成。

**影响**

- 运维误判“进程池已经并行”；
- 看不到“容量 8、实际 1”的差距；
- 进程池利用率无法评估。

**伪代码**

```python
def pool_health(pool):
    procs = list(getattr(pool, "_processes", {}).values())
    return {
        "capacity": pool._max_workers,
        "spawned": len(procs),
        "alive": sum(1 for p in procs if p.is_alive()),
        "pending": pool._pending_work_items.__len__(),
        "completed": pool._completed_futures.__len__(),
    }
```

**验收**

- 日志/health 同时显示 `capacity / spawned / alive / pending`；
- 压测 8 个并发任务时 `spawned` 能到 8；
- 空闲 10 分钟后 `spawned` 回落到 0/1，而不是假装 8。

### A8 `[NEW][P2]` 进程池降级为同步执行时，会在主线程跑 CPU 任务，阻塞脉冲总线

**证据**

- `ReasoningWorkerPool.submit()`：`_degraded_sync` 时调用 `_sync_future()`，在主进程同步执行；
- `ProcessPoolExecutor` broken 后，`_degraded_sync=True`，恢复窗口 300s；
- 调用方（如 `PulseLiver`）会 `.result()` 等待，主线程被占住。

**根因**

“功能可用”优先于“主线程不被阻塞”；没有把降级任务移到独立队列/低优先级线程。

**影响**

- 进程池崩溃后，频率编码/补丁验证在主线程跑，脉冲分发/对话被拖慢；
- 降级状态可能持续 5 分钟，用户感知为“突然卡顿”。

**伪代码**

```python
def submit(self, func_name, *args):
    if self._degraded_sync:
        # 不直接跑；放入低优先级 fallback 队列
        return self._fallback_queue.submit(func_name, *args)
    ...
```

**验收**

- 模拟 `BrokenProcessPool` 后，主线程 p95 不超过基线 +10%；
- fallback 队列有深度/耗时指标；
- 恢复后自动回到进程池。

## 三、磁盘/存储 I/O（B 组）

### B1 `[NEW][P0]` 全量快照可能 768MB 级重写，且没有磁盘预算

**证据**

- `organs/body/PulseLiver.py:1603 / 1725 / 1830`：`if now - _last_snapshot_save_time >= 60: self.snapshot.save()`。
- `nucleus/mnemosyne/PulseSnapshot.py:_save_locked()`：
  - 变更节点 ≤ `SNAPSHOT_INCREMENTAL_MAX_NODES`（200）且距上次全量 <6h ⇒ 增量日志；
  - 否则走 `_m67_full_checkpoint()`（JSON + Parquet）。
- `SNAPSHOT_FULL_SAVE_INTERVAL=21600`（6h），但“变更 >200”会**提前触发全量**。
- `_atomic_write_with_rotation()`：把旧快照 rename 成 `.bak`，流式写新 JSON，`fsync`，`os.replace`；随后 `save_l1()` 再写 L1 快照。
- 实测 `data/knowledge` 约 **1373.2MB**；存在 **768.5MB** 的 `pulse_knowledge_snapshot.json.20261103_064554.bak`。
- 没有“磁盘忙时推迟快照”的闸门；`PulseLiver` 只按时间。

**根因**

快照是“时间驱动 + 变更量驱动”，不是“磁盘压力驱动”；全量 JSON 序列化和 fsync 都在主进程内完成。

**影响**

- 一次全量快照可能造成几百 MB 写入 + fsync，持续数秒到数十秒；

- 大快照期间 Python GIL 被 JSON 序列化占用，所有线程变慢；
- `.bak` 持续累积，磁盘空间被吃掉。

**伪代码**

```python
class SnapshotScheduler:
    def request_save(self, reason: str, force: bool = False):
        if not force and disk_pressure() >= HIGH:
            self.deferred.append(reason)
            return DEFERRED
        if self.changed_count <= INCR_MAX and not force:
            self.wal.append_delta(self.changed_nodes)  # 组提交
        else:
            self._full_checkpoint_async(rate_limit_mbps=20)

    def _full_checkpoint_async(self, rate_limit_mbps):
        # 独立 writer 线程；分块 JSON/Parquet；每块检查磁盘压力
        for chunk in chunks(self.nodes, size=2000):
            if disk_pressure() >= CRITICAL:
                pause_until_low()
            write_chunk(chunk)
        fsync_once()
        write_manifest()
```

**验收**

- 全量快照写入速率受限（如 ≤20MB/s），对话 p95 不退化 >10%；
- 快照期间 `disk.await_ms` 不超过阈值；
- `.bak` 保留数量/总大小有上限；
- 变更 >200 节点时先写 WAL，不立刻全量。

class IoMeter:
    def __init__(self):
        self.prev = psutil.disk_io_counters(perdisk=True)
        self.per_path = defaultdict(Counter)  # 逻辑路径 -> bytes/ops

    def sample(self):
        cur = psutil.disk_io_counters(perdisk=True)
        return {disk: delta(self.prev[disk], cur[disk]) for disk in cur}

    @contextmanager
    def measure(self, path, op):
        t0 = perf_counter()
        yield
        self.per_path[path][op] += 1
        self.per_path[path][op + "_ms"] += (perf_counter() - t0) * 1000
```

### C1 `[NEW][P0]` 脉冲优先级没有 deadline，L0 队列无上限

**证据**

        while running:
            self.state = sample_all()   # 非阻塞/缓存
            sleep(1.0)
```

## 五、数字生命核心与状态一致性（D 组）

### D1 `[NEW][P0]` `SelfState` 没有单写者/版本，身份与记忆可能“最后写入者赢”

**证据**

- `PulseSnapshot` 管节点快照；`PulseNodePool` 管节点增删；`PulseSelfAwareness`/`SelfAwarenessEngine` 管自画像；`PulseInnerWorld` 管推理/对话状态；`PulseLiver` 管记忆巩固。
- 这些对象各自有锁/状态，但没有统一的 `SelfState` 事务/版本号。
- `PulseSnapshot._save_locked()` 保存的是“当时节点列表”，没有与身份/目标/情绪在同一版本提交。

**根因**

“自我”是多个对象的集合，不是单一状态机；并行车道直接改各自状态。

**影响**

- 记忆车道和对话车道同时改节点/身份，可能出现“刚记住又被覆盖”；
- 快照捕获的是某个瞬间的混合状态，不是一致版本；
- 数字生命的“连续性”无法证明。

**伪代码**

```python
class StateCommitter:
    def __init__(self):
        self.version = 0
        self.domains = {name: DomainState() for name in DOMAINS}
        self.lock = RLock()

    def commit(self, domain, delta, base_version):
        with self.lock:
            if base_version != self.domains[domain].version:
                raise Conflict()
            self.domains[domain].apply(delta)
            self.domains[domain].version += 1
            self.version += 1
            self.wal.append(domain, delta, self.version)
```

**验收**

- 每个域只有一个写入口；
- 冲突显式返回，不静默覆盖；
- 快照带 `global_version`，所有域一致。

### E2 `[NEW][P1]` `PulseInnerWorld._model_cache` 是实例级共享 dict，没有锁/请求隔离

class RequestScopedCache:
    def __init__(self):

        self._lock = Lock()

    def get_or_compute(self, key, ttl, fn):

            hit = self._data.get(key)
            if hit and not expired(hit, ttl):
                return hit.value
        value = fn()
        with self._lock:
            self._data[key] = Entry(value, now())
            self._evict()
        return value
