## 一、逐项验收

### 1.1 心跳 livelock —— **对**（并更正我 390 的假设）

**代码逐行**：

- `PulseHeart.py:674-675`（`_m365_watchdog_loop`）：`_iv = current_interval`；**`_nap = max(5.0, _iv / 2.0)`** ⇒ iv=9.5 时 **5.0s**。
- `PulseHeart.py:396-407`（`_schedule_next_beat`）：`with _timer_lock:` → **`self._next_timer.cancel()`** → 新建 `Timer(self.current_interval, self._trigger_heartbeat)` → `start()`。
- `PulseHeart.py:768-783`（`m365_beat_watchdog`）：`gap > 2×_iv`（19s）时调 `_schedule_next_beat()`，并打"已尝试续链"。

**推演**：t0 时 gap 越过 19s → 取消在途 Timer（本来 9.5s 后到期）→ 新建 9.5s 后到期；t0+5s 看门狗再跑，gap 已 >19s → **再次取消那个还没到期的 Timer** → 新建……**每一拍都在到期前被取消**，`_trigger_heartbeat` 永不执行，gap 永远 ≥19s。

**现场吻合**：`beat` 冻在 35、gap 从 702s 单调涨到 2,237s、443 条"已尝试续链"、`_action=rescheduled` 每次成功——与 livelock 完全一致。

**结论**：洞鉴这一条 **对**，而且它解释了"看门狗把链掐死"的悖论。**同时更正我 390 的假设**：我在 390 说"断点在 `if self.info_field is None: return` 的静默早退"——该路径**会重新排链**（每 9.5s 一拍继续），`gap` 不会单调增长；现场是"回调根本没再执行"，所以 **390 的早退假设不能解释 gap 增长，应以 livelock 为准**（390 报告 §二.7 的"次候选"保留，但主因改判）。

## 三、由验收与监测得到的六条判断

1. **心跳 livelock 的修复点不在"早退留痕"，在"救援节拍"**：`_nap` 必须 ≥ 心跳周期（建议 `max(iv*1.5, 15)`），或救援前先判"在途 Timer 是否还活着"（`is_alive()`／`finished` 标志），**不能无条件 cancel 重建**。这是 390 报告 P1 支点的正确形态，比我原先建议的"加 ERROR 留痕"更根本。
2. **洞鉴的 19 孤儿清单需改判**：11 真孤儿可进清理候选；`daily_reader`／`snapshot_index`／`m365_mem_attribution` 是活引用，**照单清理会破功能**。
3. **回灌优化要按本窗口径**：第一大类是"池中无该文件"（48%），不是"同文件多条"（2%）；先解决"池里为什么没有这些文件的问题条目"，再谈歧义消解。
4. **脉冲系统的真实形态是"一根主轴 + 一个万能接收器"**：眼睛 68.8% 发射、血管 26.2% 接收，任何"健康度"指标都必须先剔除这两个极值，否则全是它们的影子。
5. **L0 需要一次"生命线重新定义"**：心跳迁 L3 后，L0 只剩应激与告警；若继续用"L0+L1 占比"衡量生命线健康，读数永远偏低（375/393 两次实测一致）。
6. **16:10–20:00 的 3h50m 空档**是本次监测唯一的"整段无脉冲"窗口，建议与当天的重启/停机记录对齐（本报告只报现象，不断言原因）。
