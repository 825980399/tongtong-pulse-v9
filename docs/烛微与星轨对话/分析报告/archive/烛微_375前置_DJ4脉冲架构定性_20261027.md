## 〇、四句结论

1. **DJ4-01 成立，但「死」有三类不同性质**：`pattern_prewarm`(149)＋`pattern_prediction`(52) 是**已被直调消费的冗余广播**（不是没人消费，是消费不走路由）；`touch.hardware_snapshot`／`energy.metabolism_snapshot` 是**报告即终点/自读缓存**；`heart.alive`／`heart.beat` 是**生命线自我节律**。716 里真正"该接而没人接"的只是少数，需逐条判，**不能一刀切停发**。
2. **DJ4-02 票面证伪**：「生命线被 `_auto_layer` 误判为 L3」不成立——`_infer_layer` 只查 23 条映射表、未命中**返回 L1**，代码上**永远产不出 L3**；L3 全部来自显式 `layer="L3"`。真问题是**三处口径互相打架**：`_DEFAULT_LAYER_MAP[HeartEvent.BEAT]="L0"`／`PulseHeart.py:477` 显式 `"L3"`（v24.0 减负注释）／兜底分支写 `"L0"`；再叠加 30fps 视觉帧显式 L3 ⇒ 占比被单点高频撑起。
3. **DJ4-04 不是对错之争，是两个定义**：716＝「无 target 且无条件命中」（发布侧）；tracer 孤儿＝「无真实投递 **且** 无任何订阅平反 **且** 不在报告白名单」（观测侧，1.5s 窗＋200 条上限）。当前 `pulse_orphans.json` 实际有 200 条（10-24→10-26，L3 152／L2 38／L1 7／L0 3）⇒「自报孤儿=0」只是那个时点那个窗口，不是稳定值。根因一句话：**豁免只做在观测侧，没做在发布侧统计**。
4. **DJ4-05 票面需勘误**：`_build_call_chain` **不是纯 AST**——调用抽取是正则 `self\.(\w+)\(`（`_analyze_method_calls`），只有类/方法索引走 AST；且**只在同文件解析**，跨文件一律 `external: True`、深度 3、`visited` 只按方法名。226 处发布链对它**结构性 0% 可见**（`pulse_core.emit` 本身就在另一个文件）。但「跨文件符号表」成本被高估：`CallGraphAnalyzer` 已在位（384 文件／7598 函数／75919 边，22s 建图），接线即可。

## 二、DJ4-02 · 脉冲分层误判（L0+L1 仅 2.3%）

### 2.1 现象复核

- 票面 2.3%＝(5+231)/10,376＝2.27% ✓；反推 L2≈1,052（10.1%）、L3≈9,088（87.6%）。

### 2.2 抽样（本机孤儿快照 200 条，只读）

| 事实 | 数据 | 含义 |

### 2.3 根因方向（不是阈值，是三处口径不一致）

1. **显式标签而非推断**：L3 全部由发布侧写死（心跳、视觉帧、潜意识 18 处、内在世界 37 处…）。
2. **同一事件三套口径**：映射表说 L0（`PulseCore.py:51`）／生产说 L3（`PulseHeart.py:477`）／兜底说 L0（`:491`）／文档示例还说 L0（`const.py:83`）。任何"按 layer 统计生命线占比"的指标都会失真。
3. **高频单点放大**：视觉帧 30fps 一旦启用即可单独把 L3 拉到 90%+；心跳 ~11s/拍 贡献约 3,400/10.5h。⇒ **占比不是"生命线被误判"的结果，而是"后台高频 + 生命线稀疏"的结构结果**。

### 2.4 施工锚点 / 风险

- 锚点：`nucleus/pulse/PulseCore.py:50-74`（映射表）、`:169`（推断入口）、`:294-301`（`_infer_layer`）；`organs/body/PulseHeart.py:477/491`（心跳双口径）；`hardware/robot_body/robot_body_driver.py:93`（30fps L3）。
- 风险：①把心跳改回 L0 会改变调度语义（L0 单线程独占、不丢弃、`disable_ttl_for_l0_l1`）——v24.0 减负是**有意为之**，不能简单回退，须先定"生命线"到底是 layer 还是 tag；②视觉帧放宽到 L1 会挤占交互层队列（L1 软上限 500）；③指标口径一改，历史基线全部不可比，需同时给"新旧双口径"过渡期。

## 三、DJ4-04 · 孤儿/死信判据冲突

### 3.1 tracer「孤儿」的完整判据（四态，`utils/pulse_tracer.py:398-465`）

1. **只判 emit**，且 `now - ts ≥ PULSE_TRACER_MIN_AGE_SEC`（1.5s）；
2. 有 `route_matched`（268 刀1 发布侧当场打点）⇒ `real_matched > 0` 即平反；`==0` 继续；
3. 无 route_matched ⇒ 用 `matched_organs` **剔除万能器官**（`_UNIVERSAL_ONLY_ORGANS={"血管"}`）后计数，>0 平反；
4. **订阅表平反**（200 刀1）：`_default_bus_sub_provider` 只要存在**任意非观测者订阅 pattern**（含通配，`"**"` 除外）就平反——**不看条件是否命中、不看是否真的投递**；
5. **报告白名单**（204 刀4）：`EnergyEvent.METABOLISM_SNAPSHOT`、`pattern_prewarm`、`pattern_prediction` 直接跳过。

### 3.2 为什么 716 条被判成非孤儿（三条平反路径）

- **路径 4（订阅平反）是最主要的一条**：`heart.*`、`lungs.select_model`、`digest.knowledge` 等都有器官注册了同名条件 ⇒ 即使 `min_priority`/条件表达式让它们**一次都没命中**，tracer 也判"非孤儿"。
- **路径 5** 直接豁免 `pattern_*` 与代谢快照。
- **路径 2/3** 只在 `real_matched>0` 时平反，恰恰与 716 的"零匹配"定义一致——所以差异**不在这一层，而在 4/5 层**。

### 3.3 现状反证

`data/monitor/pulse_orphans.json`：**200 行（上限）**，时间跨 10-24 01:05 → 10-26 17:40，`real_matched_count` 全 0，`route_status`：None 101／unmatched 81／duplicate 9／ok 6／expired 3；层分布 L3 152／L2 38／L1 7／L0 3。⇒「tracer 自报孤儿=0」只对应 01:01:54 那个时点，**不是判据的稳定输出**（环容 1000、1.5s 窗、2s flush 门、200 上限滚动覆盖，任一条件都能让某次快照为 0）。

### 3.4 统一判据建议（往哪靠）

- **以「发布侧 `route_matched.real_matched`」为唯一真源**（268 刀1 已把打点接进 publish 收尾，当场权威、不受环窗/上限影响）；
- **「孤儿」改称「零真实投递」**：`real_matched==0` 即计入，不再用"有订阅"平反；
- **订阅平反降级为「待观察」**（单独一列 `pardon_reason=has_subscription`，不并入孤儿数）；
- **报告白名单保留但显式登记理由**（现已有注释，需加"发布侧统计同步豁免"，否则 716 与 0 永远对不上）。

### 3.5 风险

改判据后孤儿数会**瞬间放大**（视觉帧 30fps × 1.5s 窗可一次刷满 200 条上限）⇒ 必须同时做**按 event_type 聚合 + 采样**，否则 `pulse_orphans.json` 变成噪声文件、tracer 自身成为写盘热点。

## 四、DJ4-05 · 调用链 AST 适配度低

### 4.1 实现与边界（实读，票面需勘误）

| 项 | 事实 | 锚点 |
|---|---|---|
| 调用抽取 | **正则（非 AST）**：先剥注释与字符串，再匹配 `self.方法名(` 与 `cls.方法名(` / `类名.方法名(` 两式 | `nucleus/self_inspector.py:1253-1300` 调 `_analyze_method_calls` |
| 方法索引 | `_parse_classes`（AST）取**本文件**类/方法/行号 | `self_inspector.py` `_parse_classes` |
| 跨文件 | 被调方法在本文件找不到 ⇒ `{"external": True}`，**不解析** | `:1289-1295` |
| 递归边界 | `max_depth=3`、`visited` **只按方法名**（不按 file+name） | `:1256-1268` |
| 起点 | 仅"器官方法说明"生成时调用（`_call_chain`），非全仓图 | `:1541` |

### 4.2 226 处发布链的可见性

- 226＝洞鉴口径（`InfoField.publish` 93＋`PulseCore.emit` 94＋`InsightBoard.post` 39，10-24 HEAD）。
- **本报告独立复算（AST，生产面，attr∈{publish,emit,post}）＝702 处调用点**（publish 300／emit 276／post 126）——与 226 不是同一口径（洞鉴只计三种具名接收者）。取两个口径中的任一个，结论相同：**`_build_call_chain` 对这些发布链 0% 可见**，因为任何发布链跨出的第一跳（`pulse_core.emit`／`info_field.publish`）就在别的文件里，一律被标 `external`。
- 另：即使不跨文件，正则只认 `self.xxx(` 与 `Cls.xxx(`，`obj.method(`、模块级函数、`await`、lambda 内调用全部漏；同文件同名方法还会被 `visited` 误并（与 `self_inspector.py:5043` 已记录的"同名合并 27→541"同型风险）。

### 4.3 两条路线取舍

| 路线 | 成本 | 收益 | 结论 |
|---|---|---|---|
| **甲 · 脉冲语义通道**（`event_type → 订阅条件 → 消费方` 表） | **低**：EventBus `_subs`（123 条件）＋各器官 `get_resonance_conditions()`＋tracer 的 `route_matched` 三处现成，可生成机器可读表 | **高且直接**：脉冲审计要回答的正是"谁发谁收"，语义通道一步到位 | **建议先行** |
| **乙 · 跨文件符号表** | **被高估**：`CallGraphAnalyzer` 已有 384 文件／7598 函数／75919 边缓存（22s 建图，`load_call_graph_cache`／`blast_radius_of` 已在用） | 广（所有调用链），但对"脉冲可见性"是间接收益 | **建议接线复用，不重写** |

### 4.4 施工锚点 / 风险

- 锚点：`self_inspector.py:1253/1289/1541`（链构建）、`nucleus/self_awareness/CallGraphAnalyzer.py`（跨文件图缓存）、`nucleus/events/EventBus.py:_subs`、各器官 `get_resonance_conditions`。
- 风险：①把 `_build_call_chain` 直接改成全量 AST 会撞性能（每次器官说明生成都要解析依赖链）；②接 CallGraphAnalyzer 必须用 **(file, qualname)** 键，否则重蹈同名合并误判；③正则→AST 的替换会改变 `called_methods` 结果集，影响既有知识编织边（非零回归），须单测对照。
