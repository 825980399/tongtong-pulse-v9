## 〇、结论先行（三句话）

1. **`Thread.start()` 死等在 CPython 侧只有一个含义**：`_start_new_thread()` 已成功返回（否则会抛 `RuntimeError`），但新线程**没有执行到 `threading.py:1064 self._started.set()`**。新线程要么**在进入 Python 之前就被进程级初始化挡住**，要么**在 1058–1063 段死亡/阻塞**——两种情况在调用方看来完全同形：永久 `wait()`，无超时、无异常上抛。
2. **本现场最符合的是"新线程引导通道"问题，不是资源上限、不是 GIL 饿死、不是 stdin EOF。** 关键反证：同一进程 **12:46 采样 = 188 线程／2383 句柄时仍正常工作**，19:2x 卡死时反而是 **178 线程**；且首发卡死 **14:38** 早于 stdin EOF **18:48** 4 小时。
3. **CPython 层根因仍未坐实**（仅凭 py-spy 的 Python 栈无法分辨"死在 C 层"还是"卡在 C 层"）。本报告给出**一条可一次判决的取证口径**（OS 线程数 − `threading.active_count()`，配合 ProcDump 原生栈），并给三档方向供 374+ 排面。

### 2.2 逐条对照结论

- **符合**：C3（加载器/`DLL_THREAD_ATTACH`）、C4（CRT 锁遗留）、C5（CPython 运行时锁遗留）、C9（引导期 Python 异常死亡）。
  四者共同形态＝**"新线程进不了 Python，旧线程不受影响"**，与"只挡新建、不挡已存活"的现场完全吻合，也与"8 个不同线程、跨 5 小时陆续失败"的**系统性**吻合。
- **排除**：C1（会抛错，且 188>178）、C2（内存余量充足、无 MemoryError）、C6（旧线程持续取到 GIL）、C7（首发早于 EOF）、C10（未进主循环）。
- **无法判定**：C8（Event 损坏）——8 个对象同时坏的概率极低，保留为背景项。

### 2.3 根因方向排序（1–2 条）

1. **【第一】进程级"每线程初始化"通道被卡死（C3/C4 族）**：Windows 每建一条新线程都要跑一遍已加载 DLL 的 `DLL_THREAD_ATTACH`（持加载器锁）与 CRT 每线程初始化；任一原生组件在这条路径上等一把被别的线程持有的锁，**新线程就永远停在 `LdrpInitialize`**——`_beginthreadex` 已成功、`_started` 永不置位、旧线程完全不受影响、Python 层零异常。与本现场**四项特征全对**（新旧分化／跨小时陆续／无异常／tstate-less）。
2. **【第二】CPython 运行时锁／引导期异常（C5/C9）**：若是 `PyThreadState_New` 的运行时锁被遗留持有，形态与第一同（旧线程不需要建 tstate），但属解释器内部；若属 C9，则线程已死、只在 stderr 留痕。两者都必须在**下一次复现**时用"OS 线程数 vs Python 已注册线程数"＋原生栈一次分开（见 §五）。

> 一句话给星轨：**这条线不是"要不要给线程加超时"的应用题，而是"新线程在进程级初始化就被挡住"的系统题**；应用层能做的只有"尽早发现＋不阻断装配"，根因要靠原生栈判。

## 四、丁④ · 更深修边界建议（只出方向，不动手）

> 前置判断：**根因未坐实时，任何"修 CPython"的动作都不该做**。三档都只解决"发现/规避/兜底"，不宣称治愈。

| 档 | 做法 | 改造成本 | 风险 | 收益 | 白话评估 |
|---|---|---|---|---|---|
| **甲 · 前置自检＋引导滞留观测** | ①**「线程引导滞留数」＝ OS 线程数 − `threading.active_count()`**，随 T-107a 资源采样一起打（常态为少量原生线程，**突增≥1 且持续＝有人卡在引导**）；②线程创建外包一层 `safe_start(name, timeout)`：由**启动期预建的常驻看门狗**判定，超时即 `ERROR boot_stalled` 留痕（★不能用 `Timer` 做超时——`Timer` 自己也要 `Thread.start()`，同样会卡死）；③核心装配点（watcher／心跳看门狗／Timer 族）启动后短窗断言＋留痕 | 低（1 个观测口径＋1 个包装函数，纯观测） | 低（不改线程模型；仅多一条 ERROR 日志） | 中：把"事后 py-spy 才看得出"变成"当场一条 ERROR＋可计数" | **最该先做**。它不解决卡死，但把"每次都要人肉 dump"变成"机器自己喊"，也是判根因的唯一数据来源 |
| **乙 · 引导通道隔离** | 运行期不再"随手新建线程"：①关键线程在装配**最早**阶段一次建好（watchdog／配置 watcher／心跳 Timer 由**预建线程池**驱动，不再 `Timer.start()`）；②业务侧统一走**启动期预热的固定 worker 池**，提交任务而不是建线程；③确实需要新建的（subprocess 读线程等）改为 `select`/异步 IO 或复用池 | 中（触及 Timer 族与线程池接线，多文件） | 中（线程模型改动面广；池化后语义/超时/取消需逐点复核） | **高**：若根因是"每线程初始化锁"，**池化后就不再走这条路径**，等于绕开而不是修 CPython | 与根因无关也**稳赚**：178 线程本身就是风险面。但工作量大，须单批、带回归 |
| **丙 · 维持现状只留痕** | 不加任何装置，靠重启窗恢复；仅在装配段补一条"启动完成"横幅与 PID/线程数快照 | 最低 | 低 | 低：卡死仍不可见、仍要人肉诊断 | 只有在甲被否时才选；**不建议单用**（本轮就是"没留痕所以查了 6 小时"） |

**与 373 刀2 的关系**：刀2「watcher 前移＋启动失败留痕」方向正确但**留痕口径要补两条**——①"启动后 `is_alive()`"对**引导期卡死无效**（`is_alive()` 在 `_started` 未置位时本来就返回 False，且 `start()` 永不返回，根本走不到断言行）；②超时判定必须由**预建看门狗**做，不能在被卡线程内做、也不能用 `Timer`。这两条不写清，刀2 落地后很可能"加了留痕仍然什么都看不到"。

**排面建议（供星轨参考，本报告不排刀）**：甲（观测口径＋safe_start）可并入 373 刀2 或紧随其后；乙单独立刀（触及多器官线程模型，建议在根因有原生栈证据后再启）；丙不单独立。

## 五、边界 · 不确定性 · 重启窗复测清单

### 5.1 未坐实项（逐条认账）

1. **CPython 层阻塞点未坐实**：本报告只能证"没到 1064 行"，不能证"卡在 `take_gil`／`PyThreadState_New`／`LdrpInitialize`／CRT"中的哪一个——四者都需要**原生栈**。
2. **7 个后台线程是否全部停在 `:999`**：报告表里 3 个 subprocess 相关线程的栈末帧是 `_communicate:1612`，与 Timer 族不同；本仓**无 py-spy 原始件落盘**（只在报告里摘录），无法复核全栈。若其中确有停在 `_communicate` 的，说明"子进程管道读取"另有独立阻滞点，与本条混算会误判。
3. **C9（引导期异常死亡）无法用日志证伪**：本仓 stderr 未接入 `pulse.log`，`Exception ignored in thread started by:` 只会出现在控制台（且控制台此时已 EOF）。
4. **时序相邻≠同源**：14:30 内存高压（7.18GB、GC 每 13s 暂停 0.6s）与 14:38 首发卡死相隔 8 分钟，本报告**不主张**内存是触发因素（机器余量充足、无 MemoryError），但也不排除"内存高压导致某原生组件走了异常路径"。
5. **`_start_new_thread` 成功**这一点是从"停在 999"反推的；若 py-spy 的行号归属有偏差（把 994 报成 999），则 C1 需重新评估——概率低但列出。
