### 1.3 五个断点（按因果顺序）

#### A. 审批桥断：28KB 的 `PatchAutoApprover` 从未被实例化

- `nucleus\evolution\PatchAutoApprover.py` 28KB，`class PatchAutoApprover` 有 `classify / scan_pending / apply_patch`，但**全仓没有任何 `PatchAutoApprover()` 或 `get_patch_auto_approver()` 调用点**；唯一被生产使用的外部符号是 `record_evolution_round()`（只做“发现/修复”埋点，`SafeEvolutionExecutor.py:2687`）。
- 即使现在接上，**判据也不可达**：`classify()` 的自动放行要求 `_verified and _confidence=="high" and _risk=="low" and wait>=24h`（`:262-266`）；生产补丁的 `confidence` 分布是 **high 65 / medium 3 / None 19**（history），9 条 pending **9/9 为 None** → 自动放行分支永远进不去。
- 即使强行调用 `scan_pending(apply_approved=True)`，它会**直接改源码**（`:363-388`，只做 `.bak_batch11cd` 备份），绕过 `PatchManager` 的副本验证、回滚、`landed` 标记和闭环回写——这是第二条 apply 路径，不能当生产桥用。
- **stale 阈值与回收阈值互相打架**：`PatchAutoApprover.STALE_DAYS_DEFAULT = 7`（`:53`），`ArchiveRecovery.MAX_AGE_DAYS = 30`（`archive_recovery.py:53`）。回收器把 10.3 天的件捞回来，审批器立刻判 7 天过期——**回收即死**。

#### B. 状态桥断：没有任何东西把 `runtime_verified` 变成 `approved`

- `main.py:4243` 的 `apply_all_pending(only_approved=True)` 只认 `status == "approved"`（`PatchManager.py:5146-5158`）；
- `PulseInnerWorld._check_auto_upgrade` 只统计 `status == "approved"` 或（`auto_apply` 且 `status == "verified"`）（`:13129-13134`）——`runtime_verified` 不在任何“可应用”集合里；
- `save_pending_patch` 的自动审批只对 `source == "local_rule"` 放行，**`source == "llm"` 一律 False**（`PatchManager.py:1364`、`:3191-3192`）。10-14 之后新增的 12 条里，**10 条 `source=llm`**（9 条 pending + 1 条 history）、1 条 `llm_multi_file`、1 条 `o3_open_gate` —— **全部没有自动路径**。

**结论**：系统设计了“LLM 补丁必须人工审批”，但生产里既没有人工审批入口，也没有把 `PatchAutoApprover` 接上——**政策要求人，运行环境没有人**。

**即使把白名单全打开，也只有 0 条能同时过形态+沙箱+牵连。** 白名单不是唯一原因，但它是“第一道把所有件挡在门外”的闸。

#### E. 历史 sink：approved 但失败的补丁被移出 pending，永远不会重试
