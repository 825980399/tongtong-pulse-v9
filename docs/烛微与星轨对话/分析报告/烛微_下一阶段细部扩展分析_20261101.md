## 一 第一组：内存墙（P0-1）五问

### 1.1 "在 28GB 活体上做对象普查必然 MemoryError" —— ❌ 过度概括

**错在哪**：MemoryError 不是 `gc.get_objects()` 造成的，是 `tracemalloc.take_snapshot()` 造成的。

**证据**：

- 报错行是 `[339内存观测] 采样异常（mode=tracemalloc+gc_objects）: MemoryError`，`mode` 里带 `tracemalloc`（`organs\core\PulseMetricsCollector.py:1030`）。
- 同一小时级的 **gc 普查一直在成功**：`data\reports\memory\top_types_20261101_125507.json` → `mode=gc_objects / gc_scanned=65536 / elapsed_sec=14.09`，11:05、12:00、12:55 都有产物。**普查没死，全堆快照死了。**
- 反过来，**已经有一份 13:22 的 tracemalloc 快照落在盘上**：`data\reports\memory\_tm_baseline_pid19428_20261101-131302.snap`，**402.6 MB**。我离线加载它只用了 **6.3 秒**，直接拿到全部分布（见 1.4 与 §六）。

**结论**：不是"必然 MemoryError"，是"**在 28GB 进程里物化 37.5M 条 traceback 才 MemoryError**"。而**离线读快照**这条路根本没被用过一次——观测产物没有消费方（§六 N7）。

### 1.2 "冷启 0/5/10/15 分四点、按 type 分桶 Top20" —— ⚠️ 可行，但现有实现有三个偏差

**已有**：`_m339_memory_probe` 的 gc 分支（`PulseMetricsCollector.py:1013-1028`）就是"按 type 计数 Top20"，预算截断（386刀3）。

**三个偏差**：

| 偏差 | 实测 | 后果 |
|---|---|---|
| 只有 count，没有 bytes | `_gc_types = [{"type","count"}]`（:1022-1027） | 28GB 里"谁是 GB 级"看不出来 |
| 截断点是**最老的 4.8%** | `gc_scanned=65536` / `objects_total=1357641` | 样本全是启动期对象：top20 里 `dict 52128` + `Name/Constant/Attribute/Call/Assign`（AST 节点）——**这是导入与扫描期的对象，不是真凶** |
| 只有绝对值没有差分 | 探针每日 1 次（`M339_MEMORY_PROBE_HOURS=(5,)`） | 看不出"哪一类在涨" |

**更轻量且能直接定性的三条**（都比"四点采样"便宜）：

1. **`pyarrow.total_allocated_bytes()`**：本机 pyarrow 25.0.1（mimalloc），实测 API 可用、零成本。一行就能回答"28GB 里 Arrow/C 占多少"——而 `heap_mb` 的定义恰好把 C 内存算进去了（见 1.5 补充）。
2. **`psutil.Process().memory_maps()`** 按 region 聚合：本机 67 个 region，毫秒级。
3. **复用现成差分**：`_m377_tm_delta` + `_m389_tm_baseline_path` 已经在仓里（377刀4），只是没人拿两份快照对差。

**加一行就能补 bytes**：现有循环里 `_sz[_n] = _sz.get(_n,0) + sys.getsizeof(_o)`，1.36M 对象约 0.5–1s，仍在 2s 预算内。

### 1.6 补：`heap_mb` 不是"Python 堆"（洞鉴 P0-1 的定义误读）

## 三 第三组：并行化路线

### 3.1 "七柱面不是串行的" —— ✅ 对，但"有池"不等于"有效并行"

- `InfoField.py:470-547`：L0=1、L1=`max(4,cpu//2)`、L2=8、L3=`max(2,cpu//4)`、Adaptive 五个独立 `ThreadPoolExecutor`。
- `SelfInspector` 结构化并行 66 个器官文件，今日日志实测 **346–354ms**（多次）。
- `exploration_audit.py:655 run_parallel_audit` 挂在 `PulseCortex._do_audit`。
- **但**：GIL + 路径锁 convoy 会把"并行"退化成"排队"——8171 个线程块里 566 个堵在写盘（1.4）。所以"不是串行"对，"并行有效"不对。

### 3.2 "CPU 4-6% 是因为都在等锁／等 GC" —— ⚠️ 部分对，漏了**等 I/O 与换页**

- 事实面成立：108 线程、L1 500/500、GC 17600 次/37min（7.9/s）、单次暂停 3134ms、栈里写盘堵点成群。
- 但 28GB 时 Windows 已在换页（`memory_pressure: RSS>6144MB`、系统占用 82.8%）。`heap_mb=RSS−image` 里含 Arrow/C 内存，**这部分的等待不进 GC 统计也不进 Python 栈**。
- 准确说法：**CPU 空闲 = 等 GIL + 等路径锁 + 等 fsync + 等换页**，GC 只是其中一项。把它写成"等锁/等 GC"会漏掉最贵的那项（换页）。

### 3.3 四步路线（止血→解耦→背压→扩展）顺序 —— ✅ 大体对，但**三件可并行**

- A1（`StreamMiner` 缩进，≤10 行）与"线程收敛"可同批：它是**独立单点**，不该排在内存后面。
- 第 1 步里的"换诊断方法"与第 2 步"线程收敛"可并行：诊断不改行为。
- **`0xC0000142` 的归因要提到第 2 步之前**：它决定"第 4 步能不能用多进程"。现在把它排到 4.3，等于用结论当前提。
- 其余顺序（不先扩并行）我同意。

### 3.4 "0xC0000142 是 Windows 环境问题，不是并行度问题" —— ⚠️ 方向可能对，证据链不成立

- 实测 `logs\boot_crash.log`：`3221225794` 出现 **544 次**（不是"连续 3 次"），样例是
  `脚本=verify_phase17_1_5.py, returncode=3221225794` —— 是**代码学习器的定期测试子进程**，不是"进化 Payload"。洞鉴把对象也认错了。
- `0xC0000142 = STATUS_DLL_INIT_FAILED`，常见诱因：桌面堆/句柄耗尽、**提交内存（commit charge）不足**、DLL 路径或位数不匹配。当前 2530 句柄、28GB RSS，**不能排除内存/句柄压力**。
- 判定缺一件证据：失败瞬间的 `psutil.virtual_memory()` 与 `Process().num_handles()`。**没有这两个数，"是环境问题"就只是猜测。**
