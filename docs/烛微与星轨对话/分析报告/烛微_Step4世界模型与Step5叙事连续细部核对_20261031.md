### 1.4 hit_rate 怎么算：⚠️ **60s 容差，对 eyes 恒命中**

`StreamMiner._check_prediction_hits(event_type, timestamp, tolerance=60.0)`：

```
if abs(predicted_ts - timestamp) <= tolerance:   # 60s
    命中 +1
```

- **命中率 = hits / predictions**（现 231/253）。
- **eyes.stream_frame 实测 0.5s 一条** ⇒ 任意一条"预测 eyes 下一次"的登记，在 ±60s 内**必然被下一次帧命中** ⇒ **eyes 的预测恒命中，91% 里有多少是这一类的"白送"，必须拆开看**。
- `heart.beat` 实测中位 **13.5s** ⇒ 60s 容差 = ±4.4 个周期，同样过宽。
- 结论：**91.3% 不能当"预测准确率"用**；至少要先改成"分类型容差"（见 §五.3）再报数。

### 1.5 `consume()` 谁驱动：✅ 在跑，但只在有 prewarm/负载时产出

- 调用点：`InfoField.py:3040 _consume = self.stream_miner.consume()`（在"周期模式消费"块内）。
- 开关：`ENABLE_STREAMMINER_CONSUMPTION = True`（已开）。
- 频次：随 `discover_patterns` 后的应用块触发（分钟级），**不是空转**；产出 `prewarm`/`load_forecast`，前者走 `PatternPrewarmConsumer` 直调。

## 三、`heart.beat` 口径：❌ 这条必须改判

| 数据 | 实测（10-28） |
|---|---|
| `type=="emit" and event_type=="heart.beat"` | **5,086 行 / 1 个器官（心脏）** |
| `type=="receive" and event_type=="heart.beat"` | **111,723 行 / 23 个器官**（心脏 4,888、本体感知 4,886、叙事自我 4,886、动机循环 4,884、白细胞 4,882…） |

- 10-29／10-30／10-31 的 emit 侧同样**只有 1 个器官**（2,586／529／363 行）。
- ⇒ 洞鉴说的"24 个发射方、各约 32,100 条"是 **receive 行的接收方**，不是发射方。
- **过滤口径要改**：`type=="emit" and organ=="心脏"`。**只写 `organ=="心脏"` 会把 4,888 条"心脏作为接收方"的行混进心跳序列**。
- **真周期（复算 H-01）**：10-31 心脏节拍 **median 13.5s / mean 13.41s / p90 13.6s**（不是 9.5s；`current_interval` 会随负载自适应）。
- EventTap/订阅转发：本窗 **未见 emit 侧扇出**，扇出只存在于 receive 侧（一条 emit 对应多条 receive），所以"过滤会不会误伤"的答案是——**过滤 emit 侧不会误伤，因为本来就只有一条**。

## 七、施工时最容易踩的 3 个坑

1. **把 receive 行当 emit 行**：`pulse_pairs` 同文件混两种 `type`；10-28 里"心脏"作为**接收方**就有 4,888 行。只按 `organ=="心脏"` 过滤会把它们混进心跳序列，做出一个"周期 0 秒"的假模型。**必须 `type=="emit"`。**
2. **把 60s 容差算出的 91.3% 当预测准确率**：eyes 0.5s 一条、heart 13.5s 一条，60s 窗口下"几乎必中"。拿这个数当基线去调阈值，后面全是假优化。**先分类型容差，再报 hit_rate。**
3. **`violated` 直接进 InsightBoard 就算收工**：InsightBoard 的 `query_count=0`（405 已证），告警写进去等于扔进黑洞。**上线告警前必须先接消费者**（night_digest 摘要或 health_snapshot 字段），否则"世界模型失配"永远没人看见。
