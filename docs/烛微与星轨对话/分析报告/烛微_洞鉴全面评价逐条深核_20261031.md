## 一、P0 五条深核

### 1.1 P0-1 破零第二道（❌ 核心前提错，结论要改写）

**实读 `data/evolution/effect_verify.json`**：

| 指标 | 实测 |
|---|---|
| 结构 | `{version, updated, issues, verdicts}` |
| verdicts | **50 条** |
| patch_id 前缀 | `patc…` **40 条**（生产）、tp1–tp4 4 条（测试）、其余 6 条杂项 |
| 生产 40 条是否在 patch_history | **40/40 全在** |
| 生产 40 条 passed | **True 40**（无 False） |
| `updated` | 1792908650 ≈ **10-25 20:50**（此后无新增） |

**`patch_history` 的字段面**：`effect_verified` 存在——**True 38／False 2／None 47**；另有 `effectiveness`（None 68）、`verification_granularity`（87）、`runtime_verified`（True 80／False 5／None 2）。

**结论改写**：
- 洞鉴说"第二道从未产出、passed=0"——**不对**。第二道**产出过 40 条生产结果**（38 条 `effect_verified=True`），只是：
  ①`patch_history` 没有一个叫 `effect_verify_passed` 的字段（洞鉴按这个名字取数，全 None）；真字段是 `effect_verified`／`effectiveness`；
  ②**47 条没有效果记录**（含 11 条未落地 + 早期补丁）；
  ③**10-25 之后不再更新**——新补丁（10-25～10-31）一条 verdict 都没写。
- **是 bug 还是设计**：是**触发/落库问题**，不是"没上线"。`PatchManager` 的 apply 后验逻辑在（`ENABLE_EVOLUTION_EFFECT_VERIFY=True`），但**近期没有补丁落地**（10-14 后 applied 增量≈0）⇒ 没有触发点；而 10-25 后连 verdict 文件都不再写，需核是否 apply 路径未走到。

**最小施工方案**（约 20-30 行，1 个文件，风险低）：

1. 在 `PatchManager` 的 apply 成功后（`applied=True` 处）**强制调一次** `EvolutionEffectVerifier.verify(...)` 并 `apply_trust_adjustment`——现在这段在 `try/except` 里且只在 `ENABLE_EVOLUTION_EFFECT_VERIFY` 时执行，异常被吞。
2. 给 `patch_history` 补一个**派生字段** `effect_verify_state ∈ {passed, failed, unverifiable, missing}`（由 verdicts 反查，不改既有字段）。
3. `effect_verify.json` 的 `updated` 若超过 24h 未变，在 `health_snapshot` 打一个 `world_model.effect_verify_stale=true`。

**风险**：低。唯一注意——别把"补丁落地"和"效果验证"绑成同步阻塞（验证里有子进程/超时），必须异步或 apply 后置。
