## 一、四个"容易错"的点：逐个查到底

### 1.1 `distilled=0`：不是"分支没走到"，是"走到后两行抛了"

**代码链（唯一路径）**：

```
PulseCortex:1629 / :1756  →  indexer.record_remediation_success(q, a, rule)
  :333  record_remediation_success(1)          # success++
  :336  if not _q or not _a: delegated++ ; return   # 空答案旁路
  :349  self._exp.record(question, "remediation_success", ...)   # ← ①可能抛
  :350  with self._state_lock: self._remediation_count += 1
  :351      self._persist_state()                                 # ← ②可能抛（磁盘）
  :361  record_remediation_distilled(1)        # distilled++
```

**反证（关键）**：`remediation{success 461, delegated 292, distilled 0}`。
- `delegated=292 > 0` ⇒ 走的是同一分支、**`_double_write_enabled` 必然为 True**（该计数只在双写开时自增）。
- `success − delegated = 169` ⇒ **169 次 `q` 与 `a` 都非空**，按代码应执行到 `:361`。
- 结果却是 0 ⇒ **在 `:349` 或 `:351` 抛异常**，被 `PulseCortex:1640` 的 `except … _log_ignored_exception(e)` 吞掉（该 try 覆盖 `_idx.record_remediation_success(...)` 与紧跟的 `_rec_att(1)`）。

**结论**：洞鉴"生产代码里唯一能产生 distilled 的调用点是自我纠错验证通过分支，本窗该分支 0 次出现"——**前半句对、后半句错**。分支应出现 169 次；`distilled=0` 是**异常吞没**或**计数写丢**，属**埋点/异常问题**，不是"系统没有蒸馏行为"。

**两个候选与证伪方法**：
1. `_exp.record()` 抛（`ReasoningExperience.record` 里 `extract_structural_features`/`search` 对特殊字符可能失败）→ 在 `:349` 前后加 `DEBUG before/after` 各一行即可判定。
2. `_persist_state()` 抛（磁盘/锁）→ 把它从 `DEBUG` 升到 `WARNING`，一次复发就能看见。
3. 另需排除"计数器实例分裂"：`get_llm_dependency_metrics()` 是否被不同导入路径实例化两次（`data/metrics/llm_dependency.json` 只有一个文件，但仍需确认写者唯一）。

> 这条如果只修"加埋点"而不修异常，`distilled` 会永远 0——**洞鉴给的 Step1 会建在沙子上**。

### 1.2 经验路由 0 命中：阈值不是 0.75，是 **0.5**；且有四道硬跳过

`_detect_experience_route`（`PulseInnerWorld.py:4189`，优先级 65）：

| 关卡 | 条件 | 后果 |

| ① 复盘独占 | 正则命中"完整复盘/七步认知/多变量推演" | `return None` |
| ② 冲突独占 | 正则命中"矛盾/冲突/信任分调整…" | `return None` |

## 二、六步路线扩展（落到文件/函数）

### Step 0 · 修观测（先做，1 批）

**问题定位**：`SelfAwarenessEngine` 对 5 个分析器串行 + 统一 30s 超时，`call_graph`（110s）必然死。

**具体做法**：
1. **分片**：给 `call_graph` 与 `knowledge_quality` 加"按文件哈希分片"（每片 ≤120 文件），片间并行 2 个、片内串行；`structure_change`/`fake_loops`/`production_consumption` 本身是 AST 扫描，直接按目录分片即可。
2. **缓存**：以 `(file, mtime, size)` 为键缓存分析结果，落 `data/self_awareness/analyzer_cache.json`，TTL 24h；**未变更文件直接复用**（代码库一天变更 <10%，命中率会很高）。
3. **异步**：分析器跑在**独立线程池**（2 worker），结果写 `data/self_awareness/portrait_YYYYMMDD.json`；`get_portrait()` 只读最近一次成功结果 + `stale_seconds` 字段（**不许在请求线程里现算**）。
4. **超时分级**：`call_graph` 120s、`knowledge_quality` 60s、其余 30s（当前一刀切 30s 是根因）。
5. **可观测**：每次分析器运行落一行 `{name, elapsed_ms, shards, cache_hit, ok}` 到 `data/self_awareness/analyzer_runs.jsonl`（按天，保留 30 天）。

**验收**：连续 3 天画像三维**非空**；`analyzer_runs` 里 5 个分析器 `ok=true` 且 `elapsed_ms < 60s`。

### Step 1 · 经验回路（依赖 402 契约）

**具体做法**：
1. **先修 `distilled` 的异常吞没**（§1.1）——否则"回路"没有输入。
2. **阈值实测再定**：在 `_detect_experience_route` 的 `search()` 后打一行 `DEBUG score=…`，跑 3 天，看真实 score 分布；**0.5 是现值**，若分布大量落在 0.4–0.5 才考虑降到 0.45，**不要按 0.75 调**。
3. **放开纯知识拦截**：把 ③ 的 5 个信号改成"仅当本地检索命中 ≥3 条时才跳过"，否则仍走经验匹配——这一条能把"0 命中"直接拉起来。
4. **倒排 + 向量**：`nucleus/semantic/` 已有编码器（`semantic_cache._encode_one`）；倒排用 `PulseNodePool` 的 keywords 字段建（无需新库）。

**验收**：`experience_route` 命中 ≥10 次/天；经验命中后 LLM 调用下降 ≥5%（对比同窗口）。

### Step 2 · 低风险本地接管（D1 代码功能描述）

**具体做法**：
- 复用 `PulseCodeLearner` 已有的"器官职责说明书"生成（AST + docstring），输出格式统一为：
  `{file, qualname, signature, doc_first_line, calls[], side_effects[], confidence}` → `data/code_desc/YYYYMMDD.jsonl`。
- 下游消费者：`_detect_code_question` 与知识检索（现有），**不要再造第四个消费者**。
- 风险：`docstring` 缺失的方法（当前代码里占多数）只能给"签名+调用"，`confidence` 必须如实标 `low`。

### Step 3 · 自监督课程（三个可观测判据）

1. **复发判据**：改动后 24h 内同一 `issue_signature` 不再出现在 audit pool（可查 `data/reports/audit/`）。
2. **效果判据**：补丁落盘后 `effect_verify.verdict.passed` **非 None**（当前 68/87 为 None，先补三态）。
3. **复用判据**：经验命中后 7 天内该问题**不再产生 LLM 调用**（查 `call_recorder` 的 `origin`）。

> 三条都是"可查表＋可回滚"的，不需要新埋点。

### Step 4 · 世界模型（7 类事件＋粒度）

按我 393 的实测分布，建议这 7 类：`eyes.stream_frame`、`heart.beat`、`heart.alive`、`touch.hardware_snapshot`、`energy.metabolism_snapshot`、`spinal.inspection_report`、`digest.knowledge`。
**粒度：下一分钟**（这些事件周期 30s–300s）；**不要预测"下一秒"**——30fps 的帧级预测只有噪声，没有决策价值。

### Step 5 · 叙事连续（S5 门票）

- 落盘：`data/narrative/narrative_YYYYMMDD.jsonl`，**append-only**，每天 **1 条**（不是每事件一条）。
- 三条字段：`headline`（当日最高价值事件，从左表取 top1）、`delta`（与昨日差异：节点数/依赖度/补丁数）、`intent`（明日计划，取 `expectation_ledger` 的第一条）。
- 摘要 3 句＝`headline / delta / intent` 各一句，**模板生成即可**（不需要 LLM；要 LLM 就违背"降依赖"目标）。
- 阶段判定改用"叙事条数 + 连续天数"（现在用 <20/<50 的事件数阈值，重启即归零）。

## 三、四组关系（洞鉴没展开的）

### 3.1 内存问题（RSS 7.8GB / growth 1285MB/min）

**不是旁支，是 Step 0 的直接对手**：5 个分析器超时的根因之一就是内存压力下的 GC/换页；`call_graph` 110s 本身要建 7,714 节点/12,479 边，在 7.8GB 进程里更容易被拖死。
**结论**：内存阈值归一（6144 vs 8192）应与 Step 0 **同批**做；否则修完分片，下一次内存高峰仍会把分析器打回超时。

### 3.2 破零三道闸

**独立但共用数据源**：破零回答"补丁链有没有跑通"，内在模型回答"经验有没有复用"；两者都依赖 `route_matched` / `effect_verify` / audit pool。
**结论**：键统一（dedup_key）应作为**共同前置**；破零不需要等内在模型，但内在模型的 Step 1 需要破零的 `effect_verify` 回填。

### 3.3 19 条契约断裂（402）

**是前置依赖，不是并行项**：契约断裂会让经验检索拿到错字段（例如 `event_type` 与 `payload` 不匹配），Step 1 的"命中"会变成"命中错东西"。
**结论**：402 必须先于 Step 1；Step 0 可以并行。

### 3.4 七层体系 vs 内在模型

**七层是观测面，内在模型是能力面**——两者不是"建完七层就有内在模型"，而是：七层的 **L3（脉冲）/L5（活体）/L7（演化）正是内在模型的三个读数源**。
- 七层不修 ⇒ 内在模型所有"验收读数"不可信（例：L5 的 `health_snapshot` 曾 13.5h 停更，用它判断"活体健康"会得出反向结论）。
- 内在模型不接 ⇒ 七层只是"看得见，改不动"。
**结论**：Step 0 本质上就是七层 L5/L8 的修复；两者应共用一套写面。
