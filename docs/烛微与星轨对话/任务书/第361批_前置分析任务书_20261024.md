## 背景与一句话目标

小林 2026-10-23 在 DeepSeek 开放平台查到 **deepseek-v4-pro 单日 122 次 / 108,733,095 tokens（单次均 89 万 token，全项目级）**，但框架生产代码/日志/账本/运行进程全量静态排查均无 v4-pro 活跃调用点（账本 deepseek 仅 450,129 tokens）。星轨已实测官方模型与三条付费路径，已让路灯 360 批做「三场景统一免费优先 + 出口埋点」。

**本批烛微要回答四件事**：
1. v4-pro 到底从哪来（独立穷尽，含子进程/动态/自我修改/外部工具），以及路灯埋点能不能 100% 抓到；
2. 你（烛微/SCNet 侧）自己有没有用过这把付费 key；
3. 免费渠道总容量够不够曈曈日常消耗，缺口与付费兜底成本是多少；
4. 承接小林「该去的去、该留的留、该增的增」，全框架并行/线程/GIL 三态收口。

## 任务一　DeepSeek 付费出口全链路独立审计（P0，核心）

**1. 全 LLM 出口穷举**
- 对全仓（含 nucleus/、organs/、scripts/、tools/、data/code_backups、tmp/、docker 构建上下文、测试）列出**每一个能到达 `api.deepseek.com` 的代码路径**：
  - 文件:行号、使用的 HTTP 客户端（openai SDK / requests / httpx / 自研 safe_http_json / ssrf_guard）、model 字段从哪来（固定值/配置/默认值/运行时拼接/LLM 生成）、api_key 从哪个环境变量/配置读、是否走渠道记账（CallRecorder/channel_quota_usage）、caller 标识。
- 特别排查**绕过渠道池的可能**：
  - multiprocessing 子进程 / ReasoningWorkerPool 子进程沙箱里是否独立发起请求；
  - 运行时动态 import、importlib 加载、自我修改代码（model_self_updater/进化产物）里是否可能含独立请求；
  - 生成的补丁/脚本被执行后是否会发起请求（含 docker_build_ctx、tmp/p343_root 等施工件遗留）；
  - 是否有 openai 客户端实例直接用 base_url=api.deepseek.com 而不经肺部。

**2. v4-pro 来源定位**
- 89 万 token/次、122 次集中 10-23 白天 10–17 点的特征，最可能是什么任务（全项目代码喂给强模型做架构分析？镜像构建？SCNet Notebook？某次批量补丁生成？）。
- 给出「最可能来源排序 + 每条的证据强度（强/中/弱）+ 如何最终证实」。
- 明确：静态侧若仍无 v4-pro，结论必须落到「靠路灯出口埋点跑一周期实测」，并核验埋点方案是否无盲区。

**3. 埋点方案核验**
- 读路灯 360 批刀0-2 落的埋点（若已施工）：断言埋点是否覆盖任务一第 1 条列出的**每一个出口**；指出覆盖不到的路径（如子进程不经父进程 HTTP 层、第三方库内部 client）。
- 给出「唯一最底层收口点」建议：在哪个模块/函数做包装，才能保证任何来源（含动态代码）的 DeepSeek 请求都被记录。

**证据件**：`tmp/zw361_root/a1_exit_map.json`（出口全表）、`a2_v4pro_hypothesis.json`（来源排序与证据）、`a3_trace_coverage.json`（埋点覆盖逐条 ✓/✗）。

## 任务三　免费渠道容量 vs 曈曈日消耗（P0，算钱）

**1. 七渠道能力清单**（实测或官方文档为准，注明口径与查询日期）：
- 智谱 glm-4.7-flash（永久免费）、glm-4-flash（永久免费）；
- 百炼 qwen-plus、qwen-max（每月各 100 万 token 免费额度确认）；
- 硅基流动 GLM-5.3-Flash（积分体系，每日/总额、是否动态）；
- 魔搭 Qwen2.5-7B-Instruct（动态免费、限流）；
- 腾讯 TokenHub（新用户福利额度、广州/新加坡 key 是否共享额度）；
- 百度千帆 ERNIE-Speed（免费额度、是否需固定模型名）。
- 每个渠道：是否**必须固定模型名**（百炼/硅基/魔搭/千帆/TokenHub 各家是否可默认路由）、并发上限、RPM/TPM、限速响应码（429 表现）、上下文长度、是否支持思考模式、稳定性。

**2. 曈曈真实消耗**
- 从 `data/channel_quota_usage.json`、CallRecorder、pulse.log 统计：日均总 token、按 caller（background_learning / user_dialog / advanced / patch）分的 token 分布、高峰时段、并发请求峰值。
- 给出「免费渠道总容量（日/月） vs 曈曈日均需求」对照表，**明确缺口多少、免费能否覆盖、若只能覆盖 X%，付费兜底日均/月均成本（按 flash/pro 定价分别估算）**。

**3. 场景×渠道推荐映射**
- 给出「后台学习 / 补丁生成 / 用户对话 / 高级推理」各自最适合的免费渠道排序（考虑能力、并发、稳定），以及各渠道额度耗尽后的降级顺序。

**证据件**：`tmp/zw361_root/c1_channel_capacity.json`、`c2_usage.json`、`c3_gap_cost.json`、`c4_scene_mapping.json`。

## 任务四　高级任务免费化的质量门判据（P0，配合 360 刀0-1）

- 评估免费模型（glm-4.7-flash / qwen-plus / qwen-max / GLM-5.3-Flash 等）对 deep_think、代码生成、复杂推理的胜任度（可结合公开能力说明 + 框架已有的补丁成功率/预检通过率历史数据）。
- 设计**「免费先试 → 质量门不过 → 付费兜底」的可判定质量门**：
  - 哪些信号算「免费结果不可用」（空返回、被字段策略截断、补丁预检/完整性门禁失败、def 名不匹配、置信度低于阈值、需重试次数超限等）；
  - 各场景推荐的质量门阈值；
  - 估算「免费试错一次失败再付费」是否反而更费（白跑的免费 token 与延迟），给出是否值得、以及免费档先打哪几个的策略。
- 回答：**统一免费优先后，高级任务/补丁质量会不会明显下降？如何在不花钱的前提下尽量不降质。**

## 任务五　全框架并行 / 线程 / GIL 三态收口（P1，承接小林指令）

小林原话：「根据框架的所有闭环逻辑链路，哪些是应该并行的现在没并行——该去掉的去掉、该保留的保留、该增加的增加。」

- 354 前置给过线程三态表（已漂移 6/15 锚点），本批**按 HEAD 全量重核**：
  1. **该去（无意义/重复/可合并的线程）**：列出仍在空转、重复轮询、无真实负载的线程/定时器，给去法与风险。
  2. **该留（有意义的线程）**：列出必须保留的（如消费循环、看门狗、L1 自愈、安全隔离），给保留理由。
  3. **该增（该并行却串行的闭环链路）**：找出当前在主进程串行、阻塞主循环、本可并行的周期任务，评估「**周期性任务交子进程并行执行，完成后发脉冲通知主进程，主进程按原有数据处理逻辑接入 InfoField 继续处理，结构零破坏**」的可行性（呼应小林既定方案），逐任务给：耗时、是否受 GIL 限制（CPU 密集才受 GIL）、子进程化的输入/输出边界、数据回灌方式（落盘+脉冲还是队列）。
- 明确 GIL 在曈曈各模块的实际影响：哪些是 CPU 密集（SNN 仿真、AST 扫描、代码分析）该用子进程、哪些是 IO 密集（等 LLM、磁盘）用线程即可，避免一刀切去线程。
- 输出三张清单（去/留/增）+ 建议的施工分批，**不直接施工**（属前置评估）。

**证据件**：`tmp/zw361_root/e1_threads_current.json`、`e2_remove.json`、`e3_keep.json`、`e4_add_parallel.json`、`e5_gil_impact.json`。
