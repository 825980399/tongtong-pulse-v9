## 背景
星轨刚和小林讨论了"曈曈脉冲架构往类脑芯片靠拢"的方向，初步提出了6项改造：
1. 脉冲加时间戳+幅度字段
2. 突触权重表（空壳）
3. STDP学习实验模块
4. 器官抽象成类神经元（LIF模型）
5. 定时轮询改成事件驱动
6. 集中式存储改成本地存储

但星轨的分析可能比较片面，需要烛微从代码现状的角度，进行深层的前置分析。

## 分析任务

### §1 现有脉冲系统现状复核
**目标**：全面复核曈曈现在的脉冲系统实现，找出所有和类脑架构不兼容的地方。

**需分析**：
1. **脉冲发射机制**：现在的_emit方法是怎么实现的？有没有时间戳？有没有幅度？
2. **脉冲接收机制**：现在的on_pulse方法是怎么实现的？有没有匹配权重？
3. **脉冲总线**：现在的PulseBus是怎么实现的？是事件类型匹配还是突触权重？
4. **触发机制**：现在的heartbeat定时轮询是怎么实现的？有多少个器官依赖heartbeat？
5. **器官间通信**：现在的器官间通信是怎么实现的？是消息传递还是突触连接？
6. **存储架构**：现在的器官记忆是怎么存储的？是集中式数据库还是本地存储？

### §2 六项改造的代码面影响分析
**目标**：对星轨提出的6项改造，逐项分析代码面影响。

**需分析**：
1. **脉冲加时间戳+幅度字段**：要改哪些文件？多少个点？有没有向后兼容？
2. **突触权重表（空壳）**：要改哪些文件？多少个点？会不会影响现有脉冲传递逻辑？
3. **STDP学习实验模块**：要新建哪些文件？会不会和现有学习机制冲突？
4. **器官抽象成类神经元（LIF模型）**：要改哪些文件？多少个器官？会不会影响现有器官功能？
5. **定时轮询改成事件驱动**：要改哪些文件？多少个heartbeat依赖？会不会影响现有定时任务？
6. **集中式存储改成本地存储**：要改哪些文件？多少个器官？会不会影响现有数据一致性？

### §3 改造的技术难点分析
**目标**：分析六项改造中，哪些是技术难点，需要特别注意。

**需分析**：
1. **向后兼容性**：改造成类脑架构后，会不会影响现有功能？怎么保证向后兼容？
2. **性能影响**：类脑架构会不会影响性能？比如LIF模型的膜电位计算会不会增加CPU开销？
3. **数据一致性**：本地存储会不会影响数据一致性？比如多个器官同时写本地存储会不会冲突？
4. **调试难度**：类脑架构会不会增加调试难度？比如脉冲的时间编码会不会让日志更难读？
5. **测试覆盖**：类脑架构会不会增加测试难度？比如STDP学习的随机性怎么测试？

### §4 改造的优先级建议

**需分析**：

4. **改造顺序**：六项改造的最佳顺序是什么？先做哪个，后做哪个？
