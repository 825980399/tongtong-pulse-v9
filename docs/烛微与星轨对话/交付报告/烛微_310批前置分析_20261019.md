### 维度3 · 实现方案（五段，每段一条硬约束，全部锚在现成件上）
1. **传感＝指纹比对，不做文件系统 watcher**。在既有节拍里对扫描域文件算 `(path, mtime, size, 方法数)` 指纹（扫描域 `config.CALL_GRAPH_SCAN_DIRS`，实测 472 个 .py），与上轮指纹表求差。理由：Windows 无 inotify；且**逐文件即时触发在实测成本上直接破产**——按活体单次重扫 **27.91s** 计，472 个文件全变 ⇒ **≈3.7 小时 CPU**，而当前每日拍总共才 122s。
2. **脉冲＝一条批量聚合事件**，不是 N 条。`Event.CODE_STRUCTURE_CHANGED = "code.structure.changed"`，payload：`{changed_files[], added[], removed[], fingerprint_as_of, prev_graph_file, prev_graph_mtime, criteria_version}`；**落 L3**（低优先级、可丢弃、消费须幂等），**严禁 L1/L0**（会挤掉实时与生命线）。
3. **节流＝复用两条现成范式**：合并窗口（沿用 `pending_flush` 的"距上次 <30s 则延迟"语义）＋ `RESCAN_MIN_INTERVAL_SEC`（沿用 `SAVE_MIN_INTERVAL` 写法）；再加一条**同拍只允许一次重扫**（防止同一拍内多次差集触发多次 27.91s）。
4. **消费者只有一个**：图重扫（开关 `ENABLE_STRUCTURE_RESCAN` 默认 **False**，影子开一窗），重扫后把新 `graph_file/graph_mtime` 回写 309 刀3 的统计 ⇒ "覆盖率动了没有"自动可见，**这正是 309 §6-⑪ 那道选择题的执行器**。
5. **口径纪律**：payload 一律用图节点 `module:qualname`（`_qual_id:197`）与既有 `get_organ_code_structure:2408` 对齐，**不新造文件级健康度指标**（防我连报六窗的"N 套读数"）。

### 维度4 · 成本／收益（含我必须说清的那句"抬不了覆盖率"）
| 项 | 评估（一手依据） |
|---|---|
| 代码成本 | **中低**：1 个事件枚举值＋1 张指纹表＋1 个差集/聚合发布点＋1 个消费者开关；不改分发核心、不动队列上限、不动判据阈值 |
| 运行成本 | 有硬上限（合并窗口＋最小间隔＋同拍一次）；无节流则是 §2-维度3 算出的 3.7 小时级灾难 |
| 收益（可一手支撑） | **新鲜度**：结构一变，覆盖率/待复核数在下一拍就反映，而不是等下一次重启或每日拍；**自动化**：把"图是几点的"变成可审计字段（graph_file/graph_mtime 已就位） |
| **收益上限（重要）** | **抬不了覆盖率**。覆盖率取决于 resolve 率：活体实测 `unresolved_calls ≈ 27,000`、`dynamic_calls 17`；307 补了 event 217／entry 23 条边，覆盖率只从 56.7%→**57.6%**（≈4 条边换 1 个覆盖节点）。⇒ MVP 是"更准的尺子"，不是"更高的分数"；**若星轨要的是覆盖率过 70%（让 dead_code 判死档位生效），MVP 不解决这个问题** |
| 主要风险 | ①重扫频率失控（用 3 道节流）；②与 122s 自认知拍叠加（重扫 27.91s 约占其 23%，建议错开，不放同一拍）；③若把它当"具身自我意识"交付而没有第二个消费者，就成了只有生产者的空脉冲——**验收必须绑定消费者真的跑了一次重扫** |
