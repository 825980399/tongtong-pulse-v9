## 一、烛微的核心优势（请勿在优化中丢失）

| # | 优势 | 说明 |
|---|------|------|
| **1** | **锚点文化** | 每次交付都有明确的锚点（日志行号/文件路径/代码行号）——这是烛微最贵的资产 |
| **2** | **纠偏能力** | 多次纠偏星轨/洞鉴的错误（L2开关、RESONANCE闸状态、观测环挤出等）——三方互检的关键 |
| **3** | **纪律遵守** | 每次都有纪律申报（工具调用次数、写入面、PII、降级项）——零越权 |
| **4** | **分析深度** | 每次都能发现关键问题（五大实锤、一窗七裁、观测面失真等）——只读审计的质量很高 |

## 二、烛微工作流的可优化处（按杠杆排序）

| # | 问题 | 现象 | 优化建议 | 优先级 |
|---|------|------|---------|--------|
| **P0** | **任务接收方式被动** | 每次都是星轨派发任务书，烛微按任务书执行——有没有可能让烛微更主动一些？ | 让烛微定期主动做"全景扫描"（比如每周一次，主动发现问题），而不是只等星轨派发任务 | ⚠⚠ 中等 |
| **P1** | **交付方式单一** | 每次都是交付报告，有没有可能让烛微直接更新总账？ | 让烛微在交付报告的同时，直接在总账中追加一行结论（减少星轨的串行搬运） | ⚠ 较低 |
| **P2** | **分析范围局限** | 每次都是前置分析（施工前），有没有可能让烛微也做一些后置分析（施工后）？ | 让烛微在路灯交付后，也做一次"后置审计"（验证路灯的交付是否符合预期） | ⚠ 较低 |
| **P3** | **与洞鉴的分工模糊** | 烛微和洞鉴的分析范围有重叠（比如观测面失真问题，烛微和洞鉴都分析了） | 明确分工：烛微负责"微观审计"（代码层面的细节），洞鉴负责"宏观审查"（架构层面的方向） | ⚠ 较低 |
| **P4** | **任务书依赖星轨** | 烛微每次都是按星轨派发的任务书执行——有没有可能让烛微自己生成任务书？ | 让烛微在前置分析完成后，直接生成施工任务书（星轨只做拍板，不做编制） | ⚠ 较低 |

## 三、采纳项（P0）

### P0：任务接收方式主动化

**优化建议**：让烛微定期主动做"全景扫描"（比如每周一次，主动发现问题），而不是只等星轨派发任务。

**理由**：烛微的分析深度很深，但目前都是被动等待任务——如果能让烛微主动发现问题，可以更早地发现隐患，减少施工后的返工。

**落地方式**：
1. **定时自动化任务机制**（不确定是否可行）：如果烛微支持定时自动化任务，可以设置每周一次的"全景扫描"任务。
2. **手动触发**（如果定时自动化任务机制不可行）：由用户手动通知烛微进行"全景扫描"（比如每周一早上，用户通知烛微做一次全景扫描）。

**全景扫描的内容**：
1. 全仓grep关键配置开关的当前值（RESONANCE_WEIGHT_MAP_ENABLED / ENABLE_LIF_SHADOW / ENABLE_PULSE_PAIR_DUMP / ENABLE_SEMANTIC_CACHE_L2 / DEBUG_PULSE_TRACE / PULSE_TRACER_EVENT_RING_SIZE / PAIR_FILE_CAP 等）
2. 全仓grep关键代码文件的改动（最近一周内的改动）
3. 全仓grep关键日志文件的异常（ERROR / WARNING 等）
4. 全仓grep关键数据文件的异常（pulse_pairs / pulse_orphans / llm_dependency 等）
