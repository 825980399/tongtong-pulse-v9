## §1 任务1 · N1 望远镜改造前置分析

### 1-1 现状（实测，非叙述）
曲线 4 行，最后一行（10-18 03:01:47）：
```
actual 679.2607 = sim 679.2607 | delta 0.0（旧通道，已判死：checks.delta_legacy_void=true）
sim_mode=prev_snapshot | prev_ts=10-17 03:01 | prev_gap_days=1.0 | prev_source=legacy_mirror
delta_vs_prev=0.0 | delta_vs_prev_void=false | checks.approx_running_state=false
checks.delta_void=true，理由："approx未翻运行态(pulse计数)，delta≡0为代数恒等式，读数按作废处理"
ref 文件：{"ref": 1.0}，18 B，mtime 仍 10-15 03:02（冻结未改写）
```
⇒ 三件事同时成立：①旧的"当日两套同函数"恒等式**已按 263 结论被拆并判死**；②新通道 `delta_vs_prev` 已能给出**真读数**——而它读出来的是 **0.0（她与昨天完全相同）**；③口径仍是**静态近似**（`approx_running_state=false`，264 刀3 键名对齐已入库但**待电**）。

### 1-2 改造方案（洞鉴方案的可行性判定：可行，但不是"一行"）
"昨日 payload 喂 sim"要成立，必须先有昨日的 payload 与昨日的结构。建议**三刀，缺一不可**：
1. **落 payload 快照**：`run_once` 写曲线时同写 `data/self_awareness/lfi_activity_snapshot_YYYYMMDD.json`（`{ts, activity: raw, node_names, struct_hash}`；`struct_hash` 取 `compute_lfi` 的 nodes 名集合与邻接摘要），**上限 2 份滚动**（防新档案堆积，遵 276 教训）；
2. **sim 吃昨日 payload**：`sim_overall = _overall_score(compute_lfi(昨日activity), activity_override=昨日activity归一, ref=昨日的 cur_max)`；`actual` 仍用当日 ⇒ **这才是反事实预报**（"按昨天认识的她，今天会得几分"）；
3. **delta 必须拆两列**（否则不可解释）：`delta_activity_only`（固定结构、只换活跃度）＋`delta_structure_only`（固定活跃度、只换结构）＋总 `delta_vs_prev`。理由：`payload_raw` 与 `payload_norm` 的 nodes 来自事件图谱、结构本身天天在变，**两个变量同时动，单一 delta 无法归因**——这与 247 N1"delta≡0 被误读成仿得准"是同一类错（只是这次方向相反）。
- **前置（硬）**：`approx_running_state` 未翻 true 之前，新 delta 一律带 `delta_caveat="static_caliber"`——因为昨日的 payload 也只是"昨日的方法数"，喂进去得到的是**代码规模预报**，不是运行态的自我预报。⇒ 这一条与 274 §7、275 甲′ 同链：**先让观测口径活起来，再改望远镜。**

### 1-3 改造影响：delta 还会恒真吗
不会。恒真来自 `norm = raw/cur_max ⇒ norm_max≡1.0` 且 `ref` 冻结在 1.0（263 已证、264 已加 `delta_legacy_void` 判死）。payload 版把 sim 的**输入换成昨日数据**，两套不再是同一时刻的两种归一，**恒等结构从根上不成立** ⇒ `delta` 会有非零值。
⚠ 但要说清：现在 `delta_vs_prev=0.0` **不是**恒等式，是**真零变化**——望远镜已经是好的，只是她这两天确实没变。所以本刀的目的不是"让数动起来"，是"**让数可以解释**"（结构项/活跃项拆开）。

### 1-4 改造风险（书列两条，本窗各给结论）
| 风险 | 判定 | 处置 |
|---|---|---|
| 昨日 payload 格式不对 | **真实风险**：跨日字段可能因 264/268 改动而增删（本仓 3 天内 lfi 信封字段就加了 5 键） | 快照带 `schema_version`；不匹配 ⇒ `delta=null`＋`reason="payload格式断代"`，**严禁回落 0.0**（259/263 教训：冷启动写 0 会被读成"仿得准"） |
| 昨日 payload 过期 | 不成立为风险，但**缺口成立**：进程未跑 ⇒ 昨日无快照 | `prev_gap_days>2` ⇒ 作废（乙案硬约束已有同型先例，沿用） |
| （本窗补第三条）再造一个壳 | **真实风险**：`delta_vs_prev`（分数级）与 payload 级并存，两把尺会被混读 | 两列**必须同写**且命名分层；看板只认 `delta_activity_only`；旧 `delta` 保持判死不再消费 |

**明晨可验的两条预言**：①第 5 行 `prev_source` 应从 `legacy_mirror` 变 `telescope`（若仍 `legacy_mirror` ⇒ `_load_prev_row` 对 `sim_mode` 的读取断了）；②`delta_vs_prev` 若连续第二日 =0.0 ⇒ 跨两日零变化成立，届时应把话题从"望远镜"转到"喂料"（主题2.1 的 `distilled=0` 才是上游）。

### 2-2 开闸会发生什么（按代价排序）
1. 六条 `record_*` 开始写内存（有界 200 ⇒ **内存不是问题**）；
2. **`InfoField._record_phase18_l3:2121—2133` 开闸后才真正做事**：每次 L3 背压记录要 `sorted(self._l3_producer_counts.items(), key=…, reverse=True)[:5]` —— **对整个生产计数字典做一次全排序**（器官/类计数量级为百），并抢采集器全局锁；
3. `PatchAutoApprover:468—479` 每轮裁决额外 `record_evolution(approval_rate, pending_count, by_decision)` —— 低频，可忽略。

### 2-3 开闸风险与观测窗大小（给可执行的量法，不靠估）
- **风险主体＝锁与排序**，不是容量。现成对表指标（无需新埋点）：InfoField 的 **PHASE13 按锁名分桶** `lock_wait_by_name`（含 `publish.step7_stats`）＋ `runtime_metrics.record_pulse(duration_ms, lock_wait_ms, queue_depth)`（`:838—845` 实测在档）。
- **观测窗**：取**两个 03:00 之间的一整程**（覆盖 DailyScheduler/睡眠审计各拍），比较 `publish` 路径 `lock_wait_ms` 的 **p50/p95** 与 `duration_ms`：判据建议 **p95 增量 < 10%**；若超 ⇒ 关闸并改为"只开低频组"。
- **分档开闸（本批最重要的建议）**：现在只有**一个总布尔**，冷热路径一起开。建议加 `PHASE18_SIGNAL_GROUPS`（如 `"evolution,reasoning,strategy,knowledge"` 白名单），把 **L3 背压（热路）留到最后开**，先开低频的四类 ⇒ 这样"开闸成本=一个布尔值"才对成立，且失败时回退面最小。
- **先接消费方再翻闸**：最小消费方＝把 `snapshot()` 的四类结果并入 277 刚落地的 `daily_reader`（已有晨读结构 `read_daily_context`），日报加一节 `【PHASE18信号】`＋一行 INFO。⇒ 否则开的是"只写不读"，且零消费方告警会立刻成为新噪音（276 §0-3 同病：**别再造一份没人读的档案**）。

### 2-4 结论
**不建议现在直接翻布尔**。正确顺序：**注册消费方 → 低频四组开 → 跑一程对表锁等待 p95 → 再开 L3 热组**。成本从"一个布尔值"更正为"**一个消费方＋一个分档键＋一程对表**"，且全部是零语义变更的观测面改动。

### 3-2 升级方案（四步，前两步是后两步的前置）
1. **先落盘再谈消费**：每日 03:00 拍把图谱写 `data/graphs/event_graph.json`（含 `schema_version`、`struct_hash`、`generated_at`、`edge_count`），**滚动保留 7 份**；运行时消费者（含新加的检索扩展）**只读缓存文件，绝不调 `export_event_graph()`**——否则等于每次检索扫全仓（这是当前 `self_inspector` 路径已存在的隐患，顺手也该改成读缓存）。
2. **给 `retrieve` 加邻接位（向后兼容）**：`retrieve(..., expand_adjacent=False, adjacency_limit=None)`，默认关；影子期由 `ENABLE_GRAPH_ADJACENCY=False` 总闸包着（照 `retriever_enabled()` 同款写法）。
3. **一跳、限幅、分列返回**：只扩 1 跳；邻居候选 ≤ `top_k//2`；返回结构分 `direct` 与 `adjacent` **两列各带来源与图谱边权重，绝不混合重排序** ⇒ 由注入侧决定权重。理由：通信边的邻居是"她会跟谁说话"，不是"哪个知识更相关"，混排必伤精度。
4. **验收＝影子对比**（196/259 方法论）：同一批 query 跑两遍（关/开），比 **top-k 命中率、打分分布、注入长度**；判据建议"命中率不降 ∧ 平均注入字符数增量 ≤ 30%"才允许转实弹。

### 3-3 升级影响：她会知道什么
`retrieve_self_knowledge()` 从"我知道 A 方法是什么"升级为"A 出问题会牵连谁、谁会因 A 沉默而收不到东西"（`blast_radius` 已经在算这个数，只是没进对话注入路）⇒ 这是**同一份数据的第二个消费者**，成本几乎为零，而它正是"自我理解 + 图谱"第一次接上行为。
