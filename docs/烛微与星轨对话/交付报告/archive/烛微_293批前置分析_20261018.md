## §0 三条最硬（第一条直接替书回答问题）

1. **不是 LLM 弱，是协议与它的输出习惯冲突，而且应用语义是纯文本替换。** 实测 40 条 rejected 的补丁形态：
   **`original_code`＝片段 且 `modified_code`＝完整 def ⇒ 29/40（72.5%）**；`片段→片段` 10、`完整→完整` 1。
   应用侧 `nucleus/reasoning/PatchManager.py:246` 写得很明白：`modified_full = full_content.replace(original_code, modified_code)`——**原位整段替换**。把"片段"换成"一个完整的 `def`" ⇒ 在原方法体内**再嵌一个 def** ⇒ 语法完全合法（Python 允许函数内定义函数）⇒ 行为已被改写，但**没有任何一道关会报错**。
2. **能拦这件事的两道防御关，仓内早就造好了——但默认关着。** `PatchManager.py:229—262`（第92批 T-92c/T-92d 原文）：
   `_M92_BASE_INDENT_GUARD_DEFAULT = False`、`_M92_AST_STRUCT_GUARD_DEFAULT = False`，且注释把本病一字不差写明：「**原位整段替换，对缩进一字不改 ⇒ base 不一致时替换结果仍是合法 Python（`ast.parse`／`compile`／`py_compile`／`import` 全部放行），却会把类体/函数体提前终止**」，并说明默认关闭的理由是"任务书要求防御性校验先观察一批"。
   ⇒ **"质量一直不高"的制度性答案**：第92批之后这批补丁从未被这两道关筛过——**不是缺能力，是能力没被允许上岗**（"观察一批"从未结束）。
3. **现有拦截判据拦的是另一类病。** `:1094—1100`（284 刀5）的作废判据是 **`def名 != method` 或 `modified_code` 无 def**（我 279/281 报的那 23 条错配＋6 条无 def＝29 条）——而 72.5% 的真缺陷是"**片段→完整**"形态，这类补丁的 def 名往往**正好与 method 一致** ⇒ 判据与缺陷**正交错配**，所以拦不住。
   ⇒ 一条零成本补判据（本窗实测有效）：`original 不以 def 开头 且 modified 以 def 开头 ⇒ 拒绝入队`，**可拦 29/40**，与"def 名错配"完全正交，两者并用以覆盖绝大部分。
