2. **拦路的不推断、而是"被调函数没写返回注解"——而这恰是一个可量化的双口径陷阱**：本窗实测 返回值注解 **按 def 计数覆盖率 74.8%**（6,846 个 def 中 5,123 带 `->`），但**按调用点加权只有 23.8%**（1,681/(1,681+5,373)）。⇒ **321 刀6 无论报哪个口径，验收都必须写"按调用点加权"**，否则"74.8%"会让人以为路线②躺着就能吃下大半（这是我给 322 的第一条钉死项）。⇒ 顺推的下一步动作不是写更聪明的传播器，而是**"高热未注解函数"补注解战役**：5,373 个调用点集中挂在少数被反复调用的工厂函数上（可先按"调用点数×无注解"排序出前 50 个函数补注解，收益最大、风险最低）。⚠ 但**补注解＝改代码**，写错注解会造**假边**且比误建边更隐蔽 ⇒ 建议：**只生成清单、分批人工改，不允许自动写注解**（需星轨确认，§6-②）。
3. **【本窗最有价值的一条设计缺陷】判死的"活着"集不分边的种类 ⇒ 推断边会静默赦免死代码。** 一手：`self_inspector.py:4952` `_in_edge_ids = {e["callee"] for e in edges}`（**不带 kind 过滤**），`:5172` 判据用 `if any(_i in _in_edge_ids for _i in _ids)`，`:5106` 覆盖率也用同一集合。⇒ 320/321 一旦把 `unique_name`／`self_attr`／未来的 `typed_infer` 边落进图，它们**立刻成为"这个方法有人调用"的证据**，同时把覆盖率推高（看起来像"图更全"）——**误建的边会让死代码永久免死，且没有任何告警**。⇒ 建议按自证强度分三层，并**只让第一层进"活着"集**：
   - **硬赦免**（自证）：`static`、`event`（订阅对）、`entry`（注册入口）；
   - **软赦免**（有字面依据但是按名匹配）：`byname`、`self_attr`、`unique_name` ⇒ 只能把条目**降级为"待复核"，不得判"活"**；
   - **不入赦免集**（纯推断）：`typed_infer` ⇒ 仅作解释/候选说明。
   ⇒ 验收：同一份图按三层分别重算"覆盖率／判死候选"，**必须报三行数**（否则单行数字不可比，这是我逐窗都在防的"一个数字两把尺子"）。
4. **开闸预演结论：322/323 不会开闸，但消费面已经能接——且别拿 SC-2 当蒸馏防护**（它已被 320 证明在规则侧恒等零信息）。一手：解析率路线①＋②全落地 ≈ 42.5%＋1.7~4.6pp ⇒ **< 50%** ⇒ 判死档 X=50% **不触发**；三道闸代码就位（`consume_dead_code_verdicts` `self_inspector.py:5556`；`dump_per_item_by_version` `:5579`，路径 `data/reports/code_review/by_version/<criteria_version>/run_<ts>.json`，每版本 3 份＋全量滚动 7 份，内容已相对化），319 实测"候选 6 ⇒ 入池 ≤1、全带 `requires_confirmation`"。⇒ 第二道闸 SC-2（`CallGraphAnalyzer.py:1717 sc2_regression_selfcheck`，留痕 `:1732`）被 320 刀4 明确判定**语义不等价、不挂 hub**（`apply_rules` 30 行不碰源码不改 AST ⇒ 挂了恒等通过），覆盖范围只有补丁侧（`patch_execution_dispatch._sc2_probe`，dispatch 后 600s 节流）。⇒ **"误报污染蒸馏"这件事目前没有闸**，只能靠 §0-3 的 kind 分层＋SC-3 对表兜（§3-维度3）。
