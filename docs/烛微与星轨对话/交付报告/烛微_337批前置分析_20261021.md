### 1.3 落盘＋索引＋懒加载契约（设计，含与既有护栏的边界）

1. **索引持久化（新增，缺口项）**：`<snapshot>.index.json` ＝ `node_id → (start,end)` ＋ 头字段 `{snapshot_checksum(=现成 node_list_checksum，实测 7a7c92ade8173211), file_size, mtime, code_version, criteria_version, node_count}`。开视图时**先校验和**：匹配 ⇒ 直接读索引（省一次全扫）；不匹配 ⇒ 重扫（实测 1.1s，可接受）并回写索引。**禁止**用"文件路径相同"当校验。
2. **及时落盘（改为增量为主）**：主存动作＝"追加 `snapshot_incremental.jsonl` ＋ 更新索引"；**全量重写降级为定期 compaction**（沿用仓内既有纪律：**先 compaction 后 lazy/驱逐**，避免"边合并边碎写"——`PulseNodePool:280` 原文）。磁盘预算：当前 3 份全量 ≈2GB，compaction 后应稳定在 **1 份主档＋1 份滚动备份**（受 `KNOWLEDGE_BACKUP_KEEP` 管）。
3. **原子写**：`.tmp` ＋ `os.replace`（该 idiom 全仓已 439 处命中，属现成规矩）；Windows 下 **mmap 必须先 `close()` 才能替换/删除文件**（`lazy_snapshot._close_mm` 已注明该坑），故落盘口与视图持有必须互斥（建议：写前 `view.close()` 或写"影子副本"再替换）。
4. **幂等**：以 `node_list_checksum` 为幂等键，重复落盘不新增段、不换索引；备份份数口径**三处必须统一**（config=2／代码默认=3／注释=3）。
5. **重启后重建路径**：索引缺失或校验失败 ⇒ 重扫；重扫期间判据一律走"**不判**"语义（沿用 330刀2 的 `graph_version_ok=False`/`ok=False` 拒绝路径），**不得填 0**。
6. **与既有护栏不冲突的边界**：`COLD_POOL_SHRINK_PERCENTILE=0.20`/`BATCH_MAX=1000`/`ENABLE_COLD_POOL_PERCENTILE_SHRINK=True`、`SEMANTIC_CACHE_*`、`PULSE_TRACER_*`、`EVENT_TAP_*`、`CODE_LEARNING_MEMORY_EXPIRY_DAYS=7` —— 新释放逻辑**只能在这些既有上界之下再加一档"更保守"**，不得提高任何上界；且需解释现成疑点：`PulseNodePool:2517` 注释自陈 **"cold.index.json 5530 条 4 天 0 驱逐 0 召回（12 次启动恒）"** ⇒ 分层驱逐此前**实测不动作**，337 施工必须先把这条链跑响再谈新增释放面。

```
G2 L ≤ heap < H1（H1=2.0GB） ⇒ 软释放：
      · 语义缓存过 TTL 条目落盘并驱逐；shadow deque 截断到上界
      · 懒加载视图 max_cache 回落到**固定上限**（≤2000），**禁止抬全量**
      · 观测类样本缓冲按 maxlen 截断
G3 H1 ≤ heap < H2（H2=3.5GB）⇒ 冷化（分级写盘＋留索引）：warm→cold，每批 ≤1000（沿用 BATCH_MAX），批间 ≥1 个采样周期
      · 每次冷化必须可回载，并打 `[337内存] 冷化 类=X 条=Y 回载=可用`（不静默）
G4 heap ≥ H2 或 连续 2 轮释放后 heap 回落 <10% ⇒ **只告警、不重启**（小林已裁不做重启泄压；
      `ENABLE_MEMORY_AUTO_RESTART` 保持 False），并把读数交 W1/日报/压测基线

防误杀热数据（四条同时成立才可释放）：
   ① 最近访问时间 > N 拍（现成 last_access 字段：冷池驱逐已用分位数口径）
   ② 引用计数为 0 ∧ 不在"在途表"（pending_patches / 分诊 selected / hub 未消费条目）
   ③ 不在白名单：人格内核、宪法 v26 条款、current_user、心跳状态、索引本体
   ④ 该数据类有可回载路径（索引在 ∧ 文件在）——无回载路径 ⇒ 一律不释放
```

**与吸收回路不打乱**：释放动作**不得进入 `absorb` 的 delivered/categorized/applied 计数链**，也不得让 `[326刀5][absorb]` 的 `applied` 因缓存丢失而归零（331刀1 的证据链正在用这个数）。**观测要求**：`memory_pressure` 增加 `heap_mb`/`image_mb` 两字段（现只有 RSS 总量，无法归因），并由 W1 心跳消费——这正好补上 §0-5 的死链（`check_memory_alarm_detailed` 无调用方）。

### 1.5 风险面与验收线

**风险面（不停框架的热操作约束）**
1. **释放≠归还**：我实测 `del + gc.collect()` 后 **RSS 不回落**（17.5→17.5MB；private 505MB 也不降）⇒ **Windows/CPython 的 arena 归还有迟滞**。验收线若只看 RSS 回落会**误判"治理无效"**⇒ 必须用 ①`heap=RSS−image` ②`memory_full_info().private` ③峰值曲线 三件一起看。
2. **别在释放路径里 import 新模块**——每 import 一个大库就多一块**永久镜像**（3.7GB 教训），这是"越治越大"的真实路径。
3. **懒导入改造的风险**：把 torch/cv2 改首次使用时导入，会把卡顿从启动移到运行中（图/向量首次调用时），**压测圈次内不可接受** ⇒ 若要动，只能在压测后单独立项，且先解决"哪条链真的需要 GPU 栈"。
4. **驱逐链此前不动作**（cold.index.json 4 天 0 驱逐 0 召回）⇒ 新机制上线前必须先证明旧机制能转，否则"治理"是纸面的。
5. **磁盘 I/O 与内存无关但会挤占**：3.1h 内 `io_write 3131MB`（启动全量重写 648MB×2 份是主因）；改增量后这项应显著下降，可作为副验收。

**12GB 判定线支撑性（压测判定线第八项，335刀7）**
- 现状（未治理）：期末预测 7.9GB（稳态）~10.2GB（高危口径），**判定线可用但余量薄**。
- 治理后（撤 max_cache 全量抬升＋冷化生效，堆余额压到 ≤1.0GB）：期末预测 ≈**5.3~6.4GB** ⇒ 余量 5.6GB+，判定线**由"勉强过"变"稳定过"**。
- 建议判据写法：**"期末 RSS<12GB" ∧ "heap(RSS−image) 单日峰值 <2.0GB"** 两条并列——只写 RSS 会把"少装一个库"的架构收益与"治理有效"混为一谈。

**验收线建议（可测、不填 0）**
① `heap` 单日峰值 ≤ 2.0GB（现 1.68GB）② 启动行必须出现"**冷节点落磁盘按需召回 >0**"或"进内存数 < 全量数"（现 13044/0 ⇒ 判未生效）③ `max_cache` 抬升至全量的次数 = 0 ④ 回载命中率 ≥95%（低于即误杀证据）⑤ 同节点 30min 内"释放-回载"≥3 次 ⇒ 判抖动，该类停止释放 ⑥ `data/knowledge` 目录总量不增（现 2526MB/3 份）⑦ 释放/冷化 100% 有日志留痕（无静默）⑧ 治理前后各留一条 RSS 曲线，**禁止用重启后的低值冒充治理效果**（跨代次禁拼接）。
