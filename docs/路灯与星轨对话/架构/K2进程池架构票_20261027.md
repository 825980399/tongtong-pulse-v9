## 一、375 刀2 立项结论（本节为 2026-10-27 追加）

**结论：票立项维持，但明确「不新建进程池」——不进入施工排期。**

三条不施工理由，全部来自本仓实测而非估算：

1. **第一次跑就是净亏。** Windows 只有 `spawn` 没有 `fork` COW，`self_inspector` 的
   模块级缓存无法跨进程继承 ⇒ 每个 worker 各付一次 7.95s 预热。
   `3 workers × 7.95s = 23.9s > 串行总耗时 20.21s`。
   在「整仓预热 + spawn」组合下，进程池首跑比现状更慢，不是更快。
2. **收益上限被 I/O 占比压死。** 649 条任务单条均值 31ms，其中相当一部分是文件读取与
   页缓存命中，真正可并行的 CPU 只有 `ast.parse` + `_m325_probe_reachable`。
   若可并行 CPU 只占 10ms，3 进程序理论上限约 `649 × (31-10+10/3) ms ≈ 15.8s`（降 ~22%），
   不是理想中的 3×。
3. **吞吐已经不再卡任何人。** 342 刀3 起 `verdict` 由安全面
   （`verdict_fp_equal` ∧ `output_equal`）一票否决，吞吐降为报告字段；
   375 刀1 又把生产面纯 CPU 负载的通过线改成「并发不劣化 + 调度开销可忽略」。
   ⇒ 进程池本来要解决的那个问题（吞吐不达标）已经不存在了。

**翻案（复启）条件**——只有下面任一条成立才重新评估：

- 出现**真 I/O 型**批任务（不是 AST 扫描这类纯 CPU 负载）；或
- 微基准量出「可并行 CPU 占比 ≥ 20%」**且**预热成本能靠「按片预热/索引持久化」压到亚秒级。

**本刀不做的事**：不改任何运行时代码，不建池，不预留开关，不动 `submit_cpu_bound` 的路由。

## 一、为什么线程池到不了两位数

本负载是**纯 CPU Python**：`_live_work` 做三件事 —— 读源文件、`ast.parse`、调
`self_inspector._m325_probe_reachable` 做图外四类 probe。三件全在 GIL 下，
`ThreadPoolExecutor` 只换了调度，没换执行权。

实测两个数互相印证：合成负载 0.66%、真实 per-item 3.68%，**同一量级**，
都在噪声带里（`throughput_band=gil_noise` 的界就是 |drop| < 5%）。
340B 的 `verdict=FAIL_throughput` 不是"代码变差"，是"并行模型选错"。

改成进程池是**唯一能真正吃掉 GIL**的路（换解释器/换语言不在讨论范围）。

## 二、可行性评估

### 2.1 单任务粒度：31 ms 够不够

进程池的固定开销在每次任务派发：pickle 参数 → 管道写 → 子进程 unpickle →
执行 → pickle 结果 → 管道读 → 父进程 unpickle。本机量级 **0.3 ~ 1.5 ms**（粗估，
需微基准确认）。相对 31 ms 的任务体，占比 **1% ~ 5%** —— 粒度**不构成否决项**。

但注意一个反向事实：这 31 ms 里有相当一部分是**文件读取与页缓存命中**，
不是纯计算。真正可并行的 CPU 才是 `ast.parse` + probe。若这部分只占 10 ms，
3 进程的理论上限是 `649 × (31-10+10/3) ms ≈ 15.8 s`，即**降 ~22%**，
不是理想中的 3×。**先做微基准把这 10 ms 量出来，是这票的第一个前置动作。**

### 2.2 ★真正的拦路虎：预热成本无法跨进程继承

`warmup_live` 一次性扫全仓 AST 建 `_m325_build_name_index`，实测 **7.95 s**。
目前的线程模型里它只付一次，且**不计入任何一轮的墙钟**（340B 特意单列计时，
否则会被读成"串行更慢"）。

进程池下，每个 worker 都是新解释器（Windows 只有 `spawn`，没有 `fork` COW），
`self_inspector` 的模块级缓存**不会继承** ⇒ 每个 worker 各付一次 7.95 s：

```
3 workers × 7.95 s = 23.9 s  >  串行总耗时 20.21 s
```

**结论：在"整仓预热 + spawn"的组合下，进程池首次跑就是净亏（31 s vs 20.21 s）。**
这一条比 IPC 开销重要一个数量级，也是本票最该被记住的一句。

### 2.3 破解路径（三选一，按推荐度排序）

| 方案 | 做法 | 预估收益 | 风险 |
|---|---|---|---|
| **A. 按片预热**（推荐） | 每个 worker 只对**自己那一片**涉及的文件建 name index | 三片并行预热，墙钟仍 ≈ 8 s / 3 ≈ 2.7 s；加 IPC 后总成本接近串行最优 | 索引是"全仓口径"，按片切会漏跨文件同名判定 ⇒ **必须验证按片索引与全仓索引的判定一致**（这就是本方案唯一的真风险） |
| B. 索引持久化 | 复用 338 刀1 的思路：把 name index 落盘成侧车文件，worker 直接载入 | 预热从 8 s 降到磁盘读（亚秒级） | 需要"索引随代码失效"的失效判定（338 刀1 已有 `invalidate` 范式可抄）；改动面横跨 `self_inspector` |
| C. 长驻 worker | 池子不销毁，跨批复用 | 预热只付一次 | 与"器官零状态"规则冲突；跨批复用会让判据带上上一批的缓存，正是 340 批踩过的坑 |

**B 与 A 不冲突**：B 解决"首次载入"，A 解决"worker 数量放大"。建议先 B 后 A。

### 2.4 其他可行性项

- **可 pickle 性**：任务 item 是 `dict`（file/method/line/id），行结果是 `dict`。
  两者天然可 pickle，**没有自定义类需要 `__reduce__`**。
- **探针副作用**：`_m325_probe_reachable` 只读不写（340 刀8 已核 `writes_prod_data=False`）。
  子进程各自持有只读索引 ⇒ 无写竞争。
- **隔离根冲突**：`build_live_items` 与 `_live_read_src` 都用**绝对路径**注入
  （`project_root` 参数），子进程只需把同一 `project_root` 传下去即可，不需要 chdir。
  ⚠ 但 `ProjectRoot` **必须走参数，不能用 `os.getcwd()`** —— 子进程 cwd 默认继承父进程，
  在隔离根验证时会把"看似隔离"的读写落到生产（铁律158 同型坑）。
- **Windows 特有**：`spawn` 会重新 import 主模块 ⇒ `multiprocessing` 入口必须放在
  `if __name__ == "__main__":` 下（`tools/k2_bench_339.py` 已有该保护，符合前提）。

## 三、影响面

| 面 | 影响 | 严重度 |
|---|---|---|
| `tools/k2_bench_339.py` | `run_parallel_live` 换 `ProcessPoolExecutor`；`warmup_live` 改按片；新增结果回收与异常传播 | 中（单文件，~80 行） |
| `self_inspector` | 需支持「按文件子集建索引」或「索引持久化」，二者都要动 `_m325_build_name_index` | **高**（核心判定模块） |
| 判定口径 | 进程池下 `verdict_fp` 需重新论证：同一 item 在不同 worker 里的判定必须**逐条相同**（现有 `verdict_fp_equal` 断言天然覆盖） | 低（断言已就位） |
| 既有测试 | `test_m339_k2_script_slices_and_concludes` 只用 synthetic 路径，不受影响；live 侧 `test_m340_batch.py::test_62` 需按新并行实现同步 | 低 |
| 生产路径 | **零影响** —— `tools/k2_bench_339.py` 是离线对表脚本，不被 `main.py` 导入 | 无 |
| 判据污染风险 | 若 worker 起不来（Windows 下常见：缺 `if __name__` 保护 / 秒退），`_ex.map` 会整体抛错 ⇒ 必须显式落 `degraded`，**不许把"没跑起来"读成"降幅 0%"**（铁律166） | 中 |

## 四、分叉建议

**建议立 `K2-p` 子批（不并入 342）**，三步走，每步都能独立判死：

1. **微基准（0.5 天，零风险）**
   量出 649 条任务里「纯 CPU 可并行部分」与「IO 部分」的占比，
   以及单次 `spawn` + pickle 往返的真实开销。
   **判死线**：若可并行 CPU < 20%，进程池的理论上限 < 15%，**整票作废**，K2 就停在
   "安全面通过 + 吞吐照报"这个状态（这也是 342 刀3 已经落地的稳定态）。
2. **索引持久化（1 天，中风险）**
   抄 338 刀1 的 `snapshot_index` 范式给 name index 做侧车。这一步**单独就有收益**：
   它把 live 对表从 20.21 s + 7.95 s 预热压到 20.21 s + 亚秒，即使不上进程池。
3. **进程池落地（1 天，中风险）**
   在 1、2 都绿之后再做；验收沿用现有双口径 —— **安全面（`verdict_fp_equal` ∧
   `output_equal`）一票否决，吞吐只报**。此时吞吐报告线可以顺手抬到 30%
   （因为理论上限终于支撑得起），但仍写成报告字段而非判据。
