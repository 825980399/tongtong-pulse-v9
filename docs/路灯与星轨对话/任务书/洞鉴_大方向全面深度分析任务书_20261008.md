## 一、新能力路线图优先级验证

### 1.1 烛微 171 优先序复核
烛微 C1 建议：**① InfluxDB → ② L3 精简器（先出命名消歧设计稿）→ ③ face_welcome（影子退出小刀）**，理由"新能力第一批应选能证明运行上限的，而非能省 token 的"。
- **分析**：该排序是否符合"P0 清零后并行设计文档+新能力"的战略定调？有无更优组合？
- **重点交叉验证**：InfluxDB 接线后是否真能同时支撑 `T-运行内存增长-1` / `T-超算镜像重跑-1` / L3 收益评估三票的可测量底座？

### 1.2 L3 命名消歧
烛微指出本仓 "L3" 有两个既有语义（InfoField 分层调度 / PulseInnerWorld 内在模型），7 键多数不存在。
- **分析**：给出消歧后的命名建议与键位规划（哪些键新建、哪些沿用、与既有 L3 语义的关系），供设计稿落地。

### 1.3 新能力对"运行上限"的战略意义
从多视角（架构/宪法/安全边界/开源）评估：新能力第一批的投入方向是否与项目终极目标（数字化生命、运行上限验证）一致？有无遗漏的更优先候选（如超算镜像本身）？

### 2.1 烛微 171 归位方案验证
