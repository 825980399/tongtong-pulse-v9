## 刀1：self_inspector线程化+降优先级（核心）

**做什么**：现在self_inspector启动期全库扫方法，占满CPU导致L0看门狗超时。改成独立低优先级后台线程，启动后延迟30秒再开始扫，不跟L0生命线抢CPU。

**怎么做**：
- self_inspector启动时不立刻全库扫，改成延迟30秒后在独立线程里跑
- 线程优先级设为最低（THREAD_PRIORITY_LOWEST）
- 扫方法体时每扫10个方法sleep 1ms，别一口气占满CPU
- 加开关：`ENABLE_SELF_INSPECTOR_STARTUP_SCAN = True`，关了就启动不扫

**验收**：
- 启动后L0看门狗不再超时
- self_inspector还是能扫到全库方法，只是慢一点
- 单测：延迟启动+低优先级不阻塞主线程

## 刀2：内存95%爆发真凶定位（核心）

**做什么**：今天又爆了——启动1分钟就7.4GB，10分钟就95%了。之前只找到"对象图浅尺寸"的近似方法，没找到真凶。这次必须定位到具体是哪个对象在涨。

**怎么做**：
- 启动时打一次基线内存快照（所有大对象：知识图谱节点数/经验池大小/调用图边数/向量库大小）
- 运行10分钟后再打一次快照
- 对比两个快照：哪个对象涨得最多？
- 重点怀疑对象：
  1. 叙事落盘——每次对话都append，会不会越攒越多？
  2. 经验池——降权治理后会不会没清理？
  3. self_inspector扫过的方法体——存在内存里没释放？
  4. StructParallel那16个并行worker——每个都持有副本？
- 找到真凶后：要么加清理逻辑，要么改成分页加载，要么限制上限

**验收**：
- 有明确的"内存涨了X GB，其中Y GB是ZZZ对象"的结论
- 修复后启动10分钟内存涨幅<2GB（之前是7GB+）

## 刀3：O3补盲——裸Name值传递判据（开闸前置）

**做什么**：415抽验发现85%真死率，差的那15%全是"函数被当值传递后间接调用"——dict value裸Name、import绑定、Assign右值。把这三类判据补上，下次开闸真死率就能到95%以上。

**怎么做**：
- 加一条判据："模块级函数名出现在值位（dict value/Assign右值/import）"——就算引用
- 注意：范围只限模块级函数，别把方法内嵌套def也算进去（会误保护）
- 跑完后重新算eligible数：之前440条，补完判据应该降到390条左右
- CI基线钉住的59条先排除，不删（删了门禁会红）

**验收**：
- 补完判据后真死率>95%
- 重新抽20条验证，确认真死率达标
- 单测：三类值传递场景的判据都能正确识别
