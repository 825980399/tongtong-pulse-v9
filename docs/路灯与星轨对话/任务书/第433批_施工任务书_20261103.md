## 刀1：_m84_recompute_split加override锁 + verify_applied_patches改单写口

**修什么**：现在有个每45分钟跑一次的静默复算旁路，会把任何人工修正改回去。
- `_m84_recompute_split`不看override锁，直接复算problem_fixed
- `verify_applied_patches`用`_save_json`整份写盘，绕过了`_save_patch_list`的427状态守卫

**怎么改**：
- `_m84_recompute_split`里加`is_split_override_locked(patch)`判据——如果人工override了就跳过复算
- `verify_applied_patches`末尾的`_save_json`改成`self._patch_manager._save_patch_list()`——走单写口，带上427状态守卫

**验证**：
- 改完后，人工override的problem_fixed还会被复算改回去吗？
- 走单写口后，427状态守卫会不会误收敛？

## 刀2：history upsert by id + 加载端去重 + 重复迁移

**修什么**：patch_history是append-only的，同一条补丁的两个生命周期快照会被追加成两行。现在盘上已经有1组重复了（`o3_1792638584_57885429`）。

**怎么改**：
- `_save_patch_list()`里，对history文件按id做upsert：同id时保留旧行的status_history/wont_fix_*，用新行的runtime_verify_*/status覆盖
- 加载端也加一层去重：按id去重，保留runtime_verify_last_attempt_at最大的一条
- 把盘上那组重复迁移了：保留approved那条，把wont_fix的撤单理由合并进status_history

**验证**：
- 同id连续append两次，落盘后只有1行吗？
- status_history里有没有合并撤单理由？
- 那组重复真的合并成一条了吗？

## 刀3：applied_at哨兵0→None + schema归一/校验

**修什么**：6条未落地补丁的`applied_at=0`（epoch 0），报表显示1970年。0是"还没落地"的默认哨兵，但显示出来很丑。

**怎么改**：
- 4处构造器里的`"applied_at": 0`改成`"applied_at": None`
- 加一层归一：`applied_at in (0, "0", "")` → `None`
- 加schema校验：`applied_at`只能是`None`或`> 946684800`（2000-01-01）

**验证**：
- 新生成的补丁applied_at是None了吗？
- 盘上那6条改成None了吗？
- 报表不再显示1970年了吗？

## 刀4：steady_growth基线缓存修正 + steady_window_sec出口

**修什么**：`steady_growth_mb_per_min=3.599`这个数字是错的——它是61.8分钟窗口的斜率，不是"启动后10分钟基线起的稳态泄漏率"。deque环里最老的样本被当成了"10分钟基线"。

**怎么改**：
- 只有当这个样本真的是ramp后的第一个点时，才缓存`_m427_rss_at_10min`
- 否则用已缓存的基线算斜率，不要覆盖
- health_snapshot里加`steady_window_sec`字段——告诉我们这个稳态率是多长窗口的

**验证**：
- 改完后，steady_growth的数字合理吗？
- health_snapshot里能看到steady_window_sec吗？
- 长跑1小时后，数字还会是错的吗？
