## 〇、目标（一句话）

把「每笔提交全量串行门禁 + 文档提交陪跑 + 重锚混流」改为「路径分级 + 并行静态门 + collect 两级 + 重锚分类」，**不放松任何门禁判定严格度、不合并角色**。预计单批墙钟下降 40-55%。

## 一、刀1 · 门禁路径分级（GATE_PATH_SPLIT）

**现状**：`.git/hooks/pre-commit` 13 个执行步骤全串行；近 3 天纯文档/台账提交 68 笔（约 34%）每笔照跑 collect 4,716 节点（约 15 分钟）。

**做法**：hook 入口用 `git diff --cached --name-only` 取暂存文件清单分流：
- 仅命中 `docs/**`、`*.md`、`docs/台账/**` → 只跑登记册/文档类校验（check_pending_register、台账状态白名单），**跳过全部 *.py / collect 门**；
- 命中任一 `*.py` / `config.py` / `main.py` / 测试 / 门禁脚本 → 跑完整门禁（现状不变）；
- 混合提交按"就严"跑全套。

**改动面**：`.git/hooks/pre-commit` 及入库的安装/同步脚本（hook 本体不入库，需同步更新安装源）。
⚠️ **在途冲突**：`tools/pre_commit_selfcheck.py`（工作树 ??，归属待核）——施工前先与星轨确认归属与作用，避免与路灯在途工作冲突；若属他方在途则避开不碰。

**验收判据（机读）**：
1. 构造纯 docs 提交，hook 退出码 0 且日志明确打印「文档路径→跳过代码门禁」，全程墙钟 ≤ 30 秒；
2. 构造含 1 个 `.py` 的提交，仍跑完整 13 步（日志可证步骤数不减）；
3. 构造 docs+py 混合提交，跑全套；
4. 三条用例固化为 `tests/` 下门禁自测脚本（新增测试计入 collect）。

**回退**：开关 `GATE_PATH_SPLIT=0` 即恢复现状全串行（独立 commit）。

## 二、刀2 · 静态门禁并行化 + collect 两级化（GATE_PARALLEL / GATE_COLLECT_LEVEL）

**现状**：13 步中 check_deprecated_imports / check_event_string_gate / check_silent_exc_arity / check_legacy_assembly_gate / check_broken_chain_gate 互不共享状态，串行执行；collect 与所有静态检查无依赖。

**做法**：
1. 上述 5 个静态门**并发执行**（任一失败整体失败，输出按门分段汇总保持可读）；
2. collect 两级：
   - **增量门**（日常每笔提交）：按改动文件的 import 反向依赖图，只收集受影响测试文件；依赖图无法解析时 **fail-safe 升级全量**（宁可慢不可漏）；
   - **全量门**（批末收口 + 每日 04:00 定时 + push 前）：维持 4,716 全节点 ±5 漂移判定，锚点与红基线机制完全不变。

**夜间定时机制 v2（小林已定 2026-10-06，机制先行、参数后可调）**：
- **目标**：凌晨无人值守期间让曈曈运行时间线延长 + 全量 collect 落在框架停机窗（曈曈现处于长时间停机状态：pulse.log 最后写入 10-05 21:40:22，无 runtime.lock）。
- **编排流程（04:00 触发）**：
  1. 检测 `data/runtime.lock`：
     - **无框架运行** → 直接跑全量 collect；
     - **框架运行中** → 发优雅退出信号 → 等待进程消失（30s 超时）→ 退出成功再跑 collect；退出失败则**不硬杀进程**、放弃本次 collect、记日志 + 次日 08:00 汇报。
  2. collect 完成后 → **自动启动框架**（`python main.py`，带 3 次重试，间隔 30s）。
  3. 启动失败 → 记日志 + 次日 08:00 汇报（不无限重试）。
- **护栏**：不硬杀进程、失败即放弃并留痕、次日 08:00 强制汇报、参数全部可配置（触发时间/补丁重启时间/collect 时机后续调整，不改逻辑只改配置）。
- **实施说明**：实现为计划任务 + 编排脚本（停止/collect/启动三段分离，各段可独立手动触发）；与框架运行互斥检测为核心；首次上线建议人工盯一晚（或白天验证"优雅退出→collect→重启"一次），稳定后转全自动。

**验收判据**：
1. 纯代码提交 hook 墙钟对比基线（现约 15 分钟）降至 ≤ 6 分钟（10 次采样中位数）；
2. 人为植入一个 deprecated import，增量门必须拦截（证明并行不漏检）；
3. 批末全量门结果与改造前全量门结果完全一致（同一工作树各跑一次，结论相同）；
4. 依赖图解析失败场景自动升级全量（用例覆盖）；
5. 夜间定时：模拟框架运行态（runtime.lock 在）→ 跳过并留日志；无锁 → 正常跑完（用例或手动验证记录）。

**回退**：`GATE_PARALLEL=0` / `GATE_COLLECT_LEVEL=full` 即恢复。

**风险提示**：依赖图准确性是本刀唯一技术风险点；**fail-safe 升级全量是硬要求**。倾向自研 import 解析（与现有断链门禁复用），不引入新依赖（避免与 PyMuPDF 开源合规票同类的许可风险）。

## 三、刀3 · 重锚分类授权

**现状**：审计窗内 `[ci-gate-change]` 重锚提交 37 笔，重锚与施工混流、笔笔独立过门禁。

**做法**：hook/门禁配置内置两类重锚白名单：
- **A 类（用例增减型）**：collect 节点变化可被「本批新增/删除测试文件清单」完全解释 → 提交时自动记录归因，**批末由星轨核签后一次性重锚**，不再逐笔；
- **B 类（红面/污染变化型）**：known_fail / pollution_set 内容变化 → **维持现状：人工裁决 + 独立 `[ci-gate-change]` 提交 + 说明**（红线不自动化放行）。

**验收判据**：
1. A 类场景不再产生逐笔重锚提交（批末仅 1 笔，提交信息含归因桶统计）；
2. B 类场景尝试自动放行时必须被拦截；
3. 每次批末重锚附「新增用例数 / 口径调整 / 真回归」三字段归因桶。

**回退**：白名单清空即恢复逐笔重锚。
