### 1.3 机制现状（代码锚点，可自行核对）

- **落盘一直在做**：每 30s 全量快照（60 次，背压节流 <30s 延迟落盘）+ 每小时 .bak（18:01/19:01/20:01 实测）+ L1 快照 + 冷存 parquet + 向量 vectors.npz（21:00 落盘）。**落盘 ≠ 释放内存**。
- **冷驱逐机制存在但 0 次触发**：`nucleus/mnemosyne/PulseNodePool.py`
  - L2034-2049：温池超限 → L1 节点直接写盘驱逐
  - L2051-2069：`_enforce_cold_cache` 冷池 LRU 驱逐（条件 `len(_cold) > _max_cold_cache`，自适应 600s 降频）
  - L2416-2436：`_evict_cold_node`（写盘成功才从 `_cold` 移除 + 登记 evicted）
  - **启动日志实测**：`18:01:03 启动按需加载: 11887 节点进内存, 0 冷节点落磁盘按需召回`——11,887 节点全量驻留，冷池上限 5000（`config.py:3275 nodepool_max_cold_cache`）从未触达 → **驱逐 0 次**
- **自适应负载框架已含内存维度**：`nucleus/field/InfoField.py`
  - L1140：`load_level = _get_load_level(cpu_percent, mem_percent, gpu_percent, gpu_mem_percent)`
  - L1230-1257：阈值——mem>95=critical（熔断红线）、mem>85=heavy、mem>65=moderate；动态偏移（minimal -5 / high +3）+ 滞回 5% 防震荡
  - 等级升高持续 45s 生效、降低立即生效
  - critical 已有联动：丢低优任务、回收例外突破额度、调线程池（**但不触发内存释放**）
- **可自适应参数**：`nucleus/evolution/ParamPatchManager.py:127` `"nodepool_max_cold_cache": (500, 20000)`——冷池上限属自适应参数族，当前静态 5000

## 二、任务目标

回答三个问题：

1. **校准一周膨胀推算**：基于上述 3.5h 实测曲线，估算曈曈连续运行约一周（168h）的内存膨胀程度。星轨初步三档模型为：保守（无驱逐、每日融合波 8 次）+28GB→≈34.6GB（72%）；中性 +2.5GB/天→20-28GB（42-58%）；驱逐平衡（冷池超限触发）→8-12GB 封顶。请验证模型假设是否合理、给出更准确的推算方法（可结合节点增长速率 163/h、快照大小增长 +3MB/3h、历史批次的节点/快照演进数据），并明确**在 48GB 机器上与 16GB 低配机器上分别的触险时间**。

2. **评估"内存高压自适应释放"方案**（星轨初步设计，见第三节），指出缺陷与遗漏，并回答可行性：能否复用现有 load_level + 冷驱逐 + RUNTIME_PARAMS 底座实现"内存≥90% 持续 N 分钟后缓慢落盘释放"？需要新增什么、风险是什么（如冷驱逐对检索性能的影响、Python 内存不归还 OS 的问题、GC 触发时机、驱逐风暴、滞回设计）？

3. **寻找更好的解决方法（本任务核心）**：不限于星轨方案，从以下方向深挖更优解（可自行补充新方向）：
   - 知识图谱冷热分层的**参数动态化策略**（阈值怎么定、依据什么信号：节点访问频率/上次激活时间/层级）
   - **向量 embedding 降驻留**：磁盘映射（mmap）、按需加载、多模型仅加载在用者（当前 3 个模型文件合计 970MB，是否全部驻留）
   - **快照副本优化**：全量 520MB JSON 每 30s 构建副本的峰值占用 → 增量快照/流式写盘/写时冻结
   - **Python 内存不归还 OS**：是否值得引入内存池限制（如 `PYTHONMALLOC=malloc`、`malloc_trim` 不可用时的替代）、`gc.collect()` 与 `weakref` 策略
   - **知识图谱节点瘦身**：节点元数据去冗余、value 压缩、历史版本合并
   - **向量库环境污染修复对内存的连带收益**（落盘失败→内存驻留的 0.3-1GB 是否能通过修路径直接释放）
   - **进程级方案**：如内存达阈值后的优雅降级档位设计（从"释放内存"到"建议重启"的完整决策树）

| 档位 | 触发 | 释放动作 |
