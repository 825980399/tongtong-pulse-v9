### 1.3 快照保存性能瓶颈深度分析（已生成专项报告）

**核心发现**：保存性能对系统负载极度敏感，存在锁竞争+队列积压的正反馈恶性循环。

| 场景 | 节点数 | 保存耗时 | 差异倍数 |
|------|--------|---------|---------|
| 正常低负载 | 8700节点 | 9秒 | 1x（基准） |
| **当前高负载** | **14128节点** | **7510秒** | **834倍** |

**五大瓶颈**（按影响排序）：
1. **json.dump序列化479MB超大对象**（最主要瓶颈）+ 高负载恶性循环
2. **全量保存频率过高**（每10分钟一次，但保存需要2小时，永远在保存）
3. **轮转备份大文件操作**（1.5GB磁盘写入/次，3个备份）
4. **Parquet已启用但只是额外副本**（17.4MB，压缩比27:1，未发挥主存储作用）
5. **node.to_dict() 40+字段/节点列表推导式**（14128节点×40字段=56万次字段访问）

**代码位置**：`nucleus/mnemosyne/PulseSnapshot.py`（1749行）
- 保存流程：`save()` → `_save_locked()`（持有RLock）→ 获取所有节点 → 计算校验和 → 判断增量/全量 → `_full_save()` → 构建snapshot字典（关键瓶颈：`[node.to_dict() for node in saved_nodes]`）→ `_atomic_write_with_rotation()`（os.rename 479MB + json.dump + os.replace）→ `save_l1()` → `save_parquet()`

### 1.4 队列深度过高根因分析（已生成专项报告）

**核心发现**：主要根因是快照保存耗时过长（7510秒），次要根因是胃模块知识消化过于频繁（每小时3181条日志，占44.5%），加剧因素是器官扫描组频繁执行+CPU 70-80%高负载。

**恶性循环链条**：
```
快照保存耗时过长 → 保存线程长期运行持有锁 → 其他操作等待锁 → 
脉冲事件处理变慢 → 队列深度增加 → CPU负载升高 → 
保存速度进一步变慢 → 队列深度继续增加 → ...
```

## 二、任务清单

### T1 · P0 快照保存性能止血（异步保存+双缓冲+分批序列化+降频）

**债务ID**：P0-快照保存性能（7510秒/2小时5分钟，队列深度2000+的主要根因）

**问题描述**：
- 快照全量保存需要7510秒（2小时5分钟），而保存间隔只有600秒（10分钟），导致永远在保存
- 保存线程持有RLock，阻塞其他操作，形成锁竞争+队列积压的恶性循环
- json.dump序列化479MB超大对象是最主要瓶颈
- 轮转备份3个文件共1.5GB磁盘写入/次

**修改文件**：
- `nucleus/mnemosyne/PulseSnapshot.py`（核心修改，1749行）
- `config.py`（新增配置项）
- 可能涉及：`nucleus/PulseNodePool.py`（节点获取接口）

**具体修改点**：

#### 1.1 降低全量保存频率（配置修改，立即生效）

1. `FULL_SAVE_INTERVAL` 从 `600`（10分钟）改为 `3600`（1小时）
2. `INCREMENTAL_MAX_NODES` 从 `50` 改为 `200`（允许更多变更走增量保存）
3. `INCREMENTAL_MIN_INTERVAL` 保持 `30` 秒
4. 新增配置项：`SNAPSHOT_SAVE_TIMEOUT = 1800`（保存超时30分钟，超时则跳过本次保存并告警）
5. 新增配置项：`SNAPSHOT_ASYNC_SAVE = True`（启用异步保存）

#### 1.2 异步保存+双缓冲（消除锁竞争恶性循环）

**核心思路**：保存操作不在主线程执行，而是提交到后台线程池；使用双缓冲避免保存期间节点被修改。

1. 新增`_save_thread_pool`（ThreadPoolExecutor，max_workers=1，保证保存顺序）
2. `save()`方法改为：
   - 检查是否有正在进行的保存（`_is_saving`标志）
   - 如果正在保存，跳过本次并记录WARNING（避免堆积）
   - 如果没有正在保存，获取节点快照（浅拷贝节点ID列表+节点状态），提交到后台线程池
   - 立即返回，不阻塞调用方
3. 双缓冲机制：
   - 保存前创建节点数据的深拷贝（或不可变快照），保存过程中使用这份快照
   - 保存期间节点池可以继续正常读写，不被阻塞
   - 保存完成后更新`_last_save_time`和`_last_save_checksum`
4. 保存超时保护：后台保存线程设置超时，超时则终止并告警
5. 保存失败处理：保存失败时记录ERROR，但不影响框架正常运行

#### 1.3 分批序列化（降低内存峰值和单次CPU占用）

**核心思路**：不再一次性构建`[node.to_dict() for node in saved_nodes]`，而是分批序列化写入。

1. 将14128个节点分为10批（每批约1400节点）
2. 每批独立执行`node.to_dict()`，构建子列表
3. 使用`json.dump`的分批写入能力（或手动构建JSON数组，分批写入文件）
4. 每批之间释放临时变量，降低内存峰值
5. 可选：使用`orjson`（框架已启用）替代标准`json`，序列化速度提升3-5倍

#### 1.4 保存期间的系统保护

1. 保存开始时设置`_is_saving = True`，通知其他模块降低非关键操作频率
2. 保存期间胃模块知识消化频率降低50%（通过配置或信号）
3. 保存期间器官扫描组跳过非紧急扫描
4. 保存完成后设置`_is_saving = False`，恢复正常操作频率
5. 保存耗时超过阈值（如600秒）时，输出WARNING并建议优化

**验收标准**：
- 全量保存时间 < 300秒（当前7510秒，降低96%）
- 保存期间对话响应正常（不卡顿、不超时）
- 保存期间队列深度不持续增长
- 异步保存不阻塞主线程
- 分批序列化内存峰值降低50%以上
- 保存失败不影响框架正常运行
- 新增测试：异步保存测试、双缓冲测试、分批序列化测试、保存超时测试

### T2 · P0 真正的增量保存（增量日志+定期合并，替代当前伪增量）

**债务ID**：P0-增量保存（当前增量保存阈值50节点，实际几乎每次都走全量保存）

**问题描述**：
- 当前增量保存机制：`INCREMENTAL_MAX_NODES=50`，变更节点超过50个就走全量保存
- 实际运行中，10分钟内变更节点通常超过50个，所以几乎每次都走全量保存
- 增量保存没有真正的增量日志，只是判断"变更节点数是否小于阈值"
- 需要实现真正的增量保存：记录变更日志，定期合并到全量快照

**修改文件**：
- `nucleus/mnemosyne/PulseSnapshot.py`（增量保存逻辑重写）
- `config.py`（新增增量保存配置）
- 可能涉及：`nucleus/PulseNodePool.py`（节点变更追踪）

**具体修改点**：

#### 2.1 增量日志机制

1. 新增`_incremental_log`：记录自上次全量保存以来的节点变更（新增/修改/删除）
2. 节点变更时自动记录到增量日志（通过节点池的变更回调或钩子）
3. 增量日志格式：`{node_id, action, timestamp, node_data（仅修改时）}`
4. 增量日志持久化：每次变更后异步追加到`data/knowledge/snapshot_incremental.jsonl`
5. 增量日志大小限制：超过阈值（如100MB或10万条）时触发全量保存+清理

#### 2.2 增量保存流程

1. 每次保存时，先检查增量日志大小
2. 如果增量日志 < 阈值（如10MB或1万条），执行增量保存：
   - 将增量日志追加到增量保存文件（或合并到当前快照）
   - 清空内存中的增量日志
   - 保存耗时预期 < 5秒
3. 如果增量日志 >= 阈值，执行全量保存：
   - 执行完整的全量保存流程（使用T1的异步+分批优化）
   - 保存成功后清空增量日志和增量保存文件
4. 启动时加载：先加载全量快照，再应用增量日志，恢复最新状态

#### 2.3 定期合并机制

1. 新增后台线程：定期检查增量日志大小
2. 增量日志超过阈值时，自动触发全量保存+合并
3. 合并完成后，清理旧的增量日志文件
4. 保留最近N个增量日志文件作为备份（可配置，默认3个）

#### 2.4 兼容性和回滚

1. 保留旧的全量保存文件作为备份（至少3个）
2. 增量保存失败时，回退到全量保存
3. 启动时如果增量日志损坏，跳过增量日志，从全量快照恢复（并告警）
4. 提供配置开关：`SNAPSHOT_USE_INCREMENTAL_LOG = True`，可关闭增量日志回退到旧机制

**验收标准**：
- 增量保存时间 < 10秒（当前全量7510秒）
- 增量日志正确记录所有节点变更
- 启动时全量快照+增量日志能正确恢复最新状态
- 增量日志超过阈值时自动触发全量保存+合并
- 增量保存失败时自动回退到全量保存
- 增量日志损坏时不影响框架启动（从全量快照恢复）
- 新增测试：增量日志记录测试、增量保存测试、启动恢复测试、定期合并测试、损坏恢复测试

### T4 · P1 队列深度自适应降频机制（防止队列积压恶性循环）

**债务ID**：P1-队列深度自适应（队列深度2000+，runtime_metrics WARNING占80.2%）

**问题描述**：
- 队列深度持续2000+（上限5000的42%），8分钟增加329
- runtime_metrics WARNING占80.2%（105/131条），告警泛滥
- 当系统负载高时（如快照保存期间），非关键操作仍在高频执行，加剧队列积压
- 需要自适应降频机制：根据队列深度和系统负载，自动调整非关键操作的频率

**修改文件**：
- `nucleus/runtime_metrics.py`（队列深度监控和自适应降频）
- `config.py`（新增自适应降频配置）
- 可能涉及：各个执行非关键操作的模块（胃知识消化、器官扫描、代码学习等）

**具体修改点**：

#### 4.1 系统负载评估

1. 新增`SystemLoadMonitor`：定期评估系统负载
2. 评估指标：
   - 队列深度（当前值、增长趋势）
   - CPU使用率（1分钟/5分钟/15分钟平均）
   - 内存使用率
   - 快照保存状态（是否正在保存、保存已耗时）
   - 最近1分钟处理的事件数
3. 负载等级：
   - `LOW`（低负载）：队列深度<500，CPU<50%，无快照保存
   - `MEDIUM`（中负载）：队列深度500-1500，CPU 50-70%，或快照保存中
   - `HIGH`（高负载）：队列深度1500-3000，CPU 70-85%，或快照保存超过300秒
   - `CRITICAL`（临界负载）：队列深度>3000，CPU>85%，或快照保存超过600秒

#### 4.2 自适应降频策略

根据负载等级，自动调整非关键操作的频率：

| 操作 | LOW（正常） | MEDIUM（降频30%） | HIGH（降频60%） | CRITICAL（暂停） |
|------|------------|------------------|----------------|----------------|
| 胃知识消化 | 每30秒 | 每45秒 | 每120秒 | 暂停 |
| 器官扫描组 | 每5分钟（缓存） | 每7分钟 | 每15分钟 | 暂停 |
| 代码学习 | 每60秒 | 每90秒 | 每180秒 | 暂停 |
| 经验库清理 | 每5分钟 | 每10分钟 | 每30分钟 | 暂停 |
| 冷存compaction | 每10分钟 | 每20分钟 | 每60分钟 | 暂停 |
| 快照保存 | 正常 | 正常 | 正常（不可暂停） | 正常（不可暂停） |
| 对话响应 | 正常 | 正常 | 正常（不可降频） | 正常（不可降频） |
| 心跳/生命体征 | 正常 | 正常 | 正常（不可降频） | 正常（不可降频） |

#### 4.3 降频执行机制

1. 新增`AdaptiveFrequencyController`：统一管理所有非关键操作的频率
2. 每个非关键操作注册到控制器，声明正常频率和最低频率
3. 控制器根据当前负载等级，计算实际执行间隔
4. 操作执行前询问控制器：`should_execute(operation_name)` → 返回True/False
5. 负载等级变化时，输出INFO日志（不要频繁输出，每5分钟最多1次）

#### 4.4 队列深度保护

1. 队列深度超过`QUEUE_DEPTH_WARNING_THRESHOLD = 1500`时，输出WARNING
2. 队列深度超过`QUEUE_DEPTH_CRITICAL_THRESHOLD = 3000`时，输出ERROR并自动触发降频
3. 队列深度持续增长（5分钟内增长>500）时，输出WARNING并分析增长原因
4. 队列深度恢复正常（<500）时，自动恢复正常频率

**验收标准**：
- 系统负载评估正确，能准确识别LOW/MEDIUM/HIGH/CRITICAL四个等级
- 自适应降频策略正确，各操作频率按负载等级调整
- 队列深度超过阈值时自动触发降频
- 队列深度恢复正常时自动恢复正常频率
- 对话响应、心跳、快照保存等关键操作不受降频影响
- 降频状态变化时有日志输出（但不频繁）
- 新增测试：负载评估测试、自适应降频测试、队列深度保护测试、关键操作不受影响测试
