### T1：补丁验证空转根因分析 + 修复方案设计（P0-2）

**对应债务**：P0-2 补丁验证空转
**类型**：设计 + 代码审查
**需重启**：❌ 否
**预估工时**：2-3小时
**优先级**：★★★★★（最高）

#### 问题描述

补丁系统的验证环节是**假通过**——65/67条补丁的`baseline_errors=0`，意味着验证时没有真正对比修复前后的错误数变化。补丁验证有效率约3%，连续5轮修复率<10%。

#### 任务要求

1. **根因分析**：
   - 定位补丁验证机制的代码位置（PatchManager相关模块）
   - 分析`baseline_errors=0`的根因：是采集时机不对？对比逻辑错误？还是测试范围不对？
   - 抽查3-5条补丁的完整验证流程，确认假通过的具体环节
   - 输出根因分析报告（含代码位置、调用链、问题定位）

2. **修复方案设计**：
   - 设计补丁验证机制的修复方案，确保：
     - `baseline_errors`真实采集修复前的错误基线（在补丁应用前运行测试/检查，记录错误数）
     - 验证时真实对比修复前后的错误数变化（`before_errors` vs `after_errors`）
     - 杜绝`baseline_errors=0`的假通过
   - 设计验证结果的可信度评级（如：高/中/低可信度）
   - 设计回滚机制（验证失败时自动回滚补丁）
   - 输出修复方案设计文档（含架构图、接口定义、实施步骤、风险评估）

3. **小步实施（可选，如时间允许）**：
   - 如果根因清晰且修复方案简单，可先实施最核心的修复（如baseline_errors采集逻辑）
   - 必须有pytest测试覆盖
   - 如实施复杂，仅做设计，延后到第47批实施

#### 验收标准

- [ ] 根因分析报告完成，明确指出`baseline_errors=0`的具体原因和代码位置

### T2：SERP污染数据清洗策略 + 防污染机制设计（P0-3）

**对应债务**：P0-3 SERP污染锁死L3
**类型**：设计 + 数据分析
**需重启**：❌ 否
**预估工时**：2-3小时
**优先级**：★★★★★（最高）

#### 问题描述

经验库（SERP，Semantic Experience Retrieval Pool）**79.5%污染**（1193/1501条），且100%单一原因是"内容重复(历史灌水)"。226条不可逆污染锁死了L3经验检索层的效果。内在模型训练会"把噪声学进去"。

#### 任务要求

1. **污染数据分析**：
   - 读取`data/experience/experience_pool.json`，统计：
     - 总记录数、污染记录数、干净记录数
     - 污染原因分布（确认是否100%为"内容重复(历史灌水)"）
     - 污染记录的时间分布（哪些批次产生的污染最多）
     - 干净记录的质量分布（评分、来源、类型）
   - 分析"内容重复(历史灌水)"的具体形态：是完全重复？还是高度相似？还是模板化生成？
   - 识别226条"不可逆污染"的特征（为什么不可逆？是被标记为protected？还是有外部依赖？）
   - 输出污染数据分析报告

2. **数据清洗策略设计**：
   - 设计经验库数据清洗的完整策略：
     - 清洗范围：哪些记录可以安全删除？哪些需要保留？
     - 清洗方法：完全重复删除？相似度聚类去重？质量评分过滤？
     - 清洗顺序：先删完全重复，再处理高度相似，最后人工审核边界案例
     - 安全措施：清洗前完整备份、清洗后验证检索效果、可回滚
     - 停机窗口：清洗需要框架停机（避免与在写进程竞争）
   - 设计清洗工具的接口和使用方法
   - 设计清洗效果的验证方法（清洗前后的检索准确率对比）

3. **防污染机制设计**：
   - 设计经验库写入的防污染机制，避免未来再产生"历史灌水"污染：
     - 写入前质量检查（重复检测、相似度检测、质量评分阈值）
     - 写入配额限制（单批次/单来源的最大写入量）
     - 写入审核机制（高污染风险的记录需要人工审核）
     - 与已有的`write_guard.py`（第44批T4）的协同
   - 设计防污染机制的灰度上线方案（先观测，再拦截）

4. **小步实施（可选，如时间允许）**：
   - 可先实施污染数据分析工具（只读，不修改数据）
   - 可先实施防污染机制的观测级（只记录不拦截）
   - 实际数据清洗需等停机窗口，不在本批执行

#### 验收标准

- [ ] 污染数据分析报告完成，包含详细统计和特征分析
- [ ] 数据清洗策略设计文档完成，包含清洗范围、方法、顺序、安全措施
- [ ] 防污染机制设计文档完成，包含写入检查、配额、审核、灰度方案
- [ ] 设计文档通过代码审查（星轨审核）
- [ ] 如有小步实施，pytest通过，ruff F=0

### T3：自认知报告消费机制设计（P0-1）

**对应债务**：P0-1 自认知闭环断裂
**类型**：设计 + 架构分析
**需重启**：❌ 否
**预估工时**：2小时
**优先级**：★★★★☆（高）

#### 问题描述

框架生成了大量自认知报告（健康诊断、代码学习、进化效能等），但**报告生成后没有消费者**——躺在日志里无人读，不驱动任何决策。自认知报告消费率=0%。框架"知道自己有问题"但"不知道该怎么办"。

#### 任务要求

1. **自认知报告清单梳理**：
   - 梳理框架当前生成的所有自认知报告类型：
     - 健康诊断报告（健康问题数、异常列表）
     - 代码学习报告（学习进度、方法理解）
     - 进化效能报告（补丁成功率、修复率）
     - 运行时指标报告（队列深度、资源使用、调用统计）
     - 其他（认知反思、内在世界状态等）
   - 统计每种报告的生成频率、数据量、存储位置
   - 分析每种报告的"潜在消费者"：应该被哪个模块/机制消费？
   - 输出自认知报告清单

2. **消费机制设计**：
   - 设计自认知报告的消费机制，确保关键报告能驱动后续动作：
     - **分级消费**：P0级异常→立即触发告警/补丁生成；P1级→纳入任务队列；P2级→仅记录
     - **消费链路**：报告生成→异常检测→优先级判定→触发动作（补丁/任务/告警）→验证效果
     - **消费者模块**：设计一个统一的"报告消费器"模块，接收所有报告并分发
     - **与补丁系统协同**：关键异常报告直接触发补丁生成（与T1的补丁验证修复协同）
     - **与任务队列协同**：非紧急问题纳入技术债务清单，由星轨/路灯处理
   - 设计消费效果的验证方法（消费率、动作触发率、问题解决率）

3. **关键指标定义**：
   - 定义自认知闭环的核心指标：
     - 报告消费率（被消费的报告/总报告）
     - 异常触发率（触发后续动作的异常/总异常）
     - 问题解决率（被解决的问题/总问题）
     - 闭环时延（从报告生成到问题解决的平均时间）
   - 设计指标的采集和展示方法

4. **小步实施（可选，如时间允许）**：
   - 可先实施报告消费机制的观测级（只记录消费情况，不触发动作）
   - 可先实施最关键的1-2种报告的消费（如健康诊断P0级异常→告警）
   - 完整消费机制延后到第47-48批实施

#### 验收标准

- [ ] 自认知报告清单完成，包含所有报告类型、频率、潜在消费者
- [ ] 消费机制设计文档完成，包含分级消费、消费链路、消费者模块、协同机制
- [ ] 关键指标定义完成，包含采集和展示方法

### T4：tmp治理（备份机制 + 测试隔离目录自动回收）（P2-300/301）

**对应债务**：P2-300（tmp无备份→误删不可逆）、P2-301（测试隔离目录残留必然复现）、P2-307（旧测试在项目tmp/创建目录）
**类型**：代码实施 + pytest
**需重启**：❌ 否
**预估工时**：2-3小时
**优先级**：★★★☆☆（中高）

#### 问题描述

第45批T2 tmp清理时发生两次回归：误删3个测试依赖的tmp文件（import依赖和subprocess依赖），根因是清理判据未扫描"tmp是否被测试依赖"，且`tmp/`无任何备份机制（`.gitignore`排除+不进`.bak_batchNN`），误删不可逆。

另外，旧批次测试持续在`tmp/`创建隔离目录（`m41_t2_*`/`t_*`/`_m27_*`），残留必然复现，"一个都不能有"的断言在全量跑时必然误报。

#### 任务要求

1. **tmp备份机制实施**：
   - 设计并实施`tmp/`目录的轻量级备份机制：
     - 每次批次任务开始前，自动快照`tmp/`目录（只备份关键文件，如`_m*`/`t_*`等测试依赖文件）
     - 备份位置：`.tmp_backup/YYYYMMDD_HHMMSS/`（加入`.gitignore`）
     - 备份保留策略：保留最近5次备份，自动清理旧备份
     - 恢复工具：提供一键恢复指定备份的脚本
   - 与现有的`.bak_batchNN/`备份机制协同（`.bak_batchNN`备份源码，`.tmp_backup`备份tmp）
   - 必须有pytest测试覆盖（备份创建、恢复、清理）

2. **测试隔离目录自动回收实施**：
   - 梳理所有在`tmp/`创建隔离目录的测试文件（`m41_t2_*`/`m41_t3_*`/`t_*`/`_m27_*`等）
   - 将这些测试的`tempfile.mkdtemp(prefix=..., dir=tmp)`改为`tempfile.TemporaryDirectory(prefix=...)`（自动回收，使用系统临时目录）
   - 对于必须使用项目`tmp/`的测试，添加`tearDown`/`finally`清理逻辑
   - 确保修改后所有测试仍然通过
   - 更新第45批新增的守卫测试（`TestTmpModulesUsedByTests`/`TestTmpScriptsRunByTests`），确保与新的自动回收机制兼容

3. **tmp清理判据增强**：
   - 增强tmp清理工具的判据，在清理前必须扫描：
     - 测试文件中`import tmp.xxx`的依赖
     - 测试文件中`subprocess.run(["python", "tmp/xxx.py"])`的依赖
     - 测试文件中`open("tmp/xxx")`的依赖
   - 输出"测试依赖的tmp文件清单"，清理时自动排除这些文件
   - 与第45批新增的两道守卫测试协同

#### 验收标准

- [ ] tmp备份机制实施完成，包含自动快照、保留策略、恢复工具
- [ ] 测试隔离目录自动回收实施完成，所有相关测试改为`TemporaryDirectory`或添加清理逻辑
- [ ] tmp清理判据增强完成，清理前自动扫描测试依赖
- [ ] pytest全量通过（特别是受影响的测试文件）
- [ ] ruff F=0，E402零新增
