### T1 · P1 内存根因排查与优化（定位3.8→5.2GB增长源）

**债务ID**：P1-内存增长（第65批T5遗留，框架运行期内存从3.8GB增长到5.2GB）

**问题描述**：
- 框架运行期内存从3.8GB增长到5.2GB，增长速度约127MB/分钟
- 第65批T5已添加`runtime_metrics.get_memory_usage()` / `check_memory_alarm()`和只读分析器`tools/memory_growth_analyzer.py`
- 但尚未在运行期实际抓取Top对象类型，定位增长源

**修改文件**：
- `tools/memory_growth_analyzer.py`（可能需要增强）
- `nucleus/runtime_metrics.py`（内存监控可能需要增强）
- 可能涉及：发现内存泄漏的具体模块

**具体修改点**：

#### 1.1 运行期内存快照抓取

1. 框架运行时（建议运行30分钟以上），使用`tools/memory_growth_analyzer.py`抓取内存快照
2. 分析Top对象类型，识别内存增长最快的模块
3. 对比启动时和运行30分钟后的内存分布，定位增长源
4. 生成内存分析报告：`docs/内存增长根因分析_第66批.md`

#### 1.2 常见内存泄漏点排查

根据框架结构，重点排查以下模块：
1. **知识节点池（PulseNodePool）**：节点是否无限增长，冷存compaction是否正常
2. **经验库（experience_pool）**：经验是否无限增长，容量保护是否生效
3. **InfoField事件历史**：事件历史是否无限增长，是否有清理机制
4. **代码学习缓存**：学习结果是否无限缓存
5. **器官扫描缓存**：第64批新增的缓存是否有大小限制
6. **监听器/回调**：是否有未注销的监听器导致对象无法回收
7. **循环引用**：是否有对象循环引用导致GC无法回收

#### 1.3 内存优化（根据排查结果）

根据排查结果，针对性优化：
1. 为无限增长的缓存/列表增加大小限制（LRU淘汰或定期清理）
2. 修复对象循环引用（使用weakref）
3. 及时释放不再使用的大对象
4. 优化大对象的存储方式（如使用更紧凑的数据结构）

#### 1.4 内存监控增强

1. 增强`runtime_metrics.check_memory_alarm()`，增加内存增长率监控
2. 内存超过阈值（如80%）时自动触发GC
3. 内存持续增长时触发告警，提示可能存在内存泄漏
4. 在`status`命令中显示内存使用情况和Top内存占用模块

**验收标准**：
1. 完成运行期内存快照抓取，生成内存分析报告
2. 定位内存增长源（具体模块/对象类型）
3. 如发现内存泄漏，完成修复
4. 内存增长速度降至合理水平（预期<10MB/分钟，稳定运行后）
5. 内存监控增强，可自动告警
6. 相关测试全部通过
