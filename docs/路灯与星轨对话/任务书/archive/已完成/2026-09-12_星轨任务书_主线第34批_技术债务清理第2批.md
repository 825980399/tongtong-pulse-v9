## 二、任务清单

### T1（P2-196，★核心）：`_multi_step_execute_v2` 全步失败改返回 `None`

**优先级**：P2（建议优先，本批核心）
**预估工时**：2-3 小时
**需重启验证**：✅ 是（本批唯一需重启项）

**问题描述**：
`_multi_step_execute_v2` 在全部步骤都失败时，返回的是**非 None 的降级叙述**（如"第1步失败：...，第2步失败：..."），这会阻断上层的单次大模型兜底逻辑。用户最终得到的是"分 N 步、每步 ⚠️ 失败"的低质答案，而不是一次完整的大模型回答。

**第33批 T5 实证**：
- 检索无命中时，每条操作指令产生 **3 次**模型兜底调用（=计划步数）
- 最终答案仍是失败叙述 → **更贵、更差**
- 8 条操作指令中，即使 `ENABLE_MULTI_STEP_OPERATIONAL_ADMISSION=False`，仍有 2 条（含基础关键词"查"）进入 v2 并付出 3 次模型调用

**修复方案**：
1. 修改 `_multi_step_execute_v2` 的"全步失败"出口，从返回降级叙述改为**返回 `None`**
2. 这样无论准入开关如何，只要多步走不通就会自然回落上层单次大模型兜底
3. 这比继续调准入开关更彻底（开关只能挡住一部分指令，而返回 None 从根上消除"3 步全失败劣于大模型兜底"）

**实施要点**：
- 定位 `_multi_step_execute_v2` 方法（`organs/brain/PulseInnerWorld.py`）
- 找到"全部步骤失败"的出口（通常是循环结束后检查所有步骤结果）
- 将返回的降级叙述改为 `return None`
- 检查上层调用方：确认调用方在收到 `None` 时会正确回退到单次大模型兜底（这应该是已有的逻辑，因为 `None` 是"未找到答案"的标准信号）
- 添加灰度开关 `ENABLE_MULTI_STEP_FAIL_RETURN_NONE`（默认 `True`），关闭即复现旧行为（零回归）

**验收标准**：
1. ✅ `_multi_step_execute_v2` 在全步失败时返回 `None`（而非降级叙述）
2. ✅ 灰度开关 `ENABLE_MULTI_STEP_FAIL_RETURN_NONE` 默认 `True`，关闭即复现旧行为
3. ✅ 上层调用方在收到 `None` 时正确回退到单次大模型兜底（代码审查确认）
4. ✅ 新增门控测试：构造全步失败场景，断言返回 `None`；开关关闭时断言返回非 None
5. ✅ pytest 全量通过（基线 938 + 新增）
6. ✅ ruff F=0 全库
7. ✅ 重启框架后端到端验证：输入一条操作类指令，确认不会出现"3 步全失败"的低质答案，而是回退到单次大模型回答

**风险提示**：
- 需确认上层调用方的 `None` 处理逻辑确实存在且正确（如果调用方把 `None` 当成有效答案，会导致空回复）
- 建议先做 T0 核实：追踪 `_multi_step_execute_v2` 的所有调用方，确认 `None` 处理逻辑

### T2（P2-197+P2-198）：多步检索准入判据完善

**优先级**：P2
**预估工时**：2-3 小时
**需重启验证**：❌ 否（可通过单元测试验证）

**问题描述**：
第33批 T5 评估发现两个准入判据缺口：

**P2-197**：`_m29_has_multi_step_signal` 的动作序列正则间隔 `.{0,10}?` 过窄，且动词表缺「删掉/粘贴」等 → 真实操作指令漏判。
- 实证：「打开微信，找到张总的聊天窗口，然后把这段话发给他」判 `False`（"打开→然后"间隔 12 字），**即使打开准入也进不去 v2**
- 另：「删掉/粘贴」等动词不在动作表内

**P2-198**：`ENABLE_MULTI_STEP_OPERATIONAL_ADMISSION=False` 未能覆盖含基础门槛关键词（查/分析…）的操作指令 → 残余「3 步全失败」风险。
- 实证：8 条操作指令中 2 条（如「帮我查一下今天的天气，然后提醒我带伞」）在 **OFF 下仍放行**，同样付 3 次模型调用
- 基础门槛需增加「是否操作类」的二次判定

**修复方案**：

**P2-197 修复**：
1. 放宽动作序列正则间隔：`.{0,10}?` → `.{0,30}?`（或更合理的值，需 T0 核实典型操作指令的间隔分布）
2. 补充动词表：增加「删掉/删除/粘贴/复制/剪切/发送/转发/回复」等常见操作动词
3. 添加回归用例：「打开微信，找到张总的聊天窗口，然后把这段话发给他」必须判 `True`

**P2-198 修复**：
1. 在基础门槛关键词（查/分析/搜索/找…）命中后，增加「是否操作类」的二次判定
2. 操作类判定逻辑：检查指令中是否包含动作序列信号（动词+然后/接着/再+动词），如果是操作类且准入开关关闭，则拦截
3. 或者：更简单的方案——T1（P2-196）修复后，即使进入 v2 也会因全步失败返回 `None` 而回退兜底，所以 P2-198 的紧迫性降低。但仍建议完善判据，减少不必要的 3 次模型调用

**实施要点**：
- 定位 `_m29_has_multi_step_signal` 方法（`organs/brain/PulseInnerWorld.py`）
- T0 核实：统计典型操作指令的动作间隔分布，确定合理的放宽值
- 放宽正则间隔 + 补动词表
- 添加操作类二次判定逻辑（或评估 T1 修复后是否还需要）
- 添加灰度开关（可复用 `ENABLE_MULTI_STEP_OPERATIONAL_ADMISSION` 或新增）

**验收标准**：
1. ✅ `_m29_has_multi_step_signal` 正则间隔放宽至合理值（T0 核实后确定）
2. ✅ 动词表补充「删掉/删除/粘贴/复制/剪切/发送/转发/回复」等
3. ✅ 回归用例：「打开微信，找到张总的聊天窗口，然后把这段话发给他」判 `True`
4. ✅ 含基础关键词的操作指令在准入开关关闭时被正确拦截（或评估 T1 修复后是否已自然解决）
5. ✅ 新增门控测试：覆盖放宽后的正则、补充的动词、操作类二次判定
6. ✅ pytest 全量通过
7. ✅ ruff F=0 全库

**风险提示**：
- 正则间隔放宽过大可能导致误判（把非操作类指令判为操作类），需 T0 核实典型分布
- T1（P2-196）修复后，P2-198 的紧迫性降低，可评估是否简化处理
