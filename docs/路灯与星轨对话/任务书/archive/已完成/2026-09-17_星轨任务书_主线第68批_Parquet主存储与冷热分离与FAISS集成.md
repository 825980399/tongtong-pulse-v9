## 二、任务清单

### T1 · P0 Parquet升级为主存储（JSON降级为兼容备份）

**债务ID**：P0-Parquet主存储（当前Parquet只是额外副本，未发挥主存储作用，压缩比27:1未充分利用）

**问题描述**：
- 当前Parquet已启用（`FEATURE.use_parquet_snapshot=True`），但只是JSON的额外副本
- 每次保存还是先写479MB JSON，再写17.4MB Parquet，双重写入开销
- 查询还是从JSON加载，Parquet只用于备份，没有发挥列式存储的查询优势
- JSON快照479MB（12270节点），Parquet只有17.4MB，压缩比27:1
- 随着节点数增长，JSON快照将达到几十GB甚至几百GB，完全不可扩展

**修改文件**：
- `nucleus/mnemosyne/PulseSnapshot.py`（核心修改：Parquet主存储逻辑）
- `nucleus/knowledge_access_layer.py`（KAL增加Parquet后端）
- `config.py`（新增Parquet主存储配置）
- 可能涉及：`nucleus/PulseNodePool.py`（节点加载逻辑）

**具体修改点**：

#### 1.1 Parquet主存储加载逻辑

1. **加载优先级调整**：
   - 优先从Parquet加载（快、小）
   - Parquet不存在或损坏时，回退到JSON加载（兼容备份）
   - 加载完成后，记录加载来源（Parquet/JSON）用于诊断

2. **Parquet加载优化**：
   - 使用pyarrow或pandas的列式读取，只读取需要的列
   - 支持谓词下推（如只加载L1节点、只加载最近修改的节点）
   - 分批加载，避免一次性加载全部节点到内存（为冷热分离做准备）

3. **JSON降级为兼容备份**：
   - JSON保存变为可选（配置开关`SNAPSHOT_SAVE_JSON_BACKUP=True`，默认开启）
   - JSON保存可以异步执行，不阻塞主流程
   - JSON只用于兼容备份和回退，不再作为主存储

#### 1.2 Parquet主存储保存逻辑

1. **保存优先级调整**：
   - 优先保存Parquet（主存储）
   - JSON保存变为可选的兼容备份（异步执行）
   - 保存完成后，验证Parquet文件完整性（行数、校验和）

2. **Parquet保存优化**：
   - 列式写入，只写入有变更的列（增量列更新）
   - 按evol_level分片（L1/L2/L3独立文件）
   - 按时间分片（每月/每季度一个文件，避免单文件过大）
   - 压缩算法选择：snappy（速度快）或gzip（压缩比高），可配置

3. **按evol_level分片存储**：
   - L1热节点：`data/knowledge/parquet/L1/`（独立文件，高频访问）
   - L2温节点：`data/knowledge/parquet/L2/`（独立文件，中频访问）
   - L3冷节点：`data/knowledge/parquet/L3/`（独立文件，低频访问）
   - 每个分片独立保存和加载，避免全量读写

#### 1.3 配置项

新增配置：
```python
# Parquet主存储
PARQUET_AS_PRIMARY_STORAGE = True  # Parquet作为主存储，JSON降级为兼容备份
SNAPSHOT_SAVE_JSON_BACKUP = True   # 是否保存JSON兼容备份（默认开启）
PARQUET_COMPRESSION = 'snappy'     # Parquet压缩算法（snappy/gzip/none）
PARQUET_SHARD_BY_EVOL_LEVEL = True # 是否按evol_level分片存储
PARQUET_BATCH_SIZE = 5000          # Parquet分批写入大小
```

#### 1.4 兼容性和回退

1. **数据迁移**：首次启用Parquet主存储时，自动从JSON迁移到Parquet
2. **回退机制**：Parquet损坏或加载失败时，自动回退到JSON
3. **双写过渡期**：前N次保存同时写Parquet和JSON（确保数据安全），确认稳定后JSON变为异步备份
4. **配置开关**：`PARQUET_AS_PRIMARY_STORAGE=False`可关闭Parquet主存储，回退到JSON主存储

**验收标准**：
- Parquet加载时间 < 5秒（当前2.80秒，目标稳定）
- Parquet保存时间 < 10秒（12270节点）
- JSON保存变为可选兼容备份，不阻塞主流程
- 按evol_level分片存储（L1/L2/L3独立文件）
- Parquet损坏时自动回退到JSON
- 配置开关可关闭Parquet主存储，回退到JSON
- 新增测试：Parquet主存储加载测试、保存测试、分片测试、回退测试、兼容性测试

### T2 · P0 冷热分离（L1内存常驻，L2/L3磁盘+缓存）

**债务ID**：P0-冷热分离（当前全部节点都在内存，内存占用随节点数线性增长，100万节点将需要几十GB内存）

**问题描述**：
- 当前所有节点（L1/L2/L3）都常驻内存，12270节点占用约3.3GB内存
- 随着节点数增长，内存占用将线性增长：100万节点约需30-50GB，1000万节点约需300-500GB
- 实际上L2/L3节点访问频率很低，常驻内存是浪费
- L1热节点（约10-20%）访问频率高，应该常驻内存
- 需要冷热分离：L1热节点内存常驻，L2/L3温冷节点磁盘存储+缓存

**修改文件**：
- `nucleus/PulseNodePool.py`（核心修改：冷热分离节点池）
- `nucleus/mnemosyne/PulseSnapshot.py`（冷热节点加载/保存）
- `nucleus/knowledge_access_layer.py`（KAL支持冷热节点透明访问）
- `config.py`（新增冷热分离配置）

**具体修改点**：

#### 2.1 节点池冷热分离架构

1. **节点分类**：
   - L1热节点（evol_level=1）：内存常驻，毫秒级访问
   - L2温节点（evol_level=2）：磁盘存储+LRU缓存，秒级访问
   - L3冷节点（evol_level=3）：磁盘存储+按需加载，分钟级访问

2. **节点池改造**：
   - `_hot_nodes`：L1热节点字典（内存常驻）
   - `_warm_cache`：L2温节点LRU缓存（可配置大小，默认10000节点）
   - `_cold_nodes`：L3冷节点元数据（node_id+文件位置，不加载完整节点）
   - 访问节点时：先查热节点→再查温缓存→最后从磁盘加载冷节点

3. **透明访问**：
   - `get_node(node_id)`：透明访问，自动处理冷热节点加载
   - 冷节点访问时触发异步预加载（加载相关联的节点到缓存）
   - 缓存淘汰：LRU策略，温节点缓存满时淘汰最久未访问的节点

#### 2.2 冷热节点加载/保存

1. **启动加载**：
   - 优先加载L1热节点到内存（快速启动）
   - L2/L3节点只加载元数据（node_id+文件位置），不加载完整节点
   - 后台异步预加载高频访问的L2节点到缓存

2. **保存优化**：
   - L1热节点：高频保存（每10分钟）
   - L2温节点：中频保存（每30分钟）
   - L3冷节点：低频保存（每小时或变更超过阈值时）
   - 变更跟踪：记录每个节点的最后修改时间，只保存有变更的节点

3. **节点升降级**：
   - L2→L1：访问频率超过阈值时，自动升级为L1热节点
   - L1→L2：访问频率低于阈值时，自动降级为L2温节点
   - L2→L3：长期未访问时，自动降级为L3冷节点
   - 升降级是渐进的，避免频繁升降级

#### 2.3 缓存策略

1. **LRU缓存**：
   - 温节点缓存使用LRU（最近最少使用）淘汰策略
   - 缓存大小可配置（默认10000节点，约占内存200-300MB）
   - 缓存命中率监控：定期输出缓存命中率统计

2. **预加载策略**：
   - 访问一个冷节点时，异步预加载其关联节点（linked_nodes）到缓存
   - 高频访问的节点自动提升到热节点
   - 启动时预加载最近24小时访问的节点

3. **内存保护**：
   - 缓存大小有上限，不会无限增长
   - 内存使用率超过阈值（如80%）时，自动缩小缓存
   - OOM保护：内存接近上限时，只保留L1热节点，清空温缓存

#### 2.4 配置项

新增配置：
```python
# 冷热分离
ENABLE_HOT_COLD_SEPARATION = True   # 启用冷热分离
HOT_NODE_LEVELS = [1]                 # 热节点进化层级
WARM_CACHE_SIZE = 10000               # 温节点LRU缓存大小（节点数）
COLD_NODE_LOAD_ON_DEMAND = True       # 冷节点按需加载
NODE_PROMOTION_THRESHOLD = 100        # 节点升级阈值（访问次数）
NODE_DEMOTION_THRESHOLD = 10          # 节点降级阈值（访问次数）
MEMORY_USAGE_WARNING_THRESHOLD = 0.8  # 内存使用率告警阈值
```

**验收标准**：
- L1热节点内存常驻，访问<1ms
- L2温节点缓存访问<10ms，磁盘加载<1秒
- L3冷节点按需加载<5秒
- 内存占用降低50%以上（相比全部节点常驻内存）
- 缓存命中率>80%（温节点缓存）
- 节点升降级机制正常工作
- 内存使用率超过阈值时自动缩小缓存

### T3 · P1 FAISS向量数据库集成（替换暴力余弦计算）

**债务ID**：P1-FAISS向量检索（当前语义检索使用暴力余弦计算，CPU密集，10000节点以上检索变慢）

**问题描述**：
- 当前语义检索使用暴力余弦计算（CPU），逐个计算查询向量与所有节点向量的相似度
- 12270节点时，语义检索Top1000约需100-500ms
- 随着节点数增长，检索时间将线性增长：100万节点约需10-50秒，完全不可用
- 框架已有GPU向量检索加速（GPUCore.py batch_cosine_gpu），但没有使用专业向量数据库
- FAISS是Facebook开源的向量检索库，支持亿级向量毫秒级检索，CPU/GPU都支持

**修改文件**：
- 新增：`nucleus/vector_store/faiss_store.py`（FAISS向量存储封装）
- `nucleus/knowledge_access_layer.py`（KAL语义检索接口对接FAISS）
- `nucleus/fast_ops.py`（向量检索路径修改，优先使用FAISS）
- `config.py`（新增FAISS配置）
- 可能涉及：`nucleus/GPUCore.py`（GPU向量检索与FAISS集成）

**具体修改点**：

#### 3.1 FAISS向量存储封装

1. **FAISS索引构建**：
   - 支持IndexFlatL2（精确搜索，适合小规模）
   - 支持IndexIVFFlat（倒排文件，适合大规模，速度快）
   - 支持IndexHNSWFlat（层次化导航小世界，适合超大规模，内存友好）
   - 索引类型可配置，默认根据节点数自动选择

2. **向量存储接口**：
   - `add_vectors(node_ids, vectors)`：批量添加向量
   - `update_vectors(node_ids, vectors)`：批量更新向量
   - `remove_vectors(node_ids)`：批量删除向量
   - `search(query_vector, top_k)`：语义检索，返回TopK相似节点
   - `save(path)`：保存FAISS索引到磁盘
   - `load(path)`：从磁盘加载FAISS索引

3. **增量更新**：
   - 支持向量的增量添加、更新、删除
   - 索引定期训练（IVF/HNSW索引需要训练）
   - 索引保存到磁盘，启动时快速加载（不需要重新构建）

#### 3.2 KAL语义检索对接

1. **KAL语义检索接口修改**：
   - `semantic_search(query_vector, top_k)`：优先使用FAISS检索
   - FAISS不可用或索引未构建时，回退到暴力余弦计算
   - 检索结果后处理：过滤已删除节点、按相似度排序、返回节点对象

2. **向量编码集成**：
   - 节点的向量编码（当前使用BAAI/bge-small-zh-v1.5，512维）
   - 新节点创建时，自动编码并添加到FAISS索引
   - 节点内容更新时，自动重新编码并更新FAISS索引
   - 节点删除时，自动从FAISS索引移除

3. **GPU加速**：
   - FAISS支持GPU加速（如果有可用GPU）
   - 大规模向量检索时自动使用GPU
   - GPU不可用时自动回退到CPU
   - 与现有GPUCore.py的batch_cosine_gpu方法集成

#### 3.3 性能优化

1. **批量操作**：
   - 向量添加/更新/删除支持批量操作，减少索引更新开销
   - 批量大小可配置（默认1000）
   - 异步更新：向量更新可以异步执行，不阻塞主流程

2. **索引训练**：
   - IVF/HNSW索引需要定期训练（节点数增长到阈值时）
   - 训练在后台线程执行，不阻塞主流程
   - 训练完成后自动切换到新索引

3. **缓存**：
   - 检索结果缓存：相同查询的检索结果缓存（可配置过期时间）
   - 向量缓存：节点向量缓存，避免重复编码

#### 3.4 配置项

新增配置：
```python
# FAISS向量数据库
ENABLE_FAISS_VECTOR_STORE = True    # 启用FAISS向量存储
FAISS_INDEX_TYPE = 'auto'           # 索引类型（auto/FlatL2/IVFFlat/HNSWFlat）
FAISS_INDEX_PATH = 'data/knowledge/faiss/index.faiss'  # FAISS索引保存路径
FAISS_BATCH_SIZE = 1000             # FAISS批量操作大小
```

### T8 · P2 胃模块JSON容错解析增强（大模型输出格式不规范修复）

**债务ID**：P2-401 胃模块JSON解析失败（大模型输出格式不规范，已从"观察中"升级为"待修复"）

**问题描述**：

- 频率：约每12分钟1次，偶发但持续存在
- 影响：代码分析结果无法解析，这部分知识无法消化到知识库，长期积累影响知识库完整性

**详细根因**：
大模型返回的JSON格式不规范，典型错误模式：
```json
{
  "功能": "...",
  "关键步骤": ["...", "..."],
  "依赖的外部数据": [          // ← 声明为数组 [ ]
    "_search_topic_guard_enabled": "一个用于判断...",  // ← 但数组里放了键值对！
    "_SEARCH_PREFIX_ALT_NEW": "..."
  ]
}
```
**根因**：`"依赖的外部数据"` 声明为数组 `[ ]`，但数组里面放的是键值对 `"key": "value"`，这在标准JSON中是非法的。

**胃模块现有解析策略的不足**：
- 策略1：直接json.loads（遇到格式错误直接失败）
- 策略2：正则提取（从markdown代码块中提取JSON字符串后再解析，同样遇到格式错误失败）
- 所有策略都是"提取JSON字符串后直接解析"，**没有容错修复能力**

**修改文件**：
- `nucleus/PulseStomach.py`（核心修改：JSON容错解析）
- 可能涉及：大模型调用prompt优化
- `config.py`（新增JSON容错解析配置）

**具体修改点**：

#### 8.1 JSON容错解析增强（核心）

1. **自动检测并修复常见格式错误**：
   - 数组中放键值对 → 自动转换为对象（`[ "key": "value" ]` → `{ "key": "value" }`）
   - 缺少逗号 → 自动补全（在`}`、`]`、`"`后自动补逗号）
   - 单引号 → 转换为双引号（`'key'` → `"key"`）
   - 尾随逗号 → 自动删除（`[1, 2, 3,]` → `[1, 2, 3]`）
   - 未转义的特殊字符 → 自动转义

2. **使用容错JSON库**：
   - 优先使用`json5`库（能处理大部分不规范JSON格式）
   - 备选`demjson3`库（更宽松的JSON解析）
   - 容错库不可用时，回退到自定义修复逻辑

3. **多策略解析顺序优化**：
   - 策略1：直接json.loads（标准JSON，最快）
   - 策略2：正则提取+json.loads（从markdown代码块提取）
   - **策略3（新增）：正则提取+json5/demjson3容错解析**
   - **策略4（新增）：正则提取+自定义格式修复+json.loads**
   - **策略5（新增）：降级处理（提取关键字段，部分消化）**

#### 8.2 解析失败时降级处理

1. **关键字段提取**：
   - 即使JSON解析完全失败，也尝试用正则提取关键字段
   - 提取"功能"、"关键步骤"、"依赖的外部数据"等字段
   - 提取到的字段用于部分知识消化（不丢弃全部内容）

2. **失败记录和重试**：
   - 记录解析失败的原文（用于后续分析和优化prompt）
   - 失败的代码分析任务可以稍后重试（用不同的prompt或不同的大模型）
   - 失败率统计：按大模型渠道、任务类型统计

1. **明确JSON格式要求**：
