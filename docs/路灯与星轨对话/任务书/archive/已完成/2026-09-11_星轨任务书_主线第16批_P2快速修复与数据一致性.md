## 一、任务1：搜索主题被上游截断修复（P2-104，最优先，根因已定位）

### 问题描述

用户输入"查一下人工智能最新进展"，框架日志显示：
```
检测到明确搜索请求: '下人工智能最新进展'
```
前两字"查一"被错误截掉，"下"保留在主题开头。这是第15批T4关键词碎片（"下人工智""能最新进"）的**第一因**——主题被截断后，下游的2~4字贪婪窗口切分才会产出碎片。第15批已删除贪婪窗口，但上游截断问题仍存在。

### 根因（已定位，星轨实测）

**文件**: `organs/brain/PulseInnerWorld.py`，第547行

```python
_search_topic = re.sub(
    r'^(搜索[一下]?|查[一下]?|帮我[找查]|查找[一下]?|搜一下|百度[一下]?|谷歌[一下]?|上网查)\s*',
    '', question.strip()
)
```

**问题**: 正则字符类`[一下]?`只匹配**单个字符**（"一"或"下"），不匹配"一下"两个字。
- 用户输入"查一下人工智能最新进展"
- `查[一下]?` 匹配 "查一"（`[一下]?`取了"一"）
- `\s*` 匹配0个空白
- 剩余 "下人工智能最新进展"
- 结果："查一"被去掉，"下"残留

**正确写法**: 用分组`(一下)?`替代字符类`[一下]?`，或用`(一下|下)?`匹配"一下"或"下"。

### 修改要求

**文件**: `organs/brain/PulseInnerWorld.py`（第544-560行附近的搜索请求检测块）

1. **修正正则**: 将所有`[一下]?`改为`(一下|下)?`或`(一下)?`，确保"查一下""搜索一下""百度一下"等能完整匹配前缀
2. **全面排查**: 检查文件中其他类似的前缀去除正则，是否存在同样的字符类误用
3. **添加防御**: 截断后检查`_search_topic`是否以"下""一""的"等单字噪声开头，如果是则进一步剥离
4. **添加单元测试**: 覆盖"查一下XX""搜索一下XX""百度一下XX""查XX""搜XX"等多种前缀形态

### 灰度开关

```python
ENABLE_SEARCH_TOPIC_GUARD = True  # 总开关，关闭时退回原正则
```

### 验收标准

- 输入"查一下人工智能最新进展" → 搜索主题为"人工智能最新进展"（不含"下"）
- 输入"搜索一下今天天气" → 搜索主题为"今天天气"

## 二、任务2：FrequencyCodec Cython模块重复加载（P2-94）

### 问题描述

日志中FrequencyCodec的Cython加速模块`encode_cy`重复加载70+次。每次加载都有日志输出，说明模块没有被正确缓存，每次调用`encode_batch`时都重新导入/初始化Cython模块，造成性能浪费。

### 线索

**文件**: `nucleus/pulse/FrequencyCodec.py`
- 第80行: `# v18.0: Cython加速标记（首次加载时输出日志）`

**可能根因**:
1. Cython模块的导入在函数内部（每次调用都重新import）
2. 模块级缓存变量没有正确保持（每次调用都重置为None）
3. 多进程/多线程环境下，每个子进程都独立加载一次（如果是子进程加载则是正常的，需要区分）

3. **添加加载计数**: 记录Cython模块的实际加载次数，超过阈值（如3次）时打WARNING
4. **区分日志**: 主进程加载打INFO，子进程加载打DEBUG（避免日志刷屏）


- 主进程启动后Cython模块只加载1次（INFO日志只出现1次）
- 子进程加载打DEBUG（不刷屏）
- `encode_batch`调用性能不下降（与修复前持平或更好）

### 线索

**可能根因**:
1. 快照文件路径错误（加载了空文件或错误文件）
2. 快照格式版本不兼容（旧格式快照无法被新加载器解析）
3. 节点数据在保存时被过滤/截断（如信任分阈值过滤掉了所有节点）
4. 加载时的反序列化失败但被静默吞掉（只返回空列表）

## 五、任务5：InfoField L3层队列背压优化（P2-100）

### 问题描述

InfoField的L3层队列频繁满（34次背压），导致消息被丢弃或延迟处理。L3层是最低优先级的队列（后台学习/非关键消息），队列满时的背压机制会丢弃新消息或阻塞发送方。

### 线索

**文件**: `nucleus/field/InfoField.py`
- 第13批已修复P2-87（池重建并发计数泄漏），新增了`_layer_organ_inflight`按层按器官在途计数
- L3队列上限100（日志中可见`L3=100`）
- 背压机制：分层队列上限，L0=无上限（生命线），L1=500（软），L2=200，L3=100

**可能根因**:
1. L3消费者处理速度跟不上生产速度（L3 worker数量不足或处理逻辑太慢）
2. L3消息中有大量低价值/重复消息（应该在生产端过滤）
3. 动态扩缩容不及时（队列满了才扩容，扩容有延迟）
4. 某些L3消息处理时阻塞（如IO操作、LLM调用），导致worker被占用

### 修改要求

**文件**: `nucleus/field/InfoField.py`

1. **根因定位**: 添加L3队列的详细统计——生产速率、消费速率、队列深度时间序列、消息类型分布、worker利用率
2. **生产端过滤**: 在L3消息入队前添加轻量级过滤——重复消息（幂等去重已存在）、低价值消息（如纯DEBUG级别的状态汇报）直接丢弃或降级为计数
3. **动态扩缩容优化**: 队列深度达到80%时提前扩容（而不是满了才扩），扩容后持续观察30秒再决定是否缩容（避免震荡）
4. **L3消息批处理**: 如果L3消息是可批量处理的类型（如统计上报），攒批处理（每10条或每5秒处理一批），减少worker占用时间
5. **添加背压告警**: L3队列连续3次满时打WARNING（当前可能只有DEBUG），便于观察

### 灰度开关

```python
ENABLE_L3_BACKPRESSURE_OPTIMIZE = True  # L3背压优化开关
L3_QUEUE_EARLY_EXPAND_RATIO = 0.8       # 提前扩容阈值
L3_BATCH_SIZE = 10                        # 批处理大小
```

### 验收标准

- L3队列满的次数下降（目标：从34次/12h降至10次/12h以下）
- 提前扩容生效（队列深度达80%时扩容，而不是满了才扩）
- 生产端过滤生效（低价值消息不占队列）
- 背压告警可观测（连续满3次打WARNING）
- 不影响L0/L1/L2的正常消息处理
- 开关关闭时退回原行为（零回归）
