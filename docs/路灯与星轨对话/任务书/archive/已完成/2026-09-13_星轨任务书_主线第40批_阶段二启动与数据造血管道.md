### T1（P0）LLM调用全程留存管道·数据结构与存储层

**债务编号**：P0-254  
**预估工时**：1-2h  
**优先级**：🔴 最高（内在模型一切的燃料源头）

**背景**：第三方评估实测，当前LLM调用留存率仅2.4%（2103次调用仅保存50对输入输出），内在模型五个模型全部"没有米下锅"。

**任务内容**：
1. 新建 `nucleus/llm/call_recorder.py` 模块
2. 定义数据结构：
   ```python
   {
     "ts": float,              # 时间戳
     "origin": str,            # user_query / system_internal / evolution_task / digestion
     "prompt": str,            # 完整prompt
     "response": str,          # 完整response
     "prompt_version": str,    # prompt模板版本
     "channel": str,           # deepseek / zhipu / volcano / ark
     "model": str,             # 具体模型名
     "duration": float,        # 耗时秒
     "tokens": int,            # token数
     "status": str,            # success / failed / timeout
     "feedback": str | None    # 下游反馈（采纳/拒绝/用户重问），后续回填
   }
   ```
3. 存储层：JSONL追加写入 `data/llm_traces/calls_YYYYMMDD.jsonl`
4. 敏感数据过滤：复用现有脱敏器（PulseCodeSandbox.py:55-65），剔除凭证/密钥模式
5. 滚动窗口：保留90天热数据，更旧的归档压缩（与知识备份策略合并）

**验收标准**：
- ✅ `call_recorder.py` 模块可正常导入
- ✅ 单元测试：构造10条模拟调用，验证落盘格式正确、敏感数据被过滤
- ✅ 单元测试：验证origin标记四类全覆盖
- ✅ 单元测试：验证90天滚动窗口逻辑
- ✅ ruff F=0，E402零新增
- ✅ **无需重启框架**（纯新建模块+单元测试）

**风险提示**：
- 存储路径 `data/llm_traces/` 需确保目录存在
- JSONL追加写入需考虑并发安全（框架多线程环境）

### T2（P0）LLM调用全程留存管道·PulseLung埋点 + 依赖度埋点补全

**债务编号**：P0-254 + P0-262  
**预估工时**：3-4h  
**优先级**：🔴 最高

**背景**：路灯技术细研发现致命问题——当前"大模型依赖度97%"指标中，对话类调用SCENE_LUNG=0（全库无埋点），98.8%来自自主进化循环。这导致依赖度指标无法反映真实对话场景，所有基于该指标的目标都是"错的靶子"。本任务同时完成两件事：①LLM调用对留存（训练数据造血）②补全对话出口依赖度埋点（修正指标口径）。

**任务内容**：
1. 在 `PulseLung._call_via_channels()` 出入口埋点（LLM调用对留存）：
   - 调用前：记录prompt、channel、model、start_time
   - 调用后：记录response、duration、tokens、status
   - 调用失败：记录错误信息、status=failed/timeout
2. origin标记传递：
   - 对话入口 → `user_query`
   - 自主进化 → `evolution_task`
   - 知识消化 → `digestion`
   - 系统内部（自检/监控）→ `system_internal`
   - 调用方通过参数传入，CallRecorder不做猜测
3. **★新增：补全依赖度埋点（P0-262）**：
   - 在 `PulseLung._call_via_channels()` 或 `_call_channel()` 增加 `record_llm_call(SCENE_LUNG)`
   - 参考现有4处埋点位置（`nucleus/evolution/LLMEvolutionEngine.py:45`、`SelfReflectionEngine.py:35`、`SafeEvolutionExecutor.py:722`、`PulseSemanticComprehension.py:574`）
   - 确保对话出口的每次LLM调用都被计入依赖度指标
   - 埋点后重算基线，得到真实的"对话/进化/学习"三分占比
4. 反馈钩子接口（预留，本批不实现回填逻辑）：
   - `record_feedback(trace_id, feedback)` 方法
   - 关键消费者（cortex路由、补丁验证器）后续接入

**验收标准**：
- ✅ 单元测试：mock PulseLung调用，验证CallRecorder被正确调用
- ✅ 单元测试：验证四类origin标记正确传递
- ✅ 单元测试：验证失败/超时场景也被记录
- ✅ **单元测试：验证SCENE_LUNG埋点被正确调用（对话出口计数>0）**
- ✅ **代码审查：依赖度埋点与现有4处埋点风格一致，不重复计数**
- ✅ 代码审查：埋点不影响现有调用逻辑（try/except包裹，记录失败不影响主流程）
- ✅ ruff F=0，E402零新增
- ✅ **无需重启框架**（单元测试mock验证）

**风险提示**：
- 埋点必须用try/except包裹，记录器故障绝不能影响主推理流程
- 大response（如深度思考输出）可能导致JSONL文件膨胀，需考虑截断或压缩（可配置）
- **依赖度埋点需注意不与进化循环的埋点重复计数**：对话出口只记SCENE_LUNG，进化路径已有SCENE_EVOLUTION
