## 二、任务清单

### T1 · P0 冷热分离（L1热节点内存常驻，L2/L3磁盘+缓存）

**债务ID**：P0-冷热分离（第68批T2延续，当前全部节点都在内存，12295节点占用约3.3GB，100万节点将需30-50GB）

**问题描述**：
- 当前所有节点（L1/L2/L3）都常驻内存，12295节点占用约3.3GB
- 随着节点数增长，内存占用线性增长：100万节点约需30-50GB，完全不可扩展
- L2/L3节点访问频率很低，常驻内存是浪费
- 第68批T1已完成Parquet主存储，为冷热分离奠定了数据层基础

**修改文件**：
- `nucleus/mnemosyne/PulseNodePool.py`（核心修改：三层节点池架构）
- `nucleus/mnemosyne/PulseSnapshot.py`（冷热节点加载/保存）
- `nucleus/knowledge_access_layer.py`（KAL支持冷热节点透明访问）
- `config.py`（新增冷热分离配置）

**具体修改点**：

#### 1.1 节点池三层架构

1. **节点分类**：
   - L1热节点（evol_level=1）：内存常驻，毫秒级访问
   - L2温节点（evol_level=2）：磁盘存储+LRU缓存，秒级访问
   - L3冷节点（evol_level=3）：磁盘存储+按需加载，分钟级访问

2. **节点池改造**：
   - `_hot_nodes`：L1热节点字典（内存常驻）
   - `_warm_cache`：L2温节点LRU缓存（可配置大小，默认10000节点）
   - `_cold_nodes`：L3冷节点元数据（node_id+文件位置，不加载完整节点）
   - `get_node(node_id)`：透明访问，自动处理冷热节点加载

3. **透明访问**：
   - 访问节点时：先查热节点→再查温缓存→最后从Parquet磁盘加载冷节点
   - 冷节点访问时触发异步预加载（加载关联节点到缓存）
   - 缓存淘汰：LRU策略，温节点缓存满时淘汰最久未访问的节点

#### 1.2 冷热节点加载/保存

1. **启动加载**：
   - 优先加载L1热节点到内存（快速启动）
   - L2/L3节点只加载元数据（node_id+evol_level+文件位置），不加载完整节点
   - 后台异步预加载高频访问的L2节点到缓存

2. **保存优化**：
   - L1热节点：高频保存（每10分钟）
   - L2温节点：中频保存（每30分钟）
   - L3冷节点：低频保存（每小时或变更超过阈值时）
   - 变更跟踪：记录每个节点的最后修改时间，只保存有变更的节点

3. **节点升降级**：
   - L2→L1：访问频率超过阈值时，自动升级为L1热节点
   - L1→L2：访问频率低于阈值时，自动降级为L2温节点
   - L2→L3：长期未访问时，自动降级为L3冷节点
   - 升降级是渐进的，避免频繁升降级

#### 1.3 缓存策略

1. **LRU缓存**：
   - 温节点缓存使用LRU（最近最少使用）淘汰策略
   - 缓存大小可配置（默认10000节点，约占内存200-300MB）
   - 缓存命中率监控：定期输出缓存命中率统计

2. **预加载策略**：
   - 访问一个冷节点时，异步预加载其关联节点（linked_nodes）到缓存
   - 高频访问的节点自动提升到热节点
   - 启动时预加载最近24小时访问的节点

3. **内存保护**：
   - 缓存大小有上限，不会无限增长
   - 内存使用率超过阈值（如80%）时，自动缩小缓存
   - OOM保护：内存接近上限时，只保留L1热节点，清空温缓存

#### 1.4 配置项

新增配置：
```python
# 冷热分离
ENABLE_HOT_COLD_SEPARATION = True   # 启用冷热分离
HOT_NODE_LEVELS = [1]                 # 热节点进化层级
WARM_CACHE_SIZE = 10000               # 温节点LRU缓存大小（节点数）
COLD_NODE_LOAD_ON_DEMAND = True       # 冷节点按需加载
NODE_PROMOTION_THRESHOLD = 100        # 节点升级阈值（访问次数）
NODE_DEMOTION_THRESHOLD = 10          # 节点降级阈值（访问次数）
MEMORY_USAGE_WARNING_THRESHOLD = 0.8  # 内存使用率告警阈值
```

**验收标准**：
- L1热节点内存常驻，访问<1ms
- L2温节点缓存访问<10ms，磁盘加载<1秒
- L3冷节点按需加载<5秒
- 内存占用降低50%以上（相比全部节点常驻内存）
- 缓存命中率>80%（温节点缓存）
- 节点升降级机制正常工作
- 内存使用率超过阈值时自动缩小缓存
- 新增测试：冷热分离加载测试、缓存测试、节点升降级测试、内存保护测试

### T2 · P1 FAISS向量数据库集成（安装faiss-cpu + 替换暴力余弦计算）

**债务ID**：P1-FAISS向量检索（第68批T3延续，硬阻断已解除——星轨已批准安装faiss-cpu）

**前置条件**：
- 先执行 `pip install faiss-cpu`（星轨已批准，纯Python包，无系统级依赖）
- 验证 `import faiss` 成功

**问题描述**：
- 当前语义检索使用暴力余弦计算（CPU），逐个计算查询向量与所有节点向量的相似度
- 12295节点时，语义检索Top1000约需100-500ms
- 随着节点数增长，检索时间线性增长：100万节点约需10-50秒，完全不可用
- 第68批已落全部配置与KAL回退路径（暴力余弦仍正常），但faiss未安装导致无法真正集成

**修改文件**：
- 新增：`nucleus/vector_store/faiss_store.py`（FAISS向量存储封装）
- `nucleus/knowledge_access_layer.py`（KAL语义检索接口对接FAISS）
- `nucleus/fast_ops.py`（向量检索路径修改，优先使用FAISS）
- `config.py`（FAISS配置，第68批已落，本批验证生效）
- 可能涉及：`nucleus/GPUCore.py`（GPU向量检索与FAISS集成）

**具体修改点**：

#### 2.1 安装faiss-cpu

1. 执行 `pip install faiss-cpu`
2. 验证 `import faiss` 成功，输出版本号
3. 如果安装失败，记录错误并回退到暴力余弦（不阻断其他任务）

#### 2.2 FAISS向量存储封装

1. **FAISS索引构建**：
   - 支持IndexFlatL2（精确搜索，适合小规模<10万）
   - 支持IndexIVFFlat（倒排文件，适合大规模，速度快）
   - 索引类型可配置，默认根据节点数自动选择（<10万用FlatL2，>=10万用IVFFlat）

2. **向量存储接口**：
   - `add_vectors(node_ids, vectors)`：批量添加向量
   - `update_vectors(node_ids, vectors)`：批量更新向量
   - `remove_vectors(node_ids)`：批量删除向量
   - `search(query_vector, top_k)`：语义检索，返回TopK相似节点
   - `save(path)`：保存FAISS索引到磁盘
   - `load(path)`：从磁盘加载FAISS索引

3. **增量更新**：
   - 支持向量的增量添加、更新、删除
   - IVF索引定期训练（节点数增长到阈值时）
   - 索引保存到磁盘，启动时快速加载（不需要重新构建）

#### 2.3 KAL语义检索对接

1. **KAL语义检索接口修改**：
   - `semantic_search(query_vector, top_k)`：优先使用FAISS检索
   - FAISS不可用或索引未构建时，回退到暴力余弦计算
   - 检索结果后处理：过滤已删除节点、按相似度排序、返回节点对象

2. **向量编码集成**：
   - 节点的向量编码（当前使用BAAI/bge-small-zh-v1.5，512维）
   - 新节点创建时，自动编码并添加到FAISS索引
   - 节点内容更新时，自动重新编码并更新FAISS索引
   - 节点删除时，自动从FAISS索引移除

3. **索引初始化**：
   - 框架启动时，从Parquet加载所有节点向量，构建FAISS索引
   - 索引构建在后台线程执行，不阻塞启动
   - 索引构建完成前，语义检索回退到暴力余弦

#### 2.4 性能优化

1. **批量操作**：
   - 向量添加/更新/删除支持批量操作，减少索引更新开销
   - 批量大小可配置（默认1000）
   - 异步更新：向量更新可以异步执行，不阻塞主流程

2. **索引训练**：
   - IVF索引需要定期训练（节点数增长到阈值时）
   - 训练在后台线程执行，不阻塞主流程
   - 训练完成后自动切换到新索引

3. **缓存**：
   - 检索结果缓存：相同查询的检索结果缓存（可配置过期时间）
   - 向量缓存：节点向量缓存，避免重复编码

#### 2.5 配置项（第68批已落，本批验证生效）

```python
# FAISS向量数据库
ENABLE_FAISS_VECTOR_STORE = True    # 启用FAISS向量存储
FAISS_INDEX_TYPE = 'auto'           # 索引类型（auto/FlatL2/IVFFlat）
FAISS_INDEX_PATH = 'data/knowledge/faiss/index.faiss'  # FAISS索引保存路径
FAISS_BATCH_SIZE = 1000             # FAISS批量操作大小
FAISS_USE_GPU = False               # 是否使用GPU加速（faiss-cpu不支持GPU，默认False）
FAISS_TRAIN_THRESHOLD = 10000       # IVF索引训练阈值（节点数）
FAISS_SEARCH_CACHE_SIZE = 1000      # 检索结果缓存大小
VECTOR_DIMENSION = 512               # 向量维度（bge-small-zh-v1.5）
```

**验收标准**：
- faiss-cpu安装成功，`import faiss`正常

**具体修改点**：

#### 4.1 KAL依赖注入

1. **框架启动时初始化KAL**：

   - `get_kal(node_pool=node_pool, snapshot=snapshot)`

2. **模块获取KAL实例**：
   - 模块通过`get_kal()`获取KAL单例
   - 不需要直接访问PulseSnapshot或PulseNodePool

#### 4.2 模块迁移（先迁移读取频率高、逻辑简单的模块）

1. **胃模块知识消化**：
   - 查询节点：使用`kal.get_node(node_id)`替代直接访问node_pool
   - 关键词搜索：使用`kal.search_by_keywords(keywords, top_k)`替代直接遍历
   - 按路径搜索：使用`kal.search_by_path(path_prefix)`替代直接遍历

2. **肝模块**：
   - 查询节点：使用KAL
   - 统计节点：使用`kal.get_node_count()`和`kal.get_node_count_by_evol_level()`

3. **肾模块**：
   - 查询节点：使用KAL
   - 按进化层级搜索：使用`kal.search_by_evol_level(evol_level)`

#### 4.3 迁移原则

1. **渐进式迁移**：
   - 先迁移读取操作（get_node、search），不迁移写入操作
   - 先迁移逻辑简单的模块，不迁移逻辑复杂的模块
   - 每个模块迁移后充分测试，确认无回归

2. **双轨过渡期**：
   - 迁移后的模块同时支持KAL和直接访问（配置开关）
   - `ENABLE_KAL_MIGRATION=True`时使用KAL，`False`时回退到直接访问
   - 确认KAL稳定后，移除直接访问代码

3. **性能对比**：
   - 迁移前后对比性能（查询时间、CPU占用、内存占用）
   - 确认KAL性能不低于直接访问（KAL有LRU缓存，应该更快）
