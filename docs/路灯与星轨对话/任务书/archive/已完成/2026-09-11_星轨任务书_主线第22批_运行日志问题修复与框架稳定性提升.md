## 三、6项任务明细

### T1：PulseStomach JSON解析增强修复（核心）

**文件**：`organs/body/PulseStomach.py`

**功能**：
1. **新增策略3：JSON自动修复**：
   - 在策略1（直接解析）和策略2（正则/括号提取）之后，新增策略3
   - 策略3尝试自动修复常见JSON格式错误：
     - 缺少冒号：`"key" value` → `"key": value`
     - 缺少逗号：`"key1": v1 "key2": v2` → `"key1": v1, "key2": v2`
     - 尾随逗号：`[1, 2, 3,]` → `[1, 2, 3]`
     - 单引号：`'key': 'value'` → `"key": "value"`
     - 未转义引号：`"key": "value "quoted" end"` → 尝试转义内部引号
   - 修复后再次尝试`json.loads()`，成功则使用修复后的结果
2. **日志去重**：
   - 同一条内容的多次解析失败只记录1次WARNING（用内容哈希做去重，60秒窗口）
   - 策略1失败降为DEBUG（因为大部分内容不是纯JSON，策略1失败是正常的）
   - 只保留策略2/策略3失败的WARNING
3. **失败统计**：
   - 新增`_json_parse_failures`计数器（按错误类型分类）
   - 每100次消化输出1次统计摘要（INFO级别）："JSON解析统计：成功X次/失败Y次（冒号缺失Z次/逗号缺失W次）"

**异常处理**：
- 策略3修复失败 → 记录WARNING，保留原始内容（与现有行为一致）
- 自动修复不得改变JSON的语义（只修复格式，不改变内容）

### T2：ReasoningWorkerPool进程池重建失败排查与修复

**文件**：`nucleus/reasoning/ReasoningWorkerPool.py`

**功能**：
1. **排查"模拟重建失败"根因**：
   - 搜索代码中"模拟重建失败"的来源
   - 确认是测试环境的模拟还是真实故障
   - 如果是模拟，移除模拟代码或添加生产环境判断
   - 如果是真实故障，修复进程池创建逻辑
2. **增强进程池重建的错误处理**：
   - 重建失败时记录更详细的错误信息（错误类型、错误消息、系统资源状态）
   - 添加指数退避重试（第1次失败等1s，第2次等2s，第3次等4s）
   - 降级为同步执行前尝试最后一次重建（用最小配置：1个worker）
3. **降级状态监控**：
   - 降级为同步执行后，每隔5分钟尝试1次恢复进程池
   - 恢复成功后输出INFO："推理进程池已恢复（worker=N）"
   - 恢复失败保持降级状态，不重复输出ERROR

**异常处理**：
- 进程池创建失败 → 记录详细ERROR + 指数退避重试
- 连续3次失败 → 降级为同步执行 + 记录WARNING（不是ERROR，因为功能保持可用）
- 降级后恢复失败 → 记录DEBUG（不重复告警）

### T4：SafeEvolutionExecutor修复蒸馏空片段修复

**文件**：`nucleus/reasoning/SafeEvolutionExecutor.py`

**功能**：
1. **排查代码片段为空的根因**：
   - 分析ERROR日志的代码片段提取逻辑
   - 确认是ERROR日志格式问题（如ReasoningWorkerPool的ERROR没有关联具体文件/行号）还是提取逻辑问题
2. **增强代码片段提取**：
   - ERROR日志有关联文件和行号 → 从文件中读取代码片段
   - ERROR日志无关联文件/行号 → 尝试从错误消息中提取文件名和行号
   - 仍然无法提取 → 记录DEBUG："无法提取代码片段，跳过修复蒸馏"（不是空片段静默跳过）
3. **修复蒸馏逻辑优化**：
   - 代码片段为空时，不跳过LLM对比，而是用ERROR消息本身作为对比输入
   - 如果ERROR消息也为空，才跳过并记录DEBUG

**异常处理**：
- 文件读取失败 → 记录DEBUG，用ERROR消息作为对比输入
- LLM对比失败 → 记录DEBUG，不影响主流程

## 五、风险与注意事项

1. **JSON自动修复的安全性**：自动修复可能改变JSON语义，必须只修复格式错误（冒号/逗号/引号），不得改变内容。修复后应验证解析结果的关键字段是否完整。
2. **进程池重建的"模拟失败"**：需要先确认是测试模拟还是真实故障。如果是测试模拟，移除模拟代码；如果是真实故障，修复创建逻辑。不得盲目修改。
3. **测试隔离的兼容性**：修改verify脚本的测试路径时，不得破坏现有测试用例。所有测试必须仍然通过。
4. **日志级别变更的影响**：降级WARNING为DEBUG后，可能会影响依赖这些日志的监控或告警。需确认没有其他模块依赖这些日志。
5. **不修改大模型调用逻辑**：JSON格式问题是大模型返回的，不是调用问题。不得修改大模型的prompt或调用参数（除非有明确证据表明prompt有问题）。
