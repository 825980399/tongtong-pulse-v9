### T1（P2） P2-238 .log扩展名白名单豁免真问题

**预估工时**：1-2小时
**需重启框架验证**：否（可通过单元测试验证）

**任务描述**：
第38批T5的扩展名白名单默认排除`.log`，但这导致`logs/pulse_crash.log`（6.49MB，源码有产出方、无消费方的真问题）被排除，有效无消费从4降到3。需实现"扩展名白名单不作用于源码产出方命中的路径"的豁免机制。

**具体要求**：
1. 在`ProductionConsumptionMatcher._finalize()`中，扩展名白名单排除前增加判断：
   - 如果该路径在源码通道中有产出方（`has_producer=True`或`producer_calls`非空），则**不应用扩展名白名单排除**
   - 即：真问题（写了没人读）即使扩展名是.log，也应保留在no_consumer中
2. 排除原因`exclude_reason`增加区分：
   - `ext_whitelist`：扩展名白名单排除（仅对无源码产出方的路径）
   - `ext_whitelist_exempted`：扩展名白名单豁免（有源码产出方，保留）
3. 报告中显示豁免统计："扩展名白名单豁免X个真问题"
4. 验证：`logs/pulse_crash.log`应出现在有效无消费中（不再被排除）
5. 增加单元测试：构造有源码产出方的.log路径和无源码产出方的.log路径，验证前者被豁免、后者被排除

**验收标准**：
- [ ] 有源码产出方的.log路径不被扩展名白名单排除
- [ ] 无源码产出方的.log路径仍被正常排除
- [ ] 排除原因区分ext_whitelist和ext_whitelist_exempted
- [ ] 报告中显示豁免统计
- [ ] logs/pulse_crash.log出现在有效无消费中
- [ ] 单元测试：两种路径的正确分类
- [ ] pytest全量通过（基线1175+新增）
- [ ] ruff F=0，E402新增0

**风险提示**：
- 豁免逻辑需精确，避免误豁免其他扩展名（.md/.txt）的真问题
- 性能：豁免判断在_finalize中，需确保不影响整体性能

**具体要求**：
1. 在`SafeEvolutionExecutor`中新增公共方法`get_evolution_stats()`，返回：

   - `failed_patches`：失败数
   - `rolled_back_patches`：回滚数
   - `success_rate`：成功率
   - `rollback_rate`：回滚率
   - `crash_count`：子进程崩溃数（从get_crash_stats()获取）

2. 方法应为**只读**，不触发任何副作用（不调用verify_applied_patches/rollback/apply）
3. 修改`integrate_evolution_health()`，改用`get_evolution_stats()`替代私有属性访问
4. 保持向后兼容：如果get_evolution_stats()不可用，回退到原有逻辑（带WARNING日志）
5. 增加单元测试：mock SafeEvolutionExecutor，验证get_evolution_stats()返回正确数据

**验收标准**：

- [ ] 方法只读，无副作用

- [ ] 向后兼容（公共接口不可用时回退）

### T4（P3） P2-241 top_issues各维度severity语义对齐

**预估工时**：1-2小时
**需重启框架验证**：否（可通过单元测试验证）

**任务描述**：
第38批T1的`top_issues`从各维度收集issues并按severity排序，但各维度的severity语义不完全对齐：
- knowledge_health：用`top_issues`，severity为error/high/warning/medium/low
- fake_loops：用`critical`，severity为critical/high/medium/low
- code_health：用`by_severity`汇总，只有汇总无逐条明细
- evolution_health：用`issues`，severity为high/medium/low/info

需统一各维度的severity语义，确保top_issues排序准确。

**具体要求**：
1. 定义统一的severity等级（5级）：
   - `critical`（致命）：系统不可用/数据丢失
   - `high`（严重）：核心功能受损/安全风险
   - `medium`（中等）：功能受限/性能问题
   - `low`（轻微）：体验问题/小缺陷
   - `info`（信息）：提示/建议/无数据
2. 为各维度增加severity归一化适配层（`_normalize_severity()`）：
   - knowledge_health：error→critical，其余保持
   - fake_loops：critical保持，其余保持
   - code_health：从by_severity汇总中提取逐条issue（如果可能），或保持汇总但标记为"汇总型"
   - evolution_health：保持high/medium/low/info
3. `_collect_top_issues()`使用归一化后的severity排序
4. 报告中top_issues显示统一的severity标签
5. 增加单元测试：构造各维度不同severity的issue，验证排序正确

**验收标准**：
- [ ] 定义统一的5级severity（critical/high/medium/low/info）
- [ ] 各维度增加severity归一化适配层
- [ ] top_issues使用归一化severity排序
- [ ] 报告中显示统一的severity标签
- [ ] 单元测试：各维度severity归一化和排序验证
- [ ] pytest全量通过，ruff F=0

**风险提示**：
- code_health的by_severity汇总可能无法提取逐条issue，保守策略是保持汇总但标记为"汇总型"，不强行拆分
- severity归一化需确保不丢失原始信息（可在issue中保留original_severity字段）
