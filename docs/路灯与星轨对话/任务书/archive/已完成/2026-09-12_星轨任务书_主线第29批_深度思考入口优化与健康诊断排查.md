**优先级**：P2
**预估工时**：3-4小时
**问题背景**：第27批T1（深度思考超时保护）端到端验证时发现，高复杂度长问题被`_detect_multi_step_task → multi_step_execute`接走（复杂度仅0.5），`_deep_think`从未进入。导致深度思考类修复（如第27批T1超时保护）缺少可复现的端到端入口，无法验证修复效果。

**任务内容**：
1. **路由分析**：
   - 分析`_detect_multi_step_task`的判断逻辑和阈值
   - 分析`multi_step_execute`与`_deep_think`的适用场景差异
   - 定位为什么高复杂度长问题被路由到`multi_step_execute`而非`_deep_think`
2. **路由优化**：
   - 调整路由优先级或判断条件，确保需要深度思考的问题能进入`_deep_think`路径
   - 或在`multi_step_execute`中增加深度思考的调用入口
   - 保持现有简单问题的快速回复路径不受影响
3. **配置化**：
   - 将路由阈值提取为config配置项（如`DEEP_THINK_COMPLEXITY_THRESHOLD`）
   - 灰度开关（`ENABLE_DEEP_THINK_ROUTING_OPTIMIZATION`，默认True）
4. **验证**：
   - 构造高复杂度长问题，确认能进入`_deep_think`路径
   - 确认简单问题仍然走快速回复路径
   - 确认第27批T1的超时保护能被触发和验证

**验收标准**：
- [ ] 路由根因定位明确
- [ ] 路由优化方案实施，配置项已提取到config.py
- [ ] 灰度开关默认True，关闭后回退到原行为

- [ ] pytest新增路由相关测试用例≥5例
- [ ] 第27批T1超时保护能被端到端验证

**注意事项**：
- 不要修改_deep_think的核心逻辑，只优化入口路由
- 不要影响简单问题的快速回复

### T4：日志格式统一与日志级别修正 ✅ 无需重启

**优先级**：P3
**预估工时**：1-2小时
**问题背景**：日志分析发现，SafeEvolutionExecutor的DEBUG级别日志（如"修复蒸馏"）被标注为ERROR，导致日志统计时ERROR数量虚高。同时，各器官的日志格式不完全统一，影响日志分析效率。

**任务内容**：
1. **日志级别修正**：
   - 定位SafeEvolutionExecutor中被错误标注为ERROR的DEBUG日志
   - 修正为正确的日志级别（DEBUG/INFO/WARNING）
   - 检查其他模块是否有类似的日志级别错误
2. **日志格式统一**：
   - 分析各器官的日志格式差异
   - 统一关键信息的格式（时间戳、器官名、日志级别、消息内容）
   - 统一错误日志的格式（包含错误类型、错误消息、上下文）
3. **日志规范文档**：
   - 输出日志格式规范文档（如已有则更新）
   - 包含：日志级别定义、格式规范、常用日志场景示例
4. **验证**：
   - 运行框架，确认日志级别修正生效
   - 确认日志格式统一
   - 确认无日志丢失或格式错误

**验收标准**：
- [ ] SafeEvolutionExecutor的DEBUG日志不再被标注为ERROR
- [ ] 其他模块的日志级别错误已修正
- [ ] 日志格式统一规范已输出或更新
- [ ] 运行时验证：日志级别正确，格式统一
- [ ] 代码审查通过
- [ ] 不影响现有日志功能

**注意事项**：
- 只修改日志级别和格式，不修改日志内容
- 确保日志修改不影响依赖日志解析的功能（如健康诊断、日志分析工具）
- 保持向后兼容，旧格式日志仍可被解析
