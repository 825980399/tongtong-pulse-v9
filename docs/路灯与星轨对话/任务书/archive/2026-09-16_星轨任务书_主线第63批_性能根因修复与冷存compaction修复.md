### T1 · P0 InfoField publish步骤7锁优化（性能根因修复）

**债务ID**：P0-性能根因（锁等待300ms/队列深度7000+）

**问题描述**：
- `nucleus/field/InfoField.py:772-788`，`publish`方法步骤7使用全局锁`self._lock`
- 高并发下锁等待平均300ms，单次最高3840ms，占100%锁等待
- 导致器官扫描超时（39/62）、L0看门狗超时（6次）、队列深度7000+

**修改文件**：
- `nucleus/field/InfoField.py`

**具体修改点**：

当前代码（第772-788行）：
```python
# === 步骤7: 更新统计 ===
_lock_acquire_start = time.time()
with self._lock:
    _lock_wait_ms += (time.time() - _lock_acquire_start) * 1000.0
    _lock_wait_by_name["publish.step7_stats"] = (...)
    if matched_organs:
        self._total_matched += 1
    else:
        self._total_unmatched += 1
    self._event_publish_count[event_type] = ...
    if not matched_organs:
        self._event_unmatched_count[event_type] = ...
    for _cid in matched_cond_ids:
        self._cond_trigger_count[_cid] = ...
```

**优化方案（三选一，路灯评估后选择最优）**：

**方案A：细粒度锁（推荐）**
- 新增专用统计锁`self._stats_lock = threading.Lock()`
- 步骤7使用`self._stats_lock`替代全局锁`self._lock`
- 统计更新与其他逻辑（如器官状态、并发计数）解耦
- 优点：改动小，风险低，效果明显

**方案B：原子操作**
- 使用`itertools.count`或`threading.Lock`细粒度原子计数器
- `_total_matched`/`_total_unmatched`改为原子计数器
- `_event_publish_count`等使用`collections.Counter`+读写锁
- 优点：无锁竞争，性能最优
- 缺点：改动较大，需验证线程安全

**方案C：异步批量更新**
- 统计更新放入队列，由后台线程批量更新
- publish方法只做`put_nowait`，零阻塞
- 优点：完全消除锁等待
- 缺点：统计有延迟，需新增后台线程

**路灯选择建议**：优先方案A（细粒度锁），改动小、风险低、效果明显。如方案A效果不达标再考虑方案B/C。

**灰度开关**：
- 新增`ENABLE_PUBLISH_STATS_FINE_LOCK = True`（config.py）
- 关闭时使用原全局锁，零回归

**验收标准**：
1. 高并发下锁等待平均从300ms降至<100ms
2. `publish.step7_stats`占锁等待比例从100%降至<50%
3. 队列深度从7000+降至<2000
4. 器官扫描无超时（62/62完成）
5. L0看门狗无超时
6. 灰度开关关闭时行为与改造前完全一致
7. 相关测试全部通过

### T2 · P1 冷存compaction问题修复（parquet文件找不到 + 删除目录失败）

**债务ID**：P1-冷存compaction（第60批T6未完全解决）

**问题描述**：
框架重启后冷存compaction出现两个新问题：

1. **parquet文件找不到**（WinError 2）：
   - compaction过程中引用的parquet文件已被删除或移动
   - 大量WARNING日志："跳过无法读取的parquet文件"

2. **删除旧目录失败**（WinError 145 目录不是空的）：
   - 删除旧目录时目录中有新文件写入
   - 5次重试后仍然失败
   - 导致compaction整体失败

**修改文件**：
- `nucleus/mnemosyne/PulseNodePool.py`（`compact_cold_storage`方法）

**具体修改点**：

#### 问题1修复：parquet文件找不到

**根因分析**：
- compaction读取parquet文件列表后，在读取过程中文件可能被其他线程删除或移动
- 缺少文件存在性检查

**修复方案**：
1. 读取parquet文件前检查文件是否存在，不存在则跳过并记录DEBUG日志
2. 使用`os.path.exists()`或`Path.exists()`检查
3. 对跳过的文件计数，compaction完成后报告跳过数量
4. 跳过文件不影响整体compaction流程

#### 问题2修复：删除旧目录失败

**根因分析**：
- compaction流程：读取旧目录所有parquet → 写入新临时目录 → 删除旧目录 → 重命名临时目录为旧目录名
- 删除旧目录时，可能有其他线程正在写入旧目录（如知识节点持久化）
- 导致"目录不是空的"错误

**修复方案**：
1. **删除前检查**：删除旧目录前，再次检查目录是否为空，不为空则等待重试
2. **增加重试次数**：从5次增加到10次，重试间隔从1秒增加到2秒
3. **强制删除**：如多次重试后仍不为空，使用`shutil.rmtree(ignore_errors=True)`强制删除（记录WARNING）
4. **文件锁保护**：compaction期间对旧目录加文件锁，阻止其他线程写入
5. **原子操作优化**：先将旧目录重命名为临时删除目录（如`evol_level=L1.deleting`），再异步删除，避免阻塞主流程

**路灯选择建议**：
- 优先实现方案1+2+3（检查+重试+强制删除），改动小、风险低
- 方案4（文件锁）和方案5（原子操作）如时间允许可实现，否则记录为后续优化

**灰度开关**：
- 沿用第60批`ENABLE_COLD_COMPACT_WINDOWS_RETRY`（已存在，默认True）
- 新增配置项：`COLD_COMPACT_DELETE_RETRY_COUNT = 10`、`COLD_COMPACT_DELETE_RETRY_INTERVAL = 2.0`

**验收标准**：
1. parquet文件找不到时优雅跳过，不报错
2. 删除旧目录成功率>95%
3. compaction整体成功率>90%
4. 无WinError 145错误（或已被重试/强制删除处理）
5. 灰度开关关闭时行为与改造前完全一致
6. 相关测试全部通过
