159 前置分析 A 类 6 票 + B 类 3 票全部采信。B 类分析发现 **4 项新缺陷**，其中 **D-1 棘轮冷却续期活锁（P1）** 为现网重大缺陷——`restart_count=7>3` 自动应用通道已永久锁死，25 个未审批补丁被困队列。本批 4 刀按依赖顺序施工：**刀1（D-1+D-3，O-B7 硬前置）→ 刀2（签名基线）→ 刀3（lifecycle 表，依赖刀1）→ 刀4（快照降频+D-4，先取证后改）**。

## 一、刀1：D-1 棘轮冷却续期修复（P1，T-棘轮冷却续期-1）+ D-3 回滚额度修复（P2）

### 1.1 目标
解除现网自动应用锁死（冷却永不满期）+ 回滚失败不再烧掉那一格额度。

### 1.2 改动点（最小改动）
1. **`nucleus/reasoning/PatchManager.py:2825`**：else 分支（仍处冷却/锁死）当前**无条件** `self._save_restart_blocked_at(_now)`，每次拒绝刷新冷却起点 → 倒计时永不满期。**修法（采信①）**：仅首次锁死时写入——
   ```python
   if _blocked_at == 0:
       self._save_restart_blocked_at(_now)
   ```
   （或等价改为持久化 `first_blocked_at` 不随拒绝更新；不得改变 PM:2815 期满放行语义）
2. **`main.py:3766-3767`**：当前先取 `_rollback_ok` 再**无条件** `mark_rolled_back()`。改为**仅 `_rollback_ok` 为真时置位**；回滚失败侧记录 `rollback_failed_reason`（补丁对象新增字段，缺省空）。

### 1.3 验收判据
- (a) 人工构造"锁死后冷却期满"用例 → **必须一次期满即放行**（现状不能，回归红线）
- (b) 回滚失败 → **不得置 `rolled_back`**（D-3）
- (c) 现网重启后 `restart_blocked_at.txt` 不再被拨回（冷却正常推进）

### 1.4 测试
扩展 `tests/test_patch_self_apply_m53.py`（已有 `_max_restart_count` 注入位 `:49/:201`）新增 3 例：①冷却不续期（多轮拒绝后 blocked_at 保持首锁时刻）；②回滚失败不烧额度；③计数与回滚互不遮蔽。**并加"日志不外泄"守卫**——烛微实测 19 次「停止自动应用」中 15 次是 `Temp\m53_*` 测试串台（`_max_restart_count=0` 来自 `:201`），同段须带 `Temp\m53_*` 标记防污染生产日志口径。

## 二、刀2：票2 规则签名基线（P2，T-规则生命周期-1）

### 2.1 目标
规则改动**可被发现**。现状两个签名函数"可生成、不落基线、不参与判定"（`fp_rule_signature()` 仅自测消费；`rule_signatures()` 明文 `title|severity|scope` 拼接**不含 checker 函数体**，改检测逻辑指纹不变）。

### 2.2 改动点（扩既有件，不新建门禁脚本）
1. **`tools/ci/verify_fingerprint_gate.py`**：新增第⑩项比对。规则签名口径 = **`sha16(title|severity|scope|normalize_body(checker_src))`**——借 `tools/ci/ci_common.py` 既有 `normalize_body()`（`:59` 同源，cw2 门禁/migrate_whitelist 同口径），确保**改函数体→红、改缩进/挪行→不红**。
2. **新建 `tools/ci/baselines/rule_signature_baseline.json`**：覆盖 `rule_engine.RULE_REGISTRY`（TT001/002/003）+ **158 批新门禁 `check_legacy_assembly_gate.py`**（当前未登记未签名的实例）+ 其他 tools/ci 门禁规则常量/阈值（`FP_SKIP_DIRS` 等）。签名变更走 **`[ci-gate-change]` 标签独立 commit**（同 `244b2e1` 先例）。
3. **`nucleus/self_awareness/rule_engine.py:142-147`**：`rule_signatures()` 与 `verify_fingerprint_gate` 统一走一套 sha16 口径（与 T-唯一口径件-1 同治），不再两处各算各的。

### 2.3 验收判据
- (a) **核心断言**：改任一 checker 的**函数体**（不动 title/severity/scope）→ 签名基线比对**必须报红**（现状不会）
- (b) 改缩进/挪行 → 不报红（借 `ci_common.normalize_body`）
- (c) 新增规则未登记 `RULE_REGISTRY`/未入签名基线 → 门禁报"未登记规则"
- (d) `rule_signatures` 与 `fp_rule_signature` 统一一套 sha16 口径

### 2.4 测试
`verify_fingerprint_gate.py main()` 以第⑥⑨项为模板加 ⑩「checker 体漂移 → 红」自测；`tests/test_m117_path_norm.py` 风格补一条 rule_engine 幂等签名回归。

## 三、刀3：票1 O-B7 补丁生命周期表（P1，依赖刀1）

### 3.1 目标
补丁"激活态记账 + handoff"可证。现状四步流程覆盖 2.5 步：验证较完整（分散 4 模块）、激活**有动作无状态**、回滚**能力齐备现网零流量**、**handoff 全缺**。

### 3.2 改动点（不动枚举，section 式扩展）
1. **新建 `data/evolution/patch_lifecycle.json`**（与 task_ledger 同目录，**不改 `VALID_TASK_STATUS` 枚举**——该枚举语义是重启恢复协议，补丁是变更生命周期，混用会被 `reconcile_on_startup` 对账器把 `running` 误判为死任务）：
   ```json
   {"version": "159-OB7-1", "patches": {"<patch_id>": {
     "stage": "proposed", "stage_at": 0, "task_id": null, "risk_level": 2,
     "file": "", "backup_path": "", "rollback_available": false,
     "verified_by": "", "attempts": 0, "observation_deadline": 0,
     "owner": "", "handed_off_at": 0, "notes": ""}}}
   ```
   阶段枚举（7 态，单调可回退）：`proposed → validated → activated → observing → committed`，旁路 `rolled_back / rejected`。
2. **复用已验证机制，不新造**：① `_atomic_save`（temp+os.replace+fsync 单事务）；② `reconcile_on_startup` 增**补丁段对账**——`activated`/`observing` 超 `observation_deadline` 未 `committed` → 出诊断回执、**标记待人工，不自动回滚**；③ `dedup_key`+`no_redo` 免重做语义。
3. **写入点**：`apply_all_pending` 应用成功后写 `stage=activated`（含 risk_level/file/backup_path/rollback_available 快照）；`rollback_*` 成功后写 `rolled_back`（D-2：让现网 `rolled_back_at` 0→≥1）。
4. **handoff 四要素**（全部复用现成件）：观察期 `observation_deadline = activated_at + N×tick`（到点未 committed → 诊断回执**不自动回滚**）；告警订阅新事件 `evolution.patch_handoff`（EventBus publish，订阅方=星轨+SelfAwarenessEngine 留痕）；负责人 `patch.meta.owner/approver`（`approved_source/approved_signer/approved_at` 已存在）；免重做凭证复用 `dedup_key`。
5. **硬点同步**：`finish_task` 的 `status not in VALID_TASK_STATUS or status=="running"` 校验（`:210`）是扩展必须同步的唯一硬点；补丁观察期存活证明用**新增 `touch_patch()`**（不放宽 `heartbeat_task` 只认 running 的判断）。
6. **存量迁移**：`patch_history.json` 86 条 + `pending_patches.json` 27 条**不迁移**（lifecycle 按 patch_id 懒建，缺失即 `stage=unknown` + WARNING）→ **无破坏性回填**。
7. **风险分级接线**：`risk≥3` 或核心文件（`m80_is_core_file`）者，激活必须 `rollback_available=True` 且 `backup_path` 可读；`risk≤2` 非核心可免整文件备份但留 `before_sha`。
8. **hunks 级部分回滚**：**推迟到 160**（先只登记 `hunks[]` 字段占位，不实施部分回滚）。

### 3.3 验收判据
- (a) 每个 `applied=True` 补丁在 lifecycle 表可查 `stage` 与 `backup_path` 可读性；**`rollback_available=False` 者不得进入 `activated`**（现网 11 条将被挡，符合预期）
- (b) 重启后 `observing` 条目**不被改判 `interrupted`**（专测 pid 对账不误伤）
- (c) 现网 `rolled_back_at` 条数 **0 → ≥1**（第一次真实演练，施工验证时手工制造一次受控回滚）
- (d) 回滚失败不得置 `rolled_back`（与刀1 共用判据）
- (e) handoff 事件发布成功（EventBus 收到 `evolution.patch_handoff`）

### 3.4 测试
扩展 `tests/test_patch_self_apply_m53.py`：patch_lifecycle 写入（activated/rolled_back 落表）、对账不误伤（observing 条目 pid 死后不被改判）、超期回执（不自动回滚只出诊断）。

## 四、刀4：票3 快照增量接管降频（P1，T-快照增量写盘接管-1）+ D-4 节流误报修复（P2）

### 4.1 目标
快照 .bak 稳态占用降 **1.0–1.3GB**；修复节流命中误报"已保存"。

### 4.2 前置取证（施工第一步，先测后改）
- **L-1**：`_get_changed_nodes` 实测变更数分布（探针统计或日志）——现状 `变更>200 即走全量`，12k 节点+肝脏持续压缩下很可能**长期无法满足 ≤200 条件 ⇒ 事实上每次都走全量**（"接管没生效"真因候选）；取证后判定降频是否真实生效
- **L-2**：定位 `.bak` 轮转保留策略（为何稳态停 3 份、清理逻辑位置）——**保留数不改，降频只会让副本更旧、不省磁盘**，此为本刀能否省盘的前置

### 4.3 改动点
1. 取证确认后：**`SNAPSHOT_FULL_SAVE_INTERVAL: 3600 → 21600`**（config.py:4750，先 6h 观察一周期再谈 24h）；若 L-2 显示需配套调整 .bak 保留策略，一并给出方案
2. **D-4 修复**：`PulseSnapshot.py:402-408` 写盘节流命中当前 `return True`（仅 DEBUG 级"延迟落盘"）→ 调用方（`_on_auto_save`、退出路径）把"未写盘"当"已保存"。改返回三态或落 `pending_flush=True` 标记
3. **阈值口径统一**：类常量 `FULL_SAVE_INTERVAL=600`（注释"10分钟" `:212`）、`INCREMENTAL_MAX_NODES=50`（`:213`）与 config 3600/200 不一致 → 同步注释（config 覆盖生效，注释与类常量是过期口径）

### 4.4 硬边界
**退出/启动路径必须继续走全量**（`main.py:2832 save(force_full=True)` + 300s 线程超时 + `:437-439` 实测 8700 节点增量 170s vs 全量 9s）——**不可为省磁盘把退出改增量**。

### 4.5 验收判据
- (a) 24h 内 `.bak` 新增数从 24 → **≤4**（或按 L-2 确认的保留策略口径）
- (b) `snapshot_incremental.jsonl` 行数窗口内单调可控且**未触 MAX_LINES 清理告警**
- (c) 一次受控 `kill -9` 后重启 → 重放后节点数 = 崩溃前 `last_write` 对应值，日志出「增量日志重放完成: 应用 N 条」N>0
- (d) 退出全量耗时仍 **<90s**（12.4k 节点重测，对照 8700 节点 9s 余量）
- (e) D-4：节流命中不再误报"已保存"（调用方可见 pending_flush）

### 4.6 测试
仿 `tests/test_memory_growth_analyzer_m66.py` 注入风格 3 例：①节流命中不得返回"已保存"（D-4）；②`FULL=21600` 时 6h 内 3 次 save 走 jsonl、第 4 次越阈走全量并清空；③全量写失败**保留 jsonl**（`:1076` 承诺零丢失，断言文件未被误删）。
