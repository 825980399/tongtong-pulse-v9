## 二、任务明细

### T1 P2-88 临时快照加载根因定位与修复

**问题描述**：
框架运行时周期性加载系统临时目录下的测试快照文件（`C:\Users\Administrator\AppData\Local\Temp\snap_t4_*.json`），每次加载2个文件（5节点+4节点），产生校验和不匹配WARNING。

**已确认的事实**：
1. 临时目录下有5个`snap_t4_*.json`文件，都是今天19:10创建的（pytest测试残留）
2. 框架运行时随机加载这5个文件中的2个，每次文件名不同
3. 每次加载前都有L3动态扩缩+背压警告（可能只是时间巧合）
4. 代码搜索未找到主动扫描临时目录的逻辑
5. `snap_t4_`前缀只在`tests/test_lazy_snapshot_m9.py`中创建

**根因定位要求**：
1. 在`PulseSnapshot.load()`方法入口添加**调用栈日志**（仅DEBUG级别，可通过开关控制），记录是谁调用了load以及传入的path参数
2. 搜索所有`PulseSnapshot(`实例化点，确认是否有动态传入临时路径的情况
3. 检查是否有模块在做**快照预热/缓存预热**时扫描了所有json文件
4. 检查`LazySnapshotView`的使用场景，是否有全局扫描逻辑
5. 检查`DataQualityGuard`、`ResonanceEngine`、`PeriodicTestScheduler`等模块是否会触发测试

**修复要求**：
1. 找到根因后，修复触发逻辑，确保框架只加载项目目录下的快照
2. 添加**路径白名单校验**：PulseSnapshot加载前检查路径是否在项目目录内，临时目录的文件拒绝加载并记录WARNING
3. 添加**测试残留自动清理**：框架启动时检查临时目录下的snap_t4_*.json文件，自动删除（可选，需开关控制）
4. 灰度开关：`ENABLE_SNAPSHOT_PATH_WHITELIST`（默认True）

**验收标准**：
- 重启框架后运行10分钟，不再出现加载临时目录快照的日志
- 项目目录下的正常快照加载不受影响
- 门控单测：路径白名单校验（合法路径通过/非法路径拒绝/开关关闭零副作用）

### T2 P2-85 百科查询器403 Forbidden修复

**问题描述**：
WikiQuerier查询"计划""盲区"等短词返回HTTP 403 Forbidden，导致知识获取失败。

**根因定位要求**：
1. 检查WikiQuerier的请求头（User-Agent、Referer等），是否被Wikipedia/百度百科识别为爬虫
2. 检查查询URL编码是否正确，短词是否需要特殊处理
3. 检查是否有速率限制，查询频率是否过高
4. 确认是哪个百科源返回403（Wikipedia？百度百科？还是其他）

**修复要求**：
1. 添加**合理的User-Agent**（模拟真实浏览器，包含联系方式）
2. 添加**请求间隔控制**（至少1秒/次，遵守百科网站的robots.txt）
3. 添加**403降级处理**：403时自动切换到其他百科源，或返回空结果并记录INFO（不报错）
4. 添加**查询词预处理**：过短的查询词（<2字）自动拒绝或补充上下文
5. 灰度开关：`ENABLE_WIKI_QUERIER_RATE_LIMIT`（默认True）

**验收标准**：
- 查询"计划""盲区"等短词不再返回403
- 403时能自动降级，不影响框架运行
- 门控单测：User-Agent设置/请求间隔/403降级/短词处理

### T3 P2-86 PulseSnapshot校验和不匹配修复

**根因定位要求**：
1. 检查PulseSnapshot的校验和计算逻辑，确认`deadbeef`是硬编码的占位值还是真实计算值
2. 检查校验和方法是否在v9.5→v10升级时变更过
3. 检查快照保存时是否正确写入了校验和

**修复要求**：
1. 如果`deadbeef`是硬编码占位值：改为真实计算校验和，或移除校验和检查（如果校验和机制未完整实现）

3. 将WARNING降级为DEBUG（如果确认是已知的版本兼容问题）
4. 添加**校验和自动修复**：校验和不匹配时重新计算并更新（可选）

**验收标准**：
- 正常加载项目目录下的快照不再出现校验和不匹配WARNING
- 旧版本快照（v9.5）能正常兼容加载

### T4 P2-87 InfoField池重建并发计数泄漏修复

**问题描述**：
InfoField池重建时出现WARNING：`[S5]池重建重置器官并发计数(cancel_futures导致无法递减): {'视觉皮层': 1, '血管': 1}`

**根因定位要求**：
1. 检查InfoField的L3动态扩缩容逻辑，确认`cancel_futures`时是否正确处理了器官并发计数
2. 检查器官并发计数的递增/递减是否对称，是否有遗漏的递减点
3. 检查池重建时的状态清理逻辑，是否应该在重建前强制重置所有计数

**修复要求**：
1. 在`cancel_futures`时，**遍历所有未完成的future并手动递减对应器官的并发计数**
2. 添加**并发计数校验机制**：定期检查计数是否为负或异常大，发现异常自动重置
3. 添加**池重建前的强制清理**：重建前将所有器官并发计数归零（因为所有future都会被取消）
4. 将WARNING降级为INFO（如果修复后不再出现异常计数）
5. 灰度开关：`ENABLE_CONCURRENCY_COUNT_RECOVERY`（默认True）

**验收标准**：
- L3动态扩缩容时不再出现并发计数泄漏WARNING
- 器官并发计数始终保持非负且合理
- 门控单测：cancel_futures计数恢复/计数校验/池重建清理
