### 任务1：P2-76 PatchManager的Popen参数错误（简单快速，30分钟）

**问题**：PatchManager在验证补丁时，调用`subprocess.Popen`传入了不支持的参数，导致3次import检查失败：
```
[补丁验证] import检查失败(PulseLiver.py): 
沙箱执行异常: Popen.__init__() got an unexpected keyword argument
```

**要求**：
1. 定位`nucleus/evolution/`或相关目录中PatchManager的代码
2. 找到调用`subprocess.Popen`的位置，检查传入的参数
3. 修复不支持的参数（可能是`text`、`encoding`、`capture_output`等在某些Python版本中不兼容的参数）
4. 确保兼容Python 3.12
5. 修复后手动验证import检查能正常执行

**验收标准**：
- [ ] PatchManager的Popen调用参数正确
- [ ] 兼容Python 3.12
- [ ] import检查能正常执行（可手动测试）
- [ ] 新增至少2个测试用例

### 任务2：P2-72 宽泛except Exception治理（核心，1.5-2小时）

**问题**：全库有738处`except Exception`，捕获过多异常，掩盖真实错误。高风险路径（数据读写、LLM调用、器官启动）需要精细化异常处理。

**要求**：
1. 扫描全库`except Exception`，筛选**高风险路径**（至少50处）：
   - 数据文件读写（json.load/open）
   - LLM API调用
   - 器官启动/初始化
   - 向量库操作
   - 自主进化补丁应用
2. 精细化异常处理：
   - 替换为具体异常类型（`FileNotFoundError`、`json.JSONDecodeError`、`TimeoutError`等）
   - 保留`except Exception`作为最后兜底，但必须记录详细日志
   - 禁止裸`except: pass`（已在第7批治理核心路径31处，本次继续扩展）
3. 每个修改点必须有日志记录（WARNING级别，包含异常类型和消息）
4. 非核心路径（tmp/、测试脚本）可以不处理

**验收标准**：
- [ ] 至少50处高风险路径的except Exception精细化
- [ ] 每个修改点有日志记录
- [ ] 不改变原有逻辑（异常时行为一致）
- [ ] 全库ruff F=0
- [ ] 新增至少5个测试用例（模拟各种异常场景）

### 任务3：P2-66 代码行数红线机制（45-60分钟）

**问题**：缺少代码行数红线机制，容易产生新的上帝类（如PulseInnerWorld.py 22,040行）。需要建立约束，防止单一文件过大。

**要求**：
1. 在`config.py`中新增配置：
   ```python
   CODE_QUALITY_CONFIG = {
       "max_lines_per_file": 5000,      # 单一文件最大行数
       "max_lines_per_function": 300,   # 单一函数最大行数
       "max_functions_per_file": 50,    # 单一文件最大函数数
       "enable_line_count_check": True, # 启用语数检查
   }
   ```
2. 新建`tools/check_code_limits.py`脚本：
   - 扫描全库Python文件
   - 检查文件行数、函数行数、函数数量
   - 输出超限文件列表（按严重程度排序）
   - 支持`--json`输出（供CI/CD集成）
3. 在`verify_phase17_1_5.py`或质量门禁中集成行数检查（可选，警告模式不阻断）
4. 生成当前超限文件报告（已知9个文件超3000行，记录但不强制修改）

**验收标准**：
- [ ] CODE_QUALITY_CONFIG配置块创建完成
- [ ] check_code_limits.py脚本可运行
- [ ] 能正确识别超限文件
- [ ] 输出当前超限文件报告
- [ ] 新增至少3个测试用例

### 任务4：P2-48 知识快照provider流式读取+LRU缓存（1-1.5小时）

**问题**：知识快照当前318MB全量加载，内存占用高，启动慢。需要优化为流式读取+LRU缓存。

**要求**：
1. 分析`data/knowledge/pulse_knowledge_snapshot.json`的加载逻辑（找到加载代码）
2. 实现惰性加载机制：
   - 启动时只加载索引（节点ID→文件偏移量）
   - 查询时按需读取节点内容
   - LRU缓存最近访问的节点（可配置缓存大小，默认1000节点）
3. 保留全量加载作为备选（`full_load=True`参数）
4. 评估内存占用降低比例（可在测试中验证）
5. 不影响现有查询接口（向后兼容）

**验收标准**：
- [ ] 惰性加载机制实现
- [ ] LRU缓存实现（可配置大小）
- [ ] 向后兼容（现有接口不变）
- [ ] 内存占用降低（测试验证）
- [ ] 新增至少5个测试用例（缓存命中/失效/淘汰）

## 五、注意事项

1. **零冲突原则**：修改代码对照原有逻辑，不能存在逻辑冲突
2. **预埋设计**：每修复一个问题，顺便为下一个问题和PHASE18设计做前置铺垫
3. **不破坏现有功能**：知识快照优化必须保证向后兼容，现有查询接口不变
4. **渐进式治理**：宽泛except不要一次性全改，优先高风险路径
5. **代码行数红线**：只建立机制和报告，不强制修改现有超限文件（PulseInnerWorld拆分是单独专项）
