## 选择2：审计脚本修复范围

**你的发现**：任务书说`tools/scan_orphan_event.py`，但实际tools/下没这个文件，真实扫描器在tmp/下，部分脚本已修过。

**裁决：选选项3（抽取共用排除模块）**

**理由**：
1. 一次解决所有问题：所有审计脚本引用同一个排除逻辑，不会遗漏
2. 符合预埋设计原则：为后续审计脚本统一管理打下基础
3. 可维护性好：后续新增备份目录格式时，只需要修改共用模块一处

**具体实现要求**：

1. **新建共用模块**：`tools/audit_utils.py`（或`nucleus/utils/audit_exclusions.py`）
   ```python
   import re
   
   def get_backup_exclude_patterns():
       """返回备份目录排除模式列表"""
       return [
           r'\.bak_mainline\d+$',
           r'\.bak_batch\d+$',
           r'\.bak_\d+$',
           r'__pycache__',
           r'tmp[\\/]test_data',
       ]
   
   def is_backup_path(path):
       """判断路径是否为备份目录/文件"""
       patterns = get_backup_exclude_patterns()
       return any(re.search(p, path) for p in patterns)
   
   def filter_backup_files(file_list):
       """从文件列表中过滤掉备份文件"""
       return [f for f in file_list if not is_backup_path(f)]
   ```

2. **修改所有审计脚本**：
   - 找到所有在tmp/和tools/下的审计/扫描脚本
   - 替换硬编码的排除目录为引用共用模块
   - 包括但不限于：scan_orphan_event.py、scan_orphan_event_m10.py、check_code_limits.py等

3. **验证**：
   - 运行审计脚本，确认备份目录下的文件不会被误判

## 选择3：浏览器保活线程安全修复方案

**你的实测发现**：保活走的是`ThreadPoolExecutor(max_workers=1)`，浏览器是预热线程创建的，两个不同线程，即使max_workers=1也会报错。

**裁决：选方案A（保活信号+主线程执行）**

**理由**：
1. 风险最低：不改变现有浏览器创建和使用逻辑
2. 快速见效：保活线程只负责计时和设置标志，主线程执行实际保活
3. 不影响其他功能：浏览器仍然由预热线程创建，主线程使用

**具体实现要求**：

1. **保活线程改造**：
   - 保活线程（或ThreadPoolExecutor）只设置`self._keepalive_due = True`标志
   - 不直接操作浏览器对象
   - 保持每分钟触发一次的频率

2. **主线程执行保活**：
   - 在控制器的主线程事件循环中增加`_check_keepalive()`检查
   - 检查`_keepalive_due`标志，如果为True且浏览器存在，执行保活操作
   - 保活操作：`self._browser.page.reload(timeout=5000)`或访问一个简单页面
   - 执行后重置`_keepalive_due = False`
   - 保活失败不影响主流程（try/except包裹）

3. **线程安全**：
   - `_keepalive_due`标志使用`threading.Event`或加锁保护
   - 确保保活操作只在主线程执行

4. **验证**：
   - 重启后观察10分钟，无`cannot switch to a different thread`错误
   - 浏览器长时间不使用后仍能正常使用
   - 不影响现有浏览器自动化功能
