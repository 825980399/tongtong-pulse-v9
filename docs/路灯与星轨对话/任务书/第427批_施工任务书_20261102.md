## 刀1：剥markdown围栏再dedent（补丁生成侧修复）

**修什么**：现在生成的补丁片段首行带 ```python 围栏，导致textwrap.dedent失效，缩进全乱，ast.parse直接报unexpected indent。

**怎么改**：
- 打开 `nucleus/reasoning/PatchManager.py:3943-3944`
- 在调用 `textwrap.dedent` 之前，先剥掉开头的markdown围栏：
  ```python
  if _s.lstrip().startswith("```"):
      _s = _s.split("\n", 1)[1]  # 去掉围栏行
  # 然后再 dedent
  ```
- 剥完后再做后面的归一化处理

**验证**：
- 拿data/audit/failed_patches/里的63条标本重放，剥完围栏后ast.parse能通过多少条？
- 预期：错误从"unexpected indent"变成别的（try不平衡/截断等），不再是缩进问题

## 刀2：2a前加"片段可解析"预检

**修什么**：现在片段语法错了，先撞try平衡闸，报"try块不平衡"——报错误导，实际是片段本身就坏了。

**怎么改**：
- 在2a闸门之前（`PatchManager.py:3968` 之前）加一道预检：先ast.parse一下modified_code
- 解析失败的直接拒收，reason写"生成片段不完整（围栏/截断）"，不要让try平衡闸背锅
- 这样日志里能直接看到"这个补丁是生成坏了"，而不是"try不平衡"

**验证**：
- 故意生成一个语法错的补丁，日志里的拒收理由是"片段不完整"，不是"try不平衡"

## 刀3：按(file,method)失败冷却24h

**修什么**：现在失败计数按patch id记，换个id就绕过了——结果同一个方法（PulseLiver._compress_group）四天里被试了62次，全失败，白白浪费生成资源。

**怎么改**：
- 加一个 `data/audit/patch_fail_counts.json`
- 每失败一次，就按 (file, method) 记一次数
- 同一个(file,method)连续失败3次，冷却24小时，24小时内不再为这个方法生成补丁
- 冷却期到了自动清零，可以再试

**验证**：
- 连续生成同一个方法的补丁失败3次，第4次应该被冷却，不再生成
- 冷却记录里能看到哪个方法被冷却了、冷却到什么时候

## 刀4：修growth_mb_per_min指标（加窗口+基线）

**修什么**：现在这个指标是短窗瞬时斜率，同一天里能报1815MB/min（刚启动时）和-0.119MB/min（稳定后），同一个指标两个完全相反的读数，没法用来判断有没有泄漏。

**怎么改**：
- 记录 `rss_at_10min`（启动后10分钟的RSS）作为基线
- `growth_mb_per_min` 必须带 `window_sec` 字段，说明是多长窗口算出来的
- 启动后前10分钟的ramp期不算泄漏，单独标注
- 稳态（10分钟后）的斜率才是真正的"泄漏率"

**验证**：
- 跑起来后看health_snapshot里，growth_mb_per_min是不是带了window_sec
- 刚启动时的高斜率是不是标成了"ramp期"，不是"泄漏"
