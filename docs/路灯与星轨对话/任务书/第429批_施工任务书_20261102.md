## 刀1：关757MB JSON备份开关（你拍板：关）

**修什么**：现在知识库每次保存都会写一份757MB的JSON备份，占了全量保存82%的时间。加载用的是Parquet（24MB），这个JSON备份是冗余的。

**怎么改**：
- 找到 `SNAPSHOT_SAVE_JSON_BACKUP` 配置项
- 改成 False
- 不要删代码，只是关开关——万一以后要开还能开
- 确认：关掉后保存时间从多久降到多久？

**验证**：
- 重启后，知识库保存时间是不是真的降下来了？
- data/knowledge/目录下是不是不再生成新的JSON备份了？
- 加载功能正常吗？（Parquet读盘没问题吧？）

## 刀2：批处理链停摆根因定位（你拍板：优先查）

**修什么**：last_gen_at停在10-22 17:59，快两周没生成新补丁了——修了这么多闸，但上游为什么不再生成了？

**怎么查**：
1. 先找补丁生成的触发点：是定时触发？还是有事件就触发？
2. 触发条件是什么？满足了吗？
3. 从触发到生成，中间哪一步断了？
4. 看日志：最近有没有"准备生成补丁"的日志？如果有，卡在哪一步了？如果连"准备生成"都没有，说明根本没到生成入口——是触发条件没满足

**注意**：
- 不要上来就改代码，先定位根因
- 把根因写清楚：是触发条件太严？还是某个依赖坏了？还是生成模块抛异常被吞了？

**验证**：
- 根因到底是什么？
- 修完后，真的开始生成新补丁了吗？

## 刀4：PulseEars查证（你拍板：查一下）

**修什么**：有个测试一直红，说PulseEars应该有发射但现在没有。需要确认是设计改了还是真坏了。

**怎么查**：
1. 先看测试在断言什么：PulseEars应该发射什么事件？
2. 再看PulseEars现在的代码：它还注册了发射吗？
3. 如果设计改了——PulseEars已经不需要发射这个事件了——那就改测试，把过时的断言删掉
4. 如果是真坏了——该注册没注册——那就修代码

**注意**：
- 不要上来就改测试把红的盖住，先搞清楚为什么红
- 是设计演进了还是真bug，写清楚

**验证**：
- 结论：设计改了还是真bug？
- 如果是设计改了，测试改了什么？
- 如果是真bug，代码修了什么？
- 那个测试现在绿了吗？

## 刀5：内存16:05阶跃定位

**修什么**：烛微发现启动后1小时（16:05左右），RSS突然涨了0.48GB，还没找到根因。

**怎么查**：
1. 先复现：再启动一次，盯着16:05那个时段的日志
2. 那个时段前后，到底跑了什么任务？
3. 是哪个模块的内存涨了？（用pyarrow.total_allocated_bytes()分开看Parquet占了多少，Python对象占了多少）
4. 是真泄漏，还是一次性加载？

**注意**：
- 不要上来就"修泄漏"——先搞清楚是不是真泄漏
- 现在已经平台化了，1小时涨0.48GB然后就不涨了，可能是一次性加载，不是泄漏

**验证**：
- 根因到底是什么？
- 是真泄漏还是一次性加载？
- 如果是一次性加载，哪个模块干的？
