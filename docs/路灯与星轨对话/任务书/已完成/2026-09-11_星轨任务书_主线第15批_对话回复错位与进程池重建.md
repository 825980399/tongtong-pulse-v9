## 一、任务1：对话回复错位修复（P1-98，最优先）

### 问题描述

用户在09:18-09:30连续输入9个问题，框架回复严重错位：
- 09:22 "解释一下记忆维" → 无输出
- 09:24 "什么是语义内核？" → 无输出
- 09:27 "记忆维权重从0.4降到0.3" → 回复"框架的灰度开关..."（上一个问题的答案）
- 09:29 "语义内核不可用，框架会怎样降级？" → 回复"经验库去重..."（上一个问题的答案）
- 09:30 "查一下人工智能最新进展" → 回复"如果语义内核不可用..."（上一个问题的答案）

### 根因分析

1. **输出锁超时释放**：大脑皮层4次"超时释放输出锁"（09:24, 09:26, 09:28, 09:30）
2. **处理速度跟不上输入速度**：用户1-2分钟输入一个问题，框架处理需3-5分钟
3. **新输入覆盖旧任务**：输出锁释放后新问题进来，旧任务仍在异步处理，最终输出时已是下一个问题的上下文
4. **correlation_id管理混乱**：ctx:2→3→5→6→7→8，跳过ctx:4，有任务被丢弃

### 修改要求

**文件**: `nucleus/cortex/CerebralCortex.py`（大脑皮层，输出锁管理）

**修复方案**:
1. **输出锁超时释放时取消旧任务**：超时释放输出锁时，应该取消正在处理的旧任务（通过correlation_id标记为已取消），而不是让它继续执行后输出
2. **回复输出时校验correlation_id**：输出回复前检查correlation_id是否与当前最新输入匹配，不匹配则丢弃该回复（避免错位）
3. **添加对话队列机制**：新输入时如果有未完成的旧任务，应该：
   - 方案A（推荐）：排队等待，明确提示"正在处理上一个问题，请稍候"
   - 方案B：取消旧任务，立即处理新问题（适合快速问答场景）
   - 可通过配置项 `DIALOG_QUEUE_STRATEGY = "queue" | "cancel"` 控制，默认queue
4. **优化知识查询类问题的处理速度**：本地知识库优先，减少LLM调用（简单问题如"什么是XX"直接从知识库提取）

### 灰度开关

```python
ENABLE_DIALOG_LOCK_GUARD = True  # 总开关
DIALOG_QUEUE_STRATEGY = "queue"  # queue=排队, cancel=取消旧任务
```

### 验收标准

- 连续快速输入5个问题，每个问题的回复都正确对应该问题（不错位）
- 输出锁超时释放后，旧任务的回复不会输出到新问题的上下文
- correlation_id连续，无跳过
- 不影响正常单轮对话的回复质量

## 二、任务2：ReasoningWorkerPool进程池崩溃自动重建（P1-92）

### 问题描述

日志中出现8次真正的ERROR：`A child process terminated abruptly, the process pool is not usable anymore`

崩溃时间：02:01、03:26、03:31(x2)、03:51、05:10、07:38、08:35(x2)、08:40(x2)

**严重问题**：崩溃后没有自动重建机制！只有00:34和00:37的两次平滑重建（在崩溃之前），崩溃后完全没有重建日志。

影响：FrequencyCodec.encode_batch和verify_patch_effect_in_process任务持续失败。

### 修改要求

**文件**: `nucleus/reasoning/ReasoningWorkerPool.py`

**修复方案**:
1. **添加崩溃检测**：在submit方法中捕获`BrokenProcessPool`异常
2. **自动重建机制**：检测到进程池崩溃后，自动重建进程池（指数退避，最多重试3次）
3. **重建期间的任务处理**：
   - 重建期间新提交的任务排队等待
   - 重建完成后自动执行排队的任务
   - 超过3次重建失败则降级为同步执行（在主进程中执行，保证功能可用）
4. **添加健康检查**：定期检查进程池状态，发现异常提前重建
5. **添加重建日志**：每次重建都记录INFO日志，包含崩溃原因、重建耗时、worker数量

### 灰度开关

```python
ENABLE_POOL_AUTO_REBUILD = True  # 自动重建开关
POOL_REBUILD_MAX_RETRIES = 3     # 最大重建重试次数
POOL_HEALTH_CHECK_INTERVAL = 60  # 健康检查间隔（秒）
```

### 验收标准

- 模拟进程池崩溃后，5秒内自动重建完成
- 重建期间提交的任务在重建后正常执行
- 连续3次重建失败后降级为同步执行，不报错
- 重建日志完整（崩溃原因、重建耗时、worker数量）

## 三、任务3：SafeEvolutionExecutor子进程崩溃根因排查（P1-93）

### 问题描述

12小时内子进程崩溃109次：
- mode=review: 80次
- mode=repair: 22次
- mode=execute: 7次

每小时均匀分布11-14次，说明是系统性问题，不是偶发。

### 修改要求

**文件**: `organs/body/SafeEvolutionExecutor.py`

**排查与修复**:
1. **添加崩溃时的完整错误信息**：当前日志只有"子进程崩溃"，没有具体错误原因。需要捕获子进程的stderr和exit code
2. **分析崩溃模式**：
   - review模式崩溃最多（80次），可能是LLM返回内容解析失败
   - 检查子进程的内存使用（是否OOM）
   - 检查子进程的超时处理（timeout=600s是否合理）
3. **添加崩溃重试机制**：子进程崩溃后自动重试（最多2次），重试失败则降级为同步执行
4. **添加崩溃统计**：记录每种模式的崩溃次数、崩溃原因分布
5. **如果是LLM解析问题**：在子进程中添加更健壮的JSON解析（3种策略：直接json.loads、正则提取、保留原始内容）

### 灰度开关

```python
ENABLE_EVOLUTION_CRASH_RETRY = True  # 崩溃重试开关
EVOLUTION_CRASH_MAX_RETRIES = 2      # 最大重试次数
```

### 验收标准

- 子进程崩溃时日志包含具体错误原因（stderr、exit code）
- 崩溃后自动重试，重试成功则任务继续
- 崩溃统计可查询（每种模式的崩溃次数、原因分布）
- 不影响正常的自主迭代流程
