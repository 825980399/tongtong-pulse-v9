## T-84a：运行时验证闭环断链（核心）

**现象**：`[ReportConsumers]` 真实修复率 0.0%，`[PatchAutoApprover]` 连续10轮修复率<10%。

**根因推断（待路灯验证）**：
- 补丁提交时记了基线：`SafeEvolutionExecutor.py:1454/1471`
  ```python
  _local_patch["baseline_errors"] = self._count_errors_for_location(...)
  _local_patch["needs_runtime_verify"] = True
  ```
- 但**"修复后再数错误→对比baseline→写回problem_fixed"这条链的触发点和写回点未确认**——`needs_runtime_verify=True` 的补丁谁来跑、何时跑、结果写哪。
- `problem_fixed` 恒 None → `real_fix_rate = problem_fixed=True的补丁数/总数` 恒 0。

**改法（先只读定位，再最小修复）**：
1. **定位**：grep `needs_runtime_verify` / `problem_fixed` 的所有读写点，画出"提交→审批→应用→运行时验证→写回"完整链路；
2. **断链点**：确认断在哪里——是没人跑运行时验证，还是跑了但没写回 `problem_fixed`；
3. **修复**：
   - 如果是没人跑：在合适的生命周期点（如补丁应用后下一轮 evolution round 开始时）触发运行时验证；
   - 如果是跑了没写回：补上 `problem_fixed = True/False/None` 的写回逻辑。

**先红后绿**：
- 新增测试：构造一个 `needs_runtime_verify=True` 的补丁，触发运行时验证，断言 `problem_fixed` 被写回（不再恒 None）；
- 改前：`problem_fixed` 恒 None（红）；改后：被正确写回（绿）。

## T-84b：审批空转——_repaired 为何恒0

**根因推断**：
- `local_patched/local_verified` 有计数（:1614），但本地验证通过只到"提交待审批"（:1461）；
- 从"待审批"到"已应用"中间隔着人工/自动审批 + 运行时验证两道门，**两道门都空转**；
- `_repaired += 1` 只在"已应用且运行时确认修复"时触发，但这条路径没人走通。

**改法**：
1. **定位**：grep `applied=True` 的来源，确认本地/LLM补丁从"待审批"到"已应用"的裁决路径；

   - 如果有自动审批逻辑（如 PatchAutoApprover），确认它为何不产出 `_repaired`；
   - 如果 `_repaired` 的累加条件过于严格（要求运行时验证通过才+1），考虑区分"已应用"和"已验证修复"两个计数。

**先红后绿**：
- 新增测试：构造一个本地补丁通过自动审批并应用，断言 `_repaired` 正确+1；
