## 二、任务清单（5项，总预估工时10-14h）

### T1（P1） P2-213 Profile补overall_score和top_issues字段

**预估工时**：2-3小时
**需重启框架验证**：否（可通过单元测试验证）

**任务描述**：
当前SelfAwarenessProfile只有各维度分数，缺少综合评分和最严重问题列表。需补全这两个核心字段，让用户/星轨能一眼看出"整体健康度"和"最该修什么"。

**具体要求**：
1. 在SelfAwarenessProfile中新增`overall_score`字段（float，0-100）
   - 计算方式：各维度分数的加权平均（权重可配置，默认等权）
   - 不可用维度（status="unavailable"）不参与计算
   - 至少需要2个可用维度才计算，否则overall_score=None
2. 新增`top_issues`字段（List[Dict]，最多5条）
   - 从各维度的issues中按severity排序，取最严重的5条
   - 每条包含：dimension（维度名）、severity（严重级别）、description（描述）、suggestion（建议）
3. 新增`health_level`字段（str）：根据overall_score分级
   - ≥80: "healthy"（健康）
   - 60-79: "moderate"（中等）
   - 40-59: "concerning"（堪忧）
   - <40: "critical"（危急）
   - overall_score=None时为"unknown"
4. to_dict()和from_dict()同步更新
5. generate_report()中在报告开头显示overall_score和health_level，以及top_issues列表

**验收标准**：
- [ ] overall_score字段存在且计算正确（加权平均，排除不可用维度）
- [ ] top_issues字段存在且按severity排序，最多5条
- [ ] health_level字段存在且分级正确
- [ ] to_dict()/from_dict()包含新字段
- [ ] generate_report()开头显示综合评分和最严重问题
- [ ] 单元测试：构造多维度Profile验证overall_score/top_issues/health_level
- [ ] pytest全量通过（基线1109+新增）
- [ ] ruff F=0，E402新增0

**风险提示**：
- 权重配置需合理，避免某一维度过度影响综合评分
- top_issues的severity排序需统一各维度的severity定义

### T2（P1） P2-214 evolution_health维度接SafeEvolutionExecutor

**预估工时**：2-3小时
**需重启框架验证**：否（可通过单元测试+mock验证）

**任务描述**：
当前evolution_health维度恒为"不可用"（无数据源）。但SafeEvolutionExecutor已有丰富数据（21项指标：执行次数/成功率/回滚次数/平均耗时等）。需将这些数据接入引擎的evolution_health维度。

**具体要求**：
1. 在EvolutionHealthAnalyzer（或对应分析器）中增加从SafeEvolutionExecutor读取数据的能力
2. 数据来源：SafeEvolutionExecutor的统计接口（get_stats()或类似方法）
3. 计算evolution_health分数（0-100）：
   - 成功率权重40%（成功率越高分越高）
   - 回滚率权重30%（回滚率越低分越高）
   - 执行稳定性权重30%（耗时方差越小分越高）
4. 生成issues：
   - 成功率<80% → high severity issue
   - 回滚率>20% → high severity issue
   - 无执行记录 → info severity（"暂无进化执行记录"）
5. 若SafeEvolutionExecutor不可用或无数据，标记为"unavailable"（保持当前行为）
6. 增加单元测试：mock SafeEvolutionExecutor返回不同统计数据，验证分数和issues

**验收标准**：
- [ ] evolution_health维度可从SafeEvolutionExecutor读取数据
- [ ] 分数计算正确（成功率/回滚率/稳定性加权）
- [ ] issues生成正确（低成功率/高回滚率触发对应级别）
- [ ] SafeEvolutionExecutor不可用时标记为unavailable
- [ ] 单元测试：mock不同统计数据验证分数和issues
- [ ] pytest全量通过，ruff F=0

**风险提示**：
- SafeEvolutionExecutor的接口可能与预期不同，需先核实实际接口
- 若SafeEvolutionExecutor数据量很大，读取时需注意性能

   - 检测"process"时，同时匹配`process`和`_process`
2. 候选生成时，对每个公开方法名生成对应的私有下划线变体
3. 验证第36批发现的9候选中，私有调用是否能被正确识别
4. 报告中区分"公开方法命中"和"私有方法命中"
5. 增加单元测试：构造包含私有下划线方法的迷你工程，验证检测器能识别

**验收标准**：
- [ ] 私有下划线方法（_load/_process等）能被正确识别
- [ ] 候选生成包含公开名和私有下划线名变体
- [ ] 报告中区分公开/私有命中
- [ ] 第36批9候选中的私有调用能被识别
- [ ] 单元测试：迷你工程验证私有方法识别
- [ ] pytest全量通过，ruff F=0

**风险提示**：
- 私有方法识别可能增加误报（下划线方法可能是内部辅助，不一定是闭环），需保持保守策略
- 性能：候选数翻倍，需确保扫描时间可接受

4. 报告中显示"已排除X个自我观察文件"
5. 不影响其他目录的正常分析
6. 增加单元测试：构造包含self_awareness目录的迷你工程，验证排除生效

**验收标准**：

- [ ] 报告中显示排除统计

### T5（P2） P2-231 配对器信噪比优化（目录/扩展名排除白名单）

**预估工时**：2-3小时
**需重启框架验证**：否（可通过单元测试+独立脚本验证）

**任务描述**：
第37批T2磁盘枚举后，no_consumer达1955条，其中1951条是"磁盘存在但源码未引用"（docs/归档文档268 + 测试产物data/evolution/test_runs 957 + data/probe 576）。信噪比极低，真问题（4条"写了没人读"）易被淹没。需增加目录/扩展名排除白名单，聚焦真问题。

**具体要求**：
1. 增加配置项`PRODUCTION_CONSUMPTION_EXCLUDE_DIRS`（目录排除白名单）
   - 默认包含：`data/evolution/test_runs/`、`data/probe/`、`docs/`（归档文档）、`tmp/`
   - 可通过config.py或配置文件扩展
2. 增加配置项`PRODUCTION_CONSUMPTION_EXCLUDE_EXTENSIONS`（扩展名排除）
   - 默认包含：`.md`（文档）、`.txt`（日志/文本）、`.log`（日志）
   - 注意：`.json`/`.jsonl`/`.npz`/`.db`等数据文件不排除
3. 排除的文件标记为`excluded`，不计入no_consumer
4. 报告中区分显示：
   - "有效无消费"（源码有产出方、无消费方）= 真问题
   - "磁盘独有已排除"（按白名单排除）= 噪声
   - "磁盘独有未排除"（未匹配白名单，需人工确认）
5. 优化后目标：有效无消费<20条，信噪比>50%
6. 增加单元测试：构造包含测试产物/文档/真实数据的迷你工程，验证排除逻辑

**验收标准**：
- [ ] 目录排除白名单生效（test_runs/probe/docs/tmp默认排除）
- [ ] 扩展名排除生效（.md/.txt/.log默认排除）
- [ ] 排除文件标记为excluded，不计入no_consumer
- [ ] 报告中区分有效无消费/已排除/未排除
- [ ] 真实项目实测：有效无消费<20条，信噪比>50%
- [ ] 配置项可扩展
- [ ] 单元测试：迷你工程验证排除逻辑
- [ ] pytest全量通过，ruff F=0

**风险提示**：
- 排除白名单需谨慎，避免误排除真实的"有产出无消费"问题
- 默认排除列表需经过实测验证，确保不遗漏真问题
- 扩展名排除可能误排除某些重要的.txt数据文件，保守策略是只排除明确的文档/日志扩展名
