**问题描述**：
- 第71批完成Neo4j双写（只写不读），查询仍用节点内linked_nodes
- 第72批完成全量同步后，Neo4j有真实数据，可以开始读取路径
- 双读过渡期：查询优先从Neo4j读取，不可用时回退到节点内linked_nodes
- 渐进式启用，先读关联关系，再读节点属性

**修改文件**：
- `nucleus/knowledge_access_layer.py`（KAL增加Neo4j查询接口）
- `nucleus/mnemosyne/PulseNodePool.py`（关联查询优先Neo4j）
- `config.py`（新增双读开关）

**具体修改点**：

#### 4.1 关联查询优先Neo4j

1. **查询关联关系**：
   - 当需要查询节点的关联关系时（get_relationships）
   - 优先从Neo4j查询（query_relationships）
   - Neo4j不可用或查询失败时，回退到节点内linked_nodes
   - 记录查询来源（neo4j/node_pool），用于统计命中率

2. **多跳关联查询**：
   - query_multi_hop(node_id, max_depth, top_k)优先用Neo4j
   - Neo4j不可用时，回退到逐层遍历节点内linked_nodes（性能较差但可用）
   - 记录查询耗时对比

3. **共同邻居查询**：
   - query_common_neighbors(node_id_1, node_id_2)优先用Neo4j
   - Neo4j不可用时，回退到集合交集计算

#### 4.2 双读开关与监控

1. **配置开关**：
   - ENABLE_NEO4J_GRAPH_STORE + ENABLE_NEO4J_DUAL_WRITE + ENABLE_NEO4J_READ
   - 三个开关都开启才执行双读
   - 默认关闭（ENABLE_NEO4J_READ=False）
   - 双读过渡期：先开启只读，观察稳定性

2. **查询统计**：
   - 记录Neo4j查询次数、成功次数、失败次数
   - 记录节点内回退次数
   - 记录查询延迟对比（Neo4j vs node_pool）
   - 提供get_read_stats()查询统计

3. **一致性保障**：
   - Neo4j查询结果与节点内不一致时，记录WARNING
   - 定期对比关键节点的关联关系一致性
   - 如果不一致率>5%，自动回退到节点内查询

#### 4.3 渐进式启用

1. **第一阶段（只读关联关系）**：
   - 只从Neo4j读关联关系（linked_nodes）
   - 节点属性仍从节点池读取
   - 观察稳定性和性能

2. **第二阶段（读节点属性）**：
   - 从Neo4j读节点属性
   - 对比节点池中的属性一致性
   - 观察稳定性和性能

3. **第三阶段（完全切换）**：
   - 关联查询完全用Neo4j
   - 节点查询仍用节点池（L1热节点内存常驻）
   - 冷节点查询优先Neo4j，按需加载到节点池

**验收标准**：
- 关联查询优先Neo4j（开关开启时）
- Neo4j不可用时回退节点内
- 双读开关可关闭，关闭时零副作用
- 查询统计和监控正常
- 一致性保障机制正常（不一致时告警/回退）
- 渐进式启用设计完整

### T5 · P2 分布式主从复制与一致性级别 + 测试 + 文档 + 债务清单

**具体修改点**：

#### 5.1 分布式主从复制与一致性级别

1. **主从复制逻辑**：
   - 在NodeRegistry和NodeRouter基础上，实现主从复制逻辑
   - 主节点：负责读写，定期同步到从节点
   - 从节点：负责读（可配置），接收主节点同步
   - 复制延迟监控
   - 主节点故障时，从节点升级为主节点（手动触发）

2. **一致性级别实现**：
   - eventual（默认）：写入主节点即返回，异步同步到从节点
   - strong（关键数据）：写入主节点并等待至少N个从节点确认
   - 配置一致性级别（按分片配置：L1热节点strong，L2/L3冷节点eventual）
   - 冲突解决：LWW（最后写入胜出）

3. **一致性级别接口**：
   - write_with_consistency(node_id, data, consistency_level)
   - read_with_consistency(node_id, consistency_level)
   - 按分片自动选择一致性级别
