## 〇、批次背景与目标

### 0.1 问题背景

第三方深度分析报告（总评分5.2/10）指出P0-9级问题：**交互与任务两端系统性断链**。其中"卡对话"问题经星轨深度排查，根因如下：

1. **全局并发8 > 免费渠道实际并发**：框架允许同时发起8个大模型调用，但免费智谱实际并发只有1，导致7个调用超时/429失败
2. **无按渠道独立并发控制**：所有渠道共享全局信号量，不区分渠道实际并发能力
3. **渠道切换是"失败后重试"**：当前逻辑是调用失败（超时30秒）后才切换下一个渠道，每次失败浪费30秒
4. **后台学习与用户对话共享并发池**：后台自主学习占满免费渠道后，用户对话也受影响
5. **无真实多轮对话**：`_build_channel_messages`只包`[system, user]`两条，没有历史上下文
6. **用户无进度感知**：处理过程中无阶段性提示，用户感觉"卡住"

### 0.2 核心设计思路（星轨与用户讨论确认）

**总并发保持8，不降低**。按渠道实际能力独立分配，并**动态调整**（不写死）：

- 每个渠道有独立的并发信号量
- 按优先级顺序尝试：智谱→火山→DeepSeek
- **并发满即切换**：当前渠道并发满了，立即尝试下一个渠道（零延迟，不等待）
- **动态并发调整**：类似TCP拥塞控制，成功则缓慢增加并发上限，失败/限流则立即减少
- 用户对话可配置优先使用付费渠道（保证响应速度）

## 二、任务清单

### T1 · 按渠道独立并发控制 ✅必做

**目标**：每个渠道维护独立的`threading.Semaphore`，按渠道实际能力控制并发。

**实现要点**：

1. **配置扩展**：在`REMOTE_API_CHANNELS`的每个渠道配置中增加`max_concurrent`字段：
   ```python
   {
       "name": "zhipu",
       "model": "glm-4-flash",
       ...
       "max_concurrent": 1,  # 初始值，动态调整会修改运行时值
   },
   {
       "name": "doubao",
       "model": "doubao-seed-evolving",
       ...
       "max_concurrent": 5,
   },
   {
       "name": "deepseek",
       "model": "deepseek-v4-flash",
       ...
       "max_concurrent": 10,  # 付费渠道初始给更大并发
   },
   ```

2. **PulseLung渠道信号量管理**：
   - 在`__init__`中为每个启用的渠道创建独立的`threading.Semaphore(max_concurrent)`
   - 提供`_get_channel_semaphore(name)`方法获取渠道信号量
   - 渠道配置热重载时重建信号量

3. **全局信号量保留**：
   - 保留`api_rate_limited`全局信号量（max_concurrent=8）作为总上限保护
   - 渠道信号量在全局信号量之内工作（先获取全局许可，再获取渠道许可）

**验收标准**：
- 每个渠道有独立的信号量
- 配置中`max_concurrent`字段生效
- 全局信号量仍作为总上限
- 不破坏现有渠道路由逻辑

### T2 · 并发满即切换（核心改造）✅必做

**目标**：当前渠道并发满了，**立即**尝试下一个渠道（零延迟），而不是等待30秒超时后才切换。

**实现要点**：

1. **非阻塞获取渠道许可**：
   - 在`_call_via_channels`的渠道循环中，调用`_call_channel`之前先获取渠道信号量
   - 使用`semaphore.acquire(blocking=False)`非阻塞尝试
   - 获取失败（并发满）→ `continue`立即尝试下一个渠道（不等待、不调用）
   - 获取成功 → 调用`_call_channel`，完成后`release()`

2. **调用完成后释放**：
   - 在`finally`块中释放渠道信号量
   - 确保异常情况下也能释放

3. **全部渠道并发满的处理**：
   - 如果所有渠道都并发满，等待全局信号量（或短暂等待后重试）
   - 可配置`all_channels_full_wait`：默认1秒，等待后重试
   - 记录日志：`[渠道] 所有渠道并发满，等待{wait}秒后重试`

**伪代码**：
```python
for _ch in _candidates:
    _name = _ch.get("name", "?")
    # 非阻塞获取渠道许可
    _sem = self._get_channel_semaphore(_name)
    if _sem is None or not _sem.acquire(blocking=False):
        self._log(LogLevel.DEBUG, f"[渠道] {_name} 并发满，立即切换下一个")
        continue
    try:
        _reply = self._call_channel(_ch, prompt, ...)
        if _reply:
            return _reply
    finally:
        _sem.release()
```

**验收标准**：
- 渠道并发满时零延迟切换（日志可验证）
- 不等待30秒超时
- 所有渠道并发满时有等待重试机制
- 信号量在异常情况下也能正确释放

### T3 · 动态并发调整机制（不写死）✅必做

**目标**：类似TCP拥塞控制，根据渠道实际响应动态调整并发上限，不写死。

**实现要点**：

1. **调整策略**：
   - **成功**：缓慢增加并发上限（如每5次成功+1，或累积+0.2，达到整数时+1）
   - **失败（429限流/超时）**：立即减少并发上限（如-1，或减半，下界为1）
   - **并发上限上下界**：`min_concurrent=1`，`max_concurrent_upper=2500`（付费渠道可更大）

2. **渠道并发状态管理**：
   - 为每个渠道维护运行时状态：
     ```python
     {
         "current_max": 5,        # 当前并发上限（动态调整）
         "success_count": 0,      # 成功计数（用于增加判断）
         "consecutive_failures": 0,  # 连续失败计数
         "adjust_history": [],    # 调整历史（时间+原因+新值）
     }
     ```
   - 提供`_adjust_channel_concurrency(name, success: bool)`方法
   - 调整时记录日志：`[渠道] {name} 并发上限 {old}→{new}（原因：连续失败3次/成功5次）`

3. **配置项**：
   ```python
   "dynamic_concurrency": {
       "enabled": True,              # 总开关
       "success_threshold": 5,       # 每N次成功+1
       "failure_decrement": 1,       # 每次失败-N
       "min_concurrent": 1,          # 下界
       "max_concurrent_default": 10, # 付费渠道上界默认
       "free_channel_max": 10,       # 免费渠道上界（避免免费渠道无限增长）
   }
   ```

4. **与T2的集成**：
   - 渠道信号量的初始值来自配置的`max_concurrent`
   - 动态调整修改运行时的`current_max`，并重建信号量（或调整信号量的内部计数器）
   - 注意：`threading.Semaphore`不支持直接修改上限，需要在调整时创建新的信号量替换（加锁保护）

**验收标准**：
- 成功调用后并发上限缓慢增加
- 失败/限流后并发上限立即减少
- 并发上限有上下界保护
- 调整历史可追溯（日志+内存状态）
- 不写死，自动适应渠道实际能力

### T5 · 多轮对话修复（第三方报告P0-9）✅必做

**目标**：`_build_channel_messages`加入最近N轮历史上下文，修复"无真实多轮对话"问题。

**实现要点**：

1. **历史上下文管理**：
   - 在PulseLung或PulseCortex中维护对话历史队列（`collections.deque(maxlen=N)`）
   - 每轮对话记录：`{"role": "user", "content": "..."}` 和 `{"role": "assistant", "content": "..."}`
   - 配置项：`dialog_history_turns: 5`（默认保留5轮）

2. **`_build_channel_messages`改造**：
   - 当前只包`[system, user]`两条
   - 改造为：`[system, ...历史上下文, user]`
   - 历史上下文按token限制截断（可配置`dialog_history_max_tokens: 2000`）
   - 超出时丢弃最旧的轮次

3. **历史上下文清理**：
   - 对话结束/超时后清理历史
   - 新对话开始时可选择保留或清空历史（配置项`dialog_history_persist: True`）

**验收标准**：
- `_build_channel_messages`包含历史上下文
- 历史轮数可配置
- 超长时自动截断
- 不破坏现有单轮对话逻辑
