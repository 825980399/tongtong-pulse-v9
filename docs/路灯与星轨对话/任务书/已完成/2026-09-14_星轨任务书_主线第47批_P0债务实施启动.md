### T1：补丁验证语义拆分（No-Regression vs Problem-Fixed）（P0-2 / P2-309）

**对应债务**：P0-2 补丁验证空转、P2-309 补丁基线依赖已轮转截断的pulse.log
**类型**：代码实施 + pytest
**需重启**：⚠️ 可能（向后兼容设计，尽量不重启）
**预估工时**：2-3小时
**优先级**：★★★★★（最高）

#### 问题描述

当前补丁验证系统把两个不同语义合成一个布尔值`verified`：
- `verification.passed=true`的语义是**No-Regression**（"改完没弄坏"——syntax/import/regression通过）
- `baseline→after`想表达的是**Problem-Fixed**（"问题真消失了"）

结果："没弄坏"被当成"修好了"上报，67条补丁中62条unverifiable、仅2条real_effectiveness_computable，而claimed_effectiveness_avg=0.9766——30倍反差。

#### 任务要求

1. **语义拆分实施**：
   - 在补丁验证结果中新增两个独立字段：
     - `no_regression: bool`——语法/导入/回归测试是否通过（"没弄坏"）
     - `problem_fixed: bool | None`——目标问题是否真的修复（"修好了"，无法验证时为None）
   - 保留原`verified`字段作为向后兼容（`verified = no_regression`，但标注为deprecated）
   - 新增`verification_granularity: str`——标识验证粒度（"static_only" / "reproduction" / "effectiveness"）
   - 新增`effectiveness: float | None`——真实修复效果（可计算时填，不可计算时为None，不再默认0.97）

2. **补丁历史回填**：
   - 对现有67条补丁历史，重新计算`no_regression`和`problem_fixed`字段
   - 对于baseline_errors=0的补丁，`problem_fixed=None`（无法验证），不再默认True
   - 生成回填报告，统计拆分后的真实修复率

3. **展示层更新**：
   - 补丁列表展示时，区分显示"✅ 无回归"和"❓ 修复效果未验证"
   - 健康诊断中的"补丁修复率"改为基于`problem_fixed=True`的真实修复率，不再基于`verified`
   - 质量分计算中，补丁有效性的权重基于`effectiveness`而非`verified`

4. **pytest测试**：
   - 测试语义拆分后的数据结构正确性
   - 测试向后兼容性（旧代码读取新字段不崩溃）
   - 测试回填逻辑正确性
   - 测试展示层区分显示

#### 验收标准

- [ ] 补丁验证结果包含`no_regression`和`problem_fixed`两个独立字段
- [ ] 原`verified`字段保留但标注deprecated，向后兼容
- [ ] 67条补丁历史已回填，`problem_fixed=None`的补丁不再被当成"修好了"
- [ ] 健康诊断中的补丁修复率改为真实修复率（预计从97%降到个位数）
- [ ] pytest全量通过，ruff F=0

### T2：摘要机制止血（_summarize_experience保留raw_summary）（P0-3 / P2-308）

**对应债务**：P0-3 SERP污染锁死L3、P2-308 _summarize_experience()模板化压缩销毁原文
**类型**：代码实施 + pytest
**需重启**：✅ **需要重启**（修改了experience_pool核心逻辑）
**预估工时**：2-3小时
**优先级**：★★★★★（最高，最紧急）

#### 问题描述

`nucleus/mnemosyne/experience_pool.py:241-267`的`_summarize_experience()`方法用模板句覆盖原文：
```python
_summary = f"我曾因{_motivation[:30]}而行动，获得了{_reward_type}奖赏"
experience["summary"] = _summary[:150]      # ★覆盖原文
experience["motivation"] = _motivation[:50] # ★截断
experience["field_frequency_snapshot"] = {}  # ★清空
```

这导致83.1%的经验记录被模板化压缩，原文丢失。这是SERP污染的主要来源（不是写入灌水，是维护侧压缩）。

#### 任务要求

1. **摘要机制止血**：
   - 修改`_summarize_experience()`，不再覆盖`summary`字段，而是：
     - 保留原始`summary`（如果有）
     - 新增`raw_summary: str`字段，存储原始摘要
     - 新增`compressed_summary: str`字段，存储模板化压缩后的摘要
     - `summary`字段优先使用`raw_summary`，如果raw_summary为空则使用compressed_summary
   - 不再截断`motivation`字段（保留完整motivation，或新增`raw_motivation`）
   - 不再清空`field_frequency_snapshot`（保留原始快照，或新增`raw_field_frequency_snapshot`）

2. **check_decay()修改**：
   - `check_decay()`调用`_summarize_experience()`时，确保不覆盖原文
   - 衰减标记使用`is_summarized=true`，但原文保留在`raw_summary`中
   - 新增`summary_version: int`字段，标识摘要版本（便于未来升级摘要算法）

3. **防污染机制（写入侧）**：
   - 在经验写入时，增加重复检测（完全重复的记录不写入）
   - 与已有的`write_guard.py`协同，确保测试环境不污染生产数据
   - 新增`pollution_risk: str`字段（"low"/"medium"/"high"），标识记录的污染风险

4. **pytest测试**：
   - 测试`_summarize_experience()`不再覆盖原文
   - 测试`raw_summary`和`compressed_summary`的正确存储
   - 测试`check_decay()`的衰减逻辑正确性
   - 测试写入侧重复检测
   - 测试向后兼容性（旧记录没有raw_summary字段时不崩溃）

5. **验证**：
   - 重启框架后，运行1-2天，观察是否还有新增的模板化污染记录
   - 生成验证报告，统计新增污染记录数（目标：0新增）

#### 验收标准

- [ ] `_summarize_experience()`不再覆盖`summary`字段，原文保留在`raw_summary`中
- [ ] `motivation`和`field_frequency_snapshot`不再被截断/清空
- [ ] 新增`compressed_summary`、`raw_summary`、`summary_version`、`pollution_risk`字段
- [ ] 写入侧增加重复检测
- [ ] pytest全量通过，ruff F=0
- [ ] 重启框架后，观察1-2天确认无新增模板化污染（目标：0新增）
- [ ] 向后兼容：旧记录读取不崩溃

#### 交付物

### T3：ReportBus核心骨架（统一契约+分发层+1-2个消费者）（P0-1）

**对应债务**：P0-1 自认知闭环断裂
**类型**：代码实施 + pytest
**需重启**：❌ 否（新增模块，不影响现有逻辑）
**预估工时**：2-3小时
**优先级**：★★★★☆（高）

#### 问题描述

框架不缺自认知能力（12小时1108行报告日志），但缺的是从诊断到动作的那一跳：
- `generate_report(output_path=None)`默认不落盘（只返回字符串）
- 无注册表、无统一格式、无分发通道
- 只有"恰好知道路径"的叙事自我吃到报告

#### 任务要求

1. **ReportEnvelope统一契约**：
   - 新增`nucleus/reporting/report_envelope.py`模块
   - 定义`ReportEnvelope`数据类，包含：
     - `report_id: str`——唯一标识
     - `report_type: str`——报告类型（health/pollution/evolution/self_cognition等）
     - `generated_at: datetime`——生成时间
     - `generator: str`——生成器名称
     - `priority: str`——P0/P1/P2
     - `content: dict`——报告内容（结构化）
     - `anomalies: list[Anomaly]`——异常列表
     - `consumed_by: list[str]`——已消费者列表
     - `actions_triggered: list[str]`——已触发的动作
   - 定义`Anomaly`数据类，包含：`type`、`severity`、`description`、`source`、`suggested_action`

2. **ReportBus分发层**：
   - 新增`nucleus/reporting/report_bus.py`模块
   - 实现`ReportBus`类，功能：
     - `publish(envelope: ReportEnvelope)`——发布报告（自动落盘到`data/reports/`）
     - `subscribe(report_type: str, consumer: Callable)`——订阅特定类型的报告
     - `get_unconsumed(report_type: str = None) -> list[ReportEnvelope]`——获取未消费的报告
     - `mark_consumed(report_id: str, consumer: str)`——标记报告已被消费
     - `get_stats() -> dict`——获取报告分发统计（总数/已消费/未消费/按类型分布）
   - 报告落盘格式：JSON，路径`data/reports/{report_type}/{report_id}.json`
   - 保留最近100份报告，自动清理旧报告

3. **1-2个内置消费者**：
   - **健康异常消费者**：订阅health类型报告，当发现P0级异常时，触发告警（写入日志+标记为需人工介入）
   - **污染异常消费者**：订阅pollution类型报告，当污染率超过阈值时，触发数据清洗建议（写入待办）
   - 消费者只做"触发动作建议"，不自动执行（符合不可逆清单原则）

4. **现有报告生成器接入（可选，如时间允许）**：
   - 选择1-2个现有的报告生成器（如健康诊断、污染报告），改为通过ReportBus发布
   - 保持向后兼容（旧的直接落盘方式仍然可用）

5. **pytest测试**：
   - 测试ReportEnvelope的序列化/反序列化
   - 测试ReportBus的发布/订阅/消费/统计
   - 测试内置消费者的触发逻辑
   - 测试报告自动清理机制

#### 验收标准

- [ ] ReportEnvelope统一契约实现完成，包含所有必要字段
- [ ] ReportBus分发层实现完成，支持发布/订阅/消费/统计
