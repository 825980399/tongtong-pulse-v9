## Q2：QICA语义鸿沟残差15个错分，是否接受？三选一

**星轨裁决：选择方案3（优化refine_intent精修逻辑），低风险增强**

**具体方案**：
1. **不选方案1**（维持现状）：残差9个"知识查询黑洞"说明还有优化空间
2. **不选方案2**（扩句式通道）：对158条语料过拟合风险高，禁止
3. **选方案3**（优化refine_intent）：只做**低风险的精修规则增强**：
   - 含人名+关系词（如"你和XX是什么关系"）→ 触发身份确认/关系查询精修
   - 含"为什么"+"需要"（如"为什么框架需要XX"）→ 触发技术推理/概念解释精修
   - 含对比词（"和XX比"、"区别"）→ 触发对比分析精修
4. **精修规则必须可解释、可测试**，不能是黑盒权重调整

**理由**：方案3是规则增强，不是过拟合。"你和小林是什么关系"这类问题明显应该走身份确认，而不是知识查询，这是精修逻辑的漏洞，不是语料不足。

**纳入主线第4批**：refine_intent低风险精修规则增强。

## Q3：quality_flag是否默认挂载知识快照provider？318MB常驻

**星轨裁决：不默认挂载，保持经验库provider**

**具体方案**：
1. **默认挂载经验库provider**（当前方案）：惰性读、安全、内存占用小
2. **知识快照provider作为可选**：不自动挂载，避免318MB常驻
3. **后续优化方向**：知识快照provider可以改为**流式读取+LRU缓存**，只缓存最近访问的节点quality_flag，而不是全量加载318MB
4. **观察经验库provider效果**：重启后观察污染节点是否被有效过滤，如果效果不够再考虑优化

**理由**：318MB常驻内存代价太高，框架本身已经在运行多个器官和线程，内存压力需要控制。经验库provider已经能覆盖大部分污染节点（经验池中的polluted节点），知识快照中的polluted/suspect/placeholder_alias节点可以后续优化为流式读取。

**纳入主线第4批**：知识快照provider流式读取+LRU缓存优化（如果需要）。
