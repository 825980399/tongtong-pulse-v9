## 三、请裁决的 6 处

### 3.1 ★刀1：任务书的两处措辞都对不上码（已按实测改，请确认）

- 点名的 `_generate_life_plan` **不存在**（真名 `_generate_life_stage_summary` /
  `_generate_life_story` / `_generate_weekly_report`）；
- 「阶段判定 `narrative_events<20/<50` 阈值」**不存在**：那个变量带 `# noqa: F841`，
  算出来**根本没用**，六维里的"维度6 叙事事件丰富度"一直是空的。

⇒ 本刀做的事不是"改锚点"，而是**把这条断掉的线接上**，且用**落盘连续天数**（不是内存数）。
零回归设计：没落过盘的实例 ⇒ 不加分不加信号，与改造前逐字一致。

### 3.2 ★★刀2：`content` 是设计如此 —— 我**没有**补字段，请确认这个判断

380 条经验里 `has_content_field = 0`、`summary` 非空 380、`is_summarized` 369。
`content` 是 `record_experience()` 的**入参**，入库即落成 `summary`
（`experience_pool.py:179` `"summary": content[:200]`）。

⇒ 按任务书"如果是设计如此（只存摘要）：检索时用摘要做语义匹配就够了，确认即可"。
**我确认了，没有补字段**。若你希望真的新增 `content` 字段（保留原文不截断），
那是 413 的活 —— 现在补会动 380 条历史数据与写入契约。

顺带一个更值得看的数：**前 5 段模板合计 223/380 ≈ 59%**（411 报的 0.19 只算了最热
那一段）。污染面比先前估计的大得多。

### 3.3 ★★刀3：perf 阈值「±0.5ms」与实测「1500ms」差 3000 倍

任务书写"不需要精确——只要有数值就行，正负 0.5ms 内算 perf_ok"。
实测 `EvolutionEffectVerifier.DEFAULT_MAX_REGRESSION_MS = 1500.0`
（可由 `config.EVOLUTION_EFFECT_VERIFY_CONFIG["max_regression_ms"]` 覆盖）。

本刀**只供数，阈值一字没动**（改阈值等于改"什么算性能退化"的定义，不该由我定）。
请裁：是 0.5ms（严格，几乎必判退化）、还是保持 1500ms、还是另给一个值。

另外提醒：补上 perf 一维**不保证出 passed** —— 还要 `problem_gone` 非 None
（它来自 `apply_reprobe`，`false_pass` 会被映射成 None）。

### 3.4 ★★刀4：按当前判据**会放行 0 条** —— 这到底是判据太严，还是判死质量有问题

真问题池 + 真调用图实测（648 条 / O3 判死族 591 条 / 孤儿 2325 / 覆盖 399 文件）：

```
将放行 0 条
拒因：public_api 587 / core_file 40 / not_open 10 / method_not_isolated 4
```

**591 条判死条目里 587 条是 public API**（方法名不以 `_` 开头）。两种可能：

1. 判据太严：公共 API 也需要"确证无引用"后才删（那就得加一层确证，不是靠名字猜）；
2. **O3 判死本身质量可疑**：把一批公开 getter 判成死代码。

我倾向先查 2。建议 **413 批第一件事 = 抽查这 587 条**，而不是急着开闸。
开闸开关 `PATCH_M412_DELETE_ONLY_GATE` 默认关，一周后看报表再说。

### 3.5 刀1 的产物形态：我给摘要行加了 `events`，请确认这不算越界

任务书行格式只列了 8 个字段，且说"每天 1 条摘要"。但**只存计数的话 `load()` 恢复不了
事件列表**，"重启不归零"这条验收根本过不了 ⇒ 我在行里加了 `events`（事件体，上限 50 +
`events_truncated` 标记）。

代价：单文件从几百字节涨到约 1KB/天（7 天 ≈ 7KB，可接受）。
若你认为摘要行就该只有计数，那"重启不归零"这条验收得改成"只恢复计数与连续天数"。

### 3.6 两处 CI 规则现状（411 已上报，本批未再遇到，但话术仍矛盾）

`cw3-A` 的处方写"基准文件必须与代码同提交"，而**门禁隔离守卫**禁止 CI 门禁文件与
