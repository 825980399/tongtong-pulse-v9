# 星轨-路灯自动化协作模式说明

**版本**：v1.1
**日期**：2026-09-10
**生效日期**：2026-09-10 起
**更新说明**：v1.1 改为动态监测模式，不预设固定批次，支持路灯处理过程中追加问题

---

## 一、协作模式概述

从2026-09-10起，星轨与路灯的协作从"人工转发"升级为"文件共享+定时轮询"的自动化动态协作模式。

**核心原则**：
- **动态生成**：不预设固定批次，根据上一批完成情况决定下一批范围
- **按需追加**：路灯处理过程中发现新问题，可以随时追加，星轨定时回复
- **状态驱动**：星轨只在路灯完成当前任务后才生成新任务，不并行派发
- **闭环验证**：每批完成后星轨验证交付质量，再决定下一步

双方通过 `docs/路灯与星轨对话/` 文件夹共享文件，通过定时任务自动检测和处理。

---

## 二、文件夹结构

```
docs/路灯与星轨对话/
├── 任务书/
│   ├── 待处理/     ← 星轨生成的新任务书，路灯定时检测此目录
│   ├── 处理中/     ← 路灯领取任务后，将任务书移动到此目录
│   └── 已完成/     ← 路灯完成任务后，将任务书移动到此目录
├── 交付报告/
│   ├── 待分析/     ← 路灯生成的交付报告，星轨定时检测此目录
│   └── 已分析/     ← 星轨分析完成后，将报告移动到此目录
├── 历史归档/       ← 历史对话文件（按日期归档）
│   ├── 2026-09-08/
│   ├── 2026-09-09/
│   └── 2026-09-10/
└── 状态/
    └── current_batch.json  ← 当前批次状态（JSON格式）
```

## 三、路灯侧操作流程

### 3.1 定时任务设置

**任务名称**：曈曈PulseNet-路灯侧任务执行

**执行频率**：每小时一次（建议整点后5分钟，如01:05、02:05...）

**触发条件**：检测到 `任务书/待处理/` 目录下有新的 `.md` 文件

### 3.2 执行步骤

```
1. 检测 任务书/待处理/ 目录
2. 如果有新任务书：
   a. 读取任务书内容
   b. 将任务书移动到 任务书/处理中/ 目录
   c. 按照任务书要求执行代码修改
   d. 完成后生成交付报告，放到 交付报告/待分析/ 目录
   e. 将任务书从 处理中/ 移动到 已完成/ 目录
3. 如果没有新任务书：
   a. 记录"无待处理任务"
   b. 等待下一轮定时触发
```

### 3.3 疑问追加机制（处理过程中可用）

路灯在处理任务过程中，如果遇到疑问或发现新问题，可以随时生成疑问文件，不需要等到任务完成：

```
1. 在 交付报告/待分析/ 目录创建疑问文件
2. 文件命名：YYYY-MM-DD_路灯疑问_当前任务简称.md
3. 文件内容：
   - 疑问描述
   - 相关代码位置
   - 建议的处理方案（可选）
   - 需要星轨确认的事项
4. 星轨会在下一个整点定时检测到疑问文件并回复
5. 星轨的回复会放到 任务书/待处理/ 目录，命名为 YYYY-MM-DD_星轨回复_对应疑问.md
6. 路灯在下一轮定时检测时读取回复
```

**注意**：
- 疑问文件和交付报告都放在 `待分析/` 目录，通过文件名区分
- 路灯可以在处理任务的同时追加疑问，不需要暂停当前任务
- 星轨回复后，路灯可以根据回复调整当前任务的处理方式

### 3.4 文件命名规范

**任务书命名**：
```
YYYY-MM-DD_星轨任务书_第N批_任务简称.md
示例：2026-09-10_星轨任务书_头部完善第1批_大脑器官.md
```

**交付报告命名**：
```
YYYY-MM-DD_路灯交付_第N批_任务简称.md
示例：2026-09-10_路灯交付_头部完善第1批_大脑器官.md
```

### 3.4 交付报告必须包含的内容

1. **验收结果总览**：任务书要求的各项指标是否达标
2. **改动文件清单**：修改/新增/删除的文件列表
3. **测试结果**：单元测试通过数/总数
4. **备份文件**：.bak文件列表
5. **已知限制**：未完成的部分或需要后续处理的问题
6. **需要小林操作**：是否需要重启框架、运行验证脚本等

## 四、星轨侧操作流程

### 4.1 定时任务设置

**任务名称**：曈曈PulseNet头部文件完善-星轨侧动态监测

**执行频率**：每小时一次（整点，如01:00、02:00...）

### 4.2 执行步骤（动态监测模式）

```
1. 【最高优先级】检查交付报告/待分析/ 目录
   - 如果有新交付报告：
     a. 读取并分析报告（完成/部分完成/未完成）
     b. 验证关键文件和测试结果
     c. 更新技术债务清单
     d. 移动报告到 已分析/
     e. 根据完成情况动态决定下一步：
        - 全部完成 → 生成下一批任务书（动态选择范围）
        - 部分完成 → 生成补充任务书（只含未完成部分）
        - 发现新问题 → 追加到下一批任务书
   - 如果没有交付报告，进入步骤2

2. 检查路灯追加的疑问/问题
   - 检测 待分析/ 目录中文件名含"疑问"或"问题"的文件
   - 如果有疑问：
     a. 读取疑问内容
     b. 生成回复文件，放到 任务书/待处理/（文件名含"星轨回复"）
     c. 移动疑问文件到 已分析/
   - 如果没有疑问，进入步骤3

3. 检查任务书状态
   - 如果 处理中/ 有任务：
     a. 检查是否超过4小时未完成
     b. 超时则提醒小林（路灯可能卡住）
     c. 不生成新任务书，等待当前任务完成
   - 如果 处理中/ 和 待处理/ 都为空：
     a. 说明所有任务已完成
     b. 检查是否还有未完成的技术债务
     c. 有则生成新一批（优先级最高的债务）
     d. 无则输出"所有任务已完成"
```

### 4.3 动态生成任务书的规则

- **不预设固定批次**：根据实际完成情况动态决定下一批范围
- **优先级驱动**：优先处理P0/P1级别的技术债务
- **批量控制**：每批任务量控制在路灯2-4小时能完成的范围
- **问题追加**：路灯在上一批中发现的新问题，自动追加到下一批
- **闭环验证**：每批完成后验证质量，不达标则生成补充任务

## 六、统一头部格式规范

每个.py文件的头部必须包含以下格式：

```python
# -*- coding: utf-8 -*-
"""
PulseCodeLearner —— 代码自主学习器官

版本: v10 PulseNet
设计: 路灯、小林、星轨
日期: 2026年9月9日

职责: [根据每个文件的实际职责填写，1-3句话]
机制: [描述核心工作机制，2-5句话]
定位: [在框架中的定位和作用，1-2句话]
"""
```

**填写要求**：
- **职责**：这个文件/类负责什么功能
- **机制**：核心算法或工作流程是什么
- **定位**：在整个框架中处于什么位置，与其他模块的关系

## 七、注意事项

1. **改前必备份**：每个修改的文件都要生成 `.bak` 备份
2. **不破坏现有功能**：只修改头部注释和ruff问题，不改变业务逻辑
3. **测试验证**：每批完成后运行相关测试，确保不破坏现有功能
4. **ruff清理**：尽量修复ruff错误和警告，但不要为了过ruff而改变逻辑
5. **超时处理**：如果一批任务超过4小时未完成，在交付报告中说明进度

## 八、异常处理

| 异常情况 | 处理方式 |
|---------|---------|
| 任务书不清晰 | 在交付报告中说明疑问，星轨下一批澄清 |
| 修改导致测试失败 | 回滚到.bak，在交付报告中说明 |
| 文件被框架锁定 | 跳过该文件，在交付报告中列出 |
| 不确定头部内容 | 根据代码内容推断，不确定的标注"待完善" |

## 九、六方角色与制衡（权威映射 · v1.2 · 2026-10-02）

> 修订依据：微光《第三方输入核验与路径归一化_20261002》B1 角色核验（T-对外协作说明-1 · B-2 裁决采纳）。本表为项目角色唯一权威口径，供协作模式说明/任务书/对外说明共用。

| 角色 | 真实职责 | 红线 |
|---|---|---|
| **小林** | 业主/最终裁决：拍板、派工、资源（框架启停、额度、对外公开决策） | 唯一拍板权 |
| **星轨** | 协调与总控：任务书/总账/登记册/裁决建议/批末验收 + 三平台 push/进度管理 | 写单不施工、验收不拍板 |
| **路灯** | **唯一编码执行体**：按任务书改生产代码/测试/交付报告 | 无任务书权、无 push 权、不扩大施工面 |
| **烛微** | 第三方只读审计 + 前置分析 + 双轨互读 | 不写生产码 |
| **微光** | 阶段性分析职位：巡检/文档总管/星轨验收人（反向监督星轨） | 不随每批任务加入项目 |
| **Tongtong Dev** | 曈曈自身匿名提交身份（自动化/AI 提交） | **非团队成员**，不可授予拍板权 |

**制衡链**：写单不施工 → 施工不验收 → 验收不拍板 → 巡检不写码 → 拍板者（小林）独立于全部执行链。
