## 二、真实代码诊断（★与任务书字面三处偏差，已澄清）

我**实读了** `nucleus/runtime/RuntimeTrajectory.py`（261 行全量）、`SelfModel.py`、`Interoception.py`、`PulseCortex.py`，并用全局 grep 核对调用链。发现三处与任务书字面描述不一致，方向不影响，但实现落点要校正：

### 偏差A：持久化现状不是"w 全量覆写同一文件"
- `RuntimeTrajectory.py:200-204` 的 `_persist` 是 `open(_path, "w")`，但 `_path` 是**带时间戳的新文件名**（`trajectory_{YYYYmmdd_HHMMSS}.jsonl`）。
- 即：每次持久化 = 生成**一个新的全量快照文件**，不是覆写同一个文件。
- 真正的 bug 是：**没有启动回读 `load()`**。重启后 `_records` 为空队列，历史全丢。框架运行 10 分钟后重启，轨迹归零——这正好是星轨验收标准反面的现状。
- **校正**：修复重点 = 新增 `load()` 启动回读；持久化改造 = 增量追加（避免每 5 分钟一个新全量文件导致文件无限增长）+ 定期 compact，而非简单改 "w"。

### 偏差B：RuntimeTrajectory 类内没有 set_trajectory 方法
- 全局 grep 显示 `set_trajectory` 只在 `SelfModel.py:82` 和 `Interoception.py:84` 作为**二者各自的 setter**（接收 ref 注入）。
- `RuntimeTrajectory` 类内只有模块级 `set_runtime_trajectory()`（依赖注入用），类内无 `set_trajectory`。
- 星轨所说"set_trajectory 零调用导致 SelfModel/Interoception 死代码"——准确含义是：**没有人调用这两个类的 `set_trajectory` 把单例注入进去**，所以 `self._trajectory` 永远是 `None`，`SelfModel._get_current_state`(`:143`)、`_get_history`(`:210`) 和 `Interoception` 的 `RuntimeTrajectory` 分支永远走 `default` 死代码。
- **校正**：修复 = 在 `SelfModel.__init__` / `Interoception.__init__` 末尾调用 `self.set_trajectory(get_runtime_trajectory())` 注入，**不是**给 RuntimeTrajectory 加方法。

### 偏差C（补充）：写入端其实是活的
- 全局 grep 排除 `data/code_backups/` 备份后，当前活动代码里 `organs/brain/PulseCortex.py:132` 注入单例、`:712`/`:822` 调用 `self._trajectory.record(...)`。
- 所以"轨迹从来没被记录"不准确。现状是：**PulseCortex 在记，但 SelfModel/Interoception 没接读取端，且持久化没有回读**。
- 这反而印证子任务0 的核心价值：让落盘的轨迹能被回读、被自我认知层消费。

## 三、子任务0 实现方案

### 3.1 配置项（config.py — 高风险文件，改前先 .bak）
- 新增 `ENABLE_RUNTIME_TRAJECTORY_PERSIST = False`（默认 False，零回退）。
- 接入点：`get_runtime_trajectory()` 构建单例时 `enabled=该常量`。运行时改开关需重启（可接受，符合"框架重启验证"节奏）。

### 3.2 RuntimeTrajectory.py 改造（内核单例，非六大核心器官，先 .bak 后改）
1. **`_ensure_dir()`**：`__init__` 内 `os.makedirs(self._persist_dir, exist_ok=True)` 提前创建目录（现状 `_persist` 内已有，但提前创建更稳，满足星轨"启动时自动创建目录"）。
2. **`load()`（新增）**：从 `persist_dir` 读回历史。策略：
   - 读 `trajectory_active.jsonl`（增量文件）+ `trajectory_*_compact.jsonl`（compact 归档）；
   - 合并去重（按 `trajectory_id`），受 `max_records` 环形限制截断到最近 N 条；
   - 仅在 `enabled` 为 True 时调用；
   - 读失败降级为"空启动"，不影响主流程。
3. **`_persist()` 改增量追加**：维护 `trajectory_active.jsonl`，`"a"` 模式只追加 `_persisted_total` 指针之后的新记录；每次持久化后更新指针。
4. **每小时 compact**：把 `active` + 内存合并 → 去重 → 截断到**最近 7 天** → 写回 `active`（或按日期归档），删除 7 天前的文件。满足星轨"每小时 compact 一次、保留最近 7 天、文件大小可控"。
5. **开关保护**：`enabled=False` 时 `record()` 直接 `return None`、`_persist`/`load` 跳过 → 行为与现状完全一致（零回退风险）。

### 3.3 注入读取端（激活死代码）
- `SelfModel.__init__` 末尾：`self.set_trajectory(get_runtime_trajectory())`
- `Interoception.__init__` 末尾：`self.set_trajectory(get_runtime_trajectory())`
- 受开关保护：未启用时单例 `enabled=False`，两类仍读到空/默认，行为与现状一致。

### 3.4 启动回读（尽量不触 main.py — 高风险文件）
- 采用 **lazy load**：`get_runtime_trajectory()` 首次构建单例后自动调用 `load()`，无需改 `main.py`。
- 这样可以满足星轨"框架启动时加载历史轨迹"的验收，同时规避 `main.py` 高风险改动（符合修改纪律"核心/高风险文件改前先告知"）。

### 3.5 验证方式
- **本地自测脚本**（不启框架）：造 5 条 `record` → `_persist` → 模拟重启（新单例 `load`）→ 校验回读条数/内容一致、`active` 文件为增量、compact 7 天截断生效。
- **全量回归**：`python tools/verify_phase17_1_5.py` 零冲突。
- **框架运行 10 分钟重启验证**：交小林（需真实运行环境，验证"历史轨迹仍在"+ SelfModel/Interoception 读到数据）。
