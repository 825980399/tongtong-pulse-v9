## 二、与任务书的两处偏差澄清（重要，影响方案）

星轨任务书基于"知识节点有 metadata 容器"的预设，但**实读代码发现与事实不符**，必须校正：

### 偏差 A：PulseNode 没有 `metadata` 容器字段
`nucleus/mnemosyne/PulseNode.py` 的时间相关字段是**平铺**的：`created_at`(94)、`last_activated`(95)、`updated_at`(117)。
- 节点类**不存在** `metadata` 字典字段。
- 序列化边界是 `to_dict()`(245-279) / `from_dict()`(281-318)，所有字段逐一列平铺。

**结论**：子任务3 的"在 metadata 中增加 source_time"应改为**平铺加两个字段**（与现有 `created_at` 风格一致），而非新建 metadata 容器。

### 偏差 B：网页发布时间提取当前零实现
Grep `datePublished|publish_date|发布时间|published_time` 全项目，命中的全是 `data/code_backups/`（备份，非运行代码）和 `utils/time_utils.py`（通用时间工具）。**运行代码里没有任何"从网页提取发布时间"的逻辑**。
- 这意味着 Q3 的"网页时间提取"是**全新功能**，需改搜索器官（"双腿"/"控制器"）的解析链路，范围较大、风险较高。

**结论**：Q3 不宜与核心一并首批落地，应作为独立增量（子任务3.1）分期。

## 三、Q1-Q4 决策推荐

### Q1：时间戳存在哪里？→ **平铺加 `source_time` / `acquired_time`**
| 方案 | 评价 | 理由 |
|------|------|------|
| (推荐) 平铺加 2 字段，与 `created_at` 并列 | ✅ | PulseNode 无 metadata 容器；`to_dict`/`from_dict` 各加 2 行；向前兼容（旧快照缺失则 fallback `created_at`）；不引入新容器类型、不破坏现有逻辑 |
| 新建 `metadata` 容器字典 | ❌ | 与现有平铺风格冲突；需改序列化边界 + 新建容器读写逻辑；增大回归面，且无收益 |

**字段语义**：
- `acquired_time`：节点入库时间，默认 = `created_at`（创建即入库），写入确定性高。
- `source_time`：知识来源时间。默认 = `acquired_time`；**仅当**搜索器官从网页提取到发布时间时覆盖（子任务3.1）。

### Q2：时效性评分公式？→ **分段阈值 + 与激活新鲜度融合，权重不动**
现状 time 维（`_calc_time_dim`，ResonanceEngine.py:837-858）是**激活新鲜度**：`elapsed = now - last_activated`，分段衰减 1.0→0.05，**不是来源时效**。

推荐在 `_calc_time_dim` 的 **Python 原生兜底层**改为：

```
time_dim = 0.5 * activation_freshness(last_activated)   # 保留现状（防止激活后的旧知识继续高分）
         + 0.5 * source_timeliness(source_time)          # 新增：来源越新分越高
```

`source_timeliness` 用**分段阈值**（与现有风格一致）：
- < 7 天：1.0
- < 30 天：0.85
- < 90 天：0.65
- < 365 天：0.40
- >= 365 天：0.20（**不低于 0.2，保证"旧知识低但不丢弃"**）

**红线遵守**：time 维仍是 0.10（宪法 1.3 不动）；只在 time 维**内部**融合，不影响五维权重、不影响 peak 门（peak_ratio=0.90 勿改）。

### Q3：网页时间提取覆盖率？→ **首批不做，列为子任务3.1 增量**
- 项目当前无网页发布时间提取实现（偏差 B 已证实），从零做需改搜索器官，范围大。
- **首批（子任务3.0）只落地核心**：字段 + 检索调权 + stale 标记。
- **子任务3.1（独立增量，同一开关保护）**：在搜索器官解析结果时提取发布时间写入 `source_time`；提取不到则 `source_time` 维持默认 = `acquired_time`（符合"提取不到就用获取时间"）。
- 3.1 不阻塞 3.0 验收。

### Q4：是否需要"过时知识"标记？→ **加派生标记，不入库、不降权到 0**
- 推荐：`is_potentially_stale = acquired_age_days > STALE_THRESHOLD_DAYS`（建议 365）。
- 这是**检索时计算的派生标记**，作为结果附带的提示字段（如 `stale_flag`），由上层（皮层/嘴）决定是否提示用户"该知识可能过时"。
- **不做自动剔除、不降权到 0**，严格符合"旧知识低但不丢弃"原则。

## 五、关键坑（务必注意）

1. **Cython 同步**：若 `_resonance_cy_available=True`（`ResonanceEngine.py:278` 导入成功），`_calc_time_dim` 走 `calc_time_dim_cy(elapsed)`（848 行），Python 兜底层改动**不生效**。需确认本项目 Cython 是否真启用：
   - 若启用：需在 Cython 源码 `nucleus/synapsys/_resonance_cy*.pyx` 同步加 `source_time` 参数并重新编译。
   - 若未启用（默认 False，仅当 .pyd 存在）：Python 兜底层改动即覆盖，无碍。
   - **方案**：实施时先打印 `_resonance_cy_available` 实测值；若启用则一并改 Cython。
2. **序列化边界**：`to_dict`/`from_dict` 改动影响快照读回，必须向前兼容（旧快照无 `source_time` → `from_dict` 用 `data.get("source_time", created_at)`）。
3. **五维权重红线**：任何改动不得触碰 `DIMENSION_WEIGHTS["time"]=0.10`（ResonanceEngine.py:44）与 peak 门 0.90。
