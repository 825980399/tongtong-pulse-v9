## 二、星轨在本地修复的两个问题（请同步到你的代码库）

子任务1的代码本身是正确的（单独测试通过），但在框架集成时有两个遗漏，星轨已在本地修复，请你同步：

### 问题1：TimeCore的logger导入路径错误

**位置**：`nucleus/chronos/TimeCore.py`

**问题**：代码中写的是 `from utils.logger import get_organ_logger`，但实际模块在 `nucleus.logger`。导致TimeCore自己的日志全部丢失（包括广播异常日志）。

**修复**：
```python
# 错误
from utils.logger import get_organ_logger

# 正确
from nucleus.logger import get_organ_logger
```

### 问题2：器官未订阅time.tick事件

**位置**：`main.py` 第1822-1838行（器官共振条件注册流程）

**问题**：InfoField的分发机制是"只有注册了对应event_types的器官才能收到脉冲"。TimeCore广播了time.tick，但器官的 `get_resonance_conditions()` 中没有包含 `SystemEvent.TIME_TICK`，所以器官收不到。

**修复**：在器官注册循环中，受 `ENABLE_TIME_CORE` 开关保护，自动为每个器官添加time.tick订阅：

```python
# 在 organ.set_registered_cond_ids(cond_ids) 之前添加：
try:
    import config as _cfg_time2
    if getattr(_cfg_time2, "ENABLE_TIME_CORE", False):
        from nucleus.const import SystemEvent
        _tick_cid = self.info_field.register_condition(
            organ_name=organ_name,
            event_types=[SystemEvent.TIME_TICK],
            min_priority=1,
            handler=organ.on_pulse,  # _handle_pulse_safe会拦截并走on_time_tick
        )
        cond_ids.append(_tick_cid)
except Exception as _tick_err2:
    self._log(LogLevel.DEBUG, f"{organ_name} time.tick订阅失败: {_tick_err2}")
```

**注意**：你之前遵守了"不修改main.py"的红线，但TimeCore作为内核单例需要启动入口和器官订阅，这两处main.py修改是必要的。星轨已在本地完成，你同步即可。

## 四、批准子任务2（主动调度接管）开工

### 子任务2目标

让TimeCore从"被动广播"升级为"主动调度"——接管PulseHeart中部分周期性任务的调度权，使器官从"心跳被动驱动"进化为"时间中枢主动调度"。

### 实施要点

1. **不替换PulseHeart**：心脏仍是生命节律的核心，TimeCore是"调度协调层"而非"替代者"
2. **渐进式接管**：先接管1-2个低风险周期任务（如知识快照保存、compaction触发），验证稳定后再扩展
3. **调度信息通过time.tick payload传递**：在payload中增加 `scheduled_tasks` 字段，告知各器官"当前时间点应该做什么"
4. **器官按需响应**：器官在on_time_tick中检查payload中的scheduled_tasks，如果有自己的任务就执行，没有就跳过
5. **灰度开关**：`ENABLE_TIMECORE_ACTIVE_SCHEDULE=False` 默认关闭，验证稳定后再开启
6. **零风险回退**：开关关闭时完全不影响现有心跳调度

### 关键设计决策（请确认）

- **Q1**：先接管哪些任务？建议从"知识快照保存"和"compaction触发"开始（这两个是时间驱动的，不涉及核心生命节律）
- **Q2**：调度配置放在哪里？建议在config.py新增 `TIMECORE_SCHEDULE_CONFIG`，定义每个任务的cron表达式或间隔
- **Q3**：如何避免与PulseHeart的现有调度冲突？建议TimeCore只负责"触发建议"，实际执行仍由器官自己决定（避免双重执行）
- **Q4**：是否需要持久化调度状态？建议先不持久化，保持简单，等子任务3（知识时效性）再考虑

### 验收标准

1. 编译通过，全量回归零冲突
2. 开关关闭时0影响（与子任务1行为完全一致）
3. 开关开启时，被接管的任务按TimeCore调度执行
4. 不与PulseHeart的现有调度产生冲突（不重复执行）
5. 单元测试覆盖调度逻辑
