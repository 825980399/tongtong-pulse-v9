## 二、PulseHeart 调度机制现状（file:line 实证）

PulseHeart 内部维护 `self._scheduled_tasks: dict`（`PulseHeart.py:118`），`start()` 注册 **22 个**周期性任务（`PulseHeart.py:681-840`），每个含 `interval` + `event_type`：

- `knowledge_purge` → `"kidney.purge.check"`，interval 3600
- `snapshot_auto_save` → `"snapshot.auto_save"`，interval 1800
- `immune_scan` → `"white_cell.scan"`，600
- `narrative_reflect` → `"narrative.reflect"`，3600
- …（共 22 个，含 `health_check` / `metrics_collect` / `thymus_train` / `personality_verify` 等）

每次心跳 `_trigger_heartbeat` → `_check_scheduled_tasks`（`PulseHeart.py:479-497`）：

```python
for task_id, task_info in _scheduled_tasks:
    if now - last_run >= interval:
        due.append(task_id); task_info["last_run"] = now
for (task_id, task_info) in due:          # 锁外发射，避免死锁
    self._emit(task_info["event_type"], {"task_id":..., "last_run":...,
             "scheduled_at": now}, priority=3, layer="L3")
```

**关键结论**：Heart 仅是**触发源**（按 `event_type` 发脉冲），**执行逻辑在各器官的 `event_type` 订阅处理器中**。这是子任务2 方案的核心依据——只要把"触发源"从 Heart 换到 TimeCore，执行侧零改动。

## 四、推荐方案：A（换触发源）优于星轨字面 B（on_time_tick 执行）

星轨 §四.3-4 描述："调度信息通过 time.tick payload 传递，器官在 on_time_tick 中检查并执行"。我建议改采 **A 方案**：

### A 方案（推荐）

- TimeCore 在 tick 循环里，对被接管任务检查到期（`now - last_run >= interval`），通过 `get_info_field().publish` 发射**与 Heart 完全相同的 `event_type` 脉冲**（如 `kidney.purge.check`），pulse 结构对齐 `Heart._emit`。
- `PulseHeart.start()` 注册 `_scheduled_tasks` 时，**跳过被 TimeCore 接管的 `task_id`**（受 `ENABLE_TIMECORE_ACTIVE_SCHEDULE` 保护）。
- **执行逻辑零改动**：各器官的 `event_type` 订阅处理器原样工作，完全无感。
- **零双重执行**：Heart 移除触发源，TimeCore 成为唯一触发方。

### B 方案（星轨字面）

- TimeCore 在 tick payload 加 `scheduled_tasks` 字段。
- 器官在 `on_time_tick` 里检查 payload，认领并执行。
- 缺点：需把每个被接管任务的执行逻辑搬到各器官 `on_time_tick`，**违背 Q3"实际执行仍由器官自己决定"**，改动面大、易引入重复逻辑、与现有 `event_type` 处理器分裂。

**结论**：A 方案更贴合 Q3、改动最小、天然无双重执行。请星轨拍板 A vs B。
