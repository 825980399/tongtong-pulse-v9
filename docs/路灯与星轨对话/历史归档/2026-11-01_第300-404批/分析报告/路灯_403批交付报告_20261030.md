## 二、T0 前提核实：四处票面偏差

### 2.1 刀2 的「体积」不是主要矛盾

票面写「所有指标 5s 采样…浪费资源」「减少 5s 快照的体积」。实测：

| 读数 | 值 |
|---|---|
| 生产 `health_snapshot.json` 全量 | **4,834 字节** |
| 其中温指标（6 键） | 约 1,000 字节 |
| 其中冷指标（3 键） | 约 470 字节 |
| 每 5s 的实际开销 | 遍历全部器官、遍历全部订阅条件、glob 一次备份目录、读一次 `pending_patches.json`、拷贝 500 条历史 |

**只搬冷指标最多省 10%**，而且省下的是几百字节；真正的浪费是每 5s 做一遍全量扫描。
所以本刀把**温指标一起搬走**（60s 一档），热路径只剩读内存缓存。降幅 24.3% 是副产物。

### 2.2 刀4.2（坏 JSON）早已修好，本刀只补判据

票面：「归档目录里有空 JSON，读的时候 JSONDecodeError 炸了但被静默吞了」。
实测 `capability_ledger.reconcile_reports`：

- 333 批刀6 已改为「跳过 + **WARNING 级 + 带文件名**」；
- 356 批刀10 又加了「同一文件进程内只留痕一次」（防每轮重刷）；
- 本批实测两个坏文件（0 字节 + 截断 JSON）：`unparsable=2`、`unparsable_files` 两条、
  WARNING 消息里能定位到 `_archive/empty.json` / `_archive/broken.json`。

**不改代码，改为钉成回归判据**（`test_20/21/22`），防以后有人把它退回 silent。

### 2.3 刀4.1 的真根因：两个写口没走硬化写通道

`nucleus/data/DataAccessLayer.safe_write_json` 早就有 `_replace_with_retry`（D186-D，3 次退避），
但 `pending_patches.json` 的唯一写口 `pending_write.write_pending` 与
`evolution_budget.save_budget` **都是自己写的单次 `os.replace`**，没走那条通道。
所以 16:09-16:32 的运行窗里才会撞 WinError 5 —— 不是"没有重试机制"，是"有机制但这两个写口没用"。

### 2.4 刀3 的事件摘要不能带 payload

票面要「这 5s 里发生了什么」。如果直接塞 history 记录（含 payload），5s 一次的
`health_snapshot.json` 会从 4.8KB 涨到几十 KB（`eyes.stream_frame` 这类带图的 payload 更大）。
本刀只放**事件名**（去重、保序、上限 50），payload 仍留在 tracer/pairs 里按需查。

## 三、刀1 施工（`2d465273`）

### 3.1 两类链的口径

| 类别 | 判据 | 依据 |
|---|---|---|
| 同器官 | 同一器官**相邻**两次 emit，间隔 **< 1s**（开区间） | 器官内部处理顺序 |
| 跨器官 | 同一 `pulse_id` 的 emit→receive，间隔 **< 5s** | 投递事实；`pulse_id` 保证配对精确，不靠时间邻近猜 |

「相邻」是关键：若取"窗口内任意两点间隔 <1s"，既是 O(n²)，也会把 A→B→C 里
A→C 这种间接关系全算进去，链数瞬间爆炸。判据 `test_12` 专门守这条。

### 3.2 真实语料试跑（10-21 的 pairs，取末尾 3600s）

```
读入 38,254 行 / 16MB（打到上限 ⇒ truncated=true）
emit 8,740 ／ receive 29,514 ／ unmatched_receive 3,758
同器官链 7,698 条（1,000+ 种不同链）
跨器官链 25,441 条，涉及 55 个器官
汇总记录 5.9KB（Top20 + by_pair Top20，不存全量）

头部同器官：eyes.stream_frame → eyes.stream_frame  6,505 次（p50 513ms）
            heart.beat → heart.alive                252 次（p50 19.85ms）
头部跨器官：眼睛 → 血管      eyes.stream_frame 6,610 次（p50 2.57ms）
            眼睛 → 视觉皮层  eyes.stream_frame 6,610 次（p50 2.05ms）
```

### 3.3 三处「不假装读全」的设计

1. **滑动窗口而非增量 offset**
   offset 状态文件遇到进程重启 / 文件轮转 / 半行截断，任何一处都能让它**静默停更**——
   而"台账不再增长"比"多读几 MB"难查得多。这里每小时只跑一次，尾部读最近 3600s，
   失败可见、重启自愈、不需要状态文件。
2. **覆盖度诚实**
   16MB 尾部上限撞上时（高负载小时），记录里落 `truncated` / `coverage_s` /
   `coverage_ratio` / `complete`。上面那次试跑 `coverage_ratio < 1` —— 读方一眼能看出
   "这不是完整一小时"，不会把偏少的链数当成系统真的安静了。
3. **一发射多接收**
   去重键必须是 `(pulse_id, 接收器官)`。只按 `pulse_id` 去重会把第二个以后的接收方全丢掉：
   实测三接收方场景链数从 3 掉到 1。判据 `test_21` 守这条。

### 3.4 落盘与节流

- `data/monitor/causal_chains_YYYYMMDD.jsonl`，每小时追加**一条** `kind=hourly_summary`；
- 挂在 `_on_heartbeat_alive`（与 402 死信台账同一挂点），按 `int(now // 3600)` 判桶；
- `/data/` 整目录被 `.gitignore` 忽略 ⇒ 只落盘不进 git。

### 4.1 三档划分

| 档 | 间隔 | 键 | 落哪个文件 |
|---|---|---|---|
| 热 | 5s | 内存压力/GC/线程/句柄/心跳/脉冲/信息场/梦境/反思/肝脏/情绪/生命状态 | `health_snapshot.json` |

热文件**不保留**温冷键，只留 `tiers` 元信息（刷新时刻、年龄、hourly 路径、键清单）。
保留旧值就等于"拆了没拆"：读方仍读到 5s 一刷的旧数，体积也不降。

### 4.2 三处读方必须跟着改（本刀最容易埋的坑）

热文件里没有温冷键之后，三个读者会**静默变空**：

| 读方 | 会坏成什么样 | 改法 |
|---|---|---|
| `functions/health_ui.py` | 看板器官数/链路状态/兴趣全 0 | 在**服务端出口**合并，前端 JS 一行不改 |
| `functions/runtime_state_writer.py` | 进化看板 `knowledge_evolution`/`organs` 变 `{}` | 读合并视图 |
| `nucleus/world_model/expectation_ledger.py` | `health.knowledge_evolution.present` 等断言翻成 `field_not_exposed` | 读合并视图 |

统一走 `utils/snapshot_tiers.read_merged()`；hourly 缺失或坏掉时降级返回热文件并标
`merge_source=hot_only`，**绝不把缺失键填 0**（没测到 ≠ 真 0，这是 401/402 反复踩过的坑）。

### 4.3 降幅与「默认行为不变」

- 生产快照切片实测：**4,834 → 3,661 字节（−24.3%）**，温冷文件 1.4KB。
- `_build_observability_snapshot(skip_slow=False)`（既有调用方与测试）仍**每次全量现算**；
  只有两条写盘路径传 `skip_slow=True`。判据 `test_30` 守这条，避免"分频"变成一次静默的行为变更。
- 元信息本身也控了体积（去掉冗余的 present 列表、缩短 note）：热文件 5s 写一次，
  每多 100 字节就是每天多写 1.7MB。

## 五、刀3 施工（`f7cd202a`）

心跳段新增三个字段（频率不变，仍 5s 一次）：

| 字段 | 语义 |
|---|---|
| `prev_beat_events` | 上次快照到现在发生过的事件名（去重、保序、上限 50，**不含 payload**） |
| `prev_beat_event_count` | 条数 |
| `prev_beat_span_s` | 距上一次快照的秒数；**首拍为 `None`** |

首拍必须是 `None` 而不是 0：没有"上一次"时，0 会被读成"这 5 秒什么都没发生"，
而真相是"还没开始观测"。判据 `test_20` 守这条。

为什么新开 `InfoField.recent_event_names()`：`get_history()` 会先
`list(self._history)` 全量拷贝（上限 2000 条）再过滤，在 5s 心跳路径上白拷一份；
新方法从 deque 尾部倒着走，遇到第一条早于 `since_ns` 的就停。

- `_m403_alarm_transition`：正常→超阈值 WARNING；持续超阈值 **30s 内不重复**；
  超阈值→正常 **INFO**（恢复）。
