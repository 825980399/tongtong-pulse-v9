## 〇、结论（一句话，可复算）

> **不该先做落盘。** 实测 `l2_store_size` 全程为 **0** —— L2 的 `store()` 只接受
> `origin == "user_query"`，而曈曈自主运行（`evolution_task` / 定时拍）不产生这个
> origin，**料从来没进过 L2**。此时落盘等于给一张空表加持久化，重启后读数仍然是 0。
>
> **先修准入（让自主流量能进 L2），再谈落盘；落盘取选项①（仅落盘命中计数 + store 计数）即可。**

复算方式：`python tmp/p330_root/d5_l2.py`，看 `readings.shadow.store_size_max == 0`
与 `readings.config.ENABLE_SEMANTIC_CACHE_L2 == True` 同时成立。

### 1.2 存储态：**纯内存**

`nucleus/llm/semantic_cache.py::SemanticCacheL2`

- 条目容器：`self._entries: dict[str, L2Entry]` —— 进程内 dict，**重启即空**；
- 类体内**没有任何**落盘调用：`json.dump` / `open(` / `os.replace` / `sqlite3` / `pickle` / `makedirs` 命中 **0**；
- 淘汰：超容量按 `last_hit_ts` 做 LRU，过 TTL 懒删 —— 都在内存里完成。

⇒ 与 320 的结论一致：L2 是内存层，**能力被用上的证据随进程消失**。

### 1.3 准入态：**这才是真瓶颈**

```python
class SemanticCacheL2:
    _ALLOWED_ORIGINS = ("user_query",)          # 硬闸：只收这一种来源
```

全仓 `store_l2(...)` 的**外部调用点只有 2 处**，都在
`nucleus/reasoning/ReasoningExperienceIndexer.py`，且**硬编码** `origin="user_query"`。

而曈曈自主运行的调用来源是 `evolution_task` 一类（`call_recorder` 里
`ORIGIN_EVOLUTION_TASK`），**永远不等于 `user_query`** ⇒ `store()` 直接 return False。

## 二、三选项（三要素之二）

前提：**三个选项都建立在"先修准入"之上**。不修准入，三者收益全部为 0。

| 选项 | 做什么 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **① 仅落盘命中计数**（最小） | 把 `_stat`（hits/misses/rejected/stores）与 `l2_store_size` 周期性落 `data/reports/llm/l2_stats.json` | **低**：约 40 行，一个写盘口 + 一个读盘口；无新依赖 | 「能力被用上」有**跨重启**的时间序列（次数级证据）；能回答"这周 L2 用了没有" | 写盘频率需节流，否则日志级噪音；计数不含语义内容，**不能**回答"用对了没有" |
| **② 落盘命中 + 影子键** | 在①之上再落 `l2_would_hit` / `consistent` / `l2_sim` 的影子对表（316 已有 `l2_store_size`） | **中**：约 100 行；需要定影子键（prompt 摘要？哈希？）避免落原文 | 能算 **L1/L2 一致率**，这才是"学到的规则被正确复用"的证据 | 落 prompt 摘要 = 碰数据面，需先过 PII 纪律（铁律143 独立复扫）；键设计不当会泄露原文 |
| **③ 全量 L2 快照** | 把 `_entries`（含 response 全文）序列化落盘，重启后热加载 | **高**：150 行＋启动路径改动＋容量/一致性问题 | 重启不丢缓存，冷启动即命中 | **最大**：落的是 LLM 原文响应（可能含 PII/密钥片段）；与"永不抛出"契约冲突（加载失败要降级）；容量 2000 条 × 平均响应长度 = 体积不可控 |

## 三、建议（三要素之三）

**建议顺序：先 ①，②缓议，③不做。**

1. **本阶段不做落盘**，先补一条"准入"账：
   让自主流量的缓存效果**先在内存里可见**（`l2_store_size > 0`），否则任何落盘件拿到手都是 0。
   - 最小做法：在 `store_l2` 调用侧显式传真实 origin（而不是硬编码 `user_query`），
     并评估是否把 `evolution_task` 加进 `_ALLOWED_ORIGINS`。
   - **这是行为变更**（L2 开始对自主流量生效），必须先由星轨+小林裁，**不在 330 自行开**。
2. 准入账出数（`l2_store_size` 不再恒 0）后，落盘取 **①**（只落计数，不落内容）——
   零 PII 面，成本最低，足够支撑掌握度"能力被用上"的**次数级**外部证据。
3. **② 暂缓**：它的价值（一致率）依赖 `l2_would_hit=true` 出现，而当前为 0；
   且一旦要落影子键就进 PII 面，需独立复扫，不值当提前做。
4. **③ 不建议**：落 LLM 原文响应与项目既有的 PII 纪律正面冲突，
   而它换来的"重启不丢缓存"在 1 小时 TTL、2000 容量的设定下收益有限。

### 与掌握度证据链的关系（重要）

掌握度"能力被用上"的缺口，**根因不在 L2 落盘**。按 330 刀1 之后的读法：

- `hard_strict` 是 O3 的 N 口径（判据面），
- L2 命中是**复用面**，
- 两者都不是"能力变化自证"的唯一来源；真正缺的是**活体自转断言**（331 任务3 维度1 正在查）。

因此：**L2 落盘即便做完，也只能补"复用次数"这一小块，不应把它当成掌握度自证的堵点。**
本结论建议同步给星轨，避免把 331 的取证预期押在这条线上。
