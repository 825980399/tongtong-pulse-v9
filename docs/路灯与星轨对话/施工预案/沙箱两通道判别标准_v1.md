## 一、问题定性（不是"生成质量差"，是"口径错配"）

| 事实 | 读数 | 来源 |
|---|---|---|
| 历史补丁总数 | 84 | `data/patches/patch_history.json` |
| 子串命中沙箱黑名单 | 61（72.62%） | 325刀1 / 326复核一致 |
| 其中 `getattr(` 类 | 54 | 325刀1 |
| **真危险（非惯用法真实调用）** | **2** | 326复核：`_do_cleanup`（subprocess）、`_safe_eval_arithmetic`（eval/compile，按设计保留） |

沙箱的 `_security_precheck` 是**纯子串匹配**（`keyword.lower() in code.lower()`），
它本来的对象是**不可信外部片段**；而派单把**本仓方法体整段**喂进去，
于是 `getattr(cfg,'X',d)` 这种热加载惯用法每次都被判"危险"，同一补丁派六次败六次。

**结论**：需要的不是"放宽黑名单"，而是**按来源分流**——同一个关键字，
在本仓代码里是惯用法，在外部片段里就是危险信号。判别必须先于判断。

## 二、两通道判别标准

判别只用**三个可观测事实**（不看主观、不看"像不像"）：

1. `patch.file` 是否**落在仓内**且文件存在；
2. `patch.original_code` 是否**非空**（= 方法体替换，而不是整段新代码）；
3. `patch.modified_code` 能否 **AST 解析**。

| 通道 | 判据（需同时满足） | 用哪张表 | 处置 |
|---|---|---|---|
| `trusted_repo`（可信） | file 落仓内且存在 · original 非空 · AST 可解析 | **惯用法白名单** `TRUSTED_CODE_IDIOMS` | 命中且**全属登记册** ⇒ `class=idiom`（不算生成质量问题）；含非登记册真实调用 ⇒ `class=real`（真危险，转人工） |
| `external_fragment`（不可信） | 无 file / file 在仓外 / original 为空 | **黑名单** 沙箱 `DANGEROUS_KEYWORDS` | 子串命中即拦，**无豁免、无解释** |
| `unparsed`（解析失败） | AST 解析失败 | 同不可信 | **fail-closed**：不许"解析不了所以放行" |

**为什么 `unparsed` 单列**：325 刀1 已有 `class=unparsed` 这一档（84 条里 1 条）。
把它并入 `literal` 会让"看不清"变成"没问题"，这是判据纪律明令禁止的。

## 三、本仓惯用法登记册（7 条，每条必须写理由）

理由不写清的一律不许登记——否则登记册会退化成"把黑名单搬空的后门"。

| 关键字 | 为什么在本仓是惯用法 |
|---|---|
| `getattr(` | 热加载/配置读取：`getattr(cfg,'X',default)`，全仓数百处 |
| `setattr(` | 运行期参数回填：`refresh_runtime_params` 系补丁的常见写法 |
| `delattr(` | 属性清理：与 setattr 成对出现于状态复位路径 |
| `open(` | 文件 IO：读写 `data/` 下 json/jsonl，各器官常规操作 |
| `file(` | 历史兼容词法（py2 遗留），仅作为字符串/老代码出现 |
| `input(` | 交互式输入：控制台脚本与工具入口 |
| `raw_input(` | 历史兼容词法（py2 遗留） |

登记册**新增门槛**（写进流程，不只写进文档）：

1. 必须先有**实测证据**表明该关键字在本仓某类方法里是惯用法（不是"我觉得"）；
2. 必须**同时**在 `TRUSTED_CODE_IDIOMS` 写理由（缺理由 = 不允许登记）；
3. 登记册只影响 `class` 归类与留痕，**不影响沙箱是否拦**——拦不拦永远由 `DANGEROUS_KEYWORDS` 决定；
4. **非设计内**的真危险（`class=real`）**永不登记**：`subprocess`、`__builtins__`，以及任何"没有小林裁决依据"的
   `eval(`/`compile(` 用法，一律走外部片段口径。
   ★v1.1 修订（328刀4）：`eval(`/`compile(` 经小林拍板②登记为**设计内危险**（见第七节），
   但登记**只改归因不改拦截** —— `would_block` 仍为 True、`sandbox_incompatible` 仍为 True、
   派单照旧转人工。所以"登记"绝不等于"放行"。

## 七、v1.1 边界修订（328批刀4 · 小林拍板② 落地）

### 7.1 判据变了什么（只有一处）

| 项 | v1.0（326） | v1.1（328） |
|---|---|---|
| 白名单能否容纳 `class=real` | **永不** | **非设计内永不；设计内可进**，且必须显式登记在 `DESIGN_INTERNAL_IDIOMS` |
| `eval(` / `compile(` | 判 `real`，转人工 | 判 `idiom` / `idiom_scope=design_internal`，**仍转人工** |
| 拦截行为（`DANGEROUS_KEYWORDS` / `would_block` / `sandbox_incompatible`） | —— | **逐字未变**（84 条中 `would_block` 仍 61 条；沙箱源码 git clean） |

### 7.2 判据为什么必须"显式集合"而不是"看理由里有没有'设计内'"

理由串是给人读的，会被改写、会被翻译、会被截断。若用"在 reason 里找关键字"来判类别，
一旦有人改了措辞，分类就**静默翻转**，而且没有任何读数会变红。
故落地为两个显式集合：`TRUSTED_CODE_IDIOMS`（9 条）+ `DESIGN_INTERNAL_IDIOMS`（2 条：`eval(`、`compile(`），
外加 `registry_boundary_check()` 三项反向校验（登记不自洽 / reason 前缀不符 / "偷渡"进来的设计内）。
