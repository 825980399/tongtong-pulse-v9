## 1. 共性根因：五类问题同属"只写不读"缺陷类

烛微运行日志深度分析发现 5 类问题，本批治理的 T-105a/b/c/d 四类共同根因为：
**状态被写入后，下游消费方从未/很少回读该状态**，导致"写入→消费"链路断裂，形成假闭环或永久饥饿。

| 子任务 | "只写"点 | "不读"后果 |
|---|---|---|
| T-105a | `verify_submitted_patches` 验证字段写回 | 放行判据入队时恒假 + 验证后无人复查 ⇒ 0 放行（30 条 `runtime_verified=True` 全积压） |
| T-105b | `_deferred_from_prev_round` 延期标记写入 | 627 个 `.py` 中 0 读取点 ⇒ 8 位置连续 7~9 轮被延（永久饥饿） |
| T-105c | 策略 4 假救回把 587 字原文换 35 字标点串入库 | 策略 5（容错解析）被永久遮蔽，监控盲区 |
| T-105d | wiki 命中落胃仅 2 行（双腿断点）+ 合规 UA 被覆盖 | 上游成功率改善无法转化为知识入库；反爬命中无证据 |

本批统一治理思路：**补回读取/消费边（复通）+ 修正判据读嵌套真字段 + 加单测时序负控**。

## 2. 各子任务根因 / 改法 / 验收 / 证据

### 2.1 T-105a（P0）：T3 待审批积压修复（批准→落盘断链复通）

**根因（两层）：**
1. 放行判据在入队时即求值，但 `runtime_verified` 只能在入队 ≥300s 后才出现 ⇒ 入队时恒假。
2. 验证写回后**全仓无任何代码对已入队条目重跑放行判据** ⇒ 即使验证通过也无人复查放行。
3. 复查若读顶层 `runtime_verified` 会读**污染字段**：该字段由 `verify_submitted_patches` 对所有处理过的补丁（含失败补丁）无条件置 `True`，不可作放行依据。唯一真验证字段是嵌套 `runtime_verify_result.verified`。

**改法：**
- **补回边**（`SafeEvolutionExecutor.py`）：在 `verify_submitted_patches` 写回字段的同函数尾部，对 `status=pending` 且满足 T-101a 条件的条目调用放行路径；放行日志含可 grep 关键字 `低风险可放行(已升approved)`。
- **放行判据改读嵌套字段**（`PatchManager.py`）：放行条件由 `runtime_verified is True` 改为
  `_rvr = patch.get("runtime_verify_result") or {}` 且 `_rvr.get("verified") is True`；并追加 `baseline_errors > 0`（不可判定者转人工队列，优先顶层 `baseline_errors`，回退 `runtime_verify_result.baseline`）。
- **单测补时序负控**（`tests/test_t105a_release_loop.py`）：断言"入队时 `runtime_verified` 不存在 ⇒ 不放行"、"验证后复查 ⇒ 放行"。

**先红后绿证据：** `tmp/pytest_t105a_red.log`（修复前 **6 failed, 25 passed**）→ `tmp/pytest_t105a_green.log`（修复后 **36 passed**）。

**运行时验收（任务书要求，延后至重启）：** 验收判据"≤10min 出现首条 `低风险可放行(已升approved)` + 队列存量单调下降"依赖框架重启后的真实运行，任务书明确"等本批交付后统一重启验收"，故本次以离线单测覆盖放行判据逻辑，运行时验收列为后续待办（见第 5 节）。

### 2.2 T-105b（P1）：T4 延期标记只写不读修复

**根因：** `_deferred_from_prev_round` 在 `SafeEvolutionExecutor.py` 中被写入（同优先级组内标记），但 627 个 `.py` 中**无任何读取点**；稳定排序使前 8 个位置逐字节相同、连续 7~9 轮被延 ⇒ 永久饥饿。

**改法：** 补读取点——同分问题时 `_deferred_from_prev_round=True` 者排到该组**末尾**（后置），打破稳定排序带来的永久饥饿；其余同分位置保留原序。

**先红后绿证据：** `tmp/pytest_t105b.log`（修复前 **3 failed**）→ `tmp/pytest_t105b2.log`（修复后 **3 passed**）。

**验收：** 延期标记已有读取点；饥饿位置不再恒居尾（由单测 `tests/test_t105b_deferred_read.py` 断言后置行为）。

### 2.3 T-105c（P1）：T1 胃 JSON 解析失败修复

**根因：** LLM 生成非法 JSON 占比 75.4%；**策略 4（假救回）把 587 字原文替换为 35 字标点串入库**，且因其顺序靠前，**策略 5（容错解析）被永久遮蔽**；同时 `消化完成: N字` 打的是原文长度，造成"587→35"监控盲区。

**改法**（`PulseStomach.py`）：
1. **策略 5 与策略 4 互换顺序**：先跑策略 5（容错解析），再跑策略 4。
2. **策略 5 输出补"列表 repr 需 json 化"**：防止 `repr(list)` 文本入库。
3. **策略 4 值有效性闸**：`if v and not set(v) <= set(':,[ ]')` —— 垃圾值返回 `None`，落策略 5 / 失败报告。
4. **消化完成字数修正**：`消化完成: N字` 改打 `cleaned_content` 长度，消灭监控盲区。

**证据：** `tmp/pytest_t105c.log`（**4 passed**）；既有 `tests/test_pulse_stomach_m52.py` 仍 3 failed（pre-existing，与 T-105c 无关，见第 3 节门禁③）。

**验收：** `已格式化: 35字` 计数归 0；`策略5(容错解析` 开始有命中（由单测 `tests/test_t105c_stomach_json.py` 覆盖）。

### 2.4 T-105d（P1）：T5 百科查询器修复（部分）

**根因（三层，详见前序 + 本会话收尾）：**
1. 合规 UA 被循环内无条件覆盖 ⇒ 零生效。
2. 裸抽象词重试放大 2×。
3. `channel=="wiki"` 命中即丢 payload 的**双腿断点**（`PulseLegs.py` 中 `if _route.get("channel") != "rss": return False` 把 wiki 命中直接丢弃，落胃仅 2 行）。

**改法：**
- **UA 决策一处收口**（`WikiQuerier.py`）：合规 UA 首发；`_UA_POOL` 轮换仅在合规 UA 被拒（`HTTPError`/`403`）后启用——消除"代码里写了但请求头没带"的假生效。
- **双腿断点修复**（`PulseLegs.py`）：将 wiki 分支从"直接 `return False`"改为经 `DigestEvent.KNOWLEDGE` 走正常消化链路（与 RSS 一致，不旁路）；兼容 `dict` payload（title/keyword/summary/url）与 `WikiResult` 对象（`getattr` 兜底），命中计数与 RSS 一致（`_learn_count`/`_success_count`/`_consecutive_failures` 复位）。
- **403 响应体留证**（`WikiQuerier.py`）：`403` 时读取响应体前 512B + `Retry-After` / `X-Baidu-Error` / `X-Baidu-Trace` 头，经 `get_module_logger("WikiQuerier")` 落 `warning`（含 `403 反爬命中` 关键字），便于后续人工钉死拒绝条款。

**证据：** `tmp/pytest_t105d.log`（**5 passed**）→ `tmp/pytest_t105d_reconfirm.log`（**5 passed**，回归复确认）；既有 `tests/test_wiki_querier_403_m13.py` 纳入批次 58 passed。测试覆盖：UA 收口（首请求合规 UA / 被拒后轮换池）、403 留证（body+头）、wiki 断点复通（经 KNOWLEDGE 消化返回 `True` / 无 payload 走原路径 `False`）。

**验收：** 合规 UA 真实生效（请求头含 contact UA）；wiki 命中不再被丢弃（落胃行数 > 0）；403 响应体留证（由单测覆盖）。
