### C 类 · 结构性缺陷（最深、最该记）

**C1 · 裁决产物无版本控制（本核查最重要发现）**
`data/patches/{pending,applied_355,rejected_355}.json`、`data/reports/audit/audit_*.json`、`_m356_key_map.json` **全部被 .gitignore**。这意味着：
- 355 的裁决（7 应用/24 拒绝）、356B 的键迁移（669 合并）、对账（7 fixed/21 wontfix）——这些**不可逆、需要审计**的产物**没有任何 git 历史**。
- 回滚只能靠散落在 `.bak_batch35*/`（同样是 gitignore 的临时目录）的副本。
- 一旦池文件被后续批次重写，历史裁决永久丢失，事后无法对账"谁在何时把哪条改成了什么"。

**规避**：今后凡"裁决清单 / 键迁移映射表 / 对账清单"这类**审计性产物**，必须同时落一份到 **git 跟踪的目录**（如 `docs/路灯与星轨对话/交付报告/证据件/` 或仓库根下的 `evidence/`），不只在 data/ 下留。

**C2 · 跨批遗留无权威清单（本核查次重要发现）**
354 报告明确写"其余 **11 处** `__main__` 自测块另立批评估"（还写了快照 gzip、HHI 观察、趋势迁看板等 P2 遗留）。但 355、356 两批**没有任何一处回头闭合它**——现全库 `__main__` 自测块 **54 处**仍在（比 354 记的 12 处还多，期间还新增了）。仓库里**没有单一权威的"遗留/待办"清单**，只有零星老批次的清单文件。

**规避**：建立**一份 git 跟踪的遗留登记**（跨批不丢），每批交付末尾把"本批遗留"追加进去，下批开工前先扫一遍。这是"下次遇到时规避"最该落地的动作。

## 三、规避清单（下次开工前直接照做）

**开工前**：
1. `git log -3 -- 任务书` + `git status` + 确认活体 pid/停机状态（实测，不信任务书）

3. T0 逐刀核对代码现状（防重复施工：任务书前提 vs 代码现状，不符就按现状施工并留痕）

**施工中**：

5. 任何批量"多源→同一目标"的写，先做目标键冲突预检（A6）
6. 验收/测试判据收窄生产面 + 排 docstring + 不锁易变精确值 + 断言串从真实产物反向取（A1/A2/A3）
7. 落盘读数前用"各分支计数之和==总量"自检（A5）
8. 内嵌脚本一律 .py 文件，不 heredoc（B1）
9. 每刀落地前重看任务书（D1）

**交付后**：
10. 裁决/迁移/对账等**审计性产物落一份 git 跟踪副本**（C1）
11. 把本批遗留**追加进权威遗留清单**（C2）
12. 报告末尾的偏差披露表，逐条和"实际做了什么"对账（别写"已完成"但代码没改）

## 四、一句话结论

我的交付在**正确性、门禁、防重复施工**上总体可靠（多次靠 T0 实测和门禁纠出任务书/代码的错），但有两类**体系性**问题必须改：
