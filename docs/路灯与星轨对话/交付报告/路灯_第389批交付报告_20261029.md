### 2.1 刀1 的两个观测面缺陷（本刀已修）

**(a) 基线不按进程代分键** —— `_tm_baseline.snap` 是全局单文件。
13:37 的基线由 pid21168 写下，而该进程 **13:37:53 因 RSS 超限重启**；14:08 起的
pid22680 首次采样会拿**死进程**的 3304 万对象快照做 `compare_to` ⇒ 全负增量 ⇒
全被 `size_diff <= 0` 过滤 ⇒ 报 `no_growth`。**假「没涨」与真「没涨」同形**（铁律276）。

**(b) 槽位口径骗人（同型坑第 4 次）** —— 388刀2 把类默认改成"每 2 小时 12 槽"，
但 `config.py:6151 M339_MEMORY_PROBE_HOURS = (5, 13)` 才是生产生效值
（`_m339_cfg_get` 优先读 config）⇒ **12 槽从未生效**。
而且真生效会更糟：tracemalloc 单次实测 **837s**，12 槽 = 每 2 小时卡进程 14 分钟。
⇒ 回滚为 `(5, 13)`，密度诉求交给 gc 轻采（实测 2.1–2.8s，本来每小时都在跑）。

## 三、刀1（P0）泄漏差分归因：结论四条

报告全文见 `docs/分析报告/路灯_389_泄漏差分归因_20261029.md`，要点：

1. **「94.2MB/分钟」不是稳态速率，是重启后第一小时的斜率。**
   实测分段：07:52→08:00 = 94.4MB/min；09:00→10:00 = 35.8；10:00→11:00 = 3.5；
   **10:00→12:00 三小时净增 188MB（1.6MB/min）**。曲线在 **~11GB 处饱和**。
2. **GB 级增长的两个大头**：
   `PulseSnapshot.py:1457` 的 `tbl.to_pylist()` = **2044MB / 3304 万对象**；
   `PulseEyes.py:305` 的相机帧 = **887MB / 2018 对象**。
3. **两者性质不同**（这是本刀最关键的判读）：
   - 3304 万对象在 837s 内被释放 —— 同一次采样里 gc 全堆只数到 **dict 6678 个**。
     ⇒ 是**瞬时峰值把 RSS 顶成高水位棘轮**（free 后内存不归还 OS），不是常驻泄漏。
     ⇒ 388刀1 的逐批加载正是对症，**但重启后 tracemalloc 一槽没跑，至今未证实**。
   - 887MB 帧是**真常驻**，持有者已指认（刀2 修）。
4. **仍有 17.3MB/min 未指认**（14:09→16:04：6875→8878MB）。
   tracemalloc 可见 **3.29GB / RSS ≈11.5GB = 29%**，8GB 落在不可见面
   （最可能是 pyarrow C++ arena；13:37 那个 19.9GB 进程 164 秒只记到 3MB 是旁证）。

**只定位不修复**：本刀没有改任何加载路径、缓存大小、帧生命周期。

## 四、刀2（P0）眼睛帧持有卸载

持有链（代码走读 + 数量级吻合）：

```
PulseEyes._stream_loop → capture_frame()          # PulseEyes.py:305 = cap.read()
  → pulse_core.emit(payload={"raw_data": frame})
  → info_field.publish(pulse) → 第4步：
        self._history.append({... "payload": dict(payload)})   # 浅拷贝，整帧被带走
  → _history = deque(maxlen=PULSE["info_field_max_history"]=2000)
```

改法：新增 `_m389_elide_heavy()` —— **只在历史副本上**把重负载
（`bytes/bytearray/memoryview` 或带 `nbytes` 的 ndarray）换成
`{"_elided":"heavy","type","nbytes"}`；阈值 65536 字节，开关
`PULSE["info_field_history_elide_heavy"]=True`。
**live 脉冲一字不改** —— 视觉皮层拿的是 live pulse，不是历史副本。

**实测（隔离进程，2000 帧 × 450KB）**：

| 口径 | RSS 增量 | 历史里真字节 | 历史条数 |
|---|---|---|---|
| 省略关闭 | **+880.7MB** | 878.9MB | 2000 |
| 省略开启 | **+3.2MB** | 0.0MB | 2000 |

⇒ 票面目标「帧持有从 887MB 降到 <200MB」在机制上已达成（值从 878.9MB 降到 0），
**生产读数待重启后 13:00 槽位确认**（判据：`PulseEyes.py:305` 的 `size_kb`）。

附带修一处热路径：`payload_keys` 原来直接 `.keys()`，payload 是 list 时抛
AttributeError，把一条脏脉冲变成一次异常 ⇒ 按型别取键。

## 六、刀4（P2）重启计数桶

- 实测：`restart_count.txt` = **0**，`restart_blocked_at.txt` = 2026-10-03（旧值）
  ⇒ 票面「记了 1 次」不实，**本刀没有写生产文件**。
- 交付 `tools/m389_check_restart_counter.py`：
  - 三态读数 `ok / absent / unreadable`（读不动与"从没记过"必须分开，
    前者按 0 处理等于**放宽棘轮**）；
  - `--reset` 需 `--allow-prod` **且**过写盘守卫（不绕过铁律198），幂等；
  - **不动** `restart_blocked_at.txt`（冷却起点，清了等于提前放行）；
  - 修掉原文一处误导读数：未锁定时 `remain_sec` 原为整个冷却窗口
    （"未锁 + 还剩 6 小时"），本工具未锁即 0。

### ★留裁决：共用桶的设计风险（本刀不擅自改）

`restart_count.txt` 是**补丁自动应用**与**内存自动重启**共用的棘轮桶
（176批段2 明文"共用"，`counter > 3` 锁 `MEMORY_RESTART_COOLDOWN_HOURS`=6h）。
⇒ 4 次内存重启会把**补丁自动应用**锁 6 小时；反之补丁重启也吃内存重启的额度。
要拆成两个桶必须同时改 `apply_all_pending` 与 `memory_restart_bucket_state`
两处判定 —— 属设计变更，建议单独成批。
