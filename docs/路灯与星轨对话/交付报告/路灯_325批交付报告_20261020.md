## 二、刀1 · 生成侧危险关键字根因

### 实测把任务书的前提推翻了

任务书假设"生成侧持续产出含危险关键字的补丁"＝生成质量差。**实测不是**：

- 84 条历史补丁（有 `modified_code` 的）里 **61 条（72.62%）** 会被沙箱拦；
- 命中排行：`getattr(` **54**、`open(` 8、`setattr(` 8、`os.remove` 3、`subprocess` 2、`eval(` 2；
- 按 AST 去掉字符串字面量后分类：**idiom 57 / none 23 / real 2 / literal 1 / unparsed 1**。

`patch_1788891582_6ecc`（324 刀0 里六圈全失败那条）的真实内容是：

```python
_rp = getattr(_cfg, 'RUNTIME_PARAMS', {})
if 'search_cooldown_seconds' in _rp and hasattr(self, '_search_cooldown'):
    setattr(self, '_search_cooldown', _rp['search_cooldown_seconds'])
```

—— **本仓热加载的标准惯用法**。另有 `patch_1789060200_8ce1` 一次命中 12 个关键字，
展开看是 `PulseSkin` 的**危险模式字符串清单**（把 `"os.system"` 当数据写进列表）。

**结论**：根因是**口径错配**——沙箱 `_security_precheck` 是纯子串匹配，面对"不可信外部片段"，
而派单把**本仓方法体整段**喂进去。真危险只有 2 条（`_do_cleanup` 的 `subprocess`、
`_safe_eval_arithmetic` 的 `eval/compile`，后者按设计如此）。

### 改动（**未动沙箱黑名单**）

1. `patch_execution_dispatch.scan_dangerous_keywords()`：**唯一实现**，生成侧与派单侧共用；
   用 AST 区分 `none / idiom / literal / real / unparsed`，并给出 `would_block`（与沙箱逐字同判据）。
   > 分类顺序踩过一次坑：`getattr(` 既是"真实调用"又是"合法惯用法"，先判 `real` 会把 54 条全误报成生成质量问题。已改为"非惯用法的真实调用才算 real"。
2. 生成侧：`PatchManager.save_pending_patch` 入队前打标
   `danger_keyword_class / danger_real_calls / sandbox_blocked_keywords / sandbox_incompatible`
   ＋ 计数 `generated_flagged_dangerous`（`get_m325_danger_metrics()`）。
3. 派单侧：`select_patch_for_execution` 跳过 `sandbox_incompatible` ⇒ **不再六圈重试同一条**，
   记 `_M325_DISPATCH_REJ["sandbox_incompatible"]` 与日志（转人工）。

### 实测（`d1_danger_scan.json` / `d1_history_stats.json`）

| 用例 | class | 说明 |
|---|---|---|
| `return x + 1` | `none` | 不拦 |
| `getattr(_c,'RUNTIME_PARAMS',{})` | `idiom` | 拦但归因正确 |
| `['os.system','eval(','subprocess.call']` | `literal` | **不误判为 real** |
| `eval(s)` | `real` | 真危险 |
| 派单过滤 | `selected=['p_clean']` | 惯用法补丁被排除 |
