## 二、刀1 补丁生成器（P0·裁决②）

### 2.1 落地内容

新模块 `nucleus/evolution/patch_generator.py`（`GENERATOR_VERSION = "349.d1.v1"`）：

- **通道**：本机 Ollama `qwen2:7b-instruct-q4_K_M`（单价表 `0.0` 免费档），超时 60s。
- **输入**：池条目（`file/method/issue_type/line`）→ 程序侧 `extract_source_snippet()` 取源码片段（≤90 行）。
- **输出契约**：模型只回**锚点三元组** `{"anchor", "replacement", "reason"}` —— `original_code` 由程序从磁盘取。
- **三态可区分**（不静默）：`draft_ready` / `gate_rejected` / `generation_failed`，各有 `why`。
- **六字段证据门**（`check_evidence_six`）：`file/method/original_code/modified_code/reason/dedup_key`；`dedup_key` 还要求**可复算自洽**（与池同算法 `sha1(file|method|issue_type)[:16]`，实测同值）。
- **审核链**：草稿 → 证据门 → `requires_confirmation=True` → **独立草稿池** `data/patches/generator_drafts.json`（`schema=patch_generator_drafts/349.v1`）→ 人工审。
- **不进 O3 判死池**：`source="patch_generator"`，与 O3 消费口隔离（`d1_route.json` 的 `D_not_o3_pool` 用例）。
- **双通道并行**：`generate_patch_draft(transport=...)` 可注入传输层，隔离根用假 transport 免真调模型。

### 2.2 关键设计决策（都是踩出来的）

| 决策 | 为什么 |
|---|---|
| **锚点格式**而非整段 original+modified | 整段 JSON 要 400–700 tokens，必被 60s 截断（`json_unparseable` ×4）。锚点约 120 tokens |
| `num_predict=320`、`_SRC_MAX_LINES=90` | 实测本机 **7 tok/s**，60s 上限约 350 tokens —— 这是硬约束，不是调参偏好 |
| `check_splice_parses` 而非"片段自身能 parse" | 原判据把合法片段（改动落在 `try:` 内）判死；改后是「片段在文件中逐字唯一 → 替换 → **整文件** `ast.parse`」 |
| 锚点在**方法范围内**定位 + 记绝对行号 | 模型爱给 `try:` / `return None` 这类文件级高频行（`anchor_ambiguous:45/80`）；限定方法内 + 行号 splice 后断言 `strip()` 一致（`anchor_drifted`） |
| 独立草稿池，不塞 `pending_patches.json` | `PatchManager.save_pending_patch` 有「`modified_code` 首个 def 名 == method」硬约束 ⇒ 行级片段被**静默拒收**（隔离根落成空 list） |
