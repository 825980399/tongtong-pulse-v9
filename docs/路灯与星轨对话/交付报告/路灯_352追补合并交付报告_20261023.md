### 2. `grep REMOTE_API_CONFIG` 不可能清零

57 处里大量是设计内用法（见 §〇.6）。本批达成的是「**4 处旁路 + 3 处预检的活跃读取归零**」，不是全仓归零。任务书该验收行按铁律169 以证据否决。

### 3. 旁路端到端只做实 1 处

`ocr` 一处做了真调用端到端（`d11`）。另 3 处用「**同一取数函数 + 同一留痕模板**」做同源传递证明——构造整个器官实例（灵核/知识提炼/控制器）的代价与副作用（会触发器官初始化、外部依赖）与收益不成比例。

### 4. 判死性/命中率类读数均未产生

本批不涉及死代码判定与召回，无相关读数可报。

### 5. ★施工外发现：`TTP_` 前缀通道的既有误报

**现象**：每次 `import config` 打印 `[Config] 安全拦截: 环境变量 'TTP_REMOTE_API_KEY' 试图覆盖黑名单配置 'CONTROLLER_PERMISSION'，已忽略`。

**根因**（`config.py:3930-3970`）：`_ENV_PREFIX = "TTP_"` ⇒ 任意 `TTP_` 前缀环境变量都被当作配置覆盖通道；`TTP_REMOTE_API_KEY` → `config_path="remote_api_key"`。而告警的 `print` 条件**只是** `var_name in _HOT_RELOAD_BLACKLIST`，**没有校验是否真的匹配上**任何 `dict_key` ⇒ 宿主存在任意 `TTP_*` 变量，就会对每个黑名单配置项误报一条"试图覆盖"。

**判定**：这是 `P2-376` 安全加固的**既有判据缺陷**（非本批引入；实测 `_COVERABLE_CONFIGS` 中 `remote_api_key` 命中数 = **0**，即真的没匹配上，却已告警）。安全性未受损（确实被拦住了），但日志噪音会误导排查。

**我方未动**：`_apply_env_overrides()` 属安全/门禁逻辑，不在本批授权范围，**交星轨裁定**。可选项：(a) 把 `print` 移到 `break` 成功匹配处；(b) 退役后从宿主环境删除 `TTP_REMOTE_API_KEY`（更省事，且本批已使该变量无用）。
