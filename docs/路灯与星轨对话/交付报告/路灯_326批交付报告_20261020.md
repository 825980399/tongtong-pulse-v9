## 一、刀0 · applier 同名覆盖改多回调（★K3 并行前必做）

### 根因（实测确认）

`nucleus/mnemosyne/verification_learning_hub.py` 的 `_organ_appliers: dict[str, Callable]` 是**单值**容器。
同一器官被两条装配路径注册时后注册者**静默顶掉**前者，并刷一条「applier 被覆盖」WARNING。
`stomach` 器官即活体双注册样本（`qica_growth` 在 `main.py` 两条装配路径各注册一次，
另有 `self_inspector` / `PulseCortex` / `PulseSemanticComprehension` 多路吸收方），

   - 同 organ ＋ 同 tag ＋ **同对象** ⇒ 零动作（幂等）；
   - 同 organ ＋ 同 tag ＋ **换对象** ⇒ 原位更新（向后兼容旧"覆盖"语义）；
   - 同 organ ＋ **不同 tag** ⇒ **追加并存**（新语义，这是本刀的目的）。
3. **`_appliers_for()`** 统一归一化：兼容旧单值形态（历史内存态/旧序列化）→ 列表。

5. **调用点补 tag**（5 处，语义化命名，便于日后按吸收方定向关停）：
   | 文件 | tag | count_expect |
   |---|---|---|

## 二、刀1 · fail_count 落生产台账字段＋持久性语义（小林裁决④）

### 问题

原 `runtime_verify_fail_count` 只活在 `patch_history.json` 的单条记录里，且**只在写回路径落盘**；
派单过程中读取的是内存态。后果：
- 进程重启后若上一次写回未覆盖到该条 ⇒ **计数归零** ⇒ `_DISPATCH_FAIL_CAP=2` 永远打不到；
- 同一补丁可在"重启—失败—重启"循环里无限重试，`cap` 形同虚设。

### 改动（`nucleus/evolution/patch_execution_dispatch.py`）

1. **侧账本**：`data/patches/patch_fail_counts.json`（`version=326.1`），
   结构 `{patch_id: {fail_count, max_ever, first_at, updated_at, last_reason, source}}`。
2. **读写 API**：`_m326_load_fail_ledger` / `_m326_save_fail_ledger` / `_m326_bump_fail_ledger` /
   `_m326_reset_fail_ledger` / `_m326_persisted_fail_count` / `_m326_seed_from_trace` / `get_m326_fail_ledger`。
3. **cap 判定取持久值**：`max(记录字段, 侧账 fail_count)`，
   阻断原因文案 `verify_fail_cap(2>=2,persisted)` —— **括号里带 persisted 标记**，
   让读日志的人一眼分清"这次是累计值触顶"还是"本次会话偶发"。
4. **双写**：`_write_back` 同时更新记录字段与侧账，记录新增
   `fail_count_persisted` 与 `fail_count_source="ledger+field(326.1)"`。
5. **审计不丢**：清零时 `fail_count` 归 0 但 **`max_ever` 保留历史峰值**（只增不减）。
6. **trace 落痕**：派单 trace 行带 `fail_count_persisted` / `fail_count_ledger_version`。
7. **存量种入**：`_m326_seed_from_trace` 可从历史 trace 反推失败次数补进侧账（`dry_run` 默认开）。

### 实测（`tmp/p326_root/d1_restart_sim.json` · 6/6 PASS）

| 运行 | 模式 | 读数 |
|---|---|---|
| run1 | 失败 | `fail_count=1`、`persisted=1`、`source=ledger+field(326.1)` |
| run2 | 失败（模拟重启：新进程重读侧账） | `fail_count=2`、`persisted=2` ⇒ **跨重启累计成立** |
| run3 | 新进程再派 | `dispatched=0`、`blocked_reason=verify_fail_cap` ⇒ **cap 对新进程生效** |
| reset | 独立隔离根：1 次失败后成功 | 双写清零，`max_ever` 保留 ⇒ 审计可回溯 |

> 现有语义确认：cap 触顶后补丁**永不再派**（正确），故"成功后清零"用例改在独立隔离根上验证，
> 未污染 cap 用例。

### 生产落地（`tmp/p326_root/d1_prod_landing.json`）

## 六、刀5 · 掌握度 A5 需求承接断言 ＋ absorb 计数留痕

### 为什么加 A5

现有 A1—A4 断言只覆盖"图内被引用 / 覆盖率 / 入边"，**无法回答"需求源产出的东西有没有人接"**。
前批（324）已实证：需求条目可以进了台账就再无人看，系统对此**零断言、零告警**。
A5 把这一环补上：**N 拍内必须被引用或显式作废**，否则暴露为 `overdue`。

### 数据源（唯一）

`data/reports/evolution/intake_journal.jsonl` —— `nucleus/evolution/EvolutionLoop.py` 每拍追写
`{tick, growth_items}`。**为什么必须是它**：`intake_summary_latest.json` 是覆盖写（只有当拍），
无法回答"5 拍前的那条现在被接了吗"。故新增
`_M326_INTAKE_JOURNAL_REL` / `_m326_intake_journal_path` / `_m326_item_key` /
`_m326_next_tick`（**从台账最大 tick 接续**，跨重启不归零）/ `_m326_append_intake_journal` /
`get_intake_journal_stats`；汇总落盘前先追写台账，快照增 `growth_items` / `tick`。

### 断言实现（`nucleus/self_awareness/CallGraphAnalyzer.py`）

- `A5_WINDOW_TICKS = 5`、`A5_VOID_STATUSES`（作废状态集合）。
- `a5_growth_intake_assertion(n_window, root, journal_path, patch_history_path, handbook_refs, tick_now)`
  → 五态：`referenced`（patch_history 承接 / handbook 命中）/ `voided`（显式取消）/ `overdue`（超窗无承接）/ `pending`（窗内）/ **`UNAVAILABLE`**。
- **无台账或零条目 ⇒ `UNAVAILABLE`，绝不返回 0**（延续 322 批"读数为 0 与没接通必须可区分"）。
- `mastery_assertion_check(..., include_a5=True)`：A5 单独一栏，**不进 total/passed/failed**
  （避免新断言一上来就改动掌握度分子分母，重演 316 的计数污染）。

### absorb 留痕（刀0 的伴生读数）

每次吸收落一行，6 段：
`[326刀5][absorb] class=<吸收器类> organ=<器官> tag=<通道> rules=N applied=M tier=<high|mid|low>`，

## 七、刀6 · `_do_cleanup` 真·生成侧危险处理

### 问题

`organs/motor/PulseController.py::_do_cleanup` 用 `subprocess.run(["taskkill","/F","/PID",pid])` 关窗口。
在沙箱/受限环境里 `subprocess` 正是**黑名单第一位** ⇒ 这条**自身**代码被判 `real` 危险，
而它其实是"关自己开的窗口"的正当操作，属**口径错配**的典型样本。

### 改动

1. `import signal`；`subprocess.run(taskkill)` → **纯 Python** `os.kill(int(pid), signal.SIGTERM)`。
2. `ProcessLookupError` / `OSError` 按"**已关闭**"处理，落 **DEBUG 不刷 ERROR**
   （死 pid 是常态，不该每次清理都刷一条 ERROR 把真错误埋掉）。
3. 注释**不含** `subprocess` / `taskkill` 字样（首版正因注释里写了这两个词，子串预检照样命中，白改）。
4. `PatchManager.get_m325_danger_metrics(history_path=None)` 扩为**持久读**（不再依赖进程内计数）：
   `records` / `class_dist` / `real_class_count` / `idiom_class_count` / `sandbox_incompatible_count`。
5. **危险真值标注**（生产落地）：2 条 `real` 类补 `sandbox_incompatible=True` ＋ `reason` ＋
   `marked_by="326批刀6"`，**`status` / `runtime_verified` 零变化**（`verdict_state_unchanged=true`）。

### 实测（`tmp/p326_root/d6_cleanup.json` · 6/6 PASS）

| 检查 | 读数 |
|---|---|
| `cleanup_body_no_longer_hits_subprocess` | 对 `DANGEROUS_KEYWORDS` 实际命中仅剩 `threading.Thread`（**清窗线程本身**，移交项） |
| `cleanup_actually_kills_and_clears` | 目标 pid 33004 **4.2s 后 `alive=false`**，窗口列表自清 |
| `dead_pid_no_error_log` | pid 999999 ⇒ `DEBUG「窗口已退出或不可终止…按已关闭处理」`，`error_logs=[]` |
