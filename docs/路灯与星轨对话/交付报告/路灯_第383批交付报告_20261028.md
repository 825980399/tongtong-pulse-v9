## 三、两处设计点值得单独记

### 3.1 刀4：`stale` **不是结案**

`_is_open` 被 `prune` 用来保护「超期但未结案也留」（**留存**语义），而限额/截断排序
要的是「谁该占观察位」（**优先级**语义）。混用的后果：

| 若把 stale 塞进 `TERMINAL_STATUSES` | 结果 |
|---|---|
| `POOL_RETAIN_DAYS` 也是 **7 天** | 转 stale **当天**就被 prune 当结案删掉 |
| 结案率口径（status≠verified/wontfix 即未结案） | 被污染 |

所以另立 `_m383_is_actionable`：

```
_is_open(stale)            = True    ← 未结案，prune 继续保护
_m383_is_actionable(stale) = False   ← 让位，限额/截断排序靠后
```

有反向用例：**400 天的 stale 仍被 prune 保留**，并用「真结案才会被删」做对照
（证明不是 prune 失灵）。

### 3.2 刀5：「只收紧不放松」只有一行

```python
_whitelist_ok_a1 = _whitelist_ok_a1 and (_triage_a1 == "safe")
```

是 **`and`**。旧判定拒绝的补丁，三级绝不会放行。有源码断言
`test_m383_d5_call_site_uses_and_not_or` 钉死 —— 写成 `or` 就是
「旧拒绝 + 三级放行 = 放行」，安全面直接被打开。

另：**REVIEW 那一条的正确实现是「一行代码都不加」**。让它走「不自动」的默认路径，
由既有 `approve_o3_patch` 处理；有用例断言分级函数体内不出现
`approve_o3_patch` / `requires_confirmation =` / `auto_approved =`。
