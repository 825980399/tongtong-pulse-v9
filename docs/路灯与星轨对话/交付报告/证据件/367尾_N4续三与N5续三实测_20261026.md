（这份文档保留我第一次的错误判断作为记录：**"看起来像轮转"不等于"就是轮转"**。）

- `evolution_effectiveness.json` 是 `PatchAutoApprover.DEFAULT_FILE` **类属性**；
- `unresolved_samples_*` 是 `unresolved_samples._PREFIX` 拼接。
现有 `_M366_WRITE_REDIRECTS` 机制只能 patch **模块级常量**，加表项无效 ⇒
必须**逐个改测试**（给 fixture 注入沙箱路径），属新一刀，与本批「只测不改」的边界不同。

## 二、N5 续三：跨版本 worktree 对照 —— 既有失败有实测支撑了

### 方法（含铁律 174 的解法）

`data/` 有 **4.9GB**，不可能复制进 worktree。用 **NTFS 目录联接（junction）**：

```
git worktree add tmp/wt_b03a0798 b03a0798     # 365 批冻结前的版本
mklink /J tmp/wt_b03a0798/data <主仓 data>     # 实测 rc=0，67 子项可读
```

★**清理顺序是红线**：必须先 `rmdir` junction **再** `git worktree remove`。
顺序反了，`worktree remove` 会顺着 junction 删掉主仓 `data/`（4.9GB 生产数据）。

### 结果：64 条抽样全部 `red`

| 判 | 文件 | 用例 | 含义 |
|---|---|---|---|
| **`red`** | **8** | **64** | 旧版本（`b03a0798`）**也红** ⇒ **既有失败** |
| `green` | 0 | 0 | **无本批引入嫌疑** |
| `missing` | 0 | 0 | 旧版本也有这些用例（不是新增测试） |

抽样覆盖：`self_awareness_m18`(16) / `call_graph_m21`(12) / `m96_followups`(8) /
`m92_patch_guards`(7) / `m354_batch`(6) / `branch_concurrency_m32`(5) /
`cold_compaction_file_missing_m63`(5) / `log_decay_robustness_m49`(5)。

**⇒ 366 尾用 `git blame` 得出的「134 条既有 / 1 条本批引入」，现在有了实测对照支撑**：
64 条抽样在 365 批之前的版本上**同样失败**，不是本批引入。

（抽样 64/135 = 47%，不是全量 —— 如实标明。全量需要 135 条 × 2 版本 ≈ 40 分钟，
本轮不做的原因是与 N4 争 CPU 会让两边的写面读数互相污染。）

### 副作用与清理（如实记）

旧版 `conftest.py` **没有** 366 的写面重定向，因此对照期间产生了 2 个
`data/call_graph/unresolved_samples_*.jsonl`（各 12MB，共 24MB）。
已删除（确认是测试诊断产物，非生产数据），主仓 `data/` 校验完好：
`67` 子项 / `top_types_*` `99` 个，与跑前一致。
