## 一、A 面 · sample 间歇 provisional 成因 —— **定位到 W1 心跳，且发现"间歇"是每小时翻转**

### 1.1 代码路径（唯一降级口）

`o3_open_gate_report` 在抽样后做一次降级判定（`self_inspector.py`）：

```python
_w1b = w1_verdict_brief()            # 337刀8 薄封装，阈值只在一处
_rep["sample"] = sample_verify_hard_candidates(...)
if _w1b.get("verdict") != "alive" and _rep["sample"].get("verdict") not in (None, "UNAVAILABLE"):
    _rep["sample"]["verdict_raw"] = 原值
    _rep["sample"]["verdict"] = "provisional"
    _rep["sample"]["verdict_reason"] = "W1=%s ⇒ 抽样结论降 provisional"
```

⇒ `sample` 只有三种来源：`PASS/FAIL`（抽验自己给的）、`UNAVAILABLE`（无 hard 候选）、
**`provisional`（W1 不是 alive 时被降级）**。降级的**唯一开关是 W1**，与抽验逻辑本身无关。

### 1.2 读数（停机前 `logs/pulse.log` 实测）

| 项 | 实测 |
|---|---|
| `[326刀2][O3开闸]` 行数 | 13 |
| `sample=` 分布 | **provisional 9 / PASS 4** |
| 日志中 `W1=` 取值 | **stale × 18（无一条 alive）** |

### 1.3 ★"间歇"的真实形状：**按小时翻转的连续窗**，不是逐拍随机

```
2026-10-25 05:02 – 10:04   provisional ×6
2026-10-26 13:28 – 16:29   PASS       ×4     ← 连续 4 个整点都 PASS
2026-10-26 17:30 – 19:31   provisional ×3
```

- 每行间隔 **60 分钟**（日报整点拍），所以这是"每小时一判"的序列；
- **PASS 集中在连续 4 小时**，两侧都是 provisional ⇒ W1 的 `alive/stale` 是**成段翻转**的，
  不是每拍独立随机；
- 与之相符：W1 是**外部心跳**，有刷新就有 `alive` 窗口，超过新鲜度阈值就转 `stale`。

### 1.4 结论与后果（**这不是 bug，是判据在正常工作**）

`_all_ok = _mode_ok and _sample_ok and _mis_ok` 要求 `sample` **恰为 `PASS`**；
`provisional` 一律不算。要连续 ≥3 tick 全 PASS，就得**连续 3 个小时都恰好落在 W1 的 alive 窗**。
实测 PASS 窗只有 4 小时 ⇒ 能攒满的窗口极窄，一旦跨出就归零。

⇒ **闸①的唯一卡点不是 mode、不是 misjudge、也不是抽验本身，而是 W1 心跳的可用时长。**
要开闸，方向只有三个（都需另裁，本批不做）：
①让 W1 心跳刷新更密/更稳；②放宽"连续 3 tick"（候选乙，**已被裁决否**）；③改判据（另裁）。

> ★口径修正：371 刀3 记的是"sample **间歇** provisional（同代次 PASS 与 provisional 混现）"。
> 本刀实测把"间歇"落到了具体形状 —— **按小时成段翻转**，且 10-26 的三段完全连续无跳变。
> 这个区分决定了修复方向（不是"抽验不稳"，而是"心跳窗太短"）。

## 二、B 面 · reload_stats 写侧断点 —— **不是写侧 bug，是上游零事件**

### 2.1 代码路径（写侧只有 4 个入口）

| 入口 | 触发条件 |
|---|---|
| `PulseNodePool.py:2751` `_m349_note_reload("evict", …)` | 发生**驱逐** |
| `:3425 / :3473` `("recall", … "batch_hit")` | **冷节点**被批量召回 |
| `:3448` `("skip", … "not_evicted")` | 召回请求命中"**未驱逐**"节点 |
| `:3493` `("recall", … "not_in_cold")` | 召回请求在冷池找不到 |

`_m349_note_reload` 尾部调 `_m349_persist_reload_stats()`（内部有 `_M349_RELOAD_PERSIST_GAP` 节流 +
`os.makedirs` + 原子 `os.replace`）。

### 2.2 实测：写侧函数**从来没被调用过**

| 证据 | 读数 |
|---|---|
| `logs/pulse.log` 中 `349回载` 行数 | **0** |
| `data/` 全树 `reload_stats.json` | **不存在**（371 刀3 已实测） |
| `[338冷化] 召回 … 回载=可用` | 有 —— 但那是**另一个模块**的内存内召回口径，**不是** m349 持久化 |

### 2.3 根因：warm 池永不溢出 ⇒ 无驱逐 ⇒ 冷池恒空 ⇒ 无回载事件

`max_warm = 50000`（`PulseNodePool.py:113` / `config.py:665`、`:3695`）> 实测节点 **19087**
⇒ warm 永不溢出 ⇒ **不产生驱逐** ⇒ 冷池恒空 ⇒ 上面 4 个入口**一个都不会被走到**。

⇒ **断点在"事件源为空"，不在写侧实现**：节流不会拦（首次 `_last=0` 直接放行）、
异常不会吞（`silent_exc` 会留痕而日志 0 行）、路径不会错（`persist` 内 `os.makedirs` 自建目录）。

★这与 371 刀3 的"写侧从未落盘"结论一致，但**把"写侧没写"推进成"上游没有可写的事件"** ——
因此候选 C（"补一次启动后首次立即落盘"）**即便做了也只会写出一个全 0 的空账**，
不解决任何问题。这一条应作为候选 C 报小林拍板时的一等事实。
