## 一、先修了基线本身的一个 bug（否则归族结论不可信）

上一批 N5 固化的基线里，139 条\"失败用例\"中有 **4 条根本不是用例**：

```
pulse.module.PulseNodePool:PulseNodePool.py:4063 冷存compaction: 跳过 1 个无法读取的parquet文件...
```

那是**器官日志行**被 `FAILED ` 前缀接住 —— `_failed_cases()` 只判前缀，没校验用例 ID
第一段是否 `.py` 结尾。后果：按文件归族时会拿这 4 条去"跑文件"，得到 4 个假 unknown。

- **修**：`tools/ci/m365_full_regression_runner.py::_failed_cases` 增加
  `_part.split("::")[0].endswith(".py")` 校验；
- **重生成基线**（用同一批 26 片日志）：139 → **135 条 / 55 文件**，残留非 `tests/` 项 = 0。
- 这是\"**取证工具自身的缺陷会污染取证结论**\"的又一实例（与 366 N3 的 `--check` 咬到自己人同类）。

## 二、逐例归族方法

不是逐条单跑（135 条 × 单跑成本过高且会重复污染 `data/`），而是：
**按文件单跑**（55 个文件，每文件独立子进程 / 独立 `CODEBUDDY_TOOL_CALL_ID` /
`--timeout=60 --timeout-method=thread`），抓 `FAILED/ERROR` 用例名 + 异常族 + 首条错误摘要。
实测耗时 **18 分 56 秒**。

## 五、既有失败的形态（供 367 排面参考，未逐条深挖）

从首个错误看，134 条既有失败大致分四类：

1. **灰度开关默认值断言**（最大宗，≥6 文件）：
   `test_m92_patch_guards`（\"T-92c 默认必须关闭\"）、`test_m92_switch_registry`、
   `test_m93_apply_guard`、`test_m96_followups`（\"默认必须为 False（灰度）\"）、
   `test_event_bus_m14` —— 生产侧默认值与测试期望**不一致**，正是 356B 把
   `ENABLE_EVENT_BUS` 置 True 后遗留的账。
2. **数据/台账状态断言**：`test_patch_dedup_m43`（\"生产历史仍有重复 id 87≠86\"）、
   `test_t100a_pending_no_false_success`（\"发现 7 条假成功补丁仍在待审批队列\"）、
   `test_quota_type_m97`（1000000≠0）—— 这些是**活体数据面**的账，不是代码逻辑错。
3. **环境依赖**：Neo4j/Influx/MySQL 连接、`pytest-timeout` 之外的依赖缺失、路径不存在。
4. **历史批次自身遗留**：`test_m354/m355/m356/m337/m340/m342` 等（涉及批次编号的测试）。

★**本批不记任何\"已回归/已修\"结论、不销既有失败账**（沿用 366 §9.3 口径）——
归族的产出是\"哪些是本批的、哪些不是\"，不是\"哪些已修好\"。

## 六、边界与未做

- 135 条的**逐例**（非逐文件）定性未做：族是按文件归的，同一文件内不同用例可能不同因
  （如 `test_self_awareness_m18` 16 例同文件）；
- 8 条 `unknown` 需要看完整输出才能归类（`SystemExit: 1` 多为 unittest 收尾，非真错）；
- **未**做跨版本对照（在 `b03a0798` 的 worktree 重跑同批测试）—— 缺 `data/`（4.9G）会造出大量
  假失败（铁律 174），故改用 git 归因 + blame 取证替代，成本低且可复现。
