### 额外发现（票面没写，但正是本刀要解决的）

那条 10:24:04 的日志原文：

```
跨文件补丁验证失败: patch_multi_1793... → ["补丁完整性检查失败: try 块不平衡：
2 个 try / 1 处 except+finally，缺 1 处收尾（第 35 行的 try 没有对应 except/finally）；
片段末行='# ===== 阶段5 结束 ====='（入库前静态闸拦截，未进入副本验证）"]
```

两个缺口同时存在，且**第二个比票面说的更严重**：

1. **正文零留存** —— `data/_archive` / `data/patches` 全库查不到该 id 的任何补丁体；
2. **连 id 都是截断的** —— `SafeEvolutionExecutor.py:6344` 写的是
   `patch.get('id','')[:16] + "..."`，日志里只剩 `patch_multi_1793...`，
   **前 16 字符在多个补丁间会撞**（同一秒批量生成的多文件补丁前缀完全相同）
   ⇒ 事后连「是哪一个补丁」都无法确定。

本刀把**完整 id + 正文 + 拒收原因 + try 统计**一起落盘，两个缺口一并补上。
（日志截断本身**未改**：那属于日志格式问题，不在「只加写盘」边界内，列入交付报告待裁决。）

## 二、改动

`nucleus/reasoning/PatchManager.py`

1. 新增 `_m377_dump_failed_patch(patch, reason, *, stage, root, tb)` 与
   `_m377_failed_patch_dir(root)`（模块级，紧邻 376 刀4 的 `_m376_try_balance_reason`）。
2. 关2a 拒收分支加三行调用：算 `reason` → 落盘 → 按 `written` 打 INFO/WARNING → 原样返回。

落盘内容（`schema = failed_patch/377.v1`）：

```
issue_id / dedup_key / file / method / issue_type / source / risk_level
stage="2a" / gate="关2a try 块平衡（376刀4）" / reason（与返回给调用方一字不差）
try_balance: {state, tries, handlers, deficit, open_lines, tail}
original_code / modified_code（原样，单字段上限 200k 字符，超限置 truncated=true）
orig_len / mod_len / truncated / saved_at / saved_at_str / pid
```

安全面：

- **绝不抛**：全程 `try/except` + `silent_exc` 留痕，函数返回 `{"written": bool, ...}`；
- **不改裁决**：调用方**不看**返回值，`complete=False` 与 `reason` 一字不变；
- **写盘守卫**：走 `write_guard.guard_write(component="FailedPatchAudit")`
  ⇒ 测试环境/非框架进程一律拒写（不会污染生产 `data/`）；
- **原子写**：同目录 `.tmp` + `os.replace`，不产生半截 JSON；
- **封顶**：目录内 `.json` 达 400 条后停写并报 `why="dir_full"`（可观测，不是静默丢弃）。

## 三、三态（写在返回值里，不靠口头声称）

| 三态 | 触发条件 | 证据 |
|---|---|---|
| **拒收 + 已留档** | 关2a 命中且写盘成功 | `{"written": True, "path": …, "bytes": …}` + INFO 日志 |
