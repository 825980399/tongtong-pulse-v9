## 〇、一句话结论

**「14-16MB/min 稳态增长」这个前提有两处不成立**：

1. 老一代进程（pid22368，已跑 11h）在被测的 5 小时里 RSS **基本持平**（6948 → 6897 MB，Δ **−51MB**），
   而同期系统自测的「内存增长率」一直报 **10–36 MB/min** 并持续判「疑似内存泄漏」——
   **这个指标本身是失真的**；
2. 真正在涨的是**启动后 2 小时内的新代**（RSS 3728 → 6065 MB），而它的前 14 分钟是冷装载
   （+1410MB ≈ 100MB/min），与「稳态泄漏」不是一回事。

所以本刀的结论不是「找到泄漏点」，而是：**现有观测手段回答不了「谁占了那 2GB」，且当前用来
判「疑似泄漏」的那个增长率指标不可信**。下面给全部读数与证据。

## 三、top 增长对象类型（按条数，跨 13 代一致性）

`data/reports/memory/top_types_*.json` 共 **108 份**（每小时 +1），覆盖 **34 个进程代**。取「代内首末两点
heap 涨幅 > 200MB」的 **13 代**做差分，看谁稳定上榜：

| 入榜次数 | 类型 | 备注 |
|---|---|---|
| **13 / 13** | `dict` | 每代必涨（+1.1 万 ~ +5.6 万） |
| **13 / 13** | `list` | 每代必涨（+8 千 ~ +5.9 万） |
| 4 / 13 | `set` | 且**稳定 +3.0 万**（29206 / 30365 / 30291 / 30515） |

### 值得单独说的一条：增长是「定量整块」而不是「缓慢渗漏」

`set` 在 **4 个不同进程代**里都是 **+3.0 万左右**，`function` 在 2 代里都是 **+1.6 万左右**。
同一个数量级反复出现，说明某个子系统每代**跑固定的次数/装载固定的规模**，而不是每拍漏一点。

同代样例（当前代 08:52 → 10:00，heap +1998.5MB）：

```
dict      +47401   (254035 → 301436)
set       +30516   (     0 →  30516)   ← 08:52 时是 0，说明是后起的子系统建的
list      +20391   (244859 → 265250)
function  +16421   ( 38829 →  55300)
tuple     +12489   ( 92795 → 105284)
```

## 四、致命算术：**这些条数解释不了那 2GB**

同代增量：heap **+1998.5 MB**，而 `gc.get_objects()` 可见对象只 **+133,968 个**
⇒ 平均每新增一个可见对象要背 **15.3 KB**，这不可能（dict/list/set 单体几十到几百字节）。

真相是 `gc.get_objects()` **看不见未跟踪类型**：`str` / `bytes` / `int` / `float` 都不在
GC 跟踪表里。所以：

> **约 95% 以上的增长发生在 `str` / `bytes` 这类大缓冲上，而现有探针一行都看不见。**

这不是猜测——下面两节是硬证据。

---

## 五、硬证据：尺寸维度**从来没有采到过一行**

`top_types_*.json` 的 `mode` 分布：`gc_objects` 90 份、`tracemalloc+gc_objects` **17 份**。

对那 17 份 tracemalloc 档逐一检查：

```
17 份 tracemalloc 档快照，tracemalloc_rows 全部 = 0 行
basis 全部 = "since_start（本次开启后的分配，不代表全堆）"
tracemalloc_is_tracing 事后 = False
top20 首行 = {"type": "dict", "count": 254035}     ← 没有 size_kb 字段
有尺寸归因的快照数 = 0 / 108
```

两条结构原因（都写在代码里，不是运行时偶发）：

1. **`M339_TRACEMALLOC_MODE = "window"`（config.py:6057）** ⇒ 探针内部
   `tracemalloc.start(1)` → 立刻 `take_snapshot()` → `stop()`（`PulseMetricsCollector.py:512-536`）。
   中间只隔几十微秒，**必然采到空**。要采到东西必须让 tracemalloc **在进程早期就常驻**，
   而全仓没有任何地方在启动时调 `tracemalloc.start()`。
2. **`"top20": (_gc_types or _tm_rows)`（`PulseMetricsCollector.py:573`）** ⇒ 只要 gc 计数跑过
   （`heap > 1200MB` 恒成立），表头 `top20` 就永远是**计数**，永远没有尺寸。

后果不只是"少了个数字"：

```json
"heap_attribution": {
  "buckets": {"ast": {"size_kb": 0.0, "count": 0, "pct": null},
              "pulsenode": {"size_kb": 0.0, "count": 0, "pct": null},
              "image": {"size_kb": 0.0, "count": 0, "pct": null},
              "other": {"size_kb": 0.0, "count": 1042416, "pct": null}},
  "total_size_kb": 0.0,
  "basis": "按 tracemalloc 行的文件名归四类；pct 按 size_kb 计..."
}
```

**四类全是 0.0、`pct` 全是 null、`total_size_kb=0.0`，而 `count` 是 104 万。**
一个不看代码的人读这份产物，会得出「AST 0KB / PulseNode 0KB / image 0KB」——
**这是「没采到」被写成了「真是 0」**，与铁律276 同型（该项目已经为同一类问题立过规矩）。
`349刀5` 设计的「四类占比」自 2026-10-22 起 **108 份快照、0 次产出过数值**。

## 六、判「疑似泄漏」的那个指标本身失真

`nucleus/runtime_metrics.py` 的增长率估计，在老代上直接与 RSS 矛盾：

| | 老代 pid22368（03:51→08:48） |
|---|---|
| 指标读数 | 61.05 → 11.21 MB/min，min 10.04 / max 926.58，**前 1/3 均值 32.09 → 后 1/3 均值 36.23（上升）** |
| **RSS 实测** | **6948 → 6897 MB（5 小时净减 51MB）** |

**RSS 5 小时没动，指标一直报 10–36 MB/min 并每十几秒判一次「疑似内存泄漏」。**

### 这个误报的代价是可量化的

它触发的是「自动 GC」：

| | 次数 | 时间跨度 | 平均间隔 | 单次停顿(中位) | 累计停顿 | 占墙钟 | 单次回收对象(中位) | 累计回收 |
|---|---|---|---|---|---|---|---|---|
| pid22368 | 311 | 298 min | 57.7 s | 637 ms | 198.5 s | **1.1%** | 197 | 86,772 |
| pid8188 | 277 | 124 min | 27.0 s | 532 ms | 148.8 s | **2.0%** | 230 | 78,999 |

**588 次全量 `gc.collect()`，合计只回收 16.6 万个对象（每次中位 200 个），却吃掉了 347 秒墙钟。**
在一个 heap 5–7GB 的进程里，一次全量 GC 只捞回 200 个对象 ⇒ **那 5–7GB 几乎全是可达对象**
（不是循环垃圾）。这反过来印证：**不是"GC 没跑到"，是"跑到也没用"** —— 内存确实被某些结构持有。

## 七、另一个被忽略的事实：验收硬线早已被突破 2.6–3.6 倍

- `config.py:5601`：`MEMORY_RELEASE_G4_HEAP_MB = 2000.0`，注释写着
  「★小林 D3 验收硬线 **≤2.0GB**」；
- 实测 heap：老代 5.9–6.4GB，当前代 3.1–7.3GB；
- `release_policy` 每小时打一行 `tier=G4_ALARM_ONLY ... 开关=off(shadow)`，
  `ENABLE_MEMORY_RELEASE_LIVE = False` ⇒ **只告警，不释放，不重启**。

也就是说：**验收线 2.0GB 与实际 5.2–7.3GB 之间差了 3 倍，而系统对此只会稳定地打一行 WARNING。**
这一条不属于「泄漏」判断，但属于**验收口径失效**，必须点出来。

## 八、单点 2GB 巨浪（新发现，机制未确证）

`10:40:25` 一个采样点内 heap 从 5219 → **7283.7MB**（RSS ≈ 7894MB，**接近 8GB**），
下一采样点回到 5227.3（−2056.4MB）。

这一条是**容量风险**（不是泄漏：来去都是一个采样点内）。

**机制候选（未确证，只列证据与候选，不下结论）**：
- `nucleus/mnemosyne/PulseSnapshot.py:610` `_incremental_save()` 里
  `safe_read_json(self.snapshot_path)` —— **每次增量保存都把整份快照读进内存**；
- 该文件实测 **706.8 MB**（`data/knowledge/pulse_knowledge_snapshot.json`），
  且 08:50:01 / 08:52:16 刚生成两份 **703–707MB** 的 `.bak`；
- 707MB JSON 解析成 Python dict/list 的对象膨胀通常 2–4 倍 ⇒ **1.4–2.8GB**，与实测 +2065MB 同量级。
- **但**：10:40 那一分钟**没有任何 PulseSnapshot 保存日志**（`增量日志保存完成` 未出现），
  所以**不能认定就是它**。要定论需要在那条路径上打点（本轮不做）。

## 九、回答票面两问

**问：top 3 增长对象类型是什么？**
答：按条数 —— `dict`（13/13 代）、`list`（13/13 代）、第三位在 `set`（4 代，且稳定 +3.0 万）、
`function`（4 代，稳定 +1.6 万）、`tuple`（4 代）之间轮换。
**但这三甲解释不了字节**：heap +2.0GB 对应可见对象仅 +13.4 万，约 95% 的增量落在
`str`/`bytes` 等**未被 GC 跟踪**的类型上，而现有探针从设计上就看不到它们。

**问：是预热缓存自然增长，还是真泄漏？**
答：**证据不足以判定「真泄漏」**，理由是口径不同源（老代只有饱和态样本、新代只有预热期样本），
硬要下结论会犯铁律271 的错。已确证的是三条：
① 增长**不是线性**的，老代 RSS 5 小时持平 ⇒ 至少存在一个收敛机制；
② GC 588 次几乎捞不到东西 ⇒ 占用是**可达对象持有**，不是循环垃圾；
③ 尺寸维度**从未采到**，所以「谁占的」在现有数据里**无解**。

## 十、立项建议（本刀不做，供拍板）

| # | 建议 | 依据 | 风险 |
|---|---|---|---|
| A | 在进程早期 `tracemalloc.start(N)` 常驻（或改 `M339_TRACEMALLOC_MODE=resident`），并把探针改为「两快照差分」出**增量尺寸** | 第五节：17/17 空采 | 常驻有 5-10% 开销，需定时 stop |
| B | `heap_attribution` 在无尺寸行时返回 `state="unavailable"` 且 `pct=None`，**不许出 `0.0`** | 第五节：假 0 | 无（纯改口径） |
| C | `top20` 表头在有尺寸时优先 `_tm_rows`，或拆成 `top20_by_size` / `top20_by_count` 两键 | `:573` | 无 |
| D | `runtime_metrics` 增长率改用**滑动窗口实测斜率**并与 RSS 同源，避免「RSS 持平时报泄漏」 | 第六节 | 会改变告警频率，需拍板 |
| E | `G4_HEAP_MB=2000` 验收线 vs 实测 5-7GB：是改线、还是改「只告警」策略，需拍板 | 第七节 | 涉及小林 D3 验收口径 |
| F | `_incremental_save` 整载 707MB 快照：改为按 node_id 定点读 / mmap / 增量索引 | 第八节 | 动核心存储链，风险高，需专门批次 |
