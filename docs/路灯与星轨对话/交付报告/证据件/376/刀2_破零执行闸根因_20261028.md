## 三、`executed_ge_1` 是什么

**它不是独立计数器**，是一条纯镜射：

| 步骤 | 位置 | 事实 |
|---|---|---|
| 闸门读它 | `zero_break_judge.py:69-73` | `_ex = int(record.get("executed") or 0)`；`ok = _ex >= 1` |
| 观测侧给值 | `zero_break_judge.py:967` | 仅当 `results` 里**有这一条的结果行**才 `_rec["executed"] = 1` |
| 生产侧给值 | `patch_execution_dispatch.py:2669` | `_write_back` 里 `patch["executed"] = 1`（真进了沙箱才走到） |
| `results` 从哪来 | `:3305 / :3349 / :3408` | 只有 `verify_patches_concurrent` 真跑过才有 |

所以「`executed` 为 0」= **这条候选从来没进过沙箱**，不是"算错了"。
台账交叉验证（只读）：

```

data/patches/patch_history.json          8969 行，含该 id = 0
data/patches/patch_dispatch_trace.jsonl  缺失
```

三本账**都没有它** ⇒ 「一次都没执行」是如实读数，不是采样丢失。

### 第一层：`o3_auto_dispatch_ready` 字段不存在

## 五、反证：不是调度问题，也不是 except 吞了

| 假设 | 反证 |
|---|---|
| 触发器没被调用 | `[317刀0][分诊节拍] 触发自动分诊` 在 `logs/pulse.log` **命中 5 次**（04:17→08:19 每小时一拍），`interval=3600s`；同一拍 `[339审批][O3派单]` 与 `[351破零]` **成对出现** |
| 调了但被 try/except 吞了 | `_cands` 为空是**门禁拒收**，不是异常：日志把 `rejected` 字典逐键打出来了（`not_o3:8 / not_confirmed:3`）。`dispatch_on_tick` 的 except 分支（`:518-524`）会打 `[339审批][O3派单] 节拍调用异常`（`:523`）——**该文案在全日志 0 次命中** |
| 撞了失败上限（cap） | `rejected.cap = 0`；`patch_verify_attempts.jsonl` 18 行里没有这条 id ⇒ **一次都没跑过**，谈不上失败 |
| 被判死撤单过 | `rejected.pending_cleared = 0`；`status` 仍是 `pending`，不在 `wont_fix` |

**附带发现（另一条独立通道，同拍也在归零）**：

```
[317刀0][分诊节拍] 触发自动分诊 interval=3600s selected=1 executed=0 applied=0
    blocked=verify_fail_cap hard_cap=1 blast_cap=1（安全闸未放宽）
```

主分诊通道（llm 类）选中 1 条却 `executed=0`，`blocked=verify_fail_cap`
（`_DISPATCH_FAIL_CAP = 2`，`:2139`）。即：**系统级 `executed=0` 有两个互不相干的原因** ——
O3 通道「没人批/批不动」、主通道「选中那条撞了 cap」。两条不能混成一个结论。

## 六、修法方向（三条，均**不改破零主链路**；等星轨裁决）

### A. 立即可做：对可批的那条走人工裁决（零代码）

`o3_59cd0eef8e125186` 四项齐 ⇒ 人工在聊天里敲 `approve_o3 <索引>`（索引以 `patches` 输出为准），
下一拍 `dispatch_o3_approved` 即认领 ⇒ `executed` 变 1 ⇒ `executed_ge_1` 转绿。
**这条路不需要改任何代码**，也最符合「破零是人工裁决后自动派单」的原设计。

### B. 必须做：把观察位从死结上挪开（改一行常量）

`zero_break_judge.py:926` 的 `WATCH_IDS = ("o3_b31b31fee790d6e9",)` 指向的是一条**永远批不动的
存量条目**。后果：`missing=executed_ge_1,applied_true,ledger_verified` 会**永久红**，
看久了就没人再看——这是「假安全」的镜像：判据恒红等于没有判据（铁律 276 同族）。
两条路选一：
- B1 把 `WATCH_IDS` 换成可批的活条目（如 `o3_59cd0eef8e125186`）；
- B2 给存量条目做一次**回填**（补 `probe_out_of_graph` / `misjudge_sample` / `god_file`），
  回填要如实标"补算件"、不能伪装成入池时就有。

### C. 建议（要动诊断面，故不擅自改）：拒收理由再分一层

`_m339_o3_dispatch_ready` 目前对这两种**完全不同的事实**都只报 `not_confirmed`：

- 没人裁决（可批，等人）；
- 批不动（缺三项，等数据）。

二者在日志里长得一样，导致「破零卡点」这事每次都要人肉扒 json。建议加一个只读诊断键
（如 `not_confirmed_missing_basis`），**不改任何放行/拒收判定**。
因它落在破零派单链路的诊断面上，按任务书 §三「不直接改破零主链路、改前先报星轨」，
本刀**只登记、不实现**。
