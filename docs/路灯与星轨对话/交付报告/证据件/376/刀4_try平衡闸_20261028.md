## 二、为什么**不**自动补全（票面给了「补全或拒收」两条路，本刀选后者）

票面写「自动补全或直接拒收」。补全看着更省事，但在这里**不安全**，
用真代码形态（`PulseLiver._sample_resource_usage` 里那段 `_uptime_s`）做了三份样本，
跑**生产口径的四关**（`PatchManager._check_llm_patch_completeness`，直调、不构造实例）：

```
=== 四关判据（生产口径）===
  A 原文（真实 handler）    complete=False reason=修改内容为空或与原文完全一致
  B 截断（丢 handler）      complete=False reason=语法错误(SyntaxError): expected 'except' or 'finally' block (<llm-patch>, line 4)
  C 自动补全（raise）       complete=True  reason=

=== 行为差（同一个抛异常的 _proc）===
  A 原文      → return None
  C 自动补全  → raise 'RuntimeError: boom'
```

**C 过四关，但它已经不是原文的意思了**：原 handler 把异常降级成 `None`，
补全版把它原样抛出去。关0/1/2/3/3b 没有一关看得见这个变化 —— 因为
它们判的是「字段齐不齐 / 有没有改动 / 语法能不能 parse / 相似度 / 长度」，
**没有一关判语义**。

⇒ 若自动补全，这 12 次失败会变成 12 次**静默的行为回归**（还是"验证通过"的那种）。
这比失败更糟。故本刀**只拒收**，并把拒收理由做得能直接动手。

> 这条取舍在 `tests/test_m376_d4_try_balance.py::test_14_autofilled_handler_would_pass_all_gates`
> 里被钉成常驻判据：将来谁想加「自动补全」，这条会先红。

## 三、做了什么：关2a（摆在关2 之前）

### 判据（`_m376_try_balance`，`PatchManager.py:246` 起）

用 **tokenize** 数**语句级**的 `try` / `except` / `finally`：

- 「语句级」= 关键字前一个有效 token 是 `NEWLINE`/`INDENT`/`DEDENT` 或文件开头；
- **不用正则**：字符串、注释、属性名（`obj.try_x`）、装饰器（`@try_again`）里的
  `try` 一律不计数（铁律227 同型坑：正则会误命中，`tokenize` 按 STRING/COMMENT 排除）。

只在**必然语法非法**的两条形态上拒收：

| 形态 | 判据 | 为什么必然非法 |
|---|---|---|
| `unbalanced` | `try` 数 > `except`+`finally` 数 | 至少一个 try 块没有收尾 |
| `orphan` | `except`/`finally` 数 > 0 而 `try` 数 = 0 | 片段起点落在 try 内部（窗口错位） |

### 文案长什么样（这是本刀真正的交付物）

```
补丁完整性检查失败: try 块不平衡：2 个 try / 1 处 except+finally，缺 1 处收尾
（第 35 行的 try 没有对应 except/finally）；片段末行='# ===== 阶段5 结束 ====='
（入库前静态闸拦截，未进入副本验证）
```

对比原来的 `expected 'except' or 'finally' block (<llm-patch>, line 35)`：
多了「缺几处」「哪一行」「片段末行长什么样」，且**片段末行硬截断 60 字**
（`test_11` 钉住），不会把整行代码灌进日志。

### 能力边界（如实写）

它是个**下界探测器**，不是完整校验器：
`try:...except:...finally:...` 与一个裸 `try:` 并存时（tries=2 / handlers=2）它判 `ok`，
而代码其实非法 —— 这种仍由关2 的 `ast.parse` 兜住。
`test_13_lower_bound_false_negative_is_documented` 把这个假阴性**钉成预期行为**，
免得后来人把它当「完整校验器」用。

### V2 抓到的真缺陷（本刀最值钱的一次红）

V2 把 orphan 分支关掉后，`test_12` **竟然还是绿的**。原因不在测试，在产品代码：

```python
if tb.get("state") == "unbalanced":
    return "try 块不平衡：... 缺 N 处收尾 ..."
return "try 块不平衡：有 N 处 except/finally 却没有 try ..."   # ← else 兜底
```

那个 `else` 兜底意味着：**任何**非 `unbalanced` 的状态（包括 `ok`、`unknown`）
都会被描述成「片段窗口错位」。生产上暂时踩不到（调用方只在这两态调它），
但这正是「文案与事实不符」的老毛病（铁律166）—— 状态是 ok，文案说窗口错位。

- 修法：改为**按状态显式分支**，非两态给中性文案
  `try 块平衡检查未给出拒收结论（state=ok，不拦）`；
- 判据补强：`test_12` 现在先钉状态 `state == "orphan"`，再加**反面判据**
  —— `ok` 与 `unknown` 态的文案里**不许**出现「fragment 窗口错位」；
- 复跑 V2 单场景：`命中 test_05 / test_09 / test_12` ⇒ 2/2 PASS。

## 七、没做的与留给下一批的

1. **不自动补全** —— 理由与实证见第二节，不是省事，是补全会造成静默行为回归。
2. **补丁正文不落盘** —— 12 次失败没有一次留下 `modified_code`，事后无法复盘。
   本刀只在**拒收文案里**带了有界的片段末行（60 字）作止血；要不要把失败补丁
   正文落到独立审计件（而不是 `data/` 活体对象）需另行裁定。
3. **「分段拼接丢收尾」是否真因** —— 目前只有一条线索
   （片段末行 `# ===== 阶段5 结束 =====`）。要定论必须拿到 `modified_code`，
   故**不改 LLM prompt、不改生成链**（任务书边界），留待取证条件具备后另立。 
4. **同一 id 反复重犯** —— 12~30 次失败对应**同一个** `patch_multi_1793`，
   说明每轮都原样重来。这是「重试策略」层面的问题，不属于刀4 边界。
