### 误报机理（与 369 刀2 同型）

检测器按**字面特征**命中「方法体内出现 `threading.Timer(...)`」⇒ 把**安排定时器的调度器**
当成了**被定时器回调的周期任务**。两者角色完全不同：

- **调度器**（`_schedule_xxx`）：被上一轮回调在末尾调用一次，用来排下一轮；
  它自己**不是** Timer 的目标，不存在"上一轮未完成时重入"的问题（它本身就是串行的下一步）。
- **回调**（`_trigger_xxx` / `_auto_health_check`）：才是 Timer 的目标，才是重入风险的承载者。

⇒ 检测器连这两者都区分不了（与 369 刀2「无法区分器官直调与基础设施单例工厂」同型）。

def _trigger_exploration(self):
    if not self._running or self._stop_event.is_set():
        return
    self._emit(SubconsciousEvent.CURIOSITY_TICK, {...}, priority=3, layer="L3")

⇒ **只发一个脉冲**，无耗时操作、无 IO、无锁等待 ⇒ **重入风险低**，加守卫的收益接近于零。

⇒ 即便把命中面修正到回调侧，也**不能默认每条都要加守卫**：
守卫只对"回调耗时可能超过间隔"的场景有意义（如扫描全库、网络调用、批量写盘）。

   逐条判"间隔 vs 单次耗时"，只对"单次耗时可能 > 间隔"的加守卫。当前抽样到的回调都很轻量，
   **未发现需要重写的真缺陷**（这是实测结论，不是"还没查"）。
