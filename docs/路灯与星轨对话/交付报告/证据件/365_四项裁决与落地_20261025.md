## 事项 1 · A3 存量 76 条键迁移口径

### 分析（三层取证，跨**全部** audit 快照）

| 口径 | 实测 | 含义 |
|---|---|---|
| 按键命中（跨 5 份快照） | **1 / 76** | 补 `dedup_key` 能救的只有 1 条 |
| 仅按 file 归一可匹配到池条目 | **55 / 76** | 同文件在池里**有其他类型**的问题 |
| 池里连该文件都没有 | **20 / 76** | 该问题从未入池 |
| history 侧类型 | `silent_exception` 57／`Traceback` 9／`print_instead_of_log` 8… | 日志/异常类 |
| 池侧类型 | `dead_code` 662／`cross_module_singleton_call` 21／`cc_ge50_new` 11… | 结构/质量类 |

**根因**：不是键没填，而是**两侧描述的不是同一个问题**。补丁侧记"这段代码里有个静默 except"，
池侧记"这个方法没人调用"。同一个文件上它们同时存在，所以 `(file, issue_type)` 唯一命中
在事实上几乎不可能 —— 归一表也救不了（55 条里多数同文件有 2–4 个不同类型）。

### 三方案对比

| 方案 | 工作量 | 效果 | 风险 |
|---|---|---|---|
| 甲 补可命中的 1 条 | 极小 | 闭环样本 +1（且仅这一条能走通） | **制造"1 条假闭环"，污染破零读数**（破零统计看的是"真修好几条"） |
| **乙 整批不补、关闭该项** | 0 | 不下沉成本 | 承认"补键不解决破零"，需另找路径 |
| 丙 另立数据迁移专项刀 | 大 | 只能处理 20 条 `file_absent`（重建池条目） | 需停机写窗 + 重建判据，收益不明 |

### 裁决：**乙（整批不补）＋ 该项 wonfix 关闭**

**理由**：①补键对 75 条**结构性无效**（不是"没做"，是"做了也没用"）；②甲会让破零里出现
一条"靠补键造出来的闭环样本"，那比 0 条更糟——它会让"破零"看起来启动过；
③真正的通路是**让补丁从池条目生成**（即 B4 的池→生成器回流：入池时带键、生成时继承键），
而不是事后给历史补丁算键。

**落地**：把 `unmap` 分成两种（`file_absent` / `type_mismatch`，附 `same_file_types`），
live 时能一眼看出是"没入池"还是"类型不同" —— 这正是上面结论的可复算出口。
**反向条件**：若 live 期发现那 20 条 `file_absent` 是"池被清理过"而非"从未入池"，
则应改为**重建池条目**（丙），而不是继续说不补。

## 事项 3 · A2 开关默认值（`ENABLE_SANDBOX_PREFILTER_TWO_CHANNEL`）

### 分析

- **收益**：拒收理由更准（惯用法不再被标"结构性必败"）。**不是**"更多补丁能过"——
  沙箱 `_security_precheck` / `would_block` 判据一字未改，这些补丁到沙箱**仍会被拦**。
- **成本**：拦截点从"派单前转人工"变成"沙箱执行时拒绝" ⇒ 多一次子进程执行；
  失败会写 `runtime_verify` 失败并进 324「失败可退出」计数 ⇒ **污染补丁失败计数**。
- **证据面**：本批不停机、无 live 读数；`get_m365_sandbox_prefilter_stats()` 尚无真实分布。

### 裁决：**默认改 False（先关）**

**理由**：收益是"文案/理由更准"而非破零必需；成本会污染失败计数；无 live 数据支撑时
默认开 = 拿生产当试验场。开关已按三要素登记，翻闸只需一行。
**翻闸前置**：live 观察窗读 `get_m365_sandbox_prefilter_stats()` 分档分布 + 沙箱实际拦截率；
若 `idiom` 类占拒收 ≥60% 且沙箱全部放行，说明预拦确属误伤，可提前翻。

**落地**：config 默认改 False（注释口径同步改写）；测试增「默认必须关」断言，
其余用例显式 patch True 验新口径；顺带修掉旧口径下"无命中"被记成 `legacy:would_block` 的怪读数。
