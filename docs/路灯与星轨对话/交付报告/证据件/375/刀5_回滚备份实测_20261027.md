# 刀5 · 回滚备份失效实测（375 批 · 2026-10-27）

> 票：`T-371-回滚备份失效-1`｜数据源：`data/patches/patch_history.json`（**只读**）
> 口径：只判备份是否可读（目录非空 / 文件存在），不判备份内容与补丁前内容是否一致；空 backup_path 判不可回滚；扫描面=data/patches/patch_history.json 的 applied 条目

## 一、实测分布

| 口径 | 条数 |
|---|---|
| applied 总数 | 76 |
| 其中标 `rollback_available=True` | 76 |
| **备份物理可读（真可回滚）** | **20** |
| **标 True 但备份缺失（物理不可回滚）** | **56** |
| 未标 True 但备份其实在（反向口径错） | 0 |

缺失原因分布：`{"backup_missing": 56}`

## 二、根因

不是谁写错了：`rollback_available=True` 是**写入那一刻的真话**（当时备份在）。
后来 `data/code_backups/` 的保留策略把旧目录清掉，标记没跟着变。
坏在**没有复核口** —— 下游 `patch_lifecycle.record_activation()` 的硬点
（`rollback_available=False` 不得进 activated，验收 a）读到的是历史值，
于是「物理不可回滚」的补丁照样进 activated。

## 三、本刀做法（治本，不碰历史账）

1. 新增 `nucleus/evolution/rollback_audit.py`：`backup_present()` 把「可回滚」
   从**标记**改成**可读实测**（目录非空 / 文件存在）；`audit()` 双向复核；
   `reconcile()` 默认 dry-run，且**本模块不提供任何写盘口**。
2. 生产写入点（`PatchManager.apply_all_pending`）改为**先实测再置标记**，
   新产出记录不再有「假可回滚」；实测不可读时写 `rollback_unavailable_reason` 并 WARNING。
3. **存量不动**：任务书明令不改审计池数据、不写 `data/` 活体对象 ⇒
   本刀只出上面这份清单，改不改由裁决定。
