# 刀12 · m91 单例缓存「收口」勘误与真修（第375批 · 2026-10-27）

> 票 `T-372-m91单例缓存-1`（P3）。任务书原文：
> 「**问题**：SelfInspector._inspector() 单例索引缓存换干净实例后仍被命中，用例内无法隔离。
> **任务**：产品侧给「单例缓存可重置」口子，或该用例迁独立进程跑。」

**结论先说：这三句话一句都不成立。** 本刀既没有加产品口子，也没有迁进程 ——
真红因是**测试件两个分母不相等**，一行修完；产品侧的重置口子**早就存在**。

顺带记一笔：测试件里的 `_inspector()` 是**测试模块自己的** `_INSPECTOR` 单例
（`tests/test_log_locate_m91.py` 模块级），与产品 `get_self_inspector()` 不是同一个东西。
把它当成「产品的单例缓存」是这轮误判的起点。

## 二、真红因：两个分母不相等

原实现（368/372 两批一直是它）：

```python
with _Switch(_SWITCH, False):
    _miss = set(t for t in self.tags                       # ← 分母 A：活体日志 TAG
                if not self.insp.locate_issue(t, "").get("file"))
_still = [t for t in _GAP_TAGS if t not in _miss]           # ← 分母 B：16 个常量
```

`_still` 的语义是「16 个缺口标签里，有几个**没有**被判成不可定位」。但只要某个缺口标签
**这一天的日志里没出现**，它就不在 `self.tags` 里 ⇒ 不在 `_miss` 里 ⇒ 直接落进 `_still`
⇒ 判红。红与不红取决于**日志轮转**，与 `ENABLE_M91_LOG_LOCATE_V3` 开关无关。

而 372 记录的那 5 个标签正是低频标签：

```
AssertionError: Lists differ:
['wecom_chat_bridge', 'WriteGuard', '时间中枢', '胸腺', '硬件启动器'] != []
```

### 复现（逐字一致）

`tmp/repro375d12.py` 把「日志不含这 5 个标签」的时点造出来，跑**原样的旧口径**：

```
真实日志 TAG 数=118（is_real=True）
模拟时点 TAG 数=113（剔除 5 个）

[现在]
  V3-off 下 16 个缺口标签的真实命中 = 无
  原样逻辑得到的 _still = []
  => 绿

[模拟372时点]
  V3-off 下 16 个缺口标签的真实命中 = 无
  原样逻辑得到的 _still = ['wecom_chat_bridge', 'WriteGuard', '时间中枢', '胸腺', '硬件启动器']
  => 红
```

**模拟时点的 `_still` 与 372 记录逐字一致**，且两次 V3-off 的真实命中数都是 **0**。
⇒ 红因是分母错位，不是缓存。

`tmp/probe375d12b.py` 另给一张 16 行逐标签表（在不在 tags / V3-off 命中否 / 落点），
当前 16/16 都在日志里 ⇒ 现在是绿的。**这就是它时红时绿的机制**（铁律 269 的同类）。

## 三、改法：探测对象换成常量本体

```python
with _Switch(_SWITCH, False):
    _hit = [t for t in _GAP_TAGS if self.insp.locate_issue(t, "").get("file")]
self.assertEqual(_hit, [], ...)
```

为什么这是**升**而不是降：

- `locate_issue(organ, msg)` 对入参是纯函数，**不需要**该标签出现在日志里；
- 旧写法只探「当天日志里恰好有的那几个」，改后恒探 16 个 ⇒ 覆盖面只增不减；
- 断言不再随日志轮转变色 ⇒ 不会再出现「同一天跑两次结论不同」。

另加 `test_33b`：把 `tags` 换成**一个缺口标签都不含**，旧口径必然 16/16 全红、
新口径必须纹丝不动 —— 判据自带反向验证，改回去立刻红。

## 五、为什么不加产品口子

1. **口子已经有了**（P0 批次 3 的 `shutdown_self_inspector`）——再加一个是重复造；
2. 本批刀3 刚刚把「**有键无色**」当缺陷修（`submit_cpu_bound` 生产 0 调用）：
   为修一条**测试自身错**的用例去给生产加一个无人调用的重置口子，
   正是同一个反模式，只是换了个方向；
3. `test_08` 反向钉住「生产件不许出现本刀痕迹」——方向反了（把判据错当成被测对象错）
   会立刻被测出来。

## 六、一次施工事故与它的产物（kill-safe 快照）

复跑反向验证时我强杀了一次脚本，**残留被留下了**：`finally` 里的写回在
SIGKILL 下根本不执行，`tests/test_log_locate_m91.py` 停留在「test_33b 已被删掉」
的注入态。是靠 `grep -c test_33b` 查出 0 才发现的。

修法与纪律：

- 脚本改成 **先落快照再注入**（`tmp/.rev375d12.orig/<tag>__<basename>`）；
- 每次启动先 `_heal()`：若快照与目标文件内容不同，先用快照写回，再开工；
- **快照不删** —— 第一次实现是「正常收尾就删快照」，结果删文件撞上 safe-delete
  钩子（单轮 50 个达阈值被拒）把脚本整崩了。改为「不删 + 按内容比对」后，
  快照变成一个幂等的还原点：内容一致就什么也不做，不一致才写回。
  这比「删干净」更安全 —— 反正它躺在 gitignored 的 `tmp/` 里，几 KB。
- 这就是「反向验证脚本自己也要被验证」的又一层：**它不仅要能测出别人的错，
  还要能在自己被强杀时不留污染、在环境有自己的删文件策略时不被卡死**。
  刀9 学到的是「别信 stdout」，刀10 是「先证明该红的真的该红」，
  本条是「别信 finally，也别信『删掉临时文件』这种理所当然」。
