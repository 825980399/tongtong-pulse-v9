## 三、逐任务交付

### T1 · P0 快照保存性能止血

**真瓶颈**（源码定位）：`_full_save` L646 一次性构建 `[node.to_dict() for node in saved_nodes]`
（12327 节点 × 40+ 字段 ≈ 56 万次字段访问），再整体 `json.dump` 479MB + 轮转备份。

**改动**（`nucleus/mnemosyne/PulseSnapshot.py`）：
1. **分批流式写** `_m67_write_snapshot_streaming`：逐批 `to_dict` 直接写文件句柄，
   不再构建超大列表 → 显著降低内存峰值。
   ★**天然双缓冲**：每个节点的 dict 在生成那一刻即定格，此后节点被修改不影响已写内容，
   因此保存期间节点池可继续读写。
2. **异步保存** `_save_async`：普通周期保存提交后台线程并立即返回；
   `_m67_is_saving` 标志使进行中的保存**跳过**新触发（避免线程堆积形成新恶性循环）。
   ★`force_full=True`（退出前强制全量）**恒同步**，保证退出前落盘，语义与改造前一致。
3. **超时保护**：超过 `SNAPSHOT_SAVE_TIMEOUT` 只告警**不中断**——中断正在写的快照会丢数据。
4. `save()` 拆出 `_save_sync()` 同步主体（异步与同步共用，逻辑零变化）。

### T2 · P0 真正的增量保存

**既有问题**：`_incremental_save` 需读全量快照 + 解析 + 重建索引，
代码注释自陈「8700 节点下比全量慢 10 倍以上（170s vs 9s）」。

**改动**：新增 jsonl 增量日志
- `_m67_incremental_log_save`：变更即追加 jsonl（O(变更数)，不读全文件）
- `_m67_incremental_log_lines` / `_m67_clear_incremental_log`：行数统计与清空
- 达 `SNAPSHOT_INCREMENTAL_LOG_MAX_LINES` → 自动触发全量合并并清空（合并失败保留日志下轮重试）
- `_m67_apply_incremental_log`：启动时重放（upsert 逐字段更新保持原对象类型 / delete 移除）
- **损坏容错**：单行解析失败只跳过并告警，绝不影响启动
- 写入失败自动回退既有 `_incremental_save`

### T3 · P1 统一知识访问层 KAL

新增 `nucleus/knowledge_access_layer.py`（22 个接口方法）：
节点基础 / 查询（关键词·路径·层级·时间·来源器官）/ 语义检索（暴力余弦，预留 FAISS）/
图遍历（BFS，预留 Neo4j）/ 时序（预留 InfluxDB）/ 统计 / 写入 / 存储管理 / 缓存可观测。
**基础实现基于 json 后端**（duck typing 兼容节点池多种方法名），**LRU 缓存 + 单例**。
★本批**不做全量迁移**，现有代码仍直连快照 → 对现有行为零影响。

### T4 · P1 队列深度自适应降频

`nucleus/runtime_metrics.py` 追加：
- `assess_load_level()`：四级 LOW/MEDIUM/HIGH/CRITICAL（队列深度 / CPU / 内存 / 快照保存中），取最高维度
- `AdaptiveFrequencyController`：`register` / `get_interval` / `should_execute` / `get_stats`
- **关键操作白名单**（对话 / 心跳 / 生命体征 / 快照保存）任何等级都不降频，`get_interval` 恒 0
- CRITICAL 时非关键操作暂停；LOW 时系数 1.0 → **负载正常时行为完全不变**

★**未接线业务模块**（胃 / 器官扫描 / 代码学习 / 清理 / compaction）—— 属跨模块改造，建议下批专项。

### T5 · P2 WriteGuard 误判修复

**根因**：`reject_reason` 中 `is_test_like_env()`（含 `"pytest" in sys.modules`）判定
**优先于** `is_trusted_writer()`。框架进程内若有模块 `import pytest`，
框架即被误判为测试环境 → ReportBus 无法写生产目录（12 条 WARNING）。

**修复**：`is_test_like_env()` 中将「框架主进程」判定提到 pytest 判定之前；
新增 `resolve_env()`（production/test）与 `env_reason()`（判定依据留痕）；
新增 `WRITE_GUARD_FORCE_ENV`（None=自动 / "production" / "test"）强制覆盖。

**实测**：框架进程（pytest 已 import）→ `production`，`is_test_like_env=False` ✅ 误判消除。
