## 一、问题定义与现状（先说清"为什么是 167 条天生修不了"）

### 1.1 数据链路现状

普通 `[器官] ERROR: 消息` 日志行进入进化引擎时，**位置三要素全是空的**：

```python
# nucleus/evolution/LogAnalyzer.py:191-192
_key = f"log:{_organ}:{_level}:{_msg_key}"
_issue = self._get_or_create(issues, _key, "", 0, "", _level)   # ← file="" line=0 method=""
```

于是 `issue` 只有 `organ` 标签 + 消息文本，**没有方法名 ⇒ 没有 `original_code` 锚点**。
第88批已把这类补丁从"伪装成 LLM 生成残缺的假失败"改为**显式留痕跳过**（`_llm_bad_material`），但**能力缺口依旧**：

- `SafeEvolutionExecutor.py:501-502`：`if self_inspector and issue.get("organ") and issue.get("method")` → **method 为空直接跳过**，`_snippet` 保持 `""`；
- `SafeEvolutionExecutor.py:1216 / 2590 / 4009 / 4065`：多处按 `issue["method"]` 取素材/判可修。

### 1.2 ★ 根因（本批新查，共 4 条，均可直接验证）

| # | 根因 | 位置 | 说明 |
|---|---|---|---|
| **A** | **定位调用时 message 还是空串** | `LogAnalyzer.py:199-210` | `_locate_for_issue(_organ, _issue["message"])` 在 `_issue["message"]` 仍为 `""` 时就被调用；`message` 是在其**之后**的 `:209-210` 才填充。⇒ `guess_method_from_message("")` 恒返回 `""`；`locate_issue` 的 1a/1b 路径（从消息里抓 `File "..."`）**结构性不可达**。 |
| **B** | **定位只试一次，永不重试** | `LogAnalyzer.py:199` `_locate_attempted` | 首次尝试后置 `True`；即使后续行补上了 message，也**不再重试**。 |
| **C** | **器官名索引口径不对** | `self_inspector.py:1382-1392` 1c | 1c 只用 `_build_organ_name_index()`，键是**头部中文名**（243 个，如「脉冲驱动胃」）；而真实日志标签**多数是类名**（`PatchManager` 34 次、`InfoField`、`PulseSnapshot`、`PulseNodePool`…）⇒ **恒不命中**。第87批已建好 `_build_project_class_index()`（1007 类，§`self_inspector.py:1059-1133`）却**没接到 `locate_issue` 上**。 |
| **D** | **中文标签匹配过严** | `self_inspector.py:1390` | 模糊匹配写的是 `_cn.startswith(organ) or organ.startswith(_cn)`（**前缀**关系）。标签「胃」vs 头部名「脉冲驱动胃」、标签「肝」vs「肝器官」**都不满足** ⇒ 漏配。实测改用**包含**关系即可命中（但 2 字标签有误配风险，见 §5.3）。 |

> **一句话**：不是"没有定位能力"，而是**能力建好了、接线错了 / 口径错了 / 顺序错了**。

### 1.3 量化口径（本批实测，与第88批口径的差异已核对）

| 口径 | 数值 | 证据文件 |
|---|---|---|
| `logs/pulse.log.2`(10.8 MB) + `pulse.log` 中的 ERROR/CRITICAL 行 | **117** | `m89_t89b_proto.txt` |

| ⇒ **真实生产问题** | **31 个 / 63 行** | 同上 |

> **⚠️ 口径偏差说明（诚实记录）**：第88批报告记的 **167** 条 `method=空`，本批**未能原样复现**。

## 二、方案① 异常栈帧定位（补充用，**结论：不足以作为主方案**）

### 2.1 设计

```
ERROR 行 ──(后续 N 行内出现 Traceback)──> 取「最内层项目帧」 ──> {file, line, method, conf=0.9}
```

### 2.2 实测（`m89_t89b_proto2.txt`）

| 关联窗口 | 有栈帧的 ERROR 行 | 其中含「项目内帧」 | 覆盖率 |
|---|---|---|---|
| 1 行 | 0 | 0 | 0.0% |
| 2 行 | 7 | 2 | 1.7% |
| 5 行 | 11 | 2 | 1.7% |
| 10 行 | 17 | 2 | 1.7% |
| 20 行 | 21 | 19 | 16.2% ⚠️ |
| 40 行 | 41 | 31 | 26.5% ⚠️ |

**窗口 20/40 的跳升是假象**：框架绝大多数 ERROR 日志**不带 `exc_info`**，那些"附近"的 Traceback 多半属于**另一条错误**（实测例：`[PulseSnapshot] 全量保存失败` 被关联到 `PulseSnapshot.py:1472 _load_internal`，而它其实是 sandbox 测试注入的另一路错误）。**放宽窗口 = 提高误配**。

另一条通道 `runtime_metrics.error_snapshots`：**实测 0 条**（`m89_t89b_proto3.txt`）⇒ 当前不可用。

### 2.3 ★ 顺带发现的既有缺陷：**取帧取反了**

`_TRACEBACK_FILE_RE.search(_tb)`（`LogAnalyzer.py:226`）取的是**第一帧**；而 Python 打印顺序是**外→内**，第一帧是**调度/入口层**。
实测（`m89_t89b_frames.txt`）：

```
块#1 帧数=2
   首帧: organs/body/PulseLiver.py:493  in _do_optimize      ← search() 会选中它（调度层）
   末帧: organs/body/PulseLiver.py:2392 in _fuse_l2_to_l3    ← 真实致错点
```

⇒ 即使走①，也必须改为「**最后一个项目内帧**」。此项**独立于 T-89b 也有价值**（`_scan_runtime_metrics` 与 `LogAnalyzer` 逐行扫描两处都受影响）。

### 2.4 结论

① 的边际收益 **≤ 1.7%（2/117）**，且实现成本不低（需要跨行缓冲 + 归属判定）。**降级为可选项**，与②组合时只作为"当②失配时的二次机会"，**不单独立项**。

## 三、方案② 日志调用点定位（★ **主方案**）

### 3.1 原理

日志行的**字面量模板**在源码里是唯一的、可静态抽取的：

```python
# 源码（nucleus/field/InfoField.py:953 附近）
self._log(LogLevel.ERROR, f"handler 异常: {type(e).__name__}: {e}")
#                        └─ 字面量片段 = "handler 异常: "
# 日志（运行时）
[InfoField] ERROR: handler 异常: 'gbk' codec can't encode character ...
#                  └─ 与模板字面量前缀一致 ⇒ 反查调用点 ⇒ 所在方法 = _call_handler_safe
```

⇒ 建立 **调用点索引** `{(file, 所在方法, 行号, 字面量片段集合)}`，用日志消息回匹配，取最高分。

### 3.2 索引规模与性能实测

| 扫描范围 | 文件数 | 解析成功 | 调用点数 | 构建耗时 |
|---|---|---|---|---|
| `nucleus/` + `organs/` + `base/` | 287 | 287 | **979** | **4,476 ms** |
| 仅 `nucleus/` | 218 | 218 | 968 | 1,448 ms |
| 仅 `organs/` | 68 | 68 | 11 | 2,931 ms |

（`organs/` 调用点少但耗时高 —— 器官文件体量大，`ast.parse` 是主要成本。）

> **性能设计要求（强制）**：① 懒构建、只构建一次；② **mtime 签名失效**（复用第65批 `_method_body_cache` 的成熟模式）；③ 落盘缓存 `data/cache/log_call_sites.json`（**注意：需星轨确认该路径是否落在禁写白名单外的合法位置**）；④ 构建整体 `try` 包裹，任何文件解析失败只跳过该文件。

### 3.3 匹配规则与**误配风险量化**（本批最重要的发现）

朴素规则「取最长公共字面量」**会过火**。实测三档：

| 规则 | 折叠口径命中 | 并列 | 主要问题 |
|---|---|---|---|
| `contains`（包含，阈值≥5 字） | 23/31 = **74.2%** | 3 | 阈值 5 时把 26 条消息误配到 `experience_pool.py`（该文件有泛化模板 `写入失败: {}`） |
| `anchor`（必须以模板字面量**开头**） | 20/31 = 64.5% | **0** | 过于严格：`[补丁审批] 批量审批写入失败…` 被**去标签**预处理误伤 |
| `anchor + 覆盖率≥30%` | 1/31 = 3.2% | 0 | **过度保守，不可用** |

⇒ **修正为「best-of-variants + 交叉校验」**（推荐规则）：

1. 消息准备**两个变体**：`原文` 与 `去前导 [标签]`；
2. 每条调用点在其字面量片段上取 `max`：**锚定命中加权** `len*3+10`，包含命中 `len`；
3. 接受条件：**最长命中片段 ≥ 5 字**（实测 ≥5 与 ≥8 只差 1 条，取 5 更划算）；
4. **并列**（同分候选 >1）⇒ **拒答**（实测并列 = 0）；
5. **交叉校验**：若 `organ` 标签能定到文件（类索引/器官名索引），则要求**两路文件一致**，否则拒答。

### 3.4 推荐规则实测结果

| 指标 | 数值 |
|---|---|
| 折叠口径命中（31 个真实生产问题） | **24 / 31 = 77.4%** |
| 并列候选 | **0** |
| 交叉校验一致 / 不一致 | **23 / 0**（另 1 条 organ 定不到文件）|
| 命中文件 Top | `PatchManager.py` 10、`InfoField.py` 9、`PulseNodePool.py` 4、`StructuredParallelScheduler.py` 1 |
| **复合成功率（定位 + 抽出真实方法体）** | **24 / 31 = 77.4%** |
| 方法体长度 | min 531 / **中位 2,628** / max 17,363 字；**< 80 字的 = 0** |

命中样例（人工核对，**均正确**）：

```
[InfoField]  handler 异常: 'gbk' codec…      -> nucleus/field/InfoField.py::_call_handler_safe (L918)
[InfoField]  L0看门狗处理器超时(8.0s)…        -> nucleus/field/InfoField.py::_l0_watchdog_loop (L960)
[PatchManager] [补丁审批] 批量审批写入失败…    -> nucleus/reasoning/PatchManager.py::approve_all_patches (L726)
[pulse.structured_parallel] [任务组超时] …    -> nucleus/StructuredParallelScheduler.py::run_group (L248)
```

### 3.5 关键设计要点（必须写进实现的取舍）

1. **必须抽「完整语句/函数体」而不是"文件头 2000 字"**
   —— 第88批素材修正用的是"文件头 2000 字"，那对**方法级**补丁仍不是正确锚点（`original_code` 要在目标文件出现，且 LLM 必须整段替换）。调用点定位天然给出**方法边界**，可直接喂给 `PatchManager._verify_in_copy` 的 `original_code`。
2. **不得污染 `issue["file"]` / `_file` / `_resolved_file`**（PHASE13 红线）
   —— 新增独立字段承载，例如 `issue["call_site"] = {"file","method","line","confidence","rule"}`；第87批已确立"只回填 `issue["file"]`、不动 `_file`"的纪律，本设计沿用并**更严**（连 `issue["file"]` 也不动，避免改变 `_llm_no_file` 分支的既有行为）。
3. **`locate_confidence` 与既有 0.5 闸门对齐**
   —— `LogAnalyzer._LOCATE_CONF_THRESHOLD = 0.5`（`:245`）。建议：交叉校验一致 ⇒ `0.9`；仅单路命中且片段 ≥8 字 ⇒ `0.7`；片段 5~7 字 ⇒ `0.55`；并列/不一致 ⇒ `0.0` + `needs_human_confirm=True`。
4. **两条既有 bug 必须一起修，否则新能力打不满**
   —— 根因 A（顺序）与 B（一次性重试）：不修，则 `locate_issue` 永远拿到空消息、永远只跑一次。**修 A/B 是零风险的纯逻辑纠正**（约 12 行）。

## 四、方案③ 标签反查（文件级兜底 + 交叉校验器）

### 4.1 设计

```
organ 标签 ──(类索引 _build_project_class_index，87批已有)──> file  (conf 0.85)
           └─(器官名索引 _build_organ_name_index，需改「包含」匹配)──> file  (conf 0.7→0.6 视标签长度)
```

### 4.2 实测（`m89_t89b_proto2.txt` / `m89_t89b_folded.txt`）

- 按 organ 标签直接定到**文件**：**108/117 行 = 92.3%**（全部靠**类索引**）；
- 31 个真实生产问题：**25 个可定文件 / 6 个不能**；
- 不能定的标签：`AiBotSDK`、`ReportConsumers`、`pulse.structured_parallel`、`框架`、`肝`。

### 4.3 已知坑

| 坑 | 实测 | 处置 |
|---|---|---|
| 中文标签需**包含**匹配 | 「胃」→「脉冲驱动胃」、`肝`→「肝器官」 | 改 `in` 匹配，但**限制标签长度 ≥2 且命中唯一** |
| 2 字标签误配 | 「框架」**包含**于「能力框架」⇒ 指向 `nucleus/review/CapabilityFramework.py`（**错误**，真实来源是 `[FunctionLoader]`） | 短标签（≤2 字）+ 非唯一 ⇒ **只给 file、不打 method、conf ≤0.5**（即"需人工确认"，不进自动修复队列） |
| 头部格式不一致 | `StructuredParallelScheduler.py` 头部写成 `...py —— 结构化并行调度器`，正则把类名捕成 `py` | 索引键（中文名）仍正确；建议**另立**清理项（属头部规范化遗留，不在本设计范围） |
| `ReportConsumers` / `AiBotSDK` 定不到 | 类不在索引（可能非类名、或 `_` 前缀文件被跳过） | 承认落在**不可定位**集合（见 §6） |

## 六、明确"能定位 / 不能定位"清单

### ✅ 能定位（→ 有真实方法体，可进修复队列）

| 类型 | 实例 | 判据 |
|---|---|---|
| **器官/核心类内部的 ERROR 日志** | `PatchManager`（10/10）、`InfoField`（9/9）、`PulseNodePool`（4/4） | 调用点模板字面量 ≥5 字且唯一 |
| **带 `[批次标签]` 前缀的结构化日志** | `[补丁审批] …`、`[任务组超时] …`、`[第81批 T1] …` | best-of-variants 保留 `[标签]` 亦可锚定 |
| **异常捕获后 `_log(ERROR, f"…: {e}")` 型** | `handler 异常: 'gbk' codec…` | 字面量前缀稳定 |

### ❌ 不能定位（→ **结构性没有修复单元**，应显式留痕、**不计入修复率分母的失败统计**）

| 类型 | 实测实例 | 原因 |
|---|---|---|
| **框架/加载器级标签** | `[框架] [FunctionLoader] 功能模块 对话交互 运行时异常` | 该消息由**动态拼接**产生（`f"{模块名} 运行时异常"`），无稳定字面量；`organ` 标签也不在索引里 |
| **中文单字标签** | `[胃] 异常: boom`、`[肝] 异步优化任务异常(首报)` | 标签 = 单字 + 消息短（<8 字）；且 `boom` 系测试注入 |
| **三方 SDK** | `AiBotSDK` | 不在项目源码内（外部库） |
| **消息完全动态** | `[PulseSnapshot] Parquet 缺列 ['acquired_time', …]` | 字面量片段 <5 字（`Parquet 缺列` 前后皆变量）或模板在 `nucleus/mnemosyne/` 下但被去标签预处理吃掉 |
| **消费者/报告层字符串** | `ReportConsumers` `[自认知·补丁告警] …` | 类名不在类索引（疑似非类名或文件被 `_` 前缀跳过） |

> **建议（写入下批任务书）**：对 ❌ 集合，在 `[进化健康]` 统计里**单列** `无修复单元=N`，与 `LLM补丁失败=M` 分开 —— 否则修复率永远被这类问题稀释，无法反映真实能力。

## 七、风险与反例（必须先接受再落地）

| # | 风险 | 实测/推理依据 | 缓解 |
|---|---|---|---|
| 1 | **报错点 ≠ 致错点** | `_call_handler_safe` 是**捕获并记录**异常的地方，真正的 bug 在被调用的 handler 里 | 定位结果命名为"**报错点**"而非"缺陷点"；LLM prompt 需明示"这是记录点，请判断是否需顺着调用链下探"；confidence 上限 0.9（不给 1.0） |
| 2 | **泛化模板误吃具体消息** | 阈值 5 时 `写入失败: {}` 命中 26 条异域消息（`experience_pool.py`） | 覆盖率下限 + **要求模板唯一性或文件名与 organ 交叉一致** |
| 3 | **测试注入噪声污染** | 117 行中 54 行属 `simulated crash` / `m80_sandbox`（sandbox 测试写进了**生产** `logs/pulse.log`） | 独立问题（日志隔离未覆盖子进程）；**本设计需先按噪声过滤**，否则样本失真 |
| 4 | **日志轮转导致 file/line 过期** | `logs/pulse.log.2` 10.8 MB / 14:00 轮转 | 索引按 **mtime** 失效；line 号仅作参考，方法名才是锚点 |
| 5 | **索引构建 4.5 s 拖慢进化轮** | `m89_t89b_perf.txt` | 懒构建 + 落盘缓存 + 单轮最多构建一次；若仍超预算 ⇒ 只扫 `nucleus/`（1.4 s，覆盖 968/979 调用点） |
| 6 | **PHASE13 口径漂移** | 第87/88 批红线 | 新字段隔离（§3.5-2）+ 零回归单测（§5.4-⑥） |
| 7 | **修复率仍为 0%** | 本设计只解决"有没有素材" | 与"LLM 补丁质量 / 回归验证"分批验收，**不承诺**修复率单批改善 |
