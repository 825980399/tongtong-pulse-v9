## 一、T1 P1-98 对话回复错位（最优先）

**文件**：`organs/brain/PulseCortex.py`（任务书写 `nucleus/cortex/CerebralCortex.py`，**该路径不存在**）

### 实测证据（与任务书逐条吻合）
- `超时释放输出锁` **4 次**：09:24:43 / 09:26:42 / 09:28:53 / 09:30:31（任务书列的 4 个时间点完全一致）
- correlation_id 序列实测：`ctx:2,2,3,3,5,6,5,6,7,8,7` —— **ctx:4 缺失**（跳号确认）

### 根因
输出锁 90s 超时释放后，旧任务仍在异步链路里跑；等它终于产出答案时，用户已经在问下一个问题，
而**输出路径从不校验「这个答案属于哪个会话」**，于是把上一个问题的答案发给了新问题。

### 修复（灰度 `ENABLE_DIALOG_LOCK_GUARD`，默认 True）
| 要求 | 实现 |
|---|---|
| 输出前校验 correlation_id | 三处对话输出（普通 / 带文件 / **看门狗超时兜底**）全部加 `_dialog_should_output(cid)`；被作废或过期的回复一律丢弃并记 INFO |
| 超时释放时取消旧任务 | `cancel` 策略下把旧 cid 记入 `_cancelled_correlations`，其回复被 `_dialog_should_output` 判否 |
| 对话队列机制 | `DIALOG_QUEUE_STRATEGY="queue"`（默认）：旧任务继续、新问题入队，并先给用户「正在处理上一个问题，请稍候（队列中还有 N 个）」提示；旧任务输出完成后由 `_dispatch_queued_dialog()` 自动派发下一条。`"cancel"`：作废旧任务、立即处理新问题 |
| 排队消息不被误清 | `_cleanup_pending` 给排队会话 180s TTL（普通仍 30s） |

**关键设计**：`_dialog_mark_output_done()` 在**无论是否输出**的情况下都会调用 —— 保证被丢弃的回复不会把队列卡死。

### 验收
新增 `tests/test_dialog_guard_m15.py` **16 例**：开关默认值、关闭零副作用（不排队、恒放行）、
首次输入派发、queue 排队+提示、queue 满挤掉最旧、cancel 作废+丢弃、过期回复丢弃、
输出完成自动派发队列、排队 TTL 加长、**源码接线护栏（3 处输出 + 输入登记）**、cid 唯一递增无跳号。

## 二、T2 P1-92 进程池崩溃自动重建

**文件**：`nucleus/reasoning/ReasoningWorkerPool.py`

### 实测证据
`ReasoningWorkerPool] ERROR: 任务提交失败(...): A child process terminated abruptly, the process pool is not usable anymore`
**实测 12 次**（任务书列 8 次；实测时间点 02:01 / 03:26 / 03:31×2 / 03:51 / 05:10 / 07:38 /
08:35×2 / 08:40×2 / 09:28）。崩溃前只有 00:34、00:37 两次**平滑重建**，**崩溃后无任何重建** → 进程池永久失效。

### 修复（灰度 `ENABLE_POOL_AUTO_REBUILD`，默认 True）
1. `submit` 捕获 `BrokenProcessPool` → 触发重建 → **重试本次提交**（最多两轮）；
2. 重建在 `_rebuild_lock` 内串行化（重建期间其他线程的提交等价于排队等待，重建后按到达顺序继续），
   指数退避 0.1→0.2→0.4s（上限 1s）；**实测重建耗时 0.0~2.0ms**，远优于「5 秒内」标准；
3. 连续失败达 `POOL_REBUILD_MAX_RETRIES`（3）→ **降级为同进程同步执行**：返回**已完成的 Future**
   （与 `submit` 契约一致，调用方既有 `if _future:` 判空逻辑无需改动），功能不失效；
4. 定期健康检查（`POOL_HEALTH_CHECK_INTERVAL`，默认 60s，按间隔节流）→ 探到 `_broken` 提前重建；
5. 每次重建打 INFO：崩溃原因 / 重建耗时 / worker 数 / 代数；
6. **新增 `_closed` 守卫**：已 shutdown 的池禁止被 submit 复活（防停机期重建）。

### 修复过程中的两个硬坑（已解决）
- `BrokenProcessPool` **不在 `concurrent.futures` 顶层导出**（在 `concurrent.futures.process` 下）——
  按顶层写法会直接 ImportError。**`py_compile` 只查语法、不执行模块级代码，抓不到这个错误**，
  正是任务书把 pytest 设为 P0 门禁的价值所在。
- 灰度关闭时必须**完全退回修复前行为**（记 ERROR + 返回 None），不能走降级同步。

### 验收
`tests/test_pool_rebuild_m15.py` **9 例**：崩溃→重建→重试成功（断言 rebuild_count/pool_generation）、
池缺失触发重建、连续失败降级同步（含 Future 可用性）、健康检查提前重建、
**开关关闭时返回 None 且不重建/不复活**、停机后禁止复活、统计结构。

## 三、T3 P1-93 子进程崩溃根因排查

**文件**：`nucleus/reasoning/SafeEvolutionExecutor.py`（任务书写 `organs/body/…`，**该路径不存在**）+ `nucleus/reasoning/evolution_worker.py`

### 根因（实测定位，任务书未给出）
崩溃次数与任务书**精确吻合**：**109 次**（review 80 / repair 22 / execute 7）。
但关键证据是：`logs/pulse.log` 中 worker 内部 `except` 的打印标记 **`evolution_worker.py:` 出现 0 次**
—— 说明崩溃发生在 `run_evolution_worker` 的 try **之外**（spawn 期引导/导入阶段），
所以日志里**只有 exitcode、没有原因**。

### 修复（灰度 `ENABLE_EVOLUTION_CRASH_RETRY`，默认 True）
1. **`evolution_worker.py` 顶层只留 stdlib 依赖**（`safe_read_json` 改惰性导入）——它是 spawn 入口模块，
   顶层非 stdlib 导入失败就永远无法自报原因；
2. 新增 `run_evolution_worker_captured` 作为 spawn 目标：**先接管子进程 stderr**，再跑 worker，
   任何 `BaseException` 都落盘到输出文件（含 traceback + 阶段）；
3. `run_in_subprocess` 新增 **stderr 文件**；崩溃时把 **stderr 尾部 + 崩溃载荷 traceback** 一并打进 WARNING；
4. **崩溃自动重试** `EVOLUTION_CRASH_MAX_RETRIES`（默认 2）；
5. 重试仍失败 → **降级为同进程同步执行**（`_run_in_process_degraded`，按 mode 跑 repair/review/execute）；
6. **崩溃统计** `get_crash_stats()`：按 mode 记次数 + 原因分布 + 最近一次详情。

### 验收
`tests/test_evolution_crash_patch_m15.py`（T3 部分 11 例）：配置与开关、统计累计与读取、
stderr 尾部读取、降级路径（inspector 不可用/未知 mode 返回 None）、
**源码接线护栏**（stderr+traceback 入日志、重试循环、降级调用、stderr 临时文件、captured 入口被使用）、

4. **`tmp/test_data/` 的长期存在**
   大量 `WinError 5` 出现在 `tmp/test_data/p17_*`（`verify_phase17_1_5` 子进程测试目录）。
   属测试环境产物，非生产路径；但**建议 verify 脚本的子进程目录改用短路径 + 退出即清**
   （Windows 上长路径 + 嵌套目录易触发占用/权限竞争）。

5. **tasks 契约一致性**
   `submit()` 在降级路径返回**已完成的 Future** 而非 None —— 语义上更安全（调用方无需改动），
   但请星轨确认这一契约扩展是否与既有调用方约定一致。
