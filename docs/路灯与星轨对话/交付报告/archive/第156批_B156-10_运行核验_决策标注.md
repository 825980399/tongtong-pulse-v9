## ① 语义缓存 hit_count 字段回写（已修 · 代码提交）

- **缺陷**：`SemanticCache.add()` 每次新建 `CacheEntry(hit_count=0)`，覆盖 `lookup()` 内存累加的命中数；且命中数**从不落盘** → 「命中口径」跨写入/重启失真（死置）。
- **修复**：
  - `add()` 同 hash 已存在时保留既有 `hit_count`（`_keep_hits = _existing.hit_count if _existing else 0`）；
  - 新增 `flush()` 全量重写 `semantic_cache.jsonl` 落盘命中数（仅在守护线程 `_handle` 后 / `close()` 前触发，主推理流程零阻塞）；
  - `lookup` 命中时 `self._dirty.add(_best.hash)`，`_handle()` / `close()` 调 `flush()` 回写。
- **门控**：`tests/test_b156_10_semantic_cache_hitcount.py`（注入 `_FakeEncoder` 固定向量，验证同 hash 二次 add 不清零、flush 落盘、跨重载保留）→ 1 passed。
- **门禁复核**：ruff F=0；slice1-collect 4487 在基线 4484±5 内（无需 `[ci-gate-change]`）；cw2/deprecated/event-string/CW3-B/登记册全 PASS。
- **提交**：`df1839c`（匿名 `Tongtong Dev <dev@tongtong.local>`，未 push）。

## ③ ANN 12k 级 IVFFlat 触发（决策 + 待活体核验）

### 现状（代码实查）
- `config.py:4874` `ENABLE_FAISS_FAST_OPS = True`（fast_ops.fast_vector_search 优先走 FAISS）
- `config.py` `FAISS_FAST_OPS_MIN_CANDIDATES` 默认 5000（`fast_ops.py:208` 兜底 5000）
- `fast_ops.py:213` `_faiss_on and _n >= _faiss_min and _n>0 and _dim>0` → 走 FAISS；
- `fast_ops.py:224` 用 **`IndexFlatL2`**（`# 现建现用（FlatL2，精确）`）—— **精确检索，无 IVFFlat/量化索引**。

### 决策（已定）
1. **当前 12k 级仍属 FlatL2 精确路径**：候选 ≥ 5000 即走 FAISS，但用的是 `IndexFlatL2`（暴力精确 L2），**未触发 IVFFlat 量化索引**。故 12k 级无量化召回损失风险，与任务书「IVFFlat 触发」担忧的解法是「维持 FlatL2 精确，不引入量化」。
2. **若未来要上 IVFFlat（量化）**：须评估召回率损失 + 重建索引开销，且须以「PID / 时刻 / 夹具」三口径排除测试误计——即压测向量集必须来自真实业务进程（非测试夹具注入的假性 12k 向量），否则会虚高触发量化决策。
3. **阈值 5000 合理**：小候选集建索引开销 > 暴力余弦，故仅 ≥5000 走 FAISS（零回归关键），维持现状。

### 待活体核验（当前无法执行）
- 12k 级真实 ANN 检索时延 / 召回率压测**未做**（需停框架 + 真实业务向量集）。
- 待活体窗：以「PID/时刻/夹具」三口径确认向量源真身 → 跑 12k 级 `fast_vector_search` → 记录 FlatL2 时延基线 → 回填。

## ⑤ 依赖度基线双口径（决策 + 待强制 guard）

### 现状（代码实查 · `nucleus/LLMDependencyMetrics.py`）
- `llm_dependency_ratio()`（L275-280）：`llm / (llm + local)`，分母**只含回答类两类**（不含 search/digestion）。
  - docstring 自陈（answer_requests L173-186）：实测 `search_count=774` / `digestion_count=36032` 完全不计入分母 ⇒ 报出 **97.73%**（实为「回答通道内大模型占比」被误读为「框架总依赖度」）。
- `overall_llm_share()`（L189-205）：`llm / (llm + local + search + digestion)`，分母含全部四类处理。
  - 实测 **12.72%**，才是「全栈大模型占比」真实值。
- 二者均已在 T-94c 通过 docstring 明确口径；`answer_requests` 别名 `total_requests` 已在 T-95c 移除（唯一真源）。

### 决策（已定 · 待星轨确认）
1. **唯一真源指定**：`overall_llm_share`（全栈 12.72%）为「框架对大模型依赖度基线」**唯一对外报数口径**；`llm_dependency_ratio`（97.73%）降级为「回答通道内大模型占比」子指标（保留，docstring 已注明，不再作为总依赖度对外）。
2. **更新触发条件（基线刷新门槛）**：
   - 四类计数（llm/local/search/digestion）**齐备**且总样本量 ≥ **N=1000** 次处理事件；
   - 单次抖动 / 单场景尖峰**不触发**重锚（防噪声）；
   - 重锚须记录「样本区间 + 触发原因 + 新基线值」入台账。
3. **代码强制（guard）待活体核验**：当前仅 docstring 约定，无运行期 guard 阻止 `llm_dependency_ratio` 被误作总依赖度报出。建议加 `check_dependency_baseline_guard.py`（消费方白名单 + 对外面板仅读 `overall_llm_share`）—— 待停框架 + 星轨裁决后实施。
