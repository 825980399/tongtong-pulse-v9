## 二、T1：`_deep_think` 子进程恒降级根因修复（P2-185）

### 2.1 根因定位过程（任务书要求 4 步核实）

| 任务书要求的核查项 | 实测结论 |
|---|---|
| ① 子进程启动时的知识上下文传递机制 | **不存在传递** —— 子进程入口 `ReasoningWorkerPool._execute_reasoning_task` 是模块级静态方法，**不接收也不加载**任何知识上下文 |
| ② 子进程的知识加载逻辑 | **无加载逻辑** —— 该函数只支持两类纯计算任务（`FrequencyCodec.encode_batch` / `ResonanceEngine.resonate_batch`） |
| ③ 子进程与主进程的通信协议 | 单向：主进程 `submit(func_name, *args)` → 子进程按 `func_name` 分发；**无回传通道可用于回传知识态** |
| ④ 配置问题 / 路径问题 / 逻辑问题？ | **架构问题（有意设计）** |

**决定性证据**（`nucleus/reasoning/ReasoningWorkerPool.py:269-277` 原文注释）：

```python
# ★P1-5修复：深度思考任务返回明确的降级标记
# 子进程无法访问node_pool/knowledge_tree等核心依赖，
# 深度思考应由主进程同步执行以保证推理质量。
if func_name == "PulseInnerWorld._deep_think":
    return {"status": "degraded",
            "reason": "子进程无知识上下文，请改用主进程同步执行深度思考",
            "result": None}
```

即：**降级是第15批 P1-5 的有意架构决策**，不是 bug。

### 2.2 真正的缺陷：degraded 标记是 truthy dict，两处调用点未识别

`_deep_think` 共 3 处进程池调用点，处理方式**不一致**：

| 调用点 | 位置 | 修复前行为 | 后果 |
|---|---|---|---|
| 思考纪律·深度通道 | `PulseInnerWorld.py:914` | `_deep_result = _future.result(...)` → dict | **dict 为 truthy → `if not _deep_result:` 的主进程回退被跳过**；dict 参与后续融合 |
| 复杂度过高路径 | `:1194` | `deep_answer = _future.result(...)` → dict | 同上；且 dict 直接进入 `_cache_inference` / `_enhance_answer` → **内部 dict 可能进用户可见答案** |
| 强制深度思考调度 | `:2554` | `isinstance(_result, dict)` → 置 None | ✅ 第29批已修（正确） |

**旁证（第30批的运行日志）**：`:2554` 路径的 DEBUG 日志 `子进程返回dict(status=degraded)，改为主进程执行` 在 `logs/pulse.log` 中真实出现，说明该路径的判定生效；而另两处无任何痕迹。

### 2.3 架构裁决（对应任务书 §三.1）

**子进程方案不可行**，理由（实测）：

1. 深度思考依赖 `node_pool`（PulseNode 池）、`knowledge_tree`、`_model_cache` 等**巨型内存态对象**（主快照 318MB，禁止整体 `json.load`），跨进程序列化成本与风险不可接受；
2. `_execute_reasoning_task` 位于**模块级**，无实例可绑定，无法访问 `PulseInnerWorld` 的任何状态；
3. 该降级分支是**第15批 P1-5 的明确决策**，有注释记录设计意图。

**采纳任务书 §三.1 提出的备选方案**：「**主进程同步执行 + 超时保护**」。
—— 需要说明的是，**该方案本就已存在**（`:923-924` / `:1205-1206` 的 `if not _deep_result: _deep_result = self._deep_think(question)`），只是被 truthy dict 挡死、从未真正生效。本次修复即"让既有正确路径生效"。

### 2.4 修复方案（双层 + 双灰度开关）

**A. PulseInnerWorld 侧**（开关 `ENABLE_DEEP_THINK_SUBPROCESS_FIX`，默认 True）

新增 `_m31_accept_subproc_deep_result(result)`：
- `str` → 原样返回（空串 → None）
- `dict` → **None**（含 degraded 标记，DEBUG 留痕含真实 status）
- `None` → None
- 其他 → `str(result)`

三处调用点统一改用之；后两处（`:914` / `:1194`）的主进程回退同时补上第27批的 **deadline 预算**（`_m31_deep_fallback_deadline(start_time)`，以**推理开始时刻**起算，而非进入 `_deep_think` 的时刻）。

**B. ReasoningWorkerPool 侧**（开关 `ENABLE_DEEP_THINK_SUBPROCESS_BYPASS`，默认 True）

`submit()` 开头对该任务直接 `return None` —— 既然结果 **100% 无效**，就不必付一次跨进程往返（pickle + 进程调度 + Future 等待）。调用方 `if _future:` 判空即自然回退，与 submit 既有失败路径语义完全一致。

**零回归保证**：两个开关关闭时分别回到"dict 被当作结果"与"仍提交进程池"的原行为，并有 `test_43_switch_off_reproduces_old_bug` 用例固化。

### 2.5 门控单测（23 例，`tests/test_deep_think_subproc_m31.py`）

覆盖：str 透传 / degraded 拒绝 / 任意 dict 拒绝 / None / 空串 / **truthy 陷阱回归护栏** / 开关关闭还原 / deadline 口径（含 `None`、预算 0、开关关）/ bypass 开与关 / 其他任务不受影响 / 源码接线（4 处调用）/ **真实源码切片 exec**（degraded → 主进程被真实调用 / 携带 deadline / 关闭开关复现旧 bug）。

## 三、T2：多步检索成功率低修复（P2-184）

### 3.1 根因定位（3 项实测）

**① 检索词退化 —— 成立（任务书判断正确）**

三个多步推理入口都用**定长贪婪切片**：

```python
for _m in re.finditer(r'[\u4e00-\u9fff]{2,6}', question):   # ← 连续汉字按 6 字一刀切
    _w = _m.group()
    ...
```

长问题因此被切成**跨词边界的错位碎片**（实测见 §3.3 表）。

**② 分支生成"恒返回 None" —— 不成立（任务书偏差）**

任务书称"只读 `REMOTE_API_CONFIG`，在渠道体系下恒返回 None"。实测：

```
TTP_REMOTE_API_KEY = SET(len=35)      ← 环境变量已设置
REMOTE_API_CONFIG.enabled = True
→ _remote_available = True            → 不会恒返回 None
```

真问题是**另一个**：它**直连单端点**，绕过渠道池的优先级 / 并发管控 / 熔断（第24批成果），且只认 `TTP_REMOTE_API_KEY` 单一变量（换机/未配即恒 None，是**脆弱点**而非"恒定故障"）。

**③ 失败原因不具体 —— 成立**：v2 每步只记「成功/兜底」，无法区分卡在哪一环。

### 3.2 修复方案

**① 检索词提取（4 处调用点统一）**

新增 `_m31_extract_key_terms(question, limit)` —— **词性感知**提取：
1. `jieba.posseg` 词性标注，丢弃功能词性（副词 `d` / 连词 `c` / 介词 `p` / 助词 `u` / 代词 `r` / 方位 `f` / 标点 `x,w` / 数词 `m,q` / 时间 `t`）；
2. 停用词表滤掉高频指令词 / 疑问词 / 连接词（"请/帮我/分析/进行/对比/比较/优劣/自我/什么…"）与单字；
3. **保持原文出现顺序**取前 N 个（问题前半段承载核心实体；首版曾用"长度优先"，实测引入噪音，已改）；
4. **三级回退不降级**：`posseg` → `jieba.cut` → 标点/虚词切分；**任何一级都不会退回定长切片**。

接入点（共 4 处）：`_generate_task_plan` / `_multi_step_execute`(v1) / `_multi_step_execute_v2` / `_generate_branch_with_model` 的 prompt「核心概念」行。

**② 分支生成渠道化**（开关 `ENABLE_BRANCH_GEN_CHANNEL_FIRST`，默认 True）

新增 `_m31_branch_endpoint()` —— **渠道池优先 → 单端点回退**，返回 `(api_url, api_key, model, source)`；`_generate_branch_with_model` 的可用性判定与实际调用都改用它，日志输出 `分支生成端点: channel:ark-ds-v4-flash model=...`。

**③ 失败原因具体化**：v2 每步新增 `fail_reason` 字段并进 INFO 日志，五档判据：
`四个来源(检索/重试/降级/模型)均无结果` / `结果类型异常(X)` / `结果过短(N字<15)` / `未通过有效性判定(占位模板/中文占比不足)` / `与步骤目标无词汇交集`。
