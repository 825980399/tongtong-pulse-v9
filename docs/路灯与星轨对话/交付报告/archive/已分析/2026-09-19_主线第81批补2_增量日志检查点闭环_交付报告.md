## 0. 一句话结论

在 `PulseSnapshot` 中抽出统一的「全量检查点」方法 `_m67_full_checkpoint()`，把**外层 `save()` 全量分支 / 删除比例熔断路径 / 达阈值合并路径**三条曾经分叉的编排统一为「**JSON 物化成功 且（Parquet 未启用 或 `save_parquet()` 返回 True）→ 才清空 `snapshot_incremental.jsonl`**」。由此：

- **jsonl 不再无限累积**：常规全量（每 3600s / 退出 force_full）刷新后即被清空，jsonl 只保留「最近一次 Parquet 全量检查点之后」的增量；
- **熔断/达阈值两条路径不再丢 Parquet**：降级/合并全量时同步刷新 Parquet，主存储加载不再漏数据；
- **物化失败必保留 jsonl**：Parquet 失败 = 检查点未达成 = 清空不发生，靠下次启动「旧 Parquet + jsonl 重放」兜底，**零丢失**；
- **`SNAPSHOT_USE_INCREMENTAL_LOG=False` 时全部新增分支 no-op**：逐字节一致、不生成也不清空 jsonl（C6 零回归用例 + m81 37 双态复核证明）。

### 1.2 统一检查点方法全文（`PulseSnapshot.py:1026-1067`）

```python
    def _m67_full_checkpoint(self, saved_nodes: list, current_checksum: str,
                             start_time: float) -> bool:
        """★第81批补2 T1：统一"全量检查点"语义 = 全量物化（JSON[+Parquet]）+ 增量日志清空。

        - 先 _full_save（写 JSON 全量/兼容备份、更新内部状态、Parquet 行数校验日志）；
        - Parquet 启用（self._use_parquet，与 save() 全量分支同口径）时调用 save_parquet()
          并取 bool 返回；未启用（纯 JSON）时该步视为成功；
        - 仅当 _full_save 成功 且（Parquet 未启用 或 save_parquet() 返回 True）时，若增量
          日志启用则清空 jsonl 并返回 True；
        - 任一要素失败 → 保留 jsonl（下次启动「旧 Parquet + jsonl 重放」兜底，零丢失），
          捕获 Parquet 异常不崩溃，返回值如实反映全量 JSON 是否成功。
        """
        try:
            _json_ok = bool(self._full_save(saved_nodes, current_checksum, start_time))
        except Exception as _e:
            self._log(LogLevel.ERROR,
                      f"[第81批补2 T1] 全量保存异常（检查点未达成）: "
                      f"{type(_e).__name__}: {_e}")
            return False
        if not _json_ok:
            return False
        _parquet_enabled = bool(getattr(self, "_use_parquet", False))
        _parquet_ok = True
        if _parquet_enabled:
            try:
                _parquet_ok = bool(self.save_parquet())
            except Exception as _e:
                _parquet_ok = False
                self._log(LogLevel.WARNING,
                          f"[第81批补2 T1] Parquet 物化异常（检查点未达成，保留增量日志）: "
                          f"{type(_e).__name__}: {_e}")
        if not _parquet_ok:
            self._log(LogLevel.WARNING,
                      "[第81批补2 T1] 全量检查点未达成：Parquet 物化失败，增量日志保留"
                      "（下次启动将 Parquet+jsonl 重放兜底，零丢失）")
            return _json_ok
        if self._m67_incremental_log_enabled():
            self._m67_clear_incremental_log()
            self._log(LogLevel.INFO,
                      f"[第81批补2 T1] 全量检查点达成: {len(saved_nodes)} 节点, "
                      f"Parquet{('已刷新' if _parquet_enabled else '未启用')}, jsonl 已重置")
        return True
```

**设计要点（逐条对应任务书 T1）：**

1. **取数口径未新造**：Parquet 判据用 `self._use_parquet`（`__init__` 读 `config.FEATURE["use_parquet_snapshot"]`，config.py:1726=True），与 `save()` 全量分支改造前的口径**完全同源**；**没有**改用 `_m68_parquet_primary_enabled()`（后者读 `PARQUET_AS_PRIMARY_STORAGE`，属加载侧口径，与"是否写 Parquet 副本"是两回事）。`_m68_parquet_primary_enabled()`（L1163–1169）本批未触碰，与 `.bak_batch81c` 逐字节一致。
2. **返回值如实**：Parquet 失败时 `return _json_ok`（=True，因 JSON 已成功），**不谎称完全成功也不谎报失败**——外层 `save()` 的 L1 同步、返回值语义不变。
3. **状态计数不重复**：`_total_saves += 1` / `_last_save_*` / `_update_saved_nodes_map` 仅由 `_full_save` 内部（L698–705）执行恰好一次；熔断路径原 L974–979 的重复状态维护已随改造移除（改为直接 `return self._m67_full_checkpoint(...)`）。
4. **异常不漏**：`_full_save` 与 `save_parquet` 分别独立 try/except，均带 `type(e).__name__:e` 与 `[第81批补2 T1]` 前缀留痕，无 `except: pass`（满足铁律10）。

## 2. 四条路径状态转换表

约定：**JSON**=主快照 `pulse_knowledge_snapshot.json`；**PQ**=`data/knowledge/parquet` 分片；**jsonl**=`snapshot_incremental.jsonl`。
「检查点达成」= `_full_save` 成功 且（`self._use_parquet=False` 或 `save_parquet()==True`）。

| 路径 | 触发条件 | JSON 全量 | Parquet 分片 | snapshot_incremental.jsonl | 检查点达成后 |
|---|---|---|---|---|---|
| **A 常规全量** | `force_full=True`（退出/显式）或 `_seconds_since_full ≥ SNAPSHOT_FULL_SAVE_INTERVAL(3600)` 且变更数超限 | **重写**（`_full_save`） | `_use_parquet` 时**刷新**（`save_parquet()`） | **清空**（`_m67_clear_incremental_log()`） | jsonl 归零，回到「仅 PQ/JSON 全量」态 |
| **B 常规增量** | `_seconds_since_full < 3600` 且 `变更数 ≤ 200` 且快照已存在，且 `SNAPSHOT_USE_INCREMENTAL_LOG=True` | **不写** | **不写** | **追加** upsert/delete 行（O(变更数)） | 增量累积，等待下次全量检查点 |
| **C 删除比例熔断** | 路径 B 内，`存活>0` 且 `删除数/存活数 > SNAPSHOT_INCREMENTAL_LOG_DELETE_RATIO_MAX(0.5)` | **重写**（降级全量，`拒写 delete`）| `_use_parquet` 时**刷新** | 成功→**清空**；PQ 失败→**保留** | 熔断降级不再丢 PQ（本批修复点）|
| **D 达阈值合并** | 路径 B 追加成功后，`jsonl 行数 ≥ SNAPSHOT_INCREMENTAL_LOG_MAX_LINES(50000)` | **重写**（合并） | `_use_parquet` 时**刷新** | 成功→**清空**；PQ 失败→**保留**（下轮重试）| 达阈值合并不再丢 PQ（本批修复点）|

**改动前后差异（关键）：**

| 路径 | 改动前 | 改动后 |
|---|---|---|
| A 常规全量 | 刷 JSON+PQ，**不清 jsonl** → jsonl 无限累积、启动越来越慢 | **清 jsonl** → jsonl 只含最近检查点后增量 |

| C 熔断 | 清 jsonl，**不刷 PQ** → PQ 主存储丢数据 | **刷 PQ + 成功才清 jsonl** |
| D 达阈值 | 清 jsonl，**不刷 PQ** → PQ 主存储丢数据 | **刷 PQ + 成功才清 jsonl** |

## 6. 遗留项与风险

1. **`node_pool` 取数与 `saved_nodes` 时点一致性（T1 要求核查）**：
   `save_parquet()` 内部经 `node_pool.get_all_including_evicted()` 取数（L2510–2511）。在**外层 `save()` 全量分支**与**达阈值路径**（均在 `save()` 调用栈内、node_pool 未被并发改写）中，`node_pool` 即当前内存全集来源，与传入 `saved_nodes` **同源同帧**，无时点不一致。
   在**熔断路径**：`save_parquet()` 在 `_m67_incremental_log_save` 内部被调用的那一刻，`node_pool` 仍是调用方 `save()` 时的同一池（同进程同步执行，无 await/线程切换）。**结论：未发现取数时点不一致**；`save_parquet()` 取数/分区/schema **未改动**。残余风险：若未来 `save_parquet` 被移入异步线程执行，需重新评估（当前 `SNAPSHOT_ASYNC_SAVE` 路径与本检查点无关）。
2. **纯 JSON / Parquet 关闭场景兼容核对**：`_use_parquet=False`（`FEATURE["use_parquet_snapshot"]=False`）时，检查点内 Parquet 步恒视为成功 → JSON 全量成功即清 jsonl，**不调 `save_parquet()`**。已由 C6（显式关 `SNAPSHOT_USE_INCREMENTAL_LOG`）+ `test_33`（残缺实例无 `_use_parquet`）双向覆盖；`SNAPSHOT_SAVE_JSON_BACKUP` 开启/关闭均不影响检查点判定。
3. **RPO 窗口**：见 §7，第二步翻转后 RPO≈1h 窗口**消除**，残余仅"最后一次 jsonl 追加未 fsync 的秒级"。
4. **本批未修、仅记录**（遵命不改）：
   - `_framework_probe` 依赖 `wmic` → 沙箱/无 wmic 环境 verify 会少跑 T12（P2，第82批）。
   - `m72` 2 个预存失败（`test_benchmark_synthetic_stages` FAISS `ADD_UNDERFLOW`、`test_benchmark_real_loader_12295` 硬编码 12295 vs 实际 12359）——对照 `.bak_batch81c` 基线**同样 2 failed**，与本批无关，属预存；本批仅修正了其中的 `test_kal_neo4j_read_enabled_flag` 隔离缺陷。
