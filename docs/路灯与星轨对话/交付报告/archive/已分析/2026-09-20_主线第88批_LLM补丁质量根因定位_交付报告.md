## 二、根因定位：输入素材 / prompt / 格式 三层逐层分析

### 层1 · 输入素材 —— **真因在这里（取错，不是生成错）**

调用链（`nucleus/reasoning/SafeEvolutionExecutor.py::repair_with_distillation`）：

```
L1296  if self_inspector and _organ and _method:   ← method 为空 ⇒ 直接跳过，_snippet 仍为 ""
L1306  _related_logs = self._find_related_logs(_file or _resolved_file, _method)
L1312  if not _snippet:                            ← 进入兜底分支
L1320      _fallback_on = ENABLE_REPAIR_SNIPPET_FALLBACK (默认 True)
L1327      if _fallback_on:
【改前】       _snippet = self._extract_comparison_material(
                            _issue, _related_logs, _file or _resolved_file, _method)
                              ↑↑↑ 此处 _file / _resolved_file 恒为空
```

`_extract_comparison_material`（L725）优先级：① `_read_snippet_from_file(file_path, method)` → ② `issue` 的 `description/message/...` → ③ `related_logs`。

- `file_path` 为空 ⇒ ① 直接返回 `""`（`_read_snippet_from_file` L697 `if not file_path: return ""`）
- ⇒ 落到 ② ⇒ 素材 = `issue["description"]` = **158 字 ERROR 日志文本**（实测）

而**第87批已经把这个文件路径解析出来了**，只是存进了 `issue["file"]`（受 PHASE13 统计口径红线约束，刻意**没有**回填 `_file` / `_resolved_file`）：

```
logs/pulse.log:78207  11:17:22 [修复蒸馏] 非器官标签二级反查命中: PatchManager
                                 → <PROJECT_ROOT>\nucleus\reasoning\PatchManager.py
logs/pulse.log:78208  11:17:22 [修复蒸馏] 方法体为空 → 改用文件/ERROR消息作为对比输入:
                                 type=ERROR, organ=PatchManager, method=, file=PatchManager, 素材=158字
                                                          ↑ _loc_label = _file or _resolved_file or organ_clue
                                                            ⇒ 显示裸标签 "PatchManager"，证明两变量皆空
```

**⇒ 第87批的修复（file 反查）与素材提取之间断了一节：反查结果进了 `issue["file"]`，素材提取却只读 `_file`/`_resolved_file`。**

### 层2 · prompt —— **自洽，任务书猜测②不成立**

`_build_differentiated_prompt`（L760+）把 `{code_snippet[:2000]}` 嵌进「相关代码」块，并明确要求「请直接输出修复后的完整代码」。

关键点：**验证用的也是"完整代码 vs 完整代码"的相似度**，不是 diff 相似度 ⇒ **prompt 要求与验证口径同构，不存在格式不匹配**。任务书担心的"要求完整代码却用 diff 对比"这一情形在代码里不存在。

（副作用仍在：素材若本身不是代码，prompt 就变成了"拿一段 ERROR 日志，请输出修复后的完整代码"——**LLM 忠实地输出了一段代码，然后被判"与原文相似度过低"**。这才是 0.03 的完整叙事。）

### 层3 · 补丁格式 —— **自洽；真正的问题是"比对对象选错"**

`PatchManager._check_llm_patch_completeness`（L1130-1179）三关：

| 关 | 判据 | 0.03 现场 |
|---|---|---|
| 关1 | 非空 + 与原文有实质差异 | 过 |
| 关2 | `ast.parse("def _wrap():\n" + indent(modified))` 语法合法 | 过（LLM 输出的确实是合法代码） |
| 关3 | `difflib.SequenceMatcher(None, orig_norm, mod_norm).ratio() < 0.5` → 失败 | **在此判 0.03** |

格式本身没问题（整段替换代码），**错的是喂给关3 的 `orig_norm`** —— 它本该是"目标文件里的真实代码"，实际是"158 字 ERROR 日志文本"。

### 双重结构性失败（本批最重要的发现）

素材取错**不止**会造成 0.03 这一条噪声，它在 `PatchManager._verify_in_copy` 里还有第二道必死关口：

```python
# PatchManager.py L817-820
if patch["original_code"] not in full_content:
    → stage = "code_not_found"
```

ERROR 日志文本**不可能**出现在目标文件里 ⇒ **素材取错 100% 导致补丁不可应用**。也就是说：即使把关3 的阈值从 0.5 降到 0（把噪声抹掉），这类补丁**依然过不了**。这是"修素材"而非"调阈值"的决定性理由。

## 九、残余风险与待星轨裁决

### 9.1 ★ 阈值边际风险（**强烈建议关注**）

补丁库实证显示：**即便素材是正确代码**，LLM 的"整段重写"落在 **ratio = 0.5193 / 0.5774 / 0.6203** —— 距 0.5 阈值最近的只有 **0.019**。

- 阈值 0.5 对"LLM 输出整段替换代码"这一形态**过紧**；
- 一旦 LLM 改动稍大（如为修一个 bug 顺带重构），ratio 掉到 0.5 以下，就会被判成**`与原文相似度过低，疑似严重残缺/截断`** —— 又是一次**误诊**。
- 建议（需裁决）：把关3 的比较基准从"文件头 2000 字片段"改成"**LLM 收到的同一段 `code_snippet`**"（当前已是同一段，故更有效的是**降低阈值**，例如 0.3），或对 `source=="llm"` 走"语法 + 可定位 + 回归测试"三元校验替代相似度。

### 9.2 ★ `method=空` 的 167 条日志类问题**缺少修复单元**（结构性）

291 条「方法体为空」样本中 **167 条（57.4%）`method` 为空**（全 `ERROR` 型、file 多为裸器官标签）。这类问题：

- 无方法名 ⇒ 无 `original_code` 的天然锚点 ⇒ **LLM 补丁结构性不可能过闸**；
- 本批已把它们从"伪装成 LLM 生成残缺的假失败"改成**显式留痕**（`[LLM修复] 跳过补丁构造：对比素材非代码…请按「无方法名的日志类问题缺少修复单元」处理`），但**能力缺口依旧存在**。

**待裁决**：是否另立批次设计「日志 → 方法/代码位点」定位能力（例如按异常栈帧、按日志调用点反查？）。在这项能力落地前，**修复率仍会是 0.0%** —— 但性质已变：不再是"素材取错的假失败"，而是"这类问题确实没有修复单元"。
