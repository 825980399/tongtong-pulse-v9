## 三、任务明细

### T1 P2-81 浏览器保活线程安全修复 ✅

**根因（比任务书描述深一层，实测日志确认）**：

任务书假设"保活线程直接操作浏览器"。实测发现真因是**浏览器诞生在已退出的线程上**：

```
PulseController.start() → threading.Thread(target=self._ensure_headless_browser)  # L237 裸线程
                            ↓ 创建 Playwright 浏览器后立即退出
保活线程/搜索线程 → 操作 self._headless_page → error: cannot switch to a
                     different thread (which happens to have exited)
```

关键证据：错误信息含 **"which happens to have exited"** —— 指向的不是"另一个活着的线程"，而是"已退出线程"。

**两层修复（灰度可回退）**：

1. **方案A保活信号**（裁决方案A）：保活线程只置 `self._keepalive_due`（`threading.Lock` 保护），
   实际 touch 经 `_get_playwright_executor().submit(self._check_keepalive)` 由池线程消费。
   新增 `_keepalive_signal_mode()` / `_signal_keepalive()` / `_check_keepalive()`。
2. **属主线程模式**（本批补强，根治）：预热改为
   `_get_playwright_executor().submit(self._ensure_headless_browser)`，
   让浏览器诞生在 `max_workers=1` 的常驻池线程（创建/使用/关闭同线程）。
   新增 `_owner_thread_mode()` + `_close_headless_browser` 池内执行守卫。

**灰度开关**：`headless_keepalive_signal_mode`（默认 True）、`headless_owner_thread_mode`（默认 True）。
关闭 → 分别回退第10批旧行为 / 预热裸线程，零副作用。

**实测验证**（真实 threading，7 例门控单测）：
- 创建线程名 = `Playwright_0`（池线程）✅
- 保活 touch 线程名 = `Playwright_0` ✅
- due 消费后复位 ✅ / 已置位时不重复提交 ✅ / 无浏览器时不提交 ✅

**⚠ 运行态验收说明**：当前生产进程（PID 19844，22:53 启动）早于本批改动（23:05），
故日志中仍可见保活错误。**需重启框架后观察 10 分钟**确认该错误消失（任务书验收标准）。
