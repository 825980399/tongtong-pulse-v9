## 一、现象与根因

- **现象**：自主迭代子进程（`multiprocessing.Process` 经 `evolution_worker` spawn）被 Ctrl+C / 控制台中断终止时，`SafeEvolutionExecutor._run_subprocess_once` 的 `proc.exitcode != 0` 分支统一返回 `status="crashed"` 并调用 `_record_crash`，把「用户主动中断」虚报为「代码崩溃」——污染崩溃统计、并可能触发重试风暴与同进程降级。
- **根因**：Windows 下被 Ctrl+C 终止的子进程 `exitcode` = NTSTATUS `0xC000013A`（STATUS_CONTROL_C_EXIT，正数极大值）；`0xC0000409`（STATUS_FATAL_APP_EXIT / fast-fail）同理。原逻辑对所有非零 `exitcode` 一律判 `crashed`，缺少「主动中断」语义分类。
- **目标（路灯触发指令第 7 刀）**：NTSTATUS `0xC000013A` / `0xC0000409` → `interrupted` 非 `crashed`。

## 二、修复内容

- **`nucleus/reasoning/SafeEvolutionExecutor.py`**：
  - 新增模块级常量 `_NTSTATUS_INTERRUPTED = frozenset({0xC000013A, 0xC0000409})` 与静态方法 `_classify_subprocess_exit(exitcode)`：负数（POSIX 信号终止）→ `interrupted`；命中 NTSTATUS 控制码 → `interrupted`；其余 → `crashed`。
  - `_run_subprocess_once` 的 `proc.exitcode != 0` 分支前置「主动中断」短路：命中 `_classify_subprocess_exit == "interrupted"` 时返回 `status="interrupted"`（附 `exitcode` 十六进制 + 中断原因标签），**不调 `_record_crash`、不触发重试与降级**；仅打 INFO 级「子进程被主动中断(非崩溃)」日志。其余非零退出码仍走原 crashed 诊断链路（保留 stderr 尾部 + 崩溃载荷）。
  - 结果契约 docstring 增列 `interrupted` 状态值。
  - 消费侧 `_run_subprocess_with_retry`（:5812）的 `status not in ("crashed","error")` 已天然将 `interrupted` 视为非失败直接返回，**无需改动**。
