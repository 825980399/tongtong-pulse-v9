## 二、T1（P0-272）★日志留存根因：**外部原地截断**

### 2.1 ★先纠正任务书前提：「仅留存 2 小时」是**观测误判**

任务书写「pulse.log 时间范围仅 11:30~13:18（约 2 小时）」。实测（17:50）：

```
行数=22190  大小=2.84 MB  跨度=6.11 小时（11:30:21 ~ 17:39:57）
首行原文: 2026-09-13 11:30:21 [框架] INFO: 初始化 曈曈 v9.5 PulseNet...
```

**同一个文件、同一个首行时间**，只是当时（13:18）恰好跑了 2 小时。
⇒ 不存在「2 小时清理机制」；真实现象是「**文件内容从最近一次启动开始**」。

### 2.2 三重排除：不是框架、不是脚本、不是配置

| 排查项 | 方法 | 结果 |
|---|---|---|
| 框架代码 | **AST 全库扫描** `open(<含 log 表达式>, 写模式)` + `Path.write_text` + `truncate` | 仅 3 处，全部写业务 JSON（`data/stream/hormone_emotion_log.json` 等），**无一处针对 pulse.log** |
| 项目脚本 | 全库 `.bat/.cmd/.ps1/.sh/.vbs` | 仅 1 个 `_install_cython.bat`，与日志无关 |
| 计划任务 | 平台定时任务 | 2026-09-12 已按要求全部取消 |
| logger 配置 | **轮转模拟实验**（maxBytes=2000/backupCount=5，写 40 轮） | **配置完全正确**：`.1~.5` 正常生成、第 6 次轮转淘汰最旧、当前文件始终存在 |

### 2.3 ★决定性证据（两条）

**① `ctime` 未变 ⇒ 是「截断」而非「删除重建」**

```
pulse.log  ctime = 09-03 21:12:47（未变）   mtime = 09-13 17:39:57
```

对照实验（`tmp/scan_m42_t1_decide.py`）：

| 操作 | ctime 变化 |
|---|---|
| `truncate`（`open(f,'w')` 原地重写） | **不变** ✓ |
| `delete` + 重建 | **变化** ✓ |

**② 内容 100% 属于当日 ⇒ 11:30 时文件已空**

22190 条时间戳全部为 `2026-09-13`，**无任何旧内容残留**（时间倒退点仅 1 处、4 秒，属并发写入乱序）。
若为进程追加（`RotatingFileHandler` 默认 `mode='a'`），重启后旧内容必然保留。

**结论**：`logs/pulse.log` 在框架启动前被**外部原地清空**（典型形态：`> logs/pulse.log` 重定向、
PowerShell `Clear-Content`、编辑器另存）。`ctime` 不变 + 内容全为单日 = 铁证。

### 2.4 修复（外部操作不可拦截 → 改为「只清超期 + 被截断必留痕」）

1. **超期清理**（config：`ENABLE_LOG_RETENTION_CLEANUP=True` / `LOG_RETENTION_DAYS=7` /
   `LOG_RETENTION_PROTECT=["pulse_crash.log"]`）：只删 **mtime 超期**的 `*.log` / `*.log.N`；
   正在写入的文件 mtime 恒为当下 → **永不会被删**；保护名单内文件永不自动删除。
2. **★完整性自检**（`ENABLE_LOG_INTEGRITY_CHECK=True`）：启动时比对
   `logs/.log_state.json`（上次 size/ino）；若 **size 变小 → truncated**、**ino 变化 → replaced**、
   **文件不存在 → missing** → 追加一条 JSON 到 **独立文件** `logs/log_integrity_events.log`
   （独立是为了不随主日志一起被清空）+ 打 WARNING。
   ⇒ **下次再发生，可精确定位到「时刻 + 幅度」**，把推测变成铁证。
3. 测试环境保护：pytest 下自动跳过写生产 `logs/`。

**验证**：`tmp/check_m42_t1.py` 8 组断言全过（超期清理 / 保护名单 / 开关关闭零行为 /
截断识别 + 留痕 / 缺失识别 / 轮转上限），门控测试 **20 例**。

## 三、T2（P0-250）补丁质量评估器（★内在模型 L4 第一个落地）

### 3.1 实测输出

```
[补丁评估] 总补丁=67 优质=0 中等=0 劣质=0 假通过=2（不可验证=62 未应用=3 平均分=76.9）
报告：data/evolution/patch_quality_report.json
```

### 3.2 ★核心发现：`effectiveness` 字段本身不可信

实测 `runtime_verify_result` 值分布：

| 字段 | 分布 |
|---|---|
| `baseline` | **0 × 63**，4 × 1 |
| `after_fix` | 0 × 62，4 × 2 |
| `effectiveness` | **1.0 × 62**，0.0 × 1，0.5 × 1 |
| `verified` | True × 63，False × 1 |

⇒ 62 条的 `effectiveness=1.0` 是 **0/0 除法的产物**（`detail` 原文即「修复前错误=0, 修复后错误=0, 效果=100%」）。
**「没有错误」被算成「100% 有效」** —— 这是第41批 T1 判据缺陷的下游后果。

**本评估器的修正**：用原始 baseline/after 重算，**`baseline=0` 时返回 `None`（不可判定）**，
绝不返回 1.0；`baseline=0` 且 `after>0` 返回 `-1.0`（凭空引入错误）。

### 3.3 ★假通过 2 条（比任务书预期多 1 条）

| 补丁 | claimed | **real** | baseline/post | 判定 |
|---|---|---|---|---|
| `PulseLiver._save_fuse_cooldown` | 0.5 | **-1.0** | 0 / **4** | ★**修复后引入 4 个错误**（分数 33） |
| `PulseLiver._build_knowledge_association_graph` | 0.0 | **0.0** | 4 / 4 | 任务书点名的那条（分数 53） |

### 3.4 评分与标签

- 评分 = 效果(40) + 验证(25) + 回归(20) + 稳定性(15)
- 标签：`good` / `mediocre` / `bad` / `fake_pass` / **`unverifiable`（新增）** / `not_applied`
- ★ 新增 `unverifiable` 的理由：**“无可比基线”≠“优质”**。若只给 4 个标签，62 条无基线补丁
  要么被误判为 `fake_pass`（冤枉），要么因分数高被判 `good`（失真）。**如实标记**比凑分布更有价值。

### 3.5 L1 仅观测（三重保证）

① 只读 `patch_history.json`，只写评估报告；② 不拒绝/不改任何补丁状态；③ 开关关闭 → `evaluate_and_report()` 直接返回 `None`。

## 四、T3（P1-265）经验检索器（★内在模型 L2 第一个落地）

### 4.1 污染分析（实测）

```
data/experience/experience_pool.json
  total=1501   polluted=1193（79.5%）   clean=308
  by_reason = {"内容重复(历史灌水)": 1193}      ← ★污染原因 100% 单一
  is_summarized = {True: 1001, False: 500}
  text_coverage = 1.0（summary/motivation 全非空）
报告：data/experience/pollution_report.json
```

**现有检索器的结构性问题**：`ExperiencePool.query_experiences()` 只做**元数据过滤 + 时间倒序**，
不排除污染 → 取前 N 条时极易被同质模板文本（"我曾因维持系统平衡而行动…"）占满。

### 4.2 新检索器的三步增强 + 实测对比

1. **语义检索**：复用 `VectorEncoder`（bge-small-zh-v1.5 / 512 维；`encode()` 批量 + `cosine_matrix()` + `topk()`）
2. **污染过滤**：默认排除 `polluted=True`（可配置）
3. **质量排序**：相似度 × `quality_weight` 加权 + 激活度加成
4. **性能**：候选集有界（`EXPERIENCE_RETRIEVER_SCAN_LIMIT=200`）+ **向量按 id 缓存**（重复检索零编码）

**对比实测**（构造样本，mock 编码器）：

```
新检索 3 条 / 现有 3 条 / 重叠 2 条
现有结果污染: 1 条（33.3%）   新结果污染: 0 条
日志：[经验检索] 新检索器返回3条，现有返回3条，重叠2条（现有污染1条/33.3%）
```

### 4.3 L1 仅观测

`observe()` / `observe_daily()` **只记录对比，不返回检索结果**（调用方拿不到内容 → 结构性保证不替换现有逻辑）。
接线：`DailyScheduler`（每日 1 次，编码器未就绪时自动跳过，**不进入任何热路径**）+ `tools/run_experience_analysis.py`。

## 五、T4（P2-276）PulseLiver 假通过补丁诊断 ★**结论更正**

### 5.1 任务书假设 vs 实测

任务书：「`_build_knowledge_association_graph` 补丁 eff=0.00（baseline=4/after=4），**是真实无效修复**」

**实测结论：不是无效修复，而是「验证粒度失配」。** 三条证据：

**① 修复已 100% 落地（逐字比对）**

补丁 `diff_summary`：`第273行: 'except Exception:' → 'except Exception as e:'；第274行: 'pass' → 'self._log(LogLevel.ERROR, ...)'`

当前源码（`organs/body/PulseLiver.py`）：

```
2167:  except Exception as e:
2168:      self._log(LogLevel.ERROR, f'异常: {e}')
```

⇒ 与补丁 `modified_code` **逐字一致**。`_save_fuse_cooldown` 同样已落地（2535-2536）。

**② `baseline=4 / post=4` 是「文件级」口径**

`baseline_errors` 由第41批 `tools/backfill_baseline_errors.py` 用 `_count_errors_for_location`
回填，而该判据（第41批 T1 修正后）**只能定位到文件名**（框架日志从不输出方法名）。
⇒ 它的含义是「`PulseLiver.py` **这个文件**在窗口内的错误行数」，**与该方法无关**。

**③ 补丁历史里该 id 有两条记录**

```
patch_1788590332_d156  applied=False  apply_error=信任分数不足(30<60)   baseline=0
patch_1788590332_d156  applied=True   applied_at=1788766577（09-07）   baseline=4  post=4
```

⇒ 先被信任分拦下，后来（09-07 批量应用窗口）被应用。**"未应用"与"已应用"两条记录同时存在**，
统计与评估都会被它误导。

### 5.2 顺手修复：全文件唯一静默点

全文件扫描确认 `except ...: → pass` **仅 1 处**（`PulseLiver._compress_group`，原第 1374 行，
`self.node_pool.remove()` 的失败被静默吞掉）→ 改为记 DEBUG（与同方法内既有 `_log_ignored_exception` 口径一致）。
**修复后全文件静默点 = 0**。
