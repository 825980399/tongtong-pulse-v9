## 疑问1：`tmp/` 目录是否纳入 ruff exclude？

**现象**

第4批为执行任务新增 6 个一次性脚本（`tmp/scan_b21_struct.py`、`tmp/patch_batch21_headers.py` 等），
使全库默认扫描总数从 **495 → 525（+30）**：

| 规则 | 增量 | 来源 |
|------|------|------|
| ISC004 隐式字符串拼接 | +28 | `tmp/patch_batch21_headers.py`（头部字典里的相邻字符串字面量） |
| SIM115 未用 with 打开文件 | +1 | `tmp/check_header_b21.py` |
| UP031 printf 格式化 | +1 | `tmp/scan_b21_struct.py` |

**全部落在 `tmp/`，生产代码零新增。**

**相关位置**
- `ruff.toml:25` —— `exclude = ["data/code_backups"]`（当前只排除了备份快照目录）
- `ruff.toml:32-33` —— `[lint.per-file-ignores]` 注释写着「工具/基准脚本属一次性诊断脚本，允许更宽松」

**矛盾点**
`ruff.toml` 的注释已经表达了「一次性脚本应更宽松」的意图，但实际**没有排除 `tmp/`**；
而 `tmp/` 里既有真的一次性补丁脚本，**也有必须保持质量的正式回归测试**（`test_batch19_body.py`、
`test_batch20_motor_core.py`、`test_batch21_endo_gen_id.py`、`tools/` 的回归脚本）。

**可选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A | `exclude` 增加 `"tmp"` | 统计口径立刻干净 | 回归测试脚本也失去静态检查，测试自身的质量债会累积 |
| B | 只排除非 test 的一次性脚本：`exclude = ["data/code_backups", "tmp/patch_*", "tmp/scan_*", "tmp/check_*"]` | 保留回归测试的检查，排除一次性脚本 | 需要持续维护命名约定 |
| C | 维持现状，统计时人工标注 tmp 贡献 | 零改动 | 每批都会虚增，长期趋势失真 |

**建议**：方案 B（路灯倾向），并把「一次性补丁脚本统一用 `patch_` / `scan_` / `check_` 前缀」写成约定。

**需星轨确认**：选哪个方案？（若选 B，可在第 5 批顺带执行）

## 疑问2：`BondingEvent.UPDATED` / `NurtureEvent.STAGE_CHANGED` 常量是否从 `nucleus/const` 摘除？

代码注释写明 `★P3-5修复：删除孤儿脉冲 bonding.updated（纯状态广播，全库无订阅方）`。

但两个 Event 常量**仍然存在于 `nucleus/const`**，且两文件的 `__main__` 自测里还在校验它们：

- `organs/genetic/PulseBonding.py:105-108` —— 自测中 `updated_pulses = [p for p in mock.published if p.get("event_type") == BondingEvent.UPDATED]`

本次已在新头部里明确标注「已移除，只回状态」，但**常量和自测代码仍是误导源**。

**需星轨确认**
1. 是否删除这两个 Event 常量 + 清理对应自测断言？（会改动 `nucleus/const`，属核心文件，路灯不敢擅动）
2. 还是保留常量仅清理自测？（常量留作未来扩展位）

**关联**：全库可能还有其它已删脉冲的孤儿常量，建议顺带做一次「Event 常量订阅方普查」。

`organs/` 下已累积备份文件：

| 后缀 | 数量 | 批次 |

| `.bak_batch18_head` | 15 | 第1批 |
| `.bak_h18b` | 9 | 第1批补做 |
| `.bak_batch20_head` | 19 | 第3批 |
| `.bak_batch21_head` | 15 | 第4批 |
| `.bak_b21ws` | 15 | 第4批中间快照 |
| **合计** | **73+** | |

项目根目录另有 `config.py.bak_batch14/16/17`、`ruff.toml.bak_batch19/20/21` 等。

**风险**
1. 备份与源文件同目录 → 未来任何「全目录扫描/批量操作」脚本都会扫到它们（ruff 已用 `exclude` 规避了 `data/code_backups`，但 `organs/` 下的 `.bak` 目前靠扩展名侥幸躲过）。
2. 无法区分「有效的回滚基线」和「已被后续批次覆盖的过期基线」。

**可选方案**

| 方案 | 做法 | 评估 |
|------|------|------|
| A | 建立 `data/code_backups/<日期>/` 归档目录，把 N 批之前的 `.bak` 移入 | 干净、可追溯，路灯倾向 |
| B | 保持现状，只在交付报告里列出清单 | 零风险但持续膨胀 |
| C | 回滚窗口（如 7 天）后自动删除 | 有丢失风险，需小林确认 |
