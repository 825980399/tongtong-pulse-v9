**根因（一条被静默吞掉 995 次的 TypeError）**

```python

```

`PulseNodePool.query()` 的真实签名是 `query(evol_level, importance, source_organ, space_path_prefix, limit)`
—— **没有 `space_path` 参数，正确名是 `space_path_prefix`**。因此每次消化都抛

```
TypeError: query() got an unexpected keyword argument 'space_path'
```

被紧随其后的 `except Exception:` 裸捕获，只打一行内容固定的 DEBUG
(`"[主线10批] 静默异常已记录: organs/body/PulseStomach.py:833"`) 再 `pass`。
**处置结论：v26.0 引入的「知识免疫」自上线以来从未真正生效过。**

**修复内容**
| 项 | 修复前 | 修复后 |
|---|---|---|
| query 参数名 | `space_path="/自我"`（恒抛 TypeError） | `space_path_prefix="/自我"` |
| 返回值防御 | 无 | `isinstance(list)` 校验 + 兜底转换 |
| 结果防御 | `_consistency.get(...)`（可能 AttributeError） | `isinstance(_consistency, dict)` 守卫 |
| 异常日志 | 固定字符串 + 过期硬编码行号 | 真实 `异常类型: 消息` + **运行时真实行号**（`sys.exc_info()[2].tb_lineno`） |

**⚠️ 行为变更提示**：修复后免疫检查将**首次真正执行**——当新知识与 `/自我` 节点矛盾时，

### 1.2 NoneType 异常残留排查 —— ✅ 完成（结论与任务书预设不同）

**任务书预设**：全局搜索 `[.*] .*NoneType` 模式。
**实测结论**：`logs/pulse.log` 中 **`NoneType` 出现 0 次**；
但按「同类缺陷」口径扩大排查后，发现**一类真实且高频的残留 AttributeError**：

```
[肝] DEBUG: 代码调用关联构建异常: 'PulseNode' object has no attribute 'endswith'
```

12 小时窗口出现 **16 次**（约每 23 分钟一次，与肝脏知识关联构建周期吻合）。

**根因（`organs/body/PulseLiver.py:2097`，dict 解包顺序写反）**

```python
for _node, _key in _method_node_map.items():        # items() 返回 (键, 值)
    if _key.endswith(f".{_callee}"):                # 键是 str，值才是 PulseNode
        _callee_node = _node                        # 二者被绑反
        break
```

`_method_node_map` 的结构是 `{"器官.方法": PulseNode}`（键为字符串）。
原代码把**键绑给 `_node`、值绑给 `_key`**，于是 `_key.endswith(...)` 在
**PulseNode 对象**上调用 → AttributeError，被外层 `except` 吞掉 =>
**整个「代码调用关联（call_dependency 边）」构建被静默放弃**。

**修复**：解包顺序改为 `for _key, _node in ...`，并加 `isinstance(_key, str)` 防御；
灰度开关 `ENABLE_LIVER_CALL_EDGE_GUARD`（默认 True；False=不做模糊兜底匹配，
等价于修复前的可观测效果——该兜底此前 100% 抛异常、从未生效）。

**其余排查结论（不修，超出范围）**
- `'dict' object has no attribute 'append'` 1 次（`PulseCortex` 通用数据兜底），单次、无复现、无业务影响；
- `logs/pulse_crash.log`（9-08 旧档）中的 `'InfoField' object has no attribute '_log'` 已由后续批次修复；
- 器官启动 / 消息处理 / 知识检索三条路径未再发现 NoneType 类残留。

## 三、任务 2：nucleus E402 专项治理 —— ✅ 77 → 0

**实测基线**：`ruff check --select E402 nucleus/` = **77 条 / 19 个文件**（任务书数字准确）。
**全库**：283 条（nucleus 77 + 其他目录 206，其他目录不在本批范围）。

### 安全前置分析
先写 `tmp/scan_m14_e402_plan.py` 对 19 个文件逐一分析：
E402 行号、触发点语句、涉及的 import 模块，并**逐个做反向引用检测（循环导入风险）**
——**结论：19 个文件全部无反向引用，上移 import 不产生循环导入。**

### 三类模式与处置

| 模式 | 说明 | 文件数 | 处理方式 |
|---|---|---|---|
| **P1** | import 被放在 `_logger/_module_logger = ...` 赋值之后 | 9 | import 上移到赋值之前 |
| **P2** | 模块级 `import threading` 被放在函数/类定义之后 | 5 | 上移到顶部 import 块 |
| **P3** | `sys.path.insert(...)` 之后插了**游离字符串字面量**（第二份 docstring），其后才是 import | 4 | import 上移到紧邻 `sys.path.insert` 之后；`import os/sys` 放到 `sys.path.insert` 之前 |
| **P4** | `_module_logger` 赋值位于 `sys.path.insert` **之前** | 1 | logger 赋值下移到全部 import 之后 |

**关键技术发现（可复用）**：ruff 的 E402 判定中，`sys.path.insert(...)` 语句
**不会**关闭「import 区」，但**任何普通赋值语句会**关闭它——关闭之后，
连紧随 `sys.path.insert` 的 import 也会被判 E402。
（用 `tmp/_e402exp/` 三个最小样例实测确认；该实验目录已清理。）
