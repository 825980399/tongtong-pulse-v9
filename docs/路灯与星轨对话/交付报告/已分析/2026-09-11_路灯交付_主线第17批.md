### ★ 关键事实澄清（影响设计，务必知悉）

核实中发现 **`ENABLE_EVENT_BUS`（默认 False）并不阻断旁路事件投递**：

- `get_event_bus()` 在 `ENABLE_EVENT_BUS=False` 时**仍会创建单例**（只是 `async_enabled=False`）；
- `EventBus.publish()` 是**同步投递**，**不受 `async_enabled` 影响** —— 它只控制「是否启用异步队列/后台线程」。

**结论**：本批旁路事件在总开关关闭时**依然能送达 EventTap**（同步路径）。
这不是缺陷，而是既有设计（第14批：EventBus 的异步能力是可选增强）。已在 `config.py` 注释中显式写明，
避免后续误判「EventBus 关了事件就没了」。

## 三、5 个任务实现摘要

### T1 `nucleus/events/EventTap.py`（新建）

按任务书逐条落实：

| 要求 | 实现 |
|---|---|
| 订阅全部事件 | `subscribe("**", self._on_event, priority=EventPriority.LOW)` ✅ |
| 按事件名/来源/优先级计数 | `_by_name` / `_by_source` / `_by_priority` ✅ |
| 总数 + 环形缓存 | `_total` + `deque(maxlen=EVENT_TAP_HISTORY_LIMIT)` ✅ |
| 时间间隔统计 | min / max / avg / samples（基于 `Event.timestamp`）✅ |
| `export_stats(path)` | JSON（stats + recent + exported_at），按需触发 ✅ |
| 性能保护 | `_on_event` 只加锁计数、**零 IO**；payload 只存类型+长度摘要 ✅ |
| 无界增长保护 | 事件名种类 > `EVENT_TAP_MAX_EVENT_TYPES` → 归入 `__other__` + **仅一次** WARNING ✅ |
| 线程安全 | `threading.Lock` 全程加锁 ✅ |
| 单例 | `get_event_tap()` / `reset_event_tap()` ✅ |
| 开关 | `ENABLE_EVENT_BUS_TAP` 关闭 → `_on_event` 直接 return ✅ |

**两处设计增强（超出任务书，但为规避真实风险）**：

1. **`auto_start=True`**：构造即订阅。初版需手动 `start()`，实测极易忘记 → 监听器静默不工作。
2. **`tap_publish()` 便捷入口**：把「总开关 + 器官开关 + try/except」收敛为**一行调用**，
   使器官侧插入点保持最小侵入（否则每个发布点都要展开 5 行 try/except）。
   任务书示例是内联 if 块，这是**等价实现且更省行**，功能与开关语义完全一致。
