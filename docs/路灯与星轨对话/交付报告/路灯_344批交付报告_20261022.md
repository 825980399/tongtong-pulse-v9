## 二、刀1 · O3 执行层修复（P0）

### 病根复核（实测，铁律109）

改前复现：`d1_repro.json` —— 沙箱执行 `CompanionBridge.handshake` 补丁，`returncode=1`，
控制台 `NameError: name 'Any' is not defined`。

**根因**：`PulseCodeSandbox.on_pulse` 子进程包装器只往 `_g` 放 26 个白名单 builtins 与
`__name__`；而 Python 在 `def f(x: dict[str, Any])` 的**定义时**就求值注解 ⇒ 缺 `Any`
即把**合法代码**判成失败。这是**环境缺陷误判成代码缺陷**。

### 施工三件

**① 沙箱注解符号预注入**（`nucleus/security/sandbox_limits.py`）

```python
SANDBOX_ANNOTATION_SYMBOLS: tuple[str, ...] = (
    "Any", "AnyStr", "Callable", "ClassVar", "Dict", "Final", "FrozenSet",
    "Generic", "Iterable", "Iterator", "List", "Literal", "Mapping",
    "NamedTuple", "NoReturn", "Optional", "Protocol", "Sequence", "Set",
    "Tuple", "Type", "TypedDict", "Union",
)
```
`build_child_wrapper` 在 `globals_setup` 后注入这批名字。
**注入有界**：只注入 `typing` 的**类型名**，`typing` 模块本身不进 `_g`，`__import__`
不放开 ⇒ **逃逸面不变**（s2 实证：未注入名仍 `NameError`，`__import__` 仍不可用）。

**② O3 删除条目改走 AST 级校验**（`nucleus/evolution/patch_execution_dispatch.py`）

`o3_dead_code=true` 的补丁**不再进代码执行**，改走 `verify_ast_delete()` 静态三问：

1. 目标 def 是否存在（**行号只作 tiebreak，不作硬条件**——入池记 122、实测已在 123，
   把行号当硬条件会造出"目标明明在却报不存在"）；
2. 删除后 `ast.parse` 是否通过；
3. 孤儿引用分级告警（`call_attr` 真调用 / `attr_read` 取属性未调用 / `text_only` 仅文本）。

结论落 `runtime_verified` / `runtime_verify_result`，`detail` 标 `ast_delete`。
错误码：`ast_delete:missing_target` / `file_not_found` / `source_syntax_error` /
`target_def_not_found` / `span_unusable` / `post_delete_syntax_error`。

**③ 失败衔接**：改前 `runtime_verify_fail_count=1`（cap=2）；修复后仍保留 1 次自动重派机会。

## 六、刀5 · AST 可释放面释放点（P1）

### T0 实测把病根问清了（`d5_steady_state.json`）

**干净测法**下 6 轮 `parse → del → gc.collect()`，AST 活体 residual **恒 0、稳态不涨**
⇒ **AST 本身不泄漏**。真正的问题是「**谁把树多吊了一会儿**」：

- 解析函数里 `_tree` 在 `visit()` 之后**仍是局部变量**，往下还有几十行一直吊着整棵树；
- 异常路径 `traceback → frame → 局部变量 → 整棵树`，只要异常对象被日志/账本留住，
  整棵树就长期活着。

> **测法教训（本刀被自己污染两次）**：`gc.get_objects()` 返回的 **list 本身就是强引用**。
> 任何对 AST 节点建 list/dict/采样副本的"诊断"都会把对象吊住，使 `del` 失效，
> 读数退化成「恒等于 held」（`d5_residual_diag.py` v1/v2 的 `released: 0` 即此坑）。
> 本批所有计数一律走**内联生成器**。

### 施工

**新件** `nucleus/mnemosyne/ast_release.py`（`344.ast.rel.v1`）

- `register_ast_face(tree)` — 登记待释放面（转移所有权，隔离/兜底用）
- `note_ast_face_done(nodes)` — **生产主路径**：扫描侧 `del` 后只记账，**零持有**
- `release_ast_faces(tier, heap_before, heap_probe)` — 清池 + `gc.collect(2)` +
  **前后实测**活体计数，留痕 `[344释放] ast_cleanup nodes=… accounting=… faces=… heap=…→…`
- `ast_live_count()` — 内联生成器计数，**不建容器**
- **安全阀**：`MAX_PENDING_FACES=64` / `MAX_PENDING_NODES=400000` 双上限，
  超限按最旧驱逐并留痕 `[344释放] ast_evict`（registry 若无限长持，**它自己就成了泄漏源**）

**生产接线两处**

1. `CallGraphAnalyzer._collect_file`：`visit()` 后立即 `del _tree` + 记账
   （正常路径 + 2 条异常路径，共 3 点）。这是**真实峰值削顶**。
2. `PulseMetricsCollector._m343_release_heartbeat`：`tier ∈ {G2_SOFT_RELEASE, G3_COLD_DEMOTE}`
   时真实触发 `release_ast_faces(...)`；`candidates_offered` **不再是硬编码 0**，
   而是池内真实面数，另给 `candidates_source` 与 `ast_release.measured_nodes` 佐证
   （铁律166：「没生效」与「生效但产出 0」不同措辞）。

## 十三、本批学到的一条

**"AST 可释放"这句话本身有歧义。** 343 批读到的 `Name 76101↔83430 波动` 看起来像泄漏，
344 批用干净测法（6 轮稳态）证明 `del` 后 residual 恒 0 —— **AST 不泄漏**，
泄漏风险全在"谁多吊了一会儿"。差一点就照任务书写了个"释放泄漏的树"的空转判据（铁律163）。

同时本批被**自己的诊断脚本**骗了两次：`gc.get_objects()` 的返回 list 就是一组强引用，
拿它做"采样"会把对象吊住，让 `released` 恒等于 0。**测量工具自身也会污染被测对象** ——
这条已写进 `ast_release.py` 的模块 docstring，防下次再踩。
