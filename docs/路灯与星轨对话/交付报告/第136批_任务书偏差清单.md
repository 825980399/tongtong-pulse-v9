## 偏差一：T-136d 不可达代码「33 条」与实测「1 条」严重不符（P3 前提失真）

**任务书声称**：PyCharm 扫出 33 个写在 return 后面的死代码。

**本批实测**：按任务书显式约束「AST 扫描 return/raise 后面同块的死语句」严格实现检测器，对真实代码库首扫仅检出 **1** 条：
- `organs/brain/PulseInnerWorld.py:8709` —— `Return` 之后的不可达语句。
- 即便扩展到 `break` / `continue` 终止后同块死语句，仍为 **1** 条。

**根因判定**：任务书给定的检测器范围是窄口径（仅 `return`/`raise` 之后、同代码块内的死语句）。PyCharm 报告的「33」几乎必然采用更宽口径（例如 `if False:` 常量条件分支、永不可达的 defensive 分支、未启用的特性开关块等），远超任务书显式范围。

**处置决定**：
1. 检测器忠实于任务书范围实现，不强行扩写宽口径以避免 D1 检测器噪音爆炸（误报会污染后续告警信噪比）。
2. 将基线固化为 1 条（`data/unreachable_code_baseline.json`），后续仅「新增」不可达代码才告警。
3. 此 33 vs 1 差异判定为**工具口径差异，非 bug**；若星轨后续要求对齐 PyCharm 宽口径，须单独派发任务并明确扩展规则。
