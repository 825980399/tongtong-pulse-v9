`nucleus/evolution/`（aging 在 `nucleus/reasoning/`）。
**下一步只需一次裁决**：是「全局开 `ENABLE_PENDING_QUEUE_AGING`」（影响整个 pending 队列），

我倾向后者，但那要新增开关 + 状态流转，**属于会动状态机的改动**，不该塞进 P3 杂项批。

### 刀10 · SSRF 三类在**返回值里已经分开**，缺的是计数口径

```
nucleus/ssrf_guard.py:113   return False, "无法解析主机: …"     ← DNS_FAIL
nucleus/ssrf_guard.py:111   return False, "拒绝云元数据/保留地址: …" ← PRIVATE_ADDR
```
三类在**字符串里**可分，但计数侧（票面 DNS_FAIL 27 / PRIVATE_ADDR 2 / 其他 4）
应是调用方按返回值自行聚合。要"分开计数"需在 `ssrf_guard` 里加一个分类枚举 + 计数器，
并把调用方改为读枚举而不是匹配中文串。
**这是接口面改动**（调用方全部要跟着改），也不适合 P3 批。

## 三、我为什么停在这里（说清楚，不粉饰）

这一批把**三种不同性质的活**打包成了同一批：

1. **纯静态改码**（刀10 分类、刀9 埋点）—— 可以做，但都要改接口或拍点；
2. **运行时实验**（刀2 影子、刀3 影子、刀11 24h 观察）—— 交付物是**观测数据**，
   不是代码；它们的"单测通过"证明不了任何事，必须跑窗口；
3. **动状态机/审批路径的改动**（刀4 的 stale 计时、刀6 的三级分诊）—— 改错的代价
   是"不该自动写的补丁被写进源码"或"条目被误标 stale"，**没有回滚开关就不该动**。

把它们塞进一批、每刀一个 commit，最后会得到一个"11 笔提交全绿、但没人敢上"的结果。
我的判断：**这批次应该拆成三轮**——
- **382-A（静态安全批）**：刀9 埋点 + 刀10 分类（都加开关，各带回滚）
- **382-B（观察批）**：刀2 影子 + 刀3 影子 + 刀11 写面（交付物是窗口读数）
- **382-C（裁批）**：刀4 stale 计时 + 刀6 三级分诊（都要先定"谁能自动批"）

刀5 等烛微的表；刀7 单独当文档任务；刀8 先定位再做。
