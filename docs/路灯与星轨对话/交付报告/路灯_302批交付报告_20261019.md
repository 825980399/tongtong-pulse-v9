## 三、刀1 · 高严重度 10 条：**全部是误报**（核心判断）

逐条取证（读源码，非看报告）：

| # | 位置 | 检测器判 | 源码实况 | 判定 |
|---|---|---|---|---|
| H1 | `PulseInnerWorld._safe_eval_arithmetic:13448` | unsafe_eval | 已 `re.fullmatch` 纯算术白名单 + `ast.parse` + **AST 节点白名单** + `eval(compile(...), {"__builtins__": {}}, {})` 受限求值 | 误报（安全实现） |
| H2/H3 | `PulseInterestModel:311/406` | sql_injection | 方法内**根本不写 SQL**；源码已有注释 `no SQL at all ... false positive` | 误报（正则跨行） |
| H4 | `PulseSelfAwareness.__init__:116` | sql_injection | 该处是 `_load_self_awareness_config()` 与群体角色字典，无 SQL | 误报（正则跨行） |
| H5-H8 | `PulseSkin._load_skin_config:62/73` | unsafe_eval | 命中的是**危险命令字符串常量**：`["rm -rf", ..., "eval(", "exec(", "__import__"]` | 误报（字符串常量） |
| H9/H10 | `PulseWhiteCell._is_genuine_attack:752` | unsafe_eval | 同上，`dangerous_commands` 列表里的 `"eval("` / `"exec("` | 误报（字符串常量） |

### 修法：改检测判据（治本），而不是改业务代码

1. `self_inspector._check_unsafe_eval`——注释原本声称「排除安全注释或字符串字面量」，但**实现未做任何排除**。补齐三条判据：
   - 命中位于**字符串字面量内部**（同行前缀引号数为奇数）⇒ 跳过；
   - 同方法体已用 **AST 白名单 + `{"__builtins__": {}}`** 受限求值 ⇒ 跳过；
   - 命中行是注释 ⇒ 跳过。
2. `self_inspector._check_sql_injection`——原正则带 `re.DOTALL`，`.` 可跨行，把「远处的 SQL 关键字」与「后面任意一处 `{}`」拼成一次匹配。改为 `[^\n]` 限定**同一行内**必须同时含 SQL 关键字与 `{}`，并跳过注释行。

**验证**：重跑扫描 ⇒ **high = 0**（medium 同步 58 → 48）。

### 4-2 又一处误报（顺带消除 2 条）

**为什么 D 类 21 条也没删**：抽样看 `main.py:3889 signal_handler`、`functions/health_ui.py:807 do_GET`（HTTP handler，由 `BaseHTTPRequestHandler` 反射调用）、`web_chat.py:29 push_reply`、`voice_handler.py:83 add_keyword_action` —— **仍带明显的回调/反射特征**，说明静态调用计数对这类「框架回调」天然失效。批量删除会直接打断运行链路，与任务书「禁止盲目批量清理」冲突 ⇒ 只列不改。

> 结论：**638 条 dead_code 里「真死代码」占比很低（≤3.3%），真正的问题是检测器把「反射可达」当成了「无人调用」**——这本身是比删代码更值得修的缺陷（见刀1 同族修法）。
