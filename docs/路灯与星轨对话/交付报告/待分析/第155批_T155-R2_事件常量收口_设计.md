## 2. 侦察结论 · 三大阻断性风险

### 风险① 替换面远超任务书口径
- 任务书称 **1,379 处**硬编码事件名；实测全库 AST 静态字面量命中 **≈2,546 处**（含 `tests/`）。
- 含 tests 会污染测试断言（许多测试显式比对事件字符串值，替换枚举对象即破坏）。
- 即便仅算生产码，面也显著大于 1,379 → 工作量与回归面需重新评估。

### 风险② 事件字符串值是"歧义常见词"
`const.py` 大量事件值就是日常英文词，**机械替换字符串→枚举会在非事件上下文大面积误杀**：

| 事件值 | 候选枚举 | 误杀风险 |
|---|---|---|
| `"question"` | `PulseIntent.QUESTION` | 自然语言文本/日志/配置里大量出现 |
| `"L3"` | `PulseLayer.L3_AUTONOMOUS` | 层级标识、注释、配置键 |
| `"CRITICAL"` | `LogLevel.CRITICAL` | 日志级别字符串遍地使用 |
| `"fused"` | `OrganStatus.FUSED` | 普通英文动词/形容词 |
| `"OUTER_VIEW"` | `ViewMode.OUTER_VIEW` | 仅大写连写，仍可能与常量撞 |

→ 纯字符串匹配无法区分"这是事件名"还是"这是普通文本"。

### 风险③ `const.py` 枚举是**普通类，非 StrEnum**
- 实测 `nucleus/const.py`：事件类是 `class HeartEvent: BEAT = "heart.beat"`（**普通类**，L71 `PulseEvent`、L121 `HeartEvent` 等），**成员 ≠ 字符串值**。
- 若机械把 `"heart.beat"` 替换为 `HeartEvent.BEAT`，则：
  - 全库 `event == "heart.beat"` 比对**全部失效**（枚举对象 ≠ 字符串）；
  - 事件总线 `EventStream.py`（核心 378 行）以 `{"event_type": "heart.beat"}` **dict 值存储并 JSON 序列化**，枚举对象序列化后是枚举名而非 `"heart.beat"`，**破坏持久化/网络协议兼容**。
- 因此"替换成枚举"必须配套把**所有消费端比对 + 序列化**改为 `.value`，这是一次**全库语义重构**，非"逐文件 AST 替换保留行为"能覆盖。

## 3. 两方案（待裁决）

### 方案 A — `const.py` 转 `StrEnum` + 全库替换
- 步骤：① 把 59 个事件类（231 成员）全改 `(str, Enum)`；② 发射点/比对点全改枚举；③ 消费端/序列化统一 `.value`；④ 加 ruff 字符串事件名告警。
- **优点**：类型安全，IDE 可跳转，编译期可查。
- **致命缺点**：
  1. 即便转 StrEnum，**风险②歧义常见词仍不能机械替换**（StrEnum 成员值仍是 `"question"` 等，比对 `== "question"` 在 StrEnum 下恰好兼容，但"该词到底是不是事件"仍靠人工判断）；
  2. 全库 2,546 命中 + 序列化改造 = **巨型重构**，与任务书"保留行为、低风险逐文件替换"相悖；
  3. 回归面极大，且 StrEnum 在 Python 3.12 下 `isinstance(HeartEvent.BEAT, str)` 为真，旧 `==` 比对兼容，但任何 `json.dumps(event_type)` 旧行为依赖字符串值，须逐点核对。
- **结论**：性价比低，仅当星轨要求"强类型事件"时才考虑，且仍需上下文感知（见方案 B 的发射点收口）。

### 方案 B（推荐）— 上下文感知 · 仅替换"点分事件命名空间"于已验证发射点
- **核心思想**：事件名里**真正专属、无歧义**的是**点分命名空间**字符串，如 `"heart.beat"`、`"system.boot"`、`"organ.fused"`、`"pulse.emit"`。这些在自然语言/日志里几乎不出现，专属性高 → 可安全 AST 替换为枚举。
- 步骤：
  1. **`const.py` 保持普通类不变**（值仍是字符串，旧 `==`/序列化全兼容，零行为变更）。
  2. **仅对"点分事件名"做 AST 替换**：正则/语义锁定含 `.` 的事件值（排除裸常见词 `question/L3/CRITICAL/fused/OUTER_VIEW`）。
  3. **发射点集中收口**：`EventBus.dispatch` / `EventStream` 写入等核心发射点统一经枚举，消费端用 `.value` 比对（保持字符串兼容）。
  4. **动态拼接（30 处）+ f-string**：人工核对，不机械替换（任务书已要求"动态拼接处人工核对"）。
  5. **新增 ruff 规则**：仅告警**点分命名空间裸字符串**（false-positive 低），不告警裸常见词。
- **优点**：风险②/③ 同时规避——点分命名空间专属性高、误杀低；不动 const.py 类形态、不动序列化，行为零变更；增量推进（从事件分发核心模块 `EventBus`/`EventStream` 起批，与任务书"从事件分发核心模块起批"一致）。
- **缺点**：裸常见词（`question` 等）暂不收口，需后续人工逐点确认；非"全库一次性清零"。
- **结论**：唯一可在"保留行为"前提下安全推进的路径。
