## 三、T0 核实：任务书四处前提被推翻

> 这一节是本批最重要的部分。四处都不是"描述略有出入"，而是**照原文做会做出无效的东西**。

### 偏差 1 · 刀1「定位 `lesson_strategies.json` 或对应存储」

**路径成立、30 条确认**，但任务书没说的是：

1. 30 条每条的字段只有 11 个 —— `rule / type / issue_type / organ / tag /
   strategy / applied_total / applied_last / hit_count / first_seen / last_seen`，
   三字段**一个都没有**（所以"老 30 条标 missing"是 30/30，不是部分）。
2. **更关键**：唯一写入点 `_m335_persist_batch` 里 `_e` 是先 `_e.update(...)`、
   紧接着 `_bk[_full] = _e`，**没有任何"新增 vs 更新"的区分**。
   直接在写入前判 `_full in _bk` 会**恒为 True**（赋值就在上一行），
   于是所有条目都被当成老条目、一条 WARNING 都打不出来，
   任务书验收第 1 条（"新假设入库必带三字段"）名义上做了、实际零生效。

**处置**：在 `_bk[_full] = _e` **之前**先算 `_m409_is_new = _full not in _bk`，
并写了 AST 判据 `test_46_is_new_computed_before_writeback` 钉住"算在写回之前"
这个顺序（`ast.unparse` 比位置）。这是本批唯一一个"顺序错了就静默失效"的点。

### 偏差 2 · 刀2「在 DailyScheduler 每日 03:00 那批任务加一项」

`DailyScheduler` **没有"任务清单"**，只有注册制 `add_daily_hook(name, fn)`
（`DailyScheduler.py:788`）。而 `lesson_strategies` 的读者是
`VerificationLearningHub`（`nucleus/mnemosyne/`，记忆层），与 `DailyScheduler`
（`nucleus/self_awareness/`，自我认知层）**没有任何既有连接**。

所以这不是"加一项"，是**新建挂钩**。本刀按 402 刀3（`organ_emits`）/
404 刀1（`causal_strength`）的现成范式，挂同一个 03:00 挂点，在 `main.py`
同一个 try 里注册（复用既有 except，不新增静默 handler）。

顺带核实的另一件事：`register_organ_emits_schedule` 在 `nucleus/` 内**只有定义、
没有调用**，唯一调用方是 `main.py`。也就是说"跨层挂钩必须落在 main.py 的装配块"
是这个项目的既有约定，不是本批发明的。

### 偏差 3 · 刀3 判据2「当前 68/87 为 None（三态不全）」

**这个数字在任何一份数据里都对不上。** 实测：

### 刀3 · 三判据具体实现

**新增** `nucleus/evolution/hypothesis_probes.py`：

| 判据 | 数据源 | confirmed | refuted | unknown |
|---|---|---|---|---|
| `recurrence` 复发 | `data/reports/audit/audit_*.json` | 窗口内有覆盖、零命中 | 同签名在窗口内复现 | 窗口内无审计快照 |
| `effect` 效果 | `data/evolution/effect_verify.json` | `passed=True` | `passed=False` | `passed=None` / 无记录 |
| `reuse` 复用 | `data/llm_traces/calls_*.jsonl` | 窗口内零命中 | 方法名在 prompt 里出现 | 窗口内无 trace / 无方法名 |

三条判据的"第三态"是本刀主要工作量，因为**最容易犯的错是把"查不到"当成"没发生"**：
审核池里没有这条签名，可能是真修好了，也可能是那天根本没跑审计；
追踪里没有匹配调用，可能是真没再问，也可能是那几天的 trace 没留。

**★ 判据3 只能做文本级近似匹配（重要限制）**

任务书说"查经验命中之后同 `issue_signature` 有无新 LLM 调用记录"。
实测 `calls_*.jsonl` 的字段是：
`trace_id / ts / origin / model / prompt / response / prompt_version / channel /
cost_estimate / duration / status / tokens / usage / error / feedback`
—— **没有 `issue_signature`**。

所以复用判据只能拿签名里的方法名去 `prompt` 正文里找。这是**文本级近似**，
不是结构化匹配：
- 方法名为空（只剩文件名）⇒ `unknown(coarse_signature)`，不硬判
- 命中只说明"有调用的提示词里提到了这个方法"，不保证是同一个问题的再求解
- 每条证据里显式写 `match="text"` 与一段 `note`，避免下批误当结构匹配用
- 命中按 `origin`（`system_internal / evolution_task / user_query`）拆开写进证据

**两个实测抓出来的真 bug**

1. ★ **复发判据的覆盖判据一开始只有下界**（`snapshot_ts >= window_start`）。
   于是"窗口在 40 天前、快照都在最近几天"被判成 `confirmed` ——
   **用今天的观测给上个月的窗口背书**。真实数据 `--probe` 直接把它打了出来。
   修法：加 `_COVER_GRACE_SEC = 6h` 宽限**上界**（每日批跑与 `due_at` 必然不重合，
   不留宽限会把最正常的场景判成"没覆盖"），命中判定同样卡上界。
2. ★ 审核池条目字段叫 `issue_type`，而 `EvolutionEffectVerifier.issue_signature()`
   读的是 `type` ⇒ 直接把条目喂进去永远得到 `file::::method`，**与假设签名对不上，
   探针会静默全员零命中（假 confirmed）**。加 `_audit_sig()` 做字段映射，
   并有专门判据 `test_18` 守住。

## 八、本批自己踩的坑（如实记录）

1. **`parse_window` 把「分钟」写成单字符类** `[smhd天小时分秒]` ⇒ 匹配不到两字单位
   `"2分钟"`，合法窗口被判"无法解析"。修：改成交替分组且**长短优先**
   `(分钟|小时|天|分|秒|s|m|h|d)?`。
2. **`mark_legacy_entries` 先改后判开关** ⇒ 灰度关掉时 `marked` 报 0、字段却真被写进去
   （计数与副作用脱钩，灰度成了摆设）。修：开关判在**动手之前**。
3. **`test_53` 锁死字面调用名** 而 `main.py` 惯例是 `import ... as 别名` ⇒ 假红。
   改成语义判据："从该模块导入的注册入口必须被调用"。（又一次"钉语义不钉措辞"）
4. **★ `except ... as _e` 遮蔽循环变量 `_e`**：Python 3 在 except 块末尾 `del` 掉该名字，
   后面的 `_e.get(...)` 直接 `UnboundLocalError`。它只在 `due_at` 是非数值的脏数据上
