### 刀1 · 分析器超时分级 + 分片缓存 + 异步（`032ba911`）

- 新建 `nucleus/self_awareness/AnalyzerCache.py`（约 420 行）
  - `(文件, mtime_ns, size) → 快照`，TTL 24h，落 `data/self_awareness/analyzer_cache.json`，原子替换
  - **键带 `size`** 是为了压「同秒原地改写、长度不变」的幻觉；只带 mtime 会漏
  - `log_analyzer_run()` / `prune_analyzer_runs()` 落 `data/self_awareness/analyzer_runs.jsonl`（按天，保留 30 天）
  - `peek_analyzer_cache()`：只取已存在的，不创建不加载 —— 冷启时那 13.7 MB 白加载实测要多付约 1s
- `CallGraphAnalyzer` 拆 `_collect_snapshot()`（纯解析、不改实例状态、可线程跑）/ `_merge_snapshot()`（主线程保序）+ `analyze_sharded()`
  - 安全性依据：`_pass2_resolve(self, collectors)` 的 `collectors` 参数**体内从未使用**（AST 验证）⇒ 按文件切分不影响 Pass2

**验收（连续 3 次全量，6 个生产分析器）**

| 指标 | 结果 |
|---|---|
| 冷缓存 → 热缓存 | **54.60s → 29.70s（-45.6%）** |
| `knowledge_quality` | 8,832 ms → **1.4 ms**（命中数据源缓存） |
| `call_graph` | 11,881 ms / `shards=4` / `cache_hit=True` |
| 分片等价性 | `analyze()` vs `analyze_sharded()`：**节点 8,017 / 边 13,184 / 11 项统计逐项一致** |
| 画像三维 | 3 轮 `knowledge_health`(10 键) / `fake_loops`(6) / `call_graph_health`(12) 全非空 |
| 超时 | **6/6 分析器 ok=true，全部 elapsed_ms < 60s** |

> 一个必须写下来的设计约束：**不能把单个分析器塞进固定 worker 池**。
> 超时语义靠「放弃等待一次性 daemon 线程」实现，塞进固定池会让超时后的 worker 被占死
> （Python 无法从外部中断线程），2 worker 很快耗尽。故分工是
> 「**一轮分析**跑在池里，**单个分析器**仍起一次性线程」。判据 `test_34` / `test_34b` 分开钉这两件事。

### 刀2 · distilled 异常可见化（`79f312a0`）

- 新增模块级 `_exc_site(exc)`：从 traceback 最后一帧取 `文件:行号 in 函数()` —— 任务书要「能看到在哪一步」，光有异常类型不够

> `assertRaises` 会清 `__traceback__`（unittest 防引用环），导致 `_exc_site` 拿到 `<no-tb>`。
> 故 `test_01` **不能**用 `assertRaises`，必须显式 `try/except` + `silent_exc` 留痕。原因写在该文件 docstring 里。

### 刀6 · L6 加年龄上限（`9cdc703e`）

见 §3.4。判据顺序**不可交换**：

```
存在 → 可解析 → schema → warm/cold 齐 → 非空      ← 真故障，一律 FAIL
→ 年龄 ≤ 3700s → PASS                              ← 405 新增
→ 超龄 → SKIP（framework_down / psutil_unavailable / running_unverified 三档可分辨）
```

把年龄放最后，是为了「结构坏了 + 同时超龄」仍报 FAIL 而不是降级 SKIP。

**实测（本机，框架停机）**

```
改前：L6  PASS   schema=snapshot_tiers/403.v1 温 0.1 / 冷 62.5，年龄 15904.7s   ← 4.4 小时也报 PASS
改后：L6  SKIP   小时快照 age=16228.8s > 上限 3700s，且框架未运行
            └─ skip_reason=framework_down
--l6-max-age 999999 → L6 PASS（年龄 16236.6s ≤ 上限 999999s（cli））
```

最后一行是关键：**证明判的确实是年龄**，且覆盖生效、来源（cli/default）可辨。

提交时七层读数从 `PASS=6 / SKIP=1` 变成 `PASS=5 / SKIP=2` —— 第二个 SKIP 就是 L6。

## 八、本批最该被记住的两条

### 8.1 一道假注释可以让缺口潜伏五天

刀5 的全部工作量，来自 404 刀3 写下的一句

> `#  ★注意：本 hook 未纳入版本管理（tools/ci/hooks/ 只版本化了 commit-msg）`

它把"我改了本机忘了改模板"包装成"已知限制"。于是：

- 404 交付报告把它当"已知限制"记下
- 404 核验请求单把它写成"待裁两项"之一
- 405 任务书照着"未纳版本管理"派活

**三道工序、两个批次、三个人，全被一行注释带着走。** 而真相是模板就在版本库里
（有三笔提交历史），缺的只是同步。

⇒ 以后遇到"这是已知限制"式的注释，**先验证它是不是真的**。注释和代码一样会撒谎，
而且注释撒谎更难发现——因为没人会去"跑一下注释"。

### 8.2 静态扫描的三种盲区必须一起说，否则会得出"19 条全欠账"的错误结论

本批 19 条里 4 条是假阳性，全部绕过同一种东西 —— `emit()`：

1. **变量间接**：`self._emit(_ctrl_action["event_type"], ...)`
2. **配置表下标**：`self._emit(task_info["event_type"], ...)`
3. **直接构造**：`field.publish({"event_type": SystemEvent.TIME_TICK, ...})`（连 emit 都不走）

⇒ **「扫不到发射」≠「没人发」**。下结论前必须：查配置表 + 查同文件有无变量发射点 +
**拿生产日志复算**。`time.tick` 是唯一有日志铁证的（483 次/天），
而 `controller.*` 一天 0 次是正常的（需用户下指令才触发）——
所以"日志 0 次"也证明不了"永远不发"，只能证明"这一天没发"。
