## 2. 增长源定位（按证据强度排序）

### ① 阶跃式加载（**主因，非泄漏**）
`data/reports/memory_alarm_trace.jsonl` 共 331 行，`why` 高频为：
- 「阶跃 +1032MB ≥ 1024MB（加载组件，非泄漏）」×6
- 「阶跃 +1026/+1064/+1050/+1025MB …」各 4~5 次

即 RSS 的**大步长增长来自组件加载**（SelfIndex 模块图 / 知识节点池 / 效果卡 / 快照反序列化等一次性装载），不是逐分钟线性泄漏。`rss_at_10min=5283MB` → 当前 6942MB 的抬升与多次 ~1GB 阶跃吻合。

### ② Python 对象堆：`dict` 数量巨大
`data/reports/memory/top_types_20261113_010004.json`（最新一份，共 129 份历史）：
- `heap_mb = 6608.0`
- `dict` **2,146,959 个 / 457.5 MB**（占 top20 首位）
- `list` 94,250 / 21.8 MB，`tuple` 68,268 / 4.7 MB，`Name`/`Constant` 各 1.3/0.9 MB

**判断**：`dict` 数量级（214 万）远超其它类型，是**对象图/索引类常驻结构**的特征，最可能来源为 SelfIndex 的模块图/器官索引、知识节点池、影子/候选/账本缓存的逐条 dict。top20 的 bytes 合计远小于 heap 6608MB，说明大头在**字符串/字节缓冲与原生分配**（非 Python 对象可直接归因），需后续用 tracemalloc/objgraph 按标签细分。

### ③ 影子/账本/记忆数据积累（**次要，量级不足**）
| 文件 | 当前规模 | 判断 |
|---|---|---|
| `data/monitor/self_query_shadow.jsonl` | ~127 行 | KB 级，非 GB 增长源 |
| `data/self_index/absorb_trace.jsonl` | 3 行 | 可忽略 |
| `data/monitor/verification_learning.json` | 百余条 | KB 级 |
| `data/context/conversation_memory.json` | 51 条 | KB 级 |

**结论**：任务书猜测的「影子日志积累 / 对话记忆」**不是** GB 级增长源；它们的量级差 3 个数量级以上。

### ④ 当前不在持续增长
`is_leak_signal=false`、稳态 13.3 MB/min 低于 50MB/min 告警阈值；`memory_steady_*.md` 历史报告亦把类似斜率判为「预热期」。当前属**阶跃后平台期**，需 24 小时连续采样才能区分「持续缓涨」与「波动」。

## 4. 修复建议（放后续综合优化 P0 批次，本批不实施）

1. **按标签定位 dict 来源**：用 `tracemalloc` 快照 + `objgraph.show_growth()` 在阶跃前后各采一次，给 `dict` 打 owner 标签（SelfIndex 缓存 / 节点池 / 快照 / 会话记忆），确认 214 万 dict 的具体归属——这是当前最大未知。
2. **阶跃削峰**：组件加载改为分批/懒加载，避免单次 ~1GB 阶跃；加载后显式释放临时反序列化缓冲。
3. **给常驻容器设上限**：模块图缓存、影子/候选/账本的进程内 list/dict 补 LRU 或容量上限（对照 `ContextSnapshot._max_conversation_per_user` 范式）。
4. **接入 24h 采样闭环**：把 `rss_hourly_probe_49322.py` 挂到 1800s heartbeat，累积满 24 点后按稳态斜率 + 阶跃次数复核 `is_leak_signal` 判据。
5. **不要误修**：影子日志/对话记忆/absorb_trace 的 KB 级增长不是主因，别在这些地方做无谓清理。
