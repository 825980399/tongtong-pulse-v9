### 3.2 改动

**① `_schedule_next_beat` 幂等化（`PulseHeart.py`）**

```python
with self._timer_lock:
    _cur = self._next_timer
    _me = threading.current_thread()
    if _cur is not None and _cur is not _me and _m396_timer_alive(_cur):
        self._m396_sched_skipped += 1
        return False                     # 活着就不动它
    if _cur is not None:
        _cur.cancel()
    ...新建...
    return True
```

三个调用点各自的行为：

| 调用点 | `_cur` 是谁 | 判据 | 结果 |
|---|---|---|---|
| `_m374_schedule_ahead()`（本拍开头） | 正在执行本拍的 Timer | `_cur is current_thread()` ⇒ 放行 | **真的新建**（否则第一次到期后链就断） |
| `finally`（本拍收尾） | 开头刚建的那条 | 存活且非本线程 | **幂等返回 False**，不再 cancel 重建 |
| 看门狗救援 | 在途那条 | 存活 | **拒绝重建**（`no_rescue_needed`） |

辅助判据 `_m396_timer_alive()` 用 **`is_alive() is True`** 而不是 `bool(...)`：单测里的 `MagicMock` 什么属性都能取到、什么都返回真值，用 `bool()` 会让假 Timer 被误判成"存活"从而永久跳过调度。

**节拍口径随之变化（须记录）**：从「本体结束 + interval」变为「本体开始 + interval」。
旧口径会把本体耗时叠进 gap（9.5s 周期 + 2~3s 本体 ⇒ 实测 gap 12s+），新口径才符合任务书
验收的「gap 稳定在 9.5s ± 2s」。这是**有意变更**，不是副作用。

**② 看门狗节拍**

```python
_nap = max(_iv * _M396_WD_NAP_FACTOR, _M396_WD_NAP_MIN)   # max(1.5×iv, 15s)
```

- iv=9.5 ⇒ **15.0s**（`max(14.25, 15)`），比心跳慢 5.5s，能观察到"下一拍到底来没来"。
- **副作用（须知晓）**：`_M374_SUSPEND_MIN_SEC=30` 是在 `_nap` 之上加的，进程级停放的判定阈值从 `5+30=35s` 变为 `15+30=45s`；对"心跳迟到"的发现延迟从 ≤5s 变为 ≤15s（×2 判据仍是 2×iv=19s，未变）。

**③ 成功判据改为下游观测量**

- 动作发出 ⇒ 只记 `_m396_rescue_pending = {beat_before, at, deadline, gap_before}`，返回 `action="rescue_pending"`、**`ok=False`**；
- 下一次看门狗醒来先跑 `_m396_confirm_rescue()`：
  - `beat > beat_before` ⇒ `_m396_rescue_ok += 1`，INFO「续链已确认生效」；
  - 过 `3×interval` 仍不动 ⇒ `_m396_rescue_failed += 1`，ERROR `heartbeat_rescue_failed`，文案明确「链没断，问题在早退（is_running/info_field）或心跳体卡死」——**把排障方向直接写进日志**。
- 在途 Timer 存活时返回 `action="no_rescue_needed"`、`error_code=heartbeat_chain_alive_no_rescue`。

**④ 进入日志（首行）**


打 `beat / is_running / timer_alive / interval`。节流与级别：

### 4.1 现场

```json

"heartbeat": {"interval": 9.5, "beat_count": 35, "status": "搏动中"}
```

### 4.2 改动

**① status 改「读时按 gap 现算」**

```python
def _m396_heartbeat_status(self, interval) -> tuple[str, float | None]:
    if self._m396_explicit_stop:
        return "已停搏（显式停止信号）", None
    if self._m396_last_beat_rx_at <= 0:
        return "起搏中（尚未收到心跳）", None
    _gap = time.time() - self._m396_last_beat_rx_at
    if _gap >= 3.0 * _iv:
        return f"停搏（{_gap:.0f}s 未跳，阈值 {_iv*3:.0f}s）", _gap
    return "搏动中", _gap
```

- `_on_heartbeat_observe` / `_on_heartbeat_alive` 只记「确实收到心跳的时刻」+ 读数，**不再把 payload 的 status 存进缓存**（存了就会被后续读方当真值）；
- 唯一采信的 payload 状态是 **`已停搏`**——`stop()` 主动发的显式信号，不是推断；
- `_build_observability_snapshot()` 每次构建都重算，并写 `status_source=computed@read`、`gap_s`、`beat_rx_count`；
- **`gap_s=None` 表示"没采到"，与"真是 0"分两个字段**（铁律 276）；
- `_trigger_heartbeat` 发的 `HeartEvent.ALIVE.status` 同样现算，且**必须在 `_last_beat_time = now` 之前算**（之后再算恒为 0，等于又变回常量串）。

**② 停搏由看门狗落盘**

```python
# _m365_watchdog_loop 内、m365_beat_watchdog() 之后
self._m396_stall_snapshot()
```

- 触发：`gap ≥ 3×interval`，60s 节流；
- 写入：读-改-写，**只改 `heartbeat` 段 + 顶层 `heartbeat_stall`**，其余字段原样保留；
- 通道：`safe_write_json(backup=False)`，与采集器同一条硬化路径（路径锁 + 退避重试 + 唯一 tmp）；

| `is_running=False` 早退 | 看门狗首行会 `no_baseline` 返回，不会有"已尝试续链" |
| `info_field=None` 早退 | 该路径**会续链**，链不会死 |
| `current_interval` 被拉大导致"误判" | 597 条告警文案都是 `2×9.5s` ⇒ 停跳期间 iv 恒 9.5 |

剩下的可能只有「Timer 建了但 function 未执行」这一族（线程未调度 / 被静默取消 / 线程池层面被拦），现有日志没有任何字段能分辨。**本批新增的 `[396刀1] 心跳进入` 就是补这个盲区**：

- 重启后若再出现同样停跳，`[396刀1] 心跳进入` **连续缺席** ⇒ Timer 没到期/被取消；
- **有该行但 beat 不增** ⇒ 早退（行里直接带 `is_running` 与 `timer_alive`）或心跳体卡死（此时 `[367链]` 会出现）。

另外还有一条**本批未动但值得关注**的线索：20:07:49 那一拍前后有 `内存增长率 57.45MB/分钟 ≥ 阈值 10.0` 告警与 `自动GC完成 暂停 410.08ms`。410ms 不足以解释 9.5s 的漏拍，但同窗口 RSS 已 7994MB / 使用率 16.3%，与第 389 批记录的"11GB 饱和曲线"同族。若下次停跳仍指向"Timer 未调度"，应把内存压力列为一级嫌疑。

## 七、重启后核验（给星轨/小林）

新增只读核验脚本：

```bash
python tools/m396_verify_heartbeat.py
```

四项判据（与任务书验收标准逐条对应）：

| 判据 | 脚本如何判 | 三态 |
|---|---|---|
| J1 连续 200 拍无 `[365链]` 告警 | 窗口内 `已尝试续链` 条数 == 0 | beat 跨度 <200 ⇒ **NO_SAMPLE**（不算通过） |
| J2 `beat_count` 单调递增 | 同 `proc_gen` 的 `心跳进入 beat=N` 序列严格递增 | 样本 <3 ⇒ NO_SAMPLE |
| J3 gap 稳定 9.5±2s | 首末留痕的「时间差 ÷ beat 差」= 平均每拍，判 7.5~11.5 | 时间戳解析失败 ⇒ NO_SAMPLE |
| J4 看门狗不刷续链 | 窗口内 `心跳间隔异常` 条数 == 0 | 同 J1 |

**设计要点**：NO_SAMPLE 与 FAIL 分开（铁律 276）。日志被轮转、留痕级别被抬高、重启后没跑够 200 拍——这些都只会得到 NO_SAMPLE，**不会被当成通过**。

脚本还会打旁证：`续链已确认生效 / 续链失败 / 367跳过` 三条计数，以及 `health_snapshot.heartbeat` 的 `status / gap_s / status_source`。若 `status_source=watchdog@stall`，说明看门狗判定停搏并已接管落盘——**这正是刀2 在起作用的正面证据**。

其余人工观察点：

1. 启动后前 3 拍看 `[396刀1] 心跳进入`（INFO，带「（状态变化）」）是否出现；
2. 心跳正常时 `health_snapshot.heartbeat.status_source` 应为 `computed@read`，`gap_s` 应在 0~19；
3. 若某次卡顿后出现 `[396链] 续链已确认生效：beat X→Y`，说明延迟确认判据在工作；
4. 若出现 `[396链] 续链**失败**`，日志会直接点明「链没断，问题在早退或心跳体卡死」——按这个方向查，不要再查链。

## 九、给下一批的三条提醒

1. **「动作已发出」不等于「结果已发生」**——本批两处都是这个病（看门狗 `rescheduled`、快照 `status` 常量串）。凡是自己判自己成功的地方，都值得查一遍成功判据是不是下游观测量。
2. **改 `_nap` 这类"节拍"常量要连带看它派生的阈值**：`_M374_SUSPEND_MIN_SEC` 是加在 `_nap` 上的，改 `_nap` 会静默改变"进程级停放"的判定线（35s→45s）。
3. **`total` 这种旧字段不要改值、只改名/加注释**：改值会让历史趋势线断代且无法解释，而"两口径差集"本身是有用信号。
