### 3.2 ①锁等待：**任务书的前提不成立，真因是口径假高**

任务书说「平均 50–250ms，过高」。查下去发现两条根因，**都不是锁本身慢**：

- **A. `_lock_waits` 是 `deque(maxlen=500)`，按条数老化**：一旦某段时间出现过高峰，那 500 条要很久才被挤掉 ⇒ **均值冻结在历史高峰**，「现在快了」在读数上永远看不见。
- **B. `if _lock_wait > 0:` 才 append** ⇒ **分母里没有 0 值样本**，所有「无竞争」的快路径被系统性剔除 ⇒ 均值天然偏高。

修法（`nucleus/runtime_metrics.py`）：

- `_M418_LOCK_WAIT_WINDOW_SEC = 120.0` + `_m418_lock_window_avg(waits, stamps, now)`：**只统计最近 120s**；
- 采样**含 0 值**（`> 0` 判断去掉）；
- `_point` / `get_snapshot` 加 `lock_wait_samples` 字段（让人能看出分母多大）；
- 开关 `config.ENABLE_M418_LOCK_WAIT_WINDOW = True`。

合成数据实测（40 条 × 200ms 在 5 分钟前 + 10 条 × 2ms 在 1 分钟内 + 20 条 0 值）：

```
旧口径（全量 >0 样本，n=50）= 160.40 ms   ← 被 5 分钟前高峰冻结
新口径（120s 窗 + 含 0，n=30）= 0.67 ms
★ 判据 50ms：旧 = FAIL   新 = PASS        降幅 99.6%
```

### 3.4 ⑦额度预警：任务书没说的主因

任务书说「同一预警弹两遍」。第一版我按「去重键失效」修——`else` 分支里 `self._warned.pop(_n, None)` **无条件执行**，去重形同不存在。修完仍弹两遍。

**真主因**：`_warn_once()` **自己打一行日志**，调用点**再打一行明细** ⇒ 天然两条。

修法：把 `_warn_once()` 改成**纯闸门**——只判定「该不该打」，**不打印**，返回 `-> bool`；三个调用点改成 `if self._warn_once(...):` 再打明细。脚本内加 AST 自验：**闸门里不得出现 `_module_logger`**。

```
_warn_once 返回注解 -> bool = True
闸门内残留 _module_logger   = False
调用点用 if self._warn_once(...) = 3 处
```

## 四、刀4 · 探针加列（内存定性准备）

### 4.1 做法

`organs/core/PulseMetricsCollector.py::_m339_memory_probe` 的 gc 分支：

- 与 `_cnt` 同遍历累加 `_byt[type] += sys.getsizeof(obj)`（**shallow** 口径）；
- 失败计数 `_bytes_err`，**只在首次失败时 `silent_exc`**（1.4M 对象循环里每次留痕 = 新的刷屏源）；
- `gc_type_rows` 每行加 `bytes` 字段（与 `count` 同序，都按 count 降序取 top_n）；
- 新增载荷：`gc_bytes_total` / `gc_bytes_kind="shallow"` / `gc_bytes_shallow` / `gc_bytes_err` / `gc_objects_scope="gc_tracked_only"` / `arrow_mb` / `arrow_loaded`。

### 4.2 ★ 实测产物（隔离生成 `tmp/m418_k4_out/top_types_20261101_192109.json`，4458 B）

### 4.3 ★ 必须写进产物的口径陷阱（否则读数会被误用）

**`gc.get_objects()` 只返回「被 GC 跟踪」的对象。** 实测：`gc.is_tracked({'k':0,'v':'x'*16})` 在 **CPython 3.12** 下返回 **False**——只装 int/str 的 dict 不进 GC 链表。

本轮证据：我故意造了 **120000 个纯原子 dict** + 1 个 3MB `bytearray`，`gc_scanned` 只有 **19656**，`gc_bytes_total` 只有 **4.99 MB**。⇒ **`gc_bytes_total` 是下界，不是全堆大小。**

所以产物里必须同时有 `gc_objects_scope="gc_tracked_only"` 和 `gc_bytes_kind="shallow"` 两个字段——**让读数自带口径，不靠文档**。这也是本刀「为内存定性做准备」的真正价值：没有这两列，28GB 里「谁占的」永远只能靠猜。

**另**：`arrow_mb=None` + `arrow_loaded=False` 是正确读数（本机未加载 pyarrow），不是「0 字节」——`None` 与 `0` 必须分得开。

### 9.3 L02 · 比票面严重：`_pulse_bus` 这个**属性本身**全库从未赋值

票面只说「`request()` 不存在」。核实后是三件事：

**这个工具的三条设计原则**（都写进了单测）：

1. **`WAIT` 是一等公民，不冒充 `PASS` 也不冒充 `FAIL`**。退出码 `0` 全 PASS /
   `1` 有 FAIL / `2` 只有 WAIT。
2. **框架不活时，`patterns`/线程数判 `WAIT` 而不是 `FAIL`**——停机后 `mtime`
   当然不动，拿它判 FAIL 等于把「没开机」记成「修复没生效」。
3. **`L14` 只算真补丁**（`patch_id` 以 `patch_` 开头），演示桩（`issue_type="x"`）
   单列 `stub_rows`——否则 `3/50=6%` 会被当成"有数据"。
