## §2 刀1：稳态窗算法（写了吗？—— 写了，四段）

```
① 稳态 steady  = get_memory_growth_report(window_sec=1800)    ← 30 分钟平均
② 瞬时 instant = get_memory_growth_report(window_sec=300)     ← 原 5 分钟窗，只当输入
③ 突增 spike   = instant ≥ 阈值 ∧ instant ≥ 2 × max(steady, 阈值) ∧ 持续 ≥ 300s
④ 阶跃 step    = 瞬时窗内 (当前 RSS − 最低 RSS) ≥ 1024MB     ← 加载组件，单独标
⑤ 真泄漏       = steady ≥ 阈值（与③并列，不替代）
```

为什么 ⑤ 必须单独存在（这是本刀最容易写错的地方）：
**泄漏的特征就是"稳态一直在涨"**，此时 `instant ≈ steady`、比值 ≈ 1，光看比值判据反而会漏。
所以"稳态越线"是独立的一条，不是"突增"的兜底。

ramp 期（启动 10 分钟内）仍按 427 口径整体不判 —— 那是加载阶跃，不是泄漏。

### 2.1 同一份数据上的新旧 A/B（活体）

| 场景 | 旧口径（瞬时 ≥ 50） | 新口径 |
|---|---|---|
| **GC 掉 850MB 再 5 分钟爬回**（19:18 现场形状） | 瞬时 192.1 → **告警** | 首次 **不告警**（持续 0s）；若真持续 5 分钟才判 `spike` |
| 同一抖动、5 分钟后（已滑出窗） | 瞬时 0 → 不告警 | **不告警**（`未达告警条件`） |
| **真泄漏 +60MB/min** | 告警 | **`steady_leak` 立刻告警**（稳态 60 ≥ 阈值 50） |
| **阶跃 +1200MB** | 告警 | **`step`**（阶跃 +1200MB，单独标种类） |

## §3 刀2：验证学习枢纽首报一次

### 3.1 改法

`_m409_annotate_entry` 里加三行判断：

```python
_was_marked = bool(entry.get(_hc.F_MISSING))                 # 进来之前有没有标记
_rep = _hc.annotate_new_entry(entry, treat_as_new=is_new)    # 会原地改 entry
_newly = _hc.F_MISSING in (_rep.get("applied") or [])        # 本次真的打上了吗
if not _was_marked and not _newly and _rep.get("missing"):
    entry[_hc.F_MISSING] = True                              # 老条目首见补标记
    _newly = True
WARNING if (_newly or not ENABLE_M449_HYP_QUIET) else DEBUG
```

★`_was_marked` 必须在调用**之前**取 —— `annotate_new_entry` 原地改写 entry，查完再判永远是 True
（409 自己在 `is_new` 上栽过一次，注释里写着"要在写回 `_bk` 之前判"）。

### 3.2 活体：同一条目连扫三轮

```
第1轮: level=WARNING  marked=True ｜[409刀1] 假设缺可观测判据 …（老条目）：缺字段=…
第2轮: level=DEBUG    marked=True ｜[449刀2] 假设缺判据（已标过，降为DEBUG）…｜累计压掉 1 条
第3轮: level=DEBUG    marked=True ｜[449刀2] 假设缺判据（已标过，降为DEBUG）…｜累计压掉 2 条
新条目: level=WARNING marked=True ｜[409刀1] 假设缺可观测判据 brand_new（新增）：…
压掉计数 _m449_suppressed = 2
本轮各级别条数: {'WARNING': 2, 'DEBUG': 2}
```

**老条目重复刷的问题解决了**（3 轮 → 1 WARNING），**新条目第一次发现仍然 WARNING**。

### 3.3 改完后验证学习枢纽告警降到多少？

## §7 连带影响

1. **`get_memory_growth_report()` / `get_memory_growth_rate()` 一字未改** —— 契约、窗口口径、返回值都不变，只是被调用两次（瞬时窗 + 稳态窗）。每 5s 多一次 deque 扫描，量级可忽略。
2. **`check_memory_alarm_detailed` 返回字典只加不改**：新增 `m449_mode` / `m449_steady_mb_per_min` / `m449_instant_mb_per_min` / `m449_held_sec` / `m449_step_delta_mb`，原有 `steady_window_sec` / `steady_growth_mb_per_min` / `is_leak_signal` 等全在（`test_m433` 的字段断言仍绿）。
3. **`percent` 与 `rss` 两闸未动**（80% / 8192MB），所以内存**使用率**告警行为完全不变。
4. **告警文案变了**（多了"模式/瞬时/稳态/阶跃"）。若有下游正则匹配旧文案，需要跟着改 —— 全仓 grep 未发现此类解析（`grep "内存告警（闸因"` 只有本模块与其备份）。
5. **`_m449_spike_since` 是实例状态**：进程重启后计时归零，第一轮突增要重新累计 5 分钟。这是刻意的（重启本身就是一次阶跃）。
6. **刀2 会给老条目补写 `missing_criterion=True`**：`summarize()` 的 `no_criteria_and_no_flag` 计数会因此下降（那些条目本来是"既没判据也没标记"的漏网件）。这是修复，不是回归。
