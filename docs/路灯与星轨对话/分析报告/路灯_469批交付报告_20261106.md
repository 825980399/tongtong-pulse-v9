## 二、刀2 补丁构造时的「粒度对齐」（本批真正的根因修复）

### 病因（T0 实测，命中率 11/12 = 92%）

| original 首行缩进 | modified 首行缩进 | original 含 def | modified 含 def | 判定 |
|---|---|---|---|---|
| **8** | **0** | False | True | **MISMATCH ×11** |
| 0 | 0 | True | True | OK ×1 |

`original_code` 来自 `self_inspector.get_method_body()["body"]` —— **天生是方法体片段**；
LLM 被要求修这个片段，返回的却是**整个方法**（带 `def`）。
`full_content.replace(片段, 整个方法)` 等于在别的方法体里插入一个嵌套 `def`
⇒ 缩进关必然以 `基础缩进不一致（未替换）: original=8 modified=0` 拒绝。

**实证**：`patch_llm_1793945467_7587`（11-06 14:11 当日唯一被放行的补丁）
原文 462 字 / 9 行，首行 `        try:`；
modified 532 字 / 12 行，首行 `def _schedule_next_beat(self):`。
它就是被缩进关拒绝的，而额度已经被它吃掉，连锁导致 14:11→17:00 近三小时零落地。

### 改动

`nucleus/reasoning/SafeEvolutionExecutor.py` 新增三个模块级函数：

```python
_m469_granularity_align_on()            # 开关（ENABLE_M469_GRANULARITY_ALIGN）
_m469_find_method_span(lines, method)   # AST 定位 [lineno, end_lineno) + col_offset
_m469_method_exists(patch)              # present / absent / unknown
_m469_align_method_patch(patch)         # 对齐 + 记指纹
```

对齐规则：

* `modified` 首个非空行以 `def ` / `async def ` 开头 ⇒ LLM 重写了整个方法 ⇒
  用 AST 把 `original_code` 换成目标文件里该方法的**整段源码**，
  并把 `modified_code` 用 `textwrap.dedent` + 方法真实缩进回填。
* 同名方法不是恰好 1 个 / 整段不是唯一出现 / 读不到文件 ⇒ `ok=False`，**不构造该补丁**。
* `as_is` 分支（modified 不是整方法）也要过 `_m469_method_exists` ——
  实测 **5/12** 补丁的方法名根本不存在：

| patch | method 字段 | 文件里的真名 |
|---|---|---|
| `..._f7ed` | `_process_l2_nodes` | `_compress_l1_to_l2` |
| `..._c6a7` | `filter_keywords` | `_liver_extract_keywords` |
| `..._55f9` | `periodic_task_no_reentry` | ← **issue_type 被当成方法名** |
| `..._a8dd` | `collect_value_data` | ← 方法还没被创建 |
| `..._1481` | `preprocess_topic` | `_preprocess_search_topic` |

顺带记 `source_file_sha256` + `source_snapshot_at`，供刀1 归因漂移。

## 三、刀3 中风险门槛独立旋钮 + 安全拒绝留痕

### 病因

`trust_threshold_for` 只有「低 / 其余」两档，中风险被并进 `high(60)`，
而 LLM 中风险补丁的 `trust_score` **恒为 40** ⇒ 结构性永远不通过。
2026-11-06 实测 5/5 条全被 `信任分数不足(40.0<60.0)` 拒绝。
即便把信任分提上去，`auto_apply_max_risk=2` 还会再拦一次
（实测：把 trust 临时抬到 65 后，5 条全部变成 `风险等级过高(中)`）。

### 改动与**不**改动

* `trust_threshold_for` 拆成三级：低 → `low(40)`；中 → **`mid`**；高 → `high(60)`。
* `config.EVOLUTION_EFFECT_VERIFY_CONFIG` 新增 `"mid_risk_min_trust": 60`，
  **缺省刻意等于 `high_risk_min_trust` ⇒ 零行为变化**。
* 被安全门槛拒绝的补丁改留 `safety_blocked=True` + `safety_blocked_reason`，
  并计入 `results["safety_blocked"]`，不再静默堆积。

### 为什么**不放开**中风险自动落地

实测那 5 条中风险是 **4 条「LLM 拆 344/280/231/304 行方法」** + 1 条「删死代码」。
在 `config.py` 自述的 **0.268% 测试覆盖率**下让 LLM 自动重写整段逻辑并写盘，
风险与收益不成比例。本批只给**旋钮**，不转旋钮。

### 验效（零行为变化）

拿真实 14 条队列逐条问 `_check_patch_safety`，本批前后**逐条完全一致**：
6 条 True / 8 条 False，拒绝理由逐字相同（`信任分数不足(0<60.0)` 等）。
`mid_risk_min_trust` 调到 40 时中风险变 40、高风险仍是 60（互不连累，单测 D4 断言）。
