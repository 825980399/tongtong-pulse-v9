## §0 先说三件与任务书字面不一致的事

### ① 刀1 的归因错了：96 条原生线程几乎不是 ONNX Runtime 起的

任务书说「ONNX Runtime 自己起了 96 条原生计算线程」。逐库普查（16 核机器，
`psutil.Process().num_threads()`，含原生线程）实测：

| 阶段 | OS 线程 | 增量 |
|---|---|---|
| 进程基线 | 4 | — |
| `+numpy` | 19 | **+15** ← scipy-openblas 按核数建池 |
| `+torch` | 22 | +3（之后 `torch.mm` 再 +7 OpenMP 池） |
| `+faiss` | 37 | **+15** ← 自有 OpenMP 池 |
| `+sklearn` | 52 | **+15** ← 自有 OpenMP 池 |
| `tokenizers.encode_batch` | — | **+16** ← rust rayon 池 |
| `onnxruntime.InferenceSession(intra=2)` | — | **+1** |

**ORT 是这里面最小的那个**——`VectorEncoder` 早在 360 批就已给 fastembed 传
`threads=2`，ONNX 侧本来就没问题。生产 `pid 32860` 实测 OS 166 / Python 72
⇒ 原生 94 条，与烛微报的 96 吻合，但大头是 **OpenBLAS + faiss + sklearn 的
OpenMP 池（各 15 条）与 tokenizers 的 rayon 池（16 条）**。

所以刀1 的施工对象从「ONNX 一个库」改成「**所有原生线程池统一限流**」：
ORT 那条顺手配置化（360 批写死的 2 → `M437_ORT_INTRA_THREADS`，缺省 4），
真正的收敛靠 `OMP_NUM_THREADS / OPENBLAS_NUM_THREADS / MKL_NUM_THREADS /
NUMEXPR_NUM_THREADS / RAYON_NUM_THREADS` 五个环境变量。

### ② 刀1 必须在 `import numpy` **之前**生效，晚一步就白做

OpenBLAS 在 `import numpy` 那一刻就按核数把池建好，之后再改环境变量只是
改了个字符串。所以落点在 `main.py` **第 4~11 行**（紧跟 config / silent_exc /
warn_throttle 三个轻量导入之后，早于任何 numpy 系导入），并加了源码位置单测把
这个顺序钉死（`test_main_applies_caps_before_numpy`）。

### ③ 刀2 的盘面大头不在「超 7 天」里，规则删不到

`data/` 8.0G，`.bak` 系列 22 个 / 1373.9 MB，但按「超 7 天 + 只留 1 代」能删的
只有 **10 个 / 0.40 MB**。三个巨型里两个被规则挡住，原因见 §3.3。

### 改动（3 个文件 +105 / -9，另新增 1 模块 153 行）

| 文件 | 行数 | 内容 |

| `config.py` | +23 | 4 个开关 + 数值（见下） |

```
ENABLE_M437_NATIVE_THREAD_CAP = True    # 总闸，False ⇒ 一个环境变量都不写
M437_NATIVE_OMP_THREADS       = 4       # OpenMP/OpenBLAS/MKL/NumExpr
M437_NATIVE_RAYON_THREADS     = 2       # tokenizers(rust rayon)
M437_ORT_INTRA_THREADS        = 4       # ONNX Runtime intra/inter-op
```

### 取值怎么定的（不是拍脑袋）

同一台 16 核机器，四组参数各跑一遍「numpy 矩阵 + 编码 256 条 + faiss 检索」：

| OMP | RAYON | ORT | OS 线程 | 编码 256 条 |
|---|---|---|---|---|
| 不限 | 不限 | 2 | **39** | 1.193s |
| 4 | 2 | 4 | **18** | **0.928s** |
| 4 | 2 | 2 | 16 | 1.148s |
| 4 | 1 | 4 | 17 | 0.880s |
| 2 | 1 | 2 | 10 | 1.440s |

⇒ 选 **OMP=4 / RAYON=2 / ORT=4**：线程从 39 降到 18，编码反而更快。
再往下压（OMP=2）线程更少但编码掉到 1.44s，是拿速度换指标，不取。

### 活体验证（真实依赖链 A/B，各自独立进程，非 mock）

`tmp/_m437_live_ab.py before|after`：numpy → faiss → sklearn → torch →
fastembed 加载真模型 → 编码 256 条 → faiss 32×256 top10 → KMeans(256×512)。

| 指标 | 改前（before） | 改后（after） | 变化 |
|---|---|---|---|
| **OS 线程（终态）** | 76 | **24** | **−68.4%** |
| 其中原生（扣 python=1） | 75 | 23 | −69.3% |
| 模型加载 | 0.13s | 0.11s | −15% |
| **编码 256 条** | 1.170s | **0.663s** | **−43.3%（更快）** |
| **faiss 32×256 top10** | 0.35ms | 0.20ms | **−42.9%（更快）** |
| **KMeans(256×512)** | 1.680s | **0.120s** | **−92.9%（快 14 倍）** |
| 分阶段线程 | start 19 → faiss 37 → sklearn 52 → torch 52 → load 53 → encode 69 → end 76 | start 7 → faiss 13 → sklearn 16 → torch 16 → load 19 → encode 21 → end 24 | 每一段都收窄 |

**回答任务书两问**：
- 「OS 线程总数从 178 降到 ≤100 了吗？」→ **隔离环境 76 → 24，达标**。
  生产当前基线 **166（python 72 + 原生 94）**，按同比例（原生 75→23）
  预计重启后落在 **95~105**，需重启后实测确认（§5 复核项①）。
- 「向量检索速度降了吗？」→ **没有降，三项全部更快**（编码 −43%、
  faiss −43%、KMeans −93%）。原因是线程少了以后上下文切换与 OpenMP
  自旋等待的开销一起消失。

### 灰度回退

`ENABLE_M437_NATIVE_THREAD_CAP=False` ⇒ `apply_native_caps()` 直接返回
`{"enabled": False}`，一个环境变量都不写，逐字回到改前行为（单测
`test_switch_off_writes_nothing` 守着）。

## §5 连带影响与待复核

### 连带影响

1. **`VectorEncoder` 的 ORT 线程数 2 → 4**：这是**唯一一处可能变慢**的地方，
   但实测 4 比 2 快 15%（0.663s vs 1.148s / 256 条）。原来 `cpu_only=False`
   时传 `None`（让 ORT 按核数自选），现在无论 cpu_only 与否都给确定值。
2. **`main.py` 前 11 行变了**：任何 `import main` 的测试/工具都会在导入时写好
   5 个环境变量。已回归 2 个 `import main` 的套件（14 条全绿）。
   若某工具**先** `import numpy` 再 `import main`，限流对 numpy 无效（其余仍有效）
   —— 这是环境变量的物理限制，已在模块文档里写明。
3. **`framework.start()` 后多一个守护线程**（`M437BackupSweep`，延迟 20s、24h 节流、
   daemon）。进程退出不阻塞。
4. **`_keep_backup` 那条链不受影响**：435 批已把它改成「小文件只留 1 代」，
   所以 `.bak.1/.bak.2` 不会再新增；本次删掉的 6 个是 435 之前的历史残留。
5. **备份清理会写 2 个文件**：`data/monitor/backup_sweep_last.json`（清单）、
   `data/monitor/backup_sweep_stamp.json`（节流戳）。

### 待重启复核（框架仍跑旧代码，pid 32860）

- ① **生产 OS 线程数**：重启后用 `psutil.Process(<pid>).num_threads()` 读，
  预期从 **166** 降到 **≤105**；同时看 `health_snapshot.threads.n`（Python 线程，
  预期仍 70 上下不变 —— 本刀只动原生线程）。
- ② **语义内核仍可用**：日志出现 `[语义内核] 模型就绪 … CPU_ONLY`，
  且编码不报维度异常。
- ③ **备份清理线程**：`data/monitor/backup_sweep_stamp.json` 出现，
  `backup_sweep_last.json` 的 `scanned≈10 / deleted=0`（本次已清干净）。
- ④ **11-10 之后**：`pulse_knowledge_snapshot.json.20261103_064554.bak`（768.5 MB）
