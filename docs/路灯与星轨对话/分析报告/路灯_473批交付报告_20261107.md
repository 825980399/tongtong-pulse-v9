## 二、必须先摆清的一个事实：3.14t 换不来性能

保留 3.14t 是**未来投资**，不是当下收益。实测：

| 指标 | 实测值 |
|---|---|
| `free_threaded_build` / `sys._is_gil_enabled()` | True / **False**（GIL 确实关着） |
| CPU（15 秒采样） | 0.08s ⇒ **0.01 核** |
| CPU（进程全生命周期 1157s） | 183.6s ⇒ **0.16 核** |

这套系统从未跑满一个核。时间花在等 LLM（日志实测 `zhipu 调用成功（8.16s）`，等网络时 GIL 完全释放）与等定时器上，属 I/O 密集型。**关掉 GIL 对 I/O 等待没有任何帮助**，这与 472 批否定「GIL 导致卡死」的三条反证一致。

代价则很具体：free-threaded 引入了一类**原本不存在的故障**——代码长期按「GIL 保证原子性」写，`+=` 计数、dict 复合操作、列表就地修改都没有加锁，现在这些隐含假设可能变成真实竞态。本批把改动面收窄到「纯数值、不碰 Python 对象」的 6 个 Cython 模块，并用并发测试固定住；**其余 Python 层的并发假设尚未系统性排查**，见第六节风险 3。

## 三、四刀改动

### 刀1 · Cython 双 ABI 共存（6 个 `.pyx` + 6 个 `.c`）

每个 `.pyx` **首行**补：

```cython
# cython: freethreading_compatible=True
```

这一步不是可选项。按 PEP 703 迁移规则，**未声明 free-threading 兼容的扩展模块在导入时会让解释器把 GIL 重新启回来**——6 个模块一加载，整个迁移当场失效。实测导入前后：

```
gil_before: False
  [OK] nucleus.pulse._frequency_codec_cy          gil_after=False
  [OK] nucleus.synapsys._resonance_cy             gil_after=False
  [OK] nucleus.field._oscillon_cy                 gil_after=False
  [OK] nucleus.gpu._cosine_cpu_cy                 gil_after=False
  [OK] nucleus.reasoning._inner_world_math_cy     gil_after=False
  [OK] nucleus.reasoning._topk_retrieve_cy        gil_after=False
```

**安全性依据**：这 6 个 `.pyx` 的头部注释自述「仅纯数值计算，不涉及 Python 对象操作」「nogil 块内只允许 C 类型与 libc.math」，即它们不依赖 GIL 保护任何共享状态。

**共存验证**（双向，缺一不可）：

| 解释器 | 加载自 | 结果 |
|---|---|---|
| 3.14t | `.cp314t-win_amd64.pyd` × 6 | 全部 OK，GIL 保持关闭 |
| 3.12 | `.cp312-win_amd64.pyd` × 6 | 全部 OK，零污染 |

`.c` 生成物与 `.pyx` 同批更新，按**主环境口径**（3.12 / Cython 3.2.9）重生成，避免生成物随构建顺序漂移。

### 刀2 · 修复 `_md5_int` 空输入越界（真 bug）

重编后 m397 立即报红：

```
IndexError: Out of bounds on buffer access (axis 0)
_frequency_codec_cy.pyx:142
```

根因：

```cython
cdef const uint8_t[::1] buf = data
_md5_full(&buf[0], len(data), out)   # data 为空 ⇒ &buf[0] 越界
```

`_md5_full` 本身在 `length=0` 时**根本不读 data**（`range(0)` 不进循环），只需一个合法非空指针。故用 1 字节哑缓冲兜底即可。

**这个 bug 一直被旧的 cp312 产物掩盖**——旧 pyd 是陈旧构建，与源码不同步，正好印证了 m397 的设计意图（「pyd 早于 pyx ⇒ 符号可能与源码不同步」）。修复后 5 组样例（含 `b""`）与 `hashlib.md5` 逐字节一致。

### 刀3 · `tools/build_cython_all.py` ABI 常量去硬编码

```python
_ABI = "cp312-win_amd64"   # ← 死常量：全文件无使用点，但会误导人
```

改为 `sysconfig.get_config_var("EXT_SUFFIX")` 推导（3.14t 实测 `.cp314t-win_amd64.pyd`）。

**落位逻辑本身不需要改**：`build_one` 在独立临时目录编译，再用 `os.path.basename` 完整保留 ABI 标签落位，因此 cp314t 产物不会覆盖 cp312 产物。

### 刀4 · 新增 `tests/test_m473_cython_freethreading.py`（9 条）

| 判据层 | 内容 |
|---|---|
| 静态 | 6 个 `.pyx` **第 1 行**必须带指令（防止后续被删，静默让 GIL 复活） |
| 行为 | 8 线程 × 200 次并发，结果须与单线程基准 `repr` 精确相同 |
| 环境 | free-threaded 构建下，导入全部 6 个后 `sys._is_gil_enabled()` 必须仍为 False（3.12 上自动 skip） |

## 四、依赖可装性矩阵（口径已修正两次）

**★判定口径**：必须用 `pip install --dry-run --only-binary=:all: --no-deps <pkg>`。

- `pip index versions` **不按 ABI 过滤**，会把只有 sdist 的包误报为可用——首轮探测因此把 29/29 全报成可装，实际只有 22 个真有轮子。
- 已安装的包输出 `Requirement already satisfied` 而非 `Would install`，判据要同时认，否则会把装好的误判成无轮子。

根因：**free-threaded 解释器只接受 `cp314t` ABI 轮子或纯 Python 轮子，普通 `cp314` 轮子不兼容**——「包支持 3.14」≠「包支持 3.14t」。

`requirements-314t.txt`（独立基线，**不改动** `requirements.txt` / `requirements-ci.txt` / `requirements.lock`）：
