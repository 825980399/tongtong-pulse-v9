## 二、必须先摆清的一个事实：3.14t 换不来性能

保留 3.14t 是**未来投资**，不是当下收益。实测：

| 指标 | 实测值 |
|---|---|
| `free_threaded_build` / `sys._is_gil_enabled()` | True / **False**（GIL 确实关着） |
| CPU（15 秒采样） | 0.08s ⇒ **0.01 核** |
| CPU（进程全生命周期 1157s） | 183.6s ⇒ **0.16 核** |

这套系统从未跑满一个核。时间花在等 LLM（日志实测 `zhipu 调用成功（8.16s）`，等网络时 GIL 完全释放）与等定时器上，属 I/O 密集型。**关掉 GIL 对 I/O 等待没有任何帮助**，这与 472 批否定「GIL 导致卡死」的三条反证一致。

代价则很具体：free-threaded 引入了一类**原本不存在的故障**——代码长期按「GIL 保证原子性」写，`+=` 计数、dict 复合操作、列表就地修改都没有加锁，现在这些隐含假设可能变成真实竞态。本批把改动面收窄到「纯数值、不碰 Python 对象」的 6 个 Cython 模块，并用并发测试固定住；**其余 Python 层的并发假设尚未系统性排查**，见第六节风险 3。

## 三、四刀改动

### 刀1 · Cython 双 ABI 共存（6 个 `.pyx` + 6 个 `.c`）

每个 `.pyx` **首行**补：

```cython
# cython: freethreading_compatible=True
```

这一步不是可选项。按 PEP 703 迁移规则，**未声明 free-threading 兼容的扩展模块在导入时会让解释器把 GIL 重新启回来**——6 个模块一加载，整个迁移当场失效。实测导入前后：

```
gil_before: False
  [OK] nucleus.pulse._frequency_codec_cy          gil_after=False
  [OK] nucleus.synapsys._resonance_cy             gil_after=False
  [OK] nucleus.field._oscillon_cy                 gil_after=False
  [OK] nucleus.gpu._cosine_cpu_cy                 gil_after=False
  [OK] nucleus.reasoning._inner_world_math_cy     gil_after=False
  [OK] nucleus.reasoning._topk_retrieve_cy        gil_after=False
```

**安全性依据**：这 6 个 `.pyx` 的头部注释自述「仅纯数值计算，不涉及 Python 对象操作」「nogil 块内只允许 C 类型与 libc.math」，即它们不依赖 GIL 保护任何共享状态。

**共存验证**（双向，缺一不可）：

| 解释器 | 加载自 | 结果 |
|---|---|---|
| 3.14t | `.cp314t-win_amd64.pyd` × 6 | 全部 OK，GIL 保持关闭 |
| 3.12 | `.cp312-win_amd64.pyd` × 6 | 全部 OK，零污染 |

`.c` 生成物与 `.pyx` 同批更新，按**主环境口径**（3.12 / Cython 3.2.9）重生成，避免生成物随构建顺序漂移。

### 刀2 · 修复 `_md5_int` 空输入越界（真 bug）

重编后 m397 立即报红：

```
IndexError: Out of bounds on buffer access (axis 0)
_frequency_codec_cy.pyx:142
```

根因：

```cython
cdef const uint8_t[::1] buf = data
_md5_full(&buf[0], len(data), out)   # data 为空 ⇒ &buf[0] 越界
```

`_md5_full` 本身在 `length=0` 时**根本不读 data**（`range(0)` 不进循环），只需一个合法非空指针。故用 1 字节哑缓冲兜底即可。

**这个 bug 一直被旧的 cp312 产物掩盖**——旧 pyd 是陈旧构建，与源码不同步，正好印证了 m397 的设计意图（「pyd 早于 pyx ⇒ 符号可能与源码不同步」）。修复后 5 组样例（含 `b""`）与 `hashlib.md5` 逐字节一致。

### 刀3 · `tools/build_cython_all.py` ABI 常量去硬编码

```python
_ABI = "cp312-win_amd64"   # ← 死常量：全文件无使用点，但会误导人
```

改为 `sysconfig.get_config_var("EXT_SUFFIX")` 推导（3.14t 实测 `.cp314t-win_amd64.pyd`）。

**落位逻辑本身不需要改**：`build_one` 在独立临时目录编译，再用 `os.path.basename` 完整保留 ABI 标签落位，因此 cp314t 产物不会覆盖 cp312 产物。

### 刀4 · 新增 `tests/test_m473_cython_freethreading.py`（9 条）

| 判据层 | 内容 |
|---|---|
| 静态 | 6 个 `.pyx` **第 1 行**必须带指令（防止后续被删，静默让 GIL 复活） |

## 四、依赖可装性矩阵（口径已修正两次）

**★判定口径**：必须用 `pip install --dry-run --only-binary=:all: --no-deps <pkg>`。

- `pip index versions` **不按 ABI 过滤**，会把只有 sdist 的包误报为可用——首轮探测因此把 29/29 全报成可装，实际只有 22 个真有轮子。

### 8.2 四刀

**刀9（`b70bd06d`）— 469/470 重复告警去重**
同一次失败必报两条 WARNING（470 给「期望方法名 vs 实际方法名」，469 给 organ/type/loc），
实测 28 对 28 条一比一重复。两条信息**互补**，删任一条都丢线索 ⇒ 只让重复的那条降级：
`how == "modified_other_method"` 且 470 严格开关开 ⇒ 469 降 INFO 并在尾部注明
「详细判据见上一条 470刀1」；开关关掉时 470 不打日志 ⇒ 469 自动回 WARNING（不丢可观测性）。
`None` / `0` 一律按显式假处理（不走 `or 默认值`）。

**刀10（`bfb7e465`）— `safe_http_json` 补 `TimeoutError` 分支（本批唯一真 bug）**
该函数只有 `HTTPError` / `URLError` / `(ValueError, JSONDecodeError)` 三个 handler，
而读超时抛的 `TimeoutError` 是 OSError 的子类、却是 `URLError` 的**兄弟而非子类**
⇒ 三个 handler 全接不住 ⇒ 异常穿透，打破「一律返回 `(bool, data)`」的契约。
三份轮转日志里 51 条 `[LLM修复] …降级返回 None` **100% 都是**
`TimeoutError: The read operation timed out`。

穿透的后果才是要修的东西 —— 它们绕过了 465 的失败记账三件套：
`_m465_last_fail` 无归类、`_m465_fail_streak` 不累加（**同轮熔断永不因超时开启**，
同一轮连打多次 LLM 每次都等满 30s）、不走 `_m451` 的「连续 3 次才 WARNING」限流。

在 `ssrf_guard` 补分支后，超时自然流入既有的「调用未返回可用结果」通道，
**自动获得**归类 / 连击熔断 / 限流日志 / 渠道健康度回写，零新增记账代码。
归类仍记 `error`（不改 `_m465_fail_kind` 的既有规格，其单测明确钉住
`<urlopen error timed out> ⇒ error`），且 465 明文「超时**不换道**」——换到另一个慢渠道
只会把本轮耗时成倍拉长，本刀严格照此执行。灰度 `ENABLE_M473_HTTP_TIMEOUT_AS_RESULT`
关掉即 `raise` 逐字回滚。

**刀11（`c79371bd`）— 470刀1 两类诊断日志连击限流（134 条）**
这两类描述同一个可预期现象：LLM 补丁不合格（改名 / original 与 body 不等），

**刀12（`831e7add`）— 问题过滤告警按 (file+type) 聚合（28 条）**
`19:55:19` 与 `20:22:39` 各自同一秒打 10 条，全是

### 9.2 根因：一处调用，两处人工

`PulseInnerWorld._check_auto_upgrade` 的 win32 分支：

```python
ctypes.windll.kernel32.GenerateConsoleCtrlEvent(0, 0)
```

第二个参数为 `0` ⇒ 接收方是**与该进程共享同一控制台的所有进程**。于是：

1. `cmd.exe`（`start_tongtong.bat` 那一层）也收到 ⇒ 弹「**终止批处理操作吗(Y/N)?**」；
2. Python 自己的 SIGINT 处理器把 `user_quit_requested` 置 True ⇒ 退出路径改走
   `_confirm_apply_pending_on_quit` ⇒ 有 approved 补丁时再弹
   「**是否应用并重启验证？(Y/n，默认 Y)**」。

**脚本不是元凶**。直接 `python main.py` 时没有 cmd 这一层；换成 .bat 启动后，
控制台里多了一个 cmd.exe，"打整个进程组"的写法才第一次伤到自己人。
两个提示都不是曈曈在问业务问题，而是它在向**自己的启动器**开火。

### 9.3 处置

新建 `nucleus/evolution/graceful_apply.py`，把「应用并重启」的请求改走既有的
`data/evolution/apply_now.json` 通道（与 `EvolutionLoop`「验证通过即应用」同一条）：

```
IW 自动升级 → request_upgrade_apply() → apply_now.json
             → 主循环（每 10 拍）→ apply → framework.stop() → _spawn_self_restart(独立控制台)
```

全程不发控制台信号 ⇒ 不惊动 cmd.exe；也不置 `user_quit_requested` ⇒ 不弹补丁确认。

细节：
* 已有在途请求 ⇒ **不覆盖**（覆盖会刷新 `requested_at`，失去排队语义）；
* 同批补丁 **900s** 内不重复写（维护窗口 03:00-04:00 不该反复刷盘）；
* 灰度 `ENABLE_M473_UPGRADE_APPLY_NOW=False`、写盘失败、驱动异常 ⇒ 逐字回退旧
  `GenerateConsoleCtrlEvent(0, 0)`（保留在同一模块的 `_m473_legacy_console_ctrl_c`）。

**为什么不用 `shutdown_request.json`**：它被 `orchestration_exit_blocked_by_patches`
拦（存在 approved 补丁就不让退出），而本场景恰恰**就是**有 approved 补丁 —— 用它必然自锁。

**为什么新逻辑放独立模块**：`PulseInnerWorld.py` 受 cw3-A 语义守恒门禁（11 个 AST 计数）锁定。
独立成模块后，IW 侧只是"一行调用换一行调用"，不新增 `if/try/return/raise`
⇒ 守恒量零漂移，**不需要重锚基线**（实测 `[OK] 硬门禁指标全部一致`）。

## 十、刀15：入队缩进补偿 —— 自主进化闭环的**真正**断点

> 起因：准备批准池里那条 `verified` 补丁（`patch_llm_1793968480_715f`）时先做了体检，
> 发现它一旦落地会把 `PulseMetricsCollector` 的 56 个方法变成死代码。
> 顺着查下去，发现这不是一条补丁的问题，而是**所有**类方法补丁都被同一个环节改坏。

### 10.1 病灶：`_m323_reindent` 把完整方法也左移到 0 格

`PatchManager._m323_reindent`（3348 行）的职责是「剥掉生成片段的前导公共缩进」——
设计初衷是防**片段**被整块缩进时写出 IndentationError。但它不区分「片段」和
「含 def 的完整方法」，于是：

```
LLM 输出（正确）      入队后（存盘）
    def target(self):  →  def target(self):
        return 1              return 1
```

而入队前 `original_code` 是从真实文件读的，仍是 4/8 格 ⇒

```
base(modified) = 0  ≠  base(original) = 4/8
```

验证侧（`_verify_in_copy:4934`）与应用侧（`apply_all_pending:6472`）各有一道
`_m92_base_indent_guard`，296 批已置 `True`，**两侧都会拒**。

### 10.2 硬证据：4 条 approved 全部落不了地

| 补丁 | 文件 | 状态 | 结局 |
|---|---|---|---|
| `patch_multi_1793659423_682b` | `PulseLiver.py` | approved | applied=False · `original=8 modified=0` |
| `patch_llm_1793945467_7587` | `PulseHeart.py` | approved | applied=False · 同上 |
| `patch_llm_1793991409_5a9b` | `PulseLegs.py` | approved | applied=False · `original=4 modified=0` |
| `patch_llm_1793968322_7fee` | `PulseSubconscious.py` | approved | applied=False · 核心闸门 |

全库统计（`data/patches/*.json`）：带 `m323_truth` 的补丁 192 条，其中
`reindented=True` **12 条，12/12 的 base 都被改坏**。

**这修正了 470/471 的结论**：那时判断「瓶颈在入池额度 + 人工裁决」，
实际情况是——**批了也落不了地**。审批不是最后一道门，缩进是。

### 10.3 后果不止"应用失败"：结构会塌，而语法仍然合法

照应用器的方式（`full_content.replace(original, modified)`）对池里那条补丁离线实测：

```
替换前  PulseMetricsCollector 类方法数 = 79
替换后  PulseMetricsCollector 类方法数 = 22
        后面 56 个方法被塞进零缩进 def 的**函数体**，成为永不执行的嵌套 def
        （_m382_resource_probe / _m350_live_gate_tick / _m343_release_heartbeat /
          _m366_inventory_tick / _m364_leaderboard_tick / _m360_paid_usage_tick …）
        ast.parse 仍然成功 —— 语法合法、结构全塌
```

现有两道守卫拦得住（所以生产没出事），代价是**所有类方法补丁一律被拦死**。
这才是「补丁链 degraded：`apply==0 and queue>0`」的机械原因。

### 10.4 改动

```
nucleus/reasoning/PatchManager.py
  + _m473_realign_on()       灰度读取（缺省 True；不用 or，False 必须能生效）
  + _m473_shift_indent()     整体平移；跳过三引号字符串内部续行
  + _m473_realign_indent()   只对「两侧都含 def 且 base 不等」的整方法补偿
  ~ _m323_normalize_patch    在 ast.parse 之后调用补偿
config.py
  + ENABLE_M473_REINDENT_REALIGN = True
```

三条不可换的设计点：

1. **不动 `_m323_reindent` 本身**。它还有 3 个调用点语义各不相同
   （`_m323_ast_def_name` 解析重试 / `_m445_wrap_fragment` 取 body / 入队归一），
   改它等于同时改三处。本刀只在**入队这一个消费点**加补偿。
2. **补偿必须在 `ast.parse(_code)` 之后**。那个 parse 校验的是左移后（0 缩进）的
   LLM 原文；补偿后是 4 格类方法，单独 parse 必 `unexpected indent` ⇒ 放在前面会
   给每条正常补丁刷一条假 WARNING 并把 `parse_ok` 置 False（第一版踩了，已改，实测归零）。
3. **补偿不回写 `_code`**。`_code` 只用于 `_m323_ast_def_name` 取 def 名，
   保持 0 缩进可直接 parse；存盘走 `patch["modified_code"]`。

字符串安全：三引号内部续行**不平移**（那里是字符串内容，平移等于改语义），
不平移也不影响语法；`tokenize` 失败 ⇒ 原样返回（宁可不补偿，也不猜）。

### 13.2 先把 y/n 的归属说清（它根本不是曈曈弹的）

**y/n 是 cmd 对 `.bat` 的提示**。走 `start_tongtong.bat` 时 Ctrl+C 打到 cmd，
cmd 追问「终止批处理操作吗(Y/N)」。直接 `python main.py` 就没有 ——
Ctrl+C 直达 Python ⇒ SIGINT ⇒ `signal_handler` ⇒ `exit_requested=True` ⇒
主循环退出 ⇒ finally 六步清理。**这条不用改代码，改的是启动方式。**

### 13.3 `python` 为什么是 3.12：卡在机器级 PATH

```
where python  →  D:\Program Files\Python312\python.exe
                 C:\Users\...\WindowsApps\python.exe   (0 字节存根)
```

`Python312` 在 **Machine PATH** 的第 2/3 段。Windows 的进程 PATH = Machine + User，
**用户级永远排在机器级之后** ⇒ 只改用户 PATH 覆盖不了它。而
`D:\Program Files\Python314t` 里只有 `python3.14t.exe`，**没有 `python.exe`**
（free-threaded 官方安装包不提供，它不能抢占默认名）。

|---|---|---|
| 1 | 复制 `python3.14t.exe` → `python.exe`（同目录，同一二进制按 `python314t.dll` 找库） | `python` 有名字可指了 |
| 2 | Machine PATH 最前插入 `D:\Program Files\Python314t` + `\Scripts` | `python`/`pip` 都归位 3.14t |
| 3 | `Lib\site-packages\0_tongtong_env.pth` + `_tongtong_env.py` | TEMP/PIP_CACHE/PLAYWRIGHT 钉 D 盘，且只影响 Python |

**改完实测**：

```
import main → OK 2.3s（numpy/cython/psutil/requests/jieba/chardet/neo4j/sounddevice 全通过）
```

### 13.5 四个坑（每个都真实踩过一次）

1. **不能用 `setx` 改 PATH**。`setx` 写 `REG_SZ`，把原值的 `ExpandString`
   降级 ⇒ `%SystemRoot%\system32` 不再展开 ⇒ 系统命令全找不到。
   必须走注册表 API 并显式指定 `-Type ExpandString`（改完复核类型仍是 ExpandString、
   `%SystemRoot%` 字面保留）。
2. **`sitecustomize` 会被抢**。本机 `PYTHONPATH` 里有 WorkBuddy 的 shim 目录，
   `site.py` 的 `execsitecustomize` 先 import 到 shim 的那份 ⇒
   自己写的 `sitecustomize.py` 完全不执行（`import sitecustomize` 显示的是 shim 路径）。
3. **`tempfile` 的缓存比 `.pth` 更早**。`distutils-precedence.pth` 在 site 阶段
   import `_distutils_hack`（间接 import `tempfile`），此时 TEMP 还是 C 盘 ⇒
   `tempfile.tempdir` 被定死成 `C:\Users\...\Temp`。即使 `.pth` 抢到排序最前、
   甚至把缓存打回 `None` 都无效。唯一可靠做法：**由自己的模块主动
   `import tempfile` 再赋 `tempfile.tempdir`**，当"第一个加载者"。
4. **`pip.exe` 的 launcher 指向 C 盘**。`D:\Program Files\Python314t` 是从
   `C:\Users\...\Local\Python\pythoncore-3.14t-64` 复制来的，`Scripts\pip.exe`
   保留了原 shebang ⇒ `pip install` 会把包装到 C 盘那个环境（而 `python -m pip`
   是对的，两者不一致）。重装一次 pip 即可重建 launcher（已备份原 3 个 exe）。

顺带确认：`site-packages` 里的 `pip`/`numpy` 都是**真实目录**（不是 junction），
包确实在 D 盘。

`env` 打 `PULSE_SELF_RESTART_CHILD=1`；② main.py 模块级把接班进程输出重绑回
自己的 `CONOUT$`，失败就继续用文件句柄（打印绝不拖死框架）。

**刀22b**：落地补丁的原子写逻辑是对的，但 LLM 丢了 docstring/类型注解、
