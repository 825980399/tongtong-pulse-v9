## 三、刀1 施工（`87ae117f`）：L4 因果强度判定

### 3.1 三指标定义

落盘 `data/monitor/causal_strength_YYYYMMDD.json`，`schema = "causal_strength/404.v1"`。窗口沿用既有 `WINDOW_S`（3600s，与 `build_chains` 同源），链判定口径与 `build_chains` **严格一致**（同器官相邻 emit gap<1s、跨器官同 `pulse_id` 且 gap<5s），差别只在于本函数额外按时间段分桶计数：

| 指标 | 真实字段名 | 定义 |
|---|---|---|
| 频次 | `count` | A→B 在该窗口内出现次数 |
| 条件概率 | `p_b_given_a` | `count(A→B) / A 的全部出链数`；分母为 0 时给 `None` 而非 0（不假装观测到） |
| 反向条件概率 | `p_a_given_b` | `count(A→B) / B 的全部入链数`（同一思路刀2 回放也用：`P(本\|经)` 按入链总数归一，两处口径一致但各算各的） |
| 时间衰减 | `weighted_count` | `base_count × 1.0 + recent_count × 2.0`，按**链的完成时刻**（B 的 ts / receive 的 ts）分桶；`recent` 判据为 `ts >= now - 600` |

每条边另带 `recent_count` / `base_count`（分桶明细）与 `gap_ms_p50`（链路时延中位数），读方不用自己再算。同器官边的键是 `from`/`to`（事件对），跨器官边的键是 `from_organ`/`to_organ`/`event`/`from_event`。

> **一处刻意保留的粒度差异**：刀1 的同器官边按**事件对**聚合（键 `(from_event, to_event)`，不含器官），刀2 回放用**器官::事件**复合键。前者回答「哪类事件转移最常发生」，后者回答「这个具体事件从哪个器官流到哪」。两者粒度不同，所以交叉断言只对 `totals` 层的 `same_organ_links` / `cross_organ_links` / `unmatched` 做对平，不对明细行求等。

常量：`RECENT_WINDOW_S = 600.0`、`RECENT_WEIGHT = 2.0`、`BASE_WEIGHT = 1.0`、`STRENGTH_TOP_N = 50`（每类各取 TOP 50，不是合计 50）、`STRENGTH_MIN_GAP_S = 3600.0`、`STRENGTH_HOOK = "causal_strength_daily"`。

排序：`weighted_count` 降序，同权重看 `count`，再按名字定序（保证同日两次跑结果稳定可比）。`totals` 里给 `same_organ_links` / `cross_organ_links` / `same_organ_distinct` / `cross_organ_distinct` 四个计数，读方能自己判断「50 条是全部还是被截断」——`distinct > 50` 即截断。

### 3.2 挂点

`main.py` 里紧跟 `register_organ_emits_schedule()`（16 空格缩进，与既有 03:00 挂点同层）：

```python
# ★404刀1：L4 因果强度判定——与 organ_emits 同一 03:00 挂点，
#   落 data/monitor/causal_strength_YYYYMMDD.json（频次/条件概率/时间衰减）。
from utils.causal_chain import register_causal_strength_schedule
register_causal_strength_schedule()
```

`register_causal_strength_schedule()` 内部用 `add_daily_hook` 挂进 `DailyScheduler`，调度器不可用 / 不支持每日钩子时 `return None`（不影响启动）。

**判重口径**（`run_strength_daily`，写进 docstring 以便后人）：
> **当日文件存在且 `age < STRENGTH_MIN_GAP_S`(3600s) ⇒ 跳过**。不用内存变量判重 —— 403 批的 `_LAST_RUN` 在进程重启后归零，实测同一小时被写了两条汇总。且判重用**墙钟** `time.time() - mtime`，不用传入的 `now`：文件 mtime 永远是系统时间，用 `now` 比较会在「补跑历史窗口」（`now` 与系统时间偏离）时恒不命中，表现为同一天被反复重写。

落盘走 `_write_json_atomic()`（tmp + 3 次退避 replace）——403 刀4 的 `WinError 5` 教训复用，不新写一套原子写。

落盘结构：`schema` / `kind=daily_strength` / `day` / `generated_at` / `window_s` / `rule`（阈值自描述，含三指标的口径说明）/ `source`（读了哪个文件、多少字节、是否截断、跳过几行）/ `totals` / `same_organ` / `cross_organ` / `note="只计算不告警"`。`source` 段是**为了不假装读全**：尾部窗口读法在大文件上必然截断，截断与否必须落在产物里。

### 3.3 只计算不告警

按要求不接任何告警通道。`run_strength_daily()` 全程无 `emit`、无 `logger.warning`，失败只 `silent_exc(..., level="debug")` 并返回 `None`。

## 四、刀2 施工（`2e4ee426`）：L7 记忆回放接口

### 4.1 ★ 一版方案被真实语料整刀推翻

v1 按**裸事件名**建图（`A -> B`）。真实语料一跑就崩：

```
graph: events=25 edges=31 skipped=211
```

`眼睛 -> 血管 / 视觉皮层` 这条最大流整条消失，`eyes.stream_frame` 只剩自环，单脉冲回放返回 `empty_reason='pulse_not_observed'`。

**根因（实测两条，不是推测）：**

1. `pulse_pairs` 的 receive 行里 `event_type` 是**发送方的那个事件**。实测 7010 行，缺失率 **0.0%**。
2. 跨器官链 5360 条，`from_event == event` 的 **5360 条，不同 0 条**（100%）。

⇒ 跨器官投递根本不是「事件 A → 事件 B」，而是「**同一事件从器官 A 送到器官 B**」。按裸事件名建图，所有跨器官边两端同名 ⇒ 全被判成自环丢掉（实测丢 211 条边）。

### 4.2 修正后的模型：节点 = `器官::事件`

一张图同时装下两类边，零丢边：

| 边类型 | 两端 | 语义 |
|---|---|---|
| `cross_organ` | `(A, e) -> (B, e)` | 投递事实：e 从器官 A 送到器官 B |
| `same_organ` | `(A, e1) -> (A, e2)` | 同器官相邻两次 emit 的顺序（gap < 1s 开区间） |

`REPLAY_NOTE` 把这个语义边界写进返回值，防止读方把「投递」误读成「因果产出」：

> 跨器官边 = 投递事实（X 从 A 送到 B），不是 B 因 X 产出了新事件；同器官边 = 同一器官相邻两次 emit 的顺序。只回放 pairs 能直接证明的关系。

### 4.3 真实语料读数与交叉断言

取 10-30 尾部 3600s：

```
graph: events=44 organs=57 nodes=228 edges=240
       same_links=275 cross_links=4695 unmatched=1417 dup_recv=0 no_name=107 below_min=0
交叉断言 same_links  275 vs 275 PASS
交叉断言 cross_links 4695 vs 4695 PASS
交叉断言 unmatched   1417 vs 1417 PASS
```

三项断言是拿 `build_chains()` 的既有产物逐一对平——**不是自己数自己**（403 批栽过 `TestAggregate` 空转）。

单脉冲回放（pid=…6112）：

```
起点：眼睛::eyes.stream_frame / 血管::eyes.stream_frame / 视觉皮层::eyes.stream_frame
上游 1 节点  P(经|本)=1.0
下游 2 节点  各 P(本|经)=0.5     ← 条件概率天然修正「一发射两接收」
```

`max_depth` 行为实测：

| max_depth | up | down | truncated_depth |
|---|---|---|---|
| 1 | 1 | 1 | True |
| 2 | 2 | 2 | True |
| 5 | 3 | 4 | False |

`truncated_depth` / `truncated_breadth` 两个标志是显式的——「只回了 3 层」必须能与「只有 3 层」区分开，否则读方会把截断当成事实边界。

### 4.4 环处理

BFS 中每个节点只在**最小深度**展开，重复到达的标 `back_edge` 并记入 `cycles`，不重复展开。否则一对互相投递的器官会成为无限链。

### 4.5 不新增文件

`_scan_chain_history()` 只读既有 `causal_chains_YYYYMMDD.jsonl` 与 `pulse_pairs`，不写任何新落盘（判据里有专门的「无写盘调用」断言，用 `"json.dump(" in text` 而非 `"json.dump"`——后者会匹配到 `json.dumps`，本批踩过）。

### 5.1 三态与整体判定

| 单层 | 含义 | 进程退出码贡献 |
|---|---|---|
| `PASS` | 该层健康 | — |
| `FAIL` | 该层有实证缺陷 | 1 |

## 六、刀3 补丁（`82ce4cd1`）：L5 假阳性返修

### 6.1 事故现场

刀4 提交时门禁自己报的：

```
L5  FAIL  健康快照      快照年龄 7100.7s > 上限 90s（框架在跑但快照不更新）
```

核查：`psutil` 枚举全机 `main.py` 进程数 = **0**。盘上根本没有框架在跑。

### 6.2 根因

`is_framework_running()` 按「cmdline 里有 basename == `main.py`」匹配。而正在执行的那条命令是：

```
git commit -F tmp/m404_k4_msg.txt -- main.py utils/causal_chain.py ...
```

**提交命令自己的命令行里就含 `main.py`** ⇒ 判据返回 True ⇒ 面板认定「框架在跑，快照却不更新」⇒ FAIL。

同类假阳性还有：`python -m py_compile main.py`、编辑器把 `main.py` 当文件参数打开。

### 6.3 修法：pid 是硬证据，枚举降级为线索

新增 `_probe_pid_is_framework(pid)`：`psutil.pid_exists` → `Process(pid).cmdline()` → 复用 `_cmdline_is_framework_main()`（此刻 cmdline 是**真实进程**的，不会被提交命令骗到）。

`check_l5` 改三步制：

```python
if _snap_age <= _max:
    return _ok("L5", ...)          # ① 新鲜就 PASS，不问进程（省钱且不误报）
```

### 7.1 窗口标题

`main.py` 新增三个函数，`__main__` 块在 `main()` 前调用：

```python
def _console_title_text(pid=None, started_at=None):
    """窗口标题文本：``曈曈 pid=1234 启动于2026-10-30 19:52:31``（纯函数，便于判据核对）。"""
    _pid = int(pid if pid is not None else os.getpid())
    _ts = float(started_at if started_at is not None else time.time())
    return "%s pid=%d 启动于%s" % (_CONSOLE_TITLE_PREFIX, _pid,

```

`_set_console_title()` 走 `ctypes.windll.kernel32.SetConsoleTitleW`（设窗口标题的唯一途径），仅 win32，失败 `return False` 不抛。判据里有一条**真调 API 往返并还原原标题**的用例，不靠 mock 自证。

标题拆成纯函数 + 副作用两段，是为了让「格式对不对」能脱开控制台单测——本批 `test_17` 就吃过「`mock.patch("ctypes.windll", side_effect=...)` 只让属性访问抛、没触发异常路径」的假通过。

### 7.2 `restart_notice.txt` 与**时序差异**

`_write_restart_notice(project_root, parent_pid, child_pid, reason="self_restart")` 写 `data/restart_notice.txt`，`newline="\n"`（台账类文本按 LF 消费，Windows 文本模式会翻 `\r\n`），失败 `return None` 不抛。

**★ 与任务书的时序差异（如实记录）**：任务书写「重启**前**写」，本实现写在 `_spawn_self_restart()` 里 `Popen` **之后**、`_SELF_RESTART_CHILD_PIDS.add(_proc.pid)` 之后。

原因：接班进程的 pid 只有 `Popen` 返回后才存在，「前」写拿不到 pid，写出来的 notice 就是缺了最有用那一项。它仍然写在**父进程退出之前**，所以「重启发生时盘上有便条」这个目的完全成立。

便条是**人读的五行纯文本**（不是 JSON）：时刻 + `曈曈自重启`、`父进程 pid=… → 接班 pid=…`、`原因：…`、`接班窗口标题：…`、一行来源说明；每次重启覆盖。放 `data/` 而非「`runtime.lock` 旁边」，是因为 `runtime.lock` 全仓无创建代码（§二 #1），无法作为锚点；`data/` 与真实控制文件 `shutdown_request.json` 同目录，语义一致。

### 7.3 `scripts/stop_tongtong.py`（119 行）

- `list_framework_pids()` 复用 `nucleus.evolution.night_orchestration._cmdline_is_framework_main`，与框架自身判据同源（不另写一套）。
- `main()` **委托** `tools/night_orch_shutdown.py`（164 行，退出码 0/1/2/3 已定型），只加 `--dry-run / --reason / --timeout` 三个薄参数。
- **明确不发 `os.kill` / `SIGTERM`**：真实优雅退出通道是 `NightShutdownChannel`（写 `data/shutdown_request.json`），强杀会让快照、台账、因果链落到半截。
- **不复制核心实现**：`tools/night_orch_shutdown.py` 与 `nucleus/evolution/night_orchestration.py` 已各有一份通道逻辑，`scripts/` 再加第三份，将来改通道必然漏改一处。这条写进了判据：`assertNotIn("os.kill", src)`（不许发 SIGTERM/SIGKILL——Windows 不可靠且会跳过 `finally`）+ `assertNotIn("psutil.Process(", src)`（停止必须走 `shutdown_request` 通道，不强杀）。
