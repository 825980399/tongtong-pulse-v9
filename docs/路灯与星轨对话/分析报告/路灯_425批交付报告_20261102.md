### 2.2 改了什么

**改动 A：`_m68_verify_parquet` 拆成「footer 快路径 + 原深路径」**

```python
try:
    _fast = self._m425_verify_parquet_meta(_pq68, _base, _req, _exp_ver)
    if _fast is not None:
        return _fast
except Exception as _e:
    silent_exc(_e, where="PulseSnapshot._m68_verify_parquet[425刀1-快路径转深校验]")
return self._m68_verify_parquet_deep(_pq68, _base, _req, _exp_ver)
```

三项校验**逐条等价**（不是放宽）：缺列→`schema.names`、版本→`key_value_metadata`、塌缩→`num_rows`，
这三样全在 Parquet footer 里。快路径抛异常（footer 本身坏了）才回退 `read_table` 深校验。

**改动 B：`_m67_full_checkpoint` 在 `save_parquet()` 之后补校验**

原来只有 `_full_save` 里校过一次 Parquet，而那是在 `save_parquet()` **之前** ——
校的是**上一轮**的档；新写出来的这份从未被校验，可「清空 `snapshot_incremental.jsonl`」
的依据偏偏就是它。现在改成：

```python
_parquet_ok = bool(self.save_parquet())
...
if _parquet_ok:
    _new_rows = self._m68_verify_parquet()      # 校验刚写出来的这份
    if _new_rows < 0:
        _parquet_ok = False                      # 不清 jsonl，保留可重放账本
```

**改动 C：阶段计时**（`json写 / parquet写 / 校验` 三段进日志），下次再慢能直接定位。

**改动 D（自纠）：`ParquetSchema.names` 是物理叶子列名，不能用来判「缺列」**

等价性验证第一轮就抓到了：正常生产档快路径判 **-1（缺列）**，深路径判 **14575（通过）**。
根因是 `pq.read_metadata(f).schema.names` 返回的是**扁平的物理叶子列名**：

```
L1 分片：物理叶子 45 列 / arrow 顶层 37 列
  物理里多出：relation_type / target_node_id / established_at / element / detail / role / source / timestamp
  物理里缺的：semantic_relations / keywords / linked_nodes / evidence_chain / verification_history
```

嵌套 list/struct 被展开后，**内部字段名冒充列名、顶层列名反而消失**。
改用 `to_arrow_schema().names` 后与 `read_table` 完全一致（35 个必需列，缺失 0）。

> 这条如果没做等价性验证就上线，会在**每次全量**都误报「缺列 5 个」并打 ERROR，
> 而 Parquet 其实是好的 —— 属于「优化引出假告警」，比不优化更糟。

## 三、刀2：hit_rate 小时报（日报保留）

### 3.1 现状

| 项 | 值 |
|---|---|
| 采样 | `sample()` 挂在 `time.tick` 上，**每 60s 一次**（`main.py:822`，410刀3） |
| 日报 | `write_report()` 只在 04:00 `generate_night_digest` 里调用一次（`night_orchestration.py:588`） |
| 日报路径 | `data/world_model/hit_rate_YYYYMMDD.json` |
| 状态 | `hit_rate_state.json`，`hours[event_type] = [[hour_ts, hit, miss, no_coverage], ...]` |

原始数据本来就是**按小时分段**的（`_hour_of()` + 同小时累加到 `_segs[-1]`），
所以「本小时」不需要另做差分 —— 取 `ts == 本小时起点` 的那一段就是净增量。

### 3.2 改了什么

新增（`nucleus/world_model/hit_rate.py`，+164 −7）：

```
hourly_enabled()         开关（复用 ENABLE_M410_HIT_RATE_ALERT，叠加本批开关）
hourly_key()             "20261102_15"
hourly_report_path()     data/world_model/hit_rate_hourly_20261102_15.json
_hour_slice()            取本小时各类型增量（ts == hour_of(now) 的那一段）
hourly_report()          只四样：hit / miss / hit_rate / top，另附 rolling_24h 供对账
write_hourly_report()    原子写（temp + os.replace），本小时已存在且非 force → None
maybe_write_hourly()     sample() 里调用的入口
```

挂载点（`sample()` 的 `save_state()` 之后、`return` 之前）：

```python
save_state(_st)
_out["windows"] = int(_st["windows"])
try:
    _hp = maybe_write_hourly(_now, state=_st)   # 跨小时才写一份
    if _hp:
        _out["hourly_report"] = _hp
except Exception as _exc:
    silent_exc(_exc, where="world_model.hit_rate.sample:hourly", level="warning")
return _out
```

三条设计取舍：

1. **不新建调度器** —— 挂在已有 60s 广播上（和 410刀3 挂世界模型对账同一套做法），
   多一个订阅方就多一条要收尾的生命周期。
2. **幂等靠文件名**，不额外存「上次写入小时」的状态字段 —— 少一个字段就少一处会和文件不同步的地方。
3. **日报一字未动** —— 文件名前缀 `hit_rate_hourly_` vs `hit_rate_`，物理上不可能覆盖。
