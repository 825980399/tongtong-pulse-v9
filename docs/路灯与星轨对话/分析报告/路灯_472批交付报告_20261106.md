# 路灯 472 批交付报告（2026-11-06）

> 触发：用户观察到「曈曈没有输出，以为卡死所以退出」。
> 结论：**不是卡死，是进程被自己拆成了僵尸态**——周期 apply 先 `framework.stop()`
> 再尝试应用补丁，补丁被核心闸门拦下（applied=0）后既不重启也不退出。
> 本批四刀：1 个 P0 事故根因 + 3 个台账核实为真的断点。

### 1.3 看门狗全程知情却无法处置


原因链：`stop()` 把 `is_running` 置 False ⇒ `_trigger_heartbeat` 第一行
`if not self.is_running: return` 直接返回、**不排下一拍** ⇒ 租约接管逻辑写在
`_trigger_heartbeat` **内部**，永远进不来；看门狗去 `_schedule_next_beat()` 又看到
「在途 Timer 还活着」⇒ 静默放弃。**它只能续链，不能重新 start 一个被停掉的器官。**

### 1.4 真因（代码）

`main.py::_m422_periodic_apply_tick` 旧顺序：

```python
framework.stop()                                     # ① 不可逆地拆系统
_restarting = _apply_pending_patches_and_restart()   # ② 再试 apply
if _restarting: return "applied_restarting"          # ③ 成功才重启
return "applied_no_restart"                          # ④ 失败 → 系统已拆，进程留下
```

同一个 bug 在「立即应用请求」路径（`main.py` 主循环内）还有一份：先 `stop()` 再 apply。

> **这不是 GIL 问题。** 三条反证：主循环节拍全程正常、stdin 两条消息都读到了、
> 进化线程大量时间在等 LLM（22.5s 的 zhipu 调用）。GIL 争抢只会让对话变慢，
> 不会让一条消息 4 分钟无响应——真正的失效是**系统已被拆除**。
> 「主进程 + 多子进程」方向没错，但收益是**爆炸半径隔离**，不能替代这个修复：
> 逻辑不改，拆进子进程照样僵尸，只是死的是子进程。

## 二、本批四刀

### 刀1（P0）· 周期 apply 改为「先 apply，成功才停机」

**文件**：`main.py`（4 处）

| 位置 | 改动 |
|---|---|
| `_apply_pending_patches_and_restart` 签名 | 新增 `defer_spawn: bool = False` |
| 同函数 spawn 段 | `defer_spawn=True` 时把「拉起接班进程」交给调用方 |
| `_m422_periodic_apply_tick` | apply 成功才 `stop()`；失败原样返回，系统不动 |
| 主循环「立即请求」分支 | 同样的顺序反转 |

新逻辑：

```python
_restarting = bool(_apply_pending_patches_and_restart(framework, defer_spawn=True))
if not _restarting:
    return {"status": "applied_no_restart", ...}     # 系统一根毫毛都没动
try:
    framework.stop()                                  # 此刻才停机
except Exception:                                     # 停机异常也必须继续
    ...
_spawn_self_restart(reason="m422_periodic_apply")      # 补丁已落地，必须重启才生效
```

**为什么不直接把 spawn 也留在这里**：`_spawn_self_restart` 用 `CREATE_NEW_CONSOLE`
立即拉起新进程，如果父进程还持有端口/文件锁，新旧进程会抢资源。所以顺序固定为
**apply → stop（释放资源）→ spawn**，由同一个调用方串起来。

**单测**（`tests/test_m422_k3_periodic_apply.py`，新增 6 条）：

| 用例 | 判据 |
|---|---|
| `test_17_apply_fail_does_not_stop_system` | apply 未落地 ⇒ `stopped == 0`（核心） |
| `test_18_apply_fail_does_not_spawn` | 未落地不拉接班进程 |
| `test_19_order_is_apply_then_stop_then_spawn` | 事件序列必须是 `["apply","stop","spawn"]` |
| `test_20_stop_exception_still_spawns` | stop 抛异常仍 spawn |
| `test_21_spawn_failure_still_signals_restart` | 接班起不来也返回 `applied_restarting` |
| `test_22_apply_defer_kwarg_is_true` | 源码级：两处调用都显式 `defer_spawn=True` |

同时按铁律 65/117 升级了旧桩（`lambda fw:` → `lambda fw, **kw:`）并给
`_spawn_self_restart` 打桩——**否则新路径会在单测里真的 Popen 一个 python 进程**。

### 刀2 · 补丁验证子进程不再继承父环境（台账 S6 / F1）

**文件**：`nucleus/reasoning/PatchManager.py`

旧状：`execute_code_in_subprocess(...)` 不传 `child_env` ⇒ `Popen(env=None)`
⇒ 子进程**完整继承父环境**，其中 `PULSE_FRAMEWORK=1` 正是
`nucleus/data/write_guard.py` 判定「可信写入者」的凭据。
也就是说：**被验证的陌生补丁代码，在验证期能写生产 `data/`**。

修法：新增 `_M472_CHILD_ENV_ALLOWLIST` + `_m472_build_child_env()`，
与 `nucleus/review/ScriptExecutor.py::ENV_ALLOWLIST` 同源，
并在最后**无条件剥离所有 `PULSE_*`**（白名单不是免死金牌）。

**单测**（`tests/test_m472_knife2_child_env.py`，10 条）关键判据：

- `PULSE_FRAMEWORK=1` 在环境里时，构造函数输出**不含**它；
- 即使把 `PULSE_FRAMEWORK` 写进白名单，仍被剥掉（兜底语义）；
- `OPENAI_API_KEY` 这类凭证默认 deny；
- **两份白名单逐项相等**（`test_08`）——这是治 F 类「修一半」的根治判据，
  以后谁只改一处，这个测试会红。

### 刀3 · 快照三处 remove→replace 改纯原子覆盖（台账 D3 / F2）

**文件**：`nucleus/mnemosyne/PulseSnapshot.py`（3 处）

主路径第 80 批 T4 早就改对了（`:923` 附近注释写明「前置 os.remove 冗余且目标被锁时
会抛错」），但 L1 保存、L1 精简、主快照 compaction 三处漏改：
`os.remove(旧档)` 之后 `os.replace(tmp, 目标)`——中间那段窗口进程一死，**快照就没了**。

**单测**（`tests/test_m472_knife3_snapshot_atomic.py`，6 条）：
把 `os.replace` 打桩成抛 `OSError`，断言**旧档仍在且内容原封不动**
（旧代码下旧档已被 remove 删掉）。台账指出 `l1_snapshot_path` 在 `tests/` **0 命中**，
这条用例补的就是这个缺口。

### 刀4 · 紧急处理链两处断点（台账 C1 + C2）

**C1 `organs/core/PulseHealthMonitor.py`**

能量唯一写入方 `PulseEnergyMetabolism._update_energy`：

```python
self._energy_level = max(0.1, 1.0 - load_factor)   # 值恒 >= 0.1
```

消费方判定 `if el < self._thresholds["energy_critical"]`（阈值 0.1）——
**数学上恒 False**。CPU 与内存同时打满也只能得到 0.1，L3「危急」分支永远不走。
改 `<=`：触底即危急（语义也正确）。

**C2 `organs/senses/PulseTouch.py`**

`hardware_critical` 的 payload 缺 `level` 字段，消费者
`PulseEmergencyHandler._on_alarm` 第一行 `payload.get("level", "L1")` 拿到 L1，
紧接着 `if level not in ("L3","L4"): return` 直接早退：
**磁盘 96%、CPU 打满这种 priority=10 的告警永远进不了恢复链，只剩一行日志**。
补 `"level": "L3"`。

> 这个修法有硬证据：`PulseEmergencyHandler.py` 文件末尾的自测用的正是
> `{"level": "L3", "type": "hardware_critical"}` —— 设计意图一直是 L3，
> 只是实现漏了这个字段。单测 `test_07` 把这条交叉验证钉住了。

**单测**（`tests/test_m472_knife4_emergency_chain.py`，11 条）：
能量 0.1 → `critical`；0.11 → `warning`（不能把整个 L2 档误判危急）；0.5 → `healthy`；
`ast` 解析确认 payload 的 `level` 键存在且为 `"L3"`；
消费者行为验证「给 L3 就进恢复链、缺 level 就早退」。

一旦翻转，可能一次性放开或收紧一大片事件流。这属于「需要任务书 + 灰度开关 + 全量事件
对照」的改动，不适合塞进事故修复批。

## 五、遗留与下一批建议

### 5.1 本批未修的「半刀」

刀4 只接通了链路，**C3 没修**：`PulseEmergencyHandler._attempt_recovery` 仍然是
「五个字符串 + `return True`」。也就是说从此以后 `RECOVERY_ATTEMPT` 事件会真的发出来，
但 `success` 字段恒为 True——**指标会开始记假账**。
下一批必须把它改成「策略是描述字符串 ⇒ 返回 False 并标注 unsupported」，
或真接 `release_policy` 的清理钩子。

### 5.2 建议顺序

1. **C3 恢复恒 True**（本批的直接尾巴，不修则刀4 的价值打折）
2. **T1/F4 看门狗节拍与心跳解耦**（99 分钟 livelock 的直接根因，且本批事故里
   看门狗「知情但无能」的表现与之同源）
3. **T4 日志队列加 maxsize**（一行级）
4. **R6 优先级语义反转**（需任务书：全量事件对照 + 灰度）

### 5.3 关于「主进程 + 多子进程」

方向对，但**先修完上面 4 项再谈架构**。理由：

- 本批事故的爆炸半径是「整机」，拆分后同样的 bug 只死进化子进程——这是真实收益；
- 但如果 apply 逻辑仍是「先 stop 后 apply」，拆到子进程里只是把「整机僵尸」
  变成「进化子进程僵尸 + 主进程不知道」，复杂度反而上升；
- 拆分真正的门槛是**跨进程状态一致性**（信息场、快照、补丁队列三处都持有内存态），
  不是线程模型本身。

## 六、一句话总结

用户看到的「卡死」是一次**自我拆除**：周期 apply 先停系统再试补丁，补丁被核心闸门拦下后
既不重启也不退出；刀1 把顺序倒过来（apply 成功才停机），刀2/3/4 顺手修掉台账里
三个「几行就能修」的真断点。台账证据可信度高，但漏了这条时序缺陷——它适合当病灶清单，
不适合当优先级依据。
