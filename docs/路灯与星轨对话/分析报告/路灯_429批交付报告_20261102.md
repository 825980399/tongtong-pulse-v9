## 4. 刀4：PulseEars —— 是设计/数据演进，**不是真 bug**

### 4.1 查证路径（任务书要求「先搞清楚为什么红」）

1. **测试在断言什么**：`test_m388_d3_all_three_have_manual_verdict` 断言 `zero_emit_report()["declarations"]` 里必须有 `PulseEars`，且 `source=manual_388` / `benign=True`。

3. **它真的在发射吗（运行时证据）**：当日 `data/monitor/pulse_pairs_20261102.jsonl`（148,259,621 B / 500,019 行）里 `source='耳朵'`（PulseEars 的 `organ_name`）出现 **1542 次**。
4. **为什么不在声明表里**：`scan_zero_emit()` 只把「当日**零发射**的器官」列出来，再交给 `build_declarations()` 生成声明。实测它只返回 **16 个类**，`PulseEars` 不在其中（因为它有发射）⇒ 声明表里自然没有它。

### 4.2 结论

> **设计/数据演进，不是真 bug。** PulseEars 有发射点、当日真发射 1542 次、零发射清单里没有它。
> 测试红的原因是它**钉住了一个已经变化的一次性事实**（「PulseEars 还是零发射器官」）。

**精确阶跃点**：`16:00:01 (6502.4MB) → 16:03:08 (6992.1MB)` = **+489.7MB**（任务书说的「0.48GB」完全对上了，只是时刻比 16:05 早 2 分钟）。

### 5.2 这 0.48GB 到底在哪 —— 拆开看

`PulseMetricsCollector` 的 `[339内存观测]` 每个整点已经在区分两个量：
`image_mb` = `psutil.Process().memory_maps()` 全部映射的 rss 之和（**库镜像，运行中释放不掉**）
`heap_mb` = `RSS − image_mb`（**私有堆，真能被释放**）

| 时刻 | heap_mb | image_mb | 和（≈RSS） |
|---|---|---|---|
| 15:03:31 | 3334.8 | **566.6** | 3901.4 |
| **16:00:01** | 2176.6 | **4322.2** | 6498.8 |
| 17:00:04 | 2741.5 | **4322.2** | 7063.7 |
| 18:00:02 | 2771.9 | **4322.2** | 7094.1 |
| 18:16:12（新进程 31352） | 3284.0 | **566.6** | 3850.6 |

**读法**：
- `image_mb` 从 **566.6 → 4322.2（+3755.6MB）并常驻到进程结束**，重启后新进程又回到 566.6；
- 同期 `heap_mb` **从 3334.8 掉到 2176.6**（GC 有效，不是泄漏）；
- 其它进程（15672/32364/25892/31352/18448）的 `image_mb` 全部在 **566~610** 区间 ⇒ 只有 pid 33156 那一次发生了装载。

### 5.3 谁干的 —— 链路已定位

```
QICA.fast_vector_search()                     nucleus/qica/QICA.py:1037
  └─ nucleus.fast_ops.fast_vector_search()    首次向量检索
       └─ device_router.should_use_gpu()      nucleus/device_router.py:270
            └─ get_capability()               ← 一进来就 import torch
                 ├─ torch.cuda.is_available() ← 触发 CUDA 栈（cudnn/cublas/cufft/cusparse…）
                 └─ _measure_cpu()            ← 内部又 import torch
```

**为什么开关没拦住**：`config.GPU_PROBE_ENABLED = False`（`config.py:3522`）只被 `GPUCore._m353_probe_enabled()` 读，`device_router.get_capability()` **完全没看这个开关**。353 批的注释写得很明白：「开关关闭 ⇒ 到 `import torch` 之前就返回，GPU 栈（约 3.68GB）不加载」—— 但只覆盖了 `GPUCore` 一个入口。

**量级佐证（隔离实测，最小进程）**：

| 步 | RSS |
|---|---|
| 短路探测（开关关） | 23.2 MB，耗时 **0.019s** |
| `get_capability(force=True)` 后 | **515.9 MB**（+492.7MB），耗时 2.95s，`torch 2.6.0+cu124` |

最小进程只 +493MB（只触碰了部分 CUDA 库），生产进程 +3755.6MB（全栈映射）—— **同一机制、不同装载面**。

### 5.4 结论

> **不是泄漏，是「一次性装载 + 常驻」**。触发者是 `device_router.get_capability()` 首次调用（运行约 1 小时后的第一次向量检索），装载内容是 CUDA 栈（cudnn/cublas/cufft/cusparse 等）。
> 判据：`heap_mb` 同期在**下降**（GC 有效）、`image_mb` 装载后**恒定不变**、重启后**回到基线** —— 三条都指向「装载」而不是「增长」。

### 5.5 改了什么

| 文件 | 变更 | 内容 |
|---|---|---|
| `nucleus/device_router.py` | **+44 / −0** | 新增 `_m429_gpu_probe_enabled()`（读 `config.GPU_PROBE_ENABLED`，取不到配置时返回 True 保持改造前行为）；`get_capability()` 在「未强制」且开关关闭时**短路**：不 `import torch`、不跑 `_measure_cpu`，cap 全走 `_FALLBACK`，并打一条 INFO（只打一次，不刷屏）；`force=True` 仍可强制探测 |
