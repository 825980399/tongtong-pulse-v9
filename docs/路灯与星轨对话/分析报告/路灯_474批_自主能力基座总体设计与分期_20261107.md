## 一、本次施工的前提（星轨裁决）

1. **铁律 304**：所有优化、修改、完善，判定标准只有一个——**曈曈自身能力是否净增长**。
   外部大模型及其他外部主体只能是临时脚手架、辅助、独立审查或长尾兜底，
   不得成为能力的存放地；目标是曈曈未来成为独立的数字化生命体。
2. **外部渠道不稳定的现实压力**：LLM 渠道随时换模型（473 批实测 siliconflow 402
   余额不足、bailian-kimi-k3 400、免费渠道 429、zhipu 抖动）。
   而经验写进 prompt ⇒ 换模型/清上下文即归零。`lesson_cooldown.py` 开头已有
   实证结论：「459 的『写经验库 + append_reminder 提醒段』是**软保证**，
   LLM 不读就等于没写」。
3. **整体利用，不是专用组件**：「创建能力就是为了整体利用，而不是创建后只针对
   固定闭环逻辑使用」。补丁生成、内在世界推理、认知反思、其他子系统都要能复用。
4. **我的优点能利用的全部利用，利用不了的用更好的方式替代**。

## 二、总体架构：能力层是领域无关的「底座」，不是补丁专用组件

```
nucleus/autonomy/                      ← 本期新增，领域无关
  Capability      detect / synthesize / verify 三元组
  CapabilityKernel  按 domain 分派 + 影子/灰度 + 失败不应用
  ExperienceLedger  结构化 append-only 台账（不是 prompt 文本）
  AutonomyMetrics   按 domain 的 自给率 / 外部依赖率

         ↑ 注册（任何子系统都能挂）
   ┌─────────┬──────────────┬───────────────┬─────────────┐
 code_repair   reasoning      reflection      ...任意新域
 (本期3算子)  (第二期接入)    (第二期接入)     (无需改内核)
```

**关键设计**：`domain` 只是字符串，内核不解释 `artifact` 的结构。
单测 `test_14_generality_other_domain` 注册了一个 `reasoning` 域的自定义能力并跑通，
就是这条约束的可执行证明。

**内核绝不调用外部 LLM**：覆盖不了只返回 `external_needed=True`。
`TestAutonomyIronLaw` 用 AST 扫描 import 节点与调用节点把铁律 304 变成门禁。

## 六、四个必须守住的结构性约束

1. **独立基准**：生成侧与验收侧不同实现、不同数据源，防自写自验自判的循环论证
   （铁律 30；473 批 461 `verdict=apply` vs 447 `approved=False` 同帧即原型事故）。
2. **判别力**：每个算子配反证用例（铁律 35），判据在旧代码上必须不成立。
3. **盲审**：外部 LLM 当 reviewer 时只给 diff + 上下文 + 检查清单，
   不给曈曈的推理链与自裁决结论，否则会附和。
4. **出题人**：完全自洽的系统看不见自己的盲区（473 批「层级一致性缺口」
   是外部视角发现的）⇒ 长期保留外部 LLM 于「独立审查 / 长尾兜底 / 红队」三处。

⇒ 目标不是「全局 LLM 调用归零」，而是**高频能力类目依赖降到 0、长尾保留**，
且外部调用率可度量、按类目收敛。这与铁律 304 不矛盾：外部是脚手架，不是能力存放地。

## 九、结论

- **铁律 304 已从一句话变成三样可执行的东西**：速查表/全文/TOP 判据、
  `nucleus/autonomy/` 里跑在曈曈进程内的算子与结构化台账、
  以及 `TestAutonomyIronLaw` 的 AST 门禁（禁止内核引入外部模型/HTTP）。
- **能力层是通用的**：`domain` 只是字符串，补丁修复与内在世界推理共用同一套
  内核、台账与指标，满足「整体利用」而非「只针对固定闭环」。
- **经验不再归零**：换模型、换 prompt、清上下文都带不走 `fixer_registry` 里的算子。
- **本期没有动任何生产行为**，曈曈仍在正常运行；后续接主链路按项目惯例需任务书。

最省力的下一步：**把第二期的 `_detect_symbolic_reason` 统计接进
`ExperienceLedger`**，一行结构化记录即可让「推理自给率」成为可观测事实——
这是「曈曈逐步提升自己」从理念变成度量的第一步。

### 11.2 附带修复：PATH 切 3.14t 引入的定期测试假超时

用户在日志里发现 `verify_semantic_kernel.py 超时(60s)` 反复出现。核实后确认
**是刀20 环境改造引入的回归，不是框架真回归**：

`PeriodicTestScheduler._run_scripts` 硬编码 `["python", script]`，PATH 把 `python`
指向 3.14t 后，子进程失去 `fastembed`/`onnxruntime`（只装在 3.12）⇒ VectorEncoder
三路加载全失败、`state=disabled`、`is_available()` 恒 False ⇒ 脚本旧等待块空等
120s ⇒ 调度器 60s 杀成 `returncode=-1`。实证：12:44/13:06 报告均 `rc=0`（切 PATH 前），
15:13 起连续 9 次超时；2217 份历史报告中该脚本 1819 次 `rc=0`、9 次 `-1`。

三处修复：① 脚本新增可注入 `wait_encoder_ready()`，disabled 立即返回；
② 调度器新增 `_periodic_test_python()`（`config.PERIODIC_TEST_PYTHON_EXE` 优先、
回落 `sys.executable`），去掉硬编码；③ config 桥接期显式指向 3.12，并写明
「3.14t 具备 fastembed + onnxruntime 后删除本项」的退出条件。
**主程序仍是 3.14t free-threading**，本项只作用于定期测试子进程。

真实验收：3.12 `rc=0 / 4.7s`（黄金评测集 15/15 全过）；3.14t `rc=2 / 1.4s`，
输出明确原因「No module named 'fastembed'」，不再伪装成超时。

## 十二、真并行适配补记：分层队列与背压（提交 `e1ecd7de`）

用户提出一个关键问题：切 3.14t 后「之前不能真正并行所以 L1/L2/L3 队列不会超，
现在是不是很容易超」。核实结果分三层：

### 12.1 事实：积压是老问题，真并行放大了它

- **不是 3.14t 引入**：00:47:43（3.12 时代，`gen=pid13952@20261106`）已有
  `[背压] L1层队列已满(深度=1000, 上限=500)，累计拒绝=1`。
- **但增长确实变快**：00–01 时总队列 1006→2854（≈15/分）；19–20 时
  1009→5062（≈68/分，含本轮跑测试与门禁的 CPU 干扰，不宜当作精确倍率）。
  3.14t 下生产者真并发投递，而消费端 worker 数未变，净积压风险上升。

### 12.2 真因不是上限数字，是「降级放行」没有上限

实时 `health_snapshot.backpressure`：
`L1 = 2371/500（拒 4004）`、`L2 = 2588/300（拒 11）`、`L3 = 0/300`。

`_admit_layer_task` 的 P2-31 降级放行对 `priority<=3` 的脉冲**无上限放行**，
且对 L2/L3 也生效 ⇒ 日志 `[背压·超限放行] L2层队列已满…放行（累计2300次）`、
L1 累计放行 1400 次。这与该方法 docstring 的「L2/L3 达到上限即拒绝」直接矛盾，
也把 L1「达 2 倍软上限才拒绝」架空 ⇒ 队列无界单调增长。

**没有调大队列上限**：那只是让 RSS（当前 5.5GB）涨更多，不解决「生产 > 消费」。
背压日志里「请调高 config.PULSE_LAYER 对应层上限」是本轮的误导项。

### 12.3 刀24 修复（止血，可逐字回滚）

  深度达「上限 × 4」后，即使高优先级也拒绝。L1=2000 / L2=1200 / L3=1200。
