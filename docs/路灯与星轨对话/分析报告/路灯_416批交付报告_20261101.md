## 二、刀1 · self_inspector 线程化 + 降优先级

### 2.1 做法（4 条要点逐条对账）

| 任务书要求 | 落地 |
|---|---|
| ①启动时不立刻全库扫，改延迟 30s 后在独立线程跑 | `submit_deferred_scan(reason, delay_sec=30.0, force=False)`；线程名 `self-inspector-deferred-scan`、`daemon=True`；**单飞**（`_m416_scan_thread.is_alive()` 判定）；**启动窗口** 180s（窗口外不再起，避免运行期反复重扫） |
| ②线程优先级最低 | `_m416_set_thread_lowest()`：`ctypes.WinDLL("kernel32", use_last_error=True)` + 显式 `argtypes/restype` → `SetThreadPriority(handle, -2)` → `GetThreadPriority` **读回校验**。POSIX 走 `os.nice(19)` |
| ③每扫 10 个方法体 sleep 1ms | `_m416_coop_tick()` 挂在 `SelfInspector.get_method_body()` 入口，`_M416_YIELD_EVERY=10` / `_M416_YIELD_SEC=0.001`；上下文外**零开销**（首行 `if not _m416_coop_on: return`） |
| ④开关 `ENABLE_SELF_INSPECTOR_STARTUP_SCAN = True` | `config.py` 已加；读不到时缺省 True；另有 `M416_STARTUP_SCAN_DELAY_SEC=30.0`、`M416_STARTUP_WINDOW_SEC=180.0` |
| 接线（不改调度器） | `PulseCodeLearner._review_own_code_issues()` 在调 `detect_code_issues()` 之前插一段：`submit_deferred_scan()` 起线程成功就 `return`（把活交给线程），起不来则**回落原同步路径**并记 DEBUG 说明 `why` |

★踩坑留档：首版用 `ctypes.windll.kernel32` 默认 argtypes，64 位伪句柄 `0xFFFFFFFFFFFFFFFE` 被截成 `0x00000000FFFFFFFE` ⇒ `SetThreadPriority` 返 0（`win32_failed`）。改 `WinDLL` + 显式 `argtypes` 后读回 `-2` ✓（默认 argtypes → 0 / 显式 → 1，已实测对比）。

### 2.2 验收①：单测 16 条全绿

### 2.3 验收②：真扫描的集成 A/B（同步 vs 线程化）

`tmp/m416_k1_integration.py` —— 同一进程、不改 `sys.setswitchinterval`、50ms 心跳探测线程：

| 相位 | 耗时 | 心跳最大超期 | 8s 超阈次数 | RSS 增量 |
|---|---|---|---|---|
| P0 idle（噪声基线） | 3.0s | **0.6ms** | 0 | — |
| P1 sync（416 前行为，无让出） | 131.7s | **1.05s** | 0 | **+184.9MB** |
| P2 threaded（416 后行为） | 119.1s（扫描 118.5s） | **0.98s** | 0 | +13.8MB |
| P3 sync+coop（只开让出） | 118.4s | **0.97s** | 0 | +4.8MB |

`scan_state`（线程里读回）：`priority_backend="win32_lowest"`、`organs=66`、`issues=1017`、`thread_name="self-inspector-deferred-scan"`。

**怎么读这张表**：

- 三条路径的心跳最大超期都在 **1s 量级**，**远低于 L0 看门狗的 8s** ⇒ 「CPU 被 self_inspector 抢走导致看门狗超时」在**纯 CPU/GIL 层面站不住**。原因是 CPython 的 GIL 每 5ms 必切换，纯 Python 循环饿不死别的线程；那 1s 的尖峰来自 `ast.parse()` 大文件这种**C 层不放 GIL** 的调用，线程化和让出都消不掉。
- 线程化的真实收益在别处：①它把 118s 从**调用方（`PulseCodeLearner` 的心跳/主循环）的同步栈**里挪走；②优先级 `-2` 让 OS 调度器把 CPU 让给主线程；③真正的尖峰上限由单文件解析耗时决定，不再由"整轮 118s"决定。
- RSS：首扫 +185MB，之后每轮 +5～14MB，**没有累积性 GB 级泄漏** ⇒ 刀2 的嫌疑④「扫过的方法体没释放」**不成立**。

### 2.4 验收③：让出钩子在真路径上到底触不触发（`tmp/m416_k1b_coop.py`）

首版脚本跑出 `coop_ticks=0` —— 因为 `detect_code_issues()` 不走 `get_method_body()`。真路径是 `PulseCodeLearner`/`SafeEvolutionExecutor` 逐条问题取方法体。ABBA 四轮（全量热身排除缓存顺序效应）：

| 轮次 | 让出 | 耗时 | 让出次数（累计） | 心跳最大 |
|---|---|---|---|---|
| A1 | off | 1.2142s（均值） | 0→0 | 0.9ms |
| B1 | on | 1.2326s（均值） | 400 | 0.6ms |

⇒ **`hook_alive`：400 次调用触发 40 次让出，开销 +1.52%**（含 40×1ms 的 sleep 本身）。让出钩子有效且代价可接受。

### 2.5 「L0 看门狗还超时吗」—— 本批的诚实答案

- **能承诺的**：`self_inspector` 这一路（启动期全库扫）不再出现在主线程同步栈上，且优先级最低、窗口外不重扫 ⇒ 它不再是 8s 超时的**嫌疑源**。
- **不能承诺的**：**看门狗不会再超时**。`pulse_crash.log` 的 stall 抓栈里 Top3 是 `_on_heartbeat_observe`（15 个线程块，持 `_cache_lock` 做 `_refresh_organ_cache()` + `_build_observability_snapshot(skip_slow=True)`）与 `_on_heartbeat_alive`（13 块）。这是**锁路径**，与 self_inspector 的 CPU 无关，本批**未动**（列入待裁 §8-3）。
- **所以**：真正要验证「启动后看门狗不超时」，必须有一次活体启动 —— 判据是 `logs/heartbeat_stall/` 是否还新增、`pulse.log` 里有无新的 `heartbeat_guard_takeover`。

## 三、刀2 · 内存 95% 爆发真凶（核心）

### 3.1 真凶：探针的 tracemalloc 全堆快照**层叠**（不是对象泄漏）

链条（每一环都有代码位置 + 日志原文）：

1. **为什么要快照**：`_m339_memory_probe` 在 `M339_MEMORY_PROBE_HOURS=(5,13)` 的整点槽位跑一次内存观测。
2. **代价**：`M339_TRACEMALLOC_MODE="resident"` ⇒ 进程早期 `tracemalloc.start(1)` 并常驻，1.4M 活块全被追踪；`take_snapshot()` 在这种堆上单次要 **289～1805 秒**。
3. **阈值形同虚设**：`M339_MEMORY_PROBE_MAX_SEC=3.0` 的判定在**快照做完之后**才执行 —— 309s 做完才判「>3s 不写盘」。
4. **★致命处**：`_m339_probe_last_slot` 只在**写盘成功后**置位（`PulseMetricsCollector.py:1045-1048`）。超时分支 return、MemoryError 分支 return，**都不置位** ⇒ 30s 后心跳又起一轮 ⇒ **多份快照同时在飞**。
5. **重启放大**：`_m339_probe_last_slot` 是**进程内变量**，重启即清空 ⇒ 只要重启时的小时数 ∈ `(5,13)`，**第一个 30s 心跳立刻触发**，不用等整点。

## 四、刀3 · O3 补盲（裸 Name 值传递判据）

### 4.1 判据（`CallGraphAnalyzer._m416_name_value_ref_names()`，四个来源）

| 源 | 形态 | 说明 |
|---|---|---|
| 1 | `ast.Dict` 的 value 是裸 `ast.Name` 或字符串常量 | 反射表 `{"switch": enable_tracing}` |
