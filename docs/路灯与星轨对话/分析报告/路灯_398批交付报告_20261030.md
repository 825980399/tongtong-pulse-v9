### ③ 刀3：「65.8% 是回填时序假阳性」被实测证伪

票面的两层归因**都不成立**：

**第一层：时序。** 把单遍顺序扫（边扫边配对）改成**两遍**（先全量建 emit 索引，再扫 receive），
未匹配数**一个都没变**：

```
单遍未匹配 = 34,357
两遍未匹配 = 34,357      ← 完全相同
```

回填时序会导致"receive 排在 emit 前面就被判落空"，若是成因，两遍扫描必然大幅下降。**没降。**

**第二层：换源到 `health_snapshot.json` 的 `matched/published`。** 该字段**不存在**：
顶层 26 键，`pulse` 段只有 `emitted/completed/timeout/pending`，没有任何 `matched`。
真正同源读数在 `EventBus.m360_event_metrics()`，但那是**订阅侧**口径（谁订阅了、收到几条），
与 tracer 侧（emit 有没有对应 receive）**不是同一件事**，强行并列等于混口径（铁律 282）。

**真实归因**（`pulse_pairs_20261015.jsonl` 实测）：

```
旧口径        34,357 / 155,168 = 22.14%   ← 虚高
├─ 无 pulse_id   20,661 (60.1%)  ← 结构上无法 join，永远不可能"匹配"
└─ 真落空         13,696 (39.9%)
真落空 / 全部接收      =  8.83%
真落空 / 可 join 接收  = 10.18%
```

**60.1% 的落空是"分母里混进了不可配对的样本"，不是配对机制坏了。**
这就是铁律 271（判据分子分母必须同源）的又一例。
