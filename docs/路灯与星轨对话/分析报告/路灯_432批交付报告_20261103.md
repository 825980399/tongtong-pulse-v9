## 3. 逐刀

### 3.1 刀1：空 WARNING 刷屏 —— **消息不空，是首行空；真因是判据撞空**

#### 3.1.1 现场

```
$ grep -c "假死探测器] 框架疑似冻结" logs/pulse.log
109
$ 事件时间分布：06 点 14 次 / 07 点 60 次 / 08 点 35 次（首 06:46:34，末 08:34:12）
```

`cat -A logs/pulse.log` 抓一条现场：

```
2026-11-03 07:12:34 [pulse] WARNING: $
[假死探测器] 框架疑似冻结：连续约30秒无任何脉冲被处理。$
[假死探测器] 正在 dump 所有线程堆栈到 logs/pulse_crash.log ...  pid=18448 gen=...$
```

**三行是同一条消息**。`logging` 打多行消息时只有首行带 `级别:` 前缀，且 `_msg` 以 `\n` 开头 ⇒ 首行是空串 ⇒ 看起来「什么都没说」。
任务书看到的「空 WARNING」= 这条消息的第 1 行。

#### 3.1.2 根因（两层，缺一不可）

1. **表象**：`_msg = f"\n[假死探测器] ...\n[假死探测器] ..."` —— 前导换行 + 两条拼接。
2. **真因**：判据 `if _stall >= 3:`（3 × 10s = 30s）。而 `logs/pulse_crash.log` 里 `handled` 的真实采样是
   **175684 → 175792，108 个间隔共 +108，即每 60s 才 +1**。判据窗口 30s 比真实空闲 60s 短一半 ⇒
   **每两个窗口必有一个撞空** ⇒ 周期性必然误报，与「框架是否冻结」无关。

> 判据有判别力吗？有：用**两个不同入口**夹逼——源码阈值（`_stall >= 3` ⇒ 30s）与日志空闲上限（60s）。
> 两个数不来自同一处，不存在循环论证（铁律 35）。

#### 3.1.3 改法（`main.py`）

```python
# ★432刀1：判据分层（原单一 `_stall >= 3` 在低活跃期**必然**误报）。
_STALL_NOTE = 9     # 9 × 10s ≈ 90s：只记账，不告警不 dump
_STALL_WARN = 22    # 22 × 10s ≈ 220s：才 WARNING + dump
```

- 220s = 实测最长空闲（60s）的 **3.7 倍**；真冻结最迟 220s（≈3.7 分钟）被发现，仍在 4 分钟内。
- 90s 处打一条 DEBUG（低活跃期常见，留痕但不刷屏）。
- `_msg` 改**单行**；dump 台账改成 `stall={_stall}(~{_stall*10}s) handled={_handled}`，一眼能看出是「几十秒」还是「几分钟」。

### 3.3 刀3：线程落差 —— **不是卡在引导期，是池子轮换 + 判据把「高」当「涨」**

#### 3.3.1 现场

```
logs/pulse.log 三份 [376刀3] 线程落差快照：
  未登记 == gap（全部对上）  ident 域 = 一致
  每拍新增 2–3 个 tid，但 OS 线程总量只 +1/小时
告警 44 条：gap 93 → 96，base 恒为 [78]，persist 62 → 105
```

「每拍新增 2–3 个 tid 但总量只 +1/小时」= **有生有灭**，是线程池在工作。真「卡在引导期」的特征是
**tid 只增不减 + 总量阶梯上升**，现场不是这个形状。

#### 3.3.2 判据错在哪

```python
_delta = _g - _base            # base 在建基线那一刻定死，此后永不更新
if _delta >= THREAD_GAP_PERSIST_SAMPLES:
    _persist += 1
    warn = _persist >= ...
```

- `base=78` 是**历史基线**，gap 已经稳定在 96 —— 这是一个**一次性台阶**（pool 扩容），不是持续增长。
- 但 `delta = 96 − 78 = 17` **恒 ≥ 阈值** ⇒ 每一拍都算「还在涨」⇒ 44 条告警里绝大多数是「台阶后的余波」。
- `persist` 无上限（62→105）⇒ 数字本身也在放大错觉。

#### 3.3.3 改法（`nucleus/thread_guard.py`）

```python
THREAD_GAP_REBASE_IDLE = 6   # 连续 6 拍没再涨 ⇒ 基线复跟
THREAD_GAP_PERSIST_MAX = 60  # persist 封顶

if _g > _prev_gap:           # ★判据：与前一拍比，不与历史基线比
    _persist = min(_persist + 1, THREAD_GAP_PERSIST_MAX); _calm = 0
else:
    _persist = 0; _calm += 1
if _calm >= THREAD_GAP_REBASE_IDLE:
    _base_out = _g; _delta_out = 0; _calm = 0     # 台阶被吸收
return {..., "gap": _g}                            # 只加不改：新增 gap 键
```

同时 `organs/body/PulseLiver.py` 告警措辞纠偏：原文「疑似有线程卡在引导期」是**错判**，改为
「疑似原生线程池扩张或线程未登记；查『卡在引导期』请用 `thread_guard.stuck_snapshot()`（当前 N 条）」，
面板补 `thread_gap_abs` 键（绝对值单列，不再与 delta 混看）。

#### 3.3.4 「有线程卡超过 N 分钟打 WARNING 告诉是哪个线程」——任务书要求的那条监控

`thread_guard.stuck_snapshot()` **本来就存在**并已在跑；问题是**没人指向它**：告警文案把「gap 大」直接翻译成

### 3.4 刀4：对话落盘 —— **链断在入口，cid 生成在断链下游**

#### 3.4.1 断链全图（逐跳）

```
chat_service._send_chat_message
   emit(payload={content, original_input, ...})          ← ① 这里没有 correlation_id
        ↓
PulseCortex._on_message
   correlation_id = f"ctx:{n}:{ms}"                      ← ② 皮层自己造一个
   self._pending_messages[correlation_id] = ...          ← ③ 以它为键存
        ↓  QICA 分类
PulseCortex._on_classify_result(correlation_id="")       ← ④ 回传**空串**
   ctx = self._pending_messages.pop("")                  ← ⑤ 恒 None
        ↓
   no_pending_match  ⇒ dialogue_process_trace.begin()    ← ⑥ 一次都没被调到
```

**「cid 应该在哪里生成」**：应该在一轮对话**发出去之前**、由入口（`chat_service`）生成——它是这轮对话的身份证，
