## 二、T0 核实：刀1 的停更根因（票面判断需改口）

票面写「`_on_collect` 没跑或写失败」，三条独立证据指向**另一件事**：

1. `logs/pulse.log` 尾部是 10-29 20:58 的**完整关闭序列**（运行统计／停止序列清点／"曈曈 停止指令已发出"）；
2. 其后只有 8 行**无头 logger 点亮**记录（00:08/00:10/00:11×2/02:21/03:12/09:15），**没有任何框架启动 banner**；
3. `psutil` 扫 `main.py` → **NONE**；`data/runtime.lock` 不存在。

⇒ **停更 = 没有进程在跑，不是采集器线程挂了、不是写盘失败被吞、不是 396刀2 接线断了。**
旁证：停机前 `.bak` 序列 `20:38:31 / 20:43:31 / 20:48:32 / 20:53:57` 恰好 300s 间隔，
说明**停机前快照采集是正常按 300s 跑的** —— 票面"13.5 小时没更新"其实是"13.5 小时没启动"。

**因此本批不伪造"已恢复"**：① 若真是代码缺陷（线程挂/写盘吞异常），evidence 会留在 log 里；
② "重启后每 300s 更新"是活体判据，离线测试拿不到，只能由小林重启后核验（§七）。

附带一个事实修正：快照真实路径是 **`data/monitor/health_snapshot.json`**（4012 B，
`timestamp=1793278410` = 10-29 20:53:30），不是 `data/health_snapshot.json`（不存在）。

## 三、刀1 施工（`b0dc87f0`）

### 3.1 补的四块，全部复用**同一次**采样

`_collect_memory_pressure()` 有副作用（记峰值 / 跑 `check_memory_alarm_detailed(auto_gc=True)` 三闸 /
**可能真触发 GC**）。所以补字段**绝不能**再调一次：`_build_observability_snapshot` 里 `_m401_mp`
取一次，四个块全部复用它。判据用 AST 钉死"该函数体内 `self._collect_memory_pressure()` 恰好 1 次"。

| 块 | 键 | 来源 |
|---|---|---|
| `memory` | `process_rss_mb` / `system_percent` / `growth_mb_per_min` / `source` | `memory_pressure` + `growth_alarm` |
| `gc` | `count` / `last_gc_at` / `last_gc_gen` / `auto_gc_triggered` / `generations` | `gc.get_stats()` + `gc.callbacks` + `memory_pressure.gc_triggered` |
| `threads` | `n` | `threading.active_count()` |
| `handles` | `n` | `psutil.Process().num_handles()`，非 Windows ⇒ `None` |

两个细节：
* `last_gc_at` 拿不到现成值 —— `gc.get_stats()` **没有时间戳**，只能挂 `gc.callbacks`（只认 `phase=="stop"`，
  "start 时刻"不是"最后回收时刻"）；
* 取不到一律 `None`，**绝不填 0**（`0 MB` / `0 个句柄` 是"真测到 0"，`None` 才是"没测到"）。

### 3.2 阈值归一的两个坑

* `RUNTIME_PARAMS` 热重载有**键交集过滤**（`config.py:4086`）⇒ 新键不先登记进字典，
  override **永远**被静默丢弃。故 `memory_auto_gc_rss_mb` / `memory_high_load_rss_mb` 先登记，再派生常量。
* 常量在 **import 期**求值 ⇒ 热改这两键对 `InfoField` / `runtime_metrics` **不会立刻生效，需重启**。
  这句写进代码注释，避免下批有人以为"改了 override 就能热调"。

判据另外守一条：`PulseMetricsCollector.py` 里**不得再有 6144 / 8192 字面量**（AST 扫数字常量，
注释里写这两个数不算违规）—— 归一的判据是"第二源已拔"，不是"注释写得好看"。

### 3.3 判据

`tests/test_m401_k1_snapshot_fields.py`（8 例）：四块齐全／开关关闭回旧样子／采集只调一次（AST）／
取不到给 None／gc 块形状／`phase` 只认 stop／两个常量与 `RUNTIME_PARAMS` 相等／无 6144·8192 字面量。

## 四、刀2 施工（`d5281de5`）

### 4.1 cap 的真正病因是**量纲错配**

`_PAIR_FILE_CAP = 200000` 是**行数**上限，触发条件却是 `_LAST_PAIR_SEQ > _PAIR_FILE_CAP` ——
`_LAST_PAIR_SEQ` 是**进程内事件序号**，每次启动归零。⇒ 单进程写不满 20 万笔就永不 trim。
实证：10-29 单日 `pulse_pairs_20261029.jsonl` 95 MB ≈ 32 万行，仍在长。

### 4.2 四件改动

1. **触发判据改文件当前行数**：首见 / 跨日按实测，同文件**增量累加**（不每次 flush 全文件计数，
   否则热路径变成 O(文件大小)）；cap 提到 `RUNTIME_PARAMS["pulse_pair_file_cap"] = 500000`。
2. **trim 前先备份** `<name>.trim.bak`（只保最新一份）—— trim 等于删掉当天更早的数据，
   无备份即不可逆；备份失败只留 WARNING，不阻断 trim（但明写"数据不可回溯"）。
3. **匹配率双列**：`matched_raw`（含万能器官）/ `matched_real`（剔 `_UNIVERSAL_ONLY_ORGANS`）+
   `matched_source` 逐列口径说明。旧 `matched` 名字与值**原样保留**（health_ui / 报表消费方不动）。
   > 两者**不可互比**：health 自报 100% 而 tracer 7.8%，就是拿 raw 比 real。
4. **孤儿按天环形**：`data/monitor/pulse_orphans_YYYYMMDD.jsonl`（maxlen=5000，超了回写最近 N 行），
   跨天在去重前按 `timestamp >= 今日 00:00` 过滤。
   **数组 `pulse_orphans.json` 仍然写** —— `functions/health_ui.py:788/796/813` 每 2s 轮询它，
   只改 JSONL 会直接砸看板。数组 = UI 视图（只保当日），JSONL = 同行全量、跨日不累计。

### 4.3 判据

`tests/test_m401_k2_pairs_cap.py`（11 例）：行数实测→增量→换文件重测／真 trim 到 cap 且保留最近 N 行／
备份早于剪切／cap 非法值回退／灰度关回旧行为／触发点走行数判据（AST）／
孤儿日文件命名与环形回写／今日 00:00 基准／双列不相等／real 缺读数给 None／
**8 线程并发累加不丢增量、不死锁**。

* `call_graph_guard.select_latest_graph`（按文件名排序的那个）；

> 按 mtime 排序的消费方（`self_inspector._m342_load_latest_graph`）本不会误选 ——
