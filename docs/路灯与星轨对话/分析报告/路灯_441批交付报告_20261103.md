## §3 刀3：OPEN 消费者 —— **没跑通，且原因不是"差一步"**

### 定位

`OPEN` 与 `judge_action_open` 是**两道独立的闸**（`official_verdict_read.py:34/73`
明文写着「不得互相顶替」）。`streak` 的真正来源是
`nucleus/self_inspector.py::_m340_judge_action_open`（9090–9153）：

```python
_M340_JUDGE_ACTION_STATE = {"streak": 0, "last_tick": None, "last_open": False}  # 进程内
if _all_ok:
    if not _same_tick:          # 同一 tick 内重复调用不增计数
        _st["streak"] += 1
else:
    _st["streak"] = 0           # 任一条件不满足 ⇒ 立刻归零
_open = _st["streak"] >= _M340_JUDGE_ACTION_MIN_TICKS
```

`_all_ok = mode_ok and sample_ok and misjudge <= _O3_MISJUDGE_LINE`。

### 活体证据（这才是关键）

```
$ grep -a "340判死" logs/pulse.log | tail -3
（空）
```

当前 `pulse.log` 覆盖 **11-03 03:00 → 23:5x、5.6 万行**，
**一条 `[340判死]` 都没有** ⇒ 这个动作在当前进程里**根本没有执行**。
所以"streak 2/3"是**更早某个进程留下的残影**（counters 是进程内的，重启即归零）。

### 为什么我没硬改

要让 streak 到 3，需要**同一进程内连续 3 个不同 tick 全部满足三条件**。
现在的问题是第 0 步——动作没在跑。此时去"调低阈值"或"持久化 streak"，
等于把一个**安全闸**（O3 判死动作的开闸条件）在没有证据的情况下放宽，
和 438 批刚治好的"假成功"是同一类错。

### 交给 442 的三步

1. 先查 `_m340_judge_action_open` 的**调用方为什么没跑**（是调度没挂、还是 mode/sample
   条件长期不满足导致提前返回）；
2. 跑通后看 `[340判死] ... 连续=%d/%d` 的实际读数，确认是 2/3 还是 0/3；
3. 真要"收口"，应修**上游条件**（mode/sample/misjudge 哪一项长期不达标），而不是改闸门。
