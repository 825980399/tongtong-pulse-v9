## 二、ALL 协作（`bf0e4a69`）

### 1. 为什么做

477 已把「曈曈修订」接进补丁链，但**修复率仍 0**。

根因不是「模型不够强」：469/470 的判据要求
`original` 逐字等于方法体、`modified` 的 def 行方法名必须等于补丁 method ——
这是**格式契约**，不是智力。单模型一次命中概率太低，换更贵的模型也没用。

对策：多模型并行出草稿，用判据选。
一个模型命中概率 p，N 个并行命中概率 `1-(1-p)^N`。

### 2. 分工（「曈曈为主、ALL 为辅」的落地形态）

| 角色 | 职责 | 是否参与评判 |
|---|---|---|
| ALL（外部渠道） | 只出草稿 | ❌ |
| 曈曈（`score_code`） | AST + 最小改动相似度打分择优 | ✅ 独家 |

全程不问任何模型「哪个好」。

### 3. 判据设计（每条都有真机样本佐证）

补丁里的 `original_code` / `modified_code` 是**带 8 格缩进的方法片段**，所以：

- **必须 flex 解析**：直接 `ast.parse` 必撞 `IndentationError`。
  三路尝试：原样 → dedent → 包 class；三种都失败才算语法不通。
- **「方法体完全相等」是格式校验，不是修复质量**。
  修复必然改变方法体。质量该看「最小改动」：
  相似度 `[0.50, 0.98)` 满分；`≥0.98` 判「没真改」；`<0.50` 判「疑似重写」。
- **多因聚合**：一个补丁常同时踩多个坑（改动过大 + 裸 except），
  只留首个原因会让运维以为改一处就够。

评分 0~100：

| 项 | 权重 | 含义 |
|---|---:|---|
| parse_ok | 35 | flex 解析通过 |
| full_method | 20 | 含 `def <method>`（470 判据的硬要求） |
| minimal | 25 | 相似度落在 [0.50, 0.98) |
| no_bare_except | 10 | 无裸 except（铁律 4） |
| changed | 10 | 与原文确有差异 |

### 4. 按需触发（真机实测后的必要收紧）

真机 2 样本实测：并行 3 条要 **23~39 秒**，且 **2/3 渠道失败**
（智谱 429、推理模型把 max_tokens 全花在 reasoning 上返回空内容）。

若每次都并行，等于给主链路白加 30 秒延迟，换一个「本来就已经 100 分」的补丁。
⇒ 加阈值 `M479_ALL_COLLAB_TRIGGER_BELOW=85`：首个渠道已达标就跳过。

实测：高分场景 **0.03 秒**返回（`skipped=baseline_ok`，零配额零延迟）。

### 5. 真机验证数据（2026-11-08）

| 样本 | 存量 LLM 产物 | 新并行产出 | 判定 |
|---|---|---|---|
| `_save_lessons` / non_atomic_write | 100 分（sim 0.52） | qwen3.7-flash 88 分（sim 0.28） | 存量更好（新产出改动过大） |
| `_schedule_next_snapshot` / periodic_task_no_reentry | 100 分（sim 0.55） | qwen3.7-flash **100 分（sim 0.75）** | **新产出更优（改动更小）** |

第二行是关键证据：**同一模型在新 prompt 下产出了改动更小的更好补丁**。
说明「多模型并行 + 判据择优」这条路能提升补丁质量，不是理论推演。

低分场景实测：`best=0`（4 条候选全部 <65 分）—— 因为验证用的是临时拼的
prompt，没有真实 issue 上下文。真实生产 prompt 含 issue 详情、相关日志、
追问策略，命中率会更高（这一点需要用影子数据继续验证）。

### 6. 安全边界

## 三、接线事故与修正（本轮最值得记的一条）

### 事故 1：接错了函数

第一版用 grep 行号推断作用域，把调用点插进了 `_call_llm_with_followup`
（2418 行那段「第一轮 `answer = _call(prompt)`」）。

那个方法的参数是 `(api_url, api_key, prompt, max_followups, scene, model)` ——
**没有 `issue` / `code_snippet`**，ruff 直接报 `F821 Undefined name`。
而且它是底层通用调用，上层 `_call_llm_for_repair` 会再调一次 ⇒ 重复。

改用 **AST 定位** `_call_llm_for_repair` 与它内部的 `return _answer` 才接对。

### 事故 2：新方法插进了方法体内部

第二版先替换 `return _answer`（1 行 → 2 行，净增 1），
再按**旧的** `_fn.end_lineno` 插入新方法 ⇒ 新方法落进方法体变成内层函数。
`compile` 仍然通过（内层函数语法合法），只有 AST 断言能抓到。

修正：插在 `_fn.end_lineno + 1`，并用 AST 断言兜底。

### 两条教训已写成测试

`test_41_wire_point_exists_in_see` 用 AST 校验：

- 调用点必须在 `_call_llm_for_repair` 内；
- **不能**在 `_call_llm_with_followup` 内（反证）；
- `_m479_all_collab` 必须是类的方法，不能是内层函数。

这比字符串匹配有判别力 —— 我犯的两次错它都能抓住。

## 八、语义桥：让 3.14t 的语义内核复活（`e1c4f09d`）

### 1. 「语义内核不可用」到底影响什么

3.14t 是自由线程构建，`fastembed` / `onnxruntime` 没有 cp314t wheel
⇒ `VectorEncoder` 只能走关键词通道。grep 出 12+ 个模块受影响，
按危害排序：

| 模块 | 影响 | 危害 |
|---|---|---|
| `nucleus/llm/semantic_cache.py` | 源码自述「相同/高度相似的问题反复调用大模型 → **浪费额度** + 增加延迟」 | ★★★ 直接烧配额 |
| `nucleus/semantic/SemanticIndexer.py` + `vectors.npz`（14899 条） | 同义不同词检索不到 | ★★★ |
| `nucleus/mnemosyne/experience_retriever.py` | 历史修复经验召回退化 ⇒ 重复踩坑 | ★★ |
| `nucleus/qica/QICA.py` / `IntentChannels.py` | 意图分类退化为关键词匹配 | ★★ |
| `nucleus/reasoning/CausalInferrer.py` | 因果链匹配退化 | ★ |
| `nucleus/InsightBoard.py` | 联想/洞察退化 | ★ |

**最要命的是语义缓存**：它失效 = 每次相似问题都真调 LLM。
这跟用户反馈的「百炼额度莫名用完」有直接关系，是一条隐形推手。

### 2. 解法：3.12 长驻 sidecar（不需要重建向量库）

`data/models/fast-bge-small-zh-v1.5/`（94MB ONNX）**本地早就有**，
3.12 里 fastembed + onnxruntime 齐备。实测：

    加载 0.11s（热）/ 1.56s（冷）    编码 0.004~0.006s    维度 512
    与存量 vectors.npz（14899×512）最高相似 0.6525
    ⇒ 同一语义空间，**存量向量一条都不用重建**

### 3. 接法：鸭子类型，`encode()` 一行都没改

`BridgeEncoder.embed(texts, batch_size=N)` 与 `fastembed.TextEmbedding.embed`
签名/返回同构（`list[list[float]]`），所以 `_load_model` 里只加：

```python
_bridge = _m479_try_bridge(cache_dir)
if _bridge is not None:
    self._model = _bridge       # 就这一行
    self._state = "ready"
    return
```

之后维度校验、L2 归一化、批量逻辑**全部照旧生效**
（`test_33` 专门守住这两句质量红线不被桥绕过）。

### 4. 3.14t 真机验收

    state  = ready
    reason = 就绪（BAAI/bge-small-zh-v1.5, dim=512, load=0.12s）
    encode(['曈曈的语义内核如何工作','今天天气怎么样']) → (2, 512)
    模长 = [1.0, 1.0]
    与存量库最高相似 = 0.6525（与 3.12 原生编码**完全一致**）
    encode_one('单一文本测试') → (512,)

### 5. 可靠性

- **懒启动**：首次 `embed()` 才 spawn，失败不拖慢框架启动；
- **保活**：进程死了下次调用自动重启（`_MAX_RESTART=3` 防雪崩）；
- **失败上限**：连续失败 ≥3 次 ⇒ `available=False`，本次运行内放弃桥
  （避免每批都去 spawn 拖慢主链路），自然回落关键词通道；
- **sidecar 设 `HF_HUB_OFFLINE=1`**：本地已有模型时别去探远端
  —— 这是第一次验证时踩的坑（没设 cache_dir / 没断网，代理 502 把启动拖死）。

### 6. 顺带的眼睛收尾

477 批只接了 `PulseVisualCortex`，**PulseEyes 没接** ⇒ 每次启动刷
`WARNING 打开摄像头失败: No module named 'cv2'`，被误读成故障。
改为：感官桥可用 ⇒ INFO（说明改走按需取景）；不可用 ⇒ 才 WARNING。
新增 `m479_look()` 按需取景。

ruff 报 `F821 Undefined name 'e'`。**`compile` 能过、只有 ruff 抓得住** ——
这类笔误正是静态检查存在的意义。
