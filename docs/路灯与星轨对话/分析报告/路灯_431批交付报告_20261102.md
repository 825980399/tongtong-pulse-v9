## 3. 逐刀

### 3.1 刀1：知识库「懒加载」→ 改治内存真凶（**方案与任务书不同，请星轨裁决**）

**为什么没按任务书的懒加载做**

分层 tracemalloc 摊开了 2305MB 堆的构成：

| 层 | 节点数 | 堆占用 | 占比 |
|---|---|---|---|
| L1 | 555 | 33.6 MB | 1.5% |
| L2 | 9792 | 409.9 MB | 17.8% |
| **L3** | **4295** | **1861.8 MB** | **80.8%** |

L3 单节点平均 444.4KB，追下去只有一个字段：**`semantic_relations`**——
L3 平均 **738.4 条/节点**（max 2372），单节点该字段 JSON 文本就 105.9KB；全库 **373 万条**关系、
JSON 文本 550.2MB、反序列化后 1518.2MB。而 L1 的这个字段总量只有 **800 B**。

也就是说：**29% 的节点吃掉了 81% 的内存，且全是「重复取值的短字符串」**。
懒加载要动 40+ 处调用点、还会把成本挪到「首次访问卡顿」（任务书自己也说首访慢是正常的），
但真正的问题不是「什么时候加载」，而是「加载进来的字符串有 373 万份副本」。

**做了什么**

`nucleus/mnemosyne/PulseNode.py` 加**模块级有界共享池**（`_M431_SR_POOL`，上限 10 万，超限一次性停用并告警），
在 `from_dict` 里对 `semantic_relations` 做**原地**取值复用：

- 不用 `sys.intern`：intern 是**进程级永生表**，而 `target_node_id` 有 4205 个且在持续新增 ⇒ 等于给长跑进程造泄漏面。
- **原地替换**（`_it[_k] = _n431`）而不是重建 dict：第一版逐条 `_d={}` 复制实测让加载从 36.6s 涨到 52.6s，改原地后回到正常。

**活体 A/B（两个独立子进程，各跑一次真实加载）**

| 指标 | 关（池停用） | 开（池启用） | 差异 |

| 节点数 | 14642 | 14642 | 一致 |
| 关系总条数 | 3738351 | 3738351 | **一致** |
| 关系类型分布 | causal 2714559 / semantic_similarity 938748 / hierarchy 66117 / cooccurrence 17766 / analogy 1051 / call_dependency 110 | 完全相同 | **一致** |

### 3.2 刀2：pairs 裁切 —— **不是没生效，是裁得太勤**

**现场**

`_trim_pair_file` 每次都要 `readlines(148MB)` + 备份(148MB) + 写 tmp(148MB) + `os.replace`。
当日 `logs/pulse.log` 里 trim 出现 **1349 次**，20/21/22 点高峰各 445/442 次 ≈ **7.4 次/分钟** ⇒ **65 GB/小时**磁盘写。
根因：`_dump_pairs` 每轮只追加几十行，**裁回 cap 后下一轮立刻又超限**，于是每轮都全量重写。

**改法**

加**低水位线**：超上限时一次裁到 `cap × pulse_pair_trim_low_ratio`（默认 0.9 = 450000），
下次要再长 **5 万行**才重写 ⇒ 同等工作量下重写次数从「每轮一次」降到「每 5 万行一次」（≈10 次/日量级）。
`min(cap-1, …)` 保证 cap 很小时低水位**严格小于** cap（否则裁完还超，等于没修）。

**活体读数**：`_pair_file_cap()=500000`、`_pair_trim_low_ratio()=0.9`、`_pair_trim_low_water()=450000`；
边界全对（cap=3→2、cap=1→1、cap=0→回落 500000/450000、ratio=0/True/1.5/缺失→0.9）；
真跑 **500010 行 → 450000 行**，保留首行 seq=50010、末行 500009（**裁的是最老的**），`trim.bak` 保留 500010 行完整。

> **回答任务书第 5 问**：「真的不会再超上限了吗」——**会超，但不会再「每轮超一次」**。
> 语义是「允许涨到 500000，然后一次回落到 450000」，所以瞬时值会在 450000~500000 之间波动，
> 上限仍是硬顶（`min(cap-1, …)` 兜住小 cap）。**这是有意的容量语义变更**，见 §5.1 的测试规格变更。

**改动**：`utils/pulse_tracer.py` +72/−16、`config.py`（`pulse_pair_trim_low_ratio: 0.9`）
**单测**：7 条全绿（超上限裁到低水位／未超不动不备份／裁最老／备份=裁前全量／ratio 非法回落／小 cap 严格小于 cap／真从 RUNTIME_PARAMS 取）
**既有测试**：`test_m401_k2_pairs_cap` 11 条全绿（其中 2 条按铁律 68 改钉新值并注明回滚点）

### 3.5 刀5：`is_template` 覆盖 —— **两次返工，最后把补齐搬进加载路径**

**盘上真实状态（2026-11-03 01:25 快照）**：**344 条 / True 200 / 缺键 144 / 显式 False 0**。
缺键的根因：`annotate()` 只回写**差异条目**（412/413 的取舍，避免全量白写 False）⇒「从没被判过」= 没有这个键。

**第一次做法（失败，重要教训）**：离线改盘上的 JSON 补 143 条 False。
结果：`annotate()` 随后 `_save()` 用**内存池**重写整份文件，把补的 False **全部冲掉**（`landed=212` 但 `have_key` 仍 212）。
改走池 API（`annotate_flags()` + `_save()`）后当次成功（343/343）。

**第二次做法（也被推翻）**：1 分钟后再看盘 —— mtime `2026-11-03 01:25:19`，内容退回 **344 条 / True 200 / 缺键 144**。
原因：**活体进程的落盘权威是内存池**。它启动时加载的是 200 True 的那份内存副本，下一次 `_save()`
就把盘上的 212 True + 131 False **整份覆盖**。⇒ **对持续运行的池，离线补写这条路根本无效。**

**最终做法（耐久）**：把补齐搬进 `ExperiencePool._load()`（`_m431_backfill_template_flag()`）——
加载期给缺键补 `False`，内存里就有键 ⇒ 后续**任何一次** `_save()` 自动持久化，幂等，且不需要停机窗口。
另在 `record_experience` 的入池 dict 里加 `"is_template": False`（新条目从此自带键）。
