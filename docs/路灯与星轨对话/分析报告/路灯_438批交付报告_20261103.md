## §0 三件必须写在最前面的事

### ① 刀1 的真根因不是「阈值不一致」，是 **`prune_pending()` 从来没人调用**

任务书说「回收器 30 天阈值把 10.3 天的件捞回来，审批器立刻判 7 天过期」。前半句对，
但**判定不等于执行**——实测全仓 `grep "prune_pending("` **零个调用方**。
所以 9 条 pending 的真实状态是：

```
status 分布 = {runtime_verified: 9}        ← 一条 reject_stale 都没有
但对它们跑 PatchAutoApprover.classify()：
  reject_stale  8 条（wait 247.7~251.7h > 7 天）
  need_human    1 条（wait 4.2h，age 0.2 天）
  其中 is_obsolete()=True 的 2 条 —— 与任务书「2 条 obsolete」完全吻合
```

**判定天天在跑，回收从来没发生。** 这才是「队列只进不出」的机制性原因；
30 vs 7 的阈值差是第二层（它让回收器把注定判死的件又捞回来一次）。

### ② 刀2 按任务书做完后，基线**结构性恒为 0**——这是**日志格式**的锅，不是探针的锅

活体取证（`logs/pulse.log` 当前 56246 行）：

```
错误级 / Traceback 行            196 行
其中含 ".py" 文件名的              0 行   (0.0%)
```

框架日志格式是 `时间 [模块标签] 级别: 消息`，**从不输出文件名**。
`EVOLUTION_BASELINE_MATCH_MODE="file"` 要求行内出现 `basename` ⇒ 每个文件的
日志基线都只能是 0。这与 46/47 批记录的病根同源（日志考古不可用）。
⇒ 刀3 一旦按 `baseline>0` 收紧，**几乎所有件都会落 `runtime_undecidable`**。
这是**如实的现状**（我们确实没有可用证据），不是刀3 写错了。
**建议 439 批换基线来源**：仓里已有 `nucleus/evolution/patch_active_reprobe.py`
（用 `original_code` 静态复现问题，不依赖日志），把它接成基线主源，日志源降为备份。
详见 §5 裁决项①。

### ③ 刀2 的窗口口径我改了一次（任务书说 24h，实测只能取 19.7h）

首次实现严格按「请求 24h，日志没覆盖满就 unavailable」，活体一跑发现
`pulse.log` 首行只到 **当天 03:00** ⇒ **每个补丁都拿不到基线**，探针等于废掉。
改成 **「请求窗口 ∩ 日志实际覆盖」**，并把**真实用到的窗口长度**写进
`baseline_window_sec`（不假装它等于 24h），另设下限
`M438_BASELINE_MIN_WINDOW_HOURS=0.5`（不足半小时不配叫基线）。
活体结果见 §2.2：请求 24h → 实际 **19.7h**，`baseline_window_sec=70781`。

## §2 刀2：基线探针

### 改动（1 新模块 371 行 + 入队口接线）

`nucleus/evolution/baseline_probe.py`（新增）：

| 接口 | 作用 |
|---|---|
| `log_span()` | 廉价取日志首/末时间戳（读头部 200 行 + seek 尾部 64KB，**不全文扫**） |
| `scan_window()` | 在 `[since, until]` 数 (file, method) 的**错误级**行，并回报窗口覆盖情况 |
| `probe_baseline()` | 取「请求窗口 ∩ 实际覆盖」，返回 `baseline_errors` / `baseline_source` / `baseline_window_sec` |
| `apply_to_patch()` | 写入 `baseline_errors` / `baseline_source` / `baseline_probed_at` / `baseline_shadow` / `baseline_detail` / `baseline_window_sec` |

**三条纪律（写进模块头，单测逐条守）**：
1. 取不到 ⇒ `None` + `source="unavailable"`，**绝不填 0**；
2. 日志没覆盖窗口 ≠ 窗口内没有错（首行晚于窗口起点 / 末行过期 1h 都判 unavailable）；
3. 不改判定——只记录，是否采信由刀3 的开关决定。

**同口径保证**：匹配档位（`file` / `file_method` / `file_or_method`）与错误级判定
（`LogAnalyzer.is_error_level_line`）与 `SafeEvolutionExecutor._count_errors_for_location`
**同源同名**，不复制日志格式知识。

## §3 刀3：延迟复验自证

### 改动（`nucleus/reasoning/SafeEvolutionExecutor.py` +63）

旧判据（`verify_submitted_patches` 的延迟复验段）：

```python
_rbaseline = _patch.get("baseline_errors") or 0     # None 被折成 0
"verified": _rafter == 0,                            # ← 只看修复后
if _rafter == 0: status = "runtime_verified"         # ← baseline=0 也判通过
```

新判据：

```python
_rbaseline = int(...) if isinstance(...) else None    # 保留 None，不再折 0
_rb_undecidable = strict and (_rbaseline is None or _rbaseline <= 0)
_rpassed = (_rafter == 0) and not _rb_undecidable
if _rpassed:        status = "runtime_verified"
elif _rb_undecidable: status = "runtime_undecidable"  # 不置 needs_repair、不回滚
else:               status = "runtime_failed" + 回滚
```

- 与 `verify_fix_from_logs()` 的 **T-99d 口径**（baseline=0 ⇒ undecidable）对齐——
  同一条链上原本有两个互相打架的口径。
- 新增 `_reverify_undecidable` 计数，**不混进** `reverify_failed`。
- 回退：`ENABLE_M438_DELAYED_VERIFY_STRICT=False` ⇒ 逐字回到 `verified = (after == 0)`。

### 活体验证（用**真实归档件**跑真实方法）

从 `pending_patches_resolved.json` 取 3 条 `baseline_errors=0` 的真实补丁，
置 `needs_reverify` 后跑 `verify_submitted_patches()`，
`_count_errors_for_location` 强制返回 0（最容易被误判通过的情形）：

```
baseline=0  after=0 → status=runtime_undecidable  undecidable=True
baseline=0  after=0 → status=runtime_undecidable  undecidable=True
baseline=0  after=0 → status=runtime_undecidable  undecidable=True
汇总 reverified=0  reverify_failed=0  回滚次数=0
```

**回答任务书**：baseline=0 的件状态是 `runtime_undecidable` ✅；
不再有 baseline=0 的件被判 `runtime_verified` ✅（且不误回滚）。

## §5 连带影响与裁决项

### 连带影响

1. **`recover()` 的 `max_age_days` 默认值由常量改为运行时读 config**：
   现有测试无一条断言 `30.0`（已 grep 确认），行为面变化只在「10 天件不再被回收」。
2. **`main.py` 启动多一次 `prune_pending()`**：扫一遍 pending + 归档写盘，实测 < 200ms。
3. **入队口多两件事**（按 1h 节流）：`prune_pending()` 与基线探针。
   探针要读一次 `pulse.log` 首尾（O(1)）+ 命中窗口时全文扫一遍（10MB ≈ 60ms）。
   若嫌重可关 `ENABLE_M438_BASELINE_PROBE=False`。
4. **刀3 会让大量件从 `runtime_verified` 变 `runtime_undecidable`** —— 这是**预期**：
   它们本来就没有基线（§0-②），此前的 verified 是自证。
   用户可见影响：`real_fix_rate` 会进一步下降（从"虚高的 100%"回到"确实不知道"）。
5. **`ENABLE_M438_BASELINE_SHADOW=True` 的含义**：探针结果照写（保证 100% 带
   `baseline_source`），但**不回溯改写历史件**的判定与历史统计。刀3 的收紧只作用于
   之后进入延迟复验的件。若要让 24h 影子期后正式采信，把本键置 False 即可。

### 裁决项（本批**未做**，需你拍板）

**① 基线来源要不要换（最重要的一个）**
当前日志源结构性恒 0（196 条错误行 / 0 条带 `.py`）。仓里已有
`nucleus/evolution/patch_active_reprobe.py`：用 `original_code` 静态复现问题
（`true_pass` / `false_pass` / `partial_fix`），**不依赖日志**，且已有 6 个检测器。
建议 439 批把它接成基线主源：`baseline_source="code_repro"`，
日志源降为备份。否则刀3 收紧后，整条链会稳定停在"全部不可判定"。

**② `pending_patches_resolved.json` 只写不读**
`prune_pending()` 把它当归档 sink，全仓没有读取方。本批沿用既有文件名（未新造

建议 439 一并裁决：要么给它一个读取方（如复盘看板），要么并入 `pending_patches_archive.json`。

**③ 8 条已归档件里 2 条 obsolete 的处置**
