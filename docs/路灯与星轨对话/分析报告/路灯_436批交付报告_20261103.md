## 3. 刀1：AST 扫描次数降了吗？耗时降了吗？

**★T0 核实（任务书前提与实测的差异）**：任务书说「355 次/秒、10.6s」。实测 `detect_code_issues()` 单次 **69s / 7342 次 ast.parse**（全库比任务书假设大），但根因一致：**四个检测器各自遍历全库、各自解析**。

`traceback` 按调用者统计（改造前第 2 轮，mtime 全未变）：

```
_si_resolve_import_mods      1418 次
_detect_unreachable_code     1418 次
code2ast（radon cc_visit）   1418 次
_si_count_branches           1415 次
```

`_si_walk_py()` 实测扫 **1418 个 .py**（tests 792 + nucleus 331 + tools 184 + organs 72 + 其余 39）——不是 435 个生产文件。

**★方案两改（第一版被实测否决）**：
1. **先做「共享 AST 缓存」**（按源码 hash 缓存 tree）：第 2 轮 parse 5754→2670，但容量提到 4096 覆盖 1418 文件时，tracemalloc 显示常驻 **865MB**、首轮从 65s 涨到 **168s**（大对象堆触发 GC）——**省了解析却拿内存/GC 换，净亏**，故 `M436_TREE_CACHE_MAX` 默认置 **0**（保留代码供 A/B）。
2. **改为「检测结果缓存」**（`_m436_memo`，按 `(mtime,size)` 缓存每文件每检测器的**结果**，不是 AST）：全库 5681 条结果只占几十 MB。

**活体数据**（隔离环境 + 真实 `detect_code_issues`，三轮同一进程）：

```
round1 75.6s  parse=7357  cache=5681     ← 首次必须解析
round2 20.6s  parse=85    cache=5681     ← 改前同一行为 56.8s / 5754 次
round3 20.8s  parse=85    cache=5681
```

- **扫描次数：5754 → 85（降 98.5%）** ✅
- **耗时：56.8s → 20.6s（降 63.7%）** ✅
- **内存**：tracemalloc 常驻 191MB / 峰值 299MB（可接受）

**★如实说明：未达任务书「<1s」**。剩余 20.6s 的热点（cProfile 第 2 轮）：
- `threading.wait` 17.2s（`run_group` 结构化并行的**线程等待**，瓶颈是最慢的那个检测器）
- `_m330_classify_hard_tier` 4.1s / `_m348_protocol_iface_declared` 4.0s（已给后者加文件行缓存，收益 <2%）
- `os.walk` 2.2s（19988 次目录遍历）

要再降需重构检测器并行模型（合并全库单遍遍历 + 共享画像），属结构性改造，建议单开批次。

## 4. 刀2：同器官串行生效了吗？吞吐降了吗？

**改动**：`_dispatch_handler` 里每器官一把 `threading.RLock`——
- 同器官的脉冲在同一把锁上**排队串行**（不是拒收，不丢脉冲）；
- 跨器官各持各锁，**互不阻塞**；
- `ENABLE_M436_ORGAN_SERIAL=False` ⇒ 逐字回到改前（直接调，无锁）。

**★为什么不用 `organ_max_concurrent_pulses` 调大**：`_check_organ_concurrency` 超限是**拒收**（`return False` ⇒ 脉冲不投递），会丢脉冲；任务书要的是「串行」（排队）。二者语义不同，故选每器官锁。

**活体数据**（单测内真实并发探针）：

```
同器官 3 条脉冲并发 → 执行峰值 = 1（严格串行）✅
跨器官 2 条（心脏/肝脏，各 sleep 0.15s）→ 执行峰值 ≥ 2、总耗时 < 0.28s（真并行）✅
关开关后同器官 3 条 → 执行峰值 > 1（回到可并发）✅
```

**吞吐**：「跨器官并行」路径吞吐不变（不同器官仍并行）；「同器官」被串行化是**设计目标**（消重入竞态）。单器官吞吐会降，整体吞吐取决于器官间分布——任务书说的「应该不降」只对跨器官成立，**同器官场景是有意降**，如实说明。
