# 让曈曈自己写修改代码：可行性分析与渐进路线

> 473 批收尾议题 · 2026-11-07 · 回答用户的架构设想：
> 「把『谁写修改代码』改成曈曈自己修、外部 LLM 只做检查、曈曈按检查意见调整，
> 以此培养曈曈自己的处理能力、积累经验，最终不再依赖外部 LLM。」
>
> 本文是**设计与可行性分析，不是生产代码改动**。理由见第八节：该变更触及
> 补丁生成主链路与安全边界，按项目惯例需任务书；且曈曈当前在运行、主线刚回归。

---

## 一、直接回答

**方向是对的，而且比现状更对；但有三句话必须先说准，否则会做成"能力幻觉"。**

1. **可以培养能力，但能力的形态不是"曈曈学会像路灯一样推理"，而是"曈曈拥有一个不断增长的、可验证的确定性修复算子库 + 判据库"。**
2. **可以积累经验，但经验必须被"编译成可执行算子"，而不是"写进 prompt 提醒 LLM"。** 现状恰恰是后者，本批已有实证说明它无效（见第二节）。
3. **可以逐步降低对外部 LLM 的依赖，但目标不是全局归零，而是"高频缺陷类目收敛到 0、长尾留给 LLM"；并且必须永远保留一个独立的外部审查者**（理由见第四、七节）。

一句话结论：

> **该设想的本质不是"换一个写代码的人"，而是"把智能从外包服务变成自有资产"。**
> 这个转变值得做，但要用「程序合成 + 独立盲审 + 经验编译」来实现，
> 而不是把 LLM 从生成端挪到检查端就以为能力自动内化了。

---

## 二、先看清现状：曈曈已经有零件了，不是从零建

用户设想的三件事，曈曈其实各自都有一半。把已有零件认出来，方案才不会重复造轮子。

### 2.1 已有的「曈曈自己修」的确定性算子（全部在 LLM 生成**之后**做后处理）

| 算子 | 位置 | 做什么 |
|---|---|---|
| `_m323_reindent` | `PatchManager.py:3348` | 剥公共缩进 |
| `_m445_wrap_fragment` | `PatchManager.py:3547` | 片段 → 完整方法包裹 |
| `_m473_shift_indent` | `PatchManager.py:3682` | 整体平移缩进 |
| `_m473_realign_indent` | `PatchManager.py:3719` | ★刀15：把完整方法对齐回原文基础缩进 |
| `_m92_base_indent` | `PatchManager.py:1004` | 基础缩进守卫（检查，非修复） |
| `detector_hits` | `patch_active_reprobe.py:464` | 静态 AST 缺陷检测（446 刀1 已覆盖多类） |

**这已经是"曈曈自己修代码"的雏形**：它们不调 LLM、确定性、可单测、可回滚。
本批刀15 就是靠 `_m473_realign_indent` 把 4/4 补齐，让 3 条新补丁不再被缩进守卫拒。
缺的只是**地位**——它们现在只是"LLM 写完之后的擦屁股工"，不是一等生成者。

### 2.2 已有的「经验」机制，以及为什么它不算能力内化

| 机制 | 位置 | 形态 | 问题 |
|---|---|---|---|
| `patch_failure_experience` / `append_reminder` | 452 刀6 / 459 | 把失败原因写进**下次 LLM 的 prompt** | `lesson_cooldown.py` 开头实证结论：「**软保证，LLM 不读就等于没写**」 |
| `lesson_cooldown` | 461 批 | `(file, method, error_type)` 连续失败 → 冷却 → **不再生成** | 是**负向约束**（不让再犯），不是**正向能力**（没教会怎么修） |
| 验证学习枢纽 / 知识树 | 326 批等 | 知识条目吸收 | 与"生成补丁代码"没有编译通路 |

⇒ **现状：经验长在 LLM 的上下文里，不运行在曈曈的进程里。**
一旦换模型、换 prompt、清空上下文，经验就归零。这正是用户想解决的问题，而且问题诊断是准的。

### 2.3 本批两次「我替曈曈收口」就是最直接的 PoC 证据

- 刀22b：`715f` 落地补丁丢了 docstring/类型注解、引入裸 `except: pass` → 我手工补成合格代码。
- 刀22c：`aed5` 落地补丁把方法体整体多缩 4 格、丢 docstring → 我手工恢复。

这两次收口**都是确定性变换**（补签名、补 docstring、平移缩进、给 except 补 `silent_exc`），
没有任何一步需要"重新推理业务逻辑"。⇒ 这类缺陷完全可以由曈曈自己的算子修，不必调 LLM，也不必等人。

## 三、三个必须说清的判断

### 3.1 角色翻转 ≠ 能力转移

把"谁写修改代码"从 LLM 改成曈曈，**改变的是决策权，不会自动产生生成能力**。
曈曈是 Python 程序，没有内嵌推理模型。它"自己写"只能是以下四种之一：

| 方式 | 是什么 | 能不能泛化 |
|---|---|---|
| A. 确定性 AST 变换 / 模板 | 程序合成 | 只能在已覆盖的缺陷类目内 |
| B. 历史补丁检索复用 | 案例式推理（CBR） | 依赖历史覆盖率，新类别无效 |
| C. 算子组合 / 搜索 | 受限程序合成 | 组合空间可控但有限 |
| D. 本地小模型 | 仍是"调用模型"，只是不联网 | 有能力上限，且要训/微调 |

**前三种是程序合成，不是推理。** 所以曈曈会变强，但强的形态是「算子库 + 判据库」，
不是「像路灯一样看一眼日志就想到根因」。路灯本身是大模型——把这个能力期待
原样搬到一个规则系统上，会落空。

> 好消息是：**在收窄的、高频的缺陷域里，程序合成比 LLM 更可靠**。
> 本批 LLM 产出的 0 格缩进、丢字段、多缩 4 格，恰恰是规则系统绝不会犯的错。

### 3.2 「LLM 检查 + 曈曈调整」只在**可结构化缺陷**上闭环

「检查比生成容易」是对的（本批八闸、副本验证、AST 指纹都是检查）。
但**「根据检查意见调整」这一步仍然需要生成能力**——只是范围小很多。

| 检查意见类型 | 曈曈能否自己调整 | 依据 |
|---|---|---|
| 缩进不一致 / 层级错位 | ✅ | 已有 `_m473_shift_indent`、`_m92_base_indent` |
| 缺 `modified_code` / 字段契约 | ✅ | 模板补齐 |
| 丢 docstring / 类型注解 | ✅ | 从 `original_code` + AST 提取回填 |
| 裸 `except: pass` | ✅ | 固定替换为 `silent_exc` |
| 非原子写 / 缺重入保护 | ✅（模板化） | 本批两个补丁都是这类标准变换 |
| 语法/import/regression 失败 | ✅（回退或换算子） | `_verify_in_copy` 已有 |
| **语义错误**（改对了语法改错了逻辑） | ❌ | 需要理解意图 |
| **架构/跨模块契约问题** | ❌ | 需要全局因果推理 |
| **并发竞态 / 时序** | ❌ | 需要运行时语义 |
| **全新缺陷类别** | ❌ | 没有算子、没有历史案例 |

⇒ 闭环要成立，检查意见必须先被**归一成结构化 `error_type`**，
再由 `fixer_registry[error_type]` 分派。做不到归一的，降级回 LLM。
**不要让曈曈去"理解"自由文本的 review 意见**——那等于把生成难题又请回来了。

### 3.3 「不再依赖外部 LLM」应改为「分类目收敛到 0」

开放域代码修改是组合爆炸的，用规则累积去覆盖所有可能，是符号主义 AI 的老问题。
现实且可验收的目标是：

```
llm_dependency_rate(按 error_type 分桶) → 高频类目降到 0，长尾保留
```

而不是 `全局 LLM 调用次数 = 0`。把"完全不依赖"当 KPI，会逼出
「为了不用 LLM 而硬写规则覆盖长尾」的畸形系统，可靠性反而下降。

## 四、四个结构性风险（不是保守，是硬约束）

### 4.1 自指 / 循环论证 —— 最危险的一条

如果曈曈**自己写、自己验、自己判**，判据就失去了独立性。
项目铁律 30 正是为此：**「断言里拿被测函数的输出当基准 = 循环论证，基准必须来自另一个入口」**。

本批已有原型事故：15:17:49 出现 `[461刀3] verdict=apply`（自裁决说"证据齐备 ⇒ 放行"）
与 447 八闸 `approved=False` 同帧，排查很久才确认是历史结果单回放 + 两套判据并行。
如果再让"生成器"和"验收者"都归曈曈，这类冲突会变成常态。

**设计约束**：生成侧与验收侧必须是**不同实现、不同数据源**；外部 reviewer 至少保留在
"抽验 + 出题"位置。

### 4.2 判别力退化（铁律 35）

判据在旧代码上也成立 = 自欺。曈曈自己给自己写的算子配单测，最容易写出
"怎么改都绿"的断言。必须强制：

- 每个新算子配**反证用例**：关掉算子后同一输入必然失败（本批刀15 单测已有此范式）；
- 基准来自**另一个入口**（如 `AB.decision()` 复核，而不是复用算子自己的输出）。

### 4.3 审查者附和（sycophancy）

LLM 当 reviewer 时，如果把曈曈的推理过程、自裁决结论一起塞进 prompt，
模型会倾向于附和"看起来已经论证过的结论"。**必须盲审**：
只给 `diff + 目标文件上下文 + 检查清单`，不给曈曈的推理链、不给它自己的结论。

### 4.4 算子库需要「出题人」

谁来发现曈曈的判据盲区？本批 `_m92_base_indent_guard` 只比首行、
方法体多缩 4 格照样全闸门放行——这个盲区是**我（外部）**发现的，
不是曈曈自己发现的。一个完全自洽的系统无法看见自己的盲区。

⇒ 外部 LLM 的长期价值之一，是当**独立的出题人/红队**，而不只是审查者。

## 五、三阶段渐进路线

### 阶段 0 · 现状（基线）

```
LLM 生成 modified_code → 曈曈后处理算子 → 副本验证 → 八闸 → 应用
```
指标：`llm_dependency_rate = 100%`；经验以 prompt 提醒形式外包。

### 阶段 1 · 角色翻转（**不改任何安全闸门**）

新增两个组件，全部**影子模式 + 灰度开关**起跑：

```
PatchSynthesizer（曈曈自己）
  ├─ 按 issue_type 分派 fixer_registry 里的确定性算子
  ├─ 覆盖不了 → 降级调 LLM（保留原路径，逐字可回滚）
  └─ 产出 draft_patch + applied_operators[]

ReviewDispatcher（外部 LLM，盲审）
  ├─ 输入：diff + 目标文件上下文 + 检查清单（不给推理链）
  └─ 输出：review_findings[{error_type, severity, evidence, span}]

RepairLoop（曈曈自己）
  ├─ 按 error_type 查 fixer_registry 调整
  ├─ 最多 N 轮（配重试上限，铁律 55）
  └─ 无对应 fixer 或轮次耗尽 → 降级 LLM / 转人工
```

**关键顺序**：`曈曈先出草稿 → LLM 只检查 → 曈曈按结构化意见调整`。
这与用户设想完全一致，只是把"检查意见"钉成 `error_type` 而非自由文本。

**本阶段不改**：八闸、`decision()`、`_verify_in_copy`、`apply_all_pending`、日限额、冷却。
只是把**生成源**换掉，下游全部复用。

**验收判据**：
- 影子模式下 `draft_patch` 与现链路 LLM 补丁做 A/B，统计「谁需要更少后处理」；
- `review_catch_rate`（LLM 检出的缺陷中，曈曈能自己修掉的比例）；
- 关掉开关后逐字节回到现状。

### 阶段 2 · 经验编译（这一步才是真正的「能力内化」）

```
for (error_type, 修复动作):
    if 被 LLM 指出 >= N 次 且 曈曈修复后通过全部闸门:
        → 抽成新算子，进 fixer_registry
        → 配反证单测 + AST 结构指纹
        → 该类目后续不再问 LLM
```

**这是"积累经验"的准确形态**：不是权重更新，不是 prompt 变长，
而是**可执行算子 + 判据 + 反证用例**三件套的增长，且每一条都能被 git 追溯、被单测守护。

配套改造：现有 `patch_failure_experience.append_reminder` 从「写给 LLM 的软提醒」
升级为「写给 `fixer_registry` 的候选算子线索」；`lesson_cooldown` 保留为安全兜底
（连续修不对就停手），但不再是唯一的"学习"手段。

### 阶段 3 · 收敛与度量

按缺陷类别统计，把高频类目逐个迁出 LLM。长尾（语义/架构/新类别）明确保留给 LLM。

## 六、能力指标的准确定义

| 指标 | 定义 | 目标 |
|---|---|---|
| `llm_generation_rate` | LLM 生成补丁数 / 总补丁数 | 按类目收敛，高频 → 0 |
| `self_synthesis_rate` | `PatchSynthesizer` 独立产出且过闸 / 总补丁数 | 逐步上升 |
| `review_catch_rate` | LLM 盲审检出且曈曈自己修掉 / LLM 检出总数 | 上升到阈值后编译算子 |
| `fixer_coverage` | 有确定性算子的 `error_type` 数 / 已观测 `error_type` 数 | 稳步上升 |
| `operator_rollback_rate` | 新算子上线后触发回滚的比例 | 必须低于现链路补丁回滚率 |
| `red_team_find_rate` | 外部独立红队发现判据盲区的数量 | **不追求降到 0**（降 0 = 没人出题了） |

★ 最后一个指标是刻意设计的：**它防止系统把"没人发现盲区"误当成"没有盲区"**。

---

## 七、为什么仍要保留外部 LLM（三条结构性理由）

1. **独立基准**：防止自写自验自判的循环论证（4.1）。这不是保守，是判据有效性的前提。
2. **开放域长尾**：全新缺陷类别、语义/架构/并发问题，没有算子也没有历史案例时，
   必须有一个能生成的东西兜底。
3. **出题人**：发现判据盲区（4.4）。本批「层级一致性缺口」就是外部视角发现的。

⇒ 更准确的终局描述不是「曈曈不再依赖 LLM」，而是：

> **曈曈拥有自主生成、自主验证、自主积累的闭环；外部 LLM 退居
> 「独立审查 + 长尾兜底 + 红队出题」三个位置，且调用率可度量、按类目收敛。**

这已经非常接近用户想要的「真正能自主修改自己的状态」——
而且比"完全零依赖"更可靠、更可验证。

---

## 八、为什么不现在就改生产代码

1. **触及安全边界与生成主链路**：按本批自己定下的纪律（「不改安全闸门需任务书」、
   「判据变更需任务书 + 灰度」），这属于主线段议题，应由星轨出任务书。
2. **曈曈正在运行**（pid=37744，5051/5052 监听），改生成链路需要重启验证。
3. **主线刚回归**：本批已判定闭环成立，此时引入架构变更会破坏已验证状态。
4. **需要 A/B 基线**：阶段 1 必须先在影子模式跑出对照数据，直接切换无法判断优劣。

**建议 PoC 范围**（第一期任务书）：

- 只覆盖 **3 类高频缺陷**：缩进/层级、字段契约+docstring、裸静默 except；
  （这三类本批都有真实样本：`715f`、`aed5`、刀22b/c 的收口动作）
- 影子模式：产出 `draft_patch` 但不进主链路，只写台账；
- 灰度开关 + 反证单测 + 独立复核入口；
- 验收：`review_catch_rate ≥ 阈值` 且 `关闭开关逐字回滚` 且 `门禁全绿`；
- 明确不改：八闸、审批、应用、日限额、冷却。

## 九、结论

| 用户的问题 | 回答 |
|---|---|
| 能否培养曈曈自己的处理逻辑和能力 | **能**，但形态是「确定性算子库 + 判据库 + 反证用例」，不是让程序学会通用推理 |
| 能否逐步积累经验 | **能**，但必须把经验**编译成可执行算子**，不能继续只写进 prompt；现状 `append_reminder` 已被实证是软保证 |
| 能否最终不依赖外部 LLM | **高频类目可以收敛到 0，全局不建议归零**；保留独立审查者/长尾兜底/红队是结构需要 |
| 角色翻转是否值得做 | **值得，且比现状更对**——它把能力从"外包服务"变成"自有资产"，本批两次手工收口已证明技术可行 |

最该先做的一件事：**把本批刀22b / 刀22c 我手工做的两次收口，
原样抽成 `fixer_registry` 的前三个算子**。它们有真实输入、真实输出、真实验收记录，
是这个方向成本最低、证据最硬的起点。
