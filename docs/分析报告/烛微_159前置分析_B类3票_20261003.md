### 1.2 状态表衔接：`task_ledger` 现枚举**装不下四步**，但复用其三项机制才是正解

现状：`VALID_TASK_STATUS = frozenset({"running","done","interrupted"})`（`task_ledger.py:71`），`TASK_LEDGER_VERSION="158A-OA1-1"`；单任务字段 `status/pid/started_at/last_write/heartbeat/meta/pending_reply`（`:186-196`）；单事务原子写 = `temp + os.replace`（`:153-176`）；**不回放不续跑** = `replay:"forbidden"` + `no_redo:True` + `dedup_key="<task_id>@<last_write>"`（`:305-313`）。

判定与提案：

1. **不要把四步塞进 `VALID_TASK_STATUS`**。该枚举的语义是"重启恢复协议"（进程级任务存活），补丁是"变更生命周期"（跨重启需长期驻留）。混用会直接踩雷：`reconcile_on_startup` 对 `status=="running"` 且 pid 已死的条目一律改判 `interrupted`（`:272-289`）→ 若"activated 未 handoff"复用 `running`，**补丁会被对账器当成死任务改判**，激活态丢失。
2. **推荐扩展形制**：同一文件（`data/evolution/`）新增 **section** 而非改枚举——
   - `patch_lifecycle.json`：`{version, patches:{patch_id:{stage, stage_at, task_id?, risk_level, file, backup_path, rollback_available, verified_by, attempts, observation_deadline, owner, handed_off_at, notes}}}`
   - 阶段枚举建议（7 态，单调可回退）：`proposed → validated → activated → observing → committed`，旁路 `rolled_back` / `rejected`
   - **复用已验证的三项机制**，不新造：① `_atomic_save` 的 temp+`os.replace`+fsync 单事务；② `reconcile_on_startup` 增加"补丁段对账"（`activated`/`observing` 超 `observation_deadline` 未 `committed` → 出诊断回执、**标记待人工**而非自动回滚）；③ `dedup_key`+`no_redo` 免重做语义（避免同一补丁重复触发回滚）。
   - `TASK_LEDGER_VERSION` 随之递增并保留旧值读取分支 → **存量迁移兼容**：`patch_history.json` 86 条 + `pending_patches.json` 27 条**不需要迁**（lifecycle 表按 patch_id 懒建，缺失即 `stage=unknown` 并出 WARNING），因此**无需破坏性回填**，这是本票最大的降风险点。
3. `finish_task` 的 `status not in VALID_TASK_STATUS or status=="running"` 校验（`:210`）是扩展时必须同步的唯一硬点；`heartbeat_task` 只认 `running`（`:199`）→ 若补丁需心跳（观察期存活证明），应新增 `touch_patch()` 而非放宽该判断。

### 2.2 签名机制落点（推荐：扩既有件，不新建门禁）

- **必须换掉明文拼接**：现 `rule_signatures()` = `"title|severity|scope"`（`:145`）——**不含 checker 函数体**，改检查器逻辑（即真正会改变检测行为的部分）**指纹不变**，等于没防。

- **落点选择**：**扩 `verify_fingerprint_gate.py`**（它已经是"签名 + 漂移 + 破坏预检"三件套，且已有 `fp_rule_signature` 概念位），新增 `tools/ci/baselines/rule_signature_baseline.json` + 第⑩项比对（漂移即红）。**不建议新建门禁脚本**——`tools/ci/` 已有 **17 个**脚本，hook 链刚在 15:46 加到 1.9 段，再加一段的边际成本高于复用。

### 3.2 关键澄清：**微光/票面的内存推理链有一处断裂**

`.bak` 由 **`os.rename`** 产生（`:861`）——改名不复制字节、不占额外内存。所以「.bak 每小时整副本 1488MB」**是磁盘占用，不是内存成本**，不能用它推导 RSS 增长。真正的内存成本在三处：① `_build_full_snapshot`（`:482`）；② 流式写缓冲（`SNAPSHOT_BATCH_SIZE=1000`，`config.py:4749`）；③ 节点池本身（12.4k 节点常驻）。
`SNAPSHOT_ASYNC_SAVE=True`（`:4747`）+ 独立线程（`:844 Thread("SnapshotAsyncSave67")`）说明写盘已异步化；`SNAPSHOT_SAVE_TIMEOUT=1800`（`:4748`）+ 超阈值仅告警不中断（`:840-842`）。

与 **T-运行内存增长-1**（P2/160，待裁决）的关联判定：该票权威口径为总账 `docs/完整进化路线与技术债务清单_v1.0.md:632`「内存 3730→6037MB（+2.3GB）、脉冲 539→20986，观测 2.4h」≈ **+16MB/min**。
- 若增长由检查点驱动，应表现为**锯齿**（每 3600s 尖峰后回落）；+16MB/min 线性意味着 2.4h 内累计 2.3GB，而期间只有 2–3 次全量检查点 → **量级上不能用"2–3 次 × 单次缓冲"解释**，故我判定**快照写盘不是主因**，最多贡献尖峰。
- 旁证（口径不同，不可当 RSS 用）：`[框架] 硬件深度自适应` 的**系统内存余量**单调下降 37.1→34.5→32.3GB（`pulse.log` L183/L733/L1186，01:07→01:12→12:28）——这是全机余量，含他进程，**不能等价为框架 RSS**。

### 3.3 接管方案 + 恢复链设计（回答"崩溃恢复依赖整副本怎么办"）

1. **全量点选择**：保留"整点 + 变更超阈"两个触发；`FULL_SAVE_INTERVAL` 提到 6h/24h 后，**必须同时降低 `INCREMENTAL_MAX_NODES` 上界的失效风险**——现状 `变更>200 即走全量`（`:445`），在 12k 节点 + 肝脏持续压缩（`PulseLiver.py:1476/1598` 即时 `snapshot.save()`）下，**很可能长期无法满足"≤200"条件 ⇒ 事实上每次都走全量**，这才是"接管没生效"的真正原因（比"并存浪费"更准的表述）。→ 前置取证：`_get_changed_nodes` 的实测变更数分布（本审计未取，列为 L-1）。
2. **恢复路径**：`启动 → 读主 JSON（或 Parquet）→ _m67_apply_incremental_log 重放 jsonl`（`:1680-1681`），重放已具备**定序 + 幂等 + 类型统一 + 行 checksum 校验 + 单行损坏只跳过该条**（`:1111-1199`）。**这条恢复链已经写好且被 45 次实跑验证** → 降频整副本的可行性主要取决于 jsonl 能撑多久不损坏：`SNAPSHOT_INCREMENTAL_LOG_MAX_LINES=50000`（`:4765`）到限即触发清理/合并（`:1051`），`DELETE_RATIO_MAX=0.5`（`:4769`）防误删过半。
3. **崩溃窗口**：`<30s 未落盘`（`:402-408`）+ `jsonl 追加失败回退增量保存`（`:457`）→ 最大丢失窗口 ≈ **30s**；但若 D-4（节流 `return True`）不修，**调用方与退出路径会误判"已保存"** → 接管前建议修 D-4，把"延迟落盘"显式化为 `pending_flush=True`。
4. **退出全量关系**：`main.py:2832 save(force_full=True)` + 300s 线程超时与 `:2846` 明示「**未保存变更将丢失（不谎称增量恢复）**」；`:437-439` 注释给出**实测：8700 节点下增量 170s vs 全量 9s（慢 10 倍以上）** → **退出/启动路径必须继续走全量，不可为省磁盘把退出也改增量**（这是本票的硬边界）。
5. **回滚预案**：改 `SNAPSHOT_FULL_SAVE_INTERVAL` 是**单值可回退**（改回 3600 即恢复现状），且 `SNAPSHOT_SAVE_JSON_BACKUP=True` 保留 JSON；建议按 `[ci-gate-change]`/开关变更独立 commit，附前后 24h 的 .bak 数量与体积对比。

### 3.4 降频参数与验收判据

参数建议：`SNAPSHOT_FULL_SAVE_INTERVAL: 3600 → 21600`（先 6h，观察一周期再谈 24h）；`.bak 保留数` 需先定位其轮转清理策略（本审计实测停在 3 份，**清理逻辑位置未取到**，列 L-2）——**保留数不改，降频只会让稳态副本更旧、不省磁盘**，这是接管能否真省 1.0–1.3GB 的前置。

验收判据：(a) 24h 内 .bak 新增数从 24 → ≤4；(b) `snapshot_incremental.jsonl` 行数在窗口内单调可控且**未触 MAX_LINES 清理告警**；(c) 一次受控 kill -9 后重启，**重放后节点数 = 崩溃前 `last_write` 对应值**，且日志出「增量日志重放完成: 应用 N 条」N>0；(d) 退出全量耗时仍 <90s（对照实测 9s/8700 节点余量，12.4k 节点需重测）；(e) 内存侧：若同键采样落地，可给出"尖峰 vs 基线"分离结论，替 160 批提供判据。
