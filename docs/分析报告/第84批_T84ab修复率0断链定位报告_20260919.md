## 2. T-84a 断链精确定位（三层，缺一不可）

### 第 1 层：`problem_fixed` 的**唯一写回点**在补丁落盘时，之后永不重算 ← **可修**

- 写回点：`nucleus/reasoning/PatchManager.py:1956-1960`

  ```python
  from nucleus.evolution.patch_verification_split import apply_split as _apply_split
  _apply_split(patch)          # ← 全库唯一的运行时 apply_split 调用
  ```
- 该点位于 `apply_all_pending()` 的**应用循环内**（补丁刚写入活代码时），此刻：
  - `post_apply_errors` **尚未产生**（要等运行时验证，且要求 `applied_at` 之后 ≥300 秒）；
  - `baseline_errors` 多为 0。
  → `split_verification()` 必然落到 `_baseline is None / not _baseline / _after is None` 分支 → `problem_fixed = None`。
- 之后 `SafeEvolutionExecutor.verify_submitted_patches()`（L1849-1853）与 `verify_applied_patches()`（L1996-2004）写回了
  `runtime_verified` / `runtime_verify_result` / `post_apply_errors`，**却没有再调用 `apply_split`** → `problem_fixed` 永久停留 None。
- **这是任务书"跑了但没写回"猜中的那一层，也是本批唯一可以直接补的点。**

### 第 2 层：`baseline_errors` 在 `file` 模式仍 **61/64 = 0** ← 设计上不可判定，**不可硬凑**

- `_count_errors_for_location()`（`SafeEvolutionExecutor.py:1658-1722`）计数判据：
  读 `logs/pulse.log` → 窗口 `since = now - EVOLUTION_BASELINE_WINDOW_DAYS(7) 天` →
  命中行须 `(is_error_level_line 或 含 "Traceback"/"Exception")` 且 `file_basename in line`。
- 第41批已把判据从 `file_method` 放宽到 `file`（`EVOLUTION_BASELINE_MATCH_MODE="file"`），
  该批 docstring 自述"56 个补丁位置放宽后仅命中 **8** 条" → 即**绝大多数目标文件在近 7 天日志里没有错误行**。
- `patch_verification_split.py:146-152` **故意**把"基线为 0"判为 `problem_fixed=None`：
  > `旧逻辑会把它当成"修复前 0 个错 → 效果 100%"，实际是"基线根本没采到"`
  → 这是**正确的诚实设计**，不能改成 True/False（改了就是造假指标，违反铁律 56）。
- ⇒ 结论：**靠日志基线永远无法让大多数补丁"可判定"**。

### 第 3 层：`reprobe_verdict`（第51批设计的"最高优先级、不受日志轮转影响"判据）**在运行时从未写入** ← 真正的架构断链

- `patch_verification_split.py:119-141` 的**第一优先级**：

  ```python
  _rp = patch.get(F_REPROBE_VERDICT)          # 'true_pass' / 'partial_fix' / 'false_pass' / ...
  if _rp == "true_pass":      _problem_fixed = True     # ← 代码级判据，不需要 baseline
  elif _rp == "partial_fix":  _problem_fixed = True
  elif _rp in ("false_pass", "ineffective"): _problem_fixed = False
  ```
- 即：**只要 `reprobe_verdict` 有值，`problem_fixed` 就与日志基线无关**（这正是第51批设计意图）。
- 实查：`active_reprobe()` 的调用方**只有** `tools/reprobe_patches.py`（一次性批处理工具）与
  `nucleus/self_awareness/quality_score_v2.py`（只读 `true_fix_rate`）。
  **`PatchManager` / `SafeEvolutionExecutor` / `PulseCodeLearner` 三处运行时链路均未调用 `active_reprobe`。**
- ⇒ history 里 60 条 `reprobe_verdict` 字段存在但值为 `null`（第51批批处理回填过一次，之后新补丁再也不写）。
- ⇒ **要让"真实修复率"对基线为 0 的大多数补丁也变得可判定，唯一正解是在补丁**应用/验证**时接入 `active_reprobe`。这是架构级接线，本批按任务书"不要硬上"处理。**

## 3. T-84b 断链精确定位（任务书前提需改写）

### 3.1 任务书前提的实查反驳

- 全库 grep `_repaired`：`SafeEvolutionExecutor.py` 内只有
  `L1582: _repaired = _local_submitted + _submitted`、`L1606/1613/1619/1620`（使用点）。
  **不存在 `_repaired += 1`**，也不存在"运行时确认"作为其门槛。
- `_repaired` 语义 = **本轮的"提交待审批"补丁数**。
- 实测每轮 `_local_submitted=0 且 _submitted=0`（`submitted/local_patched/local_verified` 全 0）
  → `_repaired=0` → `PatchAutoApprover.fix_rate = 0/found = 0%`。

### 3.2 为什么 `submitted=0`（真因链）

1. **问题类型 100% 落在本地规则能力之外**。
   `_bump_reason` 分类（`L1486-1523`）对每轮结果的分布（§1.5）全部是
   `本地无规则·转LLM(Traceback / ERROR / cross_module_singleton_call / long_method)`
   —— 这些 type ∉ `_local_fixable_types`，本地规则引擎**按设计不产出补丁**。
   由于 `_bump_reason` 在这两类下的分支顺序（`L1513`）正是"最后一个 elif"，说明**整条提交段
   （L1448-1480）都没有走到 `_local_submitted += 1` / `_submitted += 1`**。
2. **LLM 路径同样无产出**。全日志 `[自主修复]` 仅 1 条（09-18 13:51），此后无新的 LLM 补丁提交。
3. **即使有补丁也永不落地**：`config.EVOLUTION_CONFIG["auto_apply_enabled"] = False`
   （`config.py` 第 S1 条注释："★S1：关闭自动改写源码，需人工审批后再开启"）。
   `main.py:3289` 只调 `apply_all_pending(only_approved=True)`，而 `PatchManager._m80_auto_apply_enabled()`
   默认读该开关 → False ⇒ **落地闸门关闭**。这就是 §1.4 那 4 条 `auto_approved=true` 却 `applied=false` 的原因。

### 3.3 判定

- `_repaired` 的**门槛不是"过高"，而是"根本没东西进来"**。
- 让 `fix_rate` 变正有三条路，**全部超出"最小改动"边界，需星轨决策**：
  - (i) 扩充 `_local_fixable_types` 覆盖 Traceback/ERROR 类（**改自动化行为**，风险高，本批不做）；
  - (ii) 让 LLM 补丁路径真正产出（需先查清 LLM 门禁/验证为何零产出，属独立课题）；
  - (iii) 打开 `auto_apply_enabled`（**红线②禁止改 config 开关**，且属星轨的安全决策，本批不碰）。
- **本批可做的、诚实的最小改动**：把"提交"与"已应用/已验证修复"**在计数上分开**
  （任务书 T-84b 第 2 条的本意），使 `修复率` 不再把一个含义模糊的数当"修复数"。
