## 一、刀1′ · 补反射边（P0）—— event 0→217、entry 0→23、byname 3→11

**问题**（烛微）：305 刀2 分色落地名义达成、实质只有 3 条边；`kind` 字段确实在边上，但分布是
`{static: 7367, byname: 3}`，`event: 0 / entry: 0` —— 两类根本没有写入路径。

**改动**（`nucleus/self_awareness/CallGraphAnalyzer.py`，+360 行）：

| 子项 | 实现 |
|---|---|
| 事件枚举规范化 | 新增 `_event_taxonomy()`：静态解析 `nucleus/const.py` 的 `*Event` 类成员 → `"mouth.reply"`。**这是 event 边恒为 0 的根因**——发/订两侧源码大多写枚举成员（`MouthEvent.REPLY`），不做规范化两侧字符串不可比。纯 AST、不 import、不执行 |
| event 边（发） | `_sniff_event_and_entry()` 识别 `self.pulse_core.emit(event_type=...)`（含第 2 位置实参形态）→ `self.emits` |
| event 边（订） | `_collect_roles()` 取两个权威来源：① `get_resonance_conditions()` 里 `event_types` 列表（处理器身份=本类 `on_pulse`）② `on_pulse()` 体内 `event_type == X` / `in (...)` 判定；`["*"]` 记通配订阅者 |
| event 边（连） | `_pass2_reflect()`：订阅索引 `event → [handler_id]`，对每个发射点建 `kind="event"` 边（跨器官 Y→T→X 的**方法级**投影，排除自环；通配订阅者对全部已发射类型建边） |
| entry 边 | 注册类调用（`register*` / `add_daily_hook` / `add_handler` / `subscribe` / `attach`）的可调用实参 → `kind="entry"` 边。支持 `f` / `self.f` / `Cls.f` / `mod.f`，以及 `handler=lambda p: self._on_x(p)`（注册条件时几乎全用 lambda 适配签名） |
| byname 升级① | `_resolve_by_name()` 从「多义即放弃」升级为**作用域优先消歧**：同类 → 同模块 → 同目录 → 全库唯一，仍多义才放弃（不猜测） |
| byname 升级② | 新增 `visit_Dict`：字符串键 → 可调用体的**按名派发表**（`{"refresh": self._do_refresh, ...}`）计入 byname。判据刻意加严：键**全部**为字符串常量、值**全部**为可调用引用、数量对齐（否则 `{"ts": _ts}` 这类数据字典会误连） |

**实测**（全库 6754 节点 / 7633 边，耗时 12.9s）：

```

```

- event 217 条：最大订阅方 `PulseBloodVessel.on_pulse`(47，通配订阅) / `PulseSubconscious.on_pulse`(17) / `PulseCortex.on_pulse`(16)
- entry 23 条：`PulseFramework._init_self_awareness → analyze_production_consumption / analyze_fake_loops`、`PulseFramework.start → _on_auto_save / _on_self_modify_constraint / _on_motivation_urge / _on_emotion_signal / _on_launch_plan`、`EventTap.start → EventTap._on_event` 等

## 二、刀2′ · 三轨合一（P0）—— problem_fixed 只剩一个派生源，68 对 58 已消除

**问题**：305 刀5 的 `problem_fixed` 由 T4 派生**只落在评估器输出层**，评估器自己 `bool(_reprobe_ok or _real>0)` 又派生一遍、还把「不可判定」折叠成 False ⇒ 两个同名数字：评估器 84/84（True 68 / False 16）、台账层 84 条（True 58 / None 26）。

**改动**：

- `nucleus/evolution/patch_verification_split.py`
  - 新增 **`derive_problem_fixed(patch) -> (value, reason_code)`：全仓唯一派生源**。规则：`true_pass` 且复现基线命中 → `True`；`false_pass`/`ineffective` → `False`；`partial_fix` → **`None` + partial 标**；`verification_failed` → `None`；`not_applicable`/缺失 → `None`；**仅当完全没有探针结论时**才退文件级基线对比（legacy 兜底）
  - 新增原因码：`reprobe_true_pass` / `reprobe_false_pass` / `reprobe_ineffective` / `reprobe_partial_fix` / `verification_failed` / `no_probe` / `legacy_unverifiable` / `baseline_compare`，随 `problem_fixed_reason` / `problem_fixed_partial` 一并落字段
  - `split_verification()` 删掉自带的一整段分支（原 60 行），改调派生源；`apply_split` / `backfill` 同步写原因码
  - `real_fix_rate()` 改为**同源**：一律重派生（带原因码的投影 dict 直接采信，避免对已剥离探针字段的 dict 重算出另一套数）；只保留 `problem_fixed_corrected` 人工锁定例外
- `nucleus/evolution/patch_quality_evaluator.py`：`evaluate_patch()` 删掉 `bool(...)` 折叠，改调同一派生源并输出原因码

**实测（patch_history 84 条）**：

| 口径 | 修正前 | 修正后 |
|---|---|---|
| 评估器输出层 | True 68 / False 16 | **True 58 / None 26** |
| 台账层（split） | True 58 / None 26 | **True 58 / None 26** |
| 逐条一致 | ✗（差 10） | **✓ `equal_pf=True`** |
| `real_fix_rate` 两处 | 0.9444 vs 1.0 | **1.0 / 1.0（同源）** |

原因码分布：`reprobe_true_pass 54`｜`no_probe 15`｜`reprobe_partial_fix 7`｜`legacy_unverifiable 4`｜`baseline_compare 4`。
不可判定（26 条）**全部保留 None 并带原因码**，无一条被折叠成 False；评估器 `unverifiable` 标签仍是 14 条（与烛微口径一致）。

| 编号 | 事项 | 说明 |
|---|---|---|
| D1 | **dead_code 当前实测 0 条** | 305 刀1 的「判据让位」（图入边覆盖率 <70% ⇒ dead_code 判据主动沉默）尚未复原，所以新阈值眼下读数是 0。尺子已装上且 FAIL 路径已用合成数据实证；待图覆盖率恢复（本批补的 217 条 event 边 + 23 条 entry 边正是为此）后自然生效。**不得据「dead_code=0」判定「已无死代码」** |
| D2 | 并发扫描污染计数 | 首跑 `medium=52`（当时另一进程在同时扫描，`_issue_states` 状态机被并发改写），复跑 `medium=44`。采信**复跑**：44 ≤ 48 PASS。门禁属单进程工具，CI 串行调用不受影响 |
| D3 | `avg_fix_rate` 未改 | 它长在 `PatchAutoApprover.get_stats()`，是**轮次级**指标（found/fixed 计数均值），与补丁级 `problem_fixed` 不同量纲，强行合并会混淆口径。本批统一的是补丁级的 `problem_fixed` / `real_fix_rate` |
| D4 | 台账文件未回写原因码 | 纪律「不碰 data/」，`patch_history.json` 未改。派生源与写回通道（`apply_split` / `backfill`）已就绪；且实测存储值与派生值**逐条相等**（58/26），故无需落盘也对得上。需要把 `problem_fixed_reason` 也写进台账时，跑一次 `backfill(load_history(), apply=True)` 即可 |
| D5 | `real_fix_rate == 1.0` | strict 口径下 26 条不可判定出分母后，可判定样本 58 条**全部 True**（False=0）⇒ 58/58=100%。这是**旧台账层本来就有的值**，本批只是把评估器（0.9444）对齐到它。指标饱和的根因是「没有一条补丁被证伪」，不是口径放水 |
| D6 | byname 只到 11 条 | 不是不敢放宽，是可放宽的形态就这么多：`getattr(x,"字面名")()` 全库仅 17 处；派发表按「键全字符串 + 值全可调用 + 数量对齐」加严后剩 11 条。放开判据能到数十条，但会把 `{"ts": _ts}` 这类数据字典误连成「按名派发」，故不加 |
| D7 | 工具需 `PYTHONPATH=.` | `python tools/check_code_issue_trend_302.py` 直接跑会 `ModuleNotFoundError: nucleus`（`sys.path[0]=tools`）。既有行为，未改（属 CI 调用约定）；本次实测均带 `PYTHONPATH=.` |
