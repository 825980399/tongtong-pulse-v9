## 一、执行摘要

### 1.1 核心命题

让曈曈PulseNet框架根据自身运行产生的数据，训练并孕育适用于自己的**内在模型群**，逐步从"完全依赖外部大模型"走向"自有模型为主、大模型为辅"，最终实现框架拥有"自己的灵魂"。

### 1.2 ★现状痛点（基于三方实测）

| 指标 | 当前值 | 问题 | 数据来源 |
|------|--------|------|---------|
| 大模型依赖度 | **96.96%** | 但**98.8%来自进化循环，对话=0（未埋点）** | 路灯实测 |
| LLM调用留存率 | **2.4%** | 2103次调用仅保存50对输入输出 | 第三方实测 |
| 进化验证 | **空转** | 56个已应用补丁baseline_errors=0，100%假通过 | 双方一致 |
| 数据规模 | **4.8GB** | 含1.98GB ONNX模型、2.7GB知识目录、1273个损坏文件 | 路灯实测 |
| 经验库污染率 | **79.9%** | 1501条中1199条polluted | 第三方实测 |
| 本地推理占比 | **3.1%** | 66次本地推理 vs 2103次大模型调用 | 双方一致 |

### 1.3 ★核心结论（修订版）

> **可行，但必须"先测量、再修根因、后建模型、全维度渗透"四步走。**

1. **先测量**：当前"依赖度97%"只覆盖4个埋点（98.8%是进化循环），对话类未埋点 → **必须先补全埋点、重算基线**
2. **再修根因**：依赖度的真实根因是「进化验证空转→重复修复→重复调LLM」。**修好真实基线比建任何模型都更直接**
3. **后建模型**：按"作用于多少比例调用"排序，首期从「补丁质量评估器」与「经验检索器（复用bge）」入手
4. **全维度渗透**：内在模型不是"一个分类器"，而是渗透到L1数据层→L2推理层→L3决策层→L4进化层的完整模型群

## 二、★依赖度指标的真实构成（路灯致命发现）

### 2.1 实测构成

`data/metrics/llm_dependency.json` → `counters.llm_call_count`：

| 场景 | 次数 | 占比 |
|------|------|------|
| **自主进化（SCENE_EVOLUTION）** | **2,077** | **98.8%** |
| 其他（SCENE_OTHER） | 26 | 1.2% |
| 肺回答（SCENE_LUNG） | **0** | 0% |
| 代码学习（SCENE_CODE_LEARN） | **0** | 0% |

### 2.2 根因：对话出口完全没有埋点

全库`record_llm_call(...)`只有4处调用点，全部在进化循环：
- `nucleus/evolution/LLMEvolutionEngine.py:45`
- `nucleus/evolution/SelfReflectionEngine.py:35`
- `nucleus/reasoning/SafeEvolutionExecutor.py:722`
- `organs/brain/PulseSemanticComprehension.py:574`

⇒ **"大模型依赖度"这个指标，从设计上就不包含对话。**

### 2.3 依赖度真实根因链

```
进化验证空转（56补丁baseline_errors全为0，100%假通过）
        ↓
补丁"假通过" → 问题并未真正修好
        ↓
下一轮自主进化又发现同样问题 → 再次调用LLM生成补丁（含多轮追问）
        ↓
2,077次进化LLM调用（占依赖度分子的98.8%）
        ↓
"大模型依赖度97%"
```

## 四、★全维度涵盖架构（L1-L4四层模型群）

### 4.1 架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│  L4 迭代进化层  ← 补丁评估器、进化策略器、技术债务评估器          │
│  (SafeEvolutionExecutor / SelfReflectionEngine)                  │
│  作用：98.8%的LLM调用源，收益最大                                │
├─────────────────────────────────────────────────────────────────┤
│  L3 决策协同层  ← 器官调度器、优先级评估器、背压预测器、资源分配器│
│  (PulseController / EventBus / NodePool)                        │
│  作用：框架自己管理自己，动态调整                                │
├─────────────────────────────────────────────────────────────────┤
│  L2 推理认知层  ← 意图分类器、响应预测器、经验检索器、语义缓存器  │
│  (PulseCortex / PulseInnerWorld / PulseLung)                    │
│  作用：对话推理，用户直接感知                                    │
├─────────────────────────────────────────────────────────────────┤
│  L1 数据感知层  ← 数据质量评估器、知识消化器、异常检测器          │
│  (PulseStomach / PulseFileDigester / KnowledgeTree)             │
│  作用：数据入口，质量决定上层模型质量                            │
└─────────────────────────────────────────────────────────────────┘
         ↑ 统一路由层（InnerModelRouter）↑
         ↑ 统一数据管道（data/training/）↑
         ↑ 统一监控层（自我认知引擎inner_models维度）↑
```

### 4.2 L1 数据感知层（最先接入，风险最低）

| 内在模型 | 接入器官 | 功能 | 训练数据 | 优先级 |
|---------|---------|------|---------|--------|
| **语义缓存器** | PulseLung前置 | 精确/语义命中直接返回，零LLM调用 | 历史LLM调用对 | 第41批 |
| **数据质量评估器** | PulseStomach（胃） | 判断输入数据是否有毒/污染 | 经验库polluted标签 | 阶段二 |
| **知识消化器** | PulseFileDigester | 自动分类/摘要/打标签 | 文件消化历史 | 阶段二 |
| **异常检测器** | 全器官日志 | 识别异常模式（JSON解析失败根因） | 运行日志+错误模式 | 阶段二 |

**为什么最先做**：L1是数据入口，质量决定了上层所有模型的训练数据质量。

### 4.3 L2 推理认知层（核心价值，中期接入）

| 内在模型 | 接入器官 | 功能 | 训练数据 | 优先级 |
|---------|---------|------|---------|--------|
| **经验检索器** | PulseInnerWorld | 相似问题复用历史经验，复用bge-small-zh | 1501条经验+12853知识节点 | 第42批 |
| **意图分类器** | PulseCortex入口 | 对话意图识别，路由到本地推理或LLM | 对话历史+IntentGenerator | 阶段三 |
| **响应预测器** | PulseLung出口 | 简单问题直接生成响应 | 简单问答对 | 阶段三（后置） |
| **置信度路由器** | PulseLung前置 | 统一路由：高置信→本地，低置信→LLM | — | 阶段一（基础设施） |

### 4.4 L3 决策协同层（框架智能的核心，长期接入）

| 内在模型 | 接入器官 | 功能 | 训练数据 | 优先级 |
|---------|---------|------|---------|--------|
| **器官调度器** | PulseController | 根据任务类型动态分配器官负载 | 任务执行历史+负载数据 | 阶段四 |
| **优先级评估器** | EventBus | 事件优先级动态调整 | 事件处理历史 | 阶段四 |
| **背压预测器** | NodePool/L0-L3队列 | 预测队列拥塞，提前限流 | 队列深度历史 | 阶段四 |
| **资源分配器** | GPUCore/硬件监测 | 根据硬件动态调整并发 | 硬件监测+性能数据 | 阶段四 |

**这一层对应你之前提出的**：
- 线程池/进程池动态根据硬件调整 → 资源分配器
- 鲁棒性缓冲器（资源红线不直接降级）→ 背压预测器
- 自我分析能力独立进程 → 技术债务评估器（L4）

### 4.5 L4 迭代进化层（最高阶，框架自我进化）

| 内在模型 | 接入器官 | 功能 | 训练数据 | 优先级 |
|---------|---------|------|---------|--------|
| **补丁质量评估器** | SafeEvolutionExecutor | 评估补丁是否真的有效，打断"假通过"循环 | 56补丁+真实基线测试结果 | **第42批（模型第1优先）** |
| **进化策略器** | SelfReflectionEngine | 根据历史补丁成功率，调整进化方向 | 补丁历史+成功率 | 阶段五 |
| **模型自更新器** | 内在模型自身 | 每日增量训练，漂移检测，自动回滚 | 训练数据+效果监控 | 阶段二 |
| **技术债务评估器** | 自我认知引擎 | 自动识别新债务、评估优先级 | 技术债务清单+代码分析 | 阶段五 |

## 六、★统一基础设施设计（三个统一）

### 6.1 统一路由层（InnerModelRouter）

**位置**：`PulseLung._call_via_channels()` **之前**（渠道选择的上游）

**依据**：PulseLung是全部LLM调用的统一出口，在此拦截可覆盖100%调用（含进化路径）。

**架构**：
```
调用方 → PulseLung._call_via_channels()
             ↓ 新增前置钩子
        InnerModelRouter.route(scene, payload)
             ↓ 高置信度(>阈值)且ECE达标
        本地模型结果（不发起网络请求）
             ↓ 低置信度 / 场景不支持 / 超时200ms
        原渠道流程（零改动）
```

**关键约束（红线）**：
- 路由只做"前置短路"，不改动既有渠道逻辑 → 天然零回归
- 首期只放行`SCENE_EVOLUTION`（占98.8%，收益最大、风险最可控）
- 默认关闭，`ENABLE_INNER_MODEL_ROUTING=False`兜底
- 每个模型有独立开关：`ENABLE_INNER_MODEL_<NAME>`
- 路由层加**200ms超时保护**：本地模型未出结果即降级到LLM

**灰度策略（三级）**：
- L1 观测级：只算不答，记录"如果接入会怎样"到日志
- L2 对话级：简单问答场景放行，用户无感知
- L3 决策/进化级：全场景放行，需充分验证

### 6.2 统一训练数据管道（data/training/）

**目录结构**：
```
data/training/
  llm_pairs/
    evolution.jsonl      # 进化循环调用对（2077次/4天）
    dialogue.jsonl       # 对话调用对（第40批埋点后开始积累）
    other.jsonl          # 其他场景
  labels/
    intent.jsonl         # 意图标签（人工/自动标注）
    patch_quality.jsonl  # 补丁质量标签
  stats/
    daily.json           # 每日语料统计
    quality_report.json  # 数据质量报告
```

**数据格式**（第40批T1定义）：
```python
{
  "ts": float,              # 时间戳
  "origin": str,            # user_query / evolution_task / digestion / system_internal
  "prompt": str,            # 完整prompt
  "response": str,          # 完整response
  "prompt_version": str,    # prompt模板版本
  "channel": str,           # deepseek / zhipu / volcano / ark
  "model": str,             # 具体模型名
  "duration": float,        # 耗时秒
  "tokens": int,            # token数

  "feedback": str | None    # 下游反馈（采纳/拒绝/用户重问），后续回填
}
```

**铁律（防退化）**：
- 训练数据**只收教师（LLM）直答样本**
- 内在模型命中结果**永不**入训练集
- 可记录"内在模型vs LLM"的差异用于监控，但不作为训练标签

**开关**：`ENABLE_TRAINING_DATA_COLLECTION=True`（默认开启，只写本地小文件，零网络开销）

### 6.3 统一健康监控（自我认知引擎inner_models维度）

**复用**：PHASE18自我认知引擎（第39批刚收官，每日03:00调度）

**新增维度**：`inner_models`
- 各模型的：置信度分布、采纳率、降级率、ECE（校准误差）
- 漂移趋势：准确率周环比、置信度分布偏移
- 数据健康：训练数据量、污染率、覆盖率
- **趋势下降即告警**，自动触发回滚

**这是方案与现有资产的最佳结合点**：自我认知引擎正是"监控模型自身健康"的现成载体。

## 七、★关键设计补全（第三方评估）

### 7.1 置信度校准机制（路由地基）

**问题**：没有校准的模型会"自信地犯错"——输出概率80%但实际准确率只有50%。

**方案**：
- 训练后做**温度缩放**（Temperature Scaling），最小化NLL
- 上线前验证**ECE（Expected Calibration Error）< 0.05**
- 路由层只在**置信度>阈值且ECE达标**时才放行本地模型
- 否则降级到LLM

### 7.2 自我蒸馏退化防护（铁律）

**问题**：如果把内在模型的输出记入训练数据，下一代模型会在自己的输出上学→错误固化放大。

**铁律**（已在§6.2强调）：
- 训练数据只收LLM直答样本
- 内在模型输出永不入训练集
- 记录差异用于监控，不作为标签

### 7.3 模型测试三层防护

1. **固定测试集**（golden set）：从早期数据中切出20%冻结为测试集，永不参与训练 → 每次重训后跑一次，准确率不得下降>2%
2. **影子模式**（shadow）：新模型上线前先"只算不答"，与LLM结果对比≥3天，一致率达标才切换
3. **漂移哨兵**：复用自我认知引擎inner_models维度，每日监控，趋势下降即告警

## 八、★训练策略

### 8.1 三阶段训练

| 阶段 | 方式 | 频率 | 说明 |
|------|------|------|------|
| 初始训练 | 离线批量训练 | 一次性 | 用历史数据训练初始模型 |
| 每日增量 | 离线增量训练 | 每日03:30（挂DailyScheduler后） | 用前一天数据增量更新 |
| 定期重训 | 离线全量重训 | 每周 | 用积累的全部数据重训，防止漂移 |

**不做实时在线学习**（路灯建议）：
- 当前LLM调用集中在进化循环（21.6次/小时），频率低且突发，逐次更新收益极低
- 实时更新会引入模型漂移，而漂移检测+回滚机制尚未建立
- 先有监控再开在线学习

### 8.2 数据标注策略

- **自动标注**：大模型的输出作为"标准答案"
- **隐式反馈**：用户是否继续追问、是否表达不满
- **显式反馈**：用户点赞/点踩（如有）
- **结果验证**：代码补丁是否通过测试、任务是否成功

### 8.3 模型管理

- 版本号：每个模型有独立版本号，存储`data/models/inner/<name>/<version>/`
- 只保留最近2版（避免重演data/knowledge的2.13GB备份问题）
- 回滚机制：新模型效果下降时自动回滚到上一版本
- A/B测试：部分请求用新模型，对比效果

## 十一、风险与缓解

### 11.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 数据质量不足 | 高 | 模型准确率低 | 严格数据治理，数据质量评估器（L1）先行 |
| 模型漂移 | 中 | 在线学习导致效果下降 | 不做实时学习，每日增量+每周重训+回滚机制 |
| 冷启动问题 | 高 | 初期模型效果差 | 渐进式接入，低置信度始终降级到LLM |
| 训练算力不足 | 中 | 训练时间长 | 用轻量模型（scikit-learn），避免深度学习；生成式模型排除出阶段一/二 |
| 模型间冲突 | 低 | 多个模型给出矛盾结果 | 统一路由层，明确优先级 |
| 自我蒸馏退化 | 致命 | 错误固化放大 | 铁律：内在模型输出永不入训练集 |

### 11.2 工程风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 与现有代码冲突 | 中 | 集成困难 | 模块化设计，通过接口集成，不修改核心逻辑 |
| 性能开销 | 中 | 内在模型推理增加延迟 | 模型轻量化，200ms超时保护，缓存预测结果 |
| 维护复杂度 | 高 | 多模型管理困难 | 统一模型管理框架，自动化监控（自我认知引擎） |

### 11.3 战略风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 过度依赖内在模型 | 中 | 回答质量下降 | 始终保留大模型兜底，置信度阈值保守 |
| 知识固化 | 低 | 框架无法学习新知识 | 定期用大模型"刷新"内在模型 |
| 用户体验波动 | 中 | A/B测试期间体验不一致 | 灰度发布，用户无感知切换 |
