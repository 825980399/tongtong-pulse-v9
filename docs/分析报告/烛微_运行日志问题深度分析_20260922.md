### 4.2 为什么"自动审批"没生效——三条独立证据链闭合
**① 判据被设计成结构性不可达（S 型，代码正身）**：T-101a `_m101_low_risk_release_path` 要求 `risk=低 ∧ runtime_verified is True ∧ 非核心 ∧ 非护栏`；它在生产**唯一调用点是 `save_pending_patch`（入队瞬间）**。而 `runtime_verified` 只能在入队 ≥300s 的验证窗口后由 `verify_submitted_patches` 写 True ⇒ **入队时该字段必为 False**（或不存在），判据在唯一评估点恒假。第101批的意图（低风险直通）事实上**从未放行过任何一条**：生产文案 `低风险可放行(已升approved)` 全窗 **0** 命中；对照面"每10分钟自动升级窗口报无可自动应用项"持续刷屏。
**② 无人复查（T 型，最硬的实证）**：验证窗口过后字段变 True 了——**12:37 实查 30/30 `runtime_verified=True`**，但全仓没有任何代码对已入队条目重跑 T-101a（`approve_all` 无生产调用点；`scan_pending` 仅测试自证）⇒ 30 条全部处于"判据现已满足、无人再看"状态。反例锚 e37a（昨夜基线 5→现网 1、effectiveness 0.8、真验证通过）与其余 29 条同命：卡 13h+ pending。**这正是第3期"闭环断在批准→落盘"的前半段：断在验证→复查。**
**③ 即使复查，读到的也是污染字段（S 型）**：满足 T-101a 的 30/30 个 True 来自第3期点名的**三处无条件置真**写入点之一（`runtime_failed` 29 条同样 rv=True 即为铁证），而真正经过验证的嵌套 `runtime_verify_result.verified` 为 0/30。`confidence` 键 0/30 存在 ⇒ PatchAutoApprover 的放行分支同样不可达。
**单测为何绿**：`test_t101a:62` 手动构造 `runtime_verified=True` 的补丁再调 `save`——**伪造了生产时序里不存在的状态**。这是第3期"测试自证"模式的重演（同：m53 的 `scan_pending`、m79 的 MagicMock 掉唯一会推翻修复的函数）。

**结论**：积压不是补丁质量问题，是**审批环的状态机缺一条"验证完成→复评放行"的回边**。30 条中除 e37a 有真实效果证据外，其余 29 条本就预防型（静默异常/单例调用）**不产生运行期错误 → baseline 恒 0 → 验证器永远判不了**——这类补丁走"自动放行"通道在原理上不可行，应改走"人工抽批 + 落盘后 reprobe 原文案消失"验证。
