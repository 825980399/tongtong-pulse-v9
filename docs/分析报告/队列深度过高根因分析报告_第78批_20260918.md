# 队列深度过高根因分析报告（主线第78批 · 2026-09-18）

> 纠正 09-16 根因报告的前提错误：本报告经实测定位，队列深度指标的真实来源是
> `InfoField._inflight_dispatch_count`，**不是** `runtime_metrics` 内部 5000 容量队列。

## 1. 结论速览

- **队列深度真身**：`InfoField._inflight_dispatch_count`——四层线程池异步分发在途计数
  （publish 提交 `+1` / `_dispatch_handler` 完成 `-1`），经 `record_pulse(queue_depth=_depth)`
  上报给 `runtime_metrics`，显示为"队列深度"指标。
- **09-16 报告的偏差**：把队列深度等同于 `runtime_metrics` 内部的 `self._queue: queue.Queue(maxsize=5000)`。
  该队列是**指标采集队列**（埋点投递用），与上报的"队列深度"不是同一概念；其 `maxsize=5000`
  是采集缓冲上限，不是业务积压深度。原报告据此归因为"快照保存2小时"，前提错误。
- **实测**：09-18 日志队列深度范围 [1006, 14890]，均值 963，全局最大 14890，L3 背压 270/300（90%）。

## 2. 双根因（只增不减）

### 根因 A · inflight 计数器竞态 + 异常漏减（星轨点名）
- `InfoField.py:723-724` 的 publish `+1` 使用 `self._task_count_lock`（有锁）。
- `InfoField.py:898` 的 `-1` 原在 `_dispatch_handler` 的 `try/finally` **之外**且**无锁**
  （星轨 2026-09-18 指认：":712 有锁 / :898 无锁，指标漂移"）。
- 危害：多线程下 `-1` 的读-改-写互相覆盖、部分 `-1` 丢失 → 计数只增不减、指标持续偏高；
  且 `finally` 外意味着 handler 抛异常时 `-1` 永不执行 → 永久泄漏。

### 根因 B · 池重建取消旧池任务，其 −1 永不执行（泄漏）
- `InfoField._resize_layer_pool`（L2043-2115）：`old_pool.shutdown(wait=False, cancel_futures=True)`
  取消旧池排队任务。这些被取消任务的 `-1` 永不执行 → 计数泄漏。
- 原 P2-87 回收段（L2087-2115）**只递减 `_organ_concurrent_count`，未回收 `_inflight_dispatch_count`**
  → 取消的在途分发永久计入深度。
- 放大因素：第75批引入的频繁 L3 动态扩缩容使池重建频繁发生 → 泄漏持续放大 → 队列深度只增不减。

## 3. 修复方案（T1）

1. **竞态修复**：L898 的 `-1` 移入 `_dispatch_handler` 的 `finally` 块，并用 `self._task_count_lock`
   加锁（与 publish `+1` 对称）→ 消除读-改-写覆盖 + 异常漏减。
2. **泄漏修复**：`_resize_layer_pool` 的 `_recover` 分支按
   `_cancelled = sum(_layer_pending.values())` 精确递减 `_inflight_dispatch_count`
   （带 `ENABLE_CONCURRENCY_COUNT_RECOVERY` 开关，默认开，零回归）。
3. **趋势告警**：`runtime_metrics` 新增队列深度趋势窗口（每采样点记录瞬时深度），
   窗口持续上升 + 涨幅≥800 + 未破绝对阈值 → 提前预警（早期缓冲窗口）。

## 4. 验证

- 静态：生产源码 `±` 均加 `_task_count_lock`；`_recover` 分支按 `_cancelled` 递减（grep 二验）。
- 并发：200 线程 × 20 次 `+1`/`-1` 往返，最终计数归零、不转负（无漂移、无泄漏）。
- 单测：`test_m78_inflight_lock.py`（7 例）、`test_m78_queue_depth_trend.py`（6 例）全过。
- 验收：队列深度稳定 < 5000（修复后计数不再只增不减；配合第75批滞回+冷却，稳态收敛）。
