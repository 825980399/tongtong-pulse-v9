## 一、问题概述

### 1.1 现象

框架运行时CPU使用率持续维持在**70-80%**，即使在无用户对话的空闲状态下也不下降。

### 1.2 初步判断

用户怀疑"框架之前的自适应能力是不是又被破坏了"。

### 1.3 分析结论

**自适应能力没有被破坏，但存在严重的设计缺陷和覆盖范围不足。**

| 方面 | 状态 | 说明 |
|------|------|------|
| 自适应模块是否运行 | ✅ 正常运行 | HybridParallelScheduler和InfoField都在工作 |
| 自适应阈值配置 | ✅ 配置正确 | CPU阈值80%，内存阈值85% |
| 自适应触发记录 | ✅ 有记录 | 最近57条触发记录 |
| **自适应覆盖范围** | ❌ **严重不足** | **只覆盖InfoField，不覆盖器官扫描组等重操作** |
| **缓存机制** | ❌ **完全缺失** | **_scan_all_organs()每次都全量重新解析** |
| 自适应调整方式 | ❌ 单一 | 只调线程池/进程数，不调任务频率 |
| 自适应效果 | ⚠️ 有限 | CPU峰值能降，但稳定在70-80%下不来 |

## 二、根本原因深度分析

### 2.1 核心根因：器官扫描组缺少缓存，每秒全量重新解析

#### 问题定位

**文件**：`nucleus/self_inspector.py`
**方法**：`_scan_all_organs()`（第1514行）
**问题**：**完全没有缓存机制**，每次调用都：
1. 遍历`organs/`目录下的所有子目录（9个目录）
2. 收集所有`.py`文件（62个器官文件）
3. 使用结构化并行调度器创建名为"器官扫描组"的任务组
4. 并行解析每个文件的类定义和方法列表
5. 每次都重新做一遍，**没有任何缓存**

#### 调用链分析

`_scan_all_organs()`被**12个地方**调用，其中多个是公共方法：

| 调用点 | 行号 | 方法名 | 调用频率 |
|--------|------|--------|----------|
| 1 | 1109 | `get_method_info()` | 高（代码学习、自主进化频繁调用） |
| 2 | 1512 | `scan_all_organs()`（公开封装） | 高（代码学习、安全演化调用） |
| 3 | 1658 | `resolve_organ_file()` | 中（日志分析反查文件时调用） |
| 4 | 1691 | `get_organ_code_structure()` | 中 |
| 5 | 1720 | `get_method_detail()` | 中 |
| 6-12 | 2165等 | 其他内部方法 | 低-中 |

#### 性能影响估算

| 指标 | 数值 | 说明 |
|------|------|------|
| 每次扫描文件数 | 62个 | 全部器官文件 |
| 每次扫描耗时 | 600-1000ms | 平均800ms |
| 扫描频率 | **每秒1次** | 多个模块频繁调用 |
| CPU占用 | **60-70%** | 800ms/1000ms = 80%时间在扫描 |
| 重复计算率 | **>99%** | 文件内容几乎不变，但每次都重新解析 |

**这是CPU使用率70-80%的首要原因！**

### 2.2 次要根因：自适应覆盖范围不足

#### 当前自适应覆盖的模块

| 模块 | 自适应动作 | 证据 |
|------|-----------|------|
| HybridParallelScheduler | 根据CPU调整进程数（2↔6） | CPU 96%→6进程，CPU 9%→2进程 |
| InfoField线程池 | 根据负载调整线程数（4↔8） | heavy负载→4线程，light负载→8线程 |
| InfoField任务门控 | 高负载时丢弃normal优先级任务 | 丢弃胃知识消化、自我诊断、梦境推演 |

#### 当前自适应**没有覆盖**的重操作

| 重操作 | CPU占用 | 是否受自适应控制 | 问题 |
|--------|---------|-----------------|------|
| **器官扫描组** | **60-70%** | ❌ **不受控制** | 最大CPU消耗者，自适应管不到！ |
| 冷存compaction/内容去重 | 10-15% | ❌ 不受控制 | 持续运行，不看负载 |
| 代码学习 | 5-10% | ❌ 不受控制 | 每分钟1次，每次17秒 |
| 后台学习消化（肺） | 5% | ❌ 不受控制 | 持续运行 |
| 动机循环 | 2-3% | ❌ 不受控制 | 每30秒1次 |

#### 自适应调整方式单一

当前自适应只做"资源调整"：
- ✅ 调整线程池大小（8→4）
- ✅ 调整进程数（2→6）
- ✅ 丢弃低优先级任务

当前自适应**没有做**"任务频率调整"：
- ❌ 降低器官扫描组的频率（1秒→5秒）
- ❌ 降低代码学习的频率（1分钟→5分钟）
- ❌ 暂停冷存compaction
- ❌ 降低后台学习消化的频率

**这就像**：汽车发动机转速太高了，自适应只知道关空调、降车窗，但不知道松油门！

### 2.3 其他设计缺陷

#### 缺陷1：自适应阈值设置不合理

- CPU阈值：80%
- 用户观察到CPU在70-80%之间
- 结果：CPU刚好在阈值附近，自适应反复触发又恢复，不稳定

#### 缺陷2：队列深度未纳入自适应监控

- 队列深度持续7000+（正常1000+）
- 但自适应只看CPU和内存，不看队列深度
- 队列积压导致更多任务排队，更多线程竞争，进一步恶化性能

#### 缺陷3：缺少统一的自适应调度器

- 各个模块各自为政，没有全局协调
- HybridParallelScheduler调自己的进程数
- InfoField调自己的线程池
- 器官扫描组完全不管负载
- 结果：可能出现"InfoField在降频，但器官扫描组在全速运行"的矛盾情况

**债务ID**：P0-性能根因（器官扫描组缺少缓存，CPU 60-70%）

**问题描述**：
- `nucleus/self_inspector.py:1514` `_scan_all_organs()`方法完全没有缓存
- 每次调用都全量重新解析62个器官文件
- 被12个地方调用，每秒触发1次，CPU占用60-70%
- 重复计算率>99%（文件内容几乎不变）

**修改文件**：
- `nucleus/self_inspector.py`

**具体修改点**：

1. **添加缓存数据结构**：

2. **修改`_scan_all_organs()`方法**：
```python
def _scan_all_organs(self):
    # 检查缓存是否有效
    now = time.time()
    if (self._scan_cache and 
        now - self._scan_cache_time < self._scan_cache_ttl and
        not self._check_files_changed()):
        # 缓存命中，直接返回
        return self._scan_cache
    
    # 缓存未命中，执行全量扫描
    result = self._do_scan_all_organs()  # 原扫描逻辑移到这里
    
    # 更新缓存
    self._scan_cache = result
    self._scan_cache_time = now
    self._update_file_mtimes()
    
    # 记录缓存统计
    _module_logger.debug(f"[SelfInspector] 器官扫描缓存已更新: {len(result)}个器官")
    
    return result
```
