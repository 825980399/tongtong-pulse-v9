## 1. 阶段一：独立代码摸底（禁止先读总账/登记册/任何进度文档）

按以下维度对代码做全维独立分析（每个结论附证据锚=文件:行号或命令输出）：

1. **规模与结构**：`.py` 文件数/行数（按目录：nucleus/organs/tools/tests/functions 等）、import 依赖图顶层、入口链（main.py→装配→循环）
2. **架构实现核验**：器官装配机制（声明式 `use_declarative_assembly` vs legacy `_create_organ` 段）、九大核心器官/四层记忆/信息场/类比迁移/认知反思等设计概念在代码中的真实落点与"壳"程度
3. **运行链风险**：静默 except 面、裸 except/noqa、事件系统一致性（事件常量 vs 字符串字面量）、多进程/线程/锁面、超时与重试、资源（内存/磁盘/CPU）监控真实性
4. **测试面**：测试文件数/用例收集数、红基线现状（`known_fail` 实际真红 vs 假绿）、测试与源码覆盖映射、依赖真实数据/环境的测试占比
5. **安全与合规面**：PII 处理链、导出器（公开包/白名单/占位符渲染/包体复扫）、鉴权/黑名单配置、外部依赖与许可证风险

## 2. 阶段二：技术债务清单与设计落地对照（独立摸底完成后才可读进度文档）

1. **技术债务核验**：读 `docs/台账/待裁决登记册.csv`（192 条）与 `docs/完整进化路线与技术债务清单_v1.0.md` §2——逐类独立重摸"已结案/已排期/待排期"的代码真实状态，输出**口径偏差清单**（官方说已消化但代码未落地 / 官方未收但代码有风险）
2. **设计文件落地审计**：枚举 `docs/设计文档/`、架构总览、README 等设计载体 → 对每个设计概念给出落地等级（已落地=可指到代码锚 / 部分落地 / 壳=仅接口无实现 / 未落地=无代码痕迹），汇总未落地/壳清单
3. **红测试归因**：对 collect 收集的全部红节点做归因分桶（真生产缺陷/数据依赖/判据缺陷/在途他方/环境工件），给出确定性 floor

## 3. 阶段三：协作模式诊断（新增维度，基于 git 历史+文档结构审计）

1. **git 历史审计**：提交频率与时段分布、作者分布（可据 committer 名）、批次-提交-报告对应关系、commit message 规范率（票号标注/`[ci-gate-change]` 标记/中文措辞）、revert/重锚频率
2. **流程闭环审计**：任务书→施工→交付报告→采信/验收→登记册结案的闭环结构；从文档时间线统计"一刀一报告一裁决"粒度下的批次周期、积压票数与结案速率比、登记册滞后现象
3. **协作问题清单**：输出结构化问题（每条=现象+证据+影响+建议方向），重点：①批次粒度与裁决延迟 ②角色分工（施工/分析/审计职责边界）③门禁/纪律成本收益 ④跨角色消息依赖与上下文传递损耗 ⑤文档维护滞后
