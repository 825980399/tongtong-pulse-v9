> 验收：规则矛盾条目清零。

## 〇、矛盾定义（为什么要对齐）

两套规则长期并行，语义冲突，各角色（路灯/烛微/微光）按字面执行会互相打架：

| 来源 | 规则字面 | 隐含假设 | 冲突点 |
|---|---|---|---|
| 《多角色协作防踩坑清单 v1.0》第 6 条 | 「大文件整读前确认框架停」 | 夜间=框架停机窗 | 隐含"夜间默认停窗" |
| 158上-A 夜间施工包裁定（10-03） | 「P2-65 不适宜夜间连续施工模式」 | 夜间=不停机连续施工 | 两处"夜间"语义相反 |
| 157 批后多次夜间长任务（159/161/163/167/169） | 路灯通宵连续施工 | 夜间=正常施工窗 | 与"停窗"命名混用 |
| 曈曈 03:00 自动应用补丁重启 | 框架凌晨自重启 | 凌晨=框架自动活动期 | "停窗"若含凌晨则与自动重启冲突 |

**根因**：两套词汇描述的是**两个正交维度**，被混进同一个"夜间"词里：
- **维度 A（施工许可）**：是否允许施工 → 停窗 = 施工禁区；夜间连续施工 = 施工许可模式。
- **维度 B（框架状态）**：框架停 or 运行 → 决定能否做数据面/装配面改动。

## 一、对齐裁定（二选一 → 采纳方案 B：夜间连续施工定为窗口许可模式）

**正式定义"夜间连续施工窗"为一种窗口许可模式**，替代"深夜停窗"提法：

```
夜间连续施工窗（Night Continuous-Construction Window, NCCW）
├─ 时间：20:00 至次日 08:00（用户家时段，随项目排期可调整）
├─ 性质：★施工许可模式（允许路灯施工 / 烛微分析 / 微光文档），
│        不是"框架停机"的同义词
├─ 框架状态：按任务书现场标注三态之一
│   ├─ 运行态：框架在跑，只允许代码面/只读面改动（禁 data/ 写盘）
│   ├─ 停机态：框架已停，允许数据面/装配面改动（禁整读超大文件须先确认停）
│   └─ 无要求：框架状态与本刀无关
└─ 次晨复核节点（★新增，NCCW 专属纪律）：
    次日 09:00 由星轨对夜间全部提交做一次复核——
    1. 逐提交核对交付报告/登记册销账是否同步；
    2. 门禁日志留痕抽查（cw2 非沙箱前置实测）；
    3. 若有框架运行态夜间施工，核对 data/ 无写盘污染；
    4. 复核结论记入当日总账。
```

**废除"深夜停窗"提法**：此后任务书一律写"停窗/不停窗"（指框架状态），不再写"深夜/夜间停窗"；夜间时段统一用 NCCW 表述（指施工许可模式）。

## 二、防踩坑清单第 6 条修订（规则矛盾清零）

原第 6 条：「大文件整读前确认框架停」→ 修订为：

> **6. 大文件整读与框架状态（NCCW 对齐版）**
> - 施工方（路灯）：改数据面/装配面文件前，**先确认框架停**（无 runtime.lock / 无主进程）；改代码面可在运行态进行。
> - 只读方（烛微/微光）：>100MB 一律流式分块读（8MB 块），无需等框架停；仅在确需整读时先确认框架停。
> - 夜间施工（NCCW）不等于停窗：是否停框架以**任务书现场标注**为准，不得自行推定。

## 三、任务书措辞模板（后续批次统一引用）

任务书"施工边界"节固定写：

```
施工边界：
- 框架状态：【运行态 / 停机态 / 无要求】（三选一，由星轨排期时标注）
- 运行态禁写：data/ 下任何文件（runtime_state/alerts/pending_patches/快照/台账）
- 停机态确认：开工前查 runtime.lock 与主进程，无则视为安全窗
- 夜间时段：属 NCCW 施工许可模式，按上述框架状态三态执行，次晨 09:00 星轨复核
```

## 四、与 03:00 自动重启机制的衔接

曈曈 03:00 自动应用补丁重启属**框架自动活动期**：
- 该时段若有"停机态"任务，须避开 02:45–03:30（重启窗），任务书应标注；
- 该时段默认按**运行态**纪律执行（只读/代码面），禁 data/ 写盘，避免与重启快照重写冲突。
