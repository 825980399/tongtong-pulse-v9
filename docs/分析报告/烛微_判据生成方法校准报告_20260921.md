### 1.2 两条判据各自为什么不可复现（均有脚本实证，`tmp/cw_criteria_verify_output.txt`）

**判据①「目标符号 `_calc_math_question` 全文件 0 次」——魔法串问题**
- 事实层面该观察没有错：09-21 复验 `grep -c _calc_math_question PulseInnerWorld.py` 仍 = 0。
- 但"目标符号"在账本里**没有任何字段能推导出这个串**：该记录的 `method='_safe_eval_arithmetic'`（磁盘出现 4 次 ≠0），`_calc_math_question` 只是 `modified_code` 正文里我（zw2）人工挑出的一行标记。
- 路灯做"全账本扫描：每条记录的『目标符号』磁盘 0 次"时，可推导的符号只有 `method`/`file` 字段 → **必然 0 条命中**。
- **定性：判据依赖一个未报告的"为什么是这串"的人工选择 = 对第三方不可实现。**（若当时报告写明"从该记录 modified_code 提取新增标记串"，就已可复现。）

**判据②「当前文件与落地前备份逐字节相同」——快照状态 + 路径暗坑双重问题**
- 结构性缺陷：该判据只能命中"刚落地、之后无人再碰该文件"的记录。67 条里 09-11～09-19 的记录所在文件都被后续批次改过 → **逐条扫描天然只有 1 条可能命中**（09-21 实测命中数 = 1，且正是 18:13 那条）——**它连烛微自己的 2 条都圈不全，从来就不是产出"2"的判据。**
- 复现暗坑：`backup_path` 字段存的是**目录**（`.../backup_20260920_181309`），需再拼 `/organs/brain/PulseInnerWorld.py` 才能比对；按"文件"去 `open()` 会抛异常 → 扫描跳过 → 得 0 条。报告未写这个路径结构，路灯得 0 是必然。
- **定性：把"会随主体移动而失效的瞬时状态"当判据，且缺执行细节。**

**为什么我会犯这个错（过程根因，不找借口）**
1. 汇总压缩时优先引用"最具体、最生动"的证据（一条精确到符号名的观察），胜过"无聊但可靠"的算法描述——具体性 ≠ 可复现性，这是写作直觉压过了审计纪律。
2. 第 1 期报告交付前，主线程对 7 项代理结论做了交叉复核（F3/审批拒写/胃 bug/gitignore 等），**但没有对"报告正文每一行判据做一次冷启动可执行性自测"**——复核的是结论真伪，漏了判据可跑性。这两道门缺一不可。

### 1.3 判据失效的两类通用模式（后续所有审计的警报词）

| 模式 | 特征 | N2 对应 |
|---|---|---|
| **魔法串** | 判据里的关键词/数字来自审计者的人工挑选，无字段或算法可推导 | `_calc_math_question` |

## 二、T-CW-2：可复现判据生成规范 v1.0（烛微自约，下期起强制执行）

### 2.1 判据四要素（缺一即不合格）

任何写进报告的问题判据，必须同时给出：

| 要素 | 内容 | 反例（N2） |
|---|---|---|
| **① 主体与锚点** | 数据源精确路径 + git HEAD + 观测时刻（绝对日期时间，禁用"今日/当前"） | 备份路径结构未给；"落地前备份"含糊 |
| **② 提取算法** | 测试对象如何从记录/文件推导，禁止无来源的人工挑串；若确需字面常量，显式标注"字面常量如下" | `_calc_math_question` 来源未说明 |
| **③ 判定规则 + 命令** | 一条可直接粘贴执行的命令（或脚本相对路径 + 完整命令行，含 `-X utf8`）+ **预期输出的逐字格式** | 判据②按字面执行会异常跳过 |
| **④ 稳定性声明** | 三选：**S 结构型**（HEAD 不变即恒定）/ **T 时间窗型**（日志窗口，写明日期过滤）/ **V 活体快照型**（会漂移，附采集时刻 + "复跑值可能变化属正常"，结论不得单独依赖 V） | 判据②实为 V 型却按 S 型措辞 |

### 2.2 最小化原则

- **一条判据圈一个集合，不举单例**：报告写"判据 → 命中清单（全量 N 条）"，不写"我看了其中一条，它如何如何"。N2 正确写法是"探针判据，命中 2 条：A、B"，逐条细节降级为佐证。
- **最少的证据**：能用结构型就不用活体型；能一条命令不用脚本；能 grep 不用解析器。堆砌观察值不增加可信度，只增加失效面。

### 2.3 交叉验证方法（每问 ≥2 通道）

每个问题结论至少两条**独立来源通道**（不同数据源才算独立：账本≠磁盘≠日志≠git≠进程内存），格式：

```
交叉验证：通道A（账本）：effect_verified=True 且 applied=True → 67 条
          通道B（磁盘）：A 中按探针判据失配 → 2 条
          通道C（git） ：2 条所在文件 git 状态一致于落地前形态 → 佐证（可选）
          计数一致 → 结论成立；不一致 → 先解释再入报告
```

- **自灭测试**：若结论为真，修复落地后该判据应"变绿"——预判哪些判据会被修复动作自我作废（N10"台账 grep 烛微=0"就是典型：第 96 批入账后即自灭），这类判据必须带观测时刻 + 作废预告，避免被误读为"不可复现"。
- **换形不改数测试**：对 V 型判据，给一个"必然随时间变的数"和一个"不随时间变的数"（如"悬空边 133,767（09-20 21:1x 快照，复跑会变）"+"删除路径零调用（结构型，不变）"）。

### 2.4 复现命令卫生（本期新增，血泪条款）

- Windows 下所有交付命令显式带 `-X utf8`（烛微 09-21 复核脚本再次 GBK 崩于 `⇒` 字符——与被审计系统的 P0-2 同族，教训对等）。
- 命令必须在报告声明的工作目录下可跑（写明 `cd D:/xinrenlei/tongtong-pulse-v9`）。
- 路径字段要注明语义陷阱（目录 vs 文件），如 `backup_path=目录，需拼 /<相对file>`。

### 2.5 交付前判据门禁（烛微自检清单）

> **冷启动测试**：报告定稿前，遮住"根因/分析"段，只看"复现"字段，逐条问——一个从未读过取证脚本的路灯，能否仅凭这行文字得到与报告相同的**计数**？任何一条需要"我还知道一件没写下来的事"才能执行 → 不合格，返工。
