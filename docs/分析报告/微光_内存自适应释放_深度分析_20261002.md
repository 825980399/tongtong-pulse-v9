### 1.3 三档推算（48GB 机；物理内存实测 47.9GB，85% 告警线 ≈ 40.7GB）
| 档 | 日增量假设 | 7 天末 | 触 85% 告警线 |
|---|---|---|---|
| 保守（无驱逐/每日 8 融合波） | +4GB/天 | ≈34.6GB（72%） | **~8.5 天** |
| 中性（实测 0.29GB/h 取整 5GB/天） | +5GB/天 | ≈41.6GB（87%） | **~6.8 天** |
| 极端（实测上界 7GB/天） | +7GB/天 | ≈55.6GB（116%） | **~4.9 天** |

- **16GB 低配**：可用 85% ≈ 12.9GB；启动加载即占 5.6GB（43%）；中性 **~1.5 天**触险、极端 **<1 天**。
- **结论：星轨"中性 20-28GB（42-58%）"偏乐观**——实测平台渗漏 0.29GB/h 高于其模型隐含值；48GB 机一周内必触 85% 告警线（除非驱逐/瘦身落地）。推算方法：初始 6.6GB + 日增量×天数，日增量=融合波跳升（实测 3 跳/3.3h ≈ +0.9GB）+ 慢渗漏（0.2GB/h×24≈4.8GB）取中 ~5GB/天。

## 三、更优解对比（5 候选）

**S1 快照增量写盘接管（P1｜收益：削 0.5GB×每小时峰值）**
- 原理：jsonl 增量日志已存在（SNAPSHOT_INCREMENTAL_MAX_NODES=200 / 阈值 50000 行 / 删除熔断 0.5，config.py:4738-4758）；PARQUET 主存已开（L4790）但 JSON 全量 .bak 仍每小时做。
- 动作：30s 周期只追加增量；阈值内不重建全量 JSON 副本；.bak 降频至 6h/24h。
- 代价：增量回放复杂度；收益明确、零新框架。

**S2 冷池参数动态化（P2｜收益上限 0.6GB + 召回性能保护）**
- 原理：复用 PulseNodePool L174-175 RUNTIME_PARAMS 动态读取 + ParamPatchManager L127 可调域。
- 改进星轨方案：不设固定阈值，按**最近访问分位数**收缩（驱逐 last_access 最低 20% 分位）；分两次收缩（每次 -1000，间隔 ≥10min）防风暴；驱逐在检索热路径外执行。
- 风险：召回 IO 延迟（COLD_SIDECAR_INDEX 已存在缓解，config.py:4704）。

**S3 进程级优雅降级决策树（P3｜兜底）**
- 档位1（已有 heavy）：节流+丢低优；档位2（新增）= S1+S2 组合；档位3（新增）：mem≥95% 持续 15min → 告警 + **建议受控重启**（重启成本 ≈15min 加载，远小于 OOM 数据风险）；不自动重启（"曈曈是生命体"，重启语义须小林确认）。
- 衔接：与 O-A1 重启恢复协议（158 上-B）同语义族，建议合并立项。

**S4 连带：VectorStore 落盘路径修复（P0｜收益 0.3~1GB，路灯已接）**
- 任务书 §1.1 自述"向量库主路径指向 Temp\p17_iso_* 落盘失败（20+10 次）→ 数据保留内存"；触发指令第 2 刀 **T-落盘路径泄漏-1**（22:17 派发路灯）已在修 → 修通即释放 0.3-1GB，零新增代码成本。**本任务最优先推荐。**

**S5 连带：embedding 模型驻留核查（P2｜磁盘可清 613MB，内存无驻留）**

## 五、结论摘要（10 行）

1. 48GB 机：当前形态 **4~8.5 天**触 85% 告警线；16GB 低配 **1~2 天**即险（启动即占 43%）。
2. 冷驱逐（星轨二级）收益上限 ≈0.6GB，杯水车薪，且召回引入 IO 风险——不解决根因。
3. 真正大头：快照全量 JSON 副本（每小时 0.5GB 峰值）+ 向量库落盘失败驻留（0.3-1GB）+ 节点对象膨胀。
4. 星轨"驱逐平衡 8-12GB 封顶"不成立（冷池 5530 节点全驱逐才 ~0.9GB）。
5. ENABLE_MEMORY_AUTO_GC=True 是**死开关**（生产 0 调用）；内存告警 RSS=9999.0MB 为 psutil 降级假值。
6. jina 613MB 未加载（config.py:769 已排除），任务书 §1.1"3 模型 970MB 是否全驻留"实为 **1 模型 ~90MB 驻留**。
7. 推荐 P0 向量路径修复（已在路灯手）→ P1 快照增量 → P2 冷池分位动态化 → P3 降级决策树。
