## 二、★依赖度指标的构成（本报告最重要的发现）

方案的**所有目标**都锚定在"大模型依赖度"上（§7.1：97.0% → <90% → <70% → <50%）。
因此必须先看清这个 **97% 到底是什么**。

### 2.1 实测构成

`data/metrics/llm_dependency.json` → `counters.llm_call_count`：

| 场景 | 次数 | 占比 |
|---|---|---|
| **`自主进化`（SCENE_EVOLUTION）** | **2,077** | **98.8%** |
| `其他`（SCENE_OTHER） | 26 | 1.2% |
| `肺回答`（SCENE_LUNG） | **0** | 0% |
| `代码学习`（SCENE_CODE_LEARN） | **0** | 0% |
| **合计** | **2,103** | 100% |

`local_inference_count`：

| 类别 | 次数 |
|---|---|
| `本地简单回答`（KIND_SIMPLE） | 66 |
| `规则通道`（KIND_RULE） | 0 |
| `置信度守卫`（KIND_GUARD） | 0 |

### 2.2 为什么「肺回答 = 0」不是"没触发"，而是"没埋点"

全库检索 `record_llm_call(...)` 的调用点，**只有 4 处**：

| 位置 | 场景 |
|---|---|
| `nucleus/evolution/LLMEvolutionEngine.py:45` | `SCENE_EVOLUTION` |
| `nucleus/evolution/SelfReflectionEngine.py:35` | `SCENE_EVOLUTION` |
| `nucleus/reasoning/SafeEvolutionExecutor.py:722`（`_call_llm_with_followup`） | `SCENE_EVOLUTION` |
| `organs/brain/PulseSemanticComprehension.py:574` | `SCENE_OTHER` |

而 `SCENE_LUNG = "肺回答"` / `SCENE_CODE_LEARN = "代码学习"` 虽然在
`nucleus/LLMDependencyMetrics.py:32-36` 有定义并进入 `LLM_SCENES`，
**但全库没有任何一处在对话出口调用 `record_llm_call(SCENE_LUNG)`**。

⇒ **"大模型依赖度"这个指标，从设计上就不包含对话**。
它度量的是「**进化循环的 LLM 调用**在（4 个埋点口径下的）总请求中的占比」。

### 2.3 推论：方案的主攻方向与指标错位

| 方案设计 | 对"依赖度"指标的影响 |
|---|---|
| 模型 1 **意图分类器**（对话入口） | **≈ 0** —— 对话调用不记账 |
| 模型 2 响应预测器（对话） | **≈ 0** —— 同上 |
| 模型 3 经验检索器（辅助进化） | 间接 |
| **模型 4 补丁质量评估器（进化）** | **直接作用于 98.8% 的调用源** |
| 模型 5 情绪预测器 | ≈ 0 |

★**结论**：方案把**收益最小**的模型（意图分类器）列为「🔴 最高」优先级、
把**收益最大**的模型（补丁质量评估器）列为第 4 位 —— **优先级与收益倒挂**。

### 2.4 依赖度的真实根因链（建议作为方案的新 §2.5）

```
进化验证空转（56 条 applied 补丁 baseline_errors 全为 0，100% 假通过）
        ↓
补丁"假通过" → 问题并未真正修好
        ↓
下一轮自主进化又发现同样问题 → 再次调用 LLM 生成补丁（含 _call_llm_with_followup 多轮追问）
        ↓
2,077 次进化 LLM 调用（占依赖度分子的 98.8%）
        ↓
"大模型依赖度 97%"
```

⇒ **要降低依赖度，先要打断"假通过→重复修复→重复调 LLM"这个循环**，
而不是在对话入口加分类器。

## 三、三个结构性缺陷

### 缺陷 1（🔴 致命）：测量口径错位

**问题**：目标的度量与实际改动的作用域不匹配（§二）。

**修复建议**（**应先于任何建模工作**）：
1. **补全埋点**：在对话真实出口（`PulseLung._call_via_channels` 或 `_call_channel`）
   增加 `record_llm_call(SCENE_LUNG)`；在代码学习路径补 `SCENE_CODE_LEARN`。
2. **重算基线**：补全后重新采集 24 小时，得到**真实**的"对话/进化/学习"三分占比。
3. **拆指标**：把单一"依赖度"拆为三个可独立改进的子指标
   （`对话本地化率` / `进化 LLM 精简率` / `学习 LLM 精简率`）。

### 缺陷 2（🔴 高）：优先级与收益倒挂

建议**按"作用于多少比例的调用"重排**：

| 原优先级 | 模型 | 建议新优先级 | 依据 |
|---|---|---|---|
| 1 🔴 | 意图分类器 | **4**（降级） | 对话调用占比 ≈ 0（且指标未埋点） |
| 4 🔴 | **补丁质量评估器** | **1**（升级） | 直接作用于 98.8% 的调用源 |
| 3 🟡 | 经验检索器 | **2** | 辅助进化 + 已有嵌入基础 |
| 2 🔴 | 响应预测器 | **5**（降级） | 对话调用占比 ≈ 0 |
| 5 🟢 | 情绪预测器 | 6 | 数据量极小（5.7 KB） |

（★最终排序应**在完成缺陷 1 的埋点补全后用真实数据复核**，本表是基于当前数据的初步判断。）

### 缺陷 3（🔴 高）：模型 4 的前置依赖未列入前置任务

方案 §4.2 自述模型 4「训练数据 = 56 个已应用补丁 + **真实基线测试结果（需先建立真实基线）**」——
但 §五 的「阶段零·准备期」与「阶段一」**都没有"建立真实基线"这一任务**。

而实测已确认：**56 条 applied 补丁的 `baseline_errors` 全部为 0**（100% 假通过）。

⇒ **"建立真实的错误基线"必须提为阶段零的显式任务**，否则模型 4 无训练数据可用。
建议新增前置任务：**T0-3「进化验证真实基线与回滚判据」**。

## 五、技术细研：对 §8.2 八个问题的回答

> 全部基于**本仓实测代码**，非泛论。

### Q1. InnerModelRouter 应集成在哪里？如何与 PulseLung 协同？

**推荐位置**：`PulseLung._call_via_channels()` **之前**（渠道选择的上游）。

**依据**：
- `PulseLung` 是全部 LLM 调用的**统一出口**（渠道路由 `_call_via_channels` /
  `_call_channel`），在此拦截可**覆盖 100% 调用**（含进化路径）。
- 但注意：**不要**在 `PulseInnerWorld` 的策略链里做路由 —— 实测策略链只覆盖
  `PulseInnerWorld` 自身推理（约占 22% 的源码调用点），**覆盖不到进化循环**。

**协同方式**：
```
调用方 → PulseLung._call_via_channels()
             ↓ 新增前置钩子
        InnerModelRouter.route(scene, payload)
             ↓ 高置信度
        本地模型结果（不发起网络请求）
             ↓ 低置信度 / 场景不支持
        原渠道流程（零改动）
```

**关键约束（红线）**：
- 路由**只做"前置短路"**，不改动既有渠道逻辑 → 天然零回归
- 场景白名单：**首期只放行 `SCENE_EVOLUTION`**（占 98.8%，收益最大、风险最可控）
- 默认**关闭**，用 `ENABLE_INNER_MODEL_ROUTING=False` 兜底

### Q2. 模型文件应该存在哪里？

**建议**：`data/models/inner/<model_name>/<version>/`，与现有 HF 缓存并列不冲突。

**依据**：`data/models/` 已有 `models--<org>--<name>/`（HF 缓存格式）与
`fast-bge-small-zh-v1.5/`（本地目录）两种风格。**新建 `inner/` 子目录**可避免与
HF 缓存混排，且便于备份策略差异化（**inner 需备份，HF 缓存可随时重下**）。

**同时建议**（配套）：
- 模型目录加入 `.gitignore`（体积大）
- 版本目录**只保留最近 2 版**（避免重演 `data/knowledge` 的 2.13 GB 备份问题）

### Q3. 在线学习应在什么时候触发？

**建议**：**不要**做"每次推理后实时更新"。理由（基于实测）：

1. 当前 LLM 调用集中在进化循环（2077 次/4 天 ≈ **21.6 次/小时**），
   频率低且**突发**（一轮进化可能 10+ 次），逐次更新收益极低。
2. 框架已有**每日 03:00 的自我认知调度**（`DailyScheduler`），
   天然适合挂载"每日增量训练"。
3. 实时更新会引入**模型漂移**，而方案的"漂移检测 + 回滚"机制尚未建立 ——
   先有监控再开在线学习。

**推荐梯度**：
- 阶段一：**仅离线批量训练**（手动触发）
- 阶段二：**每日 03:30 增量训练**（挂在 DailyScheduler 之后）
- 阶段三：再评估是否需要对高频场景做"准实时"更新

### Q4. 内在模型推理会增加多少延迟？

**实测基线**：
- 本地 ONNX 嵌入（`bge-small-zh-v1.5`，90 MB）在本机为**毫秒级**（已有 `VectorEncoder`）。
- 当前 LLM 平均响应 **13.6 s**（方案 §7.1 自述）。
- 因此**只要本地模型 < 1 s，整体就是净收益**（把"不调 LLM"省下的十几秒换掉）。

**优化建议**：
- 模型加载**常驻单例**（`get_vector_encoder()` 已是此模式，但**首次加载为分钟级**须预热）
- 用 `onnxruntime` **量化版**（`model_optimized.onnx` 已是量化产物，实测存在）
- 路由层加**超时保护**（如 200 ms 未出结果即降级到 LLM）—— 避免本地模型拖慢主流程

### Q5. 内在模型与现有 73（实测 86）个缓存机制是什么关系？

**实测区分**：
- 现有 `cache` 类代码**绝大多数是"代码分析缓存"**（`CodeAnalyzer` / `CallGraphAnalyzer` /
  `SemanticIndexer` 等），**不是推理缓存**。
- **但框架已有"推理缓存"的雏形**：`PulseInnerWorld._cache_inference()`
  （在 `_detect_simple_query_local` 命中后调用）。

**结论与建议**：
- **不重复**，但是**互补的两层**：
  - **L0 推理缓存**（精确命中，已有）→ 相同问题直接返回
  - **L1 内在模型**（语义泛化，新建）→ 相似问题本地推理
- 建议**优先做大 L0**（成本极低：统计"相同问题重复率"），若重复率 > 15%，
  其收益可能**先于**任何模型训练见效。

### Q6. GPUCore.py 的能力是否足够支撑训练？

**实测结论**：**不需要 GPU 训练**。

- `nucleus/GPUCore.py` 只有 **10 KB**，定位是"向量检索加速"，
  **不是训练框架**。
- 方案 §6.1 已写"用轻量模型（scikit-learn），避免深度学习" —— **这个判断是对的，应坚持**。
- 对首期 3 个候选模型（意图分类 / 补丁分类 / 经验检索），
  `scikit-learn`（TF-IDF + 逻辑回归 / 线性 SVM）**CPU 秒级即可完成训练**，
  无需 GPU。
- **风险提示**：若后续要做"响应预测器"（生成式），则**必须**引入 GPU 或改用
  检索式方案 —— 建议**明确把生成式模型排除在阶段一~二之外**。

### Q7. 数据管道如何设计？需要新建哪些？

**实测数据源与可用性**：

| 数据源 | 位置 | 规模 | 首期可用性 |
|---|---|---|---|
| LLM 调用对（输入+输出） | `logs/pulse.log`（仅 0.53 MB）+ **渠道调用记录** | 2,103 次 | ⚠️ **需确认是否留全量 input/output** |
| 经验库 | `data/experience/experience_pool.json` | 1,501 条 | ✅ 直接可用 |
| 知识节点 | `data/knowledge/parquet/evol_level=L{1,2,3}/` | 12,853 节点 | ✅ 可用（**勿读 437 MB 主快照**） |
| 补丁历史 | `data/patches/patch_history.json` | 67 条 | ⚠️ 需先补真实基线 |
| 意图分类语料 | `logs/pulse.log` 的 `[R3-Intent]` 行（含 `来源=llm`） | 少量 | ⚠️ 需累积 |

**★首要任务不是建模型，而是"确认训练语料是否存在"**：
- `pulse.log` 实测仅 **0.53 MB** —— **无法支撑 2,103 对调用数据的留存**。
- ⇒ **必须新增"LLM 调用对留存管道"**（`data/training/llm_pairs.jsonl`，
  按 scene 分文件、带时间戳与反馈字段），**且应在建模型之前先跑起来**（否则永远没数据）。

**建议新建的最小管道**：
```
data/training/
  llm_pairs/<scene>.jsonl     # {ts, scene, prompt_hash, input, output, model, ok}
  labels/<task>.jsonl         # 人工/自动标注（意图标签、补丁好坏）
  stats/daily.json            # 每日语料统计
```
**红线**：管道写入**必须**受 `ENABLE_TRAINING_DATA_COLLECTION` 开关控制，
默认开启（只写本地小文件，零网络开销）。

### Q8. 如何测试模型效果不随时间下降？

**建议三层**：
1. **固定测试集**（golden set）：从早期数据中切出 **20% 冻结为测试集**，
   永不参与训练 → 每次重训后跑一次，准确率不得下降 > 2%。
2. **影子模式**（shadow）：新模型上线前先"只算不答"，
   与 LLM 结果对比 **≥ 3 天**，一致率达标才切换。
3. **漂移哨兵**：复用已有的 **自我认知引擎**（PHASE18，第39批刚收官）——
   在 `SelfAwarenessEngine` 增加一个 `inner_models` 维度，
   每日记录各模型的"置信度分布 / 采纳率 / 降级率"，**趋势下降即告警**。

★**这是方案与现有资产的最佳结合点**：方案没提到自我认知引擎，
但它**正是**"监控模型自身健康"的现成载体（第37批已实现每日调度）。

## 六、建议的修订方案

### 6.1 修订后的执行摘要（替换原 §1.3）

> **可行，但必须"先测量、再修根因、后建模型"三步走。**
> 1. **先测量**：当前"大模型依赖度 97%"只覆盖 4 个埋点（98.8% 是进化循环），
>    对话类未埋点 → **必须先补全埋点、重算基线**，否则所有目标都是错的靶子。
> 2. **再修根因**：依赖度的真实根因是「进化验证空转（56 补丁 baseline=0）→
>    重复修复 → 重复调 LLM」。**修好真实基线**比建任何模型都更直接地降低依赖度。
> 3. **后建模型**：在真实数据基础上，**按"作用于多少比例调用"排序**建模，
>    首期建议从「补丁质量评估器」与「经验检索器（复用已有 bge 模型）」入手。
