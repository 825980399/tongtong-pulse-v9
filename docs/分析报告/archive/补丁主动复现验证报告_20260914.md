## 一、问题回顾（第46/47批的结论）

原补丁验证靠「**历史日志考古**」—— 在 `pulse.log` 里数目标文件的错误行数：

```
baseline_errors = 修复前的错误日志行数
post_apply_errors = 修复后的错误日志行数
verified = (state == applied) 且 (没有错误)
```

第46批根因：`pulse.log` 只覆盖 11.9 小时，而补丁时间戳都早于日志首行
→ **100% 补丁取不到基线** → `baseline_errors` 恒为 0
→ 「**无法复现**」被当成「**修复有效**」。

第47批语义拆分后实测：`problem_fixed` = 0 true / 1 false / **59 none**，
可判定率仅 **1.67%**。

## 二、本批方案：代码级主动复现（不依赖日志）

**核心转变**：

```
旧：日志考古  →  依赖外部日志，日志被截断即失效
新：代码复现  →  用补丁自身的 original_code / modified_code 做静态复现
```

**数据基础**（实测）：60/60 条补丁**都有** `original_code` + `modified_code`，
且 **60/60 两者不相同**（不存在"空补丁"）。

**验证流程**（`nucleus/evolution/patch_active_reprobe.py`）：

```
① 按 issue_type 选检测器（AST 静态分析）
② original_code  →  期望检出 ≥1 处目标问题（复现成功）
③ modified_code  →  期望问题减少/消失（修复有效）
```

**检测器**（本库 `issue_type` 分布）：

| issue_type | 条数 | 检测器 |
|---|---|---|
| `silent_exception` | 50 | AST 找 `except ...: pass` / except 体无留痕 |
| `print_instead_of_log` | 8 | AST 找 `print(...)` 调用 |
| `code_optimization` | 2 | **无可靠静态判据** → `not_applicable`（不判通过） |

**结论分类**（任务书 §T1.4，另加 `partial_fix` 细分）：

| 结论 | 含义 |
|---|---|
| `true_pass` | **真通过**：修复前复现出问题 + 修复后**完全消失** |
| `partial_fix` | **部分修复**：问题**减少但未清零**（★新增细分，不掩盖部分修复） |
| `false_pass` | **假通过（无法复现）**：修复前**根本复现不出**该问题 |
| `ineffective` | **修复无效**：修复前有问题 + 修复后**未减少** |
| `verification_failed` | 代码片段无法解析 |
| `not_applicable` | 无对应检测器（不判通过） |

## 三、验证结果（60 条历史补丁全量复现）

| 结论 | 数量 | 占比 |
|---|---|---|
| **真通过**（完全清零） | **51** | 85.0% |
| **部分修复**（减少未清零） | **7** | 11.7% |
| 不适用（无检测器） | 2 | 3.3% |
| **假通过（无法复现）** | **0** | **0.0%** |
| 修复无效 | **0** | 0.0% |
| 验证失败 | 0 | 0.0% |

**修复率**：

| 口径 | 数值 | 说明 |
|---|---|---|
| 严格（仅完全清零） | **0.8793** | 51 / 58 可判定 |
| 宽松（含部分修复） | **1.0** | 58 / 58 可判定 |

### 3.1 ★与第47批口径的对比（本节为核心结论）

| 口径 | `problem_fixed` 结果 | 可判定率 |
|---|---|---|
| 第47批（**日志基线**） | 0 true / 1 false / **59 none** | **1.67%** |
| 第51批（**代码复现**） | **58 true** / 2 none | **96.7%** |

**⇒ 结论修正**：

> **「无法用日志验证」≠「没有被修复」。**
> 第47批的 0% 是**日志口径不可判定**，而非"补丁无效"。
> 代码级复现证明：**补丁系统实际上是有效的**（58/58 可复现，0 条假通过）。

**"空转"的真正根因**不是"补丁是空的"，而是**验证方式依赖了会被轮转截断的日志**。

### 3.2 七条「部分修复」的说明

7 条 `partial_fix` 全部满足 `after < baseline`（问题确实减少），
未清零的原因是**检测器按整个代码块统计**，而补丁只修其中**一处**，
代码块内其他同类问题**不属于本补丁的目标范围**。

例（`organs/core/PulseProprioception.py::_print_report_console`）：
修复前 20 处 `print(...)` → 修复后 7 处（该补丁只改其中一处）。

**⇒ 这是代码块级统计的固有局限**，已在报告中显式标注，未当作"修复无效"。

## 四、接入（problem_fixed 的最高优先级数据源）

`nucleus/evolution/patch_verification_split.py` 新增分支：

```
⓪ 主动复现（代码级）  ← 最高优先级（不依赖日志）
① 日志基线（第47批逻辑）← 回退（零回归）
```

映射规则：

| `reprobe_verdict` | → `problem_fixed` | 粒度 |
|---|---|---|
| `true_pass` | `True` | `active_reproduction` |
| `partial_fix` | `True` | `reproduction` |
| `false_pass` / `ineffective` | **`False`** | `active_reproduction` |
| `verification_failed` / `not_applicable` | `None`（不判定） | `static_only` |

**接入后实测**（60 条）：`problem_fixed` = **58 True / 2 None**。
（接入前：0 True / 1 False / 59 None）

★**零回归**：无 `reprobe_verdict` 字段时**完全回退**第47批日志逻辑
（门控测试 `test_33` / `test_34` 覆盖）。

## 七、结论与建议

1. **补丁系统有效性得到证明**：58/58 可复现，51 条完全修复 + 7 条部分修复，
   **0 条假通过**。
2. **P0-2 的"空转"已根治**：验证不再依赖会被截断的日志。
3. **建议后续**：
   * 新增 `issue_type` 时**必须**实现对应检测器，否则该补丁**不可判定**
     （当前 `code_optimization` 2 条即此情况）；
   * `partial_fix` 的"剩余项"应配合**diff 区域限定**进一步收敛（登记为债务）；
   * 日志基线逻辑**保留**（作为补充证据），但**不再**作为唯一判据。
