## 3. 口径合理性分析（任务书要求的第二项）

### ★ 缺陷一：分母**排除**了两类真实的本地工作（量级碾压）

| 计数 | 值 | 是否进分母 |
|---|---|---|
| `local_inference_total` | **125** | ✅ 进 |
| `search_total`（无头浏览器 774） | **774** | ❌ **不进** |
| `digestion_total`（知识消化 36032） | **36032** | ❌ **不进** |

**代码依据**：`:132 total_requests = llm_total + local_total` —— 只加两项。
`search` / `digestion` 被**记录**（计数在增长）却**不进任何派生指标**。

**影响量化**：

| 口径 | 计算 | 依赖度 |
|---|---|---|
| **现行**（分母 = llm + local_inference） | `5382 / 5507` | **97.73%** |
| 若计入 search | `5382 / (5507 + 774)` | 85.7% |
| 若计入 search + digestion | `5382 / (5507 + 774 + 36032)` | **12.72%** |

★ **同一份原始数据，只因分母口径不同，结论从「严重依赖大模型」变成「自持力 87%」。**

**语义质疑**：`total_requests` 的注释自称「回答类请求总数」。
但「知识消化 36032 次」是真真切切的**本地处理**，「无头浏览器检索 774 次」也是
**本地发起的、不经 LLM 的能力**。把它们全部排除在「自持力」之外，
等于宣称「只有不调用大模型的对话式回答才算自立」—— 这是一个**过窄**的定义。

### ★ 缺陷二：分母**缺少增长来源**（构造上不可能下降）

`record_local_inference` 全项目**仅 1 个生产调用点**（`PulseInnerWorld:2095`，
且只在「本地简单回答」这一条路径上）。而分子有 **5 个调用点**，其中
`SCENE_EVOLUTION`（自主进化）就有 **3 个**。

**结构性不对称**：

```
分子（LLM 调用）              分母（本地推理）
  ├─ 自主进化 × 3 处            └─ 本地简单回答 × 1 处
  ├─ 肺回答 × 1 处
  ├─ 语义理解 × 1 处
  └─ ★进化循环每轮都调 LLM         ★进化循环的本地规则修复**无埋点**
```

★★ **最致命的一点**：T-93b 已实测 `local_rule` 补丁 **65 条、修复率 95.4%** ——
这是**实实在在的本地工作成果**，却**一条也没有计入 `local_inference`**
（`KIND_RULE = "规则通道"` 零调用点）。

⇒ **「自学习闭环降低大模型依赖」这个命题在指标上被构造性地证伪**：
闭环每产出一个本地修复，分子（因 LLM 被调用）涨，分母**纹丝不动**。
**依赖度只可能上升，不可能下降** —— 与台账 D008「依赖度反升 97%」完全一致。

### 缺陷三：场景/类型常量空转

- `SCENE_CODE_LEARN`（代码学习）：**定义存在、零调用点** ⇒ 恒 0
- `KIND_RULE`（规则通道）、`KIND_GUARD`（置信度守卫）：**定义存在、零调用点** ⇒ 恒 0

⇒ `LLM_SCENES`（4 项）与 `LOCAL_KINDS`（3 项）在报表里呈现**结构性零值**，
读者容易误读为「这些能力从未使用」，实际是**埋点缺失**。

### 缺陷四：`llm` 总量未区分「有效调用」与「无效调用」

`SCENE_EVOLUTION = 3426` 包含**大量重复调用**（T-93b 实测：每轮 20 个问题里
8~10 个是「已有待审批」的重复问题，`_llm_skipped_pending` 计数器已存在但
**其值为多少未进依赖度报表**）。
⇒ 指标把「因待审批死循环而白白消耗的 LLM 调用」与「有价值的调用」**混为一谈**。

## 4. 修正方案建议（任务书要求的第三项）

★ 以下均为**方案建议**，本批**不实施**；三个方案可独立裁决。

### 方案 A（推荐·最小风险）：**分层报告**，不改现有指标值

保留 `llm_dependency_ratio` 原义（**对话/回答场景**的依赖度，命名澄清为
`dialog_dependency_ratio` 或仅在文档中标注），**新增**两个并列指标：

| 新指标 | 公式 | 语义 |
|---|---|---|
| `overall_llm_share` | `llm_total / (llm_total + local_total + search_total + digestion_total)` | **全栈**大模型占比（实测 **12.72%**） |
| `evolution_local_rule_rate` | 本地规则修复数 / 总修复数 | 自学习闭环的**本地化成效**（T-93b：**95.4%**） |

**优点**：零行为变化、历史数据可比、直接回应 D008（给出「闭环是否降依赖」的可判据指标）。
**缺点**：报表字段变多。

### 方案 B：**补齐埋点**（治本，但改动面大）

| 动作 | 位置 | 说明 |
|---|---|---|
| `record_local_inference(KIND_RULE)` | 本地规则修复成功处（`SafeEvolutionExecutor` 本地闸门通过后） | 让分母反映本地修复能力 |
| `record_llm_call(SCENE_CODE_LEARN)` | 代码学习通道 | 让 `代码学习` 不再恒 0 |
| `record_local_inference(KIND_GUARD)` | 置信度守卫拦截处 | 让 `置信度守卫` 不再恒 0 |
| 新增「有效/无效 LLM 调用」拆分 | 依赖度报表 | 用已有的 `_llm_skipped_pending` 等计数 |

**优点**：指标真实反映能力。**缺点**：属**行为改动**（新增计数），需评估对
`log_hourly` 告警阈值的影响；且埋点位置分散在进化主循环热路径上。

### 方案 C：**重命名 `total_requests`**（消除命名误导）

`total_requests` 实际 = `llm + local`，**不含** search/digestion，
字段名严重误导（读者会以为它是「所有请求」）。

**建议**：重命名为 `answer_requests`（或加文档标注），**保留旧字段一个版本**做兼容。
**优点**：零逻辑变化、纯澄清。**缺点**：会动 `data/metrics/llm_dependency.json` 的
字段契约（需同步 `get_snapshot` 消费端）。

### 建议的裁决顺序

1. **先做 C**（纯澄清，零风险）—— 消除「97% 是什么」的歧义源头
2. **再做 A**（分层报告）—— 让 D008 变成可判据命题
3. **最后议 B**（补埋点）—— 涉行为改动，建议单独立批
