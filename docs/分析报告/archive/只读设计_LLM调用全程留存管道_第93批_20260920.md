## 2. 真实缺口（任务书要求的第二项）

### 2.1 缺口一：`tokens` 恒为 0（三路证据）

**路径 A —— schema 层**：`call_recorder.py:314` `record(..., tokens: int = 0, ...)`
⇒ 默认值 0，且 `:342` `"tokens": int(tokens or 0)` 对 `None`/`0` 一律写 0。

**路径 B —— adapter 层（★根因）**：`openai_compatible_adapter.py:57 parse_response`
**只取 `choices[0].message.content`，完全不解析响应里的 `usage`**：

```python
def parse_response(self, response: Any) -> str | None:
    """提取 choices[0].message.content，逐层做结构防御。"""
    ...
    content = message.get("content", "")
    ...
    return _text or None          # ← usage / prompt_tokens / completion_tokens 全部丢弃
```

**路径 C —— 调用点层**：实测 `calls_20260920.jsonl` 761 条中
`"tokens"` 字段全部为 `0`；`prompt_tokens` / `completion_tokens` / `total_tokens`
/ `usage` 关键词命中数 **均为 0**。

⇒ **adapter 不解析 `usage` ⇒ 调用点拿不到值 ⇒ 无从传入 ⇒ 恒 0。**

### 2.2 缺口二：`cost` 字段不存在

`record()` 的 schema 共 **13 个字段**：
`trace_id / ts / origin / prompt / response / prompt_version / channel / model /
duration / tokens / status / error / feedback`

**没有 `cost` / `price` / `money` 任一字段**（全库关键词命中 0）。

### 2.3 缺口三：`channel` / `model` 实盘为空

首条样本 `channel = ""`、`model = ""` ⇒ 无法按模型/渠道**分账**，
即便补上 tokens 也无法算成本。

### 2.4 缺口四：留存覆盖不全（见 §1.1）

对话（肺回答 1895 次）与语义理解通道**未接留存** ⇒ 「全程留存」尚不成立。

## 3. 留存格式设计方案（任务书要求的第三项）

### 3.1 设计原则

1. **向前兼容**：现有 13 字段**一字不改**（8 天存量数据仍可读）；
   新增字段一律**可选 + 缺省安全值**。
2. **不新增开关**：复用 `ENABLE_LLM_CALL_RECORDER` 总开关 + 已登记的
   `ENABLE_LLM_TRACE_*` 子开关（避免第92批已裁决的「防御性开关必须落 config.py」同型债）。
3. **成本可算但不必在线算**：留存**用量**（tokens），单价与换算**离线**做
   （单价会变，写死进日志会让历史数据不可比）。

### 3.2 建议 schema（v2，向后兼容叠加）

| 字段 | 类型 | 状态 | 说明 |
|---|---|---|---|
| `trace_id` | str | 现有 | `m40-<hex12>` |
| `ts` | float | 现有 | epoch |
| `origin` | str | 现有 | `evolution_task` / `system_internal` / `user_query` |
| `prompt` | str | 现有 | 已脱敏 + 截断 |
| `response` | str | 现有 | 已脱敏 + 截断 |
| `prompt_version` | str | 现有 | 如 `evolution.repair.v1` |
| `channel` | str | 现有 | ★**建议补实**（app 层填入 gateway 名） |
| `model` | str | 现有 | ★**建议补实**（adapter 填入实际 model id） |
| `duration` | float | 现有 | 秒 |
| `tokens` | int | 现有 | ★**建议补实**（见 §3.3） |
| `status` | str | 现有 | `success` / 错误码 |
| `error` | str | 现有 | 规范化文本 |
| `feedback` | null/obj | 现有 | 旁路文件回填 |
| **`usage`** | **obj** | **新增（可选）** | `{prompt_tokens, completion_tokens, total_tokens}` —— 原始三值，便于按不同单价重算 |
| **`cost_estimate`** | **float** | **新增（可选）** | 仅当**显式配置了单价**时写入；未配置则缺省 `null`（**不猜**） |
| **`cost_currency`** | **str** | **新增（可选）** | 如 `"CNY"`；与 `cost_estimate` 成对出现 |
| **`request_id`** | **str** | **新增（可选）** | 上游 gateway 返回的 request id，便于与账单对账 |
| **`retry_of`** | **str** | **新增（可选）** | 重试链：指向被重试的 `trace_id`（本框架有 followup 重试） |

### 3.3 打通 `tokens` 的最小改动路径（**本批不实施，供裁决**）

```
① adapter 层（根因）
   BaseLLMAdapter 新增可选方法  extract_usage(response) -> dict | None
   OpenAICompatibleAdapter 实现：返回 response.get("usage") 的规范化三值
   ★不改 parse_response 签名（零回归），只**新增**方法

② 调用层
   LLM 调用出口拿到 (text, usage)，把 usage 传给 record(..., usage=usage)
   `tokens` 字段 = usage.total_tokens（保持向后兼容；无 usage 时仍写 0）

③ 留存器
   record() 新增可选参数 usage: dict | None = None
   写入新增字段 "usage"；★`tokens` 语义不变（= total_tokens 或 0）
```

**为什么先补 adapter 而不是直接在调用点猜**：`usage` 只能从**原始响应**取；
调用层拿到的是已经 `parse_response` 过的**字符串**。⇒ **必须改 adapter**。

### 3.4 成本换算的落位建议

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 在线算 | 写入时按 config 单价算 `cost_estimate` | 写入简单；但**单价变更后历史数据不可比** |
| B. **离线算（推荐）** | 只留 `usage` 原始值，另设离线脚本按「当时的单价表」重算 | 历史可比；需维护单价表版本 |
| C. 双写 | 两者都写 | 冗余但最灵活 |

★ 建议 **B**，理由：本框架已有 `ENABLE_LLM_CALL_RECORDER` 长留存（8 天+）与按天文件，
离线重算成本极低；而单价（尤其国内渠道）变动频繁，**写死进日志会污染历史**。

### 3.5 留存覆盖补齐建议

| 通道 | 现状 | 建议 |
|---|---|---|
| 自主进化 3 处 | ✅ 已接装饰器 | 保持 |
| 对话（`PulseLung:1742`） | ❌ 无 | 加 `record_call(origin="user_query", ...)` |
| 语义理解（`PulseSemanticComprehension:574`） | ❌ 无 | 加 `record_call(origin="system_internal", ...)` |
| 意图分类（`SearchIntentClassifier`） | ❌ 无 | 可选（低频） |
