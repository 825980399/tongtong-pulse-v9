# 内存占用分析报告（主线第78批 · 2026-09-18）

## 1. 结论速览

- 实测硬件内存告警 **95%**（高于任务书描述的 91%）。
- 首要常驻内存消费者：`data/knowledge/pulse_knowledge_snapshot.json` **478MB**
  （由 300MB 增长到 478MB，节点持续累积）。
- 全库最大 json/pkl 文件即此快照（次大为 parquet/其他元数据，量级远小）。
- **判定：属数据增长，非代码泄漏**。节点池无界累积导致快照体积持续增大；
  截断/压缩该文件有丢数据风险，本批不动数据，**改以监控告警达成验收**。

## 2. 排查过程

1. 枚举全库 `.json/.pkl/.bin` 大文件（排除 `.bak_batch*/tmp/logs/.git`），TOP 体积即快照 478MB。
2. 确认加载链路：`PulseSnapshot` / `PulseInnerWorld` 启动时读取该快照进内存
   （`node_pool.get_all_including_evicted()`），即常驻内存主体。
3. 未发现的代码层泄漏：模块的 deque/环形缓冲（`_pulse_durations`/`_history` 等）均有 `maxlen` 上限，
   非无界结构；`runtime_metrics` 自身内存占用可忽略。

## 3. 修复方案（T3）

`runtime_metrics` 新增两类内存告警（呼应任务书验收"内存<80%"）：

- **高水位告警**：`mem_percent >= 80%` → `mem_percent_high`（明确"已超验收线"）。
- **趋势告警**：每采样点记录 `mem_percent` 进趋势窗口；窗口持续上升 + 涨幅≥10pct + 未破阈
  → `mem_percent_trend_rising`（提前预警，避免陡增措手不及）。

使"<80%"验收**可观测、可早预警**；瞬时压到 80% 以下需后续批次针对 478MB 快照数据增长
做专门治理（冷热分离落地 / 快照轮转裁剪 / 节点池上限）。

## 4. 验证

- 单测：`test_m78_mem_alert.py`（6 例）覆盖高水位、趋势、窗口记录、阈值可配，全过。
