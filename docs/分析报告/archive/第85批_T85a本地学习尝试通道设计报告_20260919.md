## §2 设计：独立的最小闭环通道

### 2.1 接线点

**位置**：路径A 块（L1278-1316）**之后**、路径B（L1328）**之前**。

```python
# ★M85-1（第85批 T-85a）：本地学习尝试通道。
#   对「本地无规则」的问题，先做一次低风险保守修复尝试（不替代 LLM 通道，
#   不自动应用，只入队待审批）。验证失败则如实记录并交给既有 LLM 通道。
if (not _local_ok and not _has_pending_dup and _snippet
        and self_inspector and _organ and _method
        and (_file or _resolved_file)):
    try:
        self._m85_learning_attempt(
            _issue, _file or _resolved_file, _method, _snippet, _organ)
    except Exception as _m85e:
        _module_logger.debug(
            f"[M85 学习尝试] 异常已忽略: {type(_m85e).__name__}: {_m85e}")
```

**零侵入保证**：
- 位置在路径A **之后**（不改路径A 的 `_local_ok` 判据）；
- 在路径B **之前**，但**不 `return`/不 `continue`** → LLM 通道行为**逐字不变**；
- 不复用 `_local_patch` 变量 → 不参与 L1448 的择优提交（避免改变 `_local_submitted` 语义）。

### 2.2 保守修复策略（只做「纯文本、可验证、语义不变量明确」的两类）

| 策略名 | 触发形态 | 改写 | 为何安全 |
|---|---|---|---|
| `except_log` | `except [X] :\n <缩进>pass` | 补 `self._log(LogLevel.ERROR, f'异常: {e}')` | 与既有 `silent_exception`/`bare_except` 策略**同源同形**（复用同一正则） |
| `http_timeout` | `requests.(get\|post\|put\|delete\|patch\|head)(...)` 且实参无 `timeout=` | 追加 `timeout=<N>` | 只增不删；`timeout` 是 requests 官方关键字；N 取保守值 |

**明确不做**（写入报告，避免后续误以为遗漏）：
- 「加 try-except 包裹裸调用」→ 需要作用域/缩进/异常语义三重推断，纯文本替换无法保证语义不变量；
- 「加 None 检查」→ 需要数据流分析（该表达式是否可能为 None）；
- 「long_method 拆解」→ 属结构性重构，不属"低风险保守修复"。

> 理由：任务书 §T-85a 四类改法里，后三类都需要**语义分析**才能安全改写；在"补丁不自动应用"的前提下，产出错误改写仍是**污染 pending 队列**的成本。本批取「可证明安全的两类」，其余类型如实记录 `no_safe_fix`。

### 2.3 学习记录

落盘 `data/patches/local_learning_attempts.jsonl`（**append-only**，JSONL），每次尝试一行：

```json
{"ts": 1758290000.0, "issue_type": "long_method", "file": "organs/xxx.py",
 "method": "foo", "strategy": "except_log", "result": "success|failed|no_safe_fix",
 "llm_fallback": true, "patch_id": "patch_learn_...", "verify_reason": "..."}
```

字段与任务书 §T-85a.2 一致（`issue_type/file/method/attempted_fix/result/llm_fallback`），
其中 `attempted_fix` 落地为 `strategy`，另加 `patch_id`/`verify_reason` 便于审计。

### 2.4 补丁标记

入队补丁设 `source="local_learning"`、`learning_attempt=True`、`confidence="high"`、`risk_level="低"`。
- `source="local_learning"` ≠ `"local_rule"` → **天然不被 T-85d 的自动应用条件命中** ⇒ 满足「默认不自动应用」；
- 走 `save_pending_patch()` ⇒ 复用既有备份/审批/去重链路。

### 2.5 灰度开关

`_m85_learning_attempt_enabled()` 读 `EVOLUTION_CONFIG.get("learning_attempt_enabled", True)`。
- **不改 `config.py`**（红线②）：键不存在时取默认 `True`；
- 关闭 → 通道整体短路，行为回到改造前（零副作用）。

## §3 安全设计小结

| 风险 | 缓解 |
|---|---|
| 生成错误补丁污染队列 | ① 只做两类可证明安全的纯文本改写；② 必须通过 `verify_in_copy` 才入队；③ 不自动应用 |
| 影响既有本地/LLM 双通道 | 接线点不 `return`/`continue`，不复用其变量；开关关闭即完全短路 |
| 队列膨胀 | 复用 `has_pending_patch_for` 前置预检（同位置已有待审批 → 跳过） |
| 写盘风险 | 仅追加 `data/patches/local_learning_attempts.jsonl`（任务书指定路径），不碰 `data/knowledge/`（红线③） |
| 异常扩散 | 整个调用点包 `try/except` 且带 `type(e).__name__: e`（铁律：降级分支必须带异常对象） |

## §4 与任务书的差异清单（供星轨裁决）

1. **插入点**：任务书 `_cooldown_classify` → 实测改在路径A 之后（理由见 §0/#1、§1）。
2. **「直接转 LLM」的表述**：LLM 通道（路径B）**本来就无条件执行**，不存在"需要显式转"的动作；本通道只是**新增一次本地尝试**并把结果记入学习日志。
3. **四类保守修复**：只实现 2 类（`except_log` / `http_timeout`），另 2 类需语义分析 → 如实记录 `no_safe_fix`，不硬做。
