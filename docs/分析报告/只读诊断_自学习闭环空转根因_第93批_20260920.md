## 0. 结论先行

**任务书的因果假设需要修正。**

任务书（转述台账 D014）称：「进化验证空转是依赖度 97% 的根因」，并要求定位「空转在
哪一环：①发现问题后不生成补丁？②生成后验证不通过？③验证通过但不应用？」

**实测结论**：

1. 空转**确实存在**，且已量化：14 轮累计 **发现 168 / 修复 4 = 总修复率 2.38%**。
2. 空转的**主因是第 ③ 环「验证通过但不应用」**，而非第 ② 环。具体机制是
   **「待审批永不被消化」的闭环**（占未修复归因的 **28.6%**，单项最大）。
3. 但 ③ 环**不是依赖度 97% 的根因**。依赖度高的**首因是指标口径缺陷**
   （见 `只读分析_大模型依赖度指标口径_第93批_20260920.md`）：
   分子随每次 LLM 调用单调增长，分母只有「本地简单回答」一个来源。
   **即便修复率提到 100%，依赖度也不会显著下降** —— 因为修复成功**没有埋点**。
4. 台账 D008「依赖度未实质下降」的描述是**正确的**；台账给的处置建议
   「按真实修复率重定义闭环成效，勿称已降依赖」**也是正确的**。
   ⇒ 本批支持该建议，并补上量化依据。

## 2. 根因定位（任务书要求的第三项）

### 2.1 ③ 环「验证通过但不应用」= 待审批死循环（主因，48 次）

**机制链（四处代码位互相印证）**：

```
① main.py:3289        _patch_mgr.apply_all_pending(only_approved=True)
                      └─ 只应用 status == "approved" 的补丁
② PatchManager.py:2144  only_approved 为真时，非 approved 一律跳过并计数
                      └─ 生成出来的补丁默认 status 是 pending ⇒ 被跳过
③ SafeEvolutionExecutor.py:1455/1530/3839
                      三处前置检查「同文件同方法已有待审批补丁」
                      └─ 命中即 _bump_reason("已有待审批") 并**跳过生成**
④ SafeEvolutionExecutor.py:287
                      冷却表 "已有待审批": 7200.0（2 小时）
```

**闭环**：
```
发现问题 → 生成补丁 → 入 pending（等人工裁决）
   ↑                                        ↓
   └── 下一轮重新发现同一问题 ←── 补丁永不被 apply（无人裁决）
       （命中③，计入「未修复」）        （②只应用 approved）
```

**后果**：同一批问题**每轮重复出现**，每次都计入「未修复」分母，而**修复数恒 0**。
这解释了为何 14 轮里 10 轮修复率为 0.0%。

**为什么自动化流程里无人裁决？** 用户侧（星轨）按批交付报告定期裁决，而进化循环
是**分钟级/小时级**连续运行的 ⇒ 裁决速率远低于生成速率 ⇒ pending 只增不减。

### 2.2 ② 环「生成后验证不通过」= LLM 补丁质量（32 次）

`logs/pulse.log` 实测（第93批当日）：

| 日志模式 | 次数 |
|---|---|
| `补丁验证失败` | **42** |
| `完整性检查失败` | 12 |
| `语法错误` | 8 |
| `路径沙箱拒绝` | 7 |

与上表 `llm` 补丁 **0/11 可判定** 完全一致。
★ 第91/92 批已修「缩进漂移」与「关2 文案」，但**存量 LLM 补丁仍全部不可判定** ——
因为它们生成于修复之前，且 `problem_fixed` 依赖 `reprobe`/`baseline`，**不会被追溯重算**。

**注**：`real_fix_rate` 的分母是**可判定补丁数**（`None` 不计），故 LLM 补丁全 `None`
时**不进分母**——这让 `real_fix_rate()` 显示 100%，却**掩盖了 LLM 通道彻底无效**这一事实。
⇒ 见 §4 建议 3。

### 2.3 ① 环「无本地规则」= 覆盖不足（37 次）

| 类型 | 次数 |
|---|---|
| `cross_module_singleton_call` | 22 |
| `ERROR`（泛化日志类） | 13 |
| `non_atomic_write` | 2 |

⇒ 本地规则对这三类问题无方案，全部转 LLM；而 LLM 通道通过率 0%（§2.2）⇒
这 37 次**必然**计入未修复。

### 2.4 「进化验证空转」的准确定位（回应台账 D014 的措辞）

台账 D014 原文：`patch_verification_split.py 确证 baseline 恒 0 根因；...但自主修复率仍~1.8%`。

实测**支持**「`baseline` 恒 0」这一根因，但需**分层**：

| 层 | 现象 | 证据 |
|---|---|---|
| L1 判据层 | `baseline_errors` 采集不到 ⇒ `problem_fixed=None` | 26 条 None 中 9 条 reason 明写「修复前基线为 0」 |
| L2 探针层 | `EvolutionEffectVerifier` 缺「问题复查探针」⇒ 效果恒「未判定」 | `EvolutionEffectVerifier.py:168`；日志 5 条 `[效果验证] 未判定（缺少问题复查探针）` |
| L3 应用层 | 补丁卡在 pending，**从未产生 post_apply 数据** | §2.1 闭环 |

★ **L3 是 L1/L2 的上游**：补丁不应用 ⇒ 没有 `post_apply_errors` ⇒ 即便有基线也无法比对
⇒ 验证必然「空转」。**故 L3（待审批死循环）才是「空转」的真正起点**。

## 4. 改进建议（供星轨裁决，本批不实施）

| # | 建议 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **待审批队列设上限 + 老化策略**：`pending` 超过 N 条或超过 T 小时未裁决时，对**低风险 + 非核心文件 + local_rule 来源**的补丁走已有的 `_m85_local_low_risk_auto_apply` 自动放行 | 直击 28.6% 主因 | 需确认 `_m85_local_low_risk_auto_apply` 的判据足够严（已有开关） |
| 2 | **`已有待审批` 计时器改为「按补丁」而非「按问题位置」**：现有 7200s 冷却对同一位置反复生效，导致问题被无限期跳过 | 降低重复发现 | 需与 #1 配套，否则只是更快地重复发现 |
| 3 | **`real_fix_rate` 增加「通道有效性」副指标**：分别报告 `local_rule` / `llm` 的可判定率与修复率（本报告 §1.2 即该口径） | 消除「100% 修复率」的假象 | 纯指标口径，零代码风险 |
| 4 | **为 LLM 补丁补 `reprobe` 检测器**：`cross_module_singleton_call` 等 3 类问题补探针 | 让 LLM 通道可判定 | 工作量较大，建议单独立批 |
| 5 | **为「本地规则修复成功」补埋点**：`record_local_inference(KIND_RULE)` 当前**无生产调用点**（仅 `PulseInnerWorld` 的 `KIND_SIMPLE` 1 处） | 让依赖度指标能反映本地修复 | 见 `只读分析_大模型依赖度指标口径_第93批_20260920.md` §3 |

★ 建议 1/2 属**行为改动**，建议 3/5 属**指标改动**，建议 4 属**能力改动** ——
三者应分开裁决，避免混批。
