## 二、现状分析

### 2.1 `write_guard` 的生效范围（源码取证）

`nucleus/data/write_guard.py` 的拒写判据是**三条件同时成立**：

```python
def reject_write(path, explicit=False, component=""):
    if explicit:                  return False   # ① 显式注入 → 放行
    if not guard_enabled():       return False   # ② 开关关闭 → 放行
    if not is_test_env():         return False   # ③ ★非 pytest → 放行
    return is_production_data_path(path)         # 路径在项目 data/ 下 → 拒写
```

其中 `is_test_env()`：

```python
if os.environ.get("PYTEST_CURRENT_TEST"): return True
return "pytest" in sys.modules
```

★**这就是缺口**：判据是「**进程里有没有 pytest**」，而不是「**这是不是一个受控的测试进程**」。

### 2.2 实测验证（本批 T5 实测）

| 场景 | `guard_write()` 返回值 | 判定 |
|---|---|---|
| pytest 环境，`explicit=False` | **False（拒写）** | ✅ 正确拦截，并打印 WARNING |
| pytest 环境，`explicit=True` | `True`（放行） | 设计如此（显式注入=隔离） |
| **非 pytest 进程（普通脚本）** | **`True`（放行）** | 🔴 **完全不设防** |


## 四、★对「24/27 条记录」真实来源的判定

任务书 P2-335 的证据是「生产库出现 `raw_summary`/`summary_version=2` 记录，
`before` 窗口 24 条」。本批实测澄清如下：

| 事实 | 数值 |
|---|---|
| 带 `raw_summary` 的记录数 | **27** |
| `summary_version == 2` | **27 / 27** |
| `is_summarized` | **27 / 27** |
| 这些记录的 `timestamp` | **全部集中在 2026-09-09 20:07:28 ~ 20:19:30**（12 分钟窗口） |
| 框架重启时刻（日志取证） | 2026-09-14 15:14:07 |
| 第47批止血代码落地 | 2026-09-14 07:40 |

**判定**：这 27 条是 **09-09 创建的旧记录**，其 `timestamp` **未被改动**；
`_summarize_experience()`（第47批版）会给旧记录**补写** `raw_summary` +
`summary_version=2` 而**不动 timestamp** —— 与实测特征**完全吻合**。

⇒ **结论**：
1. **不是测试写入**（测试被守卫拦截，且无参构造为 0）；
2. **不是普通脚本写入**（无证据；且脚本路径守卫虽空但本次会话未运行写脚本）；
3. **而是「框架自身在第47批代码生效后，对旧记录执行摘要路径」的产物** ——
   即 **P0-3 止血机制生效的副产品**，属**预期行为**（第47批已加 `raw_summary` 保全原文）。

★**任务书对 P2-335 的定性需修正**：风险**真实存在**（非 pytest 脚本无防护），
但**本次事件并非该风险触发**，不宜用本次数据作为 P2-335 的"真实案例"。

## 五、修复方案评估

### 方案 A：扩展 `write_guard` 到非 pytest 语境

```python
def is_test_env():
    if os.environ.get("PYTEST_CURRENT_TEST"): return True
    if "pytest" in sys.modules: return True
    return bool(os.environ.get("PULSE_TEST_MODE"))     # ← 新增
```

| 项 | 评估 |
|---|---|
| 优点 | 改动最小（3 行）；与既有判据同源；零回归 |
| 缺点 | **仍需人工设环境变量** → 靠自觉，**不解决"忘记设置"** |
| 成本 | 0.2 小时 |
| 风险 | 低 |

### 方案 B：环境变量指定经验库路径（`PULSE_EXPERIENCE_POOL_PATH`）

```python
_BASE = os.environ.get("PULSE_EXPERIENCE_POOL_PATH") or <默认 data/experience>
```

| 项 | 评估 |
|---|---|
| 优点 | 测试/脚本可**天然隔离**；不依赖守卫判据；语义清晰 |
| 缺点 | 需改 `ExperiencePool.__init__` 的路径解析；**需同步改所有读取方**（否则读写不同库） |
| 成本 | 1.5~2 小时（含读取方核对） |
| 风险 | 中（路径解析变更影响面广） |

### 方案 C：写路径守卫升级 —— 默认只读 + 显式授权 ★推荐

```python
# 新增：只读模式（写入需显式授权）
def write_allowed(kind: str = "experience_pool") -> bool:
    """
    默认规则（按进程类型）：
      * 生产框架进程（PULSE_FRAMEWORK=1，由 main.py 设置）→ 允许写
      * 其他进程（测试/脚本/导入方）                → 默认只读
      * 显式授权：PULSE_ALLOW_DATA_WRITE=1 或显式 base_dir
    """
```

| 项 | 评估 |
|---|---|
| 优点 | **根治**：不再依赖"是不是 pytest"，而是"**是不是框架进程**"；默认安全 |
| 缺点 | 需在 `main.py` 设置 `PULSE_FRAMEWORK=1`；需梳理全部写入点 |
| 成本 | 2~3 小时 |
| 风险 | 中（若漏设 `PULSE_FRAMEWORK` → 框架自身写被拒 → **必须加"框架进程自检"降级**） |

### 方案 D：现状可接受，只加监控告警

| 项 | 评估 |
|---|---|
| 优点 | 零改动 |
| 缺点 | **不解决**非 pytest 脚本无防护的**真实缺口**；长期埋雷 |
| 成本 | 0.5 小时（埋点） |
| 风险 | 低（但问题留存） |

### ★推荐组合

**第51批**：**方案 C（主）+ 方案 A（辅）+ consumers 隔离落点**
1. **C**：新增 `PULSE_FRAMEWORK` 进程标识 → 写路径默认"非框架进程只读"；
   `main.py` 启动时设置；★**必须**保留"显式 base_dir 注入即放行"（否则测试全红）。
2. **A**：`PULSE_TEST_MODE` 作为过渡期兼容判据。
3. **consumers 隔离落点**：pytest 下 `data/reports/` 改写到 `tmp/pytest_reports/`（保持审计意图不变）。

**不建议**单独用方案 B（影响面大、收益与 C 重叠）。
