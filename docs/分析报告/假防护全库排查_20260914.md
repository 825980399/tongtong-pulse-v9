## 一、排查背景

第50批发现 **P2-339 假防护**：

```python
_gw(_p, explicit_base_dir=True)     # 真实参数名是 explicit → TypeError
                                    # 被紧跟的裸 except: pass 吞掉 → 守卫从未生效
```

**教训**：「有守卫」≠「守卫生效」。本批按要求做**全库排查**。

---

## 二、排查口径（AST）

扫描条件（**三条同时成立**才命中）：

| # | 条件 | 判据 |
|---|------|------|
| ① | `try` 块内调用了**守卫类**函数 | 精确名：`guard_write` / `reject_write` / `guard_enabled` / `is_test_env` / `is_production_data_path` / `is_test_like_env` / `is_framework_process` / `is_test_mode` / `reject_reason` / `strict_enabled` |
| ② | 其 `except` 分支**无任何留痕** | body 无 `pass`（单语句）/ 无日志调用 / 无异常对象引用 / 无结果写回 |
| ③ | 守卫调用的**关键字参数名**与真实签名不符 | `inspect.signature` 比对（`**kwargs` 签名豁免） |

★**关键实现细节（踩坑记录）**：

1. **必须不进入嵌套函数/类**：首版用 `ast.walk` 深度遍历，把 `try` 块内**嵌套作用域**的调用也算进来
   → 误报 2 处（`check_package` / `check_tool` 是业务方法，被外层安装 `try` 覆盖）。
   修正：自定义 `_iter_calls_limited()`，遇到 `FunctionDef`/`ClassDef`/`Lambda` 即停止。
2. **「静默」判据要收窄**：首版把「只记日志未含异常对象」也判为静默 → 又误报 2 处
   （`except subprocess.TimeoutExpired:` 分支把错误写进 `result` 并记日志）。
   修正：**只有「无任何留痕」才算静默**（与任务书口径「没有日志记录」一致）。

### 4.1 编号 #1 的特别说明（唯一的安全类守卫）

```python
# 修复前
try:
    from nucleus.data import write_guard as _wg
    if not _wg.is_production_data_path(os.path.abspath(path)):
        return {**_rep, "applied": False, "error": "目标不在生产 data/ 路径下，拒绝写入"}
except Exception:
    pass                       # ★守卫异常被静默吞 → 会继续写
```

该守卫的语义是「**只允许写生产 `data/` 路径**」（防误写他处）。
故障时按 **fail-open** 继续（与 `write_guard` 的「守卫故障不得阻断正常功能」同源），
但**必须留痕** —— 否则与 P2-339 同型（守卫失效而无人知）。

## 七、结论

1. **第50批 P2-339 的同类问题在全库不存在其他实例**（A 类 0 处）—— 说明「参数名错误」是孤例。
2. **真实缺口是「守卫/检查被静默吞」共 5 处**，全部已改为显式留痕（不改变失败语义）。
3. **误报控制是本节最大工作量**：两轮收窄（不进入嵌套作用域 + 静默判据收紧）→ 7 处候选降至 5 处真问题 + 0 残留。
4. 建议：后续新增任何「守卫类调用」，**一律不得用裸 `except: pass` 包裹**；
   本批的 AST 防回归测试已将其固化为门禁。
