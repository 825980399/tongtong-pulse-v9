### A4. 失效实证

- **未找到「同一文件因格式差异被漏判/重复处理」的真实现场实例**：
  `data/patches/patch_history.json` **86 条全部 rel_fs、0 多形态**；`pending_patches.json` **22 条全部 rel_fs、0 冲突**。时间窗内未观察到同源同文件双格式同时进入同一匹配点并产出错误结果。
- **但理论风险面成立（已定位 5 个依赖字符串相等的匹配点）**：A3 表内标 ❌ 的 5 处。**只要写侧格式不稳，这些去处重/匹配必失效**。典型链条：
  `probe_strategy.record_round` 按裸 `file` 聚合成**绝对反斜杠**键 → `PulseCortex:2618` 喂回 →
  `exploration_audit:208` 用**相对正斜杠** issue.file 去 `in focus_files` → **永不命中**（策略聚焦静默失效）。
  （复现：`probe_strategy.json` 键为 `D:\...\organs\brain\X.py`，而审计 issue.file 为 `organs/brain/X.py`。）
- `PatchManager._patch_dedup_key` 仅取裸 file，文档注释（L354-371）自述已多轮补丁，属**已知脆弱点**。

### A5. 结论与修复建议

- **判定：部分属实。** 路径格式混用 = **属实**（多类写法 + 同文件多写法 + 单文件字段级混用）；「去重失效」= **未证实**（无现场实例），但**理论风险面确认存在**。
- **修复点（P2）**：
  1. 将 `SafeEvolutionExecutor._normalize_file_key` 提炼为公共函数（如 `nucleus/utils/paths.py:norm_file_key`）；
  2. 所有账本**写入侧**调用方前置归一化：`PatchManager._patch_dedup_key`、`probe_strategy.record_round`、`exploration_audit._normalize_issue(dedup key)`、`self_inspector` per_file、profile writer；
  3. 读侧匹配点（`exploration_audit:181/208`、`main.py:2905`）在比较前统一 `norm_file_key`。
- **排期**：**P2 / 建议 158 或 159**，与探针链路改造同批（因非凡事故，无需插队）。

### B3. 对外协作说明结论（★核心）

**「缺少公开协作规范」不全面成立——需精确切分两层：**

- **① 贡献者层（对外，已具备 ✅）**：仓库根已有
  `README.md`(7281B，含定位/快速开始/架构/参与指引) · `CONTRIBUTING.md`(1851B，明写"**内部协作的完整规范不随开源包发布，此处为公开子集**"+5 条必过门禁) · `LICENSE`(AGPL-3.0,34657B) · `SECURITY.md`(1716B) · `CHANGELOG.md`(1526B) · `.github/PULL_REQUEST_TEMPLATE.md`。
  → 对外参与路径**完整**。
- **② 团队治理层（内部，存在但未公开）**：`协作模式说明_v1.0.md`、`星轨工作流程规范.md`、`微光入职引导与职责说明书.md`、`烛微_工作模式说明.md`、`协作模式说明`。
  → 存在，**按 CONTRIBUTING 声明有意不随开源包发布**（属内部治理）。

- **结论**：第三方所指「公开协作规范缺失」**部分成立**——**贡献者规范不缺**；缺的是「**六方角色与制衡体系**」的**对外可读版**。是否补，取决于开源定位（若诉求是"吸引外部贡献者理解项目"，则建议补 ①的一节；若诉求是"保护内部工作流"，维持现状合理）。
