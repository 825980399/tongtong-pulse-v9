## 0. 一句话结论

**票面要求的「相邻两拍差分」在施工前拿不出可用读数**（两处观测面缺陷，本刀已修）；

1. **94.2MB/分钟不是稳态速率，是重启后第一小时的斜率**；曲线在 ~11GB 处**饱和**（10:00→12:00 仅 +1.6MB/min）。
2. 今日 GB 级增长的两个大头已指认：`PulseSnapshot.py:1457` 的 `tbl.to_pylist()`（**2.04GB / 3304 万对象**）与 `PulseEyes.py:305` 的相机帧（**887MB / 2018 帧**）。

## 1. 为什么原有的 `tracemalloc_delta_rows` 不可用（已修，见 §5）

### 1.1 基线不按进程代分键 ⇒ 跨代比较全是负数

`_m377_tm_delta` 的语义是「当前快照 vs 上一份基线快照」。改前基线固定叫 `_tm_baseline.snap`，不区分进程代。实测时间线：

| 时刻 | proc_gen | heap_mb | 事件 |
|---|---|---|---|
| 13:37:36 | pid21168@20261029-133452 | 19923.6 | 写下基线 `_tm_baseline.snap` |
| 13:37:53 | 同上 | — | **RSS 连续超限，内存自动重启** |
| 14:08:18 | pid22680@20261029-140818 | 6875.5 | 新进程 |

新进程首次采样会拿**死进程**的快照做 `compare_to`：死进程里 3304 万个对象在新进程里根本不存在 ⇒ 增量为负 ⇒ 全被 `size_diff <= 0` 过滤 ⇒ 报 `no_growth`。
**「没采到」与「真的没涨」同形**（铁律276）——这正是本刀要堵的。

### 1.2 槽位口径：388刀2 改的 12 槽从未生效，且真生效会更糟

- `config.py:6151` 钉着 `M339_MEMORY_PROBE_HOURS = (5, 13)`，而 `_m339_cfg_get` **优先读 config** ⇒ 类默认值被覆盖。
- 388刀2 把类默认改成 `tuple(range(0, 24, 2))`（12 槽）⇒ **生产上一槽没多**，只让默认值骗人。
  这是同型坑的**第 4 次**（383刀4 / 385刀1 / 387刀1 / 388刀2）。
- 而且真生效会更糟：tracemalloc 单次实测 **837s**（3304 万对象做 `statistics("lineno")`）。12 槽 = 每 2 小时卡进程 14 分钟 ⇒ 正是 386刀3 要避免的「治理变增负」。
- 结论：**tracemalloc 重采保持每日 2 槽**；「密度不够」的诉求由 **gc 轻采**（实测 2.1–2.8s，且因为 `_heap_hi` 恒真，实际上**每小时都在跑**）承担。

### 1.3 现有产物里真正"相邻"的是 gc 类型计数

今日 24 份产物中，tracemalloc 只在 13:00 / 13:01 / 13:37 / 13:37 / 13:57 出现（多为手工核验触发），其余全是 `gc_objects`。所以 §2 的逐拍差分用的是 gc 类型计数（每小时），§3 用 tracemalloc 快照做结构确认。

- ⇒ 真正要回答的不是"每分钟漏多少"，而是"**为什么每代都要爬到 11GB 才平**"。

## 3. tracemalloc 结构确认（13:00 槽位，cumulative）

`heap_mb=10955.5`，`image_mb=609.9` ⇒ RSS ≈ 11.5GB；tracemalloc 可见 **3.29GB（29%）**。

| # | 位置 | size | count | 判读 |
|---|---|---|---|---|
| 1 | `PulseSnapshot.py:1457` | **2044.2MB** | **33,044,590** | `tbl.to_pylist()` 全量物化（Parquet 加载） |
| 2 | `PulseEyes.py:305` | **886.9MB** | **2,018** | 相机帧 numpy 数组，**真常驻** |
| 3 | `ast.py:52` | 114.9MB | 1,531,864 | AST 节点（自检器反复 parse） |
| 4 | `__init__.py:136` | 45.6MB | 518,535 | 第三方库对象 |
| 5 | `PulseSnapshot.py:3065` | 33.0MB | 58,726 | 行 → 字段还原字典 |
| 6 | `PulseNode.py:1015` | 25.7MB | 9,417 | 节点对象（池规模，非泄漏） |
| 7 | `self_inspector.py:1063` | 12.9MB | 147,445 | `_parse_methods` 方法表字典 |

**差分行（基线为 05:13，跨 7.7 小时，仅作方向参考）**：

| 位置 | 增量 | 对象增量 |
|---|---|---|
| `PulseSnapshot.py:1457` | +9.9MB | +156,854 |
| `self_inspector.py:1063` | +4.3MB | +48,590 |

### 3.1 3304 万对象是**瞬时峰值**，不是常驻泄漏

同一次采样里，gc 全堆扫描（837s 之后）只数到：

```
function 15216 | tuple 11166 | dict 6678 | list 3286 | ReferenceType 3012
```

**dict 只有 6678 个**。若 3304 万对象真被持有，dict/str 计数应是千万级。⇒ 这些对象在 tracemalloc 快照之后、gc 扫描之前（约 14 分钟内）**被释放了**。

⇒ 机制是**高水位棘轮**：
每次 Parquet 加载瞬时申请 ~2GB Python 对象 → 峰值把进程 RSS 顶高 → `free` 后内存不归还 OS（pymalloc arena / Windows heap 策略）⇒ **RSS 只上不下**。
这解释了「对象数不涨、RSS 照涨」的全部现象，也解释了曲线上限 ~11GB。

**388刀1 正是对症的修复**（`to_pylist()` 全量 → `to_batches(20000)` 逐批），但 14:08 重启后 **tracemalloc 没再跑过一槽**（槽位 5/13），所以**修复效果至今未被证实**——这是本刀最该说清的一句话。

### 3.2 887MB 帧是**真常驻**，持有者已指认

`PulseEyes.py:305` 是 `ret, frame = self._camera_cap.read()`，count=2018 ≈ 每帧 ~450KB。

持有链（代码走读 + 数量级吻合）：

```
PulseEyes._stream_loop → capture_frame()  # 分配点 305
  → pulse_core.emit(payload={"raw_data": frame_data, ...})
  → info_field.publish(pulse)
  → InfoField.publish 第 4 步：
         self._history.append({... "payload": dict(pulse.get("payload", {}))})
                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 浅拷贝，raw_data 原样带走
  → InfoField._history = deque(maxlen=config.PULSE["info_field_max_history"] = 2000)
```

**2018 ≈ 2000（history 上限）+ 18（在途队列）**，数量级完全吻合 ⇒ 就是它。
389刀2 修（历史归档时省略重负载，live pulse 不受影响）。

已知两项都解释不了它：
- **帧**：`deque(maxlen=2000)` 是**有界**的，稳态不再增长（刀2 只降水位，不降斜率）。

**最可能的落点（假设，未证实）**：tracemalloc 只看得到 Python 分配器 + numpy（numpy 有 `PyTraceMalloc_Track`）；**pyarrow 的 C++ arena 不在其中**。
证据：tracemalloc 可见 3.29GB，RSS ≈ 11.5GB，**8GB 落在可见面之外**；而 13:37 那个进程 19.9GB RSS 时，tracemalloc 累计只记到 ~3MB（`cumulative` 口径下 164 秒只长出 3MB）——典型的「大块内存在 C++ 侧」。

1. **04:00–05:30**：确认 `data/reports/memory/_tm_baseline_<proc_gen>.snap` 生成（分代分键生效）。
2. **13:00 槽位**：看新代码下 `PulseSnapshot.py:1457` 是否从 2044MB 掉到 GB 以下（**388刀1 的判据**）。
3. **13:00 的另一半**：看 `PulseEyes.py:305` 是否 <200MB（**刀2 的判据**）。
4. **曲线形状**：看 heap 是否在更低的位置（<6GB）饱和；若仍爬到 11GB，则 §4 的 pyarrow 假设成立，下一批该查 `_m81_load_parquet_unified` / `_m68_parquet_dir` 的读取放大。
