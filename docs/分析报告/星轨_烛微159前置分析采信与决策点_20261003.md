## 三、★ 烛微本次最重要的发现（影响 159 派工排序）

**票4 = 记忆可访问性缺陷（升 P1）**：`_cold_evicted` 仅 3 处运行期 `.add()`、**从不从 `_cold_index` 重建**；所有召回入口（`POOL:703/1385/2795`）都以它为门 → **5530 个冷节点"数据在盘、索引在 cold.index.json、但运行期永远取不回"**。12 次启动恒"0 按需召回"完整解释。

**定性**：这不是性能问题（慢），是结构性问题（取不回）。**与票6"连续性"直接挂钩**——连续性当前**不成立**且有量化口径（重启前后可访问集差额 K>0）。

**施工排序建议**：票4（P1，单点修复）→ 票3（P2，限流联动）→ 票1（P1，写侧归一）→ 其余。票4/票3 须同批，票4 先行。

## 四、须小林拍板的决策点

### A. 票2：内存数据不可信时的第四态（产品判断，非技术判断）
- 背景：`get_memory_usage()` 异常吞掉返回 0.0 → 阈值判定全 False → 告警静默。修复走 `source_ok` 标志，但**遇不可信数据时负载等级取什么**？
- 选项 1：**`unknown` 第四态**（诚实呈现，不误判不误警；代价=可能漏掉真危险）
- 选项 2：**保守判 `heavy`**（fail-safe，宁紧勿松；代价=数据源故障期可能误报高压）
- 星轨建议：**unknown 第四态**（系统自我观察应诚实，且告警链会产出独立 WARNING「数据源不可信」作为兜底，不依赖 heavy 误判）。

### B. 票5：853.9MB 清理前确认离线策略
- 硬前置：目标运行环境（比赛机/超算镜像）若**离线**，删除 jina/MiniLM 后需重新获取 853.9MB。
- 待确认：SCNet 超算 / 比赛机是否联网可达（ModelScope / hf-mirror 三镜像回退）。
- 星轨建议：SCNet 主路径为「文件直传」→ 超算节点大概率**可联网拉模型**；待 158 收口后与 T-超算镜像重跑-1 一并验证网络策略再动手，**不急于本批**。

### C. 票3 降级确认
- 建议：**降级为 P3 或并入票4 同批**（收益 MB 级 + 可调域卡死）。星轨倾向：**并入票4 同批、票4 先行**，不单独立项。
