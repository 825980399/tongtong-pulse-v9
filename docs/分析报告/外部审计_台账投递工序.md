# 外部审计报告 → 台账条目 · 固定投递工序（SOP）

> 建立：路灯（第96批 T-96e）
> 依据：烛微第1期审计 N10 —— 「三方审计最重要的输入没有进入两方工作流的事实清单。
>       这是**机制问题不是态度问题**」
> 适用：任何外部/第三方审计报告（烛微系列、G-agent 系列等）

---

## 1. 为什么要有这道工序

台账（`docs/分析报告/技术债务台账_代码实查_*.csv`）是两方工作流（星轨 ⇄ 路灯）的**唯一事实清单**：
任务书从台账取条目、交付报告回写台账状态。若外部审计的发现不进台账，则：

- 外部报告会随时间/目录调整而失传；
- 批次任务书取不到这些条目 ⇒ **自然不会被排期**；
- 下次审计只能重复发现同一批问题。

烛微 09-18 六项 P0 就是这么丢的。

## 2. 投递工序（4 步）

| 步 | 动作 | 时限 | 判据 |
|---|---|---|---|
| 1 | 审计报告出稿 → 提取全部发现条目（含编号、P 级、复现方法） | 出稿后 24h 内 | 条目清单落成文件 |
| 2 | 每条追加一行进台账 CSV（12 列，格式见 §4） | 同批 | CSV 行数 +N |
| 3 | 建立 **P 级映射表**（外部编号 ↔ 台账 D 编号），写在本文 §5 | 同批 | 映射表条目数与报告发现数一致 |
| 4 | 由**下一个批次**的任务书从台账取条目排期；交付报告回写「实查状态」 | 下一批 | 台账对应行的「实查状态」列不再是「待投递」 |

**验收判据（可机检）**：台账中出现该报告的期号（如「烛微第1期」出现在「首次章节」列）。

## 3. ★投递纪律（来自本批教训）

1. **「实查状态」列必须由执行方实填，不得照抄报告的声称。**
   本批投递时核对发现：烛微 N2 给出的两条证据路径（目标符号 0 次、与备份逐字节相同）
   **均无法复现**，结论虽成立但需换成可靠判据才能定位到真正的 2 条。
2. **不得重复投递**：追加前先检查台账是否已有该期号的行；同发现重复挂账会污染优先级排序。
3. **保留外部编号**：台账行的「文档声称状态」列必须写「{期号} {外部编号}【{P级}】」，
   便于双向追溯。
4. **一行一发现**：多个子项（如 N1 的①②③④）合并为一行，在「原文关键句」里展开，
   避免同一问题拆成多行导致「看起来很多」。

## 4. 台账 CSV 列格式

```
id, 优先级, 模块, 问题简述, 首次章节, 最近章节,
文档声称状态, 原文关键句, 实查状态, 代码证据, 置信度, 处置建议
```

- `首次章节` / `最近章节`：外部审计填**期号**（如「烛微第1期」），后续批次处理时更新 `最近章节`
- `实查状态`：执行方实填（如「本批 T-96b 已处置」/「未动（待立项）」/「重复挂账→Dxxx」）
- `置信度`：`高` / `中` / `低`；外部报告**已附复现脚本**的可标 `高`
- `处置建议`：末尾必须写 `★映射：{期号} {外部编号} ↔ 台账 {D编号}`
