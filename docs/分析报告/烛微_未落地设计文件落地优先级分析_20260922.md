## 5. Task-5 · Top5 具体落地方案（给路灯的施工卡）

### 5.1 Parquet 三键收口（0.5 批）
**核心点**：`PARQUET_COMPRESSION/PARQUET_SHARD_BY_EVOL_LEVEL/PARQUET_BATCH_SIZE`（`config.py:4759-4761`）定义完整、框架内 0 读取；写盘 4 处硬编码 `compression="snappy"`（今晚实锤：`IndexStore.py:92`、`PulseNodePool.py:2451/2922`、`PulseSnapshot.py:2628`）。
**改法**：4 处字面量改读 config 键（带默认 "snappy" 兜底）；`PARTITION_BY` 若与 :2627 硬编码分片逻辑同型则一并接线。
**验收**：①三键各≥1 个生产读取点（`wo4_detect_writeonly.py` 复跑死键表 20→17）；②改键值→重存快照→parquet 元数据压缩算法变化（pyarrow `read_metadata()` 可证，非日志口径）；③回滚=还原 4 字面量。
**坑点**：写盘方有 3 个文件（含冷层 `PulseNodePool:2922`），只改快照处会留半死键——**必须 4 处全接**。

### 5.2 KAL 迁移收口（1~1.5 批）
**核心点**：三开关全 True、肾/肝/胃各 1 点真消费（`PulseKidney.py:740` 等），但同三器官仍直连 `node_pool.` 37/12/7 处（21:0x 复测原样）——同一数据两条访问路径并存，正是"通道归因"类 bug 温床（第 3 期已吃过一次）。
**改法**：按器官分 3 个子批机械改 `kal.get_nodes_batch/get_level` 等对应入口；每子批改完跑该器官既有测试+`tools/ci/audit_subscriptions.py`（107 批新产物）类静态哨兵防漏。
**验收**：①`grep -c "node_pool\." 肝/肾/胃` → 0（或白名单注记）；②改造前后节点查询结果等价（对偶测试：同参调 KAL 与直连比对 id 集合）；③运行日志无新增 KAL miss/回退告警。
**坑点**：`PulseNodePool.py:3479` 有本地同名 `query()` 包装，改 KAL 入口时勿把包装层当直连误删；`ENABLE_KAL_MIGRATION=True` 的"迁移完成"判定字段本身要有读取点（否则又造一个只写键）。

### 5.3 自认知报告消费机制·闭环补半（1.5~2 批）
**核心点**：总线已跑（09:37:46 实证 4 消费者注册），缺的是设计承诺的后半：**5 消费者类、PriorityRouter、ConsumeResult、resolution_rate/闭环回写全 prod=0**。今日已实锤同款病灶：`_survival_state` 15 写 0 读、`silence_details` 收了即 `# noqa: F841` 丢弃、Cortex 路由表查而不用。
**改法**：①先做"消费存在性机检"（与 106b 门禁合流，别造第二套）；②选 1 个真实消费者（建议 self_cognition→进化环：resolution_rate 由"报告问题 7 天后是否仍在"计算，数据源现成）；③ConsumeResult/PriorityRouter 按设计落最小实现，**只落会被读的那半**，其余键不落（防新增死键）。
**验收**：①resolution_rate 有生产读取点且进周报面板（`health_ui` 在跑）；②连续 2 批出现"报告→消费→状态翻转"事件对（日志机检）；③死订阅清零复查：`audit_subscriptions` 报告 0 死订阅。
**坑点**：本设计是"只写不读"总根因正解——**落地过程自身必须示范闭环**：每加一键当天验证读取点，宁少勿全。

### 5.4 RequestDeduplicator 通电（1 批含观察）
**核心点**：实现体+唯一消费方（`PulseLung.py:1202`）在位，开关 `ENABLE_REQUEST_DEDUP` 走 `os.environ.get(...,"0")` **默认关**，`config_override.json` 无该键——即"永远关"。设计 v1.0 契约三符号已改接口（文档自述）。
**改法**：①env 开关升格 config.py 真键（保持 env 覆盖兼容）；②灰度：先对肺检索类请求开白名单，观测 `dedup_hit` 计数；③若 24h 内 dedup_hit>0 且无"误合"投诉信号，默认 True。
**验收**：①生产日志出现去重命中事件（否则通道白开）；②同参并发请求 LLM 后端实收数下降（`LLMCallRecorder` 现成对账）；③回滚=一键 False。
**坑点**：`acquire_or_join` 的 join 语义要配超时（参考 T5 教训：403 一次阻塞 11s）；去重键若含时间参数会永不去重——先跑离线重放（traces 里有现成 `calls_*.jsonl`）。

### 5.5 大模型调用精简·首环 batch_merge（1.5~2 批）
**核心点**：观测面已齐（prompt_version/trace_id/LLMCallRecorder），削减面 `ENABLE_LLM_CALL_BATCH_MERGE`+batch_merge **prod=0**（今晚复测）。它是 LLM 依赖链（→语义缓存 L2→L3 精简器）第一环；本周两大痛点都挂它：T2 补丁质量（46.94% 失败重放=重复烧 LLM）、T4 吞吐触顶。
**改法**：①先用 recorder 离线量化"可合并调用占比"（同时段同 provider 相似 prompt），无 15%+ 收益则整环降级——**这一步就是验收门 0**；②落最小合并器（同窗口同模板批量拼接送检、拆响应回填），挂 `LLMCallRecorder` 对账；③开关默认 False，灰度同 5.4。
**验收**：①门 0 报告存档（占比数字）；②开启后每小时 LLM 调用数下降 ≥ 预估的 50%（保守）；③回填正确性对偶测试（合并响应拆回单条 == 单独调用结果结构）。
**坑点**：批量拆回失败会污染 T2 的补丁验证链——合并器必须"失败即降级为单发"，不可静默丢响应（今日胃 JSON 假救回的教训：宁可失败，不可假成功）。
