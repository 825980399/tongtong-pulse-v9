## 二、刀1 · S1蒸馏断链修复（根因定位＋修复）

### 根因（决定性）
`ReasoningExperienceIndexer` 的补救蒸馏逻辑（`:354` `record_remediation_distilled`、
`:417` 回执路径的 `record_remediation_returned→distilled`）**全部**被
`if self._double_write_enabled:` 门控。而 `_double_write_enabled` 由
`main.py:460` 设定：

```python
_rei_cfg = getattr(config, "REASONING_EXPERIENCE_INDEX_CONFIG", {}) or {}   # main.py:446
_rei.set_enabled(bool(_rei_cfg.get("enable_reasoning_double_write", False))) # main.py:460
```

但 `enable_reasoning_double_write` 实际位于 **config 顶层**（`config.py:1104`，值 `True`），
**不在** `REASONING_EXPERIENCE_INDEX_CONFIG` 子节内。子节无该键 → `.get(..., False)` 恒返
`False` → `_double_write_enabled=False` → 蒸馏整段永不执行。

这完美解释 248批实测：`remediation` 块 `attempt=179 / success=165 / distilled=0`
——`success` 由 PulseCortex 直调 metrics 模块函数 `record_remediation_success` 撞计数（:1466），
而真正含蒸馏逻辑的 indexer 实例方法因门控关闭从未触发蒸馏。

> 注：indexer `:352` 注释曾称"main.py 已 set_enabled(True) 修复根因"——该注释**误导**，
> 实际因读错 config 路径从未启用。本批已通过正确读取落地真正的修复。

### 修复
`main.py:460` 改为 fallback 读顶层 config 键：
```python
_rei.set_enabled(bool(_rei_cfg.get(
    "enable_reasoning_double_write",
    getattr(config, "enable_reasoning_double_write", False))))
```
config 顶层键 `True` 现可正确生效 → 双写启用 → 补救成功真正蒸馏为 L2 节点＋`distilled` 计数+1。
此改动**零配置变更**（不碰 config.py），纯代码修复。

### 验证
隔离测试 `test_indexer_distills_when_double_write_enabled`：构造 enabled indexer，
调用 `record_remediation_success("q","a")` → 蒸馏计数 `distilled` +1，且旁路哨兵
`success==distilled`（缺口 0，证明无未蒸馏的补救成功）。反向测试 `..._disabled` 确认
门控关闭时零蒸馏（守卫不破）。

## 三、刀2 · S2指标键入运行时（根因定位＋修复）

### 根因
241批在 `LLMDependencyMetrics._blank_counters()` 新增 `remediation.returned/missed`
键，但**运行中进程若在 241 之前启动**，其 `self._counters["remediation"]` 仅含旧三键；
`_load()`（:491）用 `setdefault(g,{}).update(...)` 合并持久化值——虽能保留新键，
却无法为"启动期即缺键"的老进程补键，导致线上 `llm_dependency.json` 长期缺键。

### 修复
`_load()` 末尾新增**防御性合并**：遍历 `_blank_counters()`，对每组的每个键
`self._counters[g].setdefault(k, default)`。无论加载态多旧，新键始终存在且默认 0。
此修法对任意未来新增键同样免疫。

### 验证
隔离测试：
- `test_load_merges_new_remediation_keys`：写旧三键持久化态 → 重载后
  `returned/missed` 存在且 ==0。
- `test_returned_missed_count_and_persist`：`record_remediation_returned(2)` /
  `record_remediation_missed(3)` → 计数正确，落盘重读仍保持。

## 四、刀3 · 批卷人SOP（实测前提与任务书不符）

### 4.1 任务书前提失实（已核实）
任务书称"45个待审补丁全停在C级灰带（不自动、也不拒）"。实测 `data/patches/pending_patches.json`：

| 维度 | 实测 |
|------|------|
| 总数 | 45，`applied=False` 全部 |
| status | `verified`:23 · `runtime_verified`:16 · `runtime_failed`:6 |
| aesthetic_grade | A/B/S（**无 C 级**） |
| risk_level | **全部"低"** |
| source | 全部 `llm` |

即：45 条均为"已验证/低危"但**从未被应用**；其中 6 条 `runtime_failed` 本就不应应用。
任务书的"C级灰带"表述不准确——真实状态是"**已验证待应用**"，缺的是批卷人执行应用，
而非卡在某个中间评级。

### 4.2 批卷人SOP（已建）
```
批卷SOP（路灯作为批卷人）：
1. 每日审 3-5 个（status∈{verified, runtime_verified} 且 risk_level=低 且 applied=False）补丁；
2. 应用补丁：经 SafeEvolutionExecutor 带备份+验证写入目标文件，置 applied=True；
3. 验证补丁：应用后跑对应模块隔离测试 + 门禁链，确认零回归；
4. 排除 runtime_failed / 高风险的补丁，单独上报星轨裁决。
```

### 4.3 为何未自动应用（降级申报）
- **前提失实**：任务书验收"45→40"隐含"C级灰带待批卷"，但实测为"已验证待应用"，
  性质不同，需星轨确认应用范围（全部39已验证？仅示例5条？）。
- **无安全一键应用API**：`PatchManager` 仅 `_m94_apply_pending_aging`（老化剔除），
  **无**"apply pending patch"公共入口。应用须自建"读 modified_code→SafeEvolutionExecutor
  带备份写入→置 applied=True"路径＝对 PulseTouch.py 等**生产器官代码**的实质性改写，
  属破坏性操作，按纪律须星轨裁决后执行。
- **保护**：未对任何生产文件做未裁决的批量改写；本报告仅交付 SOP 与状态举证。

**待星轨裁决**：是否授权我据此 SOP 应用 5 条（或 39 条已验证）补丁？授权后我会
逐条备份+验证+门禁，并申报每步结果。
