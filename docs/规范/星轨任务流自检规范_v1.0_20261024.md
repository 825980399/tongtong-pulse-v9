## 二、问题诊断（按严重度）

### A 类 · 体系性缺陷（缺装置，不是某次失误）

**A1 跨批遗留无权威跟踪，被静默遗忘（最严重）**
- 证据：354 明确写"__main__ 11 处另立批/快照 gzip/HHI 观察"，355/356 没有一处回头闭合；__main__ 期间反增到 54 处。直到**路灯 356 自查才补建**《跨批遗留清单》——这本是星轨进度管理职责，被路灯补位。
- 根因：星轨每批只盯"最新批次刀序"，没有一个跨批强制回扫的动作。
- 优化：**每批排任务书前必扫《跨批遗留清单》，对每条遗留强制三选一**（本批处理 / 显式后置到指定批 + 理由 / 关闭并留证），不允许无限期挂着。

**A2 登记册状态机不同步（排了不核销、判了不推进）**
- 证据：360 已排 def 名归一(P0)、负样本回灌(P0)、DJ4-01/02、LogAnalyzer、GPU、tool 通道等，但登记册仍停在"待裁决/待排期"；待裁决 6 条 P0 里有已排期的。
- 根因：星轨把"写任务书"和"更新登记册"当成两件事，常常只做前者。
- 优化：**排发动作原子化——写任务书、登记册状态推进（到期批次列填实际批）、总账更新、遗留清单更新，四步同一轮做完**；改登记册基线走 `[ci-gate-change]` 独立 commit。

**A3 审计产物无版本（流程设计缺陷，路灯 C1 已先发现）**
- 证据：裁决清单、键迁移映射、对账清单全在 gitignore 的 data/ 下，不可逆决策无历史。
- 优化：任务书标准条款固定写入——"凡裁决/迁移/对账类产物，必须同时落一份 git 跟踪副本到 `docs/路灯与星轨对话/交付报告/证据件/`"。

### B 类 · 任务书纪律破洞

**B1 任务书施工中途被改写（D1）**
- 证据：354 刀6/7、356 v1.1/v1.2 施工中追加，354 刀6/7 推倒重做。
- 根因：星轨在路灯施工期间发现新问题就直接改原书。
- 优化：**任务书一旦开工即冻结**。新发现一律进下一批；确需本批追补的，出独立"追补书"，注明"在原批某刀之后、不得推翻已完成刀"，并经小林确认再发。

**B2 任务书落盘缺口 / 合并后原版未清**
- 证据：346–351 六批无任务书；352 合并后原版仍在。
- 优化：① 凡派发必有落盘任务书，不允许只在对话里口头派；② 一个批号只保留一个有效书，合并后原版立即移入 `docs/路灯与星轨对话/任务书/归档/`（不删）。

**B3 批号无统一规则，施工/前置/洞鉴撞号**
- 证据：357–359 被烛微前置占用，施工跳到 360；洞鉴曾用"357 刀序"与烛微 357 撞车（已纠偏）；历史多处跳号。
- 优化：**批号分段**（见第三节看板），派号前先查总账"批次占用看板"。

### C 类 · 任务书质量（判据/锚点不严谨，路灯替我兜底）

**C1 验收判据口径不严谨**（路灯 A1/A2/A3）：扫全仓未排 docstring 致假 FAIL；测试锁易变生产值；批次号手打错误。
- 优化：任务书"扫描/计数"类判据默认限定生产面（config/main/organs/nucleus，排除 tests/tmp/data/.bak）并排 docstring；测试只守不变量不锁总行数；留痕串/批次号从真实产物反向取。

**C2 任务书锚点漂移**（路灯 D2）：星轨给的行号/前提过时（353 刀1、354 刀2），靠路灯 T0 实测纠偏。
- 优化：**星轨写任务书前先自己做 T0 核对 HEAD 行号/现状**，不把过时锚点丢给路灯；确实无法预先核对的，在任务书里标注"行号以开工 T0 为准"。

### D 类 · 裁决与验证

**D1 待裁决积压、靠小林反复催**：26 条待裁决含 6 条 P0，没有固定清账节奏。
- 优化：**每批排发前固定做一次"待裁决清单 → 白话 + 建议 → 集中请小林拍板"**；P0 不跨批积压。

**D2 星轨自查自裁闭环占比 40%**：高风险结论缺少外部复核。
- 优化：涉及架构方向、停机操作、付费/数据安全的结论，强制抽样送烛微/洞鉴独立复核，星轨不自行结案。

**D3 完成态三态混用**：static_verified / fixed / live verified 容易被说成"已闭环"。
- 优化：总账与任务书统一三态——static_verified（静态校验）、fixed（对账回写）、live verified（运行时真触发），不提前宣称闭环；对账式破零与 live 自然闭环分开表述。

**D4 陈年 P2/P3 债务只增不清理**：37 条待排期里 336–342 批老账长期挂着。
- 优化：每批开工前对"待排期超过 5 批"的条目做一次"清/留/并"决策，显式写明去向，不让债务静默沉淀。

## 三、固化机制：星轨每动作自检清单

### ① 排发任务书（前）
- [ ] 查总账"批次占用看板"，取未占用批号（施工/前置/洞鉴分段）
- [ ] 扫《跨批遗留清单》，每条遗留给三选一去向
- [ ] 扫登记册"待裁决/待排期"，把本批要排的项在脑中列清
- [ ] 待裁决项（尤其 P0）先给小林白话+建议，得到授权再排
- [ ] 逐刀核对 HEAD 行号/开关实测值（T0），不写过时锚点
- [ ] 扫描/计数判据限生产面、排 docstring；测试不锁易变值
- [ ] 涉及停机/数据文件的刀，醒目标注并提前告知小林
- [ ] 任务书含"审计产物落 git 副本"标准条款

### ② 排发任务书（后，同一轮做完）
- [ ] 登记册状态推进 + 到期批次列填实际批（基线改动 `[ci-gate-change]` 独立 commit）
- [ ] 总账追加（批次号/刀序/停机提示/状态/看板）
- [ ] 一个批号只留一个有效书，原版/旧版移入归档
- [ ] 回复小林只给"路径：docs\…"，不贴全文；停机项单独提醒

### ③ 收到交付报告（核验）
- [ ] 逐刀核对"改动文件:行号/证据/测试"，不看报告自称，独立回读
- [ ] 完成态按 static_verified / fixed / live verified 三态标注
- [ ] 核销登记册（已交付→已结案）；没做完的不得标结案
- [ ] 路灯/烛微/洞鉴报告里的"遗留"追加进《跨批遗留清单》
- [ ] 高风险/架构结论抽样送外部复核
- [ ] 更新总账 + 批次看板

### ④ 批号分段规则
- **路灯施工**：主力连续号（当前 360 起）
- **烛微前置**：紧随施工号的独立号（当前 361 起），不与施工同号
- **洞鉴**：用"季"编号（第四季/第五季…），不占用三位施工批
- 任一角色派号前都在总账看板登记"批号/角色/主题/状态/是否停机"

### ⑤ 任务书冻结纪律
- 开工即冻结；中途新发现 → 下一批或独立追补书（不推翻已完成刀）
- 确需变更，先告知小林，再发 v1.x，且任务书头部写"变更点 + 影响刀"

## 六、实战补丁（2026-10-24 当日自省后追加，v1.1）

**E1 施工方在工避让（动文件前先看 git status）**
- 任何要写台账/登记册/基线/共享文件的动作，先 `git status` 看路灯/烛微是否正在改同一文件（施工中常见未提交的 `M tools/ci/baselines/*` 与新建源码）。
- 若施工方正在改登记册/CI 基线（交付时会追加条目），星轨的"登记册核销"**让到该批交付核验轮统一做**，不中途写、不覆盖、不抢锁；这与"排发即核销"不矛盾——排期映射先记在总账看板，文件级核销在不撞车的最近一轮落。
- 只读分析不受影响，可照常进行。

**E2 排发即核销的最小动作（不依赖大改登记册）**
- 排发当下：先在总账看板写"批号↔登记册 ID 映射"（轻量、无冲突）；
- 文件级状态推进（待裁决→已裁决待排期、到期批次）集中在：①施工方未在改该文件时；或②该批交付核验轮。
- 改登记册/基线一律 `[ci-gate-change]` 独立 commit，改前备份、改后校验记录数=期望值。

**E3 第三方结论与小林口述冲突时，定"悬案"不臆断**
- 当审计方结论（如烛微：v4-pro 来自框架外同 key 消费者）与小林现场情况（新 key 昨天才建、只加载环境变量、未给其他工具）冲突时，**不得直接采信任一方**，立为"悬案"并给双向验证路径：
  - 框架内：看路灯埋点 paid_api_trace（改动后需重启生效）；
  - 框架外：平台用量明细按时间/IP/UA/key 核对，检查 key 作用域（User 级环境变量=所有新进程可读，含 Trae/VSCode/其他代理 runtime）；
  - 时间线对齐：key 创建时刻、首次 v4-pro 消耗时刻、当时在跑的进程。
- 结论以"下一周期实测/平台数据"为准，不靠静态推断下终论。

**E4 排发动作里的"先确认活体"**
- 排施工/前置前先确认曈曈 pid、路灯/烛微/洞鉴在工状态（git status + 任务书/报告目录 + 最新 commit），避免给已在工的角色重复派、或给已交付的批次再派。
- 看批次进度以总账"批次与角色占用看板"为权威源，不以对话记忆为准。

**E5 提交前隔离暂存区（2026-10-25 误带事故后追加）**
- `git commit` 不带路径参数会提交**整个暂存区**；路灯/烛微在工 `git add` 过的探针件、源码件会被星轨 docs 笔连带入库，违反"分笔不含他方件"纪律。
- 星轨每笔提交二选一：①先 `git restore --staged -- <他方暂存件>` 退回路灯件（工作区保留不动），只 `git add` 本笔件后裸 commit；②commit 命令末尾带 `-- <本笔路径清单>` 路径限定（双保险）。
- 提交前必跑 `git diff --cached --name-only` 核对暂存清单与本笔件一一对应；提交后 `git show --stat HEAD` 复核入库件，误带立即 `reset --soft HEAD~1` 拆分重提，不带着他方件收尾。
- 路径比较统一转正斜杠（`replace("\\", "/")`），避免反斜杠/正斜杠不等误判暂存清单。

## 七、上下文窗口治理与交接 SOP（窗口变重必做）

1. **窗口过重时主动交接**：当对话历史明显变长、涉及多批次多角色，星轨应主动建议小林开新窗口，并先产出一份《新窗口对接提示词》，不拖到上下文丢失。
2. **交接三件套**（缺一不可）：
   - 一段**可直接复制的精简提示词**（自举式：含角色、铁律、当前批次、让新窗口先读的文件指针）；
   - 总账末尾"批次与角色占用看板"（权威状态）；
   - 本规范文件 + 跨批遗留清单。
3. **新窗口星轨开局动作**（按序）：读总账末尾看板 → 读本规范 → 读跨批遗留清单 → git status 确认在工 → 读最新一批任务书/在途报告 → 用自己的话向小林复述当前状态与待办，确认无误再动手。
4. 交接文档**只放指针和结论，不复制大段源码/报告全文**，让新窗口按需读文件，避免把上下文又灌满。
5. 交接当轮仍需：更新总账、提交 git，保证新窗口从干净的仓库状态接管。

## 八、工具沉淀与流程提速（2026-10-25 v1.2 · Q1–Q3 小林裁决批准）

> 依据《星轨任务流耗时复盘与提速方案_v1.0_20261025.md》归因：3.1 工具零沉淀为主因、3.2 先成文后返工、3.3 校验链分散、3.4 大结果件灌爆上下文、3.5 轮次过细。本节把复盘方案固化为规范动作；第五节原有七项指标保留不变，8.4 为新增提速指标，366 起逐批核对。

### 8.1 自用工具目录 `tools/xingrui/`（Q1 批准）

- 该目录只服务星轨的台账只读、门禁复跑、文档体例校验、git 隔离提交与排发轮公共段编排；
- 边界：**不被生产代码 import、不进入 tools/ci 门禁链、不写 data/、不改 config.py、不触碰 nucleus/organs/main、不占用路灯施工刀面**；
- 生产编码唯一执行体仍是路灯；本目录脚本纯标准库，只读或编排，批次特异的台账行修改不在通用脚本内完成。

### 8.2 五件自用工具与调用口径（Q2 批准，星轨自行落盘与维护）

| 工具 | 用途 | 标准调用 | 替代的一次性探针 |

| doc_style.py | BOM/行尾/表格列数/行数/字节数体例校验 | `python tools/xingrui/doc_style.py --file <路径> [--bom required/absent/any] [--eol lf/crlf/any] [--expect-rows N]` | csv_style/final_check 体例探针 |
| isolate_commit.py | 暂存区隔离核对＋路径限定提交（E5 落地） | `status` / `check --files ...` / `commit --message "..." --files ...` | 手工 status/add/diff cached/show stat 来回 |
| freeze_round.py | 排发轮公共段编排：改前快照→备份→门禁→体例→终检报告 | `python tools/xingrui/freeze_round.py --batch N --backup <件...> --docs <件...> [--md-bom required] [--md-eol lf] [--out <结果件>] [--dry-run]` | 冻结/核验轮分散收尾脚本 |

- 口径纪律：工具只读/编排，**不做台账状态推进、不刷新基线、不执行 git commit**；若工具判据与 tools/ci 实测口径漂移，以 CI 门禁为准，先修工具再使用；
- 体例默认值：总账/规范/报告 md＝BOM required＋纯 LF；任务书正式书/草案＝BOM absent＋纯 LF；CSV 由三门禁主责，工具仅辅助查看。

### 8.3 流程提速口径（Q3 批准，轮次合并；施工方避让纪律不变）

1. **T0 前置合并（对应 3.2）**：写草案前一次做完 HEAD 锚点/现状实测、台账快照、体例基线；成文后只做终检，不再回炉返工锚点、字段真名、BOM、表格列数。
2. **同轮连续拍板台账一遍写（对应 3.5）**：同一轮内小林连续裁决多组时，登记册、总账、遗留清单同轮一遍落完，基线重锚一次；E1 施工方在工避让纪律不变，撞车仍让到交付核验轮。
3. **日志聚合截断（对应 3.4）**：日志探针默认只给计数、分布与前 50 行异常样本；全量日志落盘仅限需要逐行归因的场景，当轮结束即清场，不跨批堆积 2 MB 以上大结果件。
4. **收尾清场与提前交接（对应 3.4/第七节）**：每轮结束清理本会话临时探针/结果件（workspace 内），证据件入库 docs；长窗口提前按第七节 SOP 交接一页快照，不拖到上下文丢失。
